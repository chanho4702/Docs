## 요약

DMOVE는 고객사 **폐쇄망**에 설치된다. 제품이 본사 서버에 "이 고객 유료 맞나?"를 물어볼 수 없다.
그래서 **우리가 서명한 라이선스 파일(`.lic`)을 고객이 제품에 등록**하고, 제품은 자기 안에 박힌
공개키로 그 서명을 검증한다. 인터넷 연결이 전혀 필요 없다.

| | |
|---|---|
| 형식 | `.lic` 파일 (RS256 서명된 JWT, 약 800자) |
| 기간 | **발급 시 정해져 키에 서명된다** (시작일 지정 가능) |
| 만료 후 | 즉시 차단이 아니라 **4단계로 축소** |
| 발급 | 사내 발급기(`moveseye-license-issuer`)에서 우리가 발급 |

---

## 1. 왜 이 방식인가

일반적인 SaaS는 고객 서버가 본사에 실시간으로 문의한다. 해지도 본사 DB만 고치면 된다.

**우리는 불가능하다.** 고객사 서버는 인터넷이 없는 폐쇄망에 있다.

그래서 방향을 뒤집었다 — **증명서에 미리 다 적어두고, 위조만 못 하게 만든다.**

```
우리    개인키로 서명   →   .lic 파일   →   고객
고객사  제품에 내장된 공개키로 검증  →  통과하면 그 내용대로 문을 연다
```

인감도장이 찍힌 계약서와 같다. 계약서를 보여주면 되지, 볼 때마다 인감증명원에 전화하지 않는다.

- **개인키**(서명하는 열쇠) — 사내 발급기에만 있다. 이것이 곧 발급 권한이다.
- **공개키**(검증하는 열쇠) — 제품 소스에 들어 있다. 검증만 되고 서명은 안 된다.

고객이 제품을 뜯어봐도 키를 새로 만들 수 없는 이유다.

## 2. 라이선스 파일 안에 무엇이 들어 있나

`.lic`을 열면 긴 문자열이 보이지만 **암호화된 것이 아니다.** 누구나 내용을 볼 수 있다.

```
고객사명          OO병원
등급              PREMIUM
추가 기능         GPU_MONITORING
시작일            2026-09-01
만료일            2027-09-01
유예              30일
등록 기한         발급 후 7일
고유번호(jti)     f6372257-fba5-4586-...
```

**내용은 숨기지 않는다. 대신 고칠 수 없게 한다.**
고객이 만료일을 `2099-01-01`로 바꾸면 뒤에 붙은 서명이 맞지 않아 제품이 즉시 거부한다.

### 🔴 유효기간이 키에 들어 있다

시작일과 만료일이 발급 시점에 확정돼 **서명 아래 놓인다.** 고객사 DB를 고쳐도 기간은 바뀌지 않는다.

**계약~설치 지연은 시작일로 흡수한다.** 계약은 3월인데 현장 설치가 5월로 밀리는 일이 온프레미스에서는
흔하다. 그럴 때는 발급할 때 **시작일을 미래로 잡는다** — 만료일이 그 날짜부터 계산된다.
예상보다 더 밀리면 재발급하면 된다(우리가 클릭 몇 번 하는 일이라 비용이 없다).

> 2026-08-12 변경. 이전에는 "며칠짜리"만 키에 담고 고객이 등록하는 순간 만료일을 계산했다.
> 지연 문제는 그걸로 해결됐지만, 만료일이 고객사 DB에만 존재하게 되어 **UPDATE 한 줄로 기간을
> 무한 연장**할 수 있었다. 기간 자체가 상품인 제품이라 그 통로를 닫았다.

### 등록 기한(기본 7일)은 별개다

"발급 후 7일 안에 등록하라"는 조건이다. 키가 유통되다 한참 뒤에 쓰이는 것을 막는다.
현장 설치가 밀릴 것이 예상되면 발급할 때 늘려서 낸다.

> ⚠️ 등록 기한은 **등록 시점에만** 검사한다. 등록 후에는 다시 보지 않는다.

## 3. 검증 원리

### 라이선스 키는 실제로 JWT다

"JWT와 비슷한 것"이 아니라 **형식 자체가 JWT**다. 로그인할 때 쓰는 그 JWT와 같은 규격이고,
점(`.`)으로 나뉜 세 덩어리로 되어 있다.

```
eyJhbGciOiJSUzI1NiJ9  .  eyJjdXN0b21lciI6...  .  Qm3xK9vT...
└──── 헤더 ────┘        └──── 내용 ────┘      └── 서명 ──┘
   알고리즘 정보           고객사·등급·기간        위조 방지
```

앞의 두 덩어리는 **그냥 인코딩된 텍스트**라 누구나 읽을 수 있다. 세 번째 서명이 전부다.

### 🔴 그런데 로그인 토큰과 알고리즘이 다르다

| | 로그인 토큰 | 라이선스 키 |
|---|---|---|
| 알고리즘 | **HS256** (대칭키) | **RS256** (비대칭키) |
| 키 | 비밀문자열 1개 | 개인키 + 공개키 **쌍** |
| 만드는 곳 | 고객사 서버 | **우리 (본사)** |
| 검증하는 곳 | 고객사 서버 | 고객사 서버 |

**로그인 토큰은 만드는 쪽과 검증하는 쪽이 같은 서버**다. 그래서 비밀문자열 하나로 충분하다.
자물쇠와 열쇠가 같은 방식이다.

**라이선스는 만드는 곳(우리)과 검증하는 곳(고객사)이 다르다.** 여기에 같은 방식을 쓰면
검증용 비밀문자열을 제품에 넣어야 하는데, 그 문자열이 곧 **키를 만드는 능력**이다.
고객이 제품 파일을 뒤져서 그것만 찾아내면 PREMIUM 영구 키를 스스로 찍어낼 수 있다.

그래서 **잠그는 열쇠와 여는 열쇠를 분리**했다.

```
개인키(우리)   서명은 되고,  검증도 된다   →  발급기에만 있다
공개키(제품)   검증만 되고,  서명은 안 된다  →  고객에게 줘도 안전하다
```

### 서명과 검증이 실제로 하는 일

```
[발급]  내용 → 해시(지문 생성) → 개인키로 암호화 → 이게 서명
[검증]  내용 → 해시(지문 다시 생성)
        서명 → 공개키로 복호화 → 원래 지문
        두 지문이 같으면 → 내용이 안 바뀌었고, 우리가 서명한 게 맞다
```

내용을 한 글자만 고쳐도 지문이 완전히 달라지므로 즉시 걸린다.
고객이 새 서명을 만들려면 개인키가 필요한데, 공개키에서 개인키를 역산하는 것은 불가능하다
(RSA 2048비트).

### 공개키를 여러 개 둘 수 있게 해뒀다

제품은 `public-1.pem`, `public-2.pem` … 을 **순서대로 시도**해서 하나라도 통과하면 인정한다.

지금은 하나뿐이지만, 이 구조가 없으면 **개인키가 유출됐을 때 대응이 불가능**하다.
공개키를 그냥 새것으로 바꾸면 **이미 발급한 고객 키가 전부 무효**가 되기 때문이다.
새 공개키를 *추가*하고 구 공개키를 한동안 함께 두면, 기존 고객이 멀쩡히 쓰는 채로 넘어갈 수 있다.

### 등록용 검증과 사용 중 검증이 다르다

| | 언제 | 무엇을 보나 |
|---|---|---|
| 등록용 | 고객이 키를 넣을 때 | 서명 + **등록 기한** |
| 판정용 | 요청이 들어올 때마다 | 서명만 |

같은 함수를 쓰면 안 된다. 등록 기한은 기본 7일이라, 사용 중 검증에서도 그걸 보면
**등록 8일째 되는 날 정상 고객이 전부 잠긴다** (영구 라이선스 고객까지).
등록 기한은 *미등록 키의 수명*이지 *등록된 라이선스의 수명*이 아니다.

### 🔴 표준 만료 필드(`exp`)를 쓰지 않는 이유

만료 시각은 키에 있지만, JWT 표준 필드인 `exp`가 아니라 **별도 클레임**에 담는다.

`exp`를 쓰면 JWT 라이브러리가 **서명 검증 단계에서 만료된 토큰을 거부**한다. 그러면 만료 다음 날
곧바로 "유효하지 않은 키"가 되어 잠기고, **유예·읽기 전용 4단계(5절)가 통째로 사라진다.**
만료 판정은 우리 상태 머신이 해야 하므로 라이브러리가 먼저 손대면 안 된다.

> ⚠️ "표준을 쓰는 게 낫지 않나" 하고 `exp`로 되돌리면 만료 고객이 유예 없이 즉시 잠긴다.

## 4. 전체 흐름

| 단계 | 누가 | 무엇을 |
|---|---|---|
| ① 발급 | 우리 | 발급기에서 고객사명·등급·기간 입력 → `.lic` 생성 |
| ② 전달 | 우리 | 메일·USB 무관. 중간에 노출돼도 위조는 불가 |
| ③ 등록 | 고객 | 제품 화면 `설정 > 라이선스 > 적용`에서 파일 업로드 또는 붙여넣기 |
| ④ 사용 | 제품 | 요청마다 라이선스 확인 (60초 캐시) |
| ⑤ 경고 | 제품 | 만료 30일 전부터 화면 상단 배너에 남은 기간 표시 |

**①에서 유효기간이 확정된다.** 시작일 2026-09-01에 365일로 발급하면 만료는 2027-09-01이고, 고객이 8월에 등록하든 10월에 등록하든 그 날짜다.

현재 상태는 `설정 > 라이선스`에서 항상 확인할 수 있다.

## 5. 만료 후 — 끊지 않고 좁힌다

모니터링 제품이라 실시간 조회를 끊으면 **화면이 통째로 빈다.** 서버 목록도, 알람도, 그래프도.
병원·공장 현장에서 이건 사고다. 그렇다고 영원히 열어두면 아무도 갱신하지 않는다.

그래서 4단계로 나눴다.

```
 만료일 ─────── +30일 ─────── +30일 ──────────────► 계속
    │            │             │
    │  유예       │  읽기 전용①  │  읽기 전용②
    │  전 기능    │  보는 건 다 됨│  과거 데이터만
    │  (경고만)   │  (수정 불가)  │  (실시간 끊김)
```

| 구간 | 고객이 겪는 것 | 기간 |
|---|---|---|
| **유예** | 평소와 동일. 강한 경고 배너만 | 만료 후 30일 |
| **읽기 전용 ①** | **모니터링은 계속 된다.** 설정 변경·등록·삭제만 막힘 | 그 후 30일 |
| **읽기 전용 ②** | 실시간 조회가 끊긴다. DB에 쌓인 과거 기록만 조회 | **영구** |

**읽기 전용 ①을 둔 이유** — 갱신 협상과 대체 수단 마련에 시간을 주기 위해서다.
만료 다음 날 인프라 가시성을 통째로 빼앗는 것은 제품이 아니라 협박이다.

**읽기 전용 ②는 영구히 유지된다.** 돈을 내지 않았다고 고객 데이터를 인질로 잡지 않는다.
자기 데이터를 조회하고 내보내는 것은 언제까지나 보장한다.

> 참고: 유예 기간(기본 30일)과 만료 전 경고 시작점(30일)은 값이 같을 뿐 다른 개념이다.
> 전자는 만료 *후* 전 기능 유지 기간, 후자는 만료 *전* 배너 표시 시작점이다.

## 6. 상황별 대응

### 고객이 키를 분실했다

다시 보내주면 된다. 발급 대장(`issued/issued-licenses.csv`)에 모든 발급 내역이 남아 있다.
**같은 키를 다시 등록해도 기간은 원래대로**이며, 재등록으로 기간이 늘어나지 않는다.

### 갱신하려면

새 키를 발급해 전달하고, 고객이 등록하면 끝이다. **기존 키는 자동으로 내려간다**
(활성 라이선스는 항상 1개). 별도 해지 작업이 필요 없다.

### 고객이 "만료 임박하니 지웠다가 다시 넣으면 되지 않나"라고 한다

**되지 않는다.** 만료일이 키에 서명돼 있어서 몇 번을 다시 등록하든 같은 날짜가 나온다.

### 고객이 스스로 라이선스를 해지했다

**완전히 잠긴다** (읽기 전용이 아니다).
읽기 전용은 정당하게 구매했다가 만료된 고객에 대한 배려이지, 스스로 내린 설치본에 대한 것이 아니다.
새 키를 등록하면 바로 풀린다.

### 위조되거나 손상된 키를 넣었다

등록 단계에서 거부된다. 어떤 경우에도 읽기 권한조차 열리지 않는다.

### 체험판을 발급해야 한다

**반드시 유예를 0으로 발급한다.** 기본값 30일이 붙으면 30일 체험이 실질 60일이 된다.

### 만료 후 한참 지난 고객이 갱신했다

새 키를 등록하면 즉시 정상으로 돌아온다. 읽기 전용 ② 구간에 있어도 데이터는 보존돼 있다.

## 7. 발급 방법 (사내)

```bat
cd /d C:\solutions\moveseye-license-issuer
issue.bat --web
```

브라우저에서 **http://127.0.0.1:877** 을 열고 폼을 채운 뒤 **발급**을 누르면
`.lic` 파일이 생성되고 바로 내려받아진다.

| 입력 | 설명 |
|---|---|
| 고객사명 | 키에 그대로 박힌다. 유출 시 추적 근거 |
| 등급 | STANDARD / PREMIUM |
| 유형 | 기간제 / 영구 |
| **시작일** | 기본 오늘. **설치가 밀릴 예정이면 미래로** — 만료일이 여기서부터 계산된다 |
| 기간 | 기간제일 때만. 시작일부터 계산 |
| 유예 | 기본 30일. **체험판은 0** |
| 등록 기한 | 기본 7일. 설치가 밀릴 예정이면 늘린다 |

- **그 명령 창이 곧 서버다.** 창을 닫으면 서버도 종료된다.
- **발급이 끝나면 끈다.** 이 프로세스는 개인키를 들고 있어, 켜져 있는 동안 그 자체가 발급 권한이다.
- 첫 실행은 자동 빌드로 수십 초 걸린다.
- 콘솔 대화형(`issue.bat` 단독 실행)은 **한글 고객사명이 깨질 수 있다.** 웹으로 발급한다.

### 🔴 개인키 취급

`keys/private-key.pem` **이 파일이 곧 발급 권한이다.** 유출되면 누구나 PREMIUM 영구 키를
무한정 만들 수 있다.

- 커밋·공유·메일 첨부 금지
- 발급 도구를 **제품 저장소와 분리**해 둔 이유가 이것이다 (고객에게 넘어가는 소스에 섞이면 끝난다)
- 발급기 웹은 기본적으로 **자기 PC에서만** 접속된다

### 발급 대장

`issued/issued-licenses.csv`가 발급 대장이다. **갱신 문의와 분쟁 대응의 유일한 근거**이므로
삭제하지 않는다.

## 8. 막는 것과 막지 못하는 것

정직하게 정리한다. 폐쇄망에서 완벽한 복제 방지는 불가능하다.

| 시도 | 결과 |
|---|---|
| 키 위조 | **막힌다** — 우리 개인키 없이는 서명할 수 없다 |
| 키 파일에서 기간·등급 수정 | **막힌다** — 한 글자만 고쳐도 서명이 깨진다 |
| 지웠다가 재등록해 기간 연장 | **막힌다** — 만료일이 키에 있어 몇 번을 넣어도 같다 |
| 만료된 키 재등록 | **막힌다** — 유예까지 끝난 키는 거부된다 |
| DB에서 **등급·기능** 고치기 | **막힌다** — 매번 키에서 다시 읽는다 |
| DB에서 **만료일** 고치기 | **막힌다** — 만료일도 키에 서명돼 있다 |
| **키를 복사해 여러 서버에 설치** | **막지 못한다** |
| **서버 시계를 되돌리기** | **막지 못한다** |

**DB를 고쳐도 등급은 못 올린다** — 제품은 DB에 적힌 등급·기능을 믿지 않는다. 요청이 올 때마다
저장된 키 문자열을 **다시 서명 검증해서** 거기서 값을 꺼낸다. DB에 `PREMIUM`이라고 써넣어도
키가 STANDARD면 STANDARD다. 가짜 키 문자열을 밀어 넣으면 검증에 실패해 **오히려 잠긴다.**

**만료일도 마찬가지다**(2026-08-12부터). `expires_at`을 100년 뒤로 UPDATE해도 판정은 꿈쩍하지
않는다 — 그 컬럼은 목록 표시용 사본이고, 판정은 키에 서명된 값을 본다. 실기동으로 확인했다.

**복사 방지가 불가능한 이유** — 두 서버가 같은 키를 쓰는지 확인하려면 서로 통신하거나 본사에
물어봐야 하는데, 폐쇄망에서는 둘 다 불가능하다. 대신 키마다 고객사명과 고유번호가 박혀 있어
**유출 시 출처를 즉시 특정할 수 있다.** 기술이 아니라 계약과 추적으로 다루는 영역이다.

**시계 조작을 막지 않은 이유** — 표준시 서버가 없는 폐쇄망에서는 서버 시계를 대조할 기준이 없다.
다만 모니터링 서버의 시계를 1년 되돌리면 로그 타임스탬프·인증서·배치 스케줄이 모두 엉키므로
실제로 감수하기 어렵다. 필요하면 나중에 방어를 추가할 수 있다.

**막지 못하는 둘의 공통점** — 전부 **서버 관리자 권한**이 있어야 한다. 화면에서 사용자가 할 수
있는 일이 아니라 DB에 직접 접속하거나 OS 시계를 바꿔야 한다. 온프레미스라 서버가 고객 소유인
이상, 작정한 관리자는 결국 우회할 수 있다. 어느 선까지 막을지는 기술이 아니라 정책 판단이다.

> 설계 원칙: **정직한 고객이 불편하지 않게, 대충 하는 우회는 막히게.**

## 9. 용어

| 용어 | 뜻 |
|---|---|
| `.lic` | 라이선스 파일. 서명된 텍스트 한 줄 |
| jti (고유번호) | 키마다 부여되는 식별자. 유출 시 어느 발급 건인지 특정하는 근거 |
| 유예(grace) | 만료 후에도 전 기능이 유지되는 기간. 기본 30일 |
| 등록 기한 | 발급 후 이 안에 등록해야 한다. 기본 7일 |
| 등급(edition) | STANDARD / PREMIUM |
| 기능(feature) | 등급과 별개로 개별 부여하는 항목 (예: GPU 모니터링) |
| 읽기 전용 | 조회는 되고 변경이 막힌 상태 |
| 잠금 | 라이선스 화면 외에는 아무것도 못 하는 상태 |
