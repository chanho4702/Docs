# Problem

> **사이드바** 이벤트/알림 > Problem
> **경로** `/event-alert/problem` → 상세 `/event-alert/problem/:id`

## 무엇을 하는 화면인가

현재 열려 있는 장애(Problem)를 확인하고 조치 상태를 기록하는 화면이다. **장애 대응의 중심 화면**이다.

## Problem과 Event의 차이

이 둘을 같은 말로 쓰면 화면이 이해되지 않는다.

| 용어 | 의미 |
|---|---|
| **Problem** | 트리거가 이상으로 판정해 **열려 있는 상태** |
| **Event** | 발생·복구·상태 변화가 일어난 **시점의 기록** |

하나의 Problem에 여러 Event가 달린다.

## 화면 구성

### 목록

| 필터 | 내용 |
|---|---|
| 호스트 그룹 | 담당 범위로 좁힌다 |
| 호스트 | 특정 장비 |
| 발생 일시 / 처리 일시 | 기간 |
| 숨겨진 problem 표시 | 억제된 항목 포함 |
| 검색 | problem 세부 정보 |

### 상세

| 영역 | 내용 |
|---|---|
| 트리거 세부 정보 | 호스트, 트리거, Severity, **Problem expression**, 복구 표현, 이벤트 생성, 수동 종료 허용 |
| 이벤트 세부 정보 | 시간, Acknowledged, 태그, 설명, 순위 |
| 운영 데이터 | 관련 수치 |
| 작업 | 수행된 조치 |
| 이벤트 목록 [이전 20] | 같은 트리거의 최근 이력 |

## Acknowledge의 의미

🔴 **acknowledge는 장애 해소가 아니다.** "운영자가 인지했고 조치 중"이라는 **기록**이다.

- acknowledge해도 Problem은 열려 있다
- 실제 해소는 원인이 사라져 트리거가 정상으로 돌아갈 때 일어난다
- 팀 단위로 "누가 보고 있는지" 공유하는 것이 목적이다

## 사용 흐름

1. 호스트 그룹으로 담당 범위를 좁힌다.
2. Severity 높은 순으로 확인한다.
3. 대응을 시작하면 **acknowledge**로 기록을 남긴다.
4. 상세에서 **[이전 20]** 이벤트 목록을 본다 — 반복되는 장애인지 처음인지가 원인 판단에 결정적이다.
5. 필요하면 해당 호스트의 모니터링 화면으로 이동해 지표를 확인한다.

## 주의할 점

- **권한이 없는 호스트 그룹의 Problem은 목록에도 집계에도 나오지 않는다.** 전체 장애 수를 파악해야 하는 담당자라면 권한 범위를 확인한다.
- **숨겨진(억제된) Problem**이 있다. 유지보수 등으로 억제된 항목은 기본적으로 보이지 않으므로, 전수 확인이 필요하면 표시 옵션을 켠다.
- 상세의 **Problem expression**은 트리거 판정 조건이다. 왜 이 상황이 장애로 잡혔는지 이해할 때 본다.
- **수동 종료 허용**이 켜진 트리거만 사람이 직접 닫을 수 있다.

## 알림 벨

화면 상단의 알림 벨은 주기적으로 갱신된다. **세션이 만료되면 이 갱신이 반복 실패해 무한 로딩처럼 보일 수 있다**(알려진 이슈). 이때는 재로그인한다.
