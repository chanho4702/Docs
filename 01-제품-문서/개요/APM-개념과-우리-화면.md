# APM 개념과 우리 화면

[읽기 안내](MovesEye-%EC%B5%9C%EA%B7%BC-%EC%9E%91%EC%97%85%EA%B3%BC-APM-%EC%9D%BD%EA%B8%B0-%EC%95%88%EB%82%B4.md) · 다음: [OpenTelemetry](OpenTelemetry%EC%99%80-MovesEye-%EC%88%98%EC%A7%91-%ED%9D%90%EB%A6%84.md)

APM은 Application Performance Monitoring의 약자로, **애플리케이션이 사용자 요청을 얼마나 잘 처리하는지 살펴보는 방법과 도구**입니다. MovesEye에서는 서버·네트워크 상태와 함께 애플리케이션의 처리량, 지연, 오류, 호출 관계를 분석하는 영역입니다.

## 1. 서버 모니터링에 APM을 더하는 이유

쇼핑몰 주문 화면이 3초 걸린다고 가정해 보겠습니다. 서버 CPU 사용률은 30%이고 메모리도 충분합니다. 인프라 지표만 보면 원인을 찾기 어렵습니다.

APM에서 주문 요청을 펼쳐 보니 주문 코드 100ms, DB 조회 200ms, 결제 API 2,500ms가 보입니다. 이 경우 먼저 조사할 곳은 CPU 증설보다 결제 API의 응답 지연입니다.

이 수치는 설명용 예시입니다. 실제 요청에서는 호출이 겹치거나 관측되지 않는 구간도 있어 모든 span 시간을 단순 합산하면 안 됩니다.

## 2. 가장 먼저 볼 세 가지 숫자

| 지표 | 쉬운 뜻 | 해석할 때 함께 볼 것 |
|---|---|---|
| 처리량, Rate | 일정 시간에 처리한 요청 수 | 초당인지 분당인지, 요청이 없었는지 수집이 끊겼는지 |
| 오류율, Errors | 관측한 요청 중 오류로 분류된 비율 | 분모, 오류 판정 규칙, 수집 누락 |
| 응답 시간, Duration | 요청 완료까지 걸린 시간 | 평균뿐 아니라 p95·p99, 단위, 표본 여부 |

예를 들어 1분 동안 600건을 처리했다면 평균 처리량은 초당 10건입니다. 그중 오류가 12건이면 해당 집합의 오류율은 2%입니다.

**p95가 800ms**라는 말은 관측 집합의 약 95%가 800ms 이내라는 뜻입니다. “평균 800ms”와 다릅니다. 히스토그램에서 계산한 백분위는 버킷 경계와 계산법에 따른 근사치일 수 있습니다.

평균값이 좋은데 p99만 크게 나빠지면 일부 사용자가 긴 지연을 겪는 상황일 수 있습니다. 반대로 표본 수가 매우 적을 때는 백분위 하나로 전체 서비스 상태를 단정하기 어렵습니다.

## 3. 서비스와 인스턴스

**서비스**는 주문 API처럼 논리적으로 같은 일을 하는 애플리케이션입니다. **인스턴스**는 그 서비스를 실행하는 개별 프로세스나 컨테이너입니다.

주문 API를 세 대에서 실행하면 서비스 하나에 인스턴스 세 개가 있습니다. 서비스 전체 평균이 정상이어도 특정 인스턴스 하나만 느릴 수 있으므로 전체 지표에서 인스턴스로 내려갈 수 있어야 합니다.

서비스 이름, 환경, 인스턴스 식별자가 불안정하면 서로 다른 실행체가 섞이거나 같은 실행체가 여러 개로 보입니다. 설치 설정은 단순 연결 정보뿐 아니라 데이터의 정체성을 정하는 작업입니다.

## 4. Trace와 Span

**Trace**는 요청 하나의 이동 경로이고, **Span**은 그 안의 작업 한 구간입니다. 주문 요청 안에 DB 조회와 결제 API 호출이 있으면 각각 span으로 나타날 수 있습니다.

```text
주문 요청 전체                     0ms ────────────────── 3000ms
  DB 조회                           100ms ── 300ms
  결제 API 호출                            350ms ───────── 2850ms
  응답 작성                                                2850ms ─ 3000ms
```

워터폴은 이런 구간을 시간축에 놓은 화면입니다. 오래 걸린 구간, 병렬 호출, 부모 작업이 끝난 뒤 이어지는 비동기 작업을 살펴봅니다.

계측이 없는 라이브러리나 끊어진 컨텍스트 때문에 일부 구간은 보이지 않을 수 있습니다. **빈 구간은 자동으로 CPU 연산 시간이나 DB 대기 시간이라고 확정할 수 없습니다.** 별도의 프로파일이나 DB 진단이 필요할 수 있습니다.

## 5. 전체 지표와 저장된 트레이스가 다른 이유

전체 요청의 지표와 개별 요청의 상세 기록은 비용이 다릅니다. 모든 상세 기록을 오래 저장하면 용량이 커지므로 일부 trace만 선택할 수 있습니다. 이를 **샘플링**이라고 합니다.

따라서 저장된 trace 목록의 오류 비율을 전체 서비스 오류율로 사용하면 안 됩니다. 오류 요청을 더 많이 보관하도록 설정했다면 목록에는 오류가 의도적으로 많습니다.

MovesEye는 메트릭 집계, 보존용 trace, 실시간 완료 span을 다른 경로로 처리합니다. 세 화면의 건수가 다를 때 먼저 같은 시간창·같은 서비스·같은 수집 경로·같은 표본 조건인지 확인해야 합니다.

## 6. 실시간 관제의 두 종류

**완료 요청 관측:** 요청이 끝난 뒤 duration과 결과를 받습니다. X-View는 완료 시각과 소요 시간을 점으로 표현해 느린 요청의 분포를 살펴봅니다.

**진행 중 요청 관측:** 아직 끝나지 않은 요청이 몇 개이고 얼마나 오래 진행 중인지 봅니다. MovesEye Java 확장이 시작·종료와 현재 하위 작업을 추적하고 별도 메트릭·로그 형태로 보냅니다.

진행 중 10초라는 값과 완료 요청 p95 500ms는 동시에 성립할 수 있습니다. 전자는 아직 끝나지 않은 요청, 후자는 끝난 요청 집합을 말하기 때문입니다.

현재 확장은 JDK 17, Java agent 2.31.1 및 특정 Spring MVC/Tomcat 조합의 검증 기록을 갖습니다. 같은 수준의 진행 중 요청 목록이 모든 언어에서 제공된다는 뜻은 아닙니다. [확장 범위](../../12-%EC%98%A8%EB%B3%B4%EB%94%A9-%EA%B7%9C%EC%95%BD/OTel-%ED%99%95%EC%9E%A5-%EC%86%8C%EA%B0%9C.md).

## 7. 화면을 목적에 맞게 읽기

| 상황 | 먼저 볼 화면 | 다음 행동 |
|---|---|---|
| 전체적으로 느려졌다 | APM 개요·서비스 | 시간 범위와 오류율·p95 확인 → 문제 서비스 선택 |
| 특정 API만 느리다 | 서비스의 트랜잭션·트레이스 | endpoint 조건 확인 → 느린 trace 워터폴 |
| DB 호출이 의심된다 | DB 호출 그룹 | 샘플링·SQL 마스킹 확인 → 해당 trace 연결 |
| 다른 서비스 영향이 의심된다 | 서비스 맵·외부 의존 | 연결 방향과 호출 지연 → 하위 서비스 조사 |
| 지금 요청이 쌓인다 | 실시간 관제 | 진행 중 요청과 완료 요청을 구분 → 걸림 장부 |
| 서버는 정상인데 사용자가 불편하다 | RUM | 브라우저의 페이지 성능·오류와 서버 trace를 가능한 범위에서 대조 |
| 장기 품질을 판단한다 | SLO·리포트 | 측정 기간·분모·데이터 부족 여부 확인 |

메뉴 배치는 최근 변경됐습니다. 수집기와 APM 알람 규칙은 관리 콘솔로 이동했고 기존 URL에는 리다이렉트가 있습니다. 정확한 진입 경로는 [현재 routes](../../moveseyee_fe/src/routes/routes.tsx)가 기준입니다.

## 8. RUM, 합성 점검, SLO의 차이

**RUM**은 실제 사용자의 브라우저에서 성능과 오류를 관측합니다. 사용자 환경을 볼 수 있지만 방문자가 없으면 관측도 없습니다. 브라우저 전송 제한이나 수집 실패로 전체 방문을 모두 기록하지 못할 수 있습니다.

**합성 점검**은 정해진 요청을 주기적으로 실행하는 점검입니다. 사용자가 없어도 상태를 확인할 수 있지만 실제 모든 사용자 경로를 대표하지는 않습니다. MovesEye의 합성 점검은 Zabbix 웹 점검과 연결됩니다.

**SLO**는 “측정 기간 동안 얼마나 좋은 서비스를 제공할 것인가”라는 목표입니다. 예를 들어 성공률 99.9%를 목표로 정할 수 있습니다. 지표가 없으면 목표 달성으로 처리하기보다 판단 불가로 구분해야 합니다.

## 9. 빈 값은 장애와 다르다

0은 “관측했으며 0”일 수 있고, 빈 값은 미지원·수집 안 됨·기간 만료·권한 부족일 수 있습니다. 수집기 마지막 수신 시각, 서비스 등록 상태, 지표 지원 범위, 보존 기간을 차례로 확인하세요.

최근 화면 자기설명 작업은 이 차이를 보여 주는 방향입니다. 다만 모든 차트가 같은 수준으로 처리되는지는 별도 검증 항목입니다. [자기설명 구현](../%EA%B8%B0%EB%8A%A5/APM-%ED%99%94%EB%A9%B4-%EC%9E%90%EA%B8%B0%EC%84%A4%EB%AA%85.md).

## 10. 현재 APM으로 단정할 수 없는 것

- 모든 요청과 모든 함수 호출을 빠짐없이 기록했다는 보장
- trace에 나타난 느린 SQL의 DB 실행 계획·락 원인을 자동으로 확정하는 기능
- Java 진행 중 요청 확장의 동작을 모든 언어에서 동일하게 제공한다는 보장
- 콜드 아카이브 파일만 있으면 바로 화면에서 과거 상세를 재조회할 수 있다는 보장
- AI 설명만으로 장애 원인이 확정됐다는 결론
