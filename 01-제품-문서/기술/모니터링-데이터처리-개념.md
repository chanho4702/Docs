# 모니터링 데이터 처리 핵심 개념

모니터링 화면의 속도·신선도·정확성을 논의할 때 자주 나오는 개념을 정리한다. 이 문서는 구현 설계서가 아니다. 현재 MovesEye의 적용 여부는 2026-09-07 소스 기준이며, “제안”은 아직 구현되지 않은 방향이다.

## 핵심 개념

| 개념 | 쉬운 설명 | 언제 필요한가 | MovesEye 적용 상태 |
|---|---|---|---|
| **Polling** | 화면이 일정 시간마다 서버에 “새 데이터가 있나?”라고 다시 요청하는 방식 | 주기 갱신만으로 충분하고 구현을 단순하게 유지할 때 | 사용 중. 상대 기간 차트는 기본 3분마다 새 시간 범위를 요청한다. |
| **SSE** | 서버가 열린 HTTP 연결로 브라우저에 변경 소식이나 데이터를 보내는 단방향 방식 | 서버에서 브라우저로 알림을 보내면 충분할 때 | 사용 중. 알람은 변경 신호를 보내고, APM Live는 데이터 bucket도 보낸다. |
| **WebSocket** | 브라우저와 서버가 열린 연결에서 서로 메시지를 주고받는 양방향 방식 | 채팅·공동 편집·실시간 제어처럼 브라우저도 즉시 메시지를 보내야 할 때 | 미사용. 현재 일반 REST 요청과 SSE 조합을 쓴다. |
| **최신값 조회** | 원천이 현재 가진 마지막 측정값을 읽는 조회 | 현재 CPU·메모리 사용률처럼 “지금”이 중요한 화면 | 사용 중. 단, 최신값 조회가 측정 즉시 반영을 보장하지는 않는다. |
| **시계열 차트** | 시간에 따라 쌓인 여러 측정 포인트를 그리는 차트 | CPU 추이·트래픽·응답 시간처럼 변화 흐름을 볼 때 | 사용 중. 현재는 선택 시간창 전체 범위를 다시 요청한다. |
| **증분 조회** | 처음에는 전체를 받고, 다음부터는 새로 생긴 구간만 받는 방식 | 같은 시간창을 계속 갱신하는 차트의 전송량·원천 조회를 줄일 때 | 제안. 현재 주요 차트에는 구현되지 않았다. |
| **Cursor / Watermark** | 마지막으로 성공적으로 확보한 데이터 구간의 끝 시각 또는 ID | 다음 증분 조회의 시작점을 정하고, 중단 뒤 누락을 보충할 때 | 제안. HTTP 응답을 받은 현재 시각과 혼동하면 안 된다. |
| **Overlap window** | 증분 조회 때 최근 일부 구간을 다시 받는 겹침 범위 | 지연 도착·수정된 값·재전송을 안전하게 반영할 때 | 제안. 겹친 포인트는 새 응답으로 교체한다. |
| **병합(merge)** | 새 포인트를 기존 차트 데이터에 추가하고 겹치는 포인트는 교체하는 처리 | 증분 조회 결과를 끊김 없이 차트에 반영할 때 | 제안. 중복 제거 기준과 시간창 밖 포인트 제거가 함께 필요하다. |
| **Backfill** | 서비스 중단·네트워크 단절 동안 빠진 과거 데이터를 다시 채우는 처리 | 탭 복귀, 재연결, 동기화 실패 뒤 정확성을 회복할 때 | 일부 적용. 알람 사본은 보정 경로가 있고, 차트 증분 보충은 제안이다. |
| **Cache** | 최근 결과를 짧게 저장해 같은 원천 조회·계산을 반복하지 않는 것 | 여러 사용자나 같은 화면이 동일 데이터를 자주 볼 때 | 사용 중. 서버·그룹 목록과 홈 일부에 Redis 캐시가 있다. |
| **TTL** | 캐시를 재사용할 수 있는 시간 | 데이터 신선도와 원천 부하 사이의 균형을 정할 때 | 사용 중. 예: 서버·그룹 목록 스냅샷 30초. |
| **Cache stampede** | 캐시 만료 순간 여러 요청이 동시에 원천으로 몰리는 현상 | 접속자가 많거나 캐시 만료 시점이 겹칠 때 | 위험이 남아 있다. 단순 get → miss → 원천 조회 구조만으로는 막지 못한다. |
| **Single-flight** | 같은 캐시 미스 요청 중 한 요청만 원천 조회하고 나머지는 그 결과를 함께 받는 방식 | cache stampede를 막고 동일 Zabbix 호출을 한 번으로 합칠 때 | 제안. 사용자·권한·필터가 같은 키끼리만 합쳐야 한다. |
| **Stale-while-revalidate** | 약간 오래된 캐시를 먼저 보여주고 뒤에서 새 데이터를 갱신하는 방식 | 화면 응답을 빠르게 유지하면서 원천 호출 급증을 막을 때 | 제안. 사용하면 마지막 갱신 시각을 화면에 보여줘야 한다. |
| **Snapshot** | 특정 시점의 상태를 통째로 담은 값 | 서버 목록·현재 상태처럼 시점 기준으로 보여도 되는 화면 | 사용 중. 목록 조회 결과를 짧은 TTL로 보관한다. |
| **Read model / 사본** | 조회 화면에 맞게 별도로 저장한 데이터 | 원천을 매 화면 요청마다 조회하지 않고 빠르게 목록·통계를 제공할 때 | 사용 중. `event_problems`는 알람 목록·벨을 위한 사본이다. |
| **Incremental sync** | 원천에서 전체를 매번 복사하지 않고, 변경 가능성이 큰 부분을 자주 반영하는 동기화 | 알람처럼 신선해야 하지만 전체 상세 조회는 무거울 때 | 사용 중. 기본 15초 경량 알람 확인과 5분 전체 보정을 조합한다. |
| **Eventual consistency** | 원천과 사본이 즉시 같지는 않지만 잠시 뒤 맞춰지는 상태 | 사본·비동기 동기화를 사용할 때 | 적용됨. 사본의 갱신 시각과 보정 실패 여부를 운영에서 확인해야 한다. |
| **Raw data / history** | 수집한 원본 측정값 전부 | 짧은 구간의 상세 추이·정확한 분석 | 사용 중. 대량 조회를 막는 건수 상한이 있다. |
| **Rollup / aggregation** | 원본을 시간 단위 평균·최대·최소 같은 요약값으로 압축하는 것 | 긴 기간 차트·통계·보고서에서 원천 조회량을 줄일 때 | 사용 중. 긴 범위는 Zabbix `trends`를 우선 사용한다. |
| **Rate limit** | 일정 시간에 보낼 수 있는 요청 수를 제한 | 원천이나 API를 초당 호출량으로 보호할 때 | 전역 요청률 제한은 미적용. 필요 시 다중 인스턴스 전체 기준으로 설계한다. |
| **Concurrency limit** | 동시에 실행할 수 있는 요청 수를 제한 | 느린 원천에 요청이 한꺼번에 쌓이는 것을 막을 때 | 사용 중. Zabbix 호출은 BE 인스턴스당 기본 10개 연결로 제한한다. |
| **Circuit breaker** | 원천이 계속 실패하면 잠시 호출을 멈추고 빠르게 실패시키는 장치 | Zabbix 장애 때 재시도가 원천을 더 악화시키는 것을 막을 때 | 미적용. timeout·동시성 제한과 별개로 필요성을 판단한다. |
| **Idempotency** | 같은 데이터를 두 번 처리해도 최종 결과가 같게 만드는 성질 | 재연결·중복 이벤트·재시도에서 데이터 중복·상태 되돌림을 막을 때 | 알람 사본 동기화에 필요하며, 증분 차트 병합에도 필수다. |

## Redis에 무엇을 넣고 무엇을 넣지 않는가

| 위치 | 적합한 데이터 | 피해야 할 데이터 |
|---|---|---|
| 브라우저 메모리 | 사용자가 현재 보고 있는 차트의 포인트, 마지막 확보 구간 | 탭을 닫은 뒤에도 보존해야 하는 장기 이력 |
| Redis | 여러 사용자가 재사용하는 짧은 스냅샷, 캐시 키, single-flight 조정 정보 | 사용자별·호스트별·차트별 전체 시계열을 무제한 저장하는 데이터 |
| PostgreSQL 또는 집계 저장소 | 보고서·통계용 이력, 영속해야 하는 사본과 집계 결과 | 초 단위 UI 임시 버퍼 |
| Zabbix | 모니터링 원천값과 장기 원본·요약 데이터 | 화면 사용자별 상태나 MovesEye 전용 조회 캐시 |

따라서 차트 증분 조회를 도입해도 **이전 차트 전체를 Redis에 넣는 구조가 아니다.** 브라우저는 표시 기간만큼의 포인트를 제한적으로 들고, 다음 요청에서 새 구간과 보정 구간을 병합한다. 화면을 닫으면 브라우저 버퍼는 사라진다.

## 판단 빠른표

| 상황 | 먼저 검토할 개념 |
|---|---|
| 같은 목록을 여러 사용자가 자주 본다 | Cache, TTL, Single-flight, Read model |
| 서버가 바뀐 사실을 화면에 빨리 알려야 한다 | SSE |
| 차트 갱신 때 겹치는 과거 범위를 계속 읽는다 | 증분 조회, Cursor, Overlap window, 병합 |
| 탭이 멈추거나 네트워크가 끊겼다 | Backfill, Idempotency |
| 긴 기간 차트나 보고서가 느리다 | Rollup, aggregation, `trends` |
| Zabbix가 느리거나 장애다 | timeout, Concurrency limit, Circuit breaker |
| 여러 BE 인스턴스를 운영한다 | 전역 Rate limit, 인스턴스 간 SSE 전달, 분산 캐시 정책 |
