# Zabbix 부하 절감 아키텍처

> 한 줄 요약 — **화면 트래픽과 Zabbix 부하를 분리했다.** 알람 목록·벨은 자체 DB 사본을 읽고,
> 신선도는 15초 증분 동기화+SSE 푸시가 책임지며, Zabbix가 받는 것은 접속자 수와 무관한
> 배치 주기당 상수 콜이다. (Jira 에픽 **ZM-123**, ZM-124~131·133)

계약·영업 관점의 부하 상한 문구는 [운영 문서 「Zabbix 성능·부하 책임 경계」](../%EC%9A%B4%EC%98%81/%EC%9E%90%EB%B9%85%EC%8A%A4-%EC%84%B1%EB%8A%A5-%EC%B1%85%EC%9E%84-%EA%B2%BD%EA%B3%84.md)가 정본이다. 이 문서는 그 숫자가 나오는 **구조**를 설명한다.

## 1. 문제 — 왜 했나

개선 전 부하의 본체는 Zabbix가 아니라 **MovesEye BE의 호출 패턴**이었다.


| 경로         | 개선 전                                                          | 문제                               |
| ---------- | ------------------------------------------------------------- | -------------------------------- |
| 알람 목록·알림 벨 | 전 사용자 화면이 1분 폴링마다 problem.get+trigger.get+acknowledges **직행** | 부하가 접속자 수에 비례. 자빅스 순단 = 알람 화면 전멸 |
| 심각도 칩 카운트  | 등급별 problem.get countOutput **7콜**                            | 화면 하나에 7콜                        |
| 이벤트 동기화    | 1분마다 규칙·조치·사용자 목록까지 **전체 한 벌**                                | 무거운 사이클이 고빈도로                    |
| 긴 기간 차트    | 원시 history(수억 행 테이블)를 **무제한** 조회                              | 30일 창이면 수십만 행, 절단도 무경고           |
| 인터페이스 상세   | search 키마다 item.get — **9콜**                                  | N+1                              |
| 호출 통제      | 커넥션 상한·계측 없음                                                  | "우리가 자빅스를 얼마나 때리나"를 알 수 없음       |


## 2. 구조 — 무엇으로 바꿨나

```
[사용자 화면 N명]                     [Zabbix]
 알람 목록/벨  ──읽기──▶ event_problems 사본(자체 DB)
 SSE 구독     ◀─푸시─── EventStreamHub          ▲
                              ▲                 │ 상수 콜
                        EventSyncService ───────┘
                        · 증분 15초: 경량 problem.get 1콜(recent 포함)
                        · 보정 5분: 규칙·조치·사용자 한 벌
                        · 조치 직후: 표적 재동기화(해당 행만)
```

### 2.1 사본 서빙 (ZM-125)

- 알람 목록·알림 벨은 `event_problems` 테이블(자체 DB)만 읽는다. 목록 서빙에 필요한 컬럼
(억제·원인·규칙 활성·그룹 JSON·조치 수·**host_ids**)을 동기화가 함께 싣는다(V49).
- **권한 재현이 핵심 난점** — 사본은 시스템 토큰으로 만들므로 Zabbix가 토큰으로 해 주던
스코핑을 앱이 재현해야 한다. 두 축:
  - 호스트 축: 호출자의 가시 호스트 집합으로 필터. 다중 호스트 트리거는 **전 호스트 AND**
  (Zabbix 축 그대로), host_ids 빈 배열은 fail-closed.
  - 태그 축: usergroup **tag_filters**가 설정된 설치본만 `ProblemTagFilterGuard`(5분 캐시)가
  감지해 후보 id를 사용자 토큰으로 재검증(event.get). 보통 설치본은 검증 콜 0.
- 화면에 보이는 페이지만 조치 타임라인을 실시간 하이드레이션(콜 1회) — 나머지는 사본 값.

### 2.2 동기화 이원화 (ZM-127)

- **증분(15초)**: 경량 problem.get 1콜. 시간창 없음(오래 열린 장애 포함), `recent:true`
(창 사이에 발생·해소된 초단명 사건까지 적재). 신규는 표적 완전 동기화, 기존은 휘발 필드만
조건부 UPDATE(`IS DISTINCT FROM` — 실제 변화만 집계), 창 내 해소는 복구 시각 즉석 채움.
- **보정(5분)**: 규칙·조치·사용자·읽음 상태·되짚기(사라진 사건=해소 판정) 전부.
- 좀비 정리는 **updated_at 기준 2일** — 보정이 살아 있는 행을 매번 upsert하므로 오래 열려
있는 진짜 장애는 절대 안 지워진다. 해소분은 30일 후 삭제.
- 안전핀: 콜당 1만 건 상한(도달 시 warn), 사본이 15분 이상 낡으면 warn.

### 2.3 SSE 알람 스트림 (ZM-128)

- `EventStreamHub`가 `events-changed` **신호만** 푸시(페이로드 없음 — FE가 재조회). 변화가
있었던 사이클만, DB 반영이 모두 끝난 뒤 1회.
- 구독은 visitorId 세션 대조, 하트비트 25초마다 세션 재검(fail-closed), 수명 30분.
- FE는 라이브 연결 시 폴링을 5분 안전망으로 늦추고, 신호 수신 시 관련 쿼리 무효화(2초 스로틀).
- 조치(ack) 직후엔 읽음 기록 → 표적 재동기화 → 신호 순서(다른 탭의 unread 부활 방지).

### 2.4 적응 조회 (ZM-130·131)

- `AdaptiveSeriesQuery`: 차트는 48시간 이상, 통계(min/max/avg)는 **1시간 초과** 창에서
원시(history) 대신 시간당 요약(trends, 1/60 크기)을 읽는다. trends가 전부 비면(보존 0 아이템
·미완결 버킷) 원시로 폴백.
- history.get은 limit 미지정 시 **기본 상한 10만 행** 강제 + 도달 warn. 아이템 이력 차트는
상한에 닿은 그룹의 절단 원시를 폐기하고 trends로 폴백(부분 데이터의 조용한 왜곡 차단).
- item.get 다중 키는 `search.key_` 배열+`searchByAny` **1콜**(종전 9콜).

### 2.5 통제·가시성 (ZM-126·129)

- 모든 Zabbix 호출이 단일 커넥션 풀 경유 — 동시 상한 기본 10(`ZABBIX_CLIENT_MAX_CONNECTIONS`),
풀 대기 5초.
- `ZabbixCallMetrics`가 60초마다 `[zabbix-calls]` 요약 로그(메서드별 횟수·소요) — 운영 중
호출량 실측의 근거.
- 호스트 목록·가시 호스트 집합은 Redis 캐시(30~60초 스냅샷).

## 4. 운영 시 알아야 할 것

- **event_sync 스케줄러는 필수 전제** — 끄면 목록이 정지된 사본을 보여준다(15분 초과 시 warn 로그).
주기는 스케줄러 화면에서 조정 가능(기본 15초, V50).
- 배포 직후 첫 동기화(≤15초)까지 rule_enabled·host_ids가 NULL인 기존 행은 유예 포함된다.
- 태그 필터 설치본에서 Zabbix 순단 시 태그 검증은 fail-closed(일시적 빈 목록 &gt; 권한 누출).
- 진단 순서: `[zabbix-calls]` 로그 → event_sync 로그(`N open, N new, N changed, N resolved`) →
사본 stale warn.
