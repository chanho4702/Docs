# 하네스 엔지니어링 — 에이전트 팀/스킬 설계 노하우

> 새 프로젝트에 하네스(전문 에이전트 + 스킬 + 오케스트레이터)를 구축할 때 반복적으로 통하는 원칙. `harness` 메타 스킬을 쓰되, 아래 교훈을 먼저 적용하면 헛도는 설계를 피한다. moves-workforce에서 설계→실전 가동→재구성까지 한 바퀴 돌며 검증.

## 요약 (가장 중요한 5가지)

1. **런타임 제약을 먼저 확인하고, 실제 동작하는 경로를 주 경로로 써라.** 멋진 팀 모드를 설계해도 런타임이 못 받으면 폴백이 진짜 경로다. 폴백을 각주로 두지 마라.
2. **경계면 계약(응답 shape)을 단일 진실로.** 풀스택 하네스의 런타임 버그는 대부분 생산자↔소비자 경계면 불일치다.
3. **순차가 병렬보다 안전할 때가 많다.** 소비자가 생산자의 *실제* 산출물을 읽으면 추측이 사라진다.
4. **에이전트(누가) ↔ 스킬(어떻게)를 분리하라.** 정체성/협업 프로토콜은 에이전트, 실행 절차/패턴은 스킬.
5. **프로젝트 특화 지식을 박아라.** 일반론 하네스는 가치가 낮다. 코드를 읽어야만 나오는 디테일이 실효성을 만든다.

## 패턴 / 노하우

### ① 런타임 제약 확인 → 실행 모드 결정 (제일 먼저)
- 빌트인 `agent_type`만 받는가, 커스텀도 받는가? `TeamCreate`/`SendMessage`(팀 직접통신)가 있는가?
- **런타임 능력은 고정이 아니다 — 하네스 점검 때마다 재확인하라.** 2026-05 시점엔 빌트인 타입만 받았지만, **2026-06-11 재확인 결과 커스텀 `subagent_type`(`.claude/agents/` 정의가 타입으로 노출)과 `SendMessage`(기존 에이전트를 컨텍스트 유지한 채 재호출)가 지원됨.** `TeamCreate`(팀원 간 직접통신)는 여전히 없음 → 순차 파이프라인은 유지하되, "general-purpose로 띄우고 agent.md를 Read시키는" 역할 채택 우회는 폐기하고 커스텀 타입 직접 생성으로 전환. 수정 루프는 SendMessage 재호출이 새 스폰보다 빠르고 정확.
- 안티패턴: 팀 모드(`TeamCreate`+병렬+`SendMessage`)를 메인으로 길게 써놓고 폴백을 "런타임 미지원 시"로 각주 처리 → 실행 시 안 되는 경로를 먼저 시도하고 헤맨다.
- 처방: **실제 동작하는 모드를 기본 워크플로우로 승격**하고, 더 좋은 모드는 "런타임이 지원하면" 옵션으로 강등. 문서와 실행을 일치시킨다.

### ② 경계면 계약을 단일 진실로 (풀스택 QA의 핵심)
- 각 컴포넌트가 개별적으로 맞아도 **연결 지점에서 계약이 어긋나면** 런타임에 터진다. 빌드 통과 ≠ 정상 동작.
- 설계 에이전트의 1순위 산출물 = **경계면 계약 표**(함수명 · 입력 · 응답 shape · 대응 소비처). 이게 이후 모든 단계의 기준.
- QA 에이전트는 "존재 확인"(resolver 있나? invoke 부르나?)이 아니라 **"양쪽 동시 읽기"**(생산자 응답 shape ↔ 소비자 접근 경로를 같이 열고 글자 단위 비교)를 한다.
- QA는 전체 완성 후 1회가 아니라 **각 모듈 완성 직후 incremental**하게. 초기 불일치의 후속 전파를 막는다.
- QA 에이전트는 `general-purpose` 타입(검증 스크립트 실행 필요). `Explore`는 읽기 전용이라 부적합.

### ③ 순차 파이프라인이 병렬보다 경계면을 줄인다
- 생산자→소비자 순서를 **의도적으로 강제**하면, 소비자가 설계상의 *계약*이 아니라 생산자가 확정한 *실제* 산출물을 읽는다 → 추측 제거.
  - 예: backend→frontend 순서. frontend가 `02_backend_report.md`의 실제 응답 shape을 읽어 `invoke().content` 접근을 맞춘다.
- 병렬(생산자 ∥ 소비자)이 이득이 되려면 둘이 **실시간으로 산출물(shape)을 교환**할 수 있어야 한다(=팀 통신). 교환 채널이 없으면 양쪽이 계약만 보고 독립 작업하다 실제 구현이 미세하게 벗어나는 순간 경계면 버그.
- 결론: 팀 통신이 없으면 **순차가 더 안전**. 병렬은 팀 모드를 쓸 수 있을 때만.

### ④ 파일 기반 통신 — "산출물의 명확성이 곧 통신"
- 순차/서브에이전트 모드엔 `SendMessage`가 없다. 약속된 경로의 **리포트 파일**이 통신 수단이다.
- 리더(오케스트레이터)가 한 단계의 산출물에서 핵심(실제 shape, 검증 실패 목록)을 추출해 **다음 에이전트 프롬프트에 주입**해 중계한다.
- QA 리포트는 모호한 "안 맞음"이 아니라 `파일:라인 + 불일치 + 수정 방법`. 그래야 리더가 보고 담당 에이전트를 재호출할 수 있다.

### ⑤ 작업 디렉토리는 기능별 서브디렉토리
- 평면 `_workspace/01_...`는 두 기능을 동시/연속 작업할 때 충돌한다.
- `_workspace/<feature-slug>/01_...` 로 격리. 리더가 기능명→kebab-case 슬러그를 정하고 모든 에이전트 프롬프트에 작업 디렉토리를 주입.
- 에이전트/스킬 정의에는 `_workspace/<feature>/NN_...` 플레이스홀더로 일반화, 리더가 실제 슬러그로 치환.

### ⑥ 에이전트 ↔ 스킬 분리, 그리고 프로젝트 특화
- **에이전트(`.md`)** = 정체성 · 작업 원칙 · 입출력 프로토콜 · 협업 프로토콜(누가/누구와 어떻게).
- **스킬(`SKILL.md`)** = 실행 절차 · 패턴 · 체크리스트(구체적으로 어떻게). 중복 없이.
- description은 **적극적("pushy")**으로 — 하는 일 + 구체적 트리거 상황 + **후속 작업 키워드**("다시", "수정", "보완", "~만 다시"). 안 그러면 후속 요청이 트리거 안 됨.
- **프로젝트 특화 지식을 코드에서 캐내 박아라**: 네이밍 비일관(예외 함수명), 문서와 다른 실제 경로(빈 스텁), 수정 금지 공통 경로, 성능 제약(N+1 회피·캐시 패턴). 일반론으로는 절대 안 나오고, 이게 하네스 실효성의 대부분.

### ⑦ 하네스는 진화하는 시스템
- `CLAUDE.md`에 **포인터(트리거 규칙) + 변경 이력 테이블**만 등록(에이전트/스킬 목록은 중복이니 넣지 않음).
- 매 실전 가동 후 문서↔실행 불일치를 교정하고 변경 이력에 날짜·대상·사유를 남긴다. 같은 피드백이 2회 반복되면 진화 트리거.

### ⑧ 사실 정정은 grep 전수 동기화로 (부분 수정 = drift 씨앗)
- 하네스 문서의 사실(경로·규칙)을 정정할 때 **한 파일만 고치면 나머지가 drift로 남는다.** 같은 사실을 언급하는 모든 에이전트/스킬/CLAUDE.md를 grep으로 전수 찾아 한 번에 동기화하라.
- 실사례(moves-workforce i18n): 2026-05-29에 "merge 소스는 `locales/kr`·`en`, `locales/script`는 빈 스텁"을 발견하고 스킬 1곳만 정정 → 에이전트 3 + 스킬 2 + CLAUDE.md 본문에 옛 경로가 남음 → 이후 작업에서 `locales/script/*.json`에 죽은 스텁 파일들이 실제로 생성됨(번역 미반영 위험). 2026-06-11 감사에서 전수 동기화.
- **스킬 frontmatter 파싱도 감사 항목이다.** `---`가 `/---`로 1글자 깨지면 에러 없이 description만 조용히 미노출 → 트리거가 약해진다. 스킬 목록에 description이 제대로 보이는지 확인하라.

## 하네스 점검 체크리스트 (다른 프로젝트에서 빠르게)
- [ ] 런타임이 커스텀 agent_type / 팀 통신을 받는가? → 주 실행 모드가 실제 동작과 일치하는가(폴백이 각주로 숨어있지 않은가)? **(런타임 능력은 변하니 점검 때마다 재확인)**
- [ ] 모든 스킬 frontmatter가 정상 파싱되어 description이 노출되는가?
- [ ] 과거에 정정한 사실이 모든 파일에 반영됐는가(grep 전수 확인)?
- [ ] 경계면 계약 표가 설계 산출물에 명시돼 있는가? QA가 교차 비교(양쪽 읽기)를 하는가?
- [ ] 생산자→소비자 순서가 강제돼 소비자가 실제 산출물을 읽는가?
- [ ] 작업 디렉토리가 기능별로 격리돼 있는가?
- [ ] 스킬 description에 후속 작업 키워드가 있는가?
- [ ] 프로젝트 특화 디테일(네이밍/경로/성능/금지사항)이 박혀 있는가, 일반론만 있는가?
- [ ] CLAUDE.md에 포인터+변경이력이 있는가?
