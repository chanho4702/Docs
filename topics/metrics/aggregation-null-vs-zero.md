# 집계 지표 설계 — "모름"과 "0"을 섞지 않기

> 사례: [[2026-08-03-team-analytics]] · [[2026-06-11-analysis-review]] · [[moves-workforce]]

같은 프로젝트에서 **네 번 이상 반복된 계열의 사고**를 정리한다. 에러가 나지 않고 숫자만 조용히 틀리기 때문에
발견이 늦고, 발견돼도 "계산이 좀 이상한데" 수준으로만 인지된다.

---

## 규칙 1 — `null`(모름)을 `0`으로 채우지 마라

```js
const teamEffort = rows.reduce((s, r) => s + (r.effortMd ?? 0), 0);   // ✗
```

배치가 아직 안 돌아 값이 없는 팀이 **"공수 0인 팀"** 으로 화면에 나간다. 사용자는 그것을 사실로 읽는다.

- 기여한 행이 하나도 없으면 → **`null`(집계 전)**, `0` 이 아니다
- 일부만 없으면 → 있는 값만 합산하고 **빠진 개수를 함께 노출**한다(조용히 삼키지 않는다)
- 차트에서도 마찬가지 — **막대 높이 0은 "값이 0"이라는 주장**이다. 집계 전이면 시리즈에서 빼고 안내한다

## 규칙 2 — 그런데 **"알려진 0"을 `null`로 만들면 분모까지 잃는다**

규칙 1을 오래 지키다 보면 정반대 실수가 나온다. 실제 사례:

```js
// 지연율 = 지연 공수 / 전체 공수
delayedEffortMd: isDelayed ? effortMd : null,   // ✗ 정상 프로젝트를 null 로
```

집계 함수가 **분자·분모가 둘 다 숫자인 행만** 누적하면, 정상 행이 **분모에서도 빠진다.**

```
지연 5MD + 정상 5MD 인 팀  →  5/5 = 100%     (실제 50%)
```

**정상 프로젝트의 지연 공수는 "모름"이 아니라 알려진 `0`** 이다.

> 💡 **판단 기준**: 그 값을 **계산할 수 있는데 결과가 0**이면 `0`. 계산할 재료가 **아직 없으면** `null`.

## 규칙 3 — 비율 필드는 분자와 분모가 **같은 행 집합**을 봐야 한다

규칙 2의 일반형이다. 분자만 조건부로 `null` 로 만들면 그 행이 분모 계산에서도 탈락한다.
비율을 만들 때는 **분자·분모를 같은 시점에 같은 조건으로** 만들어라.

## 규칙 4 — 비율은 계층으로 더할 수 없다

팀 → 본부 롤업에서 하위 비율을 평균 내면 틀린다. **분자·분모를 각각 합산해 두고 `Σ/Σ` 로 재계산**한다.

산술평균이 특히 위험한 경우: 분모가 0에 가까운 구성원이 섞일 때.
기간 내 참여가 없는 사람은 개인 가동률 0%인데, 산술평균은 그 0을 그대로 넣어 팀 평균을 끌어내린다.
가중(`Σ/Σ`)은 분모에 그 사람 가용량을 더해 "가용했지만 안 쓴 만큼"으로 정확히 반영한다.

> 실무: 집계 API에 **산술평균 옵션 자체를 두지 않는 것**이 안전하다. 두면 언젠가 쓰인다.

## 규칙 5 — 합산 가능 여부를 **상수로 고정하고 테스트로 감시**하라

"사람 단위 값이니 팀으로 더하면 되겠지"가 지표마다 틀린다. 판정 기준은 **"사람 간 겹치는가"**:

| 겹치지 않음(합산 가능) | 겹침(합산 불가) |
|---|---|
| 개인 워크로그 시간·공수 | 이슈 건수(한 이슈에 여러 명 참여 → 중복 계상) |
| 개인 가용일 | 참여 프로젝트 수 |
| 개인 연차 차감 | 공휴일 일수(팀 전원 공통 → 인원수만큼 부풀음) |

주석만으로는 다음 사람이 다시 더한다. **`ADDITIVE_SUM_FIELDS` / `NON_ADDITIVE_FIELDS` 를 상수로 두고
교집합이 비었는지 테스트로 감시**한다.

⚠ 목록에 넣는 **이유도 정확히 적어라.** "합산하면 틀려서"와 "전용 경로가 이미 처리해서 이중 계상"은
결과는 같지만 근거가 다르다. 이유가 틀리면 다음 사람이 잘못된 판단을 한다.

## 규칙 6 — 필터는 **집계 진입 전**에 건다

결과를 나중에 거르면 두 가지가 깨진다:

1. **비율의 분모가 전체로 남는다** — 5개 팀 중 2개만 보는데 분모는 5개 팀 합계
2. 집계 함수 내부에 **복원 로직**이 있으면 걸러낸 항목이 되살아난다
   (실제 사례: 메타 사전에만 필터를 걸었더니 `if (!meta.has(key)) meta.set(key, {name: null})` 세 줄이
   비가시 팀을 "알 수 없는 팀"으로 복원 — **이름만 가려지고 수치는 그대로 노출**)

→ 집계 함수가 **스코프를 필수 인자로 받고 미전달 시 throw** 하게 만들면 구조적으로 막힌다.

## 테스트 — 기대값을 검증 대상 함수로 만들지 마라

```js
expect(getQuickRange('lastMonth', NOW)).toEqual({
    start: fmt(new Date(2026, 6, 1)),   // ✗ 기대값도 같은 fmt 를 쓴다
    end:   fmt(new Date(2026, 7, 0)),
});
```

**동어반복이다.** `fmt` 를 무엇으로 바꿔도 통과한다. 실제로 이 형태가 UTC 하루 밀림 버그
(`toISOString()` 이 KST 로컬 자정을 전날로 만듦 → "지난 달"이 6/30~7/30)를 **정답으로 고정**하고 있었다.

> 💡 날짜·금액처럼 **사람이 검산할 수 있는 값은 리터럴로** 쓴다. 경계(월말 30/31일·연도 경계·자정 직후)를 함께 넣는다.

같은 계열: **characterization test 는 "현행 동작"을 기록하는 것**이다. 설계서에 적힌 의도가 아니라
**실제 코드를 읽어** 쓴다. 다르면 코드가 정답이고, 그 차이 자체가 발견이다.

## 표기 — 산출 근거를 화면에 밝힌다

숫자가 맞아도 **기준이 다르면 사용자는 틀렸다고 판단**한다.

- **직속 / 누적을 분리 표기** — 하나만 보이면 "세로로 더하면 왜 안 맞나"가 된다
- **인원 수가 여러 종류면 각각 라벨을 붙인다** (조직 인원 / 참여 인원 / 지표 산출 대상 인원)
- **필터에 반응하지 않는 축은 배지로 명시** — 숫자는 그대로 두되 무관함을 밝힌다
- **잘랐으면 몇 개가 빠졌는지 적는다**(상위 N개·기타 묶음) — 조용한 절단은 "전부 봤다"로 읽힌다
- 집계 기준 시점("현재 소속 기준" 등)을 밝힌다 — 과거 이력이 없으면 그 사실 자체가 정보다
