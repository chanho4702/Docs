# 가짜 안전망 — 테스트가 green인데 아무것도 안 지키는 자리

> 출처: [[2026-08-10-license-kernel-implementation]](라이선스 게이트 도입에서 6곳 발견),
> [[2026-08-12-license-expiry-in-key]](뮤테이션이 **"정확히 2건만"** 깨뜨리는지로 방어 범위를 확인 —
> 더 깨지면 과잉 결합, 안 깨지면 가짜 안전망. 캐시가 낀 곳은 실기동으로 한 번 더),
> [[2026-08-03-team-analytics]](기대값을 검증함수로 만든 테스트가 버그를 정답으로 고정),
> [[atlassian-ao-schema-constraints]]("API 200"≠"화면 정상")

테스트가 **통과하는데도** 결함이 사는 자리는 몇 가지 정해진 모양이 있다. 공통점은
**"테스트가 검증한다고 믿는 것"과 "실제로 검증하는 것"이 다르다**는 것이다.

---

## 1. 다른 계층이 이미 결론을 내고 있다

"A가 B보다 먼저 실행된다"를 검증하려 했는데, **더 앞의 계층이 이미 같은 결과를 내주는** 경우.

**사례**: Spring에서 "라이선스 인터셉터는 인증 뒤에 서야 한다"를 *인증 없는 요청 → 401* 로 테스트했다.
Security 필터 체인은 `DispatcherServlet`보다 앞이라 **인터셉터 순서를 뒤집어도 401**이 난다.

👉 **A와 B가 정말 같은 링에서 겨루는지부터 확인하라.** 필터 vs 인터셉터, 프록시 vs 대상,
DB 제약 vs 애플리케이션 검증 — 계층이 다르면 순서 테스트는 성립하지 않는다.
위 사례에서 진짜 링은 *다른 인터셉터*(세션 검사)와의 겨룸이었다.

**발견법**: 검증 대상 순서를 **일부러 뒤집고** 테스트를 돌린다. 통과하면 그 테스트는 가짜다.

---

## 2. 새 전역 게이트가 기존 테스트를 거짓 통과시킨다

전역 차단(라이선스·권한·rate limit)을 추가하면, **그 게이트와 같은 코드로 실패하던** 기존
"거부 테스트"가 전부 무의미해진다.

**사례**: 라이선스 잠금도 바디 `code=403`. 그러자 "일반 USER는 거부된다"류 권한 계약 테스트가
**권한 검사를 통째로 지워도 green**이 됐다. 라이선스가 대신 403을 내주기 때문이다.

👉 **게이트를 켠 직후 "무엇이 여전히 통과하는가"를 의심하라.** 특히 같은 상태코드·에러코드를
쓰는 테스트가 위험하다. 해법은 **테스트 환경에서 게이트를 정상 통과 상태로 열어 두는 것**
(우회 스위치가 아니라 실제 유효한 상태를 심는 쪽. 스위치를 만들면 게이트 회귀를 영영 못 잡는다).

---

## 3. 컴파일러는 "구현했는지"만 알지 "호출했는지"는 모른다

데코레이터·프록시·어댑터처럼 **N개 메서드를 빠짐없이 감싸야 하는** 구조.

- 인터페이스에 추상 메서드만 있으면 컴파일러가 *구현 누락*은 잡아준다.
- 그러나 **`default` 메서드가 하나라도 있으면 누락해도 컴파일된다** → 그 경로만 조용히 열린다.
- 더 흔한 것: 오버라이드는 했는데 **위임만 하고 검사를 빠뜨리는 것**. 어떤 컴파일러도 못 잡는다.

👉 **개별 메서드를 나열하는 테스트 대신 리플렉션으로 인터페이스 전 메서드를 훑어라.**
차단 상태를 만들고 전 메서드를 호출해 "전부 막히는가"를 본다. 나중에 메서드가 추가돼도
테스트가 자동으로 따라간다.

```java
for (Method m : port.getDeclaredMethods()) {
    try { m.invoke(decorator, defaultArgs(m)); unguarded.add(m.getName()); }  // 예외 없음 = 게이트 통과 안 함
    catch (InvocationTargetException e) { if (!(e.getCause() instanceof BlockedException)) unguarded.add(...); }
}
assertThat(unguarded).isEmpty();
```

같은 부류: **`@Primary`/빈 선택이 실제로 이기는지**는 별도 검증이 필요하다. 데코레이터 단위 테스트는
직접 `new` 해서 보므로 `@Primary`가 빠져 게이트가 통째로 무력화돼도 전부 통과한다.

---

## 4. 응답만 보고 저장된 값을 안 본다

"기록한다"는 기능은 **응답이 아니라 저장 결과**로 검증해야 한다.

**사례**: 감사 컬럼 `registered_by`가 항상 null이었다(JWT에 `username` 클레임이 없어
`getUsername()`이 언제나 null). API는 정상 200을 냈고 IT는 응답 shape만 봤다.
null이어도 INSERT는 성공한다.

👉 **nullable 컬럼에 기록하는 코드는 테스트가 그 컬럼을 읽어야 한다.** NOT NULL이면 DB가
잡아주지만, 감사·메타 컬럼은 대개 nullable이라 아무도 안 잡는다.

---

## 5. 정상 입력만 보낸다 (에러 계약 미검증)

에러 응답 규약을 정해 둔 프로젝트(예: "비즈니스 오류도 HTTP 200 + 바디 code")에서
**catch-all로 빠지는 예외는 곧 계약 위반**이다.

**사례**: 요청 본문 타입이 어긋나자 `HttpMessageNotReadableException`이 전역 catch-all로 빠져
**실제 500 "Internal server error"**가 나갔다. 사용자가 고칠 수 있는 입력 오류인데 화면은
재시도 외에 안내할 것이 없다.

👉 **깨진 입력을 일부러 보내는 테스트를 최소 한 건 두라.** 특히 파일 업로드·타입 불일치·빈 본문.
같은 자리에서 "없는 경로가 404가 아니라 500"인 것도 함께 드러난다.

---

## 6. mutation test 를 습관으로

위 다섯을 **전부 잡아낸 방법이 하나**다: **코드를 일부러 망가뜨리고 그 테스트만 실패하는지 확인.**

| 망가뜨릴 것 | 기대 |
|---|---|
| 순서 의존 코드의 순서를 뒤집는다 | 순서 테스트 1건만 실패 |
| 가드/검사 한 줄을 지운다 | 그 경로 테스트만 실패 (이름까지 지목되면 더 좋다) |
| 제약을 지키는 코드(선-해지-후-삽입 등)를 뺀다 | DB 제약 위반으로 해당 1건 실패 |
| 구조 규칙 위반 코드를 넣는다 | ArchUnit 해당 규칙만 실패 |

**전부 통과하면 테스트가 아니라 장식이다.** 특히 새로 추가한 안전장치(게이트·가드·인터셉터)는
"켰다"는 사실만으로 안심하기 쉬워서, 이 확인을 붙이는 값어치가 가장 크다.

⚠️ **망가뜨린 코드는 반드시 되돌리고 `git diff`로 확인할 것.** 커밋에 섞이면 최악이다.

---

## 7. 곁가지 — 플레이키를 mutation 과 혼동하지 말 것

기준 시각을 **테스트와 구현이 각각 읽으면** 그 사이 tick 경과에 따라 결과가 갈린다
(예: `daysRemaining`이 99/100). 단독 실행은 통과하고 전체 실행에서 실패한다.

👉 표시용 파생값(남은 일수 등)은 **정확값이 아니라 범위로 단언**하고, 왜 그런지 주석에 남긴다.
하루 오차가 계약이 아니라면 그것을 계약으로 만들지 말 것.
