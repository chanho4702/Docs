# Forge 앱 REST API (`core:apiRoute`) — 외부 노출

> 2026-09-16 · Moves Workforce에서 실측. 전체 조사 문서는 리포지토리 `_workspace/api-exposure/API_EXPOSURE.md`.
> 관련: [[forge-licensing]] · [[forge-readonly-appfield-write]] · [[moves-workforce]]

Forge 앱의 기능을 외부 시스템에 열어야 할 때 쓰는 모듈. 웹트리거의 대체재이고, 실질적으로 유일한 선택지다.

## 왜 웹트리거가 아닌가

웹트리거는 플랫폼 인증이 **전혀 없다**. URL만 알면 누구나 호출되므로 키 검증을 직접 짜야 하고, 무엇보다 **호출자 사용자 컨텍스트가 없어 전부 `asApp`으로 돈다.** principal 기반 권한 판정을 태울 수 없다. Runs on Atlassian 기준으로도 `dynamic` 웹트리거는 실격이다.

`apiRoute`는 반대다. Atlassian OAuth 2.0(3LO) 토큰을 게이트웨이가 검증하고 통과한 요청만 우리 함수에 닿는다. 토큰 발급·갱신도 전부 Atlassian 몫이다.

## 밟은 함정들

**① 커스텀 스코프는 매니페스트만으로 안 된다.**
`scopes: [read:x:custom]` 을 써 놓고 배포하면 `Deployment failed due to missing scopes`로 죽는다. 별도 `custom-scopes.yaml` + `forge custom-scopes create -e <env> -f <file>` 로 **환경마다 먼저 등록**해야 한다.

**이게 중요한 이유: 등록한 스코프는 삭제도 이름 변경도 불가능하다.** 환경당 20개가 상한이다. 시험 삼아 만든 이름이 영구히 한 칸을 차지한다. 이름 체계를 확정하고 등록할 것.
(`displayName` 패턴은 `^[a-zA-Z0-9\s:_\-.]+$` — 괄호를 넣으면 검증 실패한다.)

**② 배포가 메이저 버전을 강제한다.**
`MAJOR_VERSION_RULE` 승인 없이는 배포가 막힌다. 사유가 "스코프 증가"가 아니라 **`core:apiRoute` 모듈 사용 그 자체**다. 라우트를 몇 개 열든 첫 도입에서 한 번 올라간다. 고객사는 관리자가 업데이트를 승인해야 새 버전을 받는다.

**③ Runs on Atlassian 배지는 안 깨진다.**
`apiRoute`를 넣고도 `forge eligibility`가 계속 적격으로 보고했고 관리 콘솔의 배지도 그대로였다. 실격 사유는 `remotes`와 `dynamic` 웹트리거 쪽이다. 걱정할 대상을 혼동하지 말 것.

**④ 관리자 스위치가 설치본 단위로 따로 있다.**
Atlassian 관리 → 연결된 앱 → 해당 앱(환경별로 항목이 갈린다) → 세부 사항 하단 「앱 REST API」. 기본 **사용 중지**다. 켜야 기본 URL이 나온다.

다만 안내문이 중요하다. **연동을 만드는 사람은 관리자로 한정되지 않는다** — 조직의 확인된 계정을 가진 구성원 누구나 만들 수 있다. 관리자는 문을 열지 말지만 정하고, 그 뒤 범위를 좁히는 책임은 전부 우리 코드에 있다.

## ⚠ 가장 중요한 것 — 기존 권한 체계가 통째로 우회된다

`apiRoute`는 resolver와 **완전히 별개인 진입점**이다. `guardedDefine`, `PermissionMap`의 deny-by-default, `resolvePrincipal`, 라이선스 검사가 **하나도 실행되지 않는다.**

"가드 통과 ≠ 데이터 범위 확정"이라는 기존 교훈이 여기선 한 단계 더 나아간다. **가드 자체가 없다.**

핸들러마다 신원 확정 → 작업 권한 → 프로젝트·팀 스코프 → 급여·원가 정책 → 라이선스를 직접 통과시켜야 한다. 그리고 요청 body의 `accountId`를 principal로 신뢰하면 **임의 사용자 사칭**이 된다. 신원 미확정이면 거부(fail-close).

같은 데이터를 내주는 경로가 resolver와 REST 둘로 늘어나므로, **판정 로직을 공용 함수로 뽑아 두 경로가 같은 것을 보게** 해야 한다. 한쪽만 막히는 사고의 전형적인 조건이다.

## 게이트웨이 동작 (실측)

토큰 없음 / 엉터리 토큰 / 선언 안 한 경로 — 셋 다 `401 {"code":401,"message":"Unauthorized"}`. 우리 함수는 실행되지 않고, 없는 경로도 404가 아니라 401이라 **경로 존재 여부조차 새지 않는다.**

## 아직 모르는 것

**핸들러가 호출자 `accountId`를 받는지, 안에서 `asUser()`가 호출자 자격으로 도는지 공식 문서에 없다.** 튜토리얼 예제도 `req`를 문자열로 찍기만 한다.

이 답에 설계가 갈린다. 신원이 들어오면 기존 principal 체계를 거의 그대로 재사용할 수 있고, 안 들어오면 **스코프 설계가 곧 권한 설계**가 되는 별도 모델을 짜야 한다. 확인하려면 3LO 연동을 만들어 실호출해야 한다.

## 교훈

- 공식 문서에 **핸들러 계약이 빠져 있는 Preview 기능**은 설계 전에 프로브를 배포해 실측하는 게 맞다. 문서만 보고 설계하면 권한 모델을 통째로 다시 짜게 된다.
- **되돌릴 수 없는 등록**(커스텀 스코프)이 섞인 기능은 시험용 이름을 함부로 만들지 말 것.
- 조사용 임시 엔드포인트는 **환경변수 가드**로 운영 유입을 막고(`PROBE_ENABLED`), 인자를 덤프할 때 **값이 아니라 형태만** 반환한다. 런타임이 인자에 토큰을 실어 보내면 그대로 외부로 나간다.
