# APM 보존·선별 수집·장기 상세 조회 설계

작성: Codex · 2026-09-17 · 상태: **후속 작업용 설계 초안 / 구현 보류**

사용자 요청: APM 데이터를 많이 저장하는 위험과 7일 상세 조회 한계를 검토한 뒤, 나중에 작업할 수 있도록 설계를 남긴다. 이번 요청은 문서 작성이며 코드·DB·설정 변경이나 배포 승인이 아니다. 30·90일 등 아래 수치는 **권고 초깃값이며 고객 요구 및 용량 검증 후 확정**한다.

## 1. 목표와 완료의 의미

최근 장애뿐 아니라 다음 주·월간 검토에서 발견한 문제도 상세 요청 단위로 조사할 수 있게 한다. 동시에 데이터 유입 폭증이나 아카이브 장애가 DB 전체 장애로 번지지 않게 한다.

- 성능 통계: 기존 1분 7일 / 5분 30일 / 1시간 400일을 기본안으로 유지.
- 상세 트레이스: 정상 요청은 선별하여 발생 시점부터 총 30일, 오류·느린 요청은 우선 선별하여 총 90일 접근 가능하게 한다.
- 최근 7일은 온라인 DB, 그 이후는 아카이브 검색·비동기 복원으로 접근하는 안을 우선 채택한다. **30일 모두 즉시 조회한다는 약속은 아니다.**
- 조사 자료는 사용자가 별도로 보존할 수 있다.
- 표본 비율·유실·보존 만료·복원 필요를 구분해 보여 준다.
- 파일 다운로드만 완성한 단계에서는 제품에 “30/90일 상세 분석 지원”을 표시하지 않는다.

## 2. 현재 확인된 사실과 설계 경계

| 항목 | 확인 내용 | 근거 |
|---|---|---|
| 메트릭 보존 | 7/30/400일 기본값, 실제 삭제는 retention 잡 options | `ApmRetentionJob`, `ApmRetentionService` |
| 조회 해상도 | `ApmResolution`에도 보존 일수 사본이 있음 | 값 변경 시 삭제와 조회가 어긋날 수 있음 |
| 트레이스 보존 | span·summary 각각 기본 7일, 날짜별 파티션 DROP | V44, retention 잡 |
| tail sampling | 오류·지연·정상 확률 정책, decision_wait=10s, num_traces=50000 | `collector-template.yaml` |
| 수집 재시도 | 기본 템플릿 영속 큐 5000, 최대 재시도 30분 | 같은 템플릿; 실제 배포 설정은 별도 확인 필요 |
| 콜드 아카이브 | 기존 설계는 파일 기록·DROP 게이트 중심, restore는 1차 제외 | ZM-156 설계·보고서 |
| 용량 | 합성 1분 메트릭 하루 1,404만 행 약 9.6GB, 행당 약 686B | R3; 운영 실측 및 스팬 용량이 아님 |
| 역할 | COLLAB STATUS는 SOLO-CLAUDE, Codex 검수 역할 | 구현 재개 시 최신 상태 재확인 |

기존 문서의 코드 주석과 감사 결과를 실제 운영 관측값으로 취급하지 않는다. 특히 tail sampling이 이미 있다는 사실은 중요한 트레이스가 전부 도착하거나, 선별 사유가 BE에 정확히 전달된다는 보장이 아니다.

### 기존 설계와의 관계

- [콜드 아카이브 설계](%EC%84%A4%EA%B3%84-APM-%EC%BD%9C%EB%93%9C-%EC%95%84%EC%B9%B4%EC%9D%B4%EB%B8%8C-%EB%B3%B4%EC%A1%B4-%EB%A7%8C%EB%A3%8C-%EC%A0%84%EC%97%90-%ED%8C%8C%EC%9D%BC%EB%A1%9C-%EB%B3%B4%EA%B4%80-%28ZM-156%29.md): writer·원장·경로 검증·DROP 게이트·manifest를 재사용한다. 이 문서는 **보존 등급, 장기 검색·복원, 사용자 지정 보존, 용량 제어**를 추가한다.
- [자빅스 아카이빙](%EC%84%A4%EA%B3%84-%EB%8D%B0%EC%9D%B4%ED%84%B0-%EC%95%84%EC%B9%B4%EC%9D%B4%EB%B9%99-%28%EA%B0%90%EC%82%AC-%EA%B7%9C%EC%A0%9C-%EB%8C%80%EB%B9%84-%EC%9E%A5%EA%B8%B0-%EB%B3%B4%EA%B4%80%29.md): 공용 기반을 공유한다. APM 정책을 Zabbix 보존 정책에 자동 적용하지 않는다.
- 기존 문서 §5.5의 “7일 보류 후 DROP”은 미확정 권고다. 본안에서는 §7의 명시적 모드로 대체한다. 구현 전 두 문서의 결정을 동기화해야 한다.
- 기존의 아카이브 비활성 상태에서 현재 동작을 유지한다는 원칙은 유지한다. 신규 기능을 켜지 않은 설치본은 기존 7일 정책이 계속 적용된다고 표시한다.
- 기존 ZM-156 구현과 본 설계의 복원 조회는 단계가 다르다. ZM-156만 완료했다고 본 설계 전체가 완료된 것으로 처리하지 않는다.

## 3. 보존 정책 초안

| 종류 | 온라인 보존 | 전체 접근 기간 | 원칙 |
|---|---:|---:|---|
| 1분 메트릭 | 7일 | 7일 | 원본 장기 보관은 별도 옵트인 |
| 5분 메트릭 | 30일 | 30일 | 인스턴스 축 소실 등 기존 집계 의미 유지 |
| 1시간 메트릭 | 400일 | 400일 | 장기 추세 |
| 정상 트레이스 | 7일 | 발생부터 30일 | 서비스별 확률 샘플링 |
| 오류·느린 트레이스 | 7일 | 발생부터 90일 | 우선 선별, 폭증 시 대표 표본 및 제한 공개 |
| 사용자 지정 보존 | 복원 캐시와 별도 | 지정일부터 기본 90일 | 명시적 연장·해제, 영구 보관 기본 금지 |

총 30일은 온라인 7일에 30일을 더한 37일이 아니다. 기본 만료 기준은 trace의 최초 관측 시작 시각이다. 사용자 지정 보존만 지정일 기준이다. 일 단위 파일/파티션 경계 때문에 최대 약 하루 더 보관할 수 있으며, 만료일보다 일찍 삭제해서는 안 된다. UI는 실제 `expiresAt`을 표시한다.

사용자 지정 보존은 아직 존재하는 자료에만 가능하다. 이미 삭제되거나 수집 전 제외된 요청을 복구할 수 없다. 기존 설치본의 만료 자료도 정책 활성화로 되살아나지 않는다.

RUM 원본·브라우저 오류, 로그, SQL/오류 지문 본체·파생 집계, 배포·작업 이력의 보존은 이번 초안으로 일괄 변경하지 않는다. 트레이스 보관 파일에서 독립 해석에 필요한 참조 정보는 동봉한다. RUM과 서버 트레이스의 연계 장기 보존은 후속 범위로 표시한다.

### 정책 정본

논리 구성요소 `ApmRetentionPolicyResolver`를 core에 둔다. 수집·분류·아카이브·DROP·조회·설정 화면이 동일한 유효 정책을 읽는다. 이름 및 실제 패키지는 구현 착수 때 확정한다.

- 전역 기본 + 서비스별 허용된 재정의. 서버 상한을 서비스 옵션이 초과할 수 없다.
- 정책 버전, 적용 시작 시각, 변경자, 변경 사유를 기록한다.
- 데이터/아카이브에는 적용된 정책 버전과 만료일을 남긴다.
- 기간 확대는 남아 있는 자료에만 적용 가능. 이미 발행된 파일까지 연장할지는 별도 재평가 작업으로 처리한다.
- 기간 축소는 삭제 예정 날짜·규모·보존 지정 충돌을 사전 산출한 뒤 적용한다. 설정 저장과 즉시 대량 삭제를 결합하지 않는다.
- 첫 도입 시 기존 scheduler options를 유효 정책으로 이관한다. `ApmResolution`의 상수 사본도 제거하거나 resolver를 소비하도록 바꾼다. 두 경로를 동시에 편집 가능한 정본으로 남기지 않는다.

## 4. 선별 수집과 트레이스 완전성

### 보존 등급과 판정

등급은 `NORMAL`, `IMPORTANT`; 추가 보존은 별도 pin 레코드로 관리한다. `IMPORTANT` 사유는 `ERROR`, `SLOW`, `ERROR_AND_SLOW`, 사유 판정의 신뢰도는 `OBSERVED`, `INFERRED`, `UNKNOWN`으로 구분하는 초안이다.

- Collector의 샘플링 사유를 단순히 추측해서 확정값으로 기록하지 않는다. 버전별 사유 전달 가능 여부를 검증하고, 불가능하면 BE가 실제 수신 span의 status 및 trace duration으로 판정한다.
- 지연 기준은 서비스별 threshold와 정책 버전을 보존한다. 이후 기준 변경이 과거 등급을 자동 하향하지 않는다.
- 부분 trace에서 늦게 ERROR가 도착하면 NORMAL→IMPORTANT로 승격한다. 한 번 승격한 trace는 자동 하향하지 않는다.
- 승격은 ERROR delta만 오래 남기는 것으로 끝내지 않는다. 아직 존재하는 이전 세대의 모든 관련 span을 IMPORTANT 파일로 복사·검증하고 locator를 전환할 때까지 기존 NORMAL 파일을 참조 보호한다. 이미 만료된 span은 복구할 수 없으므로 PARTIAL과 누락 기간을 표시한다. 복사 완료 후 원래 NORMAL 파일의 보호를 해제한다.
- 동일 traceId의 모든 span이 같은 tail sampler에 도착하도록 라우팅을 검증한다. head sampling으로 사라진 trace는 후단에서 복원할 수 없다.
- 10초 decision window 밖의 span, 누락된 부모, 여러 날짜에 걸친 trace를 테스트한다. 완전성은 `UNKNOWN/PARTIAL`을 표현할 수 있어야 하며 수신 종료를 확정할 근거 없이 COMPLETE로 표기하지 않는다.

### 예산과 통계

- 서비스별 일일 저장 바이트 예산, 전역 저장 예산, 순간 수신율 상한을 함께 둔다. 바이트 계측이 추정이면 오차와 산정 방식을 명시한다.
- 정상 표본 비율은 임의 숫자를 확정하지 않고 용량 시험으로 정한다. 정상 요청이 적은 서비스에는 최소 대표 표본 예산을 둔다.
- 오류 폭증 시 오류 지문·시간 구간별 표본과 새로운 유형의 표본을 확보한다. 예산 초과 구간·선별 비율·누락 건수를 기록한다.
- 요청 수·오류율·지연 통계는 선별된 trace 집합과 분리한다. 전체 요청을 반영하는 메트릭 경로를 사용하고 그 경로의 누락도 독립 표시한다. 전체 메트릭 부재 시 추정치 또는 확인 불가로 표시한다.
- URL/SQL 정규화와 허용 태그를 적용한다. 사용자 ID·요청 ID 등 무한히 증가하는 값을 메트릭 차원에 허용하지 않는다.
- DB 저장을 줄여도 Collector까지의 네트워크와 tail sampler 메모리는 줄지 않을 수 있다. 수집 계층의 부하도 별도 측정한다.

## 5. 저장·아카이브 구조

### 채택안: 온라인 7일 유지 + 보존 등급별 파일 + 검색 카탈로그

기존 span/summary 일 파티션은 유지한다. 온라인 테이블 전체를 90일로 늘리거나 일 파티션에 pin 1건이 있다는 이유로 전체 날짜를 계속 보관하지 않는다.

제안하는 논리 레코드(테이블명·컬럼·인덱스는 착수 때 DDL로 구체화):

| 레코드 | 책임 |
|---|---|
| `apm_retention_policy` | 버전별 유효 정책 및 전역/서비스 범위 |
| `apm_trace_retention` | trace 식별자, 최초 시각, 등급·사유·정책 버전, 만료일, 수정 세대 |
| 공용 archive 원장 | 파일 ID·경로·크기·체크섬·상태·스키마 버전·coverage·보존 등급·만료일 |
| `apm_trace_archive_locator` | traceId·서비스 범위·시간·요약·파일/청크 위치의 검색 카탈로그 |
| `apm_trace_preservation` | pin 범위·소유자·사유·만료·복사 상태·용량 |
| `apm_trace_restore_job` | 요청자·범위·상태·오류·복원 캐시 만료 |

traceId의 범위는 기존 인증/서비스 모델을 재사용하되, 서비스 간 trace가 서로 다른 접근 범위에 걸치는 경우 권한 필터를 적용한다. traceId 문자열만으로 존재·내용을 공개하지 않는다. 검색 카탈로그도 30/90일 및 pin 기간에 따라 정리하며, 인덱스 용량을 총 예산에 포함한다.

### 아카이브 발행 및 DROP 게이트

1. 만료 예정 원본 파티션을 대상으로 일관된 snapshot에서 읽고, 임시 파일에 streaming 기록한다.
2. 기존 `(dataset, day)` 단위를 `(dataset, day, retentionClass, expiryBucket, accessScope, generation)`으로 확장한다. expiryBucket은 유효 만료일을 일 단위로 올림한 값이다. 서비스별 재정의로 만료일이 달라진 자료는 같은 파일에 섞지 않는다. accessScope는 파일 접근 경계이며 실제 권한 검사는 별도로 수행한다. 이미 발행된 파일에서 일부 trace의 기간이 바뀌면 해당 자료를 새 만료 구간 파일로 복사·검증·locator 전환한 후 이전 참조를 해제한다.
3. trace 검색용 locator와 해당 span 데이터의 연결을 작성한다. 날짜를 넘는 trace는 여러 파일 참조를 허용한다.
4. 파일 크기·행 수·체크섬·manifest·사전의 일관성을 검증하고 최종 파일을 발행한다. 파일 rename과 DB 트랜잭션은 원자적이지 않으므로 중단 시 reconciliation 작업으로 고아 파일/미완료 원장을 정리한다.
5. 검증된 파일과 locator가 모두 사용 가능한 뒤 원장을 VERIFIED로 전환한다.
6. DROP 직전에 소스의 변경 세대와 coverage를 재확인한다. snapshot 이후 추가·수정된 데이터가 있으면 delta 세대를 발행하고 검증할 때까지 DROP을 막는다.
7. 일반 DROP은 원본 파티션의 모든 필수 coverage가 충족되고 진행 중 pin 복사도 안전한 경우에만 허용한다. BEST_EFFORT의 손실 삭제는 §7의 별도 경로로만 허용한다. export·pin·DROP의 경쟁은 같은 파티션 단위 lease/fencing으로 제어한다. 긴 작업은 lease 갱신 또는 TTL 안의 청크 실행이 필요하다.

단순히 “파일이 존재한다” 또는 “어제 export가 성공했다”는 이유로 삭제를 허용하면 안 된다. ingest의 늦은 도착·summary 변경을 함께 막는 최종화 구간이 필요하다. 최종화 중 유입은 durable delta 경로에 저장하거나 재시도 가능한 응답으로 돌려야 하며, 성공 응답 후 버리지 않는다. 소스 수정 세대 갱신은 데이터 쓰기와 같은 트랜잭션에서 보장한다.

만료 파티션의 재생성 여부, 허용 지연 도착 기간 및 이후 거부 사유는 S0에서 확정한다. 오래된 이벤트 하나 때문에 이미 지운 파티션이 무기한 재생성되지 않게 한다.

스팬 JSONL.gz, 요약 CSV.gz, manifest·체크섬·시간대·서비스 이름·스키마/정규화 버전 등 자기 완결 정보를 기존 설계에 맞춰 동봉한다. 단일 거대 gzip 파일은 부분 조회가 비싸므로 일정 크기의 청크로 나누고 locator가 청크를 가리키게 한다.

### 사용자 지정 보존

pin은 전용 보존 파일로 필요한 trace를 복사하고 검증한 뒤 ACTIVE가 된다. REQUESTED/COPYING 상태는 성공으로 표시하지 않는다. 원본/아카이브 삭제와 복사 간 참조 보호를 설정하고, 실패 시 원본의 남은 보존 기간을 알린다. pin 용량·개수·최대 연장 기간에 상한을 둔다.

pin 때문에 오래된 하루치 파일 전체가 무기한 남지 않도록 복사 완료 후 원본 참조를 해제한다. 법적 보존(legal hold)은 별도 정책이며 일반 pin과 동일시하지 않는다.

## 6. 장기 조회와 사용자 화면

- 온라인 기간은 기존 trace 조회를 사용한다.
- 온라인 밖은 locator에서 서비스·시간·traceId 및 최소 요약 조건으로 검색한다. 원문 SQL·span attribute 전체 검색은 1차 제외한다.
- 상세 열기는 restore job을 요청하고 `QUEUED → RUNNING → READY / FAILED / CANCELLED`로 표시한다. 취소·재시도·중복 요청 합치기를 지원한다.
- 복원 자료는 전용 임시 저장소에 둔다. 원래 ingest 테이블에 다시 넣어서 통계·롤업·알람을 재실행하지 않는다.
- 복원 동시 실행 수·파일/압축 해제 크기·시간 범위·캐시 용량·TTL을 제한한다. 실제 수치는 S0 실측에서 정한다.
- 여러 날짜/세대의 span을 합쳐 기존 식별 규칙으로 중복 제거한다. 갱신 세대 우선순위와 충돌 처리 규칙을 계약에 명시한다.
- 서비스 메타 삭제나 이름 변경 뒤에도 권한은 현재 기준으로 판단하고 표시 정보는 보관 사전을 사용한다. 삭제된 서비스의 접근 권한은 관리 정책으로 명시한다.

응답에 필요한 논리 필드: `availability`, `sourceTier`, `expiresAt`, `policyVersion`, `completeness`, `samplingInfo`, `restoreJobId`. 실제 API 경로·nullable·오류 코드는 구현 시 `_workspace/contract_apm-retention-policy.md`로 확정한다. 이 문서는 기존 API를 변경하지 않는다.

표시 상태 초안: `ONLINE`, `ARCHIVED`, `RESTORING`, `EXPIRED`, `NOT_FOUND`, `UNKNOWN`, `STORAGE_UNAVAILABLE`. **trace별 샘플링 제외 여부는 탈락 기록이 없으면 알 수 없다.** 이때 “샘플링 제외됨”으로 단정하지 않고, 시간 구간/서비스의 수집·선별 통계만 보조 설명한다.

권한은 기존 APM 조회·관리 권한을 재사용하고 부족한 보존/복원 관리 권한만 추가한다. 혼합 서비스 파일을 그대로 다운로드시켜 조회 권한을 우회하지 않는다. 접근 범위별 분리 또는 서버에서 허용 자료만 추출하는 방식으로 제공한다.

## 7. 저장 공간과 실패 정책

### 예측·경보

DB, WAL/임시 작업 공간, 아카이브, 복원 캐시의 여유를 따로 측정한다. 같은 디스크라면 합산한다. 현재 사용률뿐 아니라 일일 순증가·보류 증가량·예상 고갈일까지 표시한다. R3 메트릭 수치를 스팬 용량 산정에 전용하지 않는다.

산정식: 온라인 보존량 + 아카이브 보존량 + locator/인덱스 + pin + 복원 캐시 + WAL/작업 여유. 평균과 장애 폭증 조건을 모두 계산하고 압축률·일일 바이트는 실측한다.

### 아카이브 실패 시 동작

| 모드 | 동작 | 사용 조건 |
|---|---|---|
| `PRESERVE` 권고 기본 | 미검증 자료 DROP 금지. 저장 예산 임박 시 정상 트레이스 신규 수집부터 제한, 마지막에는 신규 상세 수집 거부 및 명시적 장애 알림 | 보존 약속을 우선하는 설치본 |
| `BEST_EFFORT` 명시 선택 | 유예 기간/용량 초과 시 미아카이브 자료 삭제 가능. 사유·범위·손실량을 원장과 경보에 기록 | 보존 손실을 허용하기로 설정한 설치본 |

두 모드 모두 실패 첫날부터 경보한다. PRESERVE도 무한 저장이 아니다. 신규 유입 제한과 다른 DB 기능을 위한 예약 공간이 필수다. 공간 보호로 중요한 신규 trace까지 수집하지 못하면 이를 숨기지 않는다. BEST_EFFORT의 유예 수치는 예산과 함께 정하며 기존 “7일” 제안을 자동 확정하지 않는다.

BEST_EFFORT 손실 삭제는 일반 coverage 검증을 성공으로 위조하지 않고 `LOSS_AUTHORIZED` 판정과 별도 감사 이벤트로 처리한다. 유효 정책의 명시 선택, 유예/용량 조건, 삭제 범위·손실량 기록이 모두 확인되어야 한다. 활성 pin과 진행 중 pin 복사 보호가 우선이며 해당 자료가 안전하게 분리되기 전 파티션을 지우지 않는다. 진행 중 pin은 작업 timeout 시 FAILED로 전환하고 사용자에게 실패를 알린 뒤 보호를 해제할 수 있다. ACTIVE pin은 이 예외로 삭제하지 않는다. 감사/정책 판정 기록 실패 시 손실 삭제도 거부한다.

압력 시 순서: 만료 복원 캐시 회수 → 만료 검증 자료 정리 → 정상 표본 축소 → 중요 표본 예산 적용 → 상세 수집 제한. 이미 약속한 기간의 원본을 조용히 삭제하지 않는다. 메트릭 경로도 공간이 무한하지 않으므로 예약 예산과 최종 보호 동작을 별도 설정한다.

라이선스 만료가 보존 정리·기존 파일 무결성 확인을 중단시키지 않게 한다. 다중 BE에서 공통 원장·lease와 공유 또는 명시적 노드 귀속 저장소를 사용한다. 컨테이너 영속 볼륨은 활성화 전 필수 검증이다.

## 8. 원문·민감정보 보존

SQL 값, HTTP 인증 헤더·쿠키·본문 등은 수집 시 최소화/마스킹한다. 오래 보관할수록 노출 기간도 길어진다. 아카이브에서 마스킹된 값을 복원 화면이 원문이라고 표시하지 않는다.

파일 접근 권한, 다운로드·복원·pin·삭제 감사 기록을 제공한다. 공용 감사 기반의 유무는 재개 시 확인한다. 파일/복원 캐시/임시 파일 모두 만료·삭제 대상이다. 백업에서의 삭제 반영은 별도 운영 정책으로 정의한다. 암호화와 키 관리의 필수 여부는 설치 환경 요구로 확정하며, 기존 ZM-156의 “암호화 1차 제외”를 장기 민감 원문 보관의 자동 승인으로 해석하지 않는다.

## 9. 단계별 작업과 완료 조건

| 단계 | 작업 | 완료 조건 |
|---|---|---|
| S0 재확인·실측 | 최신 코드/계약·역할 확인, 운영 설정 읽기, 스팬·카탈로그·압축·복원·폭증 실측, 미결 정책 확정 | 대상 규모와 예산에서 기간별 용량 및 처리 한계 산출 |
| S1 정책·관측 | 정책 resolver·버전, 현재 설정 이관, 유실/예산/보류 관측 | 기본 동작 불변, 조회·삭제·아카이브의 보존값 일치 |
| S2 공용 아카이브 | ZM-156/I7 writer·원장·경로·snapshot/delta·DROP 게이트 구현/재사용 | 일반 경로에서 미검증 원본 삭제 없음; 손실 예외는 S5 검증 전 비활성 |
| S3 등급·장기 카탈로그 | 분류/승격, 클래스별 파일, locator 및 만료 정리 | 정상 30일·중요 90일 수명 주기 검증 |
| S4 복원·화면 | 권한 있는 검색·비동기 복원·기간 안내·상태 표시 | 과거 오류 trace를 UI에서 실제로 조사 가능 |
| S5 pin·압력 정책 | 지정 보존·연장·삭제 경쟁 제어, 서비스/전역 예산 적용 | pin 자료 보존과 디스크 한계 동작 검증 |
| S6 전환·검수 | API 계약, 통합·런타임 QA, 장애 복구 훈련, 단계 활성화 | 기능 주장과 실제 접근 가능 기간 일치 |

S2 단독 공개는 “파일 아카이브” 기능이다. **30/90일 상세 분석은 S4 및 관련 수집/용량 보호 검증 후에만 공개**한다. 기존 설치본은 기본 비활성, 서비스 일부로 시범 적용 후 확대한다. 정책 롤백은 신규 분류·유입에 적용하고 이미 발행한 파일·pin을 즉시 삭제하지 않는다. 새 스키마를 이전 바이너리가 못 읽는 경우 애플리케이션 롤백을 금지하고 전환 계획을 별도 수립한다.

## 10. 필수 검증 시나리오

1. 정상 trace는 8일째 ARCHIVED로 검색되고 복원된다. 30일 만료 후 pin이 없으면 접근 만료로 표시된다.
2. 중요 trace는 31일째 복원 가능하고 90일 이후 정책대로 정리된다. summary·span·locator가 서로 고아가 되지 않는다.
3. 자정을 넘는 trace, 늦게 도착한 ERROR, export 이후 추가된 span이 승격·delta 발행된다. 이전 NORMAL span도 90일 자료로 복사되어 30일 삭제 뒤 남으며, 이미 없던 span은 PARTIAL로 표시된다. 서로 다른 서비스 만료일이 같은 파일의 조기/지연 삭제로 이어지지 않는다.
4. 파일 기록 도중 종료, rename 직후 종료, 원장 실패, 파일 유실/손상, NFS 단절 시 일반 DROP이 거부된다. BEST_EFFORT 손실 삭제는 §7의 조건이 충족될 때만 별도 실행된다.
5. lease 만료 및 두 노드 동시 실행에서 stale worker가 파일/원장을 확정하거나 DROP하지 못한다.
6. pin과 원본 삭제가 경쟁해도 검증된 pin만 성공 처리된다. 한 trace pin으로 하루 파일 전체가 영구 잔존하지 않는다.
7. 오류 폭증에서 예산을 준수하고 누락이 표시된다. 전체 메트릭 통계가 선별 편향으로 바뀌지 않는다.
8. PRESERVE와 BEST_EFFORT가 한계 상황에서 서로 다른 지정 동작을 수행하고 사유를 기록한다.
9. 정책 확대/축소, 기능 비활성, 라이선스 만료, 재시작 뒤 유효 정책과 만료일이 일관된다.
10. 복원 중 취소·대용량·손상 압축 파일·캐시 만료를 처리한다. 복원은 기존 롤업·알람을 재발생시키지 않는다.
11. 권한 없는 서비스/혼합 trace/파일 접근이 차단되고, 서비스 삭제 후에도 접근 정책을 준수한다.
12. 관측 근거 없는 trace를 샘플링 제외로 단정하지 않는다. 샘플링·전송 유실·만료 설명을 구분한다.

시간 경과는 테스트 clock으로 검증한다. 만료 경계·시간대 변환은 실제 PostgreSQL 통합 테스트로 확인한다. 성능은 운영과 분리된 환경에서 현실적 payload 및 오류 폭증을 넣고 측정하며, 단위 테스트 통과만으로 용량 안전성을 주장하지 않는다.

## 11. 재개 시 결정할 항목

설계서 작성은 다음 질문의 답 없이 완료한다. 구현 착수 시 기본안을 확인하고, 측정이 필요한 값은 S0에서 확정한다.

| 질문 | 기본안/판단 기준 |
|---|---|
| 30/90일이 고객 조사 주기에 맞는가 | 권고 초안 유지, 30일 전부 즉시 조회 요구 시 별도 용량 산정 |
| 정상 표본율·서비스별 지연 기준 | 기존 설정과 실제 분포로 결정, 임의 전역값 강제 금지 |
| 전체/서비스/복원/pin 예산 | 사용 가능한 디스크·유입량·장애 폭증 실측으로 결정 |
| 아카이브 실패 모드 | PRESERVE 기본, BEST_EFFORT는 손실 허용을 명시 설정 |

| 영속 저장소 | 온프렘 로컬/NAS 지원, 다중 노드 공유/귀속과 복구 경로 검증 |
| 암호화·보관 의무·legal hold | 실제 고객 요구를 확인, 일반 pin과 분리 |
| ZM-156/I7 진행 상태 | 먼저 구현된 공용 기반을 재사용, 미완료면 S2에서 함께 설계 |
