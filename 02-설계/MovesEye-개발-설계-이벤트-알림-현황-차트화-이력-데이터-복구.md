## 🎯 무엇을 하려 했나

이벤트/알림 화면(`/event-alert/problem`)은 문제를 **한 줄씩** 보여줄 뿐, "요즘 어떤 일이 얼마나 벌어지고
얼마나 빨리 처리되는가"를 답하지 못했다. 그걸 차트로 만드는 것이 요청이었다.

**그런데 착수하자마자 데이터 자체가 못 쓸 상태라는 게 드러났다.** 그래서 작업이 셋이 됐다:
① 동기화가 해소 정보를 채우게 하고 ② 그 빈칸 때문에 생긴 데이터 손실 버그를 막고 ③ 그 위에 차트를 얹는다.

---

## 1. 🔴 착수 후 드러난 것 — 데이터가 반쪽이었다

### 1.1 해소 정보가 아예 없었다

| 필드 | 실측(수정 전) |
|---|---|
| `r_clock > 0` (진짜 해소 시각) | **0건** |
| `r_clock = 0` (미해소 표기) | 224건 |
| `r_event_id = '0'` | 252건 **전부** |

원인: `EventSyncService`가 `alertPort.listActive`(= `problem.get`, **열린 문제만**)로만 돈다.
문제가 해결되면 Zabbix 응답에서 **사라질 뿐**이라, 우리 행은 해소 시각을 받을 경로 없이 `0`으로 영구 잔류한다.

> 이 상태로 MTTR을 뽑으면 `r_clock - clock`이 **음수 17억**(=`0 - 현재epoch`)이 되고,
> 구간화하면 **"224건 전부 5분 안에 해결"** 이라는 그럴듯한 가짜 차트가 나온다. 실제로 처음 뽑았을 때 그랬다.

### 1.2 그 빈칸이 데이터 손실 버그를 만들고 있었다

`cleanupOldEvents()`가 `r_clock < (now - 30일)`로 삭제했다. 미해소의 `r_clock`이 0이니 **조건이 항상 참** —
즉 **열려 있는 문제까지 매일 자정에 지워진다.** 실측 시점에 **254건 중 226건이 삭제 대상**이었다.

살아 있던 이유는 단 하나, **그 배치가 한 번도 실행된 적이 없어서**다(`scheduler_run_log` 0건).
설정은 `enabled=true · 매일 00:00`이므로, BE가 자정을 넘겨 떠 있었다면 그때 날아갔다.

## 2. 해결 — 동기화가 해소를 되짚는다

### 2.1 "사라진 것 = 해결된 것"

동기화 끝에 `reconcileResolved()`를 붙였다.

```
DB에서 아직 해소 안 된 event_id 목록
  − 이번 problem.get 응답에 있는 id
  = 그 사이 해결된 사건
```

그 사건들만 Zabbix에 되묻는다. **사라진 게 없으면 콜도 0이다.**

### 2.2 해소 시각은 2단으로 얻는다

🔴 발생 사건에는 복구 *식별자*만 있고 **시각이 없다**. 그래서 화면의 이력 모드(ZM-99)와 같은 방식으로:

1. `listHistory(ofNativeIds(사라진 id들))` → 각 사건의 `recoveryNativeId`
2. `listHistory(ofNativeIds(복구 id들))` → 그 복구 사건의 발생 시각 = **해소 시각**
3. `UPDATE event_problems SET r_event_id, r_clock`

한 주기 상한 `RECONCILE_BATCH_LIMIT = 500` — 대량 해소 때도 한 주기가 길어지지 않게. 남은 건 다음 주기가 잇는다.

**실패는 삼킨다**: 되짚기가 실패해도 동기화 본체는 성공으로 둔다. 열린 문제 목록이 더 중요하고, 다음 주기가 다시 시도한다.

### 2.3 정리 배치를 둘로 나눴다

| 대상 | 조건 | 왜 |
|---|---|---|
| 해소분 | `r_clock > 0 AND r_clock < now-30d` | 🔴 `r_clock > 0`이 **핵심** — 없으면 열린 문제가 전부 지워진다 |
| 좀비 | `(r_clock IS NULL OR = 0) AND clock < now-90d` | Zabbix housekeeping이 원본을 지우면 해소 시각을 영영 못 받는다. 그것까지 두면 표가 무한히 자란다. **진짜 오래 열린 장애를 지우지 않으려고 기한을 훨씬 넉넉히** 준다 |

### 2.4 실서버 검증

기동 후 첫 주기 로그: `Resolved reconcile: filled resolution time for 184 of 185 vanished events`

| | 수정 전 | 수정 후 |
|---|---:|---:|
| `r_clock > 0` | 0건 | **184건** |
| MTTR 분포 | "전부 5분 미만"(가짜) | 5분미만 38 · 5~30분 72 · 30~60분 22 · 1~24시간 40 · **24시간 초과 12** |

> 가짜였을 땐 안 보이던 것이 드러났다: **하루 넘게 방치된 문제가 12건**, 가장 오래된 것은 28일째.

## 3. 차트 — `/event/stats` + 현황 탭

### 3.1 데이터 소스는 우리 DB다

**Zabbix를 다시 부르지 않는다.** 1분 동기화가 채우는 `event_problems`에서 SQL로 센다.
그래서 기간을 바꿔도 **0.16초**에 끝나고(실측), 화면이 자주 새로고침해도 실 모니터링에 부담이 없다.

대신 한계가 있다: **동기화가 채운 만큼만 보인다**(해소분 30일 보관). 화면 하단에 그 사실을 적는다.

### 3.2 BE — `GET /event/stats?from=&to=`

| 필드 | 축 | 비고 |
|---|---|---|
| `summary` | 발생·해소·미해소·호스트 수·문제 종류·**해소 중앙값**·최장 미해소·**하루 초과 미해소** | 🔴 해소 관련은 `r_clock > 0`만 |
| `severity` | 심각도별 건수 | code = Zabbix severity |
| `trend` | 일자 × 심각도 | 🔴 **발생 없는 날은 행이 없다** — 채우는 건 화면 몫(서버가 빈 날을 만들면 응답만 커진다) |
| `topHosts` / `topProblems` | 상위 10 | `topProblems`가 **알림 피로의 원인**을 드러낸다 |
| `resolutionTime` | 해소 소요 5구간 | 해소분만 |
| `openAge` | 미해소 경과 4구간 | 방치 알람 |

관리자 전용이 **아니다** — 문제 목록 화면은 전 사용자가 보는 곳이라 같은 접근 범위를 따른다.

### 3.3 FE — 문제 화면에 탭 컨테이너

```
이벤트/알림 › Problem
[현황]  [문제 목록]   ← 현황이 앞이지만 기본은 목록
```

🔴 **기본은 목록이다.** `?tab=` 없이 들어오면 예전과 똑같이 목록이 열린다 — 알림을 받고 "지금 뭐가 터졌나"
보러 오는 화면이고, 기존 딥링크·알림벨 링크가 전부 목록을 가정한다. 현황은 `?tab=overview`로만 열린다.

**기간(from/to)은 두 탭이 공유한다** — 다른 기간을 보면 숫자가 어긋난 것처럼 읽힌다.

차트 프리미티브(`OverviewCard`·`OverviewDonut`·`OverviewBarH/V`·`OverviewTrendBar`·`OverviewKpiBand`)는
**ZM-118 구성 현황과 공유**한다. 같은 제품 안에서 대시보드마다 차트가 다르게 생기면 읽는 사람이 매번 새로 배워야 한다.

### 3.4 색은 의미색으로

해소 소요·미해소 경과는 **오래 걸릴수록 나쁜 축**이라 카테고리 색이 아니라 `HEALTH`(녹색/주황/빨강)를 쓴다.
심각도는 기존 `SEVERITY_BY_CODE` 팔레트 그대로.

## 5. 남은 것 / 알려진 한계

- **보관 기간을 넘긴 과거는 복구되지 않는다** — 되짚기는 Zabbix에 원본이 남아 있는 것만 채운다(첫 실행에서 185건 중 1건이 그래서 못 채워졌다)
- 좀비 정리 기한 90일은 근거가 약한 값 — 운영 데이터가 쌓이면 재검토
- 이 화면은 **캐시가 없다**(DB 집계라 빨라서). 규모가 커져 느려지면 ZM-118과 같은 캐시 패턴을 붙인다

  인덱스가 없어 규모가 커지면 여기가 먼저 느려진다
