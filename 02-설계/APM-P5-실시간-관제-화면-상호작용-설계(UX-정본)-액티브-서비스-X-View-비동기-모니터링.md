### URL query 상태 규칙 🔴 `[X-r1 반영: 리마운트 전제 정정]`
- ✅ **정정**: 이 앱의 페이지 전환 key는 `location.key`가 아니라 **`location.pathname`**이다(`App.tsx:235~240` 주석 — 과거 `location.key` 리마운트 문제를 pathname으로 고쳤다). 따라서 **같은 경로 안의 query 변경은 페이지를 리마운트하지 않는다.** v0의 "navigate마다 리마운트" 전제와 메모리 `fe-page-remount-on-navigate`의 서술은 구 동작이다(메모리 갱신 필요 — 회신서 §5).
- 그래도 화면 상태를 URL query에 두는 이유는 바뀌지 않는다: **공유·새로고침·뒤로가기**에서 같은 화면이 나와야 한다. 로컬 `useState`는 "어떻게 보고 있는가"(접힘·스크롤·hover)에만 허용한다(워터폴 ✅ 같은 규칙).

**`at`의 약속** `[X-r1 반영: "그 순간의 화면 재현" 철회 — 오케스트레이터 결정 2]`
- `at`은 **"그 시각 범위(`at−win`~`at`)의 현재 보관 표본을 다시 조회한 것"**이지 "당시 화면의 재현"이 아니다. 늦은 수정·표본 축소·서버 재기동으로 당시 점 집합은 복원되지 않는다. 툴팁 문구 그대로: *"이 시각 범위에 대해 현재 서버가 보관 중인 표본을 보여 줍니다. 당시 화면과 같지 않을 수 있습니다."*
- 복원 가능 범위 = 현재 연결이 받은 범위(`snapshot.begin.node.coverageFrom` ~ `serverTime`, 같은 `streamEpoch`) ∩ `[at−win, at]`.
  - 전부 안 → 그대로 표시(툴팁 문구만).
  - 일부만 안 → **부분 복원** 배지 "이 범위 중 hh:mm:ss 이후만 현재 보관돼 있습니다".
  - 전부 밖(15분 이전·다른 epoch) → **복원 불가** 안내 "이 시각은 더 이상 실시간 창에 없습니다 → 트레이스 탐색으로"(`at`은 유지해 사용자가 알 수 있게, 화면은 따라가기로 그린다).
- 🔴 `pause` 같은 불리언 대신 `at`(시각)을 쓰는 결정은 유지한다 `[X-r1 반대 없음 — 판정은 약속 문구에만]` — 공유·새로고침 뒤 "어느 시각을 보고 있었나"는 시각 값이어야 남는다.

### 권한 · 라이선스 게이트 표시 `[X-r1 반영: 임계 조회 EP 정정·확장 안내 분기]`
- 라우트 보호는 기존과 같다: `PageWrapper(permissionKey=APPLICATION_MONITORING)` + `FeatureGate("APM")`(view). 설정 EP가 없으므로(정본 §3.4) `apm.edit`는 이 화면의 기능 조건이 아니다.
- `[R-P5.6 반영]` ✅ **403은 페이지 안 배너보다 라우트 가드가 먼저다.** 모듈 권한(`applicationMonitoring`)이 없는 사용자는 `PageWrapper`가 **`/errors/404`로 먼저 보내** 화면의 `forbidden` 분기(§2.5·§3.4)에 닿지 않는다(R-P5.6 §7-1 실측: `rp56noperm`으로 진입 → `location.pathname=/errors/404`, API는 정상적으로 `code:403`). 페이지 안 403 분기는 **모듈 권한은 있으나 기능 권한(`apm.view`)이 없는 조합**에서만 도달한다 — 죽은 분기는 아니지만, "403은 화면이 배너로 받는다"를 모든 무권한 사용자에게 기대하지 말 것.
- 🔴 **임계 값의 출처**: 전역 p95 참고선은 **`snapshot.config.p95ThresholdMs`**(정본 §3.2 ✅ 반영됨), 전역 느림 기준은 `config.slowMs`. 서비스별 규칙(타일 툴팁·서비스 단일 뷰)은 기존 **`GET /apm/services/{uid}/alert-rules`**(✅ `requireRead`, `useApmEffectiveRules`)로만 읽는다. ✅ **`GET /apm/alert-rules`는 `requireEdit`**라 view 사용자에게 실패한다 — 이 화면에서 쓰지 않는다(§6-12(a) 반영됨 — 정본 §3.2 주석·§4.2 정정 `[v2.2 동기]`). 오류율 참고선의 전역 `ERROR_RATE` 임계는 **`snapshot.config.errorRateThresholdPct`**(§6-12(b) 반영됨, 정본 §3.2 — 전역 규칙이 없으면 `null`) `[v2.2 동기]` → `null`일 때만 오류율 게이지에 참고선 없이 값만(화면은 대체값을 만들지 않는다).
- P5.3b "확장 설치 안내": `canEdit`(apm.edit)면 수집기 `?tab=registration` 링크, 아니면 공개 도움말(`page_guide.apm_realtime` 상세)로 보낸다.
- SSE 거절은 정본대로 `control{reject, code:403|429}`로 온다 → 화면은 `ApmQueryError`와 **같은 문구 경로**(`resolveApiError` → `messageKey`)로 배너를 세운다. 403은 재시도 버튼 없음(로그인/권한 변화로만 새 연결), 429는 `retryAfterMs`+jitter 카운트다운 버튼. 스트림을 열기 전 401(인증 필터·`VisitorSessionChecker` 둘 다)은 `EventSource.onerror`에서 세션 확인 경로로(정본 §2.5 거절 변환 표). `[contract-r1 정정]` 🔴 이 401은 **`ApiResult` 본문이 아니라 `{"code":401,"errorCode":"INVALID_TOKEN"}` 두 필드뿐**이다 — 기존 `resolveApiError`(status·message·data 전제)를 그대로 태우지 말고 이 경로만 별도 처리한다(계약서 §1.4). 🔴 **`control{paused}` 해제는 `control{resume}`으로 오지 않는다** — BE는 `resume`을 보내지 않으며, 화면은 **새 `snapshot.begin` 도착**을 재개 신호로 삼는다(§2.8·정본 §2.5).
- 라이선스 만료(`Feature.APM`)는 FeatureGate가 화면 진입 자체를 막으므로 별도 표시 없음. 열린 스트림 중 만료는 `control{reject,403,APM_LICENSE_*}` → 같은 배너.

## 1. 실시간 액티브 서비스 관제 (`?tab=active`, 탭 라벨 "요청 관제", P5.3 · 목록 P5.3b)

### 제니퍼는
서비스별 "액티브 서비스 이퀄라이저"(막대 = 진행 중 요청 수, 경과 시간 구간별 색 0~1s/1~3s/3~8s/8s+ — **처리 중인 요청이 오래된 구간으로 이동하는 모습**이 보인다), 속도계(TPS·응답시간), 진행 중 요청 목록(시작·경과·URL·스레드)을 1초 갱신으로 보여 준다. 요청이 "들어온 순간부터" 보이는 것은 자체 에이전트가 시작 이벤트를 내기 때문이다. 구간 경계를 고객이 바꿀 수 있는지는 제공 자료에서 확인되지 않았다(**추정**) `[X-r1 반영: "모든 고객에 고정" 철회]`.

### 우리 개선 — 세 가지 `[X-r1 반영: 2번을 "임계 재사용"에서 "느림 기준·오류 2축"으로 교체, 스택 이퀄라이저는 데이터 부족으로 P5.3b]`
1. **"완료 관제"와 "동시 요청 수"를 시각적으로 분리한다.** OTel 스팬은 끝나야 export된다(정본 §0 비범위). 그래서 1초마다 움직이는 것은 *방금 끝난 요청의 집계*(TPS·p95·오류율)이고, *지금 처리 중인 수*는 메트릭 `http.server.active_requests`의 인스턴스 합산(10~60초 해상도)이다. 한 이퀄라이저에 섞으면 1초 갱신되는 막대 옆에 60초에 한 번 바뀌는 숫자가 서서 "고장난 것처럼" 보인다 — 우리는 두 리듬을 **다른 부품·다른 문구**로 놓는다. 탭 라벨도 "액티브"가 아니라 **"요청 관제"**로 둬 첫 출시의 이 탭이 진행 중 목록을 뜻한다고 오해하지 않게 한다.
   - ⚠️ 제니퍼 스택 이퀄라이저의 가치("멈춘 요청이 오래된 구간에 쌓이는 모습")는 **현 데이터로 만들 수 없다** — `active.value`는 개수 하나뿐이라 경과 구간별로 쌓을 수 없다. 시작 이벤트(P5.3b 확장)가 있을 때만 "동시 요청의 경과 구간 스택"이 가능하므로 **P5.3b 범위**로 넘긴다(§5 후속 표). 첫 출시의 이퀄라이저는 "완료 처리량"이라고 제목에 못 박는다.
2. **개별 요청의 정상/느림은 서버 전역 느림 기준(`config.slowMs`)과 오류 2축으로만 가른다.** 알람 규칙 `P95_LATENCY`의 임계는 *서비스 집계 p95*의 알람 조건이지 개별 요청의 정상·비정상 기준이 아니다(집계 기간·최소 관측 조건이 다르다) → **집계 참고선으로만** 그리고 "이 요청의 알람 판정이 아님"을 도움말에 적는다(§1.4, 오케스트레이터 결정 3).
3. **신선도·관측 범위를 숫자 옆에 붙인다.** "동시 요청 7"이 아니라 "동시 요청 7 · 2/3 인스턴스 · 관측 12초 전". 정본 §2.6의 결정(`observedInstances/expectedInstances`·`asOf`·`instances[]`, stale은 0이 아니라 관측 없음)을 타일 하나에 담는다.

- `[X-r1 반영]` 게이지에는 **집계 구간 시각(최신 1초 칸의 hh:mm:ss) + 잠정 여부**를, 메트릭 타일에는 **실제 관측 나이("관측 21초 전")**를 우선 적는다. "약 10초 이내"(권장 export 주기)는 타일에서 빼고 도움말 `rt_active_tile.detail`로 옮긴다 — 같은 타일에 "약 10초 이내"와 "21초 전"이 함께 서면 자기모순으로 읽힌다.

### 1.4 지연 구간 — 느림 기준 2구간 + 확인 불가, p95 임계는 참고선 `[X-r1 반영: P95_LATENCY 개별 판정 철회·SLOW 색 통일 — 오케스트레이터 결정 3]`
제니퍼 구간(0~1s/1~3s/3~8s/8s+)을 **설치본의 느림 기준으로 만든 2구간 + 확인 불가**로 바꾼다. 개별 요청의 정상/느림 판정은 **정본 §3.1 `flags.slow`와 같은 경계(`durationMs ≥ slowMs`)** 하나뿐이다.

| 구간 | 경계 | 색(팔레트 토큰) | 라벨 | 어디에 쓰나 |
|---|---|---|---|---|
| 정상 | `< slowMs` | `CHART_SERIES[0]` | 정상 | X-View 브러시 표 지연 열 · 액티브 목록 경과 · 타일 p95 |
| 느림 | `≥ slowMs`(서버 전역 설정, `config.slowMs`) | **`HEALTH.warning`** | 느림 | 〃 — 🔴 X-View의 SLOW(§2.2·§4.1)와 **같은 색·같은 경계** |
| 오류 | `http5xx ∨ spanError`(지연과 독립) | `HEALTH.critical` | 오류 | 상태 열 — 느림과 겹칠 수 있다(툴팁에 둘 다) |
| 확인 불가 | 액티브 목록 TTL 초과 | `HEALTH.unknown` + 라벨 | 확인 불가 | 액티브 목록만 |

- **p95 알람 임계(`config.p95ThresholdMs`)는 집계 참고선**이다: p95 게이지·X-View 점선 한 줄로만 그리고, 라벨은 "참고: p95 알람 임계 N ms". 개별 점·행을 이 값으로 색칠하지 않는다. 임계가 없으면(`null`) 선을 그리지 않고 `slowMs/2` 같은 대체값을 **만들어 내지 않는다**.
- 🔴 색만으로 구분하지 않는다: 지연 값 옆에 텍스트 라벨(정상/느림/오류)을 항상 붙인다(메모리 "심각도는 색만으로 구분 불가 → 라벨 필수").
- 서비스별 임계(`slow_threshold_ms`, 설정 탭)가 있는 서비스는 🔴 **라이브 SLOW 판정이 전역값**이라(정본 §2.2 drift 결정) 화면도 전역값으로 그린다. 서비스별 값이 다르면 타일 툴팁에 "이 서비스의 느림 임계는 N ms(서비스 설정)이나 실시간 판정은 전역 M ms"라고 적는다(값은 `GET /apm/services/{uid}/alert-rules`·`useApmEffectiveRules`).
- v0의 "주의(`T_p95 ≤ x < slowMs`)" 구간은 삭제 — `T_p95 > slowMs`인 설치에서 정상·느림이 겹치는 식이었다.

### 1.6 완료 요청 지연 구간 차트 `[2026-09-17 신설 — A안 구현]`

제니퍼·와탭의 **액티브 트랜잭션 속도 차트**(진행 중인 요청을 경과 구간으로 쌓는 그림)를 지금 가진
데이터로 만들 수 있는 만큼 세운 것이다. 진행 중 요청을 구간별로 쌓으려면 **요청 시작 이벤트**가
필요하고 그것은 자바 에이전트 확장(P5.3b)이 있어야 온다 — 그 전까지는 **이미 끝난 요청**을 걸린
시간대로 가른다. 제목·도움말이 그 차이를 적는다.

- **재료**: 버킷의 `stats.hist` 15칸. 🔴 **산점도와 모집단이 다르다** — 산점도의 점은 버킷마다 상한이
  걸린 **표본**이지만 `hist`는 수신 관문을 통과한 **전량**에서 센 것이다(BE `LiveSpanRing#offer`가
  `stats.add`를 먼저 하고 보존을 나중에 판단한다). 점이 잘려 나간 구간에서도 분포는 온전하고,
  두 화면의 숫자가 다른 것은 **오차가 아니다**. 카드 각주와 도움말이 이것을 상시 적는다.
- **구간 경계**: `100 ms / 500 ms / 1 s / 5 s / 그 위` — 🔴 전부 `LiveSpanStats.BOUNDS`의 **칸 경계
  위**에만 놓는다. 칸 중간에 두면 보간이 들어가고 그 순간 "센 것"이 아니라 "추정한 것"이 된다.
  라벨 문구는 박아 두지 않고 **경계값에서 만들어 낸다**(BE가 경계를 바꿔도 라벨만 옛말이 되지 않게).
- **가로 칸**: 창 길이와 무관하게 **60개 고정**. 창을 넓히면 한 칸이 넓어진다(1분 → 1초, 5분 → 5초).
- **고를 수 있는 창**: 60초와 `config.snapshotSeconds`. 🔴 **받은 범위를 넘는 창을 주지 않는다** —
  15분을 고를 수 있는데 5분치만 그리면 그 빈 10분이 "요청이 없던 시간"으로 읽힌다. URL 키 `lat`.
- **관측 없음**: 버킷이 하나도 안 들어온 칸은 `0`이 아니라 **막대를 그리지 않는다**. 0으로 그리면
  바닥에 붙은 선이 "그 시각엔 0건"으로 읽히는데 우리가 아는 것은 "그 칸을 받지 못했다"까지다.
- **칸 배정 식**은 §1.2 스파크라인과 **같은 식**을 쓴다 — 다른 식이면 같은 화면의 두 부품이 같은
  1초를 서로 다른 자리에 그린다.

### 1.7 액티브 요청 목록 — 문구 정정 `[2026-09-17]`
🔴 예전 문구 "진행 중 요청 목록을 **제공하는 서비스가 없습니다**"는 고객사 서비스를 탓하는 말이었다.
사실은 **우리가 아직 만들지 않은 기능**이다. 무엇이 없어서 못 만드는지(요청 시작을 알리는 자바
에이전트 확장)를 적고, "수집기 등록 안내" 링크는 **뺐다** — 설치로 해결되는 일이 아니라 사용자가
자기 설정을 고치러 갔다가 헛걸음한다.

### 1.8 관제실(wall) 모드 · 전체화면 · 다크 `[X-r1 반영: URL은 배치만·전체화면은 버튼·원복 조건 정의]` `[X-r1 부분 반영: 다크 스코프]`
- `?mode=wall`은 **배치만** 복원한다(속도계 3 + 동시 요청 타일 상단 1행 높이 2배, 이퀄라이저 좌측, 타일 그리드 우측, 글자 1.4배·간격 1.5배, 사이드바·헤더·브레드크럼 숨김). ✅ **전체화면은 URL 진입만으로 켤 수 없다**(Fullscreen API는 사용자 동작이 필요) → wall 배치 안의 **"전체화면" 버튼**이 `requestFullscreen()`을 부른다. 실패(거부·미지원)면 배치는 유지하고 버튼에 "이 브라우저에서는 전체화면을 열 수 없습니다".
- **다크**: 🔴 다크는 헤더 토글(theme slice) 기반이라(메모리) `prefers-color-scheme`으로 판단하지 않는다. `[X-r1 부분 반영]` 코덱스 권고대로 **wall 컨테이너에 다크 토큰을 스코프**하는 것을 1안으로 한다 — 단 현 팔레트가 root 단위 클래스로 토큰을 갈아 끼우는 구조면 컨테이너 스코프가 불가할 수 있다(구현 시 확인). 불가하면 2안: theme slice를 강제하되 **진입 전 값을 저장하고, 사용자 저장 선호(persist)는 건드리지 않으며**, 아래 이탈 조건 전부에서 원복한다.
- **원복·나가기 조건(전부 정의)**: 나가기 버튼 · `Esc` · `fullscreenchange`(전체화면 해제) · 페이지 이탈(unmount) · `beforeunload`. 나가면 `mode` 키 제거, 테마 원복, 사이드바 복귀.
- 🔴 wall 모드에서도 **헤더 문구 줄·연결 배지·잠정 표시는 남긴다**(정직성은 화면 크기와 무관). 툴팁·브러시·표는 없음. **일시정지 버튼과 나가기 버튼은 항상 보이는 요소**로 둔다(키보드 `Space`만으로 끝내지 않는다 — WCAG 2.2.2).
- 숨김 탭 5분 규칙(정본 §2.5)은 wall에서도 같다(관제실 모니터는 보통 항상 보이므로 실질 영향 없음).

## 2. 실시간 X-View (`?tab=xview`, P5.2 · 패턴 P5.4)

### 제니퍼는
전체 트랜잭션의 응답시간을 점 그래프(x=시각, y=응답시간)로 흘리고, 점 모양(수직선·수평 띠·우상향·군집)만 보고 이상을 직관하게 한다. 드래그로 점을 잡아 트랜잭션 목록·프로파일로 바로 내려가며, 선택 목록이 유지된다. 제공 설명상 전량 표시를 취지로 한다(모든 부하·설정에서의 표시 보장 여부는 확인하지 않았다 — **추정**) `[X-r1 반영: "모든 점이 전량" 완화]`.

### 우리 개선 — 네 가지 `[X-r1 반영: 색 결정은 flags·중복 점 한 개·조사 흐름의 선택 유지]`
1. **층(layer)을 기호로 드러낸다.** 서버는 기본 계층(균등 reservoir)과 강조 계층(오류·느림 별도 예산)을 나눠 보관한다(정본 §2.4). 화면은 두 계층을 **다른 기호**로 그린다 — 기본은 작은 원, 강조는 큰 마름모. 색은 정본 §3.1 `flags`로 결정한다: `http5xx ∨ spanError → ERROR`, 아니고 `slow → SLOW`, 아니면 OK. 🔴 기본 reservoir는 전체 관측을 대상으로 하므로 **같은 `(traceId, spanId)`가 기본·강조 양쪽에 있을 수 있다** → 한 점만 그리고 **강조 기호를 우선**한다(보관 계층 정보는 표·툴팁에 "기본+강조"로 유지).
2. **"표시 n / 관측 m"을 제목·범례·브러시 표에 상시 노출한다**(정본 §0 표·§4.1 🔴). `m = Σ stats.count`, `n = 실제 표시한 고유 요청 수`(§2.3). 점 개수로 TPS를 세지 않는다 — 게이지는 `stats`에서만 읽는다.
3. **점 클릭은 "저장된 트레이스 찾기"이지 "상세 열기"가 아니다.** 상태 전이를 `unknown → checking → stored | notFound(retryable)`로 두고, 20초로 미저장을 확정하지 않는다(정본 §4.1 🔴). 조사 흐름이 제니퍼보다 한 단계(찾기) 길어지는 만큼 **선택 목록 유지·이전/다음·저장 확인 후 즉시 상세 이동**으로 되갚는다(§2.4·§2.5).
4. **패턴 라벨은 오버레이·관측 특징 문구·닫을 수 있는 칩**으로. 원인("GC·잠금")을 쓰지 않는다(정본 §4.4 🔴).

### 2.3 상시 배지 — "표시 n / 관측 m" 한 줄의 구성 `[X-r1 반영: 중복 합산 제거·필드명 정본 일치·단계 비율은 보조]`
`표시 {displayed} / 관측 {observed}   (서버 보관 슬롯 {retainedSlots} · 이 연결 1/{k} · 브라우저 1/{j})`
- 🔴 **`observed` = 창 안 버킷의 `stats.count` 합**(정본 §3.2 예시: `stats.count=412`, `base.observed=412`, `emphasis.observed=5` — v0의 `base.observed+emphasis.observed`는 같은 요청을 두 번 센 **417**이 됐다). 🔴 **`displayed` = 실제 그린 고유 `(traceId, spanId)` 수**(중복 점 제거 후, 브라우저 솎음 반영 후).
- `retainedSlots` = `base.retained + emphasis.retained` 합 — **슬롯 수**이지 고유 요청 수가 아니다(겹침 포함). 툴팁에 그렇게 적는다.
- 단계별 비율은 **보조 정보**다: 이 연결 `pressure.clientKeepRatio`·서버 `pressure.serverKeepRatio`·snapshot `snapshotKeepRatio`·브라우저 상한 솎음(클라이언트 값). 🔴 비율 하나로 창 전체를 설명하지 않는다 — 과거 버킷의 전달률은 다를 수 있으므로 상시 배지의 기준은 **실제 표시 수**이고, 버킷별 `observed/retained/delivered`는 군집 툴팁(§2.9)에서 본다.
- `pressure.arenaPressure > 0` → 배지 "서버 보관 축소 중" · `control{degraded, reason}` → `connection_queue` "이 연결은 1/k로 솎아 받는 중" / `frame_limit` "서버 전송량 상한으로 1/k" / `arena_pressure` "서버 보관 축소로 1/k" · 브라우저 상한(잠정 300k) 초과 → "브라우저 상한으로 기본 계층 1/j 표시". 툴팁에 정본 §0 표의 "층별 약속" 4줄을 그대로 적는다. `[contract-r1 정정]` 🔴 이 배지 산식은 **`arenaPressure`가 "tick 구간 내 발생분"이라는 전제**에서만 성립한다 — 현재 BE 구현은 이 값을 **누적 카운터**로 보내고 있어(계약서 §6-C, 정본 `devdesign_apm-realtime.md` §3.3) 그대로 쓰면 서버 기동 후 압박이 한 번이라도 있었을 때 이 배지가 **영구 ON**이 된다. BE 정정 전까지는 `arenaPressure` 값 자체를 조건으로 쓰지 말고 `control{degraded, reason:"arena_pressure"}` **수신 시점에만** 일정 시간(예: 10초) 배지를 켜는 방식으로 구현한다.
- 🔴 이 줄은 wall 모드·좁은 화면에서도 접지 않는다(정본 §0 "상시").

### 2.4 브러시 → 표 `[X-r1 반영: 제목 분리·DmoveTable 설정·선택 유지·이전/다음]`
- 사각 브러시(✅ `apmScatter` 브러시 설정 재사용) → 클라이언트 버킷에서 필터(서버 왕복 없음, 정본 §4.1) → `DmoveTable`.
- 제목 🔴 **"선택 점 n건"** + 보조 줄 **"같은 시간대 전체 관측 약 m건 — 지연·경로·인스턴스 조건 미반영"**. m = 선택 시간 범위에 걸친 버킷의 `stats.count` 합(초 경계 일부만 걸치면 "약" 유지). 지연 범위·route·instance 필터는 분모에 반영되지 않는다(`hist[15]`가 있어도 route/instance 분해는 없다) → 툴팁 "지연·경로·인스턴스로 좁힌 관측 수는 제공되지 않습니다". 정본 §4.1의 "표시 표본" 정신은 유지한다(전체 목록이라 부르지 않는다).
- 🔴 **표 설정**: `hasQuery={false}`(✅ 기본 `true`는 공용 페이지 query를 먹는다 — 이 표의 정렬·페이지는 URL과 무관) · `rowKey = traceId:spanId` · 페이지 크기 상한 200(클라이언트 정렬 비용 — R4) · 행마다 **네이티브 `<button>` "찾기"**(Enter 키보드 접근은 버튼으로 보장 — ✅ `onClickRow`만으로는 Enter가 안 된다).
- 열: 시각(종료)·지연(원값 + §1.4 라벨)·상태(정상/느림/오류 — 오류는 5xx·ERROR 축 툴팁)·계층(기본/강조/기본+강조)·서비스·route·인스턴스(앞 8자)·traceId·[찾기]. 정렬 기본 지연 내림차순. 🔴 `__other__` route는 링크 없음.
- **선택 목록 유지·이전/다음**: 선택은 `?sel=`에 살고, 표 위에 [◀ 이전] [다음 ▶]가 있어 표 정렬 순서대로 점 패널(§2.5)을 옮겨 다닌다 — 패널을 열어도 표·브러시는 그대로다. "브러시 지우기"는 `sel` 제거. 옵션 재구성(1초) 시 브러시·dataZoom·선택 `(traceId, spanId)` 집합은 **보존**(정본 §4.1 보존 계약).
- 일시정지 중이 아니어도 브러시는 된다 — 다만 선택 영역이 왼쪽으로 흘러 창 밖으로 나가면 표가 비면서 "선택 영역이 창을 벗어났습니다"를 적는다(자동 일시정지하지 않는다). 흐르는 표의 재정렬로 조사 대상이 움직이는 문제는 **일시정지(§2.8)가 표·통계까지 고정**하는 것으로 답한다.
- 키보드만으로도 같은 표를 연다: "표 보기" 버튼 → 시간·지연 범위 **입력 폼**(브러시 없이 `sel` 생성) `[X-r1 반영]`.

### 2.5 점 클릭 → 사이드 패널 상태 전이 `[X-r1 반영: stored 조건·스팬 부재 상태·선택 스팬 중심 미니 워터폴·span 전달]`
패널은 🔴 `ResizableDrawer`(정본 컴포넌트)로만 연다. `storageKey="apm-xview-point"`.

```
[unknown] --클릭--> [checking: GET /apm/traces/{traceId}]
    ├─ 업무 성공(envelope OK) ∧ detail 유효
    │     ├─ spans에 pt.spanId 있음 → [stored]          : 요약(루트명·시작·지연·스팬 수·sampled 배지) + "트레이스 상세 열기(?span=<spanId>)" + 미니 워터폴(선택 스팬 + 조상 경로 중심, 최대 20행)
    │     └─ spans에 없음          → [stored.spanMissing]: "트레이스는 찾았지만 이 스팬은 응답에 없음(잘림·적재 중 가능)" + "트레이스 상세 열기" [다시 시도]
    ├─ APM_TRACE_NOT_FOUND
    │     ├─ 점 나이 < 20초 → [notFound.pending] : "현재 저장된 트레이스를 찾지 못함 — 저장 판정 중일 수 있음(tail 10초 + 적재)" [다시 시도]
    │     └─ 그 외        → [notFound]         : "현재 저장된 트레이스를 찾지 못함" + "정상 요청은 일부만 저장됩니다" [다시 시도]
    ├─ 403               → [forbidden] : 권한 문구(재시도 없음)
    └─ 그 밖의 오류     → [error] : ApmQueryError 문구 경로 [다시 시도]
```
- 🔴 **HTTP 200 자체를 `stored`로 보지 않는다** — 기존 envelope 규약(200 + JSON code)대로 **업무 성공 + 유효한 detail**일 때만.
- 🔴 **`notFound`는 종착 상태가 아니다** — 어느 나이에서도 "다시 시도"가 있고, "저장되지 않았습니다"라고 쓰지 않는다(정본 Q6·§4.1). 확정되는 전이는 `→ stored`·`→ stored.spanMissing`뿐이다(§6-12(c) 반영됨 — 정본 §4.1 상태 머신이 `stored` 조건·`stored.spanMissing`·`forbidden` 분기를 위 그림과 같게 적었다 `[v2.2 동기]`).
- 패널 상단에 점 자체의 사실(라이브 튜플)은 항상 보인다: 종료 시각·지연·상태·계층·서비스·route·인스턴스·traceId·spanId(복사). `?pt=`로 재진입했을 때 그 점이 아직 클라이언트 버킷에 있으면 거기서 복원하고, 창 밖으로 나갔으면 "이 점은 실시간 창을 벗어났습니다(저장 조회만 가능)"로 사실 칸을 비운다.
- 패널 열림은 `?pt=`. 닫으면 제거. 점 강조는 선택 `(traceId, spanId)` 집합으로 `emphasis` 계열이 아니라 **별도 마커 계열 1개**(`series.id="selected"`, 옵션 재구성에서 유지). ID→메타(서비스·route·인스턴스) 조회는 **클라이언트 인덱스**(`Map<traceId:spanId, {serviceId,b,idx}>`)로 O(1).

### 2.6 필터 · hover 군집 요약 `[X-r1 반영: dictVersion 의미·필터 해제 규칙·hover 후보 축소]`
- 필터 4종은 헤더: `svc`·`env`(서버 필터 키 — 바꾸면 `viewKey`가 바뀌어 snapshot부터), `route`·`inst`(클라이언트 필터 — 재접속 없음).
- 🔴 **`dictVersion` 증가는 세대 초기화가 아니다** — 사전 델타의 순서 번호(정본 §2.5)이며 정상적인 추가마다 필터를 풀지 않는다. URL의 `route`/`inst`는 **문자열**이라 매 사전(snapshot·delta)에서 현재 ID로 다시 해석한다. 해석 결과 없음(삭제·`removeServices`·상한 밖) → 필터는 **유지한 채** 배지 "필터 대상이 현재 사전에 없음(결과 0)"과 "해제" 버튼(조용히 풀지 않는다). `dictDelta.from` 불연속은 정본 규칙 5대로 snapshot 재요청(필터 문자열은 그대로 남아 재해석된다).
- hover는 점 하나가 아니라 **군집 요약**: 커서 반경 12px 안 점들의 (수·지연 min/p50/max·상태 비율·route 상위 2)를 툴팁으로. 🔴 300k점을 mousemove마다 선형 탐색하지 않는다 — 후보는 **시간 버킷(x) × 화면 y 격자 인덱스**로 먼저 줄이고, 탐색은 rAF당 1회로 제한(throttle). 구현은 ECharts `tooltip` 대신 `getZr().on("mousemove")` + 클라이언트 typed array(브러시와 같은 자료구조).

### 2.7 패턴 라벨 오버레이(P5.4) `[X-r1 반영: confidence 의미·분모 필드·칩 식별자]` `[v2.2 동기: §6-14 반영됨 — patterns[]에 rSquared·errorShare·trafficShare가 계약 필드(해당 kind만 값, 나머지 null)]`
| 라벨 | 오버레이 | 칩 문구(관측 특징) |
|---|---|---|
| `END_TIME_CLUSTER` | 해당 1~3초 구간에 세로 반투명 띠 `HEALTH_SOFT.warning` | 완료 시각 집중 관측 — 원인 확인 필요 |
| `DURATION_BAND` | `valueMs` ±5%에 가로 띠 | 고정 지연 띠 관측(약 N ms) — 타임아웃·정상 polling 가능 |
| `LATENCY_TREND` | 60초 p95 추세선(점선) | 응답시간 상승 추세 관측 — 적합도는 payload **`rSquared`**(정본 §3.2·§4.4, 0~1)로 "추세 적합도 R² 0.7". `confidence`(0~1 휴리스틱 점수)를 R²라고 부르지 않고 화면에서 "신뢰도"라고도 부르지 않는다. `rSquared`가 `null`이면 적합도 문구 생략 |
| `ERROR_CONCENTRATION` | `targetRouteId/targetInstanceId` 점만 테두리 강조 | 오류가 route/인스턴스에 집중 관측 — 분모는 payload **`errorShare`(오류 점유율)·`trafficShare`(트래픽 점유율)**(정본 §3.2·§4.4, 0~1)로 병기. `null`이면 **화면에서 추정하지 않고** 생략 |
- 칩 식별자 = `(serviceId, kind, since)`. 같은 식별자의 새 값은 **갱신**(칩을 늘리지 않음), `until`이 오면 오버레이를 지우고 칩은 "종료 hh:mm:ss"로 30초 남긴 뒤 제거, `[×]`는 세션 동안 같은 식별자를 숨긴다.
- 🔴 문구에 원인·권고("GC 의심", "재시작하세요")를 쓰지 않는다. 도움말 상세에 **"JENNIFER의 4패턴과 같지 않다"**를 명시(정본 §4.4).

### 2.8 일시정지 · 따라가기 · 연결 상태 · control 처리 `[X-r1 반영: 정지 시 점·통계·표 고정, control·재접속 전건]`
- **따라가기(기본)**: 오른쪽 끝이 `serverTime`을 따른다. **일시정지**(버튼·`Space`): `?at=serverTime` 기록. 🔴 **보이는 점·통계·표를 함께 고정**한다 — 축만 고정하면 늦은 수정·솎음으로 정지 화면의 표와 게이지가 계속 바뀐다. 구현: 정지 순간 창 안 버킷을 **frozen 사본**으로 떠서 렌더는 사본에서, 수신은 계속 live 버킷에 병합(정본 §2.5: 렌더만 멈추고 큐 소비). ⚠️ 사본 메모리(최대 창 1벌 추가)는 **R4 산정에 포함**한다.
- 일시정지 중 배지에 "정지 후 +n초 · 새 관측 k건(live `stats.count` 증분)"을 센다(재개 유인). 5분 넘으면 연결을 닫고 배너 "일시정지 5분 경과 — 연결을 닫았습니다. 재개하면 최신 상태를 다시 받습니다"(복귀 시 snapshot).
- **연결 상태 3단**(정본 §2.5 🔴): `연결됨`(소켓) · `갱신 중(k초 전)`(최근 **12초** 내 `spans`/`heartbeat` — 정본 ✅ 반영) · `멈춤(마지막 수신 n초 전)`. 현 `APM_LIVE_CONNECTION` 4값과의 대응: connecting → "연결 중", open+최근 수신 → 갱신 중, open+수신 없음 → 멈춤, reconnecting → "재연결 중", closed → "연결 끊김". 🔴 기존 Live hook의 상태값을 그대로 쓰는 것으로 완료하지 않는다 — P5 스트림은 `control`·snapshot 3이벤트·커서가 다르므로 **`useApmLiveSpans`(신설)**이 아래 상태 머신을 소유한다.
- **control·재접속 처리(정본 §2.5 상태 머신 전건)**:
  | 이벤트 | 화면 |
  |---|---|
  | `reject 403 retryable:false` | `source.close()`, 배너 "권한 없음"(재시도 없음 — 로그인/권한 변화 또는 사용자 새 연결) |
  | `reject 429 retryable:true` | `close()` → `retryAfterMs`+jitter(0~30%) 카운트다운 버튼 → 새 EventSource에 **`sinceEpoch/sinceSeq/viewKey`** 전달(재생 가능하면 snapshot 생략) |
  | `paused{queuePosition}` | **연결 유지**, 스켈레톤 + 배지 "입장 대기 중(n번째)" — heartbeat만 옴. 🔴 `[contract-r1 정정]` 해제는 `control{resume}`이 아니다 — **BE가 resume을 보내지 않으므로** 새 `snapshot.begin` 도착을 재개 신호로 받아 스켈레톤을 걷는다(정본 §2.5 — v1.2까지 표에 `resume`이 있었다면 오기) |
  | `degraded{clientKeepRatio, reason}` | 배지(§2.3 reason 3분기) |
  | `epochChanged` | **연결 유지**, 가진 것 전부 버리고 snapshot 대기, 배지 "서버가 재시작되어 창을 다시 받습니다" |
  | 일반 네트워크 단절(`onerror`, `CONNECTING`) | native 자동 재접속(서버 `retry: 3000`, `Last-Event-ID` 자동), 배지 "재연결 중" |
  | 스트림 열기 전 401(인증 필터·`VisitorSessionChecker` 둘 다) | `onerror`에서 세션 확인 경로(기존 관례). 🔴 `[contract-r1 정정]` 본문은 `ApiResult`가 아니라 `{"code":401,"errorCode":"INVALID_TOKEN"}` 두 필드뿐(§0 "권한 · 라이선스 게이트 표시" 참조) |
  | retryable 연속 실패 5회 | 멈추고 **사용자 버튼**("다시 연결") — 무한 재접속 금지 |
- snapshot은 `begin → chunk… → end`(chunk 수·체크섬 일치)를 모아 **한 번에** 확정하고, 그 전에는 스켈레톤이다 — 🔴 중간 chunk를 차트에 그리지 않는다. 확정 전 도착한 `spans`는 버퍼(30개)에 두었다가 `sinceSeq` 규칙으로 적용(정본 §3.2 병합 규칙 2).

### 2.9 상한 · 솎음 · keepRatio 표시 `[X-r1 반영: 강조 보존 문구 낮춤]`
- 버킷별 `observed/retained/delivered`는 군집 툴팁(§2.6)에 "이 구간 관측 412 · 서버 보관 205 · 전달 205"로. 전역은 §2.3 배지.
- 브라우저 상한(잠정 300k, R4 확정) 초과 시 기본 계층부터 1/j 솎고 강조 계층은 나중에 — 배지 문구 **"브라우저 추가 축소에서 강조 계층 우선 유지(1/j)"**. 🔴 "오류·느림은 유지"·"정상 표본만 솎음"이라고 쓰지 않는다 — 서버는 강조 계층도 예산 안에서만 보관하고(정본 §3.3 50/20k/50k), 기본 계층에도 오류·느림 점이 있다.
- 🔴 솎음을 "표본이 줄었다"로만 말하고 "요청이 줄었다"로 읽히지 않게 게이지(`stats`)는 흔들리지 않음을 도움말에 적는다.

### 2.10 키보드 · 접근성 `[X-r1 반영: 문자 단축키 범위·Esc 우선순위·입력 대체]`

## 3. 비동기 모니터링 (트레이스 상세 확장, **P5.6 신설** — 첫 출시 5항목 · 나머지 P5.6b)

### 제니퍼는
컨테이너·다중 서비스에서 비순차로 실행되는 비동기 처리(스레드 풀·메시지 큐)를 타임라인·프로파일 차트로 추적한다 — 자체 에이전트가 스레드 전환·메시지 경계를 직접 계측한다. 발행 하나에서 여러 소비를 묶어 보는 것도 제공 설명의 취지다.

### 우리 모델에서 "비동기"의 정의 — 세 층으로 분리한다 `[X-r1 반영: 관계 · 시간상 특징 · 실제 실행 방식 분리, (b) 확정 철회]`
| 층 | 우리가 말하는 것 | 데이터 근거 ✅ | 화면에서 부르는 이름 |
|---|---|---|---|
| **① 관계(links)** | `span.links[]`가 가리키는 다른 스팬 — **같은 trace / 다른 trace**는 분류 축일 뿐 실행 방식이 아니다. 부모(`parentSpanId`)를 가리키는 링크도 유효한 관계다 | `ApmTraceDetailDto.Span.links{traceId,spanId,attributes}` 저장·조회됨(`OtlpTracesReader.links` → `linksJson`(≤32/스팬) → `maskLinks`) | "연결된 스팬"(같은 트레이스 i · 다른 트레이스 j). 🔴 **링크에는 대상 `kind`가 없다** — 다른 trace를 가리킨다는 이유만으로 "발행 스팬"이라 확정하지 않는다. "발행/소비" 라벨은 **대상을 조회해 kind가 PRODUCER/CONSUMER로 확인된 경우에만** 붙인다 |
| **② 시간상 특징** | `childEnd > parentEnd + 허용 오차(1ms)` — 부모 종료 시각 이후에 끝난 스팬 | 스팬마다 `offsetMs`·`durationMs`·`parentSpanId` | "부모 종료 이후 종료". 🔴 비동기의 충분조건도 필요조건도 아니다(병렬 작업이 부모 안에서 끝날 수 있고, 다른 호스트의 시계 오차로 늦게 끝난 것처럼 보일 수 있다) — **관측 특징**으로만 부른다 |
| **③ 실제 실행 방식** | 어느 스레드에서 실제로 병렬로 돌았는가 | **없다** — `thread.*`는 스팬을 *시작한* 스레드 정보이고(OTel semconv), 스팬 DTO에 프로세스/인스턴스 식별자가 없어 같은 이름의 두 JVM을 가르지 못한다 | **주장하지 않는다.** "병렬 실행", "스레드 N개" 문구 금지. 정확한 스레드 레인은 BE 필드 보강 뒤 P5.6b |

**되지 않는 것(정직하게 화면에 적는다)**
- 🔴 **"진행 중/미완" 비동기 작업은 보이지 않는다.** 스팬은 끝나야 export된다. 그래서 "비동기 N개·미완 M개" 같은 요약은 만들지 않는다 — 대신 **"부모 종료 이후 종료 K개 · 응답에 포함된 링크 L개(같은 트레이스 i · 다른 트레이스 j)"**.
- 🔴 **완전한 링크 그래프를 약속하지 않는다.** 적재 상한 **32개/스팬**(리더 128)이고 DTO에 절단 여부가 없다 → 요약은 항상 "응답에 포함된 링크"이며 도움말에 상한·허용 속성 제한(`messaging.*` 전체가 아님)을 적는다. 절단 메타(`linksTruncated`)는 P5.6b 정본 요청(§6 후속 표).
- 🔴 **"이 응답에서 발견되지 않음" ≠ "비동기 작업이 없음."** 빈 상태 문구는 전자로만 쓴다(§3.1 빈 상태).
- 🔴 링크 대상 트레이스는 **별도 tail 샘플링 판정**을 받았으므로 저장돼 있지 않을 수 있다. 같은 trace 대상이 응답에 없으면(`truncated`) "대상 스팬이 이 트레이스 응답에 없음".
- 🔴 고아(`orphan`)·`rootMissing`·`cycleBroken`·부모 누락 스팬은 ② 판정에서 **제외하거나 "불확실"**로 표시한다(부모가 없거나 끊긴 관계를 시간 비교에 쓰지 않는다). `truncated`면 요약 옆에 "잘린 트레이스 — 일부만".
- 🔴 **X-View의 점 대상이 아니다.** X-View는 HTTP SERVER만이며(정본 §0), 자식(INTERNAL·CLIENT)·CONSUMER 처리는 점이 되지 않는다. 양쪽 도움말에 명시.
- 메시징 롤업의 `lagCount`는 "첫 링크 우선, 없으면 부모, 같은 시스템·식별 가능한 목적지·발행 1시간 lookback" 조건으로 센 것이라(✅ `ApmMessagingRollupStep`) 이 화면이 보여 주는 링크 수와 **일치한다고 설명하지 않는다**.

| 2 | **부모 종료 이후 종료 마커·해칭** | ② 해당 행에 부모의 `offset+duration` 위치 세로 점선 `╎`(`INK.muted`) + 종료선 오른쪽 해칭 `░`(같은 색, 대각선 패턴, 불투명도 0.5 — 대비는 R-P5.6 M6에서 실측) + 이름 앞 `⇢` + 툴팁 "부모 종료 이후 +N ms에 종료". 🔴 **해칭 길이 = `max(0, childEnd − max(childStart, parentEnd))`**(`childEnd − parentEnd`는 부모 종료와 자식 시작 사이 공백까지 포함한다). `ApmWaterfallBar`에 `afterParentEndPct` prop 추가 | 색만 바꾸면 오류·크리티컬 색과 충돌. 패턴+접두 기호는 색각과 무관 |

| 4 | **빈 상태(저장·응답 범위 설명)** | 요약 줄이 0·0이면: "이 응답에서는 링크나 부모 종료 이후 종료 스팬이 발견되지 않았습니다. 링크는 계측이 만들 때만 저장되며(스팬당 최대 32개), 이 트레이스가 잘렸거나(`truncated`) 대상이 별도 샘플링돼 저장되지 않았을 수 있습니다." — 🔴 "비동기 작업이 없습니다"라고 쓰지 않는다. 기존 문구 ✅ `kr.json:2004 "다른 트레이스로의 링크가 없습니다."`는 같은 trace 링크와 어긋나므로 **"이 응답에 포함된 링크가 없습니다"**로 고친다 | "발견되지 않음"과 "없음"의 구분 |
| 5 | **(선택) kind별 자기 시간 비율** | 워터폴 요약 줄 아래 접이식 카드 1개: DTO **`selfMs`**를 kind별로 합산(FE 재계산 없음 ✅), **분모 = 표시된 스팬의 `Σ selfMs`**(트레이스 경과시간·CPU 시간 아님), 합 0이면 비율을 만들지 않는다. 가로 누적 막대 1줄 + 표. 별도 탭을 열지 않는다(`?tab=async`는 P5.6b) | 워터폴이 행 단위라 못 보여 주는 한 그림, 추가 조회 없음 |

- 🔴 **트리를 다시 만들지 않는다**(✅ `apmWaterfall.ts` 계약). ② 판정은 `parentSpanId`로 원본 배열에서 부모 행을 찾는 O(n) 맵 한 번이며 정렬을 건드리지 않는다.
- 순수 함수 신설(컴포넌트 밖, 검사 가능): `apmAsyncMarks(spans) → Map<spanId, {afterParentEndMs|null, hatchMs, uncertain?: "orphan"|"rootMissing"|"cycleBroken", links: [{traceId, spanId, sameTrace, isParent, attrs}]}>`, `apmAsyncSummary(marks, meta) → {afterParentEnd, linksIncluded, linksSameTrace, linksOtherTrace, truncated}`.

### 3.3 메시징 화면과의 연결 `[X-r1 반영: 실제 경로·query 키]`
- 메시징 표(§큐/토픽)에는 새 열을 넣지 않는다(집계 화면이다). 대신 **도움말 상세에 한 줄**: "소비 지연(`lagCount`)은 발행 스팬을 링크·부모로 찾을 수 있을 때만, 같은 시스템·식별 가능한 목적지 조건으로 잽니다. 개별 메시지의 발행→소비 경로는 트레이스 상세의 링크에서 봅니다(두 수는 일치하지 않을 수 있습니다)."
- 트레이스 상세의 CONSUMER/PRODUCER 스팬 패널에 "이 목적지의 메시징 집계 보기 →" 링크: ✅ **`PATH_APPLICATION_MONITORING.messaging`**(`/application-monitoring/messaging`) + **`APM_MESSAGING_PARAM`** `msgDest`(`messaging.destination.name`)·`msgSystem`·`msgService`(스팬의 서비스) + 해당 스팬 시각을 감싸는 시간 범위(기존 페이지 query 키 재사용) — v0의 `?destination=`은 실제 키가 아니었다.

### 3.4 브레드크럼 · 되돌아가기 `[X-r1 반영: 중립 문구·상태 복원·404 문구·오류 구분]`
- `?from=<traceId>`가 있으면 헤더 아래 `Alert(info)` 한 줄: **"트레이스 {짧은 id}의 링크에서 이동했습니다 [← 돌아가기]"** — "발행에서 옴" 같은 역할 서술을 하지 않는다(소비→발행 방향일 수도 있고, `from`만으로 루트명도 모른다).

- 링크 대상 조회 실패는 셋으로 가른다(`from`이 있을 때 기존 카드의 제목을 바꾼다 — ✅ 현재 제목 "이 트레이스는 만료됐습니다"를 미저장 링크에 붙이면 틀리다):

### 3.5 R-P5.6 실측 계약 — P5.6 출시 게이트 `[X-r1 반영: 코덱스 §4 절차를 계약으로 옮김]` `[R-P5.6 반영: 실행 완료 2026-09-15 — 게이트 PASS, 결과 요약표·출시 문구는 이 절 말미]`
**목적을 둘로 나눈다.** ⓐ **생성 검증** — 해당 javaagent·라이브러리 설정에서 링크나 자식 스팬이 실제 생성되는가. ⓑ **보존 검증** — 생성된 관계가 Collector→BE→DB→API→화면까지 계약대로 유지되는가. 🔴 `@Async`·CompletableFuture의 컨텍스트 전파 지원은 "작업마다 스팬·링크가 생긴다"는 뜻이 아니다 — 자동 생성 결과와 `@WithSpan`/수동 스팬으로 관측 지점을 추가한 결과를 **분리 기록**한다.

**A. 환경 고정(결과 문서에 기록)**: JDK·javaagent·Spring·Kafka/RabbitMQ 클라이언트 버전 · SDK 샘플러·BSP 설정 · Collector 버전·저장 파이프라인 설정 · semconv opt-in·활성 계측 옵션 · fixture별 예상 작업 수·메시지 수·trace/span/message 식별자 · 프로세스/인스턴스·스레드 이름·ID를 기록한 앱 측 기준 로그. 먼저 **fixture가 전부 저장되는 격리 조건**(샘플링 100%)으로 전달 정합성을 확인하고, 그다음 실제 tail 조건으로 미저장·늦은 도착을 확인한다. P5 live 파이프라인은 필요 없다.
- `[R-P5.6 반영]` **절차 고정(실측에서 확인된 것)**: ① 격리 조건은 **BE `/apm/otlp/v1/traces`에 http/json 직접 POST**다 — tail 샘플링은 Collector 기능이고 BE 수신에는 없으므로 이것이 곧 "전부 저장" 조건이다(BE는 http/json만 받는다, protobuf/grpc는 415). ② 사용자 런타임(`:3000`·`:5173`)을 건드리지 않고 **QA BE `:3001` + 별도 Vite 포트 `5174`~`5175`**를 쓴다 — 🔴 dev CORS(`application-dev.yml`)는 **5173~5175만** 허용하므로 5176은 preflight 403이다(R-P5.6 §7-5). ③ `service.name`은 fixture 하나로 고정한다(R-P5b의 쓰레기 서비스 1,950개 재발 방지). ④ 수신 토큰은 검증 후 즉시 revoke, DB 잔존물은 순수 fixture 트레이스만 골라 삭제한다.

**B. fixture 행렬**
| fixture | 실행 조건 | 확인할 것 |
|---|---|---|
| 동기 호출 음성 대조군 | 부모 안에서 자식 DB/HTTP 호출이 끝나는 요청 | 겹치는 스팬이 2개 이상이어도 비동기/병렬로 확정하지 않는가 |
| `@Async` | fire-and-forget / 호출자가 완료를 기다리는 경우 각각 | 순수 자동계측에서 자식·링크가 생기는지, 없으면 관측 스팬을 추가했을 때 부모 전파가 유지되는지 |
| CompletableFuture | 기본 실행기·사용자 Executor, `thenApply`·`thenApplyAsync`, `allOf` 각각 | 컨텍스트 전파, 부모 선택, fan-out/fan-in 링크의 실제 생성 여부 |
| Kafka | 단건·배치 소비, 두 생산 trace의 메시지 묶음, 처리 지연 | 실제 `kind/operation`, 부모 또는 링크 경로, 메시지별 링크 속성 |
| RabbitMQ | 단건 listener·여러 소비자·배치 가능 구성 | 동일 trace/다른 trace, 생산자 참조, fan-out 관계 보존 |
| 수동 Link 대조군 | 같은 trace의 비부모 링크·부모와 같은 링크·다른 trace 링크 | UI 관계 처리를 결정적으로 검증. **자동계측 지원의 증거로 쓰지 않는다** |
| 경계·누락 | 링크 31/32/33개, 대상 미저장, 늦은 자식, 동일 스레드 이름의 두 JVM. `[R-P5.6 반영]` **128/129 행은 현 구조에서 관측 불가** — 적재 상한 `TraceIngestPipeline.MAX_LINKS=32`가 리더 상한 `OtlpTracesReader.MAX_LINKS_PER_SPAN=128`보다 작아 M3~M5 어디서도 128과 129가 구분되지 않는다(실측: 128·129 모두 DB 32개, 앞 32개 보존). 리더 상한 검증은 **P5.6b `linksTruncated`(§6.3 F2)와 함께** 다시 잡는다 — 다음 회차가 같은 시도를 반복하지 않도록 | 상한·빈 상태·잘못된 스레드 합치기·재조회 동작 |
- 최신 메시징 규약의 kind(`receive`=CLIENT, `process`=CONSUMER 등)와 기존 agent 출력이 다를 수 있으므로 **실제 출력 버전별 결과**를 남긴다.

**C. 측정 지점**: M0 앱 기준 로그(작업·메시지 수, 시작/종료, trace/span ID, 실행 스레드) · M1 Collector 수신 직후·tail 이전(원본 OTLP의 `kind`·parent·links·링크 속성·`thread.*`) · M2 저장 exporter 출력/BE 파서 입력 · M3 `linksJson`·허용목록 적용 뒤(유효 링크 순서·32개 절단·허용/별칭/차단 속성) · M4 `apm_span`(`parent_span_id`·kind·시각·attrs·links jsonb) · M5 trace detail API(동일 링크 ID·순서·마스킹·offset/duration·부분 응답 플래그) · M6 화면(마커·개수·점프 대상·선택 복귀·누락 안내·키보드·해칭 대비).

**D. 합격식**
1. **링크 전달 정합성** — 스팬 `s`마다 `L(s)` = M2에서 유효 ID를 가진 링크 목록, `E(s)` = `L(s)` 앞 32개에 현 허용목록·별칭·정책을 적용한 기대 목록. 전부 저장 조건에서 `DB.links(s) = E(s)`, `API.links(s) = 마스킹 정책 적용 E(s)`. ID·순서·허용 속성 보존 일치율 **100%**, 비허용 속성 잔존 **0건**. 33번째 링크 제거는 계약대로면 합격이되, UI가 "전체 링크"라고 말하면 **UX 불합격**.
2. **자동계측 생성 여부** — 시나리오마다 100회 반복, 작업 스팬 생성률·부모 컨텍스트 연결률·링크 생성률·같은/다른 trace 비율을 **따로** 기록. 링크 0건이면 "해당 구성에서는 자동 생성되지 않음"으로 기록하고 수동 Link 성공으로 덮지 않는다.
3. **시간·관계 계산** — 동일 JVM 결정적 fixture에서 `부모 종료 이후 표시 = childEnd > parentEnd + 허용 오차`, `해칭 길이 = max(0, childEnd − max(childStart, parentEnd))`, (P5.6b) `겹침 수 C(t) = Σ 1[start ≤ t < end]`. 기대 마커와 일치, **동기 대조군을 "병렬 실행"이라 표현한 사례 0건**. 다른 호스트 시계 차이는 별도 불확실성.
