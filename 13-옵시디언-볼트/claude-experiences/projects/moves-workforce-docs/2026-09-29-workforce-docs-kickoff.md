# Moves Workforce Docs 킥오프 — 설계·구현·교차 검증

허브: [[moves-workforce-docs]] · 관련: [[moves-workforce]] · 주제: [[forge-inter-app-integration]]

## 한 일

1. "애드온을 설치하면 Workforce 프로젝트 상세에 탭이 생기게 할 수 있나"를 공식 문서·커뮤니티로 확인 → **직접 주입은 불가**, 탭 코드를 Workforce에 넣고 설치 감지로 노출하는 방식으로 결정
2. 설계서 작성(`docs/DESIGN.md`) — 이슈 프로퍼티 계약·이동 URL·설치 감지가 두 저장소의 계약
3. 구현 2건을 병렬로 진행(계약이 설계서 하나라 가능했다): Workforce Docs 앱 신규 / Workforce 문서 탭
4. 리더가 양쪽 코드를 동시에 읽어 교차 검증, 테스트·빌드 재실행

## 결과

- Workforce Docs: 백엔드 59건·프론트 196건 통과, `CI=true` 빌드 성공. `forge lint`는 앱 등록 전이라 불가
- Workforce: 프론트 2,055건 통과, `CI=true` 빌드 성공. 기존 파일 3개에 추가만

## 교훈

- **두 Forge 앱이 만나는 곳은 엔티티 프로퍼티뿐이다.** 그러면 "어느 쪽 권한으로 읽을 수 있는 곳에 쓰느냐"가 설계의 전부가 된다. Workforce가 Confluence 스코프를 받으면 전 고객 메이저 재승인이라, 읽는 쪽 권한(Jira)에 맞춰 Jira 이슈 프로퍼티에 썼다
- **읽는 쪽이 원본을 못 읽으면 스냅샷이 필요하고, 스냅샷은 권한을 복사하지 못한다.** 문서 제목이 이슈 권한으로 보이게 된다. 설계 단계에서 한계로 명시
- **검수에서 잡은 것: 공용 기억(KVS)이 다른 제품의 데이터 범위 제한을 우회한다.** 프로젝트 이름 목록을 사이트 전체가 공유하게 구현돼 있었다. 자기 앱 안에서는 문제가 아니지만 Workforce의 소속 프로젝트 제한을 뚫는다 → 사용자별 키로 변경. 설계서에 "누구나"라고 쓴 내 탓
- 설치 감지는 API가 없어 **선언한 JQL 별칭이 유효한지**(`jql/parse` strict)로 본다. 미실측
- 병렬 구현이 성립한 조건: 계약이 문서 한 곳에 있고 두 쪽 모두 그 문서만 본다. 그래도 읽기·쓰기 조건(`url`은 `/`로 시작)이 양쪽에서 같은지는 사람이 대조해야 했다

## 외부 검토(Codex) 뒤

- 9건 중 2건 수정(저장 크기는 UTF-8 바이트로, 검색어의 검색 문법 문자 제거), 3건은 설계서에 한계로 명시, 4건 보류
- **가장 아픈 지적: 접근 범위는 Jira 권한이 정한다.** 홈 목록을 사용자별로 바꾼 것은 이름을 숨길 뿐이고, 주소를 직접 열면 Jira가 보여 주는 만큼 다 보인다. 앱 간 권한 판정 호출이 없으니 코드로는 못 막는다 → 설계서에 명시하고 사용자 결정으로 넘김
- 내가 설계서에 쓴 "페이지 단위 병합이라 다른 사용자의 연결이 남는다"는 과장이었다. 조건부 쓰기가 없으면 read-merge-write는 틈을 줄일 뿐이다
- 한계를 적을 때 "제목만 노출"처럼 줄여 쓰면 틀린다. 저장하는 필드를 전부 나열할 것

### 교훈

- **읽는 쪽에 상한이 없으면 쓰는 쪽 상한은 장식이다.** 이슈 프로퍼티는 편집 권한자가 우리 앱 밖에서도 쓴다. "30건 상한"이 우리 코드에만 있어 감사에서 이슈 1건에 2,418건을 넣어 열람자의 Confluence 호출을 폭주시킬 수 있었다. 계약은 **읽을 때도** 강제해야 하고, 두 저장소의 같은 이름 파일이 같은 상한을 가져야 한다.
- **저장된 경로를 링크에 쓰지 말고 id로 조립한다.** `/`로 시작·`//` 아님 검사는 `/../../secure/admin`을 통과시킨다. 필드를 계약에서 아예 뺐다(저장 데이터도 줄었다).
- **"사용자당 N건" 상한은 키가 N개면 성립하지 않는다.** 동시 호출이 같은 개수를 읽고 각자 쓴다(재현: 동시 1,000건 → 1,000건 저장, 삭제 205만 회 증폭). 목록을 값 하나에 넣으면 구조적으로 넘칠 수 없다.
- **react-query 재조회 실패는 `data`에 가려진다.** `data ?? null`로 실패를 판정하면 옛 성공 값이 남아 "정상"으로 보인다. `isError`를 먼저 본다.
- **한 곳도 조회하지 않으면 "가능"으로 보인다.** 연결 문서 0건이면 Confluence 조회가 안 일어나 미연결을 못 잡았다. 처음 쓰는 프로젝트가 정확히 이 경우.
- **null 하나에 두 뜻을 담지 않는다.** 분류 선택의 "아직 안 고름"과 "미분류로 바꿈"이 같은 null이라, 분류가 섞인 문서를 그대로 저장하면 전부 지워졌다.
- Codex 실행: `codex`(PATH)로 부르고 git 저장소 안에서 돌리거나 `--skip-git-repo-check`. 스크래치 폴더에서 두 번 헛돌았다.
- `npm audit fix --omit=dev`는 개발용 패키지를 지운다 → 테스트가 깨진다. `--omit=dev`는 `audit` 조회에만.
- 셸 heredoc 안에 백틱·`${}`가 든 긴 JS는 이 환경에서 자주 깨진다 → 스크립트를 파일로 쓰고 실행.

## 3일차 (2026-09-30 오후) — Workforce 본체로 흡수

- 사용자 질문 "독자적으로 할 수 있는 게 있냐" → 솔직한 답: 없다(Jira 기본 연결 + 분류·현황판뿐). 흡수 권고 → 수락.
- 하네스 전 단계 가동: 설계(Workforce 내부 매핑 — 설정 엔티티 확장·PROJECT 권한 재사용·`?view=` 뷰 전환·실패를 던지는 실행기 도입 결정) → 백엔드(manifest+설정 검증) → 프론트(코드 이식+RTL 도입) → 검증(통과 59·실패 2) + Codex(높음 1).
- 반영: 범위 판정 뒤에도 캐시로 Confluence 조회가 도는 경로(상위 `enabled` 전파), `ProjectModal`이 같은 캐시 키에 다른 모양 저장(→ `select`), S7 회귀 테스트(Atlaskit Escape는 **window keydown + keyup 쌍**), 스페이스 조회 실패 시 선택 해제.

### 교훈

- **"독자 제품인가"는 만들기 전에 물어야 했다.** 애드온 이틀치 코드는 대부분 재사용됐지만, 설치 감지·앱 간 이동·별도 라이선스·프로젝트 기억은 전부 버렸다. 두 앱 구조 자체가 비용이었다.
- **하위 쿼리의 `enabled`는 상위 게이트를 직접 물려받아야 한다.** `isSuccess`·`data`는 비활성 뒤에도 캐시로 남아 참이다.
- **한 쿼리 키에 한 모양.** `queryFn`은 원형을 저장하고 화면별 모양은 `select`로. 같은 키를 다른 화면이 다른 모양으로 채우면 "모달 열었다 닫고 60초 안에 상세 진입" 같은 재현 조건이 생긴다.
- **테스트 유효성은 변이로 확인한다.** 가드를 지우고 실패하는지 본다. Escape 테스트는 처음엔 keyup을 안 보내 두 번째 Escape가 무시된 채 통과할 뻔했다.
- 다른 세션이 같은 저장소에서 동시에 작업·커밋할 수 있다(RFC-209). 내 변경 목록은 `git status`로 다시 확인하고 남의 파일은 건드리지 않는다.
