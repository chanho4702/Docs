# 📑 Moves RMS 설계 Q&A — 지금 이 시스템은 어떻게 만들어져 있나

> Moves RMS(moves-workforce)의 **현재 구현이 어떤 구조이고, 왜 그 방식인지**를 질문-답변으로 정리한 레퍼런스. 변경 이력이 아니라 "지금 상태"를 설명한다.
> 각 답변 끝의 위키링크가 상세 노트. 기준일: 2026-07-06.
> 상위: [[moves-workforce]] · 온보딩은 [[moves-workforce-overview]] 먼저.

## A. 아키텍처 공통

### Q1. 프론트에서 요청 하나가 들어오면 백엔드는 어떻게 처리하나?

**A.** 프론트가 `invoke('함수명', params)`를 부르면 `src/index.js`에 등록된 resolver 함수가 실행된다. 흐름은 `Controller → Service → (Repository) → DB` — Controller는 함수 등록만, Service가 비즈니스 로직, Repository가 DB 접근을 맡는다(도메인별로 `src/resolver/{도메인}/`에 묶여 있음).

모든 resolver는 `responseWrapper`로 감싸져 있어서 응답 모양이 항상 같다:
- 성공: `{ success: true, ...서비스가 반환한 객체 }`
- 실패: `{ success: false, error: { name, code, message, cause } }` — Service가 커스텀 에러(`LogicalError`, `SqlError` 등)를 throw하면 wrapper가 이 모양으로 바꿔준다.

**왜 이런가**: 프론트가 어떤 함수를 불러도 "성공인지 먼저 보고, 아니면 error.code로 분기"라는 한 가지 소비 패턴만 알면 되기 때문. 실제 데이터는 대부분 `{ content: {...} }` 한 겹에 담아 반환하는데, 이건 최상위의 `success`/`error` 키와 데이터 필드가 이름 충돌하는 걸 막고, 나중에 필드를 추가할 때 기존 프론트 코드를 안 건드리기 위해서다. (진척도 같은 초기 도메인은 `res.effort`처럼 최상위에 펼쳐진 형태도 있어서, 정확한 모양은 도메인별 계약 문서가 기준이다.)

### Q2. 데이터가 SQL과 KVS 두 군데 나뉘어 있는데, 무엇이 어디에 있나?

**A.** 기준은 단순하다 — **"쌓이고 검색하는 데이터는 SQL, 몇 개 안 되고 키로 바로 꺼내는 데이터는 KVS".**
- **Forge SQL(MySQL)**: 프로젝트, 인력(projectusers), 대시보드 레이아웃, 포트폴리오 스냅샷, 간트 폴더 — 행이 계속 늘어나거나 WHERE/JOIN/집계가 필요한 것.
- **Forge KVS**: role, level, permission, status, settings, holiday, job — 종류가 유한하고 "설정값"에 가까운 것. 계산 결과 캐시(`ProjectProgress:{id}`, TTL 10분)도 KVS에 둔다.

지켜야 할 규칙 둘: ① **길이가 자라는 배열은 KVS에 넣지 않는다** — KVS는 값 하나가 240 KiB 제한이라 언젠가 터진다(포트폴리오 문제이슈 TOP50이 KVS가 아니라 SQL 테이블인 이유). ② KVS 엔티티에 새 필드를 쓰려면 **manifest의 `storage.entities` attributes에 먼저 선언하고 `forge deploy`** 해야 한다 — 선언 없는 필드는 저장 시 422 에러가 난다. → [[2026-07-06-permission-hardening]]

### Q3. 데이터 삭제(cascade)는 왜 앱 코드로 직접 하나?

**A.** Forge SQL의 실체는 TiDB인데, 일반 MySQL과 달리 **FK를 강제하지 않고, ON DELETE CASCADE가 동작하지 않고, 트랜잭션도 없다.** 즉 "부모를 지우면 자식도 지워진다"거나 "실패하면 롤백된다"는 기대가 전부 성립하지 않는다.

그래서 연쇄 삭제는 앱이 직접 한다. 방식은 **자식 테이블부터 부모 순서로, 한 단계씩 순차 DELETE**:
```
projectusers → project_dashboard → portfolio_project_snapshot → project → KVS 캐시 무효화
```
각 DELETE가 `WHERE project_id=...` 조건이라 **몇 번을 다시 실행해도 결과가 같다(멱등)**. 트랜잭션이 없어도 중간에 실패하면 그냥 처음부터 재실행하면 복구된다 — 이게 이 시스템에서 다단계 쓰기의 표준 패턴이다(간트 폴더 삭제도 같은 방식). 참고로 "삭제는 됐는데 자식 행이 남아 있다"는 현상이 보이면 FK 미강제 때문이다. → [[forge-sql-no-fk-cascade]]

### Q4. Jira API는 어떤 권한(asUser/asApp)으로 호출하나?

**A.** **기본은 asUser** — 화면을 보고 있는 사용자의 권한으로 호출한다. 사용자가 볼 수 없는 이슈는 앱도 안 보여주는 게 자연스럽고, 앱 권한(asApp)을 넓게 쓰면 마켓플레이스 심사 부담도 커진다.

asApp을 쓰는 곳은 딱 두 군데고, 둘 다 "asUser가 불가능한" 경우다:
1. **일일 배치**(포트폴리오 스냅샷) — 스케줄 트리거는 "실행시킨 사용자"라는 개념 자체가 없어서 asUser로 호출하면 401이 난다. 공통 API에 `as` 파라미터(기본 'user')가 있고 배치 체인만 `'app'`을 넘긴다.
2. **간트 계층 필드 write** — readOnly 앱 커스텀필드는 전용 엔드포인트(`PUT /app/field/{id}/value`)로만 쓸 수 있는데, 이 엔드포인트가 asApp 전용이다(Q22).
→ [[forge-readonly-appfield-write]]

### Q5. 번역(i18n)은 어떻게 관리되나?

**A.** 소스는 `locales/kr/{기능}.json` + `locales/en/{기능}.json`(기능 단위 파일)이고, `cd static/ui && npm run merge`를 돌리면 전부 합쳐져 `ko-KR.json`/`en-US.json`이 생성된다. 앱은 이 산출물을 읽는다.

**왜 이런가**: 기능별 파일로 나눠야 여러 작업이 같은 파일을 두고 충돌하지 않고, 산출물을 자동 생성하니 두 언어의 키가 어긋나는 걸 merge 시점에 잡을 수 있다. 그래서 **산출물(ko-KR/en-US)을 직접 수정하면 안 된다** — 다음 merge 때 소실된다. 주의 둘: `locales/script/*.json`은 빈 스텁이라 여기 넣으면 반영이 안 되고, UI의 `t()` 함수는 **변수 치환을 지원하지 않는다**(`t(key, {md})`의 둘째 인자는 기본값) — 동적 값은 `tFormat(t, key, vars)` 헬퍼로 `{var}` 토큰을 수동 치환한다. → [[forge-i18n]]

### Q6. 새 기능은 어떤 프로세스로 만드나?

**A.** `feature-harness` 스킬의 순차 파이프라인으로 만든다: **설계(feature-architect) → 백엔드 → 프론트 → 검증(integration-verifier)**. 산출물은 `_workspace/<기능>/`에 요구서/설계서/구현 리포트/검증 리포트로 남는다.

핵심 규율은 하나 — 설계서의 **"경계면 계약"(resolver 입력과 응답 shape을 글자 그대로 적은 표)이 백엔드·프론트 공통의 단일 기준**이라는 것. 백엔드는 이 모양대로 만들고 프론트는 이 모양대로 소비하며, 검증자는 양쪽 코드를 동시에 읽어 글자 단위로 대조한다. 백/프론트가 서로의 코드를 안 봐도 계약만 지키면 맞물리게 하는 구조다. → [[harness-engineering]]

## B. 공수 계산 모델 (MM / 가동률)

### Q7. "1MM"은 무엇인가?

**A.** **1MM(Man-Month) = 그 달의 실제 근무일 수(평일 − 공휴일)**. 관리자가 입력하는 값이 아니라 캘린더와 휴일 관리 데이터로 자동 계산된다.

하루의 "근무 가치"를 이렇게 정의한다: 주말=0, 공휴일=workRatio(0=휴무, 0.5=반휴, 1=정상), 평일=1. 어떤 기간의 기준 공수(base MD)는 이 값을 그냥 **더해서** 구한다 — 비례식 없이 근무일을 직접 센다. 이러면 모든 단위가 "근무일 1일 = 1MD"로 통일되어, 공휴일·연차 차감과 단위가 정확히 맞는다. 설정으로 남은 건 `hourRate`(1일=N시간, 시간↔MD 변환용) 하나다. → [[2026-05-27-mm-redesign]]

### Q8. MM과 가동률은 뭐가 다른가? 왜 둘 다 있나?

**A.** 서로 다른 질문에 답하는 지표라서 둘 다 필요하다:

| | MM (절대 공수) | 가동률 % (상대) |
|---|---|---|
| 질문 | "일을 **얼마나** 했나" | "가용 시간 대비 **얼마나 채웠나**" |
| 식 | `totalMd ÷ 그달 1MM 근무일` | `totalMd ÷ effectiveMd(가용 근무일)` |
| 분모 특징 | 월 기준으로 고정(연차 무관) | 연차를 뺀 실제 가용일 |

예: 이번 주에 1.6MD 일했고 가용일이 1.4MD였다면 → MM은 0.08(한 달 20일 기준 얼마 안 됨), 가동률은 114%(가용보다 많이 일함). 하나는 절대량, 하나는 포화도 — 이 둘을 한 숫자로 합치면 "3일 일했는데 1MM 초과" 같은 이상한 값이 나온다. 여러 달에 걸친 기간의 MM 분모는 걸친 달들의 1MM 평균을 쓴다(월별 차트는 달마다 정확한 값 사용). → [[2026-05-27-mm-redesign]]

### Q9. 가동률 분모는 어떻게 정해져 있나?

**A.** 두 가지 규칙이 있다.
1. **분모에 미래를 넣지 않는다** — 분모는 프로젝트 전체 기간이 아니라 `min(오늘, 종료일)`까지의 경과 근무일이다. 투입(분자)은 과거에만 쌓이는데 분모에 미래가 들어가면, 진행 중인 프로젝트는 아직 오지 않은 날들 때문에 가동률이 항상 낮게 나온다.
2. **전사 가동률은 배치에서 계산한다** — 한 사람이 같은 기간에 여러 프로젝트에 걸쳐 있으면, 프로젝트별 가용일을 단순히 더한 분모는 그 사람을 이중으로 세어 가동률이 과소된다. 올바른 분모는 "인원별 기간의 **합집합**"인데, 이건 프로젝트별 숫자를 더해서는 복원할 수 없는 값이라 원본 데이터에 접근하는 배치 시점에 계산해 둔다. 그래서 전사 가동률은 포트폴리오에서 유일하게 프론트 재집계가 아닌 배치 산출 지표다.
→ [[2026-06-02-portfolio-implementation]]

### Q10. 지표를 만들 때 지키는 공통 원칙은?

**A.** 분석 화면 전반에 적용되는 세 가지:
1. **같은 개념이면 분모도 같아야 한다** — "가동률"이 화면마다 다른 분모(전체 기간 vs 경과 기간, 고정 20일 vs 실제 근무일)를 쓰면 숫자가 화면마다 달라져 신뢰를 잃는다. 지표를 추가할 땐 분자/분모를 기존 화면과 나란히 놓고 비교한다.
2. **라벨은 실체를 정확히 부른다** — salary 합계의 실체는 참여 기간 총단가이므로 화면에서 "예산"이 아니라 **"계획 인건비"**라고 부른다. 라벨이 부풀려지면 산식이 맞아도 잘못된 의사결정을 유도한다.
3. **근사치는 숨기지 않고 화면에 명시한다** — 데이터 한계로 정확히 계산 못 하는 지표(예: 완성률의 공수 근사)는 그 사실을 InfoTip(ⓘ)으로 **모든 관련 화면에 동일하게** 노출한다. 한 곳에만 적어두면 다른 화면에서 과신이 생긴다.
→ [[2026-06-11-analysis-review]]

## C. 진척도 (Progress)

### Q11. 진척도는 왜 숫자 하나가 아니라 "3층"인가?

**A.** "프로젝트가 어떻게 되어 가나"에는 사실 성격이 다른 질문 셋이 섞여 있고, 이를 절대 한 숫자로 합치지 않는 것이 이 화면의 정체성이다:

| 층 | 질문 | 산식 |
|----|------|------|
| 층1 공수 | 얼마나 **일했나** (돈/노력 소진율) | 계획 누적(선형) vs 실제 누적(워크로그 일별합) |
| 층2 완성 | 얼마나 **끝났나** (진짜 진척) | Σ(이슈 진행률 × 계획MD) ÷ Σ(계획MD) |
| 층3 일정 | 시간이 얼마나 **흘렀나** (달력) | 경과 근무일 ÷ 전체 근무일 |

돈을 많이 썼다고(층1) 일이 끝난 게 아니고, 시간이 흘렀다고(층3) 진척된 게 아니다. 프로젝트 관리 기법 EVM의 AC/EV/PV에 해당한다. 상태 판정(정상/주의/지연)의 주 신호는 "완성 vs 일정" 비교(±5%p, settings의 threshold), 보조 신호가 "공수 vs 완성"이다. → [[2026-05-29-progress-page]]

### Q12. 이슈 하나의 "진행률"은 어떻게 구하나?

**A.** 상태 카테고리별로: **완료 = 100% 고정**(공수를 초과 투입했어도 100%로 캡) / **진행 중 = min(실투입MD ÷ 계획MD, 100%)** / **할 일 = 0%**. 계획MD가 없는 이슈는 가중 평균의 분모에서 제외한다.

알아둘 한계: Jira에 "몇 % 처리됐다"는 필드가 없어서, 진행 중 이슈의 진행률은 **공수를 얼마나 썼는가로 근사**한 값이다. "일을 많이 했다 = 많이 끝났다"는 가정이 깔려 있으므로, 이 근사가 쓰이는 모든 지표(완성률, CPI, 신호등 T)에 InfoTip으로 근사임을 명시해 둔다. 정밀화(진행률 커스텀 필드, 상태 전이 이력)는 로드맵. → [[2026-05-29-progress-page]]

### Q13. 진척도 화면엔 왜 기간 필터가 없나?

**A.** 진척도는 **"지금 이 순간, 프로젝트 전체가 어디까지 왔나"를 찍는 스냅샷**이기 때문이다. 완성률·일정률은 프로젝트 전체에 대한 값이라 애초에 기간으로 자를 수 없고, 워크로그만 기간으로 자르면 화면 안에서 어떤 지표는 전체 기준·어떤 지표는 필터 기준이 되어 서로 모순된다(S-curve 끝점과 실투입 막대가 안 맞는 식). 그래서 백엔드 조회 자체가 날짜 인자 없이 전체 기간이고, 캐시 키도 `ProjectProgress:{projectId}` 하나다. "구간을 잘라 보는" 분석은 인력/이슈 분석 탭의 역할. → [[2026-05-29-progress-page]]

### Q14. "지연"은 어떻게 측정하나?

**A.** 완료된 것과 안 된 것을 다르게 본다:
- **확정 지연**(완료 이슈, 돌아보기): 실제 완료일(Done 상태 + 마지막 워크로그 작성일) − 마감일(duedate). 지연된 것(>0)만 평균 내고, 일찍 끝낸 이슈는 별도 지표(`avgLeadDays`)로 분리한다 — 섞으면 평균이 서로 상쇄돼 둘 다 안 보인다.
- **예측 지연**(미완료 이슈, 내다보기): 남은 공수 `max(계획−실투입, 0)` 기준으로 이슈별 예상 종료일을 구해 그 최댓값을 프로젝트 종료일과 비교한다. 이슈마다 전 인원이 붙는다고 가정하므로 **낙관적인 근사**이고, 화면 카드에 그렇게 표시되어 있다.
→ [[2026-05-29-progress-page]]

## D. 포트폴리오 대시보드 (전사 통합)

### Q15. 전사 대시보드는 왜 "배치 스냅샷 + 프론트 재집계" 구조인가?

**A.** 두 단계로 이해하면 된다.
1. **왜 배치인가**: Forge 런타임은 메모리 256MB·실행 시간 제한이 있어서, 화면을 열 때마다 전 프로젝트를 실시간 집계하는 건 불가능하다. 그래서 하루 한 번 Scheduled Trigger 배치(`portfolioSnapshot.js`)가 프로젝트별 집계를 SQL 테이블(`portfolio_project_snapshot`)에 적재해 두고, 화면은 이 스냅샷만 읽는다.
2. **왜 프론트 재집계인가**: 백엔드는 **프로젝트별 raw 데이터**(인원 배열, 월별 공수 포함)만 내려주고, 화면 상단의 프로젝트 멀티셀렉트 필터에 따른 분포·합산·누적 계산은 전부 프론트 `useMemo`가 한다. 필터를 바꿀 때마다 서버를 다시 부르지 않아 즉각 반응하고, 백엔드에 "필터 조합별 사전 집계"를 만들 필요도 없다.

단 하나의 예외가 전사 가동률 — Q9의 이유(합집합 분모는 프론트에서 복원 불가)로 배치가 계산한 값을 그대로 쓴다. → [[2026-06-01-portfolio-dashboard]] · [[2026-06-02-portfolio-implementation]]

### Q16. 스냅샷 데이터는 어디에 어떻게 저장되나?

**A.** 세 갈래다:
- **프로젝트 스냅샷** = SQL `portfolio_project_snapshot`. 인원 배열은 `members_json`이라는 JSON 컬럼 하나에 통째로 — 어차피 SQL로 across 집계를 안 하고 프론트가 재집계하므로, 인원을 별도 테이블로 정규화해도 이점이 없다.
- **문제이슈 TOP50** = 별도 SQL 테이블. 길이가 자라는 배열이라 KVS 금지(Q2).
- **집계 메타**(마지막 집계 시각, 진행 중 여부 가드) = KVS.

배치는 프로젝트 2개씩 동시(pLimit 2), 한 프로젝트가 실패해도 나머지는 진행(allSettled). 인원 데이터는 projectusers(명단·role·salary) + 워크로그(투입) + Jira(표시 이름) 세 소스를 배치가 서버에서 병합해 완성한다. 화면의 "재집계" 버튼은 같은 배치를 수동으로 트리거하며, KVS 가드로 중복 실행을 막는다. → [[2026-06-01-portfolio-dashboard]]

### Q17. 종합개요의 T/S/R 신호등은 각각 무엇을 보나?

**A.** 프로젝트를 세 축으로 요약하는 신호등이다:
- **T(Time)** = 완성률과 일정률의 차이. `progressThreshold`(기본 5%p)보다 뒤처지면 빨강.
- **S(Scope)** = 잔여 작업 비중(todoRatio). settings의 `scopeTodoAmberRatio/RedRatio`(기본 0.3/0.6) 기준.
- **R(Resource)** = 가동률. settings의 밴드(0.7/1.1/1.3) 기준 — 너무 낮아도(놀림) 너무 높아도(과부하) 경고.

주의: 신호등의 R은 **그 프로젝트 안 인원들의 평균**이고, 헤더의 전사 가동률(합집합 분모)과는 의미가 다르다 — 의도된 차이이고 InfoTip에 설명되어 있다. → [[2026-06-05-portfolio-signal-thresholds]]

### Q18. 일일 배치는 어떤 권한으로 도나?

**A.** 배치 체인의 Jira 호출은 전부 **asApp**이다. 스케줄 트리거 실행에는 사용자 컨텍스트가 없어서 asUser 호출이 성립하지 않기 때문(Q4). 구현은 공통 API의 옵셔널 `as` 파라미터(기본 'user') — 배치만 `'app'`을 넘기고 일반 resolver 경로는 그대로 asUser다. 스케줄 경로처럼 "실행 컨텍스트가 다른" 코드는 유닛테스트·수동 실행으로는 검증이 안 되므로, 배포 후 tunnel로 스케줄 실행을 직접 한 번 관찰하는 것이 검증 표준이다. → [[2026-06-11-analysis-review]]

## E. 비용 분석

### Q19. 비용 분석의 salary는 무슨 값이고, 화면에선 뭐라고 부르나?

**A.** `projectusers.salary`는 월급이 아니라 **그 인원의 프로젝트 참여 기간 전체에 대한 총단가**(계약 금액)다. 그래서 Σsalary는 "이 프로젝트에 계획된 인건비 총액"이고, 화면 라벨도 **"계획 인건비"**다 — 승인된 "예산(BAC)"이 아니므로 예산이라 부르지 않는다(예산이라 부르는 순간 "예산 대비 소진율" 해석이 전부 오염된다). 실제 소진(AC)은 워크로그 MD를 인원 단가로 환산해 계산한다. 급여 데이터 접근은 `PROJECT_COST` 권한 키로 제어되고(시드 기준 Member는 못 봄), 화면에는 합계·구간 분포만 노출한다. → [[2026-07-06-permission-hardening]] · [[2026-06-11-analysis-review]]

## F. 워크로그 성능

### Q20. 워크로그 조회는 왜 "기능별 전용 페처"인가?

**A.** 워크로그는 Jira가 원본이고(앱 DB에 미러링하지 않음), 조회 패턴은 **프로젝트 단위 1회 페치 + KVS 캐시 + 프론트 슬라이스**다. 인원×이슈 단위로 반복 호출하면 N+1로 느려지므로, p-limit 동시성 제한을 건 병렬 페처가 프로젝트 전체 워크로그를 한 번에 가져오고, 화면은 그 결과를 잘라 쓴다.

이 페처가 **공통 모듈이 아니라 기능별 전용**(`getResourceProjectWorklogs` 등)인 이유: 공통 경로를 최적화하면 그 경로를 쓰는 모든 화면이 영향권(blast radius)에 들어간다. 전용 페처면 문제가 생겨도 해당 기능만 위험 부담하고, 다른 화면은 건드리지 않는다. 진척도·포트폴리오도 이 전용 페처를 재사용하는 방식으로 확장되어 있다. → [[forge-worklog-performance]]

## G. 간트 (이슈 연결 간트 + 폴더)

### Q21. 간트의 "선후행"과 "계층"은 왜 저장 위치가 다른가?

**A.** 두 관계는 요구가 달라서 저장소도 다르다:

| 관계 | 화면 | 저장 위치 | 왜 |
|------|------|----------|-----|
| **선후행**(A 끝나야 B 시작) | 막대 사이 화살표 | **Jira 네이티브 이슈 링크**("Blocks") | 표준 API로 사용자 권한(asUser) write가 되고, Jira 이슈 화면의 링크 섹션에도 자동으로 나타난다 — 앱 밖에서도 보이는 것이 장점 |
| **계층**(부모-자식 트리) | 좌측 트리 들여쓰기 | **앱 커스텀필드 `wbsParentField`** | Jira 네이티브 계층은 3레벨 고정이라, WBS처럼 **임의 깊이**가 필요한 트리는 앱이 직접 들고 있어야 한다 |

네이티브 링크는 관계 타입(FS/SS)이나 지연(lag)을 저장할 수 없으므로 화면의 `FS/lag:0`은 표시용 고정값이다. 순환 참조(A→B→A)는 Jira가 안 막아주므로 앱이 검증한다 — 트리는 `detectTreeCycle`, 링크는 `detectDagCycle`, 위반 시 에러코드로 거부하고 프론트가 토스트를 띄운다. → [[2026-07-02-issue-link-gantt]]

### Q22. 계층 필드는 왜 asApp 전용 엔드포인트로 쓰나?

**A.** `wbsParentField`는 앱이 소유한 **readOnly 커스텀필드**인데, readOnly 앱 필드는 일반적인 `PUT /rest/api/3/issue`로는 절대 쓸 수 없다("Field does not support update" 400). 유일한 write 경로가 `PUT /rest/api/3/app/field/{fieldId}/value`이고 이 엔드포인트는 asApp 전용 + issueIds를 숫자로 요구한다. 이것이 앱 전체에서 asApp을 쓰는 두 예외 중 하나다(Q4). 일반 원칙: 앱 필드에 write할 일이 생기면 그 전에 네이티브 구조(이슈 링크 등)로 풀 수 있는지 먼저 검토한다 — 선후행이 네이티브 링크인 이유이기도 하다. → [[forge-readonly-appfield-write]]

### Q23. 간트 라이브러리(SVAR)는 어떤 제약 아래서 쓰고 있나?

**A.** `@svar-ui/react-gantt`(MIT 라이선스 — GPL인 `wx-react-gantt`는 사용 금지)를 무료 빌드로 쓰며, 무료 빌드의 빈 곳은 직접 구현해 메운다:
- **세로선 마커**(오늘/시작/종료)는 PRO 전용이라 렌더 코드 자체가 없음 → 커스텀 오버레이로 그린다(SVAR 내부 좌표식과 동일한 계산으로 픽셀을 맞춤).
- **CSS/폰트 CDN**이 Forge CSP에 차단됨 → patch-package로 CDN 참조를 제거하고 폰트 자체 호스팅. 툴팁도 같은 이유로 커스텀.
- 동작 규칙: `open:true`는 자식 있는 노드에만(leaf에 주면 크래시), 트리 아코디언은 컬럼 `id==='text'`에만 붙음, scale format은 함수로.
- **편집 이벤트는 전부 가로챈다** — SVAR 이벤트에서 `return false`로 라이브러리 내부 상태 변경을 막고, 서버에 mutate한 뒤 우리 데이터로만 다시 그린다. 화면의 진실은 항상 서버 데이터라는 원칙("서버 권위").
라이브러리 동작이 궁금하면 문서보다 dist 번들 소스를 직접 읽어 확정하는 것이 이 프로젝트의 관행이다. → [[2026-07-02-issue-link-gantt]]

### Q24. 간트에서 편집하면 화면은 어떻게 갱신되나?

**A.** **낙관적 업데이트 + 부분 패치** 3단계: ① onMutate — 서버 응답을 기다리지 않고 캐시에 먼저 반영(화면 즉시 갱신), ② onSuccess — 서버 응답으로 **해당 대상만** 캐시를 부분 패치, ③ onError — 롤백. 전체 invalidate(재조회)는 하지 않는다.

**왜 재조회하지 않나**: 두 가지 이유. 전체 재조회는 느려서 편집 체감이 나쁘고, 더 근본적으로는 **Jira 검색 인덱스가 지연되기 때문** — 커스텀필드를 쓴 직후 `search/jql`로 재조회하면 옛 값이 돌아온다. 그래서 재조회 대신 서버가 돌려준 확정 값으로 캐시를 직접 패치하는 것이 정확하기도 하다. → [[2026-07-02-issue-link-gantt]]

### Q25. 간트 "폴더"는 무엇이고 어떻게 구현되어 있나?

**A.** 폴더는 Jira 이슈가 아닌 **앱 자체의 가상 그룹핑 노드**다 — 이슈들을 임의 깊이 폴더 트리로 묶어 보는 기능. SQL 2테이블(`gantt_folder` 폴더 트리, `gantt_folder_issue` 이슈→폴더 매핑)에 저장한다.

구조의 핵심은 **"기존 계약은 그대로, 폴더는 얹기만"**: read 응답의 tasks 모양은 손대지 않고 `folders[]`와 `folderIssues{}`를 별도 필드로 추가(additive)했고, 프론트 어댑터(`ganttAdapter.js`)가 이 둘을 합성해 SVAR 노드 트리를 만든다. 기존 소비 코드가 구조적으로 영향을 받지 않는 방식이다.

동작 규칙들:
- **폴더 삭제 = 내용물 승계** — 소속 이슈·하위 폴더를 상위로 올린 뒤 폴더만 지운다(순차·멱등, Q3 패턴).
- **순환 방어 이중화** — 백엔드가 부모 체인을 추적해 거부하고, 프론트 어댑터도 손상 데이터에 무한루프 없이 견딘다.
- **폴더 롤업** — 기간은 하위 이슈의 min~max, 수행율은 **계획MD 가중 평균**(계획 없는 이슈는 1MD 등가로 폴백 — 가중치 단위가 MD라서 폴백과 단위가 맞는다).
- **폴더는 이슈 편집 경로에서 배제** — 링크 추가/삭제, 이동, 수정 4경로 모두 폴더 노드면 skip. 폴더는 이슈가 아니므로.
- 이슈의 부모 결정 우선순위: wbs 계층 > 폴더 매핑 > 루트.
→ [[2026-07-02-gantt-folder-layer]]

## H. 권한 체계

### Q26. 권한 체계의 전체 그림은?

**A.** 두 축이다: **누가**(권한 세트 — Admin/Member 시드 + 커스텀, KVS 저장, 사용자당 1개. Jira 사이트 관리자는 자동 Admin) × **무엇을**(리소스 카탈로그 14키 — 페이지가 아니라 "권한 경계" 단위, 각각 read/write). 여기에 세트별 `projectScope`(ALL/MEMBER_ONLY)가 데이터 범위를 추가로 제한한다.

집행은 이중이다: **프론트**는 `canRead/canWrite`로 메뉴·버튼을 숨기고(UX), **서버**는 모든 resolver 호출을 가드로 검증한다(보안). 화면 숨김은 우회 가능하므로(브라우저 콘솔에서 `invoke()` 직접 호출) 실제 보안 경계는 서버 가드다. → [[2026-07-06-permission-hardening]]

### Q27. 서버 가드는 어떻게 동작하나?

**A.** 모든 resolver(109개)는 `guardedDefine`으로 등록되고, 함수별로 (리소스 키, read/write)가 `PermissionMap`에 선언되어 있다. 요청이 오면: `PrincipalResolver`가 `req.context.accountId`(Forge가 넣어주는 신뢰 가능한 값)로 호출자의 권한 세트를 해석(30초 인메모리 캐시라 warm 상태에선 외부 호출 0회) → 매핑된 리소스의 read/write 보유를 검사 → 통과 시에만 핸들러 실행.

안전장치 셋:
1. **deny-by-default** — 매핑에 없는 함수는 무조건 거부(`PERMISSION_UNMAPPED`). "깜빡하면 열리는" 게 아니라 "깜빡하면 잠긴다".
2. **jest 계약 테스트** — "등록된 함수 집합 = 매핑된 함수 집합"을 CI가 강제. 새 resolver를 매핑 없이 추가하면 빌드가 깨져서, 가드 누락이 배포까지 갈 수 없다.
3. **fail-close** — 백엔드가 완전한 권한 카탈로그를 응답하고, 프론트는 받은 값만 쓴다. 응답에 없는 키를 "허용"으로 채우는 기본값이 없다.
공유 조회(예: 사용자 모달이 직무 목록을 읽어야 함)는 리소스 배열 매핑(OR-grant)으로 과차단을 피한다. → [[2026-07-06-permission-hardening]]

### Q28. 권한 키는 왜 페이지당 하나가 아니라 14개인가?

**A.** 페이지:키 1:1이면 권한 관리 매트릭스가 30행 이상으로 폭발하고 페이지가 늘 때마다 관리 부담이 비례한다. 대신 **"권한 경계"가 실제로 다른 곳에서만 키를 나눈다**. 분리 기준 세 가지: (a) **민감도**가 다르다 — `PROJECT_COST`(인건비·단가)가 프로젝트 일반 정보와 분리된 이유(시드 기준 Member는 못 봄). (b) **사용자군**이 다르다. (c) **write의 의미**가 다르다. 반대로 본인 데이터만 다루는 워크로그(self-scope)는 잠글 실익이 없어 키 자체가 없다. 카탈로그는 `src/permission/ResourceCatalog.js` **한 파일이 단일 소스**이고, 시드·마이그레이션·프론트가 전부 여기서 파생된다 — 정의가 여러 곳에 흩어져 어긋나는 것을 구조적으로 막는다. → [[2026-07-06-permission-hardening]]

### Q29. projectScope(소속 프로젝트 제한)는 어떻게 동작하나?

**A.** 권한 세트의 필드 `projectScope: 'ALL' | 'MEMBER_ONLY'`. MEMBER_ONLY인 세트의 사용자는 **자기가 인력으로 등록된(projectusers) 프로젝트만** 볼 수 있다. 세트별 필드인 이유: 전역 설정 하나로는 "내부 직원은 전체, 외주는 소속만" 같은 집단별 차등이 불가능하다.

집행 지점이 둘로 나뉜다: **상세 조회**는 가드가 소속을 검증해 거부(`PERMISSION_PROJECT_SCOPE_DENIED`), **목록 조회**는 서비스가 `WHERE project_id IN (소속)` 필터를 걸어 애초에 좁혀서 반환(응답 모양은 그대로). 관리자는 항상 ALL이고, 전사 포트폴리오는 차단 대신 소속 프로젝트만의 집계로 축소된다. 시드 세트는 scope 토글만 전용 resolver로 편집할 수 있다(Admin 세트는 변경 거부). → [[2026-07-06-permission-hardening]]

### Q30. 가드 외에 서버가 추가로 지키는 규칙은?

**A.** "권한이 있어도 남의 것·남의 범위는 안 된다"를 위한 세 규칙:
1. **본인 데이터 함수는 신원을 payload로 받지 않는다** — myWork류 SELF 함수는 클라이언트가 보낸 accountId를 무시하고 서버가 `context.accountId`로 강제한다. payload는 조작 가능하므로 신원·범위 파라미터는 절대 신뢰하지 않는다.
2. **이슈 상세의 프로젝트 소속은 서버가 역산한다** — issueKey만 받고, 그 이슈가 어느 프로젝트 것인지는 서버가 JQL로 직접 확인해 scope를 검증한다(issueKey는 정규식 검사로 인젝션 방어).
3. **시드 권한 세트는 불변** — Admin/Member 시드는 어떤 update 경로로도 본문 수정이 거부된다(`PERMISSION_SEED_IMMUTABLE`). 전용 경로에만 제약을 걸면 범용 update 경로가 우회로가 되므로, 같은 리소스를 만지는 모든 경로에 동일하게 걸려 있다.
→ [[2026-07-06-permission-hardening]]

## I. 저장공간 관리 (DB 사용량 모니터링)

### Q31. 이 기능은 왜 있고, 무엇을 보여주나?

**A.** Forge SQL은 프로덕션 설치당 **1 GiB 한도**이고, 넘으면 앱이 정지된다 — 그 사고를 미리 감지하는 관리자 페이지(`/backoffice/storage`)다. 보여주는 것: 총 사용량 게이지(사용/한도, %) + 80%/90% 임계 경고, 테이블별 크기·행수(내림차순), 프로젝트별 사용량 근사. 접근은 `STORAGE_MONITORING` 권한 키(시드 기준 Admin 전용). 추이 그래프·"n일 후 도달" 예측·아카이빙·엑셀 추출은 의도적으로 뺐고(후속), KVS 용량도 안 본다 — KVS는 집계 API가 없고, 값 하나 240 KiB 제한이라 SQL 같은 "누적형" 위험이 아니기 때문. → [[2026-07-03-storage-monitor]]

### Q32. 사용량은 어떻게 재나? 눈에 띄는 설계 선택 세 가지는?

**A.** 자체 테이블 없이 **MySQL 시스템 뷰 `information_schema.tables`를 읽기만 한다** — 테이블별 `data_length+index_length`(크기)와 `table_rows`(행수)를 합산. DDL도 마이그레이션도 없는 순수 읽기 기능이다.

설계 선택 셋:
1. **임계치(80/90%)는 프론트에만 정의** — 몇 %에서 노랗게/빨갛게 할지는 표시의 문제라 서버 응답에 안 넣는다. 서버·클라 양쪽에 정의하면 언젠가 어긋난다. (`usedPercent`는 100을 넘을 수 있고, 게이지 폭만 100으로 자르고 숫자는 실제값을 보여준다.)
2. **한도는 상수 + 환경변수 오버라이드** — Forge는 코드에서 "지금 dev인지 prod인지" 알 방법이 없어서, 기본 1 GiB에 `forge variables set STORAGE_LIMIT_BYTES`로 환경별 주입한다.
3. **수치는 추정치임을 화면에 고지** — TiDB의 통계 기반 값이라 정확하지 않을 수 있다. 모니터링 용도로는 충분하고, InfoTip으로 "추정치"라고 밝힌다.
→ [[2026-07-03-storage-monitor]]

### Q33. "프로젝트별 사용량"은 정확한 값인가?

**A.** 근사치다. 프로젝트 구분이 있는 테이블들(project, projectusers, project_dashboard, portfolio_project_snapshot, gantt_folder 등)에서 **프로젝트별 행수 × 그 테이블의 평균 행 크기**로 배분한 값 — "어느 프로젝트가 용량을 많이 먹나"의 순위를 보는 용도(향후 아카이빙 대상 선정)지 정밀 측정이 아니다. 구현 디테일 둘: `project_id`가 BINARY(16)라 `BIN_TO_UUID()`로 문자열화해야 집계 키가 맞고, 평균 행 크기 매칭을 위해 테이블명은 information_schema의 실제 이름(`projectusers` — `project_users` 아님)과 정확히 일치시켜야 한다. → [[2026-07-03-storage-monitor]]

## J. 운영·배포

### Q34. 라이선스는 어떻게 체크하나?

**A.** responseWrapper 공통 가드에서 **`license.active === false`일 때만 차단**하고, `license === undefined`는 통과시킨다. undefined는 무료 배포·개발 환경·터널에서 나오는 값이라, 이걸 막으면 개발이 불가능해진다. 차단 시에는 에러가 아니라 인앱 가이드 페이지로 안내한다. manifest에 `appIsLicensed`를 넣지 않는 이유: 넣으면 Jira가 미라이선스 상태에서 앱 자체를 숨겨버려 안내 화면을 보여줄 기회가 없다. → [[forge-licensing]]

### Q35. DB 스키마 변경(마이그레이션)은 언제 실행되나?

**A.** 세 시점에서 실행된다: **설치 직후(onInstall)** + **앱 업그레이드 이벤트(`avi:forge:upgraded:app`)** + **스케줄 트리거**. 스케줄만 믿으면 "설치했는데 첫 스케줄 전까지 테이블이 없는" 공백이 생기므로 onInstall 선행이 필수다. 시드 데이터는 SEED_VERSION 비교로 멱등하게 넣는다 — 실패하면 버전이 안 올라가 있어 다음 실행에서 자동 재시도되는 구조. → [[forge-migration-lifecycle]]

### Q36. 로컬 개발 환경에서 알려진 함정은?

**A.** 코드가 아니라 환경 문제인 세 가지 — 갑자기 빌드/배포가 전멸하면 이것부터 의심:
1. `forge deploy`가 "Premature close"로 실패 → Node v24/v22.23 버그. nvm으로 **22.22.0** 사용.
2. "node.exe를 인식할 수 없다" → `NVM_HOME`/`NVM_SYMLINK` 환경변수 소실. User 변수로 복구.
3. `npm run`이 전부 exit 1 (prebuild부터 실패) → `ComSpec` 환경변수 소실. cmd.exe 경로로 복구.
