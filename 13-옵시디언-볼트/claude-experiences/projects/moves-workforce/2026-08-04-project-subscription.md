# 2026-08-04 · 프로젝트 구독 (RFC-171)

> RMS 프로젝트가 Jira **스페이스**를 구독하면 그곳에 추가되는 이슈가 자동으로 그 프로젝트 작업으로 편입된다.
> 설계 → 구현(P1~P3) → 외부 검증 2회 → 보드 제거 → development 배포·동작 확인까지 하루에 진행.
> 상태: **development 배포 확인 완료 · 운영 배포 미수행 · `develop` 머지 대기**

관련: [[moves-workforce]] · [[2026-07-14-team-managed-implementation]](앱 필드/프로퍼티 계열) · [[forge-sql-migration-column-gap]]

---

## 1. 무엇을 만들었나

기존에는 이슈를 RMS 프로젝트에 넣으려면 **작업 등록 모달에서 하나씩 골라야** 했다.
스페이스를 구독해 두면 그 일이 자동으로 일어나게 만든 것.

```
구독 규칙(DB)  →  대상 이슈 검색  →  moves_RMS_projectId 에 프로젝트 값 write
                                      └ 이 순간부터 기존 화면 20여 곳이 알아서 인식
```

편입 경로는 셋이다.

| 경로 | 담당 |
|---|---|
| 이슈 생성 이벤트 | 즉시 편입(스페이스 구독의 체감 속도) |
| 시간별 리컨실 스윕 | **정확성의 원천** — 이벤트 유실·이슈 이동·조건 후행 충족을 흡수 |
| 백필 | 구독 시 "기존 이슈도 가져오기"를 켰을 때 1회 |

## 2. 핵심 설계 결정

### 2-1. "가상 필터"가 아니라 물리 태깅

`moves_RMS_projectId` 를 JQL 술어로 읽는 곳이 **20군데 이상** 흩어져 있다. 조회 시점에 JQL을
넓히는 방식이면 그 20곳을 다 고쳐야 하고, 하나라도 빠지면 화면마다 이슈 집합이 달라진다
(진척·비용·MM이 서로 다른 모집단 위에서 계산된다). → 규칙만 저장하고 **실제로 필드에 값을 쓴다.**

### 2-2. 충돌 회피는 코드 분기가 아니라 JQL 술어

모든 대상 검색에 `AND moves_RMS_projectId IS EMPTY` 를 넣는다. 이미 다른 프로젝트 소속인
이슈는 **후보에조차 들어오지 않는다.** 분기문이 아니라 술어라서 이벤트·리컨실·백필·미리보기
전 경로에 자동 적용된다.

### 2-3. SCAN → APPLY 분리

검색하면서 동시에 태깅하면 `IS EMPTY` 결과집합이 줄어들어 **다음 페이지 커서가 이슈를 건너뛴다.**
읽기를 전부 끝내 목록을 고정한 뒤에만 쓴다.

### 2-4. 커서를 아예 쓰지 않는다 (v3)

위 분리로도 부족했다. 예산이 소진돼 부분만 처리하고 커서를 저장하면, **다음 invocation 에서
줄어든 결과집합에 옛 토큰을 쓰게 되어** 아직 안 본 이슈를 통째로 건너뛴다.
→ 커서를 버리고 매번 첫 페이지부터 재스캔한다. 태깅분이 `IS EMPTY` 에서 빠지며 앞부분이
짧아지므로 실행할수록 전진한다. 중복 스캔 비용은 있지만 누락은 없다.

### 2-5. `baseline_at` 과 `watermark` 는 별개 축

"기존 이슈도 가져오기" 선택이 양쪽에서 새지 않게 하는 장치.

| 백필 | `baseline_at` | `watermark` | 첫 스윕 |
|---|---|---|---|
| 함 | NULL | NULL | 소스 전체를 훑음 |
| 안 함 | now | now | 증분만, `created >= now` 인 것만 |

하나로 합치면 깨진다 — 리컨실은 `updated` 기준이라 **"구독 전 생성 + 최근 수정"** 이슈가
백필 OFF 구독에 흘러들어오고, 반대로 `watermark` 를 항상 채우면 백필 ON 이 과거를 못 훑는다.

### 2-6. 보드 제거 (v3, 가장 큰 결정)

이슈는 Jira 프로젝트 하나에만 속하므로 **스페이스끼리는 이슈가 겹치지 않는다.**
겹침의 유일한 경로가 "스페이스 A"와 "A 를 포함하는 보드"였고, 그 때문에 서로 다른 RMS
프로젝트가 같은 이슈 소유권을 두고 경쟁할 수 있었다 — 외부 검증이 **"release 최우선"** 으로
꼽은 P0였다.

보드를 빼자 claim 테이블 같은 구조 변경 없이 그 문제가 사라졌다. 덤으로 Agile scope 의존,
보드 filter+subQuery 결합, ORDER BY 파싱, "보드는 최대 1시간 지연"까지 함께 해소.
21건 지적 중 8건 정도가 이 결정 하나로 정리됐다.

> **기능을 빼는 것이 가장 저렴한 해결책일 때가 있다.** 보드 범위는 `extraJql`
> (`sprint in openSprints()`)로 대부분 대체된다.

## 3. 외부 검증에서 나온 것

코덱스에 두 번 검토를 맡겼다 — 설계 단계 1회, 수정 후 1회.

### 설계 검토 (21건: P0 2 / P1 7 / P2 9 / P3 3)

가장 아팠던 지적들:

- **미리보기가 권한을 우회했다** — 소스 접근 검증 없이 `asApp` 으로 count·sample 을 조회해,
  RMS read 권한만 있으면 **사용자가 볼 수 없는 스페이스의 이슈 키·요약**을 받아볼 수 있었다.
  생성에만 게이트를 두고 미리보기 경계에는 재사용하지 않은 탓.
- **`baseline_at` 이 SELECT 3개 중 1개에서 누락** — 스케줄 스윕 경로에서만 백필 OFF 가
  무력화됐다. 단위 테스트도 빌드도 못 잡았다. → 세 SELECT 를 공통 fragment 로 통합하고
  projection parity 테스트를 넣었다.

### 걸러내기

사용자 지시: **"너무 엣지 케이스에 대한 건 고려 안 해도 됨"**

- **대응** — 평범하게 쓰면 만나는 것(항상 발생 / 데이터 손실 / 권한 누출)
- **보류** — 조건이 정확히 겹쳐야 터지는 동시성 경합, 큐 부분 실패, livelock

보류한 것도 무엇을 왜 미뤘는지는 남겼다. → [[skip-edge-cases]]

## 4. 배포해서야 드러난 것 (핵심 교훈)

백엔드 1,066 테스트 + 프론트 빌드가 전부 통과한 상태로 배포했는데 **3건이 나왔다.**

### 4-1. 모달이 열리지 않음 (TDZ)

`rows` 를 `useState` 에서 파생 계산으로 바꾸며 선언이 사용처(`head`) 아래로 내려갔다.

```js
const head = { ... rows.length ... }   // 여기서 참조
const rows = rawIssues.map(...)        // 여기서 선언  ← ReferenceError
```

**문법상 완전히 유효**해서 컴파일·테스트·빌드가 전부 통과하고, 그 컴포넌트를 렌더할 때만
터진다. 정적 검증으로는 절대 안 잡히는 종류.

### 4-2. 기능을 한 경로에만 붙임

기본 계획 작업량을 **편입 경로 4개 중 리컨실 스윕 한 곳에만** 붙였다. 정작 사용자가 테스트한
이벤트 즉시 편입 경로에는 없었다. `baseline_at`(SELECT 3개 중 1개)과 **같은 계열의 실수**를
같은 기능 안에서 반복한 셈.

> 여러 경로에 걸친 기능을 추가할 때는 **경로 목록을 먼저 세어보고** 하나씩 지워야 한다.

### 4-3. 문구가 무엇을 뜻하는지 알 수 없음

"다른 프로젝트가 구독 중" — 사용자 반응: *"우리가 구독중인 거를 표시한 거야 아님 다른
프로젝트에서 작업을 등록해서 쓰는 게 있다 이거야 헷갈려"*

`takenBy` 가 `projectId` 만 담고 이름이 없었다. 이름과 `isMine` 을 함께 내려
`「웹 리뉴얼」구독중` / `이 프로젝트가 이미 구독중` 으로 갈랐다.

## 5. Forge 특성으로 겪은 것

### 5-1. 컬럼 추가 마이그레이션은 최대 1시간 공백을 만든다 ★

배포와 마이그레이션이 분리돼 있는데 `isTableReady` 가 **테이블 존재만 확인하고 컬럼은 보지
않는다.** `v017`(컬럼 추가)이 안 돈 상태에서 그 컬럼을 읽는 SELECT 가 실행돼 오류가 화면까지
올라왔다.

```
init-db 스케줄 트리거  → 시간별
onInstall             → 재배포만으로는 발동 안 함("이미 최신 버전")
ensureSeed            → seed_version 이 최신이면 스킵
```

구독만의 문제가 아니라 **이 앱 전체에 해당**한다. → [[forge-sql-migration-column-gap]]

### 5-2. resolver 25초 한도

백필 SCAN 을 사용자 요청 안에서 20초까지 돌렸는데, INSERT·큐 push·응답 직렬화를 더하면
한도를 넘겨 **저장은 됐는데 화면은 실패**로 뜬다(재시도하면 "이미 구독 중"). 8초로 줄이고
못 훑은 분량은 리컨실이 흡수하게 했다.

### 5-3. 소량은 큐를 쓰지 않는 게 낫다

사용자 제안: *"50건 이상이면 큐 처리하고 이하면 그냥 등록해버리면 안 될까?"*

앱 필드 write 는 50건을 한 번에 보낸다 → 그 이하는 PUT 1회, 1초 미만. 큐로 넘기면 사용자는
"가져오는 중"만 보고 결과를 확인하러 새로고침해야 했다. **스캔이 완주했을 때만** 즉시 처리
(예산 소진으로 50건만 읽은 걸 "전부"로 착각하면 나머지가 조용히 빠진다).

## 6. 남은 것

- **같은 스페이스 중복 구독 허용** — PK 를 `(project_id, source_type, source_id)` 로 바꾸고
  이벤트 판정이 N건 중 하나를 고르도록. 조건(JQL)을 달리해 한 스페이스를 두 프로젝트가
  나눠 쓰는 정당한 사용을 지금은 막고 있다.
- 보류한 검증 지적: sweep lease(동시 실행), 큐 부분 실패 복구, 실패 prefix starvation
- `develop` 머지 · 운영 배포

## 7. 한 줄 정리

**"테스트 통과"와 "화면이 뜬다"는 다른 말이다.** 1,066개가 초록이어도 렌더 시점 오류와
경로 누락은 안 잡힌다. 그리고 **기능을 빼는 것**(보드)이 P0 하나를 구조적으로 없애는
가장 싼 방법일 때가 있다.
