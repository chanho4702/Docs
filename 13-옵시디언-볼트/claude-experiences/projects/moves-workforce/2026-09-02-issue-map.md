# 2026-09-02 이슈 맵 뷰 + Jira dev-status는 Forge에서 못 쓴다

프로젝트: [[moves-workforce]] · 브랜치 RFC-192 · 하네스 `feature-harness` 순차 파이프라인(architect → frontend → verifier, 백엔드 없음)

## 무엇을 했나
- 작업관리 탭에 4번째 뷰 **이슈 맵**: 이슈를 티켓 카드 노드로 가로 트리 배치(React Flow + 직접 작성 레이아웃), 클릭으로 하위 펼침, 우측 드로어에 워크로그 이력·커밋 이력 탭.
- 사용자는 처음에 "메뉴 하나 더"를 원했지만, 트리 뷰가 이미 같은 계층을 보여주고 있어 **뷰 전환 그룹의 4번째 뷰**로 제안해 채택. 같은 데이터를 보는 화면이 탭 두 곳으로 갈라지는 것을 막았다.

## 결정과 이유
1. **백엔드 0줄.** 트리 뷰와 같은 원칙 — `useGanttData` → `toSvarTasks` → `buildWorkTree` 재사용, 계층 규칙을 맵에서 재해석하지 않는다.
2. **진행도는 `progressPercent`.** 요구사항은 `progress`라고 적었지만 실측하니 그건 간트 막대용 근사값이고, 트리 상세 "처리율"은 `progressPercent`였다. 같은 화면 그룹이 다른 숫자를 보이면 안 된다. 설계 에이전트가 코드를 읽고 요구사항을 정정한 사례.
3. **레이아웃 라이브러리 안 씀.** dagre/d3-hierarchy가 없었고, 트리 한 방향 배치는 O(n) 단일 패스 순수 함수로 충분(jest 대상).
4. **dev-status 파서는 throw 금지 + 고정 shape.** 비공개 API라 언제 깨질지 몰라 방어를 한 곳에 가두고, 실패는 붉은 오류가 아닌 안내 빈 상태.

## 교훈
- **Jira `dev-status`(개발 패널 내부 API)는 Forge에서 401 "scope does not match".** Atlassian 스태프가 2024-03·2025-08 두 번 "private API는 scope가 없어 Forge에서 접근 불가"라고 못박았다. 프론트 `@forge/bridge` requestJira도 같은 프록시라 결과는 같다. 커밋/PR/브랜치가 필요하면 처음부터 **Bitbucket REST + external OAuth provider**(B안) 규모로 잡을 것. 이번엔 배포 후 실측 전에 공개 자료로 판정이 나서 fail-soft 설계 덕에 화면은 멀쩡하지만 커밋 버튼은 사실상 죽은 버튼이다.
- **구현 에이전트의 "했다"는 리포트를 믿지 말고 diff로 본다.** 프론트 에이전트가 `TreeDetailPanel` 워크로그 공용화를 리포트에 적었으나 파일이 한 줄도 안 바뀌어 있었다. verifier의 `git diff --stat` 대조가 잡았다. (confluence-approval-dc의 "자기보고와 검증 분리" 교훈 재확인)
- **python으로 코드 블록을 잘라낼 때 `};` 첫 매치는 내부 중첩일 수 있다.** 화살표 함수 안의 `walk` 정의가 먼저 잡혀 꼬리가 남았고 빌드에서 `'return' outside of function`으로 드러났다. 삭제 후에는 반드시 빌드.
- 이 세션은 브라우저 자동화가 권한 분류기에 막혔다. 실화면 확인은 사용자에게 절차를 넘긴다.

## 열린 항목
