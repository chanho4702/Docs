# 배치 12 설계 — 결재 플로우 정의

> 상태: **설계안 (2026-08-19)**. 구현 전 사용자 확인이 필요하다.
> 요구 출처: 2026-08-19 사용자 지시 — "전역 결재 플로 설정 할 수 있게 했음 좋겠는데 상태도 추가 가능하고"

## 1. 먼저 정리해야 할 이름 충돌

이 저장소에는 이미 **"승인 Flow"**가 있다. 결재선 템플릿이다 — *누가 어떤 순서로 결재하는가*.
배치 12가 말하는 "결재 플로우"는 그것이 아니라 *어떤 상태를 거치는가*다.

같은 이름을 두 뜻으로 쓰면 설정 화면에서 관리자가 무엇을 고르는지 알 수 없게 된다.
이 문서에서는 아래 이름을 쓴다.

| 이름 | 뜻 | 지금 있는가 |
|------|----|-----------|
| **결재선 템플릿** (기존 "승인 Flow") | 누가 어떤 순서로 결재하는가 | ✅ 있음 (`APR_FLOW`) |
| **결재 유형** (배치 12에서 새로 만드는 것) | 어떤 단계 이름과 상태를 거치는가 | ❌ 없음 |

구현에 들어가면 기존 화면의 "승인 Flow"도 **"결재선"**으로 문구를 바꿔야 한다.

## 2. 지금 구조 — 무엇이 이미 "흐름"인가

코드로 확인한 사실이다.

**상태는 5개**이고 `ApprovalStatus` enum에 박혀 있다.

```
PENDING → APPROVED    (마지막 단계까지 통과)
        → REJECTED    (누군가 반려)
        → EXPIRED     (마감 지남 / 진행 중 본문 편집)
        → CANCELLED   (요청자·관리자 회수)
```

**닫힌 요청은 다시 열리지 않는다.** `ensureOpen()`이 `PENDING`이 아니면 전부 막는다.
편집 후 재승인도 상태를 되돌리는 것이 아니라 **새 요청을 만들어 계보로 잇는다**(`fromRequestId`).

여기서 중요한 점 — **이 앱에서 "진행"을 만드는 것은 상태가 아니라 단계(step)다.**

```java
if (currentStepIndex() >= steps.size()) {
    status = ApprovalStatus.APPROVED;
}
```

3단계 결재선이면 요청은 `PENDING`에 머문 채 1→2→3단계를 지나고, 마지막에야 `APPROVED`가 된다.
즉 **흐름은 이미 있고, 그것을 표현하는 것이 단계다.** 상태는 흐름이 아니라 *결과*다.

## 3. 그래서 "상태 추가"가 실제로 뜻하는 것

Jira의 상태(`할 일 → 진행 중 → 완료`)는 이슈가 **머무는 자리**이고, 전이는 사람이 누르는 버튼이다.
이 앱의 상태는 성격이 다르다 — 결재의 **결말**이다. 이 차이를 무시하고 Jira를 그대로 흉내 내면
"승인됨"과 "반려됨"을 같은 평면에 놓고 관리자가 임의 전이를 그리게 되는데,
그 순간 *결재 기록이 무엇을 뜻하는지*가 설치마다 달라진다.

사용자의 요구를 실제 쓸모로 풀면 네 갈래다.

| # | 해석 | 도메인 영향 | 비용 | 실제 수요 |
|---|------|-----------|------|----------|
| (a) | 상태 **표시명**만 조직 용어로 | 없음 | — | ✅ **이미 됨** (배치 8.5) |
| (b) | **단계에 이름** — 1단계 "부서 검토", 2단계 "본부 승인" | 거의 없음 | 낮음 | 높음 |
| (c) | **결과 상태 추가** — "조건부 승인", "보류" 등 | 큼 | 높음 | ? |
| (d) | **전이 규칙 변경** — 반려 시 처음이 아니라 이전 단계로 | 큼 | 높음 | ? |

(a)는 끝났다. **(b)가 대부분의 조직이 실제로 원하는 것**이고 위험이 거의 없다.
(c)·(d)는 진짜로 필요한지 확인이 필요하다 — 아래 6절.

## 4. 제안 — 세 걸음으로 나눈다

### 12a. 단계에 이름 붙이기 (권장, 먼저)

결재선 템플릿의 각 단계에 이름을 준다. 진행 중인 요청의 상태 표시가
`승인 대기 2/3` 에서 `본부 승인 대기 (2/3)` 로 바뀐다.

- 데이터: `APR_FLOW_STEP`에 `NAME` 컬럼 하나. 없으면 지금처럼 "N단계".
- 도메인: **건드리지 않는다.** 단계 이름은 표시용이고 전이 판정에 쓰이지 않는다.
- 요청 생성 시 결재선과 함께 **snapshot**한다 — 템플릿의 이름을 나중에 바꿔도
  진행 중인 요청의 이력은 그대로여야 한다(기존 결재선 snapshot과 같은 원칙).
- 화면: 업무함 상태 칸, 페이지 배너 pill, 상세 모달의 단계 목록, 알림 문구.

이것만으로 "우리 회사 결재 흐름"이 화면에 드러난다. 위험은 거의 없다.

### 12b. 결재 유형 (선택)

여러 결재선 템플릿을 묶어 "이 스페이스는 이 유형을 쓴다"를 정한다.
사실상 **기존 결재선 템플릿 + 스페이스별 기본값**이라, 12a 이후에 필요성을 다시 보는 게 맞다.

### 12c. 상태·전이 재설계 (보류 권장)

관리자가 상태를 추가하고 전이를 그리는 것. 아래 5절의 대가를 치를 값어치가 있는지
**먼저 확인해야 한다.**

## 5. 12c를 하면 무엇이 깨지는가

정직하게 적는다. 이건 "어렵다"가 아니라 "여기가 무너지면 배치 1~10이 전부 흔들린다"는 목록이다.

1. **`ApprovalStatus` enum이 사라진다.** 지금 이 enum은 AO 컬럼 값(`STATUS = 'PENDING'`),
   REST 필터(`parseStatuses`), CSS 클래스명(`.stamp.APPROVED`), 상태 표시명 설정 키,
   이메일 분기, 업무함 탭 정의에 모두 박혀 있다. 문자열 상태로 바꾸면 이 전부가 검증 없는 통로가 된다.

2. **"열린 요청은 대상당 하나"가 흔들린다.** `dedupeKey = "open:" + scopeKey`는 unique 제약이다.
   무엇이 "열린" 상태인지를 관리자가 정하게 되면, **관리자가 설정을 바꾸는 순간 기존 데이터가
   제약을 위반**할 수 있다(닫힘이던 상태를 열림으로 바꾸면 한 대상에 열린 요청이 둘이 된다).

3. **`ensureOpen()`이 의미를 잃는다.** 지금은 "PENDING이 아니면 못 건드린다"가 한 줄이다.
   전이표가 생기면 "이 상태에서 이 행동이 허용되는가"를 매번 조회해야 하고,
   그 조회는 락 안에서 일어나야 한다.

4. **감사 이력의 뜻이 설치마다 달라진다.** `ApprovalEventType`도 같이 열어야 하는데,
   그러면 "APPROVED 이벤트"가 무엇을 뜻하는지 코드가 알 수 없다. 이메일 본문·알림 문구·
   재승인 판정(`requiresReapproval`)이 전부 이벤트 타입으로 분기하고 있다.

5. **기존 데이터 이행.** 이미 쌓인 요청은 5상태 체계로 저장돼 있다. 새 체계로 옮기려면
   "기본 플로우"를 만들어 매핑해야 하고, 그 매핑이 틀리면 과거 결재 기록이 왜곡된다.

6. **C10 이식 부담이 커진다.** jakarta 어댑터는 순차 승인 이전 상태에서 멈춰 있다.
   도메인을 바꾸면 이식 대상이 그만큼 더 커진다.

## 6. 사용자 확인이 필요한 것

12a는 지금 바로 만들 수 있다. 12c로 갈지는 아래가 정해져야 판단할 수 있다.

1. **어떤 상태를 추가하고 싶은가?** 실제 예가 필요하다.
   - "조건부 승인" 같은 **결말**인가 → 상태 추가가 맞다.
   - "부서 검토 중", "본부 승인 대기" 같은 **진행 단계**인가 → 12a로 해결된다.
2. **반려된 건을 되살리고 싶은가?** 지금은 새 요청을 만들어 계보로 잇는다.
   같은 요청을 다시 여는 것은 "결재는 그 시점 그 내용에 대한 동의"라는 전제와 충돌한다.
3. **스페이스마다 다른 흐름이 필요한가, 아니면 전역 하나면 되는가?**
4. 이 요구가 **특정 고객의 것인가**, 아니면 일반 기능으로 갖추고 싶은 것인가?
   전자라면 그 고객의 실제 결재 양식을 보고 설계하는 편이 정확하다.

## 7. 결론

- **12a(단계 이름)를 먼저 만든다.** 위험이 거의 없고, "우리 회사 흐름이 보인다"는 요구의
  대부분을 채운다.
- **12c는 6절이 답해지기 전에는 착수하지 않는다.** 도메인 상태 머신은 이 앱에서 가장
  많은 것이 매달린 곳이고, 되돌리는 비용이 만드는 비용보다 크다.
- 12c로 가기로 정해지면 **C10 이식을 먼저** 한다. 도메인이 바뀐 뒤에 이식하면 두 번 일한다.
