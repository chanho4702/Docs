어플리케이션 모니터링 (APM)

사이드바 모니터링 > 어플리케이션 모니터링 (PREMIUM · APM 기능) 경로 /application-monitoring/overview → 서비스·수집기 등 하위 경로 상태 1단계(P1: 개요·서비스·수집기·알람 규칙)가 구현되어 서버 파이프라인은 종단 검증됐다. 브라우저 화면 검증과 배포는 아직이라 review다. 서비스 맵·트레이스 탐색은 2단계, 합성 감시는 3단계 예정이다.

무엇을 하는 화면인가

고객이 운영하는 애플리케이션(서비스)이 살아 있는지, 얼마나 빠른지, 얼마나 실패하는지를 서비스 단위로 보여 주고, 나빠졌을 때 어느 엔드포인트·런타임 자원이 원인인지 좁혀 주는 화면이다.

서버 모니터링과의 차이는 주어가 호스트가 아니라 서비스라는 점이다. "사내 Jira가 지금 느린가"에 답한다.

APM 개요

  • 위쪽 숫자 4개: 전체 트래픽 합계(초당 요청·오류율·p95·액티브 요청)와 비교 구간 대비 변화. 목록에서 숨긴 서비스도 포함하는 값이라 아래 상태 요약의 개수와 모집단이 다르다.
  • 서비스 상태 도넛: 상태별 개수. 숫자 칩을 누르면 그 상태만 걸러진 서비스 목록으로 간다.
  • 서비스 × 시간 히트맵: 행이 서비스, 칸이 시간 구간, 색이 오류율. 회색 칸은 오류가 없는 것이 아니라 요청이 없었다는 뜻이다.
  • 느린 서비스 Top 5 · 오류 많은 서비스 Top 5 · 최근 알람: 이름을 누르면 지금 보고 있는 시간 범위를 들고 상세로 이동한다.
  • 아래 회색 카드 3장(배포 스트립·SLO 위험·서비스 맵 미니)은 다음 단계 자리다.

서비스

목록 — 서비스마다 상태·환경(env)·초당 요청·오류율·p95·인스턴스·버전·마지막 수신·추이를 한 줄로 본다.

  • 상태는 최근 5분 판정이고, 초당 요청·오류율·p95는 상단 시간 범위 전체 합산이다. 둘의 창이 다르다.
  • 정렬은 나쁜 상태부터(중단 → 성능 저하 → 수신 끊김 → 확인 불가 → 정상). 배지에 마우스를 올리면 판정 근거("오류율 10.1% > 5.0%")가 보인다.
  • 숨긴 서비스는 '숨긴 서비스 포함'을 켜야 보인다. 숨겨도 수집은 계속된다.
  • 서비스가 하나도 없으면 온보딩 안내(수집기 설정 → 앱에 한 줄 → 수신 대기)가 뜬다.

상세 — 헤더에 상태 배지·env·버전·인스턴스 수·마지막 수신·호스트가 있고, 탭 12개 중 5개가 열려 있다. 나머지 탭(트레이스·에러·데이터베이스·외부 호출·배포·로그·합성 감시)은 단계 배지가 붙은 채 비활성이다.

탭무엇을 보나주의
개요요청수·오류율(알람 임계 점선)·응답시간 p50/p95/p99·응답시간 분포 히트맵·Apdex·액티브 요청·24시간 가용성 띠·느린/오류 엔드포인트 Top 5·인스턴스 미니카드가용성 띠는 상단 시간 범위와 무관하게 항상 최근 24시간(5분 칸). 왼쪽 %는 "수신이 있었나"이며 SLA가 아니다
트랜잭션엔드포인트(route)별 호출수·초당 요청·p50·p95·오류율 표. 행을 누르면 그 경로의 추이 3장기타(__other__)는 route 상한(서비스당 500)을 넘어 접힌 합. /**는 404, /*는 인증 필터에서 끊긴 요청이 모이는 자리 — 실제 코드 경로가 아니다. 상태코드·메서드 분포는 서비스 전체 값
런타임힙·논힙 메모리, GC 시간·횟수, 스레드, CPU, 로드된 클래스, 커넥션 풀, 풀 대기 p951단계는 JVM만 실제로 저장된다. .NET·Node·Python·Go 서비스는 '계측 미제공' 배지가 보인다. Apdex T는 초, 나머지 지연은 ms
인스턴스인스턴스별 상태(정상/수신 끊김)·버전·호스트·초당 요청·p95·오류율, 최대 6대 추이 비교인스턴스 지표는 1분 데이터(7일 보존)에만 있다 — 기간이 7일을 넘으면 값이 비어 온다. 인스턴스가 멈춘 것이 아니니 기간을 좁힌다
설정표시명·설명·태그·담당자·Apdex T(초)·느림 임계(ms)·호스트 수동 매핑·숨김·삭제, 적용 중인 알람 규칙(읽기)관리자만 저장. 환경(env)은 앱이 보내는 값이라 여기서 못 바꾼다. 삭제는 숨긴 상태에서만 되고 되돌릴 수 없다 — 앱이 계속 보내면 새 서비스로 다시 등록된다

서비스 맵 · 트레이스 탐색 (2단계 예정)

화면 자리만 있다. 서비스 맵은 서비스·DB·외부 호출·큐의 연결 그림, 트레이스 탐색은 전 서비스 산점도·검색 → 스팬 워터폴이 들어온다. 수집기 설정 파일에는 트레이스 파이프라인(tail 샘플링·SQL 마스킹)이 이미 들어 있고, 서버는 /v1/traces를 200으로 받아 버린다(폐기 통계 SIGNAL_NOT_SUPPORTED).

합성 감시 (3단계 예정)

Zabbix 웹 시나리오를 서비스에 바인딩해 "밖에서 본 가용성"을 나란히 보여 줄 자리다. 이때부터 상태 '중단(DOWN)'이 생긴다 — 1단계에서는 나오지 않는다.

수집기

탭 4개: 상태 / 토큰·설정 / 설치 가이드 / 등록·설정. 관리자 전용이다.

  • 상태: 등록된 Collector마다 버전·마지막 수신·큐 적체·전송 실패 누계. —는 0이 아니라 그 지표가 오지 않은 것이다. 누계는 수집기를 재시작하면 0으로 돌아간다. 아래에 최근 60초 수신 확인('지금 확인' 버튼)과 폐기·변형 통계(받았지만 저장하지 않은 메트릭과 그 이유)가 있다.
  • 토큰·설정: 수신 토큰 발급·회수, 설정 파일(yaml) 생성. 토큰 원문은 발급 응답 한 번에만 보인다. 서버는 해시만 갖고 있어 다시 알려 줄 수 없다.
  • 설치 가이드: OS(Windows/Linux) × 스택(Java/.NET/Node/Python/Go)별 Collector 설치·앱 계측·확인 절차. 화면이 서버에서 받아 그대로 그리므로 설치본 설정(사내 미러 등)이 반영된다. 문서판은 수집기 설치.
  • 등록·설정: 새 서비스 등록 방식(자동 / 승인 / 사전 등록만), 자동 숨김(일), 수신 끊김 판정(분), 서비스당 route 상한, SQL 마스킹·원문 SQL 보존, 승인 대기 목록.

공통으로 알아 둘 것

시간 범위와 눈금

  • 프리셋 15분·1시간·6시간·24시간·7일·30일 또는 사용자 지정. 기본은 1시간.
  • 점 간격은 창 길이로 자동 결정된다(6시간 이하 1분 · 7일 이하 5분 · 그 이상 1시간). 서버는 1분 데이터를 7일, 5분을 30일, 1시간을 400일 보존한다.
  • 시간 범위·env·탭·선택 엔드포인트 등 화면 상태는 URL에 실린다. 주소를 복사해 넘기면 같은 화면이 열린다.
  • 자동 새로고침: 끔(기본)·30초·1분·5분.

—와 0은 다르다

  • 값이 없는 구간은 —(표), 끊긴 선(차트), 빈 칸(히트맵·띠)이다. 0으로 채우지 않는다.
  • 요청수 차트의 0은 "요청이 없었다"는 측정된 사실이고, 오류율·응답시간·Apdex는 요청이 없으면 계산이 안 되어 —다.
  • 예외는 목록의 스파크라인 하나다 — 모양만 보는 칸이라 값 없음을 0으로 접어 그린다.

권한

  • 조회: 로그인 사용자. 라이선스에 APM 기능이 없으면 메뉴가 잠긴다.
  • 쓰기(서비스 설정·삭제, 알람 규칙 조회·편집, 수집기 화면 전체): 관리자만. 비관리자는 설정 탭을 읽기 전용으로 보고, 알람 규칙 화면은 배너만 본다.

서비스 상태 5종

최근 5분(설정 '수신 끊김 판정(분)', 기본 5) 데이터로 판정하며, 위에서 아래 순서로 첫 번째 맞는 것이 상태다.

상태조건조치
확인 불가 (UNKNOWN)이 서비스가 5분 이상 미수신인데 등록된 수집기도 전부 5분 이상 미보고앱이 아니라 파이프라인(Collector·네트워크·토큰·라이선스)을 먼저 본다. 이때 앱을 재기동하면 사고가 된다
수신 끊김 (STALE)5분 이상 미수신인데 수집기는 살아 있음. 새 버전 인스턴스가 처음 나타난 뒤 10분은 유예앱 프로세스·에이전트를 본다
성능 저하 (DEGRADED)수신은 있고 최근 5분 오류율 > 임계(기본 5%) 또는 p95 > 임계(기본 2000ms, 서비스 설정의 '느림 임계'가 있으면 그 값)배지 툴팁의 근거를 보고 트랜잭션 탭으로
중단 (DOWN)합성 감시(3단계)가 바인딩돼 있고 실패일 때만1단계에서는 나오지 않는다
정상 (UP)위 어느 것도 아님—
  • 요청이 0건인 5분은 임계 판정을 건너뛴다 — 야간 저트래픽 서비스가 성능 저하로 찍히지 않게.
  • 성능 저하와 수신 끊김은 같은 노랑이다. 색만 보지 말고 배지 안 문구를 본다.
  • 확인 불가 판정은 전역이다. 수집기가 여러 대이고 한 대만 끊긴 환경에서는 그 서비스가 수신 끊김으로 보인다.
  • 인스턴스 상태는 정상/수신 끊김 둘뿐이다.

알람 규칙 (설정 ⚙ > 알람 규칙)

판정은 MovesEye가 5분마다 하고, 배달은 Zabbix가 한다. 규칙을 만들면 Zabbix에 호스트 그룹·호스트 MovesEye APM(인터페이스 없는 가상 호스트) 아래 전용 트래퍼 아이템·트리거가 자동 생성되고, 평가 결과 값이 밀려 들어가 Zabbix Problem이 뜬다. 그래서 기존 Zabbix 액션·미디어(메일·Slack·Teams)·에스컬레이션·유지보수 창·이 앱의 Problem 화면이 그대로 붙는다. 알림 채널을 새로 만들지 않는다.

"알림 액션 없음" 배지 — Zabbix 액션 연결

이 배너가 있으면 알람이 떠도 아무에게도 안 간다. MovesEye는 액션·미디어를 절대 대신 만들지 않으므로 고객의 Zabbix에서 한 번 연결해야 한다.

  1. Zabbix 프런트엔드 > 알림(Alerts) > 액션 > 트리거 액션을 새로 만들거나 기존 것을 연다.
  2. 조건에 다음 중 하나를 추가한다.
    • 호스트 그룹 = MovesEye APM
    • 이벤트 태그 owner = moveseye-apm (또는 태그 owner가 있기만 하면)
  3. 오퍼레이션(보낼 사용자·미디어)은 기존 메일·Slack·Teams 미디어를 그대로 쓴다.
  4. 액션을 활성으로 두고, MovesEye 알람 규칙 > Zabbix 상태 탭을 새로고침해 '알림 액션 수'가 1 이상인지 본다.

자주 묻는 것

Q. 오류율이 높은데 404 때문인가? 아니다. 오류율은 5xx만 센다. 404·401 같은 4xx는 클라이언트 오류로 보아 제외한다. 4xx가 많은지는 트랜잭션 탭의 상태코드 분포(노란 층)에서 본다.

Q. '수신 끊김'과 '확인 불가'는 무엇이 다른가? 둘 다 5분 이상 데이터가 안 온 상태다. 차이는 수집기다. 수집기가 살아 있으면 앱 쪽 문제로 보아 '수신 끊김', 수집기까지 조용하면 앱이 죽었는지 파이프라인이 끊겼는지 알 수 없어 '확인 불가'다. 확인 불가일 때는 앱을 재기동하지 말고 Collector·네트워크·토큰(401)·라이선스(403)를 먼저 본다.

Q. 앱에 에이전트를 붙였는데 서비스가 안 보인다. 순서대로 본다. (a) 수집기 > 상태 탭의 '최근 60초 수신 확인' — 수신이 없으면 Collector가 서버에 못 보내는 것이다(주소·토큰·방화벽). Collector는 401/403을 영구 실패로 보고 즉시 폐기하므로 토큰 오타·라이선스 만료는 조용히 데이터를 잃는다. (b) 등록·설정 탭의 등록 방식이 '승인'이면 서비스가 승인 대기에 쌓여 목록에 안 뜬다(기본은 자동). (c) 앱이 OTEL_SERVICE_NAME을 안 주면 unknown_service로 와서 등록이 거부된다. (d) '숨긴 서비스 포함'을 켜 본다(14일 미수신 시 자동 숨김). (e) 화면 전체가 잠겨 있으면 라이선스에 APM이 없는 것이다. (f) Collector 자기 지표(otelcol-contrib)는 서비스로 등록되지 않는다 — 정상이다. 자세한 절차는 수집기 설치 — 문제 해결.

Q. 요청수가 0 rps인데 죽은 것인가? 요청수 차트의 0은 "그 구간에 요청이 없었다"는 측정값이다. 정말 수신이 끊겼는지는 헤더 상태(수신 끊김/확인 불가)와 24시간 가용성 띠의 색으로 가른다.

Q. p95가 튀는데 '표본 부족' 배지가 있다. 관측이 20건 미만인 구간이 있다는 뜻이다. 백분위는 히스토그램 버킷 안을 보간해 구하므로 관측이 적으면 오차가 크다. 기간을 넓혀 step을 키우거나, 트래픽이 적은 서비스면 p50을 함께 본다. 배지 없이 p95만 튀면 실제 꼬리 지연이다.

Q. 인스턴스 탭 지표가 전부 —다. 선택한 시간 범위가 7일을 넘었을 때 그렇다. 인스턴스 축은 1분 데이터에만 있고 1분 데이터는 7일 보존이다. 상단 배너가 안내한다. 기간을 7일 이내로 좁힌다.

Q. 알람이 '열림'인데 Slack/메일이 안 온다. MovesEye는 판정과 Zabbix 트리거 발화까지 책임지고 배달은 Zabbix 액션이 한다. 알람 규칙 > Zabbix 상태 탭에서 '알림 액션 없음' 배너를 확인하고 위 절차대로 액션 조건을 추가한다. '연결 불가'면 Zabbix API 자체가 안 되는 것, 동기화 배지가 '생성 실패'면 울릴 아이템이 없는 것이다.

Q. 런타임 탭이 비어 있다(.NET / Node / Python 서비스). 1단계는 JVM 런타임 지표만 저장한다. 다른 런타임의 GC·스레드풀 지표는 수신 허용목록에 아직 없어 '계측 미제공' 배지가 보인다. HTTP·DB 지표는 정상이다.

정직한 한계

  • Kubernetes 통합 모니터링 없음(로드맵), RUM(브라우저 실사용자) 없음(4단계 후보), 코드 레벨 프로파일링 없음, SaaS 없음.
  • 1단계는 메트릭만이다. 트레이스·서비스 맵·에러 분석은 2단계, 합성 감시·SLO는 3단계다.
  • 1차 목표 규모는 서비스 50 · 트레이스 일 2천만 이하. 그 이상은 저장소 승격이 필요하다.
  • 런타임 탭은 1단계에서 JVM만 실제 값이 그려진다.
  • 게이트웨이 Collector는 사이트당 1대만 지원한다(active-active 미지원 — 이유는 수집기 설치).
  • 라이선스가 만료되면 수신이 403이 되고 Collector가 데이터를 즉시 폐기한다. 나중에 갱신해도 그 사이 데이터는 돌아오지 않는다.
  • Collector 자체의 운영(업그레이드·모니터링 대행)은 하지 않는다. 설정 생성과 상태 가시화까지다.

지원 담당자를 위한 안내

  • "메뉴가 잠겨 있다" → 라이선스에 APM 기능이 없는 것. 설정 > 라이선스에서 프리미엄 모듈 포함 여부 확인.
  • "메뉴가 열리는데 서비스가 없다" → 수집기 설치 전이거나 수신이 안 되는 것. 위 FAQ 순서대로.
  • "서비스 맵·트레이스가 비어 있다" → 2단계 예정. 고장이 아니다.
  • "알람은 뜨는데 연락이 안 온다" → Zabbix 액션 연결(위 절차). MovesEye가 아니라 Zabbix 쪽 설정이다.
