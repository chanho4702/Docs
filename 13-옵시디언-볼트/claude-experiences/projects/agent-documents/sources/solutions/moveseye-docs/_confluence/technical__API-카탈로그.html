MovesEye API 카탈로그

정본은 코드와 OpenAPI다. 이 문서는 도메인 지도와 개별 엔드포인트 문서에 드러나지 않는 계약 규칙을 설명한다. 정확한 요청·응답 스키마는 dev 환경의 /v3/api-docs(Swagger UI /api)에서 확인한다. 운영에서는 Springdoc이 꺼져 있다.

기준: 2026-08-11 소스, 컨트롤러 32개.

1. 반드시 먼저 읽을 공통 계약

1-1. HTTP 200이 성공이 아니다

🔴 가장 중요한 규칙. 응답은 ApiResult 봉투로 감싸지며, 실패도 HTTP 200으로 내려올 수 있다. HTTP 상태 코드만 보고 성공 처리하면 조용히 잘못된 동작을 한다.

{
  "status": "SUCCESS | ERROR",
  "code": 200,
  "errorCode": "…",
  "message": "…",
  "data": { }
}

성공 판정은 status 필드로 한다. 오류 분류는 errorCode로 한다. null 필드는 응답에서 생략된다(NON_NULL).

이 설계는 NestJS 시절의 계약을 Spring으로 옮기면서 의도적으로 보존한 것이다. 클라이언트를 깨뜨리지 않기 위한 선택이며, 임의로 바꾸지 않는다.

1-2. syncTime

일부 응답은 봉투에 syncTime을 실어 데이터의 신선도를 알린다. 화면은 이 값으로 "언제 기준 데이터인지"를 표시한다. 값이 오래됐다면 수집·동기화 쪽을 의심한다.

1-3. 이중 언랩 주의 (FE)

FE는 axios 인터셉터와 useDmoveQuery가 봉투를 두 겹 벗긴다. 훅 소비자는 data.data가 아니라 payload를 직접 받는다. 테스트 목도 payload를 직접 주입해야 한다. 여기서 한 겹 더 벗기면 undefined가 된다.

1-4. 인증

요소방식
액세스 토큰Authorization: Bearer &lt;token&gt;
리프레시HttpOnly 쿠키
세션 검증x-visitor-id 헤더 ↔ Redis 세션 대조

x-visitor-id는 선택 헤더처럼 선언돼 있지만 실질적으로 필요하다. 인터셉터가 이 값과 Redis 세션을 대조한다. 직접 API를 호출해 테스트할 때 이 헤더를 빠뜨리면 인증이 통과하지 않는 경우가 있다.

리프레시가 쿠키 기반이므로 크로스 도메인 배포에서는 COOKIE_SECURE·COOKIE_SAME_SITE가 맞아야 로그인 상태가 유지된다.

1-5. 권한 검증

기능 권한과 호스트 그룹 데이터 범위를 서버에서 다시 검증한다. FE의 메뉴 숨김은 편의일 뿐 보안 경계가 아니다. 권한 없는 호스트 그룹은 목록뿐 아니라 집계 수치에서도 제외되어야 한다.

1-6. 라이선스 게이트

라이선스 판정은 인증 뒤에 놓인다. 앞에 두면 401 리프레시 흐름이 라이선스 잠금 화면으로 잘못 표시된다. 만료 시 읽기는 유지하고 쓰기를 차단하는 단계적 정책을 따른다(관리자 가이드 §7).

3-3. 메트릭 조회

CPU·메모리·디스크·네트워크·인터페이스·응답시간이 각각 컨트롤러로 나뉜다. 공통 규칙:

  • 관측값 없음과 0을 구분한다. 아이템이 없거나 수집이 안 되는 것과 실제 값 0은 다르다. 임의 폴백으로 메우지 않는다.
  • 트래픽은 bps다. net.if.in/out은 Zabbix가 bps 원값으로 준다. 바이트 포매터를 쓰면 약 940만 배 부풀려진다. 비트레이트 포매터(SI 1000 단위)를 쓴다.
  • 디스크는 아이템 계열이 둘이다(vfs.fs.size / vfs.fs.dependent). 호스트에 따라 한쪽만 존재해 "차트엔 있는데 상세는 빈" 현상이 생겨서, 상세 조회에 계열 폴백이 들어 있다.

🔴 폴백 체인은 응답 값을 바꿀 수 있다. 과거 메모리 사용률에서 폴백 때문에 값이 달라진 사례가 있었다(0 → 11). 폴백 없는 전용 키를 쓰는 것이 원칙이고, 폴백을 추가할 때는 값 변화를 실측한다.

3-7. Zabbix 관리 계열

쓰기 계약의 원칙 두 가지:

  1. 대상은 식별자로만 지정한다. 필터 조건으로 대량 대상을 지정하는 쓰기는 허용하지 않는다 — 필터가 의도보다 넓게 걸리면 되돌릴 수 없다.
  2. 배열 필드는 전체 교체다. tags, template link 등은 보낸 값으로 통째 대체된다. 부분 수정하려면 현재 값을 읽어 포함시킨다.

오류 매핑에 주의할 점이 있다. Zabbix의 -32602(파라미터 오류)는 create/update에서만 400으로 매핑한다. 과거 이를 401로 처리해 "인증 오류"로 오인시킨 회귀가 있었다.

부분 수정에서 clearable 필드는 빈 문자열이 "값 지우기" 를 뜻한다. 필드 미포함(변경 없음)과 빈 문자열(클리어)을 구분해 보낸다.

트리거 생성은 hostid를 넘기지 않는다 — expression의 /host/key가 대상을 결정한다.

3-8. 렌즈 조회의 페이지네이션

Zabbix API에는 offset이 없다. 그래서 렌즈 조회는 ID만 먼저 조회 → 슬라이스 → 해당 페이지만 상세 하이드레이트 방식으로 임의 페이지 이동을 구현했다. 페이지당 0.4~1.3초가 든다. LENS_CAP으로 상한을 조정할 수 있다.

3-9. 스케줄러 /settings/schedulers

job 목록·활성 토글·주기 변경·수동 실행·실행 로그 조회를 제공한다. jobKey는 코드의 잡 레지스트리와 1:1이며 DB scheduler_setting.job_key와 일치해야 한다. job 목록과 각 job의 성격은 관리자 가이드 §5에 있다.

4. 수집 엔진 포트 경계

제품은 다중 데이터소스(Zabbix·Prometheus·Datadog·Elasticsearch) 를 지향하며, 모니터링 읽기는 특정 소스를 직접 호출하지 않고 capability port를 거친다. 2026-08-11 현재 구현된 어댑터는 Zabbix 하나다.

app ──(compile)──▶ engine-api ◀──(구현, runtimeOnly)── engine-zabbix
                   중립 계약 + 소스 전용 계약              (향후: prometheus, datadog, …)

app은 어댑터 모듈에 컴파일 의존할 수 없다(빌드가 강제). 새 데이터소스를 붙일 때 앱 코드를 고치지 않기 위한 구조다.

중립 계약과 전용 계약을 가르는 기준은 "값이 답하는 질문이 무엇인가" 다. 어느 데이터소스에서도 같은 질문에 답하는 값이면 중립, 특정 소스 개념에만 존재하는 값이면 전용이다.

4-1. 포트

포트담당
MetricPort시계열·최신값·트렌드
InventoryPort호스트·그룹·인터페이스

4-3. 쓰기 계약 원칙

포트를 통한 쓰기(예: 알람 인지)는 명령은 서술적으로, 대상은 명시적 식별자로 표현한다. 필터 조건으로 대량 대상을 지정하는 쓰기는 허용하지 않는다 — 필터가 의도보다 넓게 걸리면 되돌릴 수 없다.

4-4. 어댑터를 추가할 때

새 소스를 붙이는 작업은 다음으로 한정된다. 서비스·컨트롤러·FE는 원칙적으로 손대지 않는다.

  1. 어댑터 모듈 신설, engine-api 포트 구현
  2. 소스 고유 식별자·메트릭 키를 중립 모델로 번역하는 카탈로그 작성
  3. 레지스트리에 소스와 capability 등록
  4. 기존 화면이 그대로 동작하는지 런타임 동등성 확인

폴백 체인을 임의로 넣지 않는다. 값이 없을 때 다른 키로 대체하면 응답 값 자체가 바뀔 수 있다(§3-3 참조).

5. 클라이언트 구현 시 체크리스트

  • ☐ status 필드로 성공을 판정하는가 (HTTP 200 아님)
  • ☐ errorCode로 오류를 분류하는가
  • ☐ Authorization + x-visitor-id를 보내는가
  • ☐ 리프레시 쿠키가 전송되도록 credentials 설정이 됐는가
  • ☐ 빈 값과 0을 구분해 표시하는가
