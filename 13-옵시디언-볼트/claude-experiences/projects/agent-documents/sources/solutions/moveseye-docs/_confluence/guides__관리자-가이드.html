MovesEye 관리자 가이드

이 문서는 제품을 설정하고 운영하는 관리자를 위한 것이다. 일반 사용자의 화면 사용법은 사용자 가이드를, 서버 설치·기동은 설치·배포 가이드를 본다.

상태 표기 규칙: [구현] 은 2026-08-11 소스에 존재하는 기능, [진행] 은 일부만 반영된 기능, [계획] 은 설계만 확정되고 코드가 없는 기능이다. 배포 환경에서의 동작은 별도로 확인해야 한다.

1. 관리자가 책임지는 범위

MovesEye는 여러 모니터링 데이터소스(현재 Zabbix, 향후 Prometheus·Datadog·Elasticsearch)를 통합하는 제품이며, 수집된 데이터를 그대로 보여 주는 뷰어가 아니다. 제품이 자체적으로 소유하는 것이 있고, 데이터소스가 원천인 것이 있다. 이 경계를 모르면 "고쳤는데 원복되는" 현상을 겪는다.

데이터원천관리자가 바꾸는 곳
호스트·아이템·트리거·템플릿데이터소스(Zabbix)소스 관리 메뉴(제품에서 원천에 씀)
메트릭 값·이벤트 발생데이터소스바꿀 수 없음(수집 결과)
자산 보강 필드·비용·감가상각MovesEye DB자산 관리 메뉴
네트워크 맵·지리 맵 클러스터MovesEye DB자산 관리 > 지도
호스트 좌표Zabbix 인벤토리지리 맵에서 편집하면 Zabbix에 기록됨
사용자·역할·기능 권한MovesEye DB사용자·권한 메뉴
기기 분류(device_type)호스트 태그가 진실, 분류 메타는 DB설정 > 장비 분류
배치 주기MovesEye DB설정 > 스케줄러

원칙 하나만 기억하면 된다. 데이터소스가 원천인 값은 다음 동기화가 덮어쓴다. 제품에서 영구히 유지하고 싶은 값은 MovesEye 소유 필드에 넣어야 한다.

1-1. 데이터소스 구성 [진행]

설정 > 데이터소스에서 연결된 소스와 상태를 확인하고, 소스별 관리 워크스페이스로 진입한다.

소스관리 워크스페이스상태
Zabbix호스트 · 템플릿 · 아이템 · 트리거[구현]
Prometheus타깃 · 서비스 디스커버리 · 규칙 · 레이블[계획]
Elasticsearch인덱스 · 파이프라인 · 스트림 · 질의[계획]
Datadog통합 · 모니터 · 호스트 · 태그[계획]

화면에 4개 소스가 보이는 것과 실제 연결 가능한 것은 다르다. 현재 동작하는 어댑터는 Zabbix뿐이며 나머지는 화면 골격만 있다. 고객에게 안내할 때 이 점을 분명히 한다.

소스마다 할 수 있는 일이 다르므로, 제품은 각 소스가 선언한 능력(capability) 에 따라 메뉴를 조정한다. 예를 들어 메트릭만 제공하는 소스를 붙이면 대상 관리 메뉴는 나타나지 않는다. 특정 메뉴가 보이지 않는다면 고장이 아니라 연결된 소스가 그 능력을 갖고 있지 않은 것일 수 있다.

2. 최초 도입 순서

새로 설치한 뒤 이 순서대로 진행한다. 앞 단계를 건너뛰면 뒤 단계에서 대상이 비어 보인다.

2-1. 라이선스 등록 [진행]

설정 > 라이선스에서 발급받은 키를 등록한다. 라이선스가 없으면 기능이 제한된다(§7 참조).

2-2. 데이터소스 연결 확인

설정 > 연동 정보에서 데이터소스 접속 정보와 전용 계정을 확인한다(현재 Zabbix API URL·계정). 계정은 제품 전용으로 분리한다 — 사람이 같이 쓰는 계정을 넣으면 비밀번호가 바뀔 때 제품 전체가 멈추고, 감사 로그에서 누가 한 일인지 구분되지 않는다.

연결 확인 방법은 화면 어디든 호스트 목록이 뜨는지 보는 것이다. 전 화면이 동시에 비면 연동 실패, 특정 호스트만 비면 권한이나 아이템 문제다.

2-3. 자산 최초 동기화

자산 관리 > 목록에서 동기화를 실행한다. Zabbix 호스트가 자산으로 올라온다.

⚠️ 지리 맵을 쓸 계획이면 이 동기화를 반드시 먼저 한 번 돌린다. 동기화 전에는 linked_hostid가 비어 있어 지리 맵의 호스트 후보가 0건으로 나온다. 기능 고장으로 오인하기 쉽다.

2-4. 장비 분류 정의

설정 > 장비 분류에서 조직이 쓰는 분류 체계를 만든다(서버/네트워크/스토리지 등). 분류는 호스트 태그로 호스트에 붙고, 이 테이블은 표시명·순서·메타만 갖는다. 그래서 분류를 지워도 호스트 데이터는 파괴되지 않는다 — 모르는 분류 코드는 "미분류"로 폴백한다.

2-5. 사용자와 권한

§3을 따라 역할을 먼저 만들고, 사용자를 만들면서 역할을 붙인다. 반대로 하면 사용자마다 권한을 개별 조정하게 되어 관리가 무너진다.

2-6. 스케줄러 활성화

설정 > 스케줄러에서 필요한 배치를 켜고 주기를 정한다(§5).

2-7. 리포트 보존 정책

설정 > 리포트 관리에서 자동 삭제 보존 기간을 정한다. 정하지 않으면 리포트가 무한 누적된다.

3. 사용자·역할·권한 관리

3-1. 두 층위의 권한

MovesEye의 권한은 두 축이 곱해진다. 하나만 설정하고 다른 쪽을 잊는 것이 가장 흔한 실수다.

축무엇을 통제하나설정 위치
기능 권한어떤 메뉴·기능을 쓸 수 있나역할(Role)
데이터 범위어떤 호스트 그룹의 데이터를 볼 수 있나사용자 그룹 ↔ 호스트 그룹 권한

기능 권한만 주고 데이터 범위를 안 주면 메뉴는 보이는데 목록이 텅 빈다. 사용자는 "고장났다"고 신고한다. 반대로 데이터 범위만 주고 기능 권한을 안 주면 메뉴 자체가 안 보인다.

3-2. 기능 권한 키

역할 편집 화면에서 다루는 권한 키다. 각 키에 조회(view)·편집(edit)·삭제(delete)·다운로드(download) 단위를 준다.

3-3. 역할 설계 권고안

처음부터 세밀하게 쪼개지 말고 3~4개로 시작한다. 실제 불편이 생긴 지점만 나중에 분리하는 편이 유지 가능하다.

3-4. 계정 비활성화와 삭제

퇴사·전배는 삭제가 아니라 비활성화가 기본이다. 삭제하면 그 사용자가 남긴 감사 로그·자산 변경 이력의 행위자 추적이 끊긴다. 비활성화는 로그인만 막고 이력을 보존한다.

3-5. Zabbix 사용자 동기화 [구현·기본 비활성]

user_sync 배치는 Zabbix 사용자와 MovesEye 사용자를 맞춘다.

🔴 SYNC_ENABLED 기본값이 false인 데는 이유가 있다. 이 동기화는 Zabbix에 없는 로컬 사용자를 제거할 수 있는 파괴적 작업이다. MovesEye에서만 만든 계정을 쓰고 있다면 켜는 순간 사라진다. 켜기 전에 반드시 사용자 테이블을 백업하고, 로컬 전용 계정이 있는지 확인한다.

4. 대상 관리 (Zabbix)

제품에서 데이터소스의 객체를 직접 CRUD할 수 있다. 여기서 한 변경은 원천 시스템에 그대로 반영된다 — 연습용이 아니다.

이 영역은 소스마다 개념이 달라 공통화되지 않는다. 아래는 ZABBIX_ADMIN 능력을 가진 소스, 즉 Zabbix가 연결됐을 때 나타나는 메뉴다. 다른 소스가 붙으면 그 소스에 맞는 관리 화면이 따로 제공된다.

메뉴할 수 있는 일
호스트 관리호스트 등록·수정, 그룹·인터페이스·템플릿 연결, 분류/태그 지정, 일괄 지정
템플릿 관리템플릿과 템플릿 그룹, 링크 관리
아이템 렌즈·관리아이템 조회·생성·수정·상태 전환, 정의처와 전파 범위 확인
트리거 렌즈·관리트리거 정의·심각도·상태 관리
사용자 관리Zabbix 사용자와 MovesEye 사용자 연결

4-1. 배열 전체 교체 함정

🔴 Zabbix API의 update는 부분 수정이 아니다. 태그와 템플릿 링크는 보낸 배열로 통째 교체된다. 태그 하나를 추가하려고 그 하나만 보내면 나머지 태그가 전부 지워진다.

제품 화면은 현재 값을 읽어 폼에 채운 뒤 전체를 다시 보내는 방식(round-trip)으로 이를 막고 있다. 그러므로 화면에서 폼을 열었다면 보이는 값을 임의로 비우지 말 것. 특히 다건 일괄 변경 전에는 대상 호스트의 현재 태그를 먼저 확인한다.

4-2. 렌즈(Lens) 화면의 용도

아이템·트리거 렌즈는 "이 정의가 어디서 와서 어디까지 퍼졌는지"를 보는 화면이다. 템플릿에서 상속된 것인지 호스트에 직접 만든 것인지, 몇 개 호스트에 전파됐는지를 확인한 뒤 수정한다. 템플릿 쪽을 고치면 연결된 호스트 전체가 함께 바뀐다.

기본 뷰는 디스커버리로 자동 생성된 항목을 숨긴다(노이즈 제거). 자동 생성분을 봐야 하면 뷰를 전환한다.

4-3. 트리거 수정 시 주의

트리거는 대상 호스트를 별도로 지정하지 않는다 — expression 안의 /host/key가 곧 대상이다. expression을 고치면 트리거가 다른 호스트를 보게 될 수 있다. 심각도 변경은 알람 흐름 전체에 영향을 주므로 운영 시간대를 피한다.

5. 스케줄러 관리 [구현]

설정 > 스케줄러에서 배치의 활성 여부·주기를 바꾸고, 수동 실행과 실행 이력을 볼 수 있다. cron이 코드에 박혀 있지 않고 DB 설정을 따르므로 재기동 없이 주기를 조정할 수 있다.

job_key하는 일성격라이선스 필요
asset_syncZabbix 호스트 → 자산 동기화수집예
event_sync이벤트·문제 동기화수집(짧은 주기)예
event_cleanup오래된 이벤트 정리정리아니오
report_weekly주간 리포트 생성집계예
report_monthly월간 리포트 생성집계예
report_cleanup보존 기간 지난 리포트 삭제정리아니오
user_syncZabbix 사용자 동기화수집예

5-1. 주기 설계

  • event_sync는 짧게(1분 수준) 돌아야 장애를 빨리 잡는다. 대신 무겁다.
  • 리포트 집계는 오래 걸린다. 이벤트 동기화와 겹치는 시간대를 피한다.
  • 배치 스레드 풀은 SCHEDULER_POOL_SIZE(기본 4)다. 등록 배치가 7개이므로 전부 동시에 겹치면 대기가 생긴다. 풀이 1이면 무거운 집계 뒤에 이벤트 동기화가 줄줄이 밀린다.

5-2. 정리 배치는 왜 라이선스와 무관한가

event_cleanup·report_cleanup은 라이선스가 만료돼도 계속 돈다. 멈추면 만료된 설치본의 디스크가 무한정 찬다. 이 두 배치는 외부 수집을 하지 않고 자기 DB만 정리하므로 계속 도는 것이 안전하다.

5-3. 실행 이력 읽는 법

  • 부분 실패는 예외가 아니라 요약으로 남는다: ok=38 fail=2. 성공으로 찍혔다고 전건 성공이 아니다 — 요약 문자열을 읽는다.
  • 전건 실패는 실패로 기록되고, 다음 실행은 취소되지 않는다. 원인을 고치면 다음 주기에 자연 복구된다.
  • 실행이 밀리거나 멈춘 것 같으면 수동 실행을 연타하지 않는다. 이전 실행이 아직 도는 중일 수 있다.

6. 자산·비용 관리

6-1. 자산의 두 출처

  • source=zabbix — Zabbix 호스트에서 유래. Zabbix 원천 필드는 동기화가 덮어쓴다.
  • source=custom — MovesEye에서 직접 만든 자산. Zabbix에 없는 것(비품·회선 등)을 관리할 때 쓴다. linked_hostid로 Zabbix 호스트를 참조할 수 있다.

삭제는 물리 삭제가 아니라 excluded soft delete다. 동기화 대상에서 숨겨질 뿐 이력은 남는다.

6-2. 비용·감가상각 [진행]

취득가액·취득일을 입력하면 감가상각(정액법·정률법)을 계산한다. 한국 세무 기준(월할, 잔존가액 0)을 따른다. 기기 유형별 기본 내용연수를 두고 자산별로 예외를 줄 수 있다.

  • 파라미터를 바꾸면 현재 파라미터 기준으로 소급 재계산된다. 과거 시점 스냅샷을 보존하지 않는다.
  • CSV 일괄 업로드는 비동기다. 업로드 성공 응답은 "접수됨"이지 "처리 완료"가 아니다. 작업 상태를 따로 확인한다. 파일 상한은 10MB.
  • 미입력 자산 큐를 활용해 빈 항목을 채운다.

7. 라이선스와 에디션 [진행]

7-1. 에디션 구성

에디션포함 기능
STANDARD기본 모니터링·자산·맵·리포트
PREMIUMSTANDARD + GPU 모니터링, DB 모니터링, APM

기능 판정은 에디션 기본값 ∪ 개별 부여 기능이다. STANDARD에 특정 기능만 추가 부여할 수 있다.

7-2. 등록과 갱신

설정 > 라이선스에서 키 문자열을 붙여넣거나 파일로 등록한다. 유효 기간은 등록일부터 계산된다(발급일이 아니다) — 발급받고 며칠 뒤 등록해도 손해가 없다. 영구 라이선스도 지원한다.

7-3. 만료되면 무엇이 멈추나

만료를 무 자르듯 차단하지 않는다. 모니터링 화면 전부가 죽으면 운영자가 장애 상황을 볼 수단을 잃기 때문에, 단계적으로 좁힌다.

단계기간상태
정상유효 기간 내전 기능
EXPIRED만료 후 약 30일읽기 전용. 실시간 조회는 유지, 쓰기 차단
ARCHIVED그 이후DB에 쌓인 데이터만 조회. 외부 수집 중단

정리 배치는 어느 단계에서도 계속 돈다(§5-2).

관리자 조치: 만료 30일 전부터 갱신을 준비한다. EXPIRED 구간에 들어가면 설정 변경·자산 편집 같은 쓰기가 막히므로, 갱신 전에 진행 중인 편집 작업을 마무리한다.

8. 일상 운영 점검

매일

  • ☐ 활성 문제(Problem) 목록에 미인지 항목이 쌓이지 않았는지
  • ☐ 스케줄러 실행 이력에 연속 실패가 없는지
  • ☐ event_sync 최종 실행 시각이 주기 내인지

매주

  • ☐ 자산 동기화 결과(추가/변경 건수)가 예상 범위인지
  • ☐ 신규 호스트에 분류·태그가 붙었는지
  • ☐ 주간 리포트가 생성됐는지

매월

  • ☐ 비활성 계정과 퇴사자 계정 정리
  • ☐ 역할별 권한이 실제 업무와 맞는지
  • ☐ 라이선스 잔여 기간
  • ☐ 리포트·이벤트 보존 정책대로 정리되고 있는지(디스크 사용량)
  • ☐ 감사 로그 확인

9. 관리자가 자주 오해하는 것

증상실제 원인
메뉴는 보이는데 목록이 비었다기능 권한은 있고 호스트 그룹 데이터 범위가 없다(§3-1)
지리 맵에 호스트 후보가 0건자산 최초 동기화 미실행(§2-3)
태그를 하나 추가했더니 나머지가 사라졌다Zabbix update의 배열 전체 교체(§4-1)
자산을 고쳤는데 원복됐다데이터소스 원천 필드를 고쳤고 동기화가 덮어썼다(§1)
특정 관리 메뉴가 안 보인다연결된 소스가 그 능력(capability)을 갖고 있지 않다(§1-1)
데이터소스 화면에 4개가 보이는데 연결이 안 된다현재 동작하는 어댑터는 Zabbix뿐이다(§1-1)
로컬 계정이 사라졌다SYNC_ENABLED=true 상태에서 user_sync 실행(§3-5)
차트가 비었다 = 장애다관측값 없음과 실제 0은 다르다. 아이템 키와 수집 상태를 먼저 본다
CSV 업로드 성공했는데 반영이 안 됐다비동기 처리. 접수 ≠ 완료(§6-2)
배치가 성공인데 데이터가 일부만부분 실패는 성공으로 찍히고 요약에만 남는다(§5-3)
