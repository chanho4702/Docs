# APM 전반 완성도 평가와 개선 우선순위

> 이 평가는 BE `e55948c` 기준의 감사 기록입니다. 감사 이후 순차 구현 상태와 실제 검증 결과는 [우선순위별 보완 이력](solutions--apm-priority-fixes.md)에서 확인합니다.

**핵심 기능의 범위는 넓지만, 측정 정확성과 조건부 원문 노출 결함 때문에 운영 확대 전에 보완이 필요한 상태입니다.** 현재 제품은 수집·시각화·분석·운영 기능을 연결해 놓았으나, 입력 순서·설정 전환·지연 도착·노드 분산에서도 결과가 일관된지를 충분히 보장하지 못합니다. “기능이 있다”와 “장애 때 믿고 판단할 수 있다”를 별도 축으로 평가했습니다.

이전 [구현 보완 보고서](solutions--apm-scale-readiness.md)의 메트릭 저장 원자성·SSE 작업 큐·조회 격자 상한·RUM 재시도 개선은 유효합니다. 기준 감사는 그 다음 단계의 의미·경계 조건을 확인했으며, 기존 시험 통과를 취소하는 것은 아닙니다. 다만 새로 발견한 결함을 반영해 앞선 파일럿 후보 평가보다 보수적으로 판정했습니다. 당시에는 제품 코드를 수정하거나 서버를 재기동하지 않았습니다.

## 2026-10-06 후속 구현 상태

이 문서의 표와 23개 항목은 최초 감사 시점의 기준 평가입니다. 이후 우선순위 1~8의 여러 변경이 구현됐고, 자세한 변경·시험 근거는 [우선순위별 보완 이력](solutions--apm-priority-fixes.md)에 갱신했습니다. 현재 누적계열 오차와 과거 원문 열람 결함은 코드 변경 및 선별 회귀로 보완됐으며, 늦은 메트릭 rollup·trace 재분류·RUM 시간창·archive integrity도 구현 범위가 확장됐습니다.

이 진척은 전체 APM 완성 또는 규모 보증으로 해석하면 안 됩니다. 특히 dirty/blocked/legacy rollup 구간이 SLO·burn·availability·export의 완전성 판단에 아직 연결되지 않아 잘못된 `OK`/`DATA`가 남을 수 있습니다. 서버 trace timestamp 제한도 빠져 있고, 9~10 환경·상세 범위·수동 갱신, 알람 전달 원자성, 목표 부하·HA·복구 검증은 완료되지 않았습니다. 따라서 현재 판정은 **핵심 기능 범위는 넓고 주요 정확성 개선이 진행됐지만, 대규모 운영·HA 준비 완료를 주장할 증거는 부족하다**입니다. 현재 실행한 선별 BE 188개와 FE archive Jest 84개는 관련 범위의 회귀일 뿐 전체 지원 환경 검증이 아닙니다.

## 1. 종합 평가

평가는 정량 완료율이 아닌 코드·검증 근거에 따른 판단입니다. 서비스 수나 화면 수, 테스트 수를 점수로 환산하지 않았습니다.

| 영역 | 평가 | 판단 근거 |
|---|---|---|
| 핵심 기능 범위 | 높은 편 | OTLP, RED·런타임·endpoint, trace/waterfall/flame, 오류·DB·의존·서비스 맵, 실시간 완료/진행 중 요청, SLO·합성·알람·리포트·export·archive 구현 |
| 측정값 정확성 | 우선 보완 필요 | CUMULATIVE 계열 충돌·역순 도착·경계 변경을 실제 클래스로 재현. 지연 원본과 파생 집계의 일치에도 공백 |
| 보안·데이터 보호 | 기본 방어는 있으나 전환 결함 존재 | view/edit·원문 관리자 권한, 토큰 hash·회수·수신 제한은 있음. 원문 저장 ON→OFF 뒤 과거 데이터의 열람 판단에 결함 |
| 수집 회복력 | 부분적으로 견고함 | receipt·트랜잭션·429/503·Collector 큐·rollback 보완. 누적값의 재시작/분산 상태와 지연 재정산은 미완료 |
| 실시간 관제 | 구현과 방어가 비교적 충실함 | 링·바이트 예산·SSE 재연결·대기/표본 안내·waterfall 가상화. 최대 설정의 실제 네트워크 성능은 미보증 |
| 조사 화면·UX | 기능은 많지만 조작 정합성 미흡 | 환경 필터와 실제 조회가 어긋나고 일부 수동 갱신·행 선택·조사 맥락 전달이 불완전 |
| 대규모 조회·저장 | 부분 대응 | 파티션·rollup·결과 상한은 있음. 서비스 전량 집계, 총계열 예산, SQL/JSON 전체 비용, 저장 증가량 검증 부족 |
| 다중 BE·HA | 미완료 | 누적 기준·live·예산이 노드 로컬. 공통 batch lease의 장기 실행 소유권도 보완 필요 |
| 운영 수명주기 | 중간 단계 | archive 원장·checksum·hold, export 제한은 장점. 알람 생성/전송/보존, 손상 archive의 삭제 차단, 복구 훈련 공백 |
| 검증 체계 | 개별 기능보다 교차 시나리오가 약함 | 기존 선별 회귀는 있지만 설정/시간/분류 전환, 다중 노드, 실제 언어별 설치와 복합 부하 증거 부족 |

**사용 판단:** 정확성·원문 열람의 상위 결함을 먼저 닫고 지원 입력과 배포 형태를 한정한 통제된 파일럿을 진행하는 편이 타당합니다. 지금 상태를 고객 규모와 무관하게 상용 운영 가능 또는 HA 지원 완료로 안내할 근거는 없습니다. 특히 CUMULATIVE를 사용하는 환경은 영향 확인이 먼저입니다.

## 2. 새로 확인한 핵심 증거

아래 숫자는 합성 입력으로 현재 production 클래스를 직접 실행한 결과입니다. 실제 고객 DB의 오염·정보 노출을 확인한 결과가 아닙니다.

| 재현 | 기대 | 실제 | 검증 경계 |
|---|---|---|---|
| 같은 route의 200계열 100→110, 201계열 20→22 | 다음 증분 합 12 | 112 | 실제 normalizer가 두 계열을 `2xx`로 합친 키와 tracker 직접 호출 |
| 같은 startTime의 100(t0),120(t2),110(t1),130(t3) 도착 | 전체 증가 30 | 150 | 과거값을 reset으로 처리. 정상 프로세스 재시작이 아님 |
| histogram bounds `[1]`→`[0.1]`, count 10→11 | 증분 count와 버킷 합 일치 | count=1, 버킷 합=10 | 배열 길이는 같고 경계 값이 달라지는 경우 |
| A/B 독립 tracker가 100,110,120,130,140,150을 교차 수신 | 입력 전체 증가 50 | 산출 증분 합 80 | 실제 서버 2대가 아닌 독립 tracker 2개. 상태 비공유의 계산 영향을 재현 |
| 원문 저장 ON→OFF 뒤 일반 USER가 합성 SQL 조회 | 저장 정책을 꺼도 원문 권한은 넓어지지 않음 | ON에서는 `?`, OFF에서는 합성 원문 반환 | 설정 제공자는 대역, 실제 policy/view 호출. DB/HTTP 미실행 |

앞의 세 계산 재현과 네 번째의 노드별 누적 기준 문제는 **CUMULATIVE 입력에 해당**합니다. DELTA와 차분하지 않는 GAUGE·UpDownCounter에 동일하게 적용되는 문제라고 주장하지 않습니다. 일부 설치 가이드는 DELTA를 권장하지만, 서버는 CUMULATIVE도 수용하며 실제 설치별 비중은 미확인입니다.

원문 문제는 **원문 보관을 켠 동안 저장한 행이 남아 있고, 이후 설정을 끈 환경**에서 발생할 수 있습니다. 처음부터 원문을 보관하지 않은 모든 설치본의 정보가 노출된다는 뜻이 아닙니다. 현재 마스킹도 주로 SQL 리터럴 기반이므로 모든 자유 텍스트 개인정보를 제거한다고 보증할 수 없습니다.

## 3. 개선 우선순위

아래는 **노출·수치 왜곡 → 데이터 복구와 운영 판단 → 규모·운영 효율 → 기능 확장** 순서입니다. 동일 등급 안의 세부 순서는 고객의 실제 사용 조건에 따라 바뀔 수 있습니다. P1은 해당 조건에서 운영 확대 전에 해결할 항목, P2는 다음 안정화 단계, P3는 요구 기반 확장입니다. 다중 BE를 바로 지원해야 한다면 15번은 상위 정확성 과제와 같은 P1로 올립니다.

| 순위 | 중요도·근거 | 개선점 | 이유와 완료 기준 |
|---|---|---|---|
| **1** | **P1 · 정책 재현** | **과거 원문 열람 권한 고정** | 현재 저장 설정과 열람 권한을 분리. ON→저장→OFF 뒤 비관리자 trace/error 응답이 마스킹되는 HTTP·DB 회귀 통과 |
| **2** | **P1 · 계산 재현** | **원시 시계열별 차분 후 차원 축약** | 서로 다른 누적계열을 같은 직전값으로 계산하지 않게 함. 200/201·client method·DB 속성·route overflow의 DELTA/CUMULATIVE 결과 일치 |
| **3** | **P1 · 계산 재현** | **지연·역순 누적 포인트 처리** | 관측 시각/epoch를 저장하고 과거값이 기준을 되돌리지 못하게 함. 순서 역전·중복시각·실제 reset에서 총량과 시간 버킷 정책 검증 |
| **4** | **P1 · 계산 재현** | **히스토그램 경계·단위 변경 검증** | 배열 길이만으로 차분하지 않음. 격자 fingerprint와 count=버킷 합 불변식, explicit/exponential 변화 회귀 통과 |
| **5** | **P1 · 코드상 조건부** | **지연 데이터 재집계와 원본 보존 연계** | 이미 지난 watermark 구간의 늦은 데이터가 상위 rollup에서 빠질 수 있음. dirty bucket 재정산·하위→상위 전파·미집계 원본 보호 검증 |
| **6** | P1/P2 · 코드상 조건부 | **트레이스 재분류의 옛 집계 제거** | 외부 CLIENT가 뒤늦게 내부 SERVICE로 바뀌면 새 키 UPSERT만으로 옛 HTTP/dependency 행이 사라지지 않음. 2회 집계 후 옛 분류 잔존 없음 |
| **7** | P1/P2 · 파서 재현·경로 확인 | **관측 시각과 파티션 생성 제한** | 먼 과거·미래 timestamp가 불필요한 파티션 준비로 이어질 수 있음. 허용 지연/clock skew 밖에서는 DDL·적재하지 않고 사유 계수 |
| **8** | P1/P2 · 코드상 조건부 | **손상 아카이브와 원본 삭제 차단 연결** | 수동 checksum 실패가 원장 OK/hold를 바꾸지 않음. 손상→verify 실패→retention에서도 원본 유지, 별도 DB 복구 성공 |
| **9** | **P1 · FE↔BE 코드 확인** | **환경·선택 행·실제 조회 범위 일치** | trace/오류/DB/외부 호출의 env가 옵션에만 반영됨. 같은 외부 target의 행 선택도 service 범위를 보존. 카드·목록·차트·export 모집단 일치 |
| **10** | **P1 · 이벤트·시간창 코드 확인** | **수동 갱신의 실제 데이터·현재 시각 갱신** | 오류/DB/외부 호출은 옵션만 갱신, 일부 화면은 상대 시간창이 고정. 자동 OFF에서도 활성 데이터가 현재 창으로 갱신되는 브라우저 시험 |
| **11** | **P1 · 코드상 조건부** | **알람 상태 저장·전송 원자성** | 열린 이벤트 유일성과 판정/외부 I/O 분리. 동시 평가 1건 유지, provider 지연·전송 후 crash에서도 DB 상태와 전달의 재시도 일관성 |
| **12** | **P1 · 검증 공백** | **목표 규모·복합 부하·장시간 검증** | 실 OTLP+rollup+조회+SSE와 장애 복구를 함께 측정. 활성계열/분·span/초·동시관제·보존기간 기준 지원 사양과 지연/유실 기준 확정 |
| **13** | P1/P2 · 코드 확인 | **서비스 목록 서버 페이지화·경량 선택 API** | 옵션 선택에도 전량 RED·spark를 집계함. 선택 API는 지표 SQL 0건, 목록은 필요한 페이지 중심, 카드 가상화·실제 p95 검증 |
| **14** | P1/P2 · 코드 확인 | **등록·원시계열·저장 총량 예산** | route cap만으로 service/instance/속성 조합 폭주를 막지 못함. 원시 차분 키 보강과 함께 상태 상한·초과 사유·용량 경보 검증 |
| **15** | **HA 전제 P1 · 일부 계산 재현** | **다중 BE 상태 소유권·공유 예산·lease fencing** | 누적 기준/live/RUM 예산의 노드 로컬 상태와 장기 batch TTL 만료 대응. 교대 수신·rolling restart·노드 정지/재개에서 이전 소유자 쓰기 차단 |
| **16** | P2 · 코드 확인·실측 필요 | **일반 조회·export·synthetic 전체 비용 제한** | 시간축/반환 행 상한을 넘지 않아도 SQL·다계열·느린 전송이 비쌀 수 있음. deadline·취소·총점/bytes·동시성, 무거운 다운로드 비동기화 |
| **17** | P2 · 코드 확인 | **알람 이력·배치·용량 수명주기** | 이력 전량 조회와 보존 공백, SLO backfill 긴 tx 정리. DB 페이지·종료 이력 retention·작은 재개 배치, 규칙 삭제 후 사고 이력 정책 확정 |
| **18** | P2 · 코드 확인 | **관측 부족을 SLO 운영 판정에 반영** | 작은 coverage에서도 양호 판정 가능. UNKNOWN/STALE와 실제 회복 구분, 최소 관측률·freshness 및 수집 단절 알림 연계 시험 |
| **19** | P2 · 검증 공백 | **데이터 품질·APM 자체 상태 관측** | 서비스별 temporality·폐기·지연·중복 제거·rollup lag·노드/예산을 연결. 정상 0과 관측 불가를 구별하고 재시작을 넘는 수량 대조 가능 |
| **20** | P2 · 검증 공백 | **지원 환경 E2E·백업/복구·업그레이드 검증** | 언어별 설치 가이드 존재가 동등 지원을 증명하지 않음. 실제 runtime/브로커/K8s/RUM 조합과 장애 시나리오, 복구 시간·범위 검증 |
| **21** | P2/P3 · FE 코드 확인 | **조사 맥락·오류 복구 UX 통일** | 오류/DB→trace→다른 메뉴에서 기간·환경·복귀 경로 유지. query 취소·상대창 시계 통일, 상한 오류에 기간/간격 조정 안내 |
| **22** | P3 · 계약상 미지원 | **RUM 분석 범위와 시간별 Vitals 확장** | 사이트/토큰별 범위와 시간별 p75 추이. 현 sessions는 올바르게 ‘버킷 세션 합’으로 표시하므로 버그로 바꾸지 않음 |
| **23** | P3 · 요구 기반 | **깊은 진단·조직별 격리 확장** | 로그 상관 검색·연속 프로파일·DB 실행 계획, 필요 시 서비스/팀 권한을 별도 설계. 상위 정합성·복구 과제 이후 제품 목표에 맞춰 선택 |

P1/P2 병기 항목은 착수 시 다음 조건을 확인해 확정합니다. **6번:** 부분 trace·지연 span이 들어오는 서비스 맵/의존 분석을 운영 판단에 사용하면 P1. **7번:** 원격 수집기·시계 오류·backfill을 허용하면서 날짜별 자동 partition을 만드는 운영이면 P1. **8번:** archive 성공을 근거로 원본을 삭제하는 정책을 사용하면 P1. **13번:** 목표 서비스 수/동시 사용자에서 조회 지연 기준을 넘거나 첫 화면이 막히면 P1. **14번:** 동적 instance/route/속성으로 등록·계열이 빠르게 늘거나 2번의 원시 차분 키를 도입하면 관련 상태 예산부터 P1. 조건이 없으면 P2로 진행하되, 미측정 상태를 조건이 없다는 증거로 삼지 않습니다.

중복 작업을 피하기 위해 10번은 화면별 갱신 동작 수정, 16번은 query 취소·비용 예산 구현, 21번은 화면 간 맥락과 복구 안내의 UX 정리로 나눕니다. 12번은 목표 부하에서의 용량·장애 회복 성능, 20번은 지원 환경 조합과 백업/업그레이드 절차 검증입니다. 18번은 SLO의 운영 판정 정책, 19번은 그 판단을 뒷받침할 수집 파이프라인 관측입니다.

## 4. 상위 과제의 구현 경계

### 저장 성공과 측정 정확성은 별개다 — 2~5번

현재 receipt·트랜잭션은 동일 배치가 반만 저장되거나 재전송으로 다시 더해지는 경로를 보완합니다. 하지만 잘못된 차분값을 한 번만 저장해도 측정값은 틀립니다. 원시 계열 신원·관측 time·epoch·단위·histogram 경계와 저장용 축약 차원을 분리해야 합니다.

원시 키를 그대로 늘리기만 하면 tracker 메모리 문제가 생길 수 있으므로 14번 예산을 같이 설계해야 합니다. 늦은 누적 포인트를 버리는 정책도 전체 누적량, 실제 reset, 시간 버킷 분배, 히스토그램 변화에 따라 결과가 달라지므로 “버려도 무조건 무손실”로 단정하지 않습니다.

현재 메트릭 rollup은 LAG와 전체 빈 창 방어가 있으나, 일부 수집기만 늦은 과거 버킷은 watermark 뒤로 다시 계산하지 않습니다. trace에는 이미 10분 lookback이 있으므로 이를 미구현이라고 쓰면 안 됩니다. 지원 지연 창·dirty bucket·정산 완료·보존 삭제 조건을 함께 정의해야 합니다.

### 화면에 보이는 필터와 실제 모집단을 일치시킨다 — 9~10번

환경 필터가 서비스 선택 옵션만 좁히고 실제 데이터가 전 환경 합계라면 장애 조사 결론이 달라집니다. 트레이스는 수동 갱신이 이미 수정됐지만 env 전달은 남아 있어, 두 문제를 같은 해결 상태로 취급하면 안 됩니다.

오류·DB·외부 호출의 새로고침 버튼은 옵션 query만 갱신합니다. 개요·서비스 목록·맵은 실제 query를 갱신하지만 자동 갱신 OFF의 상대 시간창이 현재로 전진하지 않는 경로가 있습니다. 기존 `useApmRefresh`를 공통 적용하고 실제 API 호출과 시계 진행을 E2E로 검증하는 편이 맞습니다.

환경 누락은 이번에 tenant 권한 우회로 판정한 것이 아니라 **분석 범위 표시의 결함**입니다. 서비스/팀별 접근 격리는 별도 요구 기반 과제입니다.

### 알람과 아카이브는 실패 이후의 상태까지 닫는다 — 8·11·17번

알람은 **Zabbix에서 분리한 독자 알림 체계와 함께 개선한다는 기존 결정**을 유지합니다. 열린 이벤트 DB 유일성, 짧은 판정 트랜잭션, outbox와 전달 재시도, 종료 이력 보존을 하나의 수명주기로 다뤄야 합니다. 전송 I/O만 락 밖으로 옮겨 중복 실행 가능성을 키우지 않도록 합니다.

archive에는 checksum·원장·잠금·미보관 hold가 이미 있습니다. 남은 문제는 생성 후 손상 검사 실패를 다음 삭제 판단이 모른다는 것입니다. 모든 삭제 때 큰 파일을 무조건 다시 해시하는 방식보다는 검증된 파일 신원·무결성 상태와 hold, 복구 가능성 확인을 연계합니다.

### 설정 최대값을 지원 규모로 쓰지 않는다 — 12~16번

기본 SSE 40+10, 최대 설정 500+200과 합성 fan-out 시험은 운영망 700명 성능 보장이 아닙니다. 시간축 20,000/120,000칸 제한도 총계열·SQL 스캔·네트워크 상한은 아닙니다. 과거 1,404만 행 SQL 시험 역시 실제 수집 처리율과 다릅니다.

서버 목록·선택 API 분리와 cardinality 예산을 먼저 잡고 측정합니다. `dims jsonb`/hash 저장 방식 변경은 이득과 migration·쓰기 비용을 실측한 뒤 결정합니다. 서비스 수만으로 “수천 개 지원” 같은 결론을 내리지 않습니다.

## 5. Claude 독립 의견과 반영

사용자 요청에 따라 로컬 Claude Code를 **읽기 전용 도구만 허용한 별도 세션**으로 실행했습니다. Claude는 관련 소스를 독립적으로 읽었고 테스트를 재실행하지 않았습니다. [검토 원문](../../_workspace/features/apm/hardening-20261006/solutions--review_apm-overall-20261006-claude.md)을 보존했습니다.

- **동의:** 원문 설정 전환·원시 누적계열 충돌·역순 도착, 전량 서비스 집계, 알람 외부 I/O와 규모 검증 공백.
- **반영한 보완:** DELTA 권장 경로와 CUMULATIVE 영향 범위 구분. 상태코드뿐 아니라 버려지는 원시 속성 전반의 충돌 가능성. 원시 키 상태 예산 필요. SQL 중심 마스킹의 한계.
- **추가 확인:** Claude가 트레이스의 env도 빠졌을 가능성을 제기했고, FE→hook→Controller를 다시 대조해 네 전역 화면 모두에 해당함을 확인했습니다. 트레이스 수동 갱신은 해결된 상태로 유지합니다.
- **채택하지 않은 단정:** “수십 서비스에서는 사용 가능”이라는 수치는 현재 복합 부하 근거가 없어 지원 규모로 채택하지 않았습니다. “한 줄 수정”이라는 표현도 권한·과거 행·마스킹 회귀 검증까지 포함한 완료 비용을 뜻하지 않습니다. 늦은 포인트 폐기의 무손실 역시 조건 검증 없이 보증하지 않습니다.

RUM session 합산은 FE의 문구·footnote·계약을 대조한 결과 의도된 ‘버킷 세션 합’임을 확인해 결함 목록에서 제외했습니다. 개선안이 현재 구현을 오해해서 생긴 항목인지도 검토했습니다.

## 6. 검증·개발 순서 제안

1. **숫자와 권한을 닫는 회귀 기준부터 작성:** 1~4번을 작은 기준 모델과 실제 HTTP/DB 시험으로 고정하고 구현을 수정합니다. **2번의 원시 키 도입과 동시에 14번 중 tracker 상태 예산·초과 정책을 설계·검증합니다.** HA가 목표라면 이때 15번의 시계열 소유권·checkpoint 경계도 함께 정하고, 다중 노드 정확성 검증을 통과하기 전 배포를 확대하지 않습니다. 기존 테스트의 잘못된 가정도 함께 바꿉니다.
2. **지연 복구·파생 결과 일치:** 5~8번을 실제 PostgreSQL의 2회 집계·backfill·손상 파일·retention 시나리오로 검증합니다.
3. **운영 판단의 일관성:** 9~11번을 환경별 fixture와 fake clock/브라우저, 알림 제공자 지연으로 검증합니다. 알람은 기존 독자 알림 작업에 통합합니다.
4. **목표 규모를 측정해 병목을 제거:** 12번의 기준과 관측을 준비하고 13~19번 개선 전후를 같은 입력으로 비교합니다. HA가 요구되면 15번을 이 단계의 전제 조건으로 올립니다.
5. **지원 범위를 공개하고 확장:** 20번의 실제 지원 조합·복구 증거를 갖춘 뒤 21~23번을 고객 요구에 맞춰 진행합니다.

전체 분석을 구현 완료로 취급하지 않습니다. 특히 코드상 조건부 항목은 작은 실제 DB/HTTP 재현으로 메커니즘을 확정한 뒤 수정해야 합니다. 반대로 이미 직접 재현된 계산·정책 문제를 부하시험이 끝날 때까지 미룰 이유도 없습니다.
