OpenTelemetry를 활용한 MovesEye APM 구축 이야기

인프라 모니터링은 서버와 자원의 상태를 파악하는 출발점이다. CPU 사용률, 메모리, 네트워크, 프로세스 상태를 보면 장애의 범위를 좁힐 수 있다. 여기에 애플리케이션 요청의 흐름을 더하면 한 단계 더 구체적인 질문을 할 수 있다.

“어떤 API가 느려졌는가?”, “그 요청은 DB와 외부 서비스 중 어디에서 시간을 썼는가?”, “지금도 응답하지 못한 요청이 있는가?”

MovesEye는 Zabbix 기반 인프라 관측에 이런 요청 단위의 관점을 더하기 위해 OpenTelemetry를 활용한 APM을 구현했다. APM은 Application Performance Monitoring의 약자로, 애플리케이션의 처리량·오류·지연과 개별 요청의 실행 흐름을 살펴보는 데 사용한다.

이 과정에서 중심이 된 선택은 관측 목적에 따라 데이터 경로를 나누는 것이었다. 전체 추세를 집계하는 데이터, 완료된 요청을 분석하기 위해 보관하는 데이터, 현재 요청의 흐름을 빠르게 보여 주는 데이터는 요구 조건이 달랐다.

계측과 수집에는 OpenTelemetry를 사용했다

애플리케이션의 HTTP 요청, DB 호출, 외부 API 호출을 관측하려면 라이브러리와 실행 환경에 맞는 계측이 필요하다. MovesEye에서는 이 수집 기반으로 OTel Agent·SDK와 Collector를 사용하고, 수신 이후의 집계·저장·조회와 운영 화면을 제품에서 구현했다.

OTel은 관측 데이터를 생성·수집·전송하기 위한 기반을 제공한다. 저장과 시각화는 별도의 백엔드가 담당하므로, 제품에서는 어떤 데이터를 어떻게 해석하고 보여 줄지 결정해야 한다. OpenTelemetry 공식 개요

MovesEye의 서버 측 수집 흐름은 다음과 같이 정리할 수 있다.

그림 1. 서버 측 주요 데이터 경로를 목적별로 단순화했다. 라이브 기능과 Java 확장 경로는 해당 기능을 활성화한 구성에 적용된다.

Agent에서 Collector로 들어오는 데이터와 Collector에서 MovesEye로 보내는 데이터는 구간별로 전송 방식을 맞춘다. 현재 MovesEye의 Collector 템플릿은 OTLP gRPC·HTTP 수신을 열고, MovesEye 백엔드로는 OTLP/HTTP JSON 인코딩을 사용한다. 백엔드 수신기가 모든 OTLP 전송 방식을 직접 처리하는 구조는 아니다.

Spring 백엔드는 수신 데이터의 인증과 형식·크기 등을 확인하고, 신호에 맞는 처리 경로로 전달한다. 일반 메트릭은 집계·저장에, 보존용 Trace는 요청 분석에, 라이브 데이터는 최근 상태를 보여 주는 데 사용한다.

실시간 화면과 분석용 저장의 요구가 달랐다

요청 데이터를 모두 오래 보관하면 저장량과 조회 부담이 커진다. 반대로 보관할 요청을 선택한 뒤 그 결과만 실시간 화면에 사용하면, 실제 요청 흐름 중 일부만 보이게 된다. 오류와 느린 요청을 우선 선택하는 정책이라면 화면의 분포도 그 정책의 영향을 받는다.

그래서 MovesEye의 Collector 구성은 보존용 Trace 경로와 라이브 완료 Span 경로를 분리한다. 두 경로는 같은 OTLP receiver에서 입력을 받지만, 서로 다른 Processor와 Exporter를 사용한다.

보존용 Trace에는 오류, 지연, 확률에 따른 선택 정책을 적용한다. 라이브 경로에는 Tail sampling을 넣지 않고, HTTP 서버 Span 중 화면에 필요한 대상과 속성을 선별한다. 이때 라이브 경로가 SDK의 Head sampling이나 앞단 손실까지 복구하는 것은 아니다.

라이브 화면의 점은 서비스별 HTTP 서버 Span을 기준으로 한다. 한 사용자 요청이 여러 서비스를 거치면 각 서비스에서 별도의 서버 Span이 생길 수 있으므로, 여러 서비스의 점을 합친 수를 사용자 요청 수로 해석해서는 안 된다. 백엔드는 수신·수용한 데이터를 집계하고, 화면에 표시할 점은 메모리와 표시 상한에 맞춰 표본으로 유지한다. 화면의 점 수와 집계 건수도 다를 수 있다.

최근 기록은 메모리 링 버퍼, 즉 제한된 공간에서 최근 구간을 순환 보관하는 구조에 두고 SSE로 브라우저에 전달한다. SSE는 Server-Sent Events의 약자로, 서버가 열린 HTTP 연결을 통해 이벤트를 계속 보내는 방식이다. 라이브 경로에서 재시도를 끈 선택은 과거 데이터를 오래 재전송하는 대신 현재 흐름의 전달을 우선하는 정책이며, 장애 구간의 누락을 감수한다.

따라서 실시간 화면에 표시된 요청과 장기 보존된 Trace가 항상 일대일로 대응하지는 않는다. 화면의 한 점은 관측되었지만, 해당 요청이 보존 정책에서 선택되지 않아 상세 Trace는 남지 않을 수 있다. 이 차이는 화면에서 사용자에게 설명해야 하는 데이터의 특성이다.

또한 화면 갱신 주기가 짧다고 요청이 발생한 즉시 보인다는 뜻은 아니다. Agent의 배치, Collector의 처리·전송, 네트워크와 브라우저 갱신이 실제 도착 지연에 함께 영향을 준다.

아직 끝나지 않은 요청을 별도로 추적했다

완료된 Span을 받는 경로는 요청이 어떻게 끝났는지 분석하는 데 유용하다. 하지만 아직 종료되지 않은 요청은 완료 데이터만으로 현재 상태를 알기 어렵다. 사용자가 응답을 기다리고 있는 동안 “지금 얼마나 오래 걸리고 있는가”를 보려면 별도의 상태가 필요하다.

MovesEye는 이를 위해 OpenTelemetry Java Agent 확장을 구현했다. 확장은 HTTP 서버 계측의 시작·종료 콜백을 이용해 진행 중 요청을 관리하고, 경과 시간별 요청 수와 오래 실행 중인 요청 목록을 전송한다.

그림 2. 완료 Span과 진행 중 요청 관측의 차이. 아래 집계 시점은 개념 예시이며 실제 화면 도착 시각을 의미하지 않는다.

요청이 시작되면 추적 토큰을 만들고 OTel Context에 연결한다. 주기적으로 추적 상태를 읽어 경과 시간별 요청 수와 오래된 요청을 계산하고, 요청이 종료되면 해당 토큰을 제거한다. 비동기 처리에서 스레드가 바뀌더라도 해당 Context가 전달되는 경로에서는 토큰을 이어서 사용할 수 있다. 화면의 목록은 마지막으로 집계·수신한 상태이므로, 화면을 보는 순간에는 이미 종료된 요청이 포함될 수도 있다.

건수와 경과 시간 분포는 Metric으로, 오래된 요청의 상세 목록은 특정 형식의 OTLP Log로 전송한다. 요청마다 달라지는 식별자를 Metric의 차원으로 늘리는 대신, 집계와 개별 목록을 나눠 다루는 구조다.

상세 목록에는 계측 가능한 DB·외부 HTTP·RPC 하위 작업 정보를 담을 수 있다. RPC는 다른 프로세스나 서비스의 기능을 호출하는 원격 호출을 뜻한다. 현재 구현은 요청당 하위 작업 하나를 표시하므로, 모든 병렬 작업이나 전체 호출 스택을 재구성하는 기능으로 해석해서는 안 된다. OTel Log를 이 전송에 사용한다는 사실도 범용 애플리케이션 로그의 저장·검색 기능을 제공한다는 뜻은 아니다.

관측 코드의 자원 사용에도 경계를 뒀다

진행 중 요청을 저장하는 공간이 무한히 커지면 장애 상황에서 관측 기능 자체가 애플리케이션에 부담을 줄 수 있다. 확장은 고정 크기의 추적 공간과 TTL을 사용해 보관 범위를 제한한다. TTL은 여기서 관측 기록을 유지하는 최대 시간을 뜻한다.

추적 공간이 부족하면 해당 요청을 추적하지 못할 수 있다. TTL이 지나면 관측용 토큰을 회수하지만, 실제 업무 요청을 취소하거나 정상 완료로 처리하는 것은 아니다. 따라서 진행 중 요청 수는 추적 범위와 만료 정책을 함께 이해해야 하는 값이다.

상세 목록을 사용하지 않는 설정에서는 요청별 상세 정보와 하위 작업 수집을 생략하도록 했다. 필요한 정보의 수준에 맞춰 수집 비용을 줄이기 위한 선택이다. Java Agent가 제공하는 확장 인터페이스인 SPI와 일부 SDK 내부 접근을 사용하는 만큼, Agent 버전을 변경할 때는 호환성과 데이터 전송을 다시 확인해야 한다.

수집 실패를 처리하는 HTTP 상태 코드가 중요했다

수집기를 연동하면서 확인한 중요한 점은 “서버 오류니까 재시도할 것”이라는 가정이 OTLP/HTTP에 그대로 적용되지 않는다는 것이었다.

OTLP/HTTP 규격은 재시도할 응답 코드를 429, 502, 503, 504로 정의한다. 그 밖의 4xx와 5xx는 재시도 대상이 아니다. 500도 여기에 포함된다. OTLP/HTTP 재시도 규격

MovesEye의 메트릭·Trace 수신 경로는 적재 중 예외가 발생하면 503을 반환하도록 구현되어 있다. 재시도가 활성화된 보존 경로의 Exporter가 일시적 실패를 다시 시도할 수 있게 하기 위해서다.

재시도는 중복 저장 문제와 함께 다뤄야 한다. 서버가 저장한 뒤 응답이 유실되면 같은 데이터가 다시 도착할 수 있다. 저장형 큐를 설정하는 것만으로 정확히 한 번 저장되거나 무손실로 전달되는 것은 아니다. 배치의 중복 판정과 저장의 원자성을 함께 검토해야 한다. 여기서 원자성은 관련 변경이 함께 성공하거나 함께 취소되는 성질을 뜻한다. 큐 상한과 재시도 예산도 별도로 고려해야 한다. Collector의 회복력과 데이터 손실 조건

마스킹 규칙도 정상 데이터로 검증해야 했다

URL, SQL, 예외 메시지에는 민감한 값이 포함될 수 있다. Collector에서는 불필요한 속성을 제거하고, 일부 값은 패턴에 따라 마스킹한다.

진행 중 요청을 구현하는 과정에서는 긴 숫자를 가리는 규칙이 로그 본문의 JSON 안에 들어 있던 timestamp까지 변경하는 문제가 있었다. 민감한 숫자 패턴을 지우려던 처리가 정상 데이터의 구조를 손상시킨 것이다.

이 경험은 마스킹 검증의 기준을 구체화했다. 민감값이 지워지는지와 함께, 정상 데이터가 파싱 가능한지, 시간과 식별 정보가 의도대로 유지되는지도 확인해야 한다. 정규식 하나가 모든 개인정보를 제거한다고 가정하기보다 수집할 필드를 제한하고 데이터 종류에 맞는 처리를 적용해야 한다.

화면에서 숫자의 의미까지 전달해야 한다

예를 들어 운영자가 실시간 화면에서 느린 요청의 점을 발견했지만 상세 Trace를 찾지 못했다고 하자. 이때는 요청이 없었다고 판단하기보다 조회한 서비스와 시간 범위가 맞는지, Trace 수신이 지연되었는지, 보존 정책에서 선택되지 않았는지를 순서대로 확인해야 한다.

이런 탐색을 돕기 위해 화면에는 수집 시점, 조회 범위, 표본과 전체 건수의 차이가 드러나야 한다. 빈 값을 항상 0으로 표시하면 실제 요청이 없었던 상황과 관측하지 못한 상황이 같아진다. MovesEye의 APM을 만들며 데이터의 범위와 의미를 사용자에게 설명하는 일도 기능의 일부라는 점을 확인했다.

인프라 상태에서 요청 흐름으로, 요청 흐름에서 개별 작업 구간으로 이동할 수 있는 관측은 문제를 조사할 근거를 더해 준다. OpenTelemetry는 그 근거를 만들고 전달하는 공통 기반이 되었고, MovesEye에서는 데이터의 목적에 맞는 처리 경로와 해석 가능한 화면을 만드는 데 집중했다.

Agent·Collector·Trace의 기본 개념은 OpenTelemetry로 이해하는 애플리케이션 관측의 기본에서 확인할 수 있다.
