## 🔴 반드시 고칠 것

### 1. §5.1·§9 — `EXPIRED` 폴러 지속은 기존 라이선스 원칙과 충돌

**근거:** §5.1은 `AccessMode != FULL`이면 폴러를 정지한다고 쓰지만, §9는 `EXPIRED`에서도 계속 수집한다고 합니다. 기존 [SchedulerJob.java:42](/C:/solutions/moveseye-be-spring/src/main/java/com/dmove/moveseye/scheduler/SchedulerJob.java:42)는 외부 수집 소스를 호출하는 배치와 내부 정리·파생 작업을 구분하고, 전자는 만료되면 중단하도록 명시합니다. 실제 `SchedulerManager`도 `canWrite()`로 차단합니다.

P17의 `allowsLiveQuery()`는 이미 Zabbix가 수집한 값을 실시간으로 **조회할 권한**입니다. 고객 DB를 계속 폴링하여 우리 PG에 새 데이터를 적재할 권한으로 확대할 근거는 없습니다. 더구나 [LicenseStatus.java:52](/C:/solutions/moveseye-be-spring/src/main/java/com/dmove/moveseye/license/domain/LicenseStatus.java:52)는 만료 상태에서 `Feature.DB_MONITORING` 자체를 거부합니다. 따라서 현재 계약대로라면 폴러가 계속 돌아도 `/dbm/**` 조회는 차단됩니다.

**결론·수정 제안:** 기존 정책을 유지한다면 `EXPIRED`부터 폴러를 정지하고 롤업·정리만 계속하십시오. 만료 후 DBM 과거 조회·내보내기를 허용할지도 별도로 결정해야 합니다. 30일 수집 유지를 원한다면 P10·P17·Feature 정책을 함께 개정해야 하며, DBM 설계서의 예외 문장 하나로 처리해서는 안 됩니다.

### 2. §5.5 — 엔진 정규화 텍스트를 그대로 신뢰하면 마스킹 보증이 깨짐

**근거:** §5.5는 PG·MySQL의 정규화 텍스트를 “그대로” 저장하도록 합니다. 그러나 PostgreSQL 공식 문서는 정규화 가능한 쿼리도 특정 상황에서 상수가 남을 수 있다고 설명합니다. 엔진 정규화는 SQL 그룹핑 기능이며, 개인정보 제거의 완전한 보안 경계가 아닙니다. [PostgreSQL 공식 문서](https://www.postgresql.org/docs/17/pgstatstatements.html)

플랜도 predicate 문자열만 처리하면 충분하지 않습니다. XML 속성, JSON 값, 기타 메타데이터에 상수가 들어갈 수 있습니다. 반대로 모든 숫자를 토크나이저로 제거하면 cost·예상 행 수 같은 분석 정보까지 훼손합니다.

**결론·수정 제안:** 엔진 정규화 여부와 관계없이 저장 직전에 방언별 검사를 적용하고, 실패하면 텍스트를 버리는 정책으로 통일하십시오. 플랜은 구조를 파싱하여 허용 필드를 보존하고 민감 필드를 제거해야 합니다. `PEEKED_BINDS` 등 바인드 노출 경로도 명시적으로 금지해야 합니다.

200건 fixture는 시작점으로 적절하지만 “리터럴 잔존 0 보증”의 충분조건은 아닙니다. 잘린 SQL·주석·DDL·중첩 문자열·비정상 인코딩도 포함하고, 큐·예외 로그·진단 번들까지 같은 정책을 적용하십시오.

### 3. §6.1 — 논리 endpoint·물리 DB·SQL 통계 식별자가 충분히 분리되지 않음

**근거:** 독립 제안은 클러스터·물리 노드·논리 DB/PDB·접속 endpoint를 구분했습니다. v1은 이를 `dbm_instance.host/port/service/db`로 압축했습니다. VIP가 다른 물리 노드로 전환되거나 같은 서버에서 여러 DB/PDB를 수집하면 인스턴스 수명과 통계 수명이 달라집니다.

SQL도 `sha256(engine, normalized_text)`만으로는 실행 의미를 구분하지 못합니다. PostgreSQL은 같은 텍스트라도 `search_path` 등에 따라 다른 의미를 가질 수 있고, 통계 식별에는 `dbid`·`userid` 등 문맥이 필요합니다. [PostgreSQL 공식 문서](https://www.postgresql.org/docs/17/pgstatstatements.html)

D8의 “외부 링크 다대다”와 단일 `zbx_hostid` 컬럼도 일치하지 않습니다. Zabbix hostid에는 데이터소스 범위와 OS 호스트/DB 논리 호스트 역할이 필요합니다.

**결론·수정 제안:** 논리 대상 UUID, endpoint, 관측 물리 노드, DB/PDB namespace를 분리하십시오. native 통계 식별자와 화면용 fingerprint도 분리해야 합니다. 하나의 fingerprint에 여러 native ID·스키마·플랜이 연결되는 모델이 필요하며, Zabbix 링크는 `(datasource_id, hostid, role)`을 가진 별도 관계로 두는 편이 안전합니다.

### 4. §5.1·§5.4·§6.3 — lease와 델타 복구가 이름만 있고 실패 계약이 없음

**근거:** `lease_owner/lease_until`만 제시되어 있고 획득 원자성·갱신·탈취·소유권 상실 후 쓰기 차단이 없습니다. 기존 `SchedulerLeaseService`는 30분 TTL의 배치 잠금이므로 상주 폴러에 그대로 적용하기 어렵습니다.

또한 델타 기준값의 보관 위치가 없습니다. BE 재시작이나 담당 노드 변경 후 누적값 전체를 이번 분의 증가량으로 처리할 위험이 있습니다. 카운터 감소만 감지하면 재시작 후 값이 이미 이전 값보다 커진 경우를 놓칩니다. 이것은 실제 구현 결함이 확인됐다는 뜻이 아니라, 현재 설계로 방지할 수 없는 시나리오입니다.

**결론·수정 제안:** 다음을 P1 계약으로 확정하십시오.

- DB 시간에 기반한 원자적 lease 획득·갱신과 증가하는 fencing token.
- 소유권을 잃은 워커의 추가 적재 거부.
- DB boot/reset 구간과 수집기 실행 구간의 별도 식별.
- 기준값·집계 적재의 일관된 checkpoint 처리.
- 복구 불가능하면 첫 관측은 기준값으로만 저장하고 해당 구간을 미완전으로 표시.

`(instance, epoch, seq)`는 kind별 sequence인지도 불명확합니다. SESSION과 COUNTER가 충돌하지 않도록 범위와 UNIQUE 제약을 명시해야 합니다.

### 5. §6·§8.3 — `at=` 재생의 기준·인덱스·수집 시차 계약이 빠짐

**근거:** 세션은 5초, 락은 10초, 카운터는 15초에 수집합니다. 인스턴스별 간격도 변경할 수 있으므로 같은 `at`를 전달한다고 동일 시점 자료가 되는 것은 아닙니다. 마지막 정상 값을 무제한으로 가져오면 장애 직전 상태가 현재 상태처럼 보일 수 있습니다.

`dbm_session_sample`에는 명시적인 파티션 시각 컬럼도 없습니다. batch를 조인해서만 시각을 얻는 구조라면 과거 조회의 partition pruning을 보장하기 어렵습니다.

**결론·수정 제안:** `at` 이하의 최근 batch를 선택하되 kind별 최대 허용 시차를 정하고, 응답에 `observedAt`·`ageMs`·`batchId`를 포함하십시오. 세션과 락을 원자적 스냅샷처럼 표현하지 않아야 합니다.

최소 인덱스 후보는 다음과 같습니다.

- batch: `(instance_id, kind, observed_at DESC)`.
- 세션: 파티션 시각을 포함한 키와 `(instance_id, batch_id)`.
- 세션 이력: 필요할 때 `(instance_id, session_key, observed_at)`.
- 락: `(instance_id, observed_at, waiter_key)`.
- SQL 추이: `(instance_id, query_dim_id, bucket_start)`.

파티션 테이블 UNIQUE/PK에는 파티션 키를 포함해야 한다는 PostgreSQL 제약도 DDL에 반영해야 합니다. [공식 문서](https://www.postgresql.org/docs/17/ddl-partitioning.html)

### 6. §6.1·§8.3 — 보존 기간끼리 충돌하고 참조 수명이 역전됨

**근거:** raw 세션은 48시간인데 `dbm_lock_edge`는 24시간입니다. 36시간 전 세션·락 트리 동시 재생 약속을 충족하지 못합니다.

SQL 차원은 마지막 관측 후 30일에 삭제하지만 SQL·activity 롤업은 180일 남깁니다. 실제 FK를 걸면 삭제가 막히거나, CASCADE라면 장기 통계를 잃고, FK 없이 지우면 이름과 SQL을 해석할 수 없게 됩니다. 사용자 사전을 무기한 유지하는 정책은 반대로 장기 개인정보 보존 문제가 됩니다.

**결론·수정 제안:** 락 상세를 세션 재생 기간에 맞추거나, 24시간 이후 가능한 재생 범위를 명확히 축소하십시오. 차원 ID는 참조가 남는 동안 유지하되 민감 텍스트는 별도 TTL로 지울 수 있어야 합니다.

“1m 집계 30일”에서 가능한 drill-down도 대기·SQL·사용자 집계까지입니다. 개별 세션 복원이 불가능하다는 §8.3 설명과, §8.2의 “대기→SQL→세션” 문구를 통일해야 합니다.

### 7. §6.2 — 기본 곱셈은 맞지만 전체 용량 결론은 과소 산정

**근거:** 5초 raw는 정확히 **17,280,000행/일**, 300B 가정이면 **5.184GB/일**, 48시간은 **10.368GB**입니다. activity 54GB, SQL 통계 30.24GB, metric 4.536GB도 산식은 맞습니다.

하지만 장기 롤업·batch·락·플랜·차원·outbox는 합계에서 빠졌습니다. 예를 들어 SQL 500개가 매시간 남는 밀집 시나리오라면:

`50 × 500 × 24 × 180 × 300B = 32.4GB`

metric 1h도 같은 메트릭 수라면 약 1.94GB입니다. 반면 activity 그룹 상한 50으로 계산한 27GB는 그룹 수를 절반으로 줄인 효과이며, 별도 1h 테이블을 추가하는 것 자체가 30일 1m 저장량을 줄이지는 않습니다.

**결론·수정 제안:** “70~100GB”는 완성된 전체 예산으로 사용할 수 없습니다. 모든 테이블군과 인덱스, 파티션 경계 여유, WAL·백업·재집계 공간을 분리 계산하십시오. 일 파티션만 DROP하면 보존량이 정확히 48시간분에 고정되지 않는 점도 포함해야 합니다.

300B는 계속 미검증 가정으로 표시하고, APM의 686B를 DBM 행 크기의 **상한**으로 부르지 마십시오. 스키마와 인덱스가 달라 상한 근거가 되지 않습니다.

### 8. §6.1 — 디스크 예산 자동 단축은 장애 증거를 먼저 지울 수 있음

**근거:** raw 보존을 줄여도 장기 집계·플랜·차원 때문에 예산 초과가 계속될 수 있습니다. 장애 시 세션과 SQL 종류가 급증하면 가장 필요한 장애 구간의 증거가 자동 삭제될 가능성도 있습니다.

롤업이 밀린 상태에서 raw 파티션부터 지우면 장기 집계까지 복구 불가능해집니다. APM에는 `PartitionDropGuard` 등 삭제 방어 구조가 실제 존재하지만, DBM이 어떤 완료 상태를 확인할지는 명시하지 않았습니다.

**결론·수정 제안:** 자동 단축은 고객이 사전에 선택한 정책 안에서만 작동하게 하십시오. 최소 보존 보장, 롤업 완료 확인, 사건 구간 보호, 변경 감사, 실제 조회 가능한 기간 표시가 필요합니다.

예산은 DBM 논리 크기와 전체 파일시스템 잔여 공간을 함께 보아야 합니다. APM과 같은 PG를 사용하므로 DBM만 100GB 이하라고 저장소가 안전하지는 않습니다. 자동 단축 후에도 부족한 경우의 수집 제한·명시적 손실 정책까지 정해야 합니다.

### 9. §7.2·§8.4 — APM 재사용 비용과 필요한 신규 모델이 누락됨

**근거:** [ZabbixAlertBridge.java](/C:/solutions/moveseye-be-spring/src/main/java/com/dmove/moveseye/premium/apm/alert/bridge/ZabbixAlertBridge.java)는 약 1,700행이며 `ApmAlertKind`, APM 규칙·binding Repository, cleanup 모델, 서비스/collector scope, `apm.*` 키와 태그에 결합돼 있습니다. 패키지를 `premium/common/`으로 옮기는 것만으로 일반화되지 않습니다.

또한 `apm_db_query_group`은 endpoint·port·namespace를 저장하지 않고 `(service_id, fingerprint)`로 묶습니다. [실제 집계 코드](/C:/solutions/moveseye-be-spring/src/main/java/com/dmove/moveseye/premium/apm/trace/rollup/ApmTraceRollupService.java:699)에서도 이 축만 남깁니다. `db.client.operation.duration`의 허용 차원에도 endpoint가 없습니다.

**결론·수정 제안:** Zabbix 전송·객체 소유권 처리와 APM 규칙/binding 관리를 분리하고, DBM 어댑터는 중립 DTO를 소비하게 설계하십시오. APM 회귀와 DBM 자체 검증을 별도 작업으로 산정해야 합니다.

APM 상관에는 서비스↔endpoint↔namespace 관측 모델이 필요합니다. 현재 서비스 단위 p95를 특정 DB 인스턴스의 p95처럼 표시해서는 안 됩니다. endpoint별 메트릭을 새로 보존하거나, 서비스 전체 지연과 DB 부하의 시간 상관임을 명시하십시오.

### 10. §5.3·§5.7 — 세션 상한과 품질 계산이 장애 시 지표를 왜곡할 수 있음

**근거:** 수천 세션 인스턴스에서 1,000행만 받으면 어떤 세션이 남는지에 따라 AAS와 락 영향도가 달라집니다. 성공 tick 수만으로 coverage를 계산하면 5,000개 중 1,000개만 받은 tick도 정상 관측으로 계산될 수 있습니다.

장기 트랜잭션·idle blocker를 저장 대상에 포함한 것은 맞지만, 이들을 모두 AAS 분자에 넣으면 활성 세션 부하를 과대 계산합니다. 반대로 그룹 상한 50에서 나머지를 버리면 AAS가 줄어듭니다.

**결론·수정 제안:** 시간 관측률·행 잘림·텍스트 잘림을 별도 품질 축으로 유지하십시오. idle blocker는 조사 자료로 보존하되 AAS에는 실제 활성 상태만 포함해야 합니다. 그룹 상한 초과분은 `OTHER`로 총량을 보존하고, SQL 상세 분해만 불완전하다고 표시하십시오.

수천 세션 부하 검증, 결정적 우선순위, 전체 건수와 저장 건수의 분리도 필요합니다. `truncated=true` 하나만으로 수치 오해를 막을 수는 없습니다.

### 11. §5.1·§5.6·§9 — JDBC 보안과 실행 예산을 구현 가능한 계약으로 내려야 함

**근거:** 비밀번호 암호화는 있지만 대상 DB 연결의 TLS·서버 인증서 검증·신뢰 CA 설정은 없습니다. “전송 암호화 지원”을 제품 특징으로 내세우려면 엔진별 JDBC 설정과 실패 동작이 있어야 합니다.

또한 단일 직렬 워커에서 SQL 통계 조회가 최대 10초 걸리면 그동안 세션 tick이 밀립니다. 활성 세션 평균이 낮아도 1초 수집 품질을 보장할 수 없습니다. Hikari `connectionTimeout`은 연결 획득 예산이며, 전체 네트워크·쿼리 취소 예산을 대신하지 않습니다.

**결론·수정 제안:** 엔진별 TLS 검증, connect/socket/query timeout, 취소 실패 시 연결 폐기, 전체 tick 예산을 정의하십시오. 1초 세션 작업과 느린 보강 작업의 실행 예산도 분리해야 합니다.

자격증명 변경·비밀번호 만료·계정 잠김은 일반 DB DOWN과 구분하고, 반복 인증으로 계정 잠김을 악화시키지 않아야 합니다. 고객 jar 업로드는 서버 코드 실행과 연결되므로 관리자 권한·허용 드라이버·설치 이력 정책이 필요합니다.

## §14 대조 표 공정성 평가 (당신 제안 중 잘못 기각/축소된 것)

**전체 평가는 “핵심 방향은 공정하게 반영했으나 일부 채택 판정이 과장됨”입니다.** 제 제안을 유지하기 위해 v1의 더 나은 단순화를 반대할 이유는 없습니다.

1. **카운터 소스 변경은 타당한 대안이지만, 제안의 의도를 좁혔습니다.**  
   제안은 Zabbix에서 카운터를 조회하고 PG에 무조건 복제하자는 것이 아니었습니다. 소스별 책임을 분리하면 이중 저장은 필연적이지 않습니다. 폴러 카운터도 같은 연결을 쓴다는 이유로 동적 성능 뷰들이 하나의 일관된 트랜잭션 스냅샷이 되지는 않습니다. 기본 C는 JDBC로 정하되, 기존 Zabbix 카운터만 있는 고객에게 제한된 개요를 제공하는 경로는 보존할 가치가 있습니다.

2. **5초 기본으로 수정한 판정은 공정합니다.**  
   제 용량 표가 1초 기본의 부담을 드러낸다는 지적을 수용합니다. 다만 “설치형 PG 예산 밖”은 보편적 사실이 아닙니다. 고객별 인스턴스 수·보존량에 따라 달라지므로, 1초를 금지하기보다 인증된 용량 프로필로 제한해야 합니다.

3. **원격형 P5는 단순한 시기 차이가 아닙니다.**  
   독립 제안은 BE에서 DB망에 접근할 수 없는 고객에게 원격형을 제공하고 기본 GA 공수에 포함했습니다. v1은 원격형과 OTel을 모두 P5로 미룹니다. 그러면 GA의 도입 가능 고객 범위가 줄어듭니다. 표의 `✅(시기만)`을 **“GA 지원 토폴로지 축소”**로 바꾸고, 대상 고객의 망 구조로 판단해야 합니다.

4. **OTel 경고를 문장으로 반영했지만 선행 실험은 축소했습니다.**  
   제안 §7은 receiver의 실제 출력·마스킹·계획 동작을 P0에서 확인하도록 했습니다. v1은 가능성을 인정하면서 비교 실험을 빠뜨렸습니다. 따라서 “전 항목 대응” 완료 판정은 과합니다. 유예 결정 자체보다 검증 없이 유예를 확정한 점이 문제입니다.

5. **Codec 재사용은 개선이지만 키 수명주기 요구는 남습니다.**  
   새 AES 구현을 제안한 부분은 불필요했습니다. 그러나 제안의 key ID·백업·교체·복호화 실패 진단은 현재 Codec으로 자동 충족되지 않습니다. “이미 같은 방식”을 “암호화 구현은 재사용, 키 운영은 추가 설계”로 바꿔야 합니다.

6. **Oracle TUNING 제외는 공정한 범위 축소입니다.**  
   독립 제안도 별도 확장 과제로 두었으므로 실질적으로 큰 기각이 아닙니다. ASH 보류도 합리적입니다. 반면 6.0 sender 유예는 이메일이 고객 통지 요구를 충족하는지에 달렸으므로 `채택`이 아니라 명시적 기능 차이로 남겨야 합니다.

7. **GA 공수의 `≈` 판정은 동등 비교가 아닙니다.**  
   v1은 원격형을 뒤로 미루면서 플랜 비교·APM 상관·리포트를 GA에 추가했습니다. 제 제안은 공통 기반과 PG/MySQL 단계도 더 분리했습니다. 기능별 포함/제외 표 없이 총합만 비슷하다고 비교하면 추가 범위의 비용이 가려집니다.

## 빠진 질문(B)·빠진 Q(F)

아래는 설계가 이미 답한 것으로 처리하면 안 되는 고객 질문입니다. 금융·제조의 실제 요구 여부는 고객 확인이 필요하며, 조사 기록의 RFP 표도 **공개 원문이 아닌 재구성**이라는 한계를 유지해야 합니다.

| 빠진 질문 | 근거 → 필요한 결정 |
|---|---|
| **BE 두 대 중 한 대가 죽으면 언제 수집을 인계하는가?** | lease 필드만 존재 → 수집 RTO, 갱신·fencing·중복 적재 시험을 정해야 함 |
| **저장 PG가 멈추면 어디까지 잃는가?** | 배치 큐 내구성 미정 → 메모리/디스크 큐, byte 상한, 폐기 우선순위와 손실 표시 필요 |
| **VIP 전환·AG 승격·PG failover 후 같은 DB인가?** | endpoint와 물리 노드가 혼재 → boot_epoch·역할·카운터 기준 재설정 필요 |
| **5,000세션에서 어떤 1,000개를 보존하는가?** | 반환 상한만 존재 → blocker 보존, 총량 분리, 편향·누락 표시 필요 |
| **DB·BE·브라우저 시간대가 다르면 무엇을 기준으로 재생하는가?** | 시각 종류 미정 → UTC 관측 시각, 원본 TZ, monotonic 경과 시간, clock skew 정책 필요 |
| **한글 SQL·계정명·객체명이 깨지면 어떻게 진단하는가?** | 문자셋 정책 없음 → JDBC 변환, Unicode, byte/문자 길이, 마스킹 실패 fixture 필요 |
| **접속 실패 알람이 수십 개씩 쏟아지는가?** | DOWN·STALE 규칙만 있음 → 장애 상관 억제, 유지보수, 연속 회복, 재통지 간격 필요 |
| **계정 비밀번호 만료·잠김·교체는 누가 관리하는가?** | 암호문 저장만 있음 → 인증 실패 분류, 교체 이력, 연결 풀 갱신·롤백 필요 |
| **누가 원문·플랜을 조회하거나 반출했는가?** | opt-in 감사만 언급 → 조회·내보내기·권한·보존 변경 감사와 보존 기간 필요 |
| **운영자가 모든 DB의 SQL을 볼 수 있는가?** | 역할 3종만 존재 → 인스턴스/그룹별 접근 범위와 SQL·사용자 정보 권한 필요 |
| **DB가 Hang이면 마지막 자료를 어떻게 표시하는가?** | JDBC 실패 시 백오프 → 마지막 관측 시각·수집 불가 이유·직접 메모리 방식과의 한계를 명시해야 함 |
| **백업 지연·DB 오류 로그·파라미터 변경은 지원하는가?** | 조사에는 등장하지만 구현 범위 불명확 → 엔진별 지원/제외 표와 후속 우선순위 필요 |

§13 기존 Q의 추천은 다음처럼 보정하는 것이 좋습니다.

- **Q1:** PG로 공통 기반을 먼저 검증하는 A안에 동의합니다. 다만 Oracle 최소 권한·SQL 검증은 P0부터 병행해야 영업 핵심 엔진의 위험을 늦게 발견하지 않습니다.
- **Q2:** 5초 기본에 동의하되, 1초 조건을 세션 평균 대신 전체 성능·용량 예산으로 바꾸십시오.
- **Q3:** RAC 무조건 P5에는 조건부 반대입니다. 금융 Oracle을 GA 대상으로 삼는다면 최소 RAC 노드 식별·중복 방지·교차 노드 blocker 범위가 필요합니다. 제외한다면 GA 지원표에 분명히 적어야 합니다.
- **Q4·Q6:** ASH와 Kill 유예에 동의합니다.
- **Q5:** 이메일 폴백만으로 충분한지는 6.0 고객의 실제 통지 요구로 결정해야 합니다. 자동 복구·순서 보장·채널 도달까지 종료 기준에 넣으십시오.
- **Q7:** 가명화 기본 OFF를 모든 고객에 고정하지 말고 보안 프로필로 선택하게 하십시오. 가명화 키 변경과 과거 필터 연속성도 필요합니다.
- **Q8:** 비밀번호 인증만 허용되지 않는 고객도 있으므로 일괄 비범위는 영업 제약입니다. Wallet·통합 인증·조직 비밀관리 연동 중 최소 지원 구성을 고객군에 맞춰 정해야 합니다.
- **Q9:** XE·Developer는 출발점입니다. 이것만으로 Oracle 12c+/SE2/EE·SQL Server 2016+ 전 범위를 인증할 수는 없습니다. 지원 버전·에디션 시험표를 먼저 확정하십시오.
- **Q10:** 4개 진입점 추천에 동의합니다. 잠금은 인스턴스 상세에서 접근하고 성능 분석은 완성 시 노출하십시오.
- **Q11:** P5 고정 대신 P0 receiver 검증과 GA 네트워크 요구를 바탕으로 확정하십시오.

**추가할 미결 Q**는 ① GA 지원 토폴로지와 원격형 필요 여부, ② 만료 후 수집·과거 조회·내보내기 정책, ③ HA RTO/RPO, ④ 보장 보존 기간과 자동 삭제 동의, ⑤ 버전·에디션 인증 범위, ⑥ TLS·인증 방식, ⑦ 인스턴스별 권한·감사 범위, ⑧ 장기 Top N 손실과 정확도 표시, ⑨ 지원 규모별 하드웨어 프로필, ⑩ 공통화한 APM 구성요소의 소유권·회귀 책임입니다.
