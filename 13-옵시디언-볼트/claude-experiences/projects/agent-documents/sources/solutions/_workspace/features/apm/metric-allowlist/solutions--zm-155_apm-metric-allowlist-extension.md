## 1. 한눈에

| | 내용 |
|---|---|
| **문제** | 폐기 통계가 `NOT_ALLOWLISTED`를 보여주면서 스스로 "허용목록 확장 근거를 찾는 창구"라고 한다. 그런데 **확장 수단이 제품에 없다** — BE 허용목록이 자바 상수 표라 코드 수정·재배포가 유일한 길이다 |
| **방향** | 잠금은 유지하되, 관리자가 화면에서 여는 **정식 절차**를 만든다 |
| **본체** | 🔴 **카디널리티 상한.** 여는 순간 상한이 같이 걸리지 않으면 BE 게이트를 둔 이유가 사라진다 |

## 2. 핵심 결정

| # | 결정 | 이유 |
|---|---|---|
| 1 | **기존 1분 테이블에 저장 + 상한**(①안). 전용 테이블(②안) 기각 | 롤업 SQL이 메트릭 이름과 무관해서, 1m에 들어오면 **롤업·보존·아카이브에 추가 코드 없이 합류**한다. ②안은 디스크·메모리를 격리하지 못하면서 고칠 곳만 네 군데로 늘린다 |
| 2 | **상한 8종** | 등록 시점 4개(규칙 수 20·차원 키 3·위험 키 금지·이름 128자), 수신 시점 2개(규칙×서비스당 조합 50·서비스당 커스텀 시계열 200), 자동 정지 1개(접힘 비율 50%가 1시간 지속) 등 |
| 3 | **초과분은 버리지 않고 "기타"로 접는다** | 기존 route 상한과 같은 방식이라 **합계가 보존**된다 |
| 4 | 새 폐기 사유 2개 | `CUSTOM_SERIES_OVERFLOW` · `CUSTOM_RULE_SUSPENDED` |
| 5 | 🔴 **"후보 관측" 기록이 먼저 필요** | 지금 폐기 통계는 이름과 건수만 남겨 **어떤 속성이 오는지 알 수 없다.** 차원을 고르는 화면이 그걸 보여줘야 한다 |
| 6 | 조회 화면이 짝으로 필요 | 임의 메트릭을 그리는 조회 API가 없어서, 허용목록만 열면 **"저장은 되는데 안 보이는" 지표**가 쌓인다 |

### 가장 어려운 지점 — 차원 선택 UX
허용목록은 이름만이 아니라 **살릴 차원 목록**까지 정한다. 설계는 "무엇별로 나눠 보시겠습니까?"라고 묻고, 기본은 전부 해제, 속성마다 위험도 색과 **예상 시계열 수**를 보여 주는 안이다(§5.3).

## 3. 설계가 코드로 확인한 것

설계서는 사실(`[코드]`)과 제안(`[제안]`)을 구분해 적었다. 확인된 주요 사실:
- 판정 위치는 `MetricIngestor.toRow` ③단계
- 이미 있는 카디널리티 방어는 route 상한 하나
- 폐기 통계에 **속성 정보가 없다** → 차원 선택 화면의 선행 조건
