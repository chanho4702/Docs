## 막힌 것·모르는 것

- P2는 각 arm을 한 번씩 고정 순서로 실행했다. 반복 분포, 오차 범위, 순서 효과를 모른다. 정상/장기 요청에서 B가 A보다 빠르고 높은 동시성/상한 포화에서는 느린 상반된 결과도 이 조건에서는 원인을 분리할 수 없다.
- 호스트가 격리돼 있지 않았다. P2 직전에 다른 worktree의 Gradle daemon과 최대 heap 1GB인 test worker가 실행됐고, 전체 메모리 사용률이 약 80~87%였다. 해당 사용자 프로세스는 중지하지 않았다.
- 요청 추적만의 비용을 구할 matched no-extension baseline이 없다. 현재 분리 행으로는 `tracking_only`에 1초 집계를 추가한 차이와, 확장 없이 metric export 주기를 60초에서 1초로 줄인 차이만 볼 수 있다.
- 할당 지표는 측정 구간에 존재했던 모든 thread의 완전한 allocation profile이 아니다. 측정 시점에 살아 있는 thread들의 누적값 차이이므로 thread 생성·종료의 영향을 받을 수 있다.
- 보유 heap은 명시적 GC 한 번과 250ms 대기 뒤의 값이며 안정 상태 retained heap을 보장하지 않는다. GC 일시정지도 `GarbageCollectorMXBean`의 ms 단위 누적 시간 차이다.
- P1은 각 조합당 요청 1건이므로 반복성, 장시간 누수, 매우 늦은 종료 callback 여부는 모른다.
- 이번 범위는 JDK 17, Java agent 2.31.1, Spring MVC/Tomcat 조합뿐이다. WebFlux, virtual thread, 다른 servlet container는 측정하지 않았다.

## 이 접근을 계속할 만한가

**확장 접근의 검증을 계속할 만하다. 다만 현재 P2 수치만으로 제품 적용 비용을 확정할 단계는 아니다.**

근거는 다음과 같다.

- 핵심 기능 신호는 명확했다. 여섯 요청 종료 경로 모두 샘플링 on/off에서 시작·종료가 1:1이었고, 종료 후 active가 0이었다.
- P2의 모든 요청은 오류 없이 완료됐고, 상한 포화를 제외하면 drop·expiry·listener failure·aggregation failure가 없었다. 수집기 단절 중에도 요청 완료는 유지됐다.
- 확장 유무 A/B에서 요청당 할당 차이는 -81.771~+365.840B, full-GC 후 heap 차이는 -165,152~+508,424B 범위로 관측됐다. 이 실행에서는 지속적인 대형 메모리 증가 신호는 보이지 않았다.
- 반면 높은 동시성의 p99는 1,932.214ms에서 2,186.430ms로, 상한 포화의 p99는 2,042.949ms에서 3,402.022ms로 관측됐다. 상한 32에서는 270개 시작이 추적에서 제외됐고 집계 최대 시간이 153.831ms였다. `tracking_only`와 1초 집계 행의 차이도 컸다.

따라서 다음 판단점은 접근 폐기가 아니라 **격리 호스트에서 matched no-extension/tracking-only 기준을 추가하고, A/B 순서를 교차해 여러 번 반복하여 p99와 집계 최대 시간의 재현성을 확인하는 것**이다. 그 결과에서도 높은 동시성·상한 포화 지연이 반복되면 집계 경로와 상한 처리 구현을 먼저 줄인 뒤 제품 단계로 넘어가야 한다.

## 추가 — 추적 자료구조 개선 (2026-09-22, 재측정 대비)

### 무엇을 바꿨나
- `ActiveRequestTracker`: `ConcurrentHashMap` + 전역 토큰 번호(AtomicLong) + 상한 카운터(CAS 루프) →
  **고정 크기 `AtomicReferenceArray<Token>`**. 상한 = 배열 크기(별도 카운터 없음). 모든 요청이 함께 두드리는 공유 변수가 없다.
  - 시작: 무작위 위치에서 64칸 → 없으면 전체 → 전체도 없으면 1ms 동안 64칸만 보고 포기(엄격한 빈도 제한은 아님).
  - 종료: 칸에 **바로 그 토큰 객체**가 있을 때만 비운다(객체 동일성). 집계: 한 번 훑으며 TTL 만료도 처리.
- `PocState`: 정상 경로 카운터 4개를 `moveseye.poc.detailed-counters`(기본 false) 뒤로, `write-every-snapshot` 기본 false.
  `run-p1.ps1`은 둘 다 켠다. `max-active` 최대 1,000,000.
- 초기화 실패 방어: provider catch가 PocState를 다시 부르지 않음, PocState 실패 시 NOOP listener.
