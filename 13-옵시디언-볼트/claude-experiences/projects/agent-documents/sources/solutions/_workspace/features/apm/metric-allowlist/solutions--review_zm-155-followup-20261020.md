# APM 커스텀 메트릭 후속 검수 — 2026-10-20

대상: BE `a9080eb`, FE `258d747` 및 현재 작업 트리. 사용자 요청은 문제점·아쉬운 점 분석이며 구현 변경은 하지 않았다. 최근 변경인 ZM-155의 수집→저장→조회→차트 경로를 검토했다. 프로젝트 전체에 대한 검수 완료를 뜻하지 않는다.

## 검수 결과

### R1 · 높음 · 정상적인 0·소수 카운터가 미수신으로 표시됨

- 근거: `MetricIngestor.java:916`은 카운터의 `count`를 `Math.round(d.sum())`으로 만든다. `ApmCustomMetricSeriesService`는 이 count와 실제 sum을 응답한다. FE `customMetricSeries.ts:43`은 `!point.count`이면 실제 sum을 보기 전에 null로 바꾼다.
- 조건: 커스텀 COUNTER의 한 관측 증가량이 0 또는 0.2. 소수 증가량 여러 개가 같은 칸에 들어와도 각각 반올림된 count가 0이면 합산 후에도 0이다.
- 영향: 정상 수신된 값이 차트와 표에서 사라진다. 증가량 0도 관측 부재와 구분되지 않는다. `received=true`이면서 화면에 표시할 값은 없는 모순도 생긴다.
- 확인: 현재 FE 소스를 TypeScript transpileModule로 CommonJS 변환하여 실제 `apmCustomMetricPoints`를 실행했다. `{count:0,sum:0}`와 `{count:0,sum:0.2}` 모두 `[[0,null]]`, 대조군 `{count:1,sum:1}`은 `[[0,1]]`.
- 권고: COUNTER의 존재 여부는 nullable sum 또는 별도 관측 여부로 판단한다. 내장 HTTP 지표까지 사용하는 공통 count 의미를 무작정 변경하지 않는다.
- 회귀 검증: 증가량 0·0.2·1, 소수 포인트 여러 개의 동일 버킷 병합, `received=true`인 전체 0 구간을 수신부터 화면까지 검증한다.

### R2 · 높음 · 자리 만료 후 종류 변경이 과거 시계열을 재해석함

- 근거: `ApmCustomMetricGate.java:392`는 최근 7일 자리만 읽고, `:483`은 자리가 없으면 입력 kind로 새 자리를 만든다. 기존 규칙의 생성 시각은 그대로다. `ApmCustomMetricSeriesService.java:74`는 조회 기간과 무관하게 현재 자리 kind를 우선하고 전체 기간에 같은 avg/sum 해석을 적용한다.
- 조건: GAUGE로 저장한 규칙을 유지한 채 7일 넘게 중단한 뒤 동일 이름을 COUNTER로 전송한다. 5분·1시간 롤업에는 과거 데이터가 남아 있다(기본 보존 30일·400일).
- 영향: 과거 GAUGE의 관측 합계를 COUNTER 증가량으로 그린다. 반대 방향이면 과거 COUNTER가 avg 계산으로 바뀌며 sum/count가 1에 가까운 무의미한 값이 될 수 있다. 같은 과거 창의 조회 결과가 새 수신 종류에 따라 달라진다.
- 확인 수준: 코드 경로 추적. 실제 DB 시간 경과 재현은 하지 않았다.
- 권고: 용량 상한 자리의 만료와 시계열 의미(kind)의 수명을 분리한다. 동일 규칙 세대에서는 kind를 유지하거나 저장·조회에 종류별 세대 경계를 남긴다.
- 회귀 검증: 규칙을 삭제하지 않은 상태에서 8일 공백 후 종류를 바꾸고, 공백 전 롤업 조회가 불변인지 확인한다.

### R3 · 중간 · 커스텀 지표 단위가 보존되지 않아 서로 다른 단위를 합산함

- 근거: 커스텀 수신은 `MetricIngestor.java:626`에서 원래 unit을 Row에 전달하지만, `ApmMetric1mStore` UPSERT(:182 부근)에는 unit 컬럼·충돌 키가 없다. 자리 원장은 종류만 고정한다. `ApmMetricStore.dimensionSeries`는 이름·버킷·차원 기준으로 합산한다. 조회 DTO에는 unit이 없고 FE 차트·표는 `unit: "count"`를 사용한다.
- 조건: 같은 서비스·이름·GAUGE가 두 인스턴스 또는 SDK 교체 전후에 각각 1 s, 1000 ms로 전송된다.
- 영향: 환산 또는 거절 없이 평균 500.5 같은 의미 없는 값으로 합쳐진다. 단위가 일관되더라도 사용자는 시간·바이트·비율 중 무엇인지 API/차트에서 확인할 수 없다.
- 확인 수준: 코드 경로 추적. 실제 OTLP 요청 전송은 하지 않았다.
- 권고: 서비스×이름×규칙 세대의 단위를 고정하고 불일치는 명시적으로 거절하거나 정규 단위로 환산한다. 응답과 차트·표에도 단위를 전달한다.

## 아쉬운 설계·운영 부분

1. **접힌 몫의 count 의미**: overflow는 MIXED/count로 보여 주지만 GAUGE 1포인트는 1, COUNTER 증가량 100인 1포인트는 100을 더한다. 이것을 일관된 포인트 건수로 읽을 수 없다. 접힌 포인트 수는 별도 집계가 필요하다. R1과 같은 count 재사용 문제의 또 다른 영향이다.
2. **등록부터 수집 확인까지 운영 흐름**: `collectorSync()`의 `regenerationRequired`는 변경 워터마크가 존재하는지만 본다. 실제 수집기별 적용 완료를 추적하지 않아 재생성 권고를 완료 상태로 닫을 근거가 없다. 설정 버전·실제 적용 버전·첫 정상 수신을 연결하면 관리자가 작업 완료를 확인할 수 있다.
3. **검증 경계**: 기존 v5 승인에는 런타임·다중 노드 미실측이 명시되어 있다. 이번 검토에서도 빌드·전체 테스트·브라우저·DB 통합 실행은 하지 않았다. 소수/0, 장기 공백, 단위 변경을 포함한 수신→저장→조회→표시 검증이 필요하다. 기존 테스트 통과 수치는 이번 실행 결과로 재인용하지 않는다.
4. **유지보수성**: `ApmCustomMetricGate` 약 844줄에 규칙 스냅샷, 자리 원장, 캐시, 경고 감시가 함께 있다. 장애 경로와 트랜잭션 경계 파악 비용이 크다. 행위 검증을 먼저 확보한 뒤 책임별 분리를 검토할 만하다.

우선순위: R1 표시 정확성 → R2 과거 데이터 의미 보존 → R3 단위 보존 → 운영 완료 상태 및 책임 분리.
