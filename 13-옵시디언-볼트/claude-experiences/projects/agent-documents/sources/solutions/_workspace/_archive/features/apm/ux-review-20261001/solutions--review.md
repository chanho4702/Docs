# MovesEye APM 화면 구성과 UI UX 평가

2026-10-01 · 검수자 Codex · 평가 대상: 현재 localhost:5173 개발 화면과 FE 구현. 제품 코드는 수정하지 않았다.

**종합 의견: 기능 범위는 충분히 넓다. 다음 개선의 중심은 정보의 우선순위, 화면 간 조사 맥락 유지, 상태 표현의 정확성이다.** 현재 화면을 처음 쓰는 운영자의 관점에서는 대략 **6.5/10**으로 평가한다. 기능 범위 8, 화면 구성 6.5, 가독성 6, 조사 흐름 6, 첫 사용 경험 5.5 정도다. 이 점수는 정량 벤치마크나 사용자 실험 결과가 아닌 휴리스틱 평가이며, 경쟁 제품의 점수와 직접 비교하지 않는다.

**평가 범위와 한계**

- Chrome headless에서 관리자 계정으로 주요 APM 12개 목록·개요 화면, 서비스 상세의 10개 탭, X-View, 트레이스 상세, SLO 상세, 합성 감시 상세, 관리 콘솔의 수집기 상태·알람 규칙 화면을 열었다. 주 화면은 1600×1000, 서비스 상세는 1366×768에서도 확인했다.
- 목록 행 클릭, 개요→서비스 상세 이동, 사이드바 이동, 수동 새로고침을 실제로 확인했다. 서비스의 트레이스 탭은 공통 Explorer 구현을 읽어 평가했다. 설정 저장·삭제·수집 토글은 실행하지 않았다.
- RUM은 최근 1시간과 30일 모두 데이터가 없었다. 메시징·배치와 서비스 배포도 데이터가 없는 상태였다. 이 화면의 데이터가 채워진 뒤의 분석 경험에는 점수를 확정하지 않았다.
- 처음 캡처에서 비어 보였던 트레이스 산점도와 합성 감시 목록은 추가 대기 후 정상 표시됐다. 따라서 이를 데이터 누락 결함으로 보고하지 않는다. `traces-final.png`, `synthetics-loaded.png`가 최종 판단 근거다.
- 경쟁 제품은 공식 문서에 제시된 화면·조사 흐름을 비교했다. 동일 데이터·동일 장비로 성능이나 사용성을 실측한 비교가 아니다. 다크 모드·모바일·전체 키보드 접근성·대규모 서비스 환경은 미검증이다.

**현재 유지할 장점**

1. 서비스 상태, 요청량·오류율·지연, 트레이스, 예외, SQL, 외부 의존성, 런타임, SLO, RUM, 합성 감시까지 분석 축이 연결돼 있다.
2. `수신 없음`, `측정 불가`, `샘플 기준`, 집계 지연을 명시한다. 데이터 없음과 정상 0을 구분하려는 설계는 신뢰에 도움이 된다.
3. 개요에서 서비스 상세로 들어갈 때 시간·환경 필터가 유지된다. 차트↔표 전환, 전체 화면, Trace ID 직접 조회, 사용자별 위젯 배치도 실무에 유용하다.
4. 실시간 X-View는 정상·느림·오류를 점과 모양으로 구분하고 표시·관측 건수를 보여 준다. 실시간 관제와 저장된 트레이스 분석을 구분할 토대가 있다.
5. 수집기·알람 규칙을 관리 콘솔로 분리한 방향은 적절하다. 다만 현재 발화한 문제를 조사하는 진입점은 관제 화면에서 계속 쉽게 찾아야 한다.

**코드와 실행 근거**

- 수동 갱신: [ApmTracesPage.tsx](../../moveseyee_fe/src/pages/application-monitoring/traces/ApmTracesPage.tsx)의 `onRefreshNow={() => listQuery.refetch()}`는 서비스 선택 옵션 쿼리를 가리킨다. 실행 요청 목록은 [interactions.json](interactions.json)의 `trace-refresh-requests`에 보존했다.
- 오류 0의 막대: [ApmTopServicesCard.tsx](../../moveseyee_fe/src/pages/application-monitoring/overview/components/ApmTopServicesCard.tsx)의 `Math.max((value / max) * 100, 2)`가 0에도 최소 폭을 준다. 엔드포인트 오류 카드의 동일한 시각적 현상은 `service-overview.png`에 기록했다. 엔드포인트 측 원인 코드는 별도 확정하지 않았다.
- 미연결 카드: [ApmOverviewPage.tsx](../../moveseyee_fe/src/pages/application-monitoring/overview/ApmOverviewPage.tsx)의 `apm-overview-upcoming`은 배포·SLO·서비스 맵 자리표시자를 계속 렌더한다.
- 단계 탭: [apm.ts](../../moveseyee_fe/src/constants/apm.ts)의 서비스 탭 순서는 12개이며 로그는 READY 목록에 없다. 서비스 상세에서 비활성 `로그 4단계`로 표시된다.
- 내부 문구: [kr.json](../../moveseyee_fe/src/locales/kr.json)의 `burndown_note`, 실시간 `retained`·`ratios`에서 화면 문구를 확인했다.
- 기간 라벨: [ApmSyntheticDetailPage.tsx](../../moveseyee_fe/src/pages/application-monitoring/synthetics/ApmSyntheticDetailPage.tsx)의 `apm.synthetics.column.availability` 재사용과 실제 화면의 `실행 60 / 60회`·선택 창 안내를 함께 확인했다.
- 필터 보존/초기화: [interactions.json](interactions.json)의 `overview-to-service`, `sidebar-to-traces`에 이동 뒤 URL을 보존했다.

**권장 메뉴와 상세 화면 구성**

사이드바 항목을 일괄 삭제하기보다 APM 구역의 깊이를 줄이고 아래 업무 관계가 드러나게 묶는 것을 권한다. 기존 SLO 진입점 유지 결정은 존중한다.

| 묶음 | 항목 | 사용 목적 |
|---|---|---|
| 현황 | 개요, 실시간 관제 | 지금 어느 서비스가 문제인지 확인 |
| 분석 | 서비스, 트레이스 탐색, 서비스 맵 | 문제 서비스에서 요청·DB·의존성으로 원인 조사 |
| 서비스 품질 | SLO, 사용자 경험, 합성 감시 | 실제 사용자 영향과 목표 준수 확인 |
| 관리 콘솔 | 수집기, 알람 규칙 | 설치·수집 정책·통지 설정 |

서비스 상세의 12개 탭은 기본 6~7개 수준으로 보이게 묶는 안을 권한다. `개요`, `요청 분석(트랜잭션·트레이스)`, `오류`, `의존성(DB·외부 호출)`, `실행 환경(런타임·인스턴스)`, `배포`, `연결된 감시`로 구성하고 설정은 헤더 작업으로 옮길 수 있다. 기존 상세 딥링크와 숙련자 접근은 유지한다.

APM 오류 분석의 `DB 호출`과 제품 사이드바의 `DB 모니터링`은 역할을 명확히 나눠 설명해야 한다. 전자는 애플리케이션 요청에서 발생한 SQL 비용, 후자는 데이터베이스 자체 상태다. 같은 식으로 실제 사용자 관측인 RUM과 능동 실행인 합성 감시의 차이도 메뉴 설명에 드러내면 학습 부담이 줄어든다.

**개선 순서 제안**

1. 갱신 버튼, 잘못된 오류 강조, 기간 라벨, 내부 단계 문구부터 정리한다.
2. 사이드바·서비스 헤더·KPI 카드의 공간을 줄여 첫 화면의 판단 속도를 높인다.
3. 시간·환경 필터 유지와 옆 패널을 통해 개요→서비스→요청→원인 구간 이동을 다듬는다.
4. RUM·배포·메시징의 초기 수집 안내를 통일한다.
5. 현재 문제·영향 범위·최근 배포 변화 요약을 강화한다. 기존 결정인 APM 독자 알림 전환은 별도 착수 지시가 필요한 후속 작업으로 남긴다.

이 평가는 구현 지시가 아니라 제품 개선 제안이다. 알림 체계나 수집 정책의 변경을 수행하지 않았다.
