## 10. P5 실시간 관제 — 한눈에

> 이 장을 읽으면: ① P5가 답하려는 질문과 그 질문이 왜 P1~P4로는 안 됐는지, ② 라이브 데이터가 흐르는 길과 저장 경로와의 관계, ③ 화면이 무엇을 약속하고 무엇을 약속하지 않는지, ④ 어디까지 만들었고 어디까지 검증됐고 무엇이 남았는지, ⑤ 고객 서버에서 이것을 실제로 켜려면 무엇을 해야 하는지 알게 된다.

**P5가 P1~P4와 다른 점 한 줄**: P1~P4가 *"굳힌 값을 DB에서 읽어 보여 주는"* 화면이라면, P5는 *"DB를 한 번도 거치지 않고 메모리에서 SSE로 흘리는"* 화면이다. 그래서 창이 15분이고, 서버를 재시작하면 빈 화면에서 다시 시작하며, 과거를 조회할 수 없다.

### 10.1 왜 만들었나 — 제니퍼 대조에서 나온 격차 셋

사용자가 요구한 것은 "제니퍼가 보여 주는 세 화면"이었다. 그래서 먼저 **그 화면들이 요구하는 데이터 특성**을 우리 자산과 한 줄씩 맞춰 봤고(설계 §1), 격차는 셋으로 정리됐다.

| 제니퍼 화면 | 답하는 질문 | 필요한 데이터 | 우리가 이미 가진 것 | 🔴 격차 |
|---|---|---|---|---|
| **실시간 X-View** | 지금 어떤 요청이 느린가·오류인가 (점 하나 = 요청 하나) | 완료 HTTP SERVER 요청의 (종료 시각, 지연, 상태, 서비스, route, traceId·spanId) — **1초 갱신** | 트레이스 산점도(`ApmScatterDto`) — 그러나 **tail 2% 샘플·DB 조회**다 | 샘플이면 점이 50배 성기고 **"정상은 안 보이는 산점도"**가 된다. 전량 수신·스트리밍이 없다 |
| **실시간 액티브 서비스** | 지금 몇 개가 처리 중이고 얼마나 오래 걸리고 있나 (목록·경과) | **시작했지만 안 끝난** 요청 | `http.server.active_requests` **개수**(Java만·export 주기 10~60초) | 목록·경과가 없고 **시작 이벤트가 없다**. 게다가 인스턴스 합산이 안 돼 3대 중 1대 값만 보였다 |
| **속도계·이퀄라이저·게이지** | TPS·응답시간·오류율이 지금 얼마인가 | 1초 집계(count·p95·오류율) | P1.5 Live의 **10초 칸**(`LiveBuffer`) | 해상도 10초 → 1초가 필요하고, ✅ 화면 도달 중앙값 **14초**·최악 **23초**(Live QA §B)를 수 초로 줄여야 한다 |

**여기서 나온 결정 두 가지**
1. X-View·대시보드는 **스팬 전량 수신**이 필요하고, 그것은 **tail 샘플링 앞**에서만 얻는다 → Collector 파이프라인을 갈라야 한다(§10.3).
2. 액티브 요청과 리소스는 **상류가 정하는 지연**(스팬 종료 후 export·메트릭 export 주기)을 화면이 넘을 수 없다 → 숫자를 꾸미지 말고 **문구로 정직하게** 말한다(§10.4·§10.5).

⚠️ 제니퍼 쪽 서술은 **제공 자료에서 확인된 범위**다. 구간 경계를 고객이 바꿀 수 있는지 같은 항목은 **추정**으로만 적었고, "제니퍼에는 없는 요소"라는 비교 주장은 근거가 없어 UX 정본에서 삭제했다.

### 10.2 한 줄 결론과 🔴 "전량"의 3분리

**한 줄 결론(정본 §0 원문)**
> 실시간은 "등록·승인·인증·유효성 조건을 충족한, Collector에 도달한 **완료 HTTP SERVER 스팬**" 전체를 처리 대상으로 **수신·집계**하되, 서버는 예산 안에서 **표본을 보관**하고 브라우저는 그 중 **표본을 표시**하며, **전부 휘발**한다. 트레이스 분석은 지금처럼 샘플·보존한다(메트릭 집계는 이미 전량이다).

이 문장이 이렇게 길어진 이유가 P5 설계에서 가장 많이 고쳐진 대목이다. v0의 "실시간은 전량·휘발, 분석은 샘플·보존"은 **두 군데가 틀렸다**.
- (1) **메트릭 분석은 이미 전량**이다 → "분석"은 **트레이스** 분석으로 한정해야 한다.
- (2) **"전량"은 수신·집계의 약속이지 표시의 약속이 아니다.** v1의 "1,500점/초까지 화면 전량 표시"는 산술 반례로 폐기됐다 — 1,500점/초 × 5분 = **450k점**인데 브라우저는 **300k점부터 솎는다**(§10.7 R4 미측정).

그래서 "전량"을 층으로 쪼갰다. 🔴 **각 층의 숫자를 섞으면 거짓말이 된다.**

**제품 문구(고정)**: *"정상 지원 부하에서 적격 수신 관측 전체로 통계를 계산합니다. X-View는 서버 보관량·선택 시간 창·브라우저 처리 한도에 따라 표본을 표시하며, 각 단계의 관측 수와 표시 수를 제공합니다."*

| 층 | 약속(숫자는 그 층의 것이다) | 화면이 보여 주는 값 | ⚠️ 이 층이 책임지지 않는 것 |
|---|---|---|---|
| **수신 대상** | 등록·승인·인증·유효성 조건을 충족한 **Collector 도달 완료 HTTP SERVER 스팬 전체** | — | 🔴 **"전체 실제 요청"이 아니다.** SDK 샘플러·SDK 큐 초과·프로세스 종료·계측 제외 경로의 상류 유실은 Collector에 닿지도 않는다 |
| **수신 처리율** | 지원 상한 **1,000 SERVER/초(L2)** 에서 정상 상태 유실 < 0.1% | 수집기 탭 카운터 | ✅ 실측은 **L2′ ≈ 600 SERVER/초 × 10분에서 유실 0.0000%(347,830건, 반복 4회 전부 0)**. 🔴 QA 호스트 부하 천장이 600/초라 **L2(1,000)·L3·L5는 미도달** — 그래서 지금 쓸 수 있는 문구는 **"합성 Collector 경로에서 약 600 SERVER/초 구간을 관측"**뿐이고, "제품 600/초 지원 검증"도 쓰지 않는다 |
| **집계**(TPS·오류율·p95·패턴) | 수신·dedup·유효성 통과 **전체 관측**으로 계산 — 표본에서 계산하지 않는다 | `stats.count` | 🔴 표본에서 오류율을 내면 오류율이 올라간다(강조 계층이 오류·느림만 담으므로) |
| **서버 보관 — 기본 계층** | 서비스당 **200점/초** · 전체 **1,300k점**(15분). 초과는 서비스·초별 **층화 reservoir**(균등) | 버킷별 `observed/retained` | 예산 압박 시 무작위 축소 + `pointsRev` 상승 |
| **서버 보관 — 강조 계층** | 오류·느림 점은 별도 예산 — 전역 **50k점**·서비스당 20k점 | 버킷별 `observed/retained` | 초과 시 그 계층도 초별 reservoir |
| **전달(연결)** | 연결별 바이트 상한 안에서 보관분을 보낸다. 넘치면 **그 연결만** 1/k 솎음 | 버킷별 `delivered`·`clientKeepRatio` | 다른 연결은 영향 없다 |
| **브라우저 표시** | 선택 시간 창(기본 5분)·브라우저 처리 한도(**잠정 300k점 — R4 확정 전**) 안의 표본 | 배지 `표시 n / 관측 m` **상시** | 🔴 **"화면 전량"은 어느 부하에서도 약속하지 않는다** |
| **대상 스팬** | 첫 출시는 **HTTP SERVER만**(Collector filter `kind==Server ∧ HTTP 판별`) | — | CLIENT·INTERNAL·PRODUCER·CONSUMER는 점이 되지 않는다. 메시징을 SERVER만으로 지원한다고 말하지 않는다. RPC/OTHER는 **P5.5 후속** |

🔴 **이 표가 화면 문구를 지배한다.** X-View 상단의 `표시 4,812 / 관측 12,930` 배지가 상시인 이유도, 브러시 표 제목이 "선택 영역의 **표시 표본**(n / 관측 m)"이지 "요청 목록"이 아닌 이유도 전부 여기서 나온다.

```text
        └─ LiveSpanArena  45B 슬롯 · 전역 base 1,300k / emphasis 50k · 초별 층화 reservoir  ← 표본은 여기서 깎인다
        └─ LiveSpanDictionary  20 MiB 예산 · 🔴 ID 네임스페이스는 **서비스별**
        ▼
   GET /apm/live/spans/stream  (SSE, 1초 tick)
        snapshot.begin → dict chunk → buckets chunk → snapshot.end(CRC32) → spans(1초) / heartbeat(5초) / control
        ▼
   화면: 실시간 관제 ?tab=active(요청 관제) · ?tab=xview(X-View)
```

**관문별 "왜 이 자리인가"**

| 관문 | 왜 여기인가 | 🔴 어기면 |
|---|---|---|
| **tail 샘플링 앞에서 분기** | `traces/live`가 `decision_wait 10s`를 **타지 않는다**. 이것이 "지연이 초 단위가 되는" 유일한 이유다 | 뒤에서 갈라면 라이브도 10초를 기다리고, 2% 샘플만 남아 X-View의 전제가 무너진다 |
| **filter(HTTP SERVER만)를 정리보다 앞** | ✅ 실측 SERVER 비율 **11.6%**(3,000,169 수신 → 347,830 live) — 88%를 먼저 버려야 뒤 단계 비용이 준다 | 전체 스팬에 정리 문장을 돌리면 CPU가 그만큼 는다 |
| **`keep_keys` 정리 → `redaction` → `filter/live-safety` 순서** | keep_keys는 **키만** 거른다. 값 안의 PII는 redaction이, 속성이 아닌 필드(`status.message`·`scope.name`·`schemaUrl`)는 live-safety가 막는다 | ✅ 설계 v2 원문 그대로 돌렸을 때 **4종이 그대로 유출**됐다(§10.7 R1-2) |
| **`error_mode: ignore` (propagate 금지)** | transform이 오류를 상류로 반환하면 fan-out이 그것을 receiver에 돌려주고, **저장 분기가 오염된다** | ✅ `propagate`에서 SDK 503 × 5,176 → 재전송 3,882 → `apm_span` **중복 26,769건(고유의 300%)**(§10.7 R2-8) |
| **BE 수신 관문이 저장 관문과 아무것도 공유하지 않음** | 🔴 라이브 hot path는 영수증(`apm_otlp_receipt`)도, 폐기 통계 테이블도, 파티션도 만지지 않는다 | 공유하는 순간 라이브 장애가 저장을 503으로 만들고, 503은 재전송 → **1m 두 배 사고**(P1.5 Live 설계 §2)로 이어진다 |
| **집계(전체 관측)와 표본(arena)을 분리** | 통계는 깎기 **전에** 나오고, arena는 통계에 영향을 주지 않는다 | 표본에서 오류율을 계산하면 강조 계층 때문에 오류율이 올라간다 |
| **SSE 발행은 tick 불변 상태 위에서만** | 1초 tick이 끝난 뒤의 고정된 상태를 내보내야 `seq`·`pointsRev`·`statsRev`·체크섬이 일관된다 | 발행 중 변하는 상태를 흘리면 snapshot 체크섬이 안 맞고 재접속이 반복된다 |

⚠️ **이중 전송이 이 설계의 비용이다.** 스팬 하나가 Collector에서 두 번 처리되고, SERVER 스팬은 두 번 export된다(하나는 깎인 것).

#### (1) 요청 관제 탭(`?tab=active`) — "지금 얼마나 들어오고 얼마나 걸리고 얼마나 실패하나"

🔴 **탭 이름이 "액티브"가 아니라 "요청 관제"인 이유**: 첫 출시의 이 탭은 **방금 끝난 요청의 1초 집계**이지 진행 중 목록이 아니다. OTel 스팬은 끝나야 export되기 때문이다(§10.5).

| 부품 | 답하는 질문 | 데이터 출처 | 갱신 리듬 | 🔴 함정 |
|---|---|---|---|---|
| **속도계 3종**(TPS·p95·오류율) | "전체가 지금 얼마나 바쁘고 느리고 실패하나" | SSE `stats`를 창 안 서비스 전체로 합산 — 오류율은 기본 `http5xx/count`, 토글 `spanError/count`(10초 이동 창) | 1초 | p95는 15칸 히스토그램 근사라 **"약 N ms"**로만 적고 소수점을 쓰지 않는다 · 최신 1초 칸은 `provisionalUntil` 전까지 **잠정**(해칭) · 참고선은 `config.p95ThresholdMs`·`config.errorRateThresholdPct`가 **있을 때만** 그리고 `null`이면 **대체값을 만들어 내지 않는다** |

#### (2) X-View 탭(`?tab=xview`) — "지금 어떤 요청이 느린가·오류인가"

| 부품 | 답하는 질문 | 데이터 출처 | 🔴 함정 |
|---|---|---|---|
| **스트리밍 산점도** | "점 하나 = 요청 하나로 보면 지금 무슨 모양인가" | `LiveSpanPoint` 튜플 — 기본 계층 OK/SLOW/ERROR 3계열 + **강조 계층** SLOW/ERROR 2계열(다른 기호). x축 = **스팬 종료 시각**, y축 = 로그 지연 | 🔴 `large: true`는 계열 단위 itemStyle만 적용 → **점마다 색을 바꾸면 large 모드가 깨진다**(기호 = 계층, 색 = 상태) · 갱신은 `appendData`가 아니라 **버킷 교체 + `replaceMerge`**(지울 수 없고 `dataset`과 못 쓰며 버킷 계약과 안 맞는다) · zoom·brush·선택은 옵션 재구성 때 **보존 계약** · 오른쪽 끝은 `serverTime`(브라우저 시계 아님) |
| **상시 배지 "표시 n / 관측 m"** | "내가 보는 점이 전체의 얼마인가" | `n` = 실제 그린 **고유 `(traceId, spanId)` 수** · `m` = 창 안 버킷의 **`stats.count` 합** | 🔴 **`base.observed + emphasis.observed`를 더하면 같은 요청을 두 번 센다**(v0가 412를 417로 셌다) · `retainedSlots`는 **슬롯 수**이지 고유 요청 수가 아니다(겹침 포함) · 🔴 이 줄은 wall·좁은 화면에서도 **접지 않는다** |
| **브러시 → 표** | "이 영역의 요청들을 목록으로" | 선택 범위를 **클라이언트 버킷에서 필터**(서버 왕복 없음) → `DmoveTable` | 🔴 제목은 **"선택 점 n건"** + 보조 줄 **"같은 시간대 전체 관측 약 m건 — 지연·경로·인스턴스 조건 미반영"**. **"요청 목록"이라 부르지 않는다** · 분모 m은 시간 범위만 반영한다(`hist[15]`가 있어도 route/instance 분해는 없다) · `hasQuery={false}`(기본 `true`는 공용 페이지 query를 먹는다) · `rowKey = traceId:spanId` |
| **점 클릭 → 사이드 패널** | "이 요청의 트레이스를 볼 수 있나" | `GET /apm/traces/{traceId}` 상태 머신 `unknown → checking → stored \| stored.spanMissing \| notFound(.pending) \| forbidden \| error` | 🔴 **HTTP 200 자체를 `stored`로 보지 않는다**(envelope 업무 성공 + 유효 detail일 때만) · 점의 정체성은 `(traceId, spanId)`라 trace가 있어도 그 span이 없으면 `stored.spanMissing` · 🔴 `notFound`는 **종착 상태가 아니다**(어느 나이에서도 "다시 시도") · 🔴 **20초로 "미저장 확정"을 선언하지 않는다** · 문구는 "현재 저장된 트레이스를 찾지 못함" + "정상 요청은 일부만 저장됩니다"("정상 2%"라고 쓰지 않는다) |

| **패턴 라벨 오버레이**(P5.4 후속) | "완료 시각이 몰렸나·고정 지연 띠가 있나·상승 추세인가·오류가 한 곳에 몰렸나" | `patterns[]` 4종 | 🔴 **패턴은 원인이 아니라 "관측 특징"이다** — 라벨에 "GC"·"잠금" 같은 원인을 쓰지 않는다 · 우리 4종은 **제니퍼 공식 4패턴과 같지 않다**(도움말에 명시) · `confidence`는 통계적 신뢰도가 아니라 **휴리스틱 점수**라 화면이 "신뢰도"라 부르지 않는다 · 🔴 현재 BE가 `patterns{}`를 **빈 맵으로 보낸다**(§10.8) |

**정직성 규칙 — 이 탭의 모든 문구가 따르는 것**
- 🔴 **관측 없음 ≠ 0**: 데이터가 안 온 것과 값이 0인 것은 다른 상태다. 타입으로도 가른다(`tps: number | null`).
- 🔴 **표시 n / 관측 m**: 어느 숫자가 어느 층인지 항상 붙인다.
- 🔴 **완료 처리량이지 유입이 아니다**: 1초 막대가 움직이는 것은 "지금 들어온 요청"이 아니라 "방금 끝난 요청"이다.
- 🔴 "초 단위"·"실시간(1초)"라고 쓰지 않는다. 갱신 리듬은 부품 제목 옆 작은 글씨로만 적는다.

#### (3) 비동기 모니터링(P5.6) — 트레이스 상세 워터폴 확장

데이터 원천이 라이브가 아니라 **이미 저장된 트레이스(샘플)**라 라이브 파이프라인과 **무관**하고, 그래서 P5.1을 기다리지 않고 먼저 출시됐다. 요소별 사전(🔗 링크 팝오버·⇢ 부모 종료 이후 종료 마커·불확실 배지·요약 줄·관련 스팬만 보기·복귀 브레드크럼·kind별 자기 시간)은 [05-menus-and-tabs.md](solutions--05-%EB%A9%94%EB%89%B4-%ED%83%AD-%EC%82%AC%EC%A0%84-%EC%9D%B4-%ED%99%94%EB%A9%B4%EC%9D%80-%EB%AC%B4%EC%8A%A8-%EC%A7%88%EB%AC%B8%EC%97%90-%EB%8B%B5%ED%95%98%EB%82%98.md) **4.5.1a**에 있다.

🔴 **"비동기"를 3층으로 쪼갠 것이 이 화면의 핵심 결정**이다 — v2의 "3종 분류"는 폐기됐다.

### 10.5 🔴 못 하는 것과 그 이유

이 절이 P5에서 가장 중요한 절이다. **"왜 제니퍼처럼 안 되나"라는 질문이 나올 자리를 미리 적어 둔 것**이고, 화면 문구도 전부 여기서 나온다.

| 못 하는 것 | 🔴 왜 |
|---|---|
| **진행 중 요청 목록**("지금 처리 중인 요청 N건의 경과 시간") | **스팬은 끝나야 export된다.** OTel 스팬의 수명은 `end()` 시점에 배치 큐로 들어가므로, 진행 중인 요청은 어떤 exporter에도 나타나지 않는다. → 가능한 유일한 길은 **Java 에이전트 확장 jar**이고 그것이 **P5.3b**다. ✅ **2026-09-22~23에 만들었다**(§10.10) — 단 **자바 + 확장 jar를 붙인 서비스만**이며, 원리는 그대로다(다른 언어·확장 없는 서비스는 여전히 못 한다) |
| **유입 곡선**("초당 몇 건이 들어왔나") | 같은 이유. 우리가 셀 수 있는 것은 **완료 처리량**뿐이다. 그래서 이퀄라이저 제목이 "완료 처리량"이고, 긴 요청이 몰리면 유입은 늘었는데 완료 곡선은 **내려간다**. ✅ 확장이 있는 서비스는 예외 — 확장이 초당 시작·종료 수를 세어 보내 무대의 "들어오는 공·나가는 공"이 된다(§10.10) |
| **경과 구간별 스택 이퀄라이저**(제니퍼의 0~1s/1~3s/3~8s/8s+ 색 구간이 쌓이는 모습) | `active.value`는 **개수 하나**뿐이라 경과 구간별로 쌓을 수 없다. 시작 이벤트(P5.3b)가 있어야 가능. ⚠️ 2026-09-17에는 완료 요청 지연 구간 차트(10.5.1)로 절반만 만들었고, ✅ **2026-09-22~23 확장으로 나머지 절반을 만들었다** — 요청 흐름 무대의 동전(파랑·주황·빨강 = 1초 미만·1~5초·5초 이상)이 그 그림이다(§10.10). 확장 없는 서비스는 여전히 못 한다 |
| **"T 시점에 진행 중이던 요청"을 완료 스팬으로 역산** | 🔴 **현재 액티브로 사용 금지.** 오래 걸리는 요청일수록 늦게 보이므로 "지금"을 말할 수 없다. 이름을 붙인다면 "완료 요청으로 재구성한 과거 동시성"뿐이다 |
| **메서드 프로파일링**(제니퍼 "메서드 레벨 스택") | OTel profiling 시그널이 **실험 단계**다([03-constraints.md](solutions--03-%EA%B5%AC%ED%98%84-%EC%A1%B0%EA%B1%B4-%EC%A0%84%EC%A0%9C-%EC%9A%B0%EB%A6%AC%EA%B0%80-%EC%A7%80%ED%82%A4%EA%B8%B0%EB%A1%9C-%ED%95%9C-%EA%B2%83.md) §3.8 비범위와 같은 판단). 자동계측 **스팬 단위까지만** 본다 |
| **다중 BE 노드 합산** | 링·arena·사전이 전부 **한 프로세스의 인메모리**다. 첫 배포 = **BE 전체 1대**(현 실서버: FE 아파치 1대 + BE·AI 도커 1대). 승격하려면 ① 모든 Collector의 live traces가 같은 노드로 ② 브라우저 snapshot·SSE·재접속도 같은 노드로(sticky만으로는 부족, **경로 기반 라우팅**) ③ 🔴 **액티브·CPU·heap 메트릭도 그 노드의 메트릭 링으로**(이것이 v1이 빠뜨린 조건 — 메트릭은 다른 노드로 갈 수 있다) ④ 토큰·라이선스 변경 지연 명시 ⑤ 롤링 중 분할 상태 방지 ⑥ ingress·프록시 실경로 검증 — **여섯을 전부** 충족해야 한다 |
| **라이브 스팬의 DB 저장·과거 조회** | 1,000 SERVER/초면 **86.4M건/일**이다(§10.3). 15분 지나면 없다 — 과거는 트레이스 탐색(샘플)의 일 |
| **비-HTTP SERVER(RPC·메시징) 점** | 첫 출시는 Collector에서 **전송 자체를 제외**한다. `stats`가 서비스별 하나라 RPC를 섞으면 TPS·p95가 오염된다. protocol별 분리는 **P5.5 후속** |
| **라이브 데이터로 알람** | 알람은 1m 집계 엔진(`ApmAlertKind` 6종)이 그대로 한다. **실시간 화면은 보는 화면이다**. ⚠️ **예외 하나(2026-09-23)** — 확장의 처리 중 목록으로 판정하는 `STUCK_REQUEST`(요청 걸림)만 1초 감시기가 판정한다(§10.10.4). 스팬 스트림·X-View로는 여전히 알람하지 않는다 |
| **표시 표본에서 계산한 통계** | 오류율·p95·패턴은 **전체 관측에서만**. 표본에서 계산하면 강조 계층 때문에 오류율이 올라간다 |
| **초 단위 CPU·메모리·스레드** | **원리적으로 불가** — 메트릭 export 주기(10~60초)가 알갱이다. 🔴 화면이 1초 갱신되는 스팬 집계와 같은 속도로 보이게 **꾸며서는 안 된다**(게이지 옆 "약 1분 이내") |
| **자체 에이전트·자체 프로토콜** | OTel 단일 원칙. Java 확장 jar도 공식 확장 지점이긴 하나 **고객 JVM에서 우리 코드가 도는 지원 범위**가 새로 생기므로 **제품 결정을 따로** 받는다 |
| **완전한 링크 그래프**(P5.6) | 적재 상한 **32개/스팬**이고 DTO에 **절단 여부가 없다** → 요약은 항상 "**응답에 포함된** 링크 L개" |

🔴 그리고 화면이 스스로 적는 한 줄: **"이 응답에서 발견되지 않음" ≠ "없음"**. ✅ R-P5.6 실측에서 javaagent 2.31.1의 `@Async`·CompletableFuture는 **14구성 1,400요청 전건 링크 0%**였다([부록 B](solutions--15-%EB%B6%80%EB%A1%9D-B.-%EC%9D%B4-%ED%94%84%EB%A1%9C%EC%A0%9D%ED%8A%B8%EA%B0%80-%EB%92%A4%EC%A7%91%EC%9D%80-%EA%B0%80%EC%A0%95-%EC%8B%A4%EC%B8%A1-%EA%B2%80%EC%88%98%EA%B0%80-%EC%84%A4%EA%B3%84%EB%A5%BC-%EB%B0%94%EA%BE%BC-36%EA%B0%80%EC%A7%80.md) #27).

#### 10.5.1 그래서 대신 만든 것 — 완료 요청 지연 구간 차트 `[2026-09-17]`

진행 중인 요청을 구간별로 쌓는 그림은 못 만든다. 대신 **이미 끝난 요청**을 걸린 시간대로 갈라
쌓는 차트를 요청 관제 탭에 넣었다(`0~100 ms / 100~500 ms / 500 ms~1 s / 1~5 s / 5 s 초과`).

- 🔴 **이것은 "지금 처리 중"이 아니다.** 제목·각주·도움말이 전부 그렇게 적는다. 두 그림은 모양이
  비슷해서 설명이 없으면 반드시 오독된다.
- 🔴 **산점도와 모집단이 다르다 — 그게 이 차트의 존재 이유다.** 산점도의 점은 버킷마다 상한이
  걸린 **표본**이지만, 이 차트가 쓰는 `stats.hist`는 수신 관문을 통과한 **전량**에서 센 것이다.
  점이 잘려 나간 구간에서도 분포는 온전하다. **두 화면의 숫자가 다른 것은 오차가 아니다.**
- 구간 경계는 히스토그램 칸 경계 위에만 놓아 **보간이 0**이다.
- 막대가 없는 자리는 "완료 0건"이 아니라 **그 칸을 받지 못했다**는 뜻이다.

같은 날 **액티브 요청 목록의 문구도 고쳤다.** 예전 문구는 "진행 중 요청 목록을 제공하는
서비스가 없습니다"였는데 이건 고객사 서비스를 탓하는 말이다 — 사실은 **우리가 아직 만들지 않은
기능**이다. 지금은 무엇이 없어서 못 만드는지를 적고, 설치로 해결되지 않으므로 수집기 링크도 뺐다.

### 10.9 운영자가 켜는 법 — 스위치 넷

🔴 **P5는 기본적으로 전부 꺼져 있다.** 넷 중 하나라도 빠뜨리면 조용히 안 되거나, 더 나쁘게는 **PII가 전송된다**.

| # | 스위치 | 어디서 | 기본값 | 🔴 빠뜨리면 |
|---|---|---|---|---|
| 1 | **BE 라이브 수신** `app.apm.live.spans.enabled` | BE 설정 | **false** | 인증은 통과하고 **503 `APM_LIVE_DISABLED`**(OTLP 본문) + `disabled` 계수. Collector가 계속 실패 로그를 남긴다 |
| 2 | **수집기 설정의 라이브 옵션**(`liveSpans`) | `POST /apm/collector-config` 생성 요청 | **꺼짐** | 생성 yaml에 `traces/live` 블록이 아예 없다 = 어떤 Collector도 `/apm/otlp-live/**`로 보내지 않는다. 🔴 꺼짐일 때 **기존 생성물은 한 바이트도 바뀌지 않는다**(회귀로 고정) |
| 3 | **Collector 실행 명령의 feature gate** `--feature-gates=ottl.set.allowNil` | Collector 서비스 실행줄(3개 OS 전부) | 없음 | 🔴🔴 **가장 위험한 누락.** `span.events`·`span.links` 정리가 **오류·경고 없이 무시**돼 스택트레이스·예외 메시지·링크 속성이 **그대로 전송**된다(✅ 실측: PII 3종 추가 유출 + 전송량 **+47%**). 그래서 생성 yaml 상단에 이 경고 문구를 **그대로 박아** 출력한다. ⚠️ gate OFF 신호는 **프로세스 수명당 WARN 1회**뿐이고 **파이프라인·컴포넌트 라벨이 없다** — 알람은 "이 Collector에 gate가 빠졌다"까지만 말할 수 있다 |
| 4 | **SDK 지연 프로필** `OTEL_BSP_SCHEDULE_DELAY=1000` (+ `OTEL_BSP_MAX_QUEUE_SIZE` 짝) | 앱 실행 환경변수 | BSP 기본 5,000 ms | 🔴 **저트래픽 서비스(10/초)의 완료→캡처 p95가 5,727 ms**다. 화면 문구 "약 2초"가 거짓이 된다 — 그래서 문구가 **"권장 설정 시"**를 반드시 달고 있고, 이 말을 빼면 거짓말이 된다. ⚠️ 이것은 **설정 요건**이지 실측 보장이 아니다(R7 전) |

| 5 | **자바 확장 jar**(진행 중 요청·요청 걸림 — 선택) `-javaagent:opentelemetry-javaagent.jar -Dotel.javaagent.extensions=moveseye-otel-extension-0.2.0.jar` | 앱 JVM 실행줄 | 없음 | 요청 관제 탭의 **진행 중 요청 카드가 "확장 없음"**으로 뜨고 요청 걸림 규칙은 아무것도 재지 않는다(빈 것이 정상 — 0건이 아니다). 상세는 §10.10.6 |

**이미 설치된 수집기를 라이브로 바꿀 때** — 6단계가 설치 가이드에 **기존 설치 갱신 절차**를 넣어 두었다: 새 yaml 받기 → 실행줄에 `--feature-gates` 추가 → 서비스 재시작. 실행줄만 바꾸고 yaml을 안 바꾸거나 그 반대면 반쪽이 된다.

**켠 뒤에 볼 것 — 수집기 탭 라이브 카드**(`GET /apm/collectors/{id}/live`, 6단계·**V59**)

| 신호 | 뜻 | 🔴 읽는 법 |
|---|---|---|
| `statement_warn` / `condition_warn` | OTTL 문장 실행 실패 / 조건 평가 실패 WARN 계수(component·pipeline별) | 🔴 **WARN 수 ≠ 손실 수** — Collector 내부 로그가 샘플링된다(✅ 실측: 13,196스팬 전부 실패인데 WARN **170줄**, 1,337 실패에 **52줄**). "발생 여부·규모"의 신호일 뿐이다 |
| `gate_warn` | feature gate 누락 안내 | 프로세스 수명당 **1회**. 0이 정상이 아니라 **"안 뜬 것"**일 수도 있다 |
| **`condition_warn{pipeline=traces/live} == 0`** 알람 | live-safety 게이트에 구멍이 뚫렸는지 | 🔴 **판정 불가 구간이 있다** — 건강한 Collector는 이 WARN을 애초에 안 쓰므로, 로그 수집이 죽으면 값이 "0"이 아니라 **`null`(결측)**이다. **결측을 정상 0으로 표시하지 않는다** |
| `filter/live-safety` 차단 수 | 정리 결과 위반으로 전송 전에 막힌 스팬 | ✅ 이것만은 **정확한 전용 카운터**다(`otelcol_processor_filter_spans_filtered{filter="filter/live-safety"}`). 단 **어느 조건에 걸렸는지는 모른다**(프로세서 단위) → BE 카나리아 `slimBypassed{reason}`과 나란히 읽는다 |
| 라이브 exporter `enqueue_failed` + `send_failed` | 전송 실패 신호 | 🔴 **둘을 합산**해서 본다(하나만 보면 절반을 놓친다) · 이것을 **"종단 유실 수"라고 부르지 않는다**(timeout 뒤 BE가 이미 수용했을 수 있고 partialSuccess·processor 실패가 빠진다) · 🔴 라이브 exporter는 **큐 5·재시도 없음**이라 설계상 실패가 정상 — 기존 **저장 전송 실패 집계에서 제외**돼 있다 |

> 이 절을 읽으면: ① §10.5가 "못 한다"고 적은 진행 중 요청을 **어떤 길로 만들었는지**(스팬이 아니라 에이전트 확장), ② 화면 다섯 부품이 각각 어느 층의 숫자를 보여 주는지, ③ 상한이 어디에 몇 개인지(확장·BE·스트림), ④ 임계를 넘긴 요청이 **장부와 알람**으로 남는 길, ⑤ 코덱스 검수가 무엇을 바꿨는지, ⑥ 켜는 법과 아직 안 한 것을 알게 된다.

**한 줄**: OTel 스팬은 끝나야 export되므로(§10.5) 진행 중 요청은 **에이전트 안에서 요청의 시작·종료를 직접 세는 확장 jar**로만 볼 수 있다. 확장은 1초마다 ① 경과 구간 분포(메트릭) ② 초당 시작·종료 수(메트릭) ③ 가장 오래된 처리 중 요청 N건(로그 한 줄)을 **기존 OTLP 파이프라인**으로 보내고, BE는 **저장하지 않고** 메모리에만 두어 SSE로 흘린다. 임계(기본 60초)를 넘긴 요청만 **요청 걸림 장부**(`apm_stuck_request`)에 요청 단위로 남고, 서비스 단위 알람 이벤트·Zabbix로도 나간다.

#### 10.10.4 요청 걸림 장부 — 임계를 넘긴 요청은 사람이 봐야 한다 `[2026-09-23]`

사용자 요구: *"쌓여 있는 장애도 결국 사람이 처리해야 하니 임계치를 걸고 넘은 요청은 우리 장애 로그로 하자."* 결정: 임계 **설정 가능, 기본 60초**(BE 자체엔 처리 시간 제한이 없고 앞단 프록시 nginx·Apache·ALB가 끊는 시간이 60초), 장부는 **기존 알람 이력·Zabbix + APM 전용 탭** 둘 다.

| 요소 | 무엇 | 🔴 규칙 |
|---|---|---|
| 규칙 종류 `STUCK_REQUEST` | 단위 ms · priority 4 · Zabbix 키 `apm.stuck_request[<svc_uid>]` · 트리거 `>0` | V67이 전역 기본 규칙 1건(60,000ms)을 시드. `windowMin`은 **쓰지 않는다**(경과 자체가 지속 조건 — 60초를 넘겼다 = 60초 이어졌다). 미리보기 없음(근거를 저장하지 않는다) |
| 1초 감시기 `ApmStuckRequestMonitor` | `LiveBuffer.runtimeSnapshot`의 목록에서 `elapsedMs ≥ 임계`인 요청을 **요청 단위**로 장부에 연다 | 닫는 이유 셋: **ENDED**(새 목록에 없다=끝났다) · **LOST**(15초 못 봄 — 끝났는지 모른다) · **RULE_OFF**. DB는 열고 닫을 때 + 15초 flush만. 재기동 시 열린 행 복원. 🔴 첫 tick `nowMs − Long.MIN_VALUE` 오버플로 함정 |
| 장부 `ApmStuckRequestLedger` | 서비스에 걸린 요청 0→N이면 `apm_alert_event` 열고 Zabbix에 최대 경과 ms push, N→0이면 닫고 0 push | 중복 억제는 5분 배치와 같다(열린 이벤트가 있으면 새로 안 연다). 5분 배치도 `monitor.currentValue`(empty=관측 없음·0=정상·양수)로 같은 규칙을 맞춘다 — 이 kind의 대상을 배치가 건너뛰면 고아 정리가 트리거를 내린다 |
| 장부 표 `apm_stuck_request` | 서비스·인스턴스·method·가려진 path·trace/span·감지 시각·감지 시 경과·최대 경과·마지막 관측·**그때 하던 일**·닫힌 시각·이유 | `resolved_at` null = 걸려 있음(0·epoch 금지, ZM-99 교훈). 보존 `stuckRequestDays` 90(닫힌 행만 삭제) |
| EP `GET /apm/stuck-requests` | serviceUid·from/to(감지 시각)·open·limit≤500·offset | **읽기 권한**(운영자 장부 — 알람 이력의 편집 축과 다르다) |
| 화면 | 알람 규칙 화면 4번째 탭 **"요청 걸림"**(`?tab=stuck`) — 서비스·"걸려 있는 것만" 필터, 상태(걸림/끝남/관측 끊김/규칙 꺼짐), 요청, 감지, 경과(감지 시/최대), 임계, 그때 하던 일, 인스턴스, trace(→ 저장된 트레이스 드로어) | 알람 이력은 **서비스 단위**, 이 탭은 **요청 단위** — 같은 사건을 두 축으로 본다. "관측 끊김"은 끝났다는 뜻이 아니다 |
