# 폐쇄망 라이선스 — 서명 기반 enforcement의 원리와 함정

> 출처: [[projects/moveseye/2026-08-06-license-kernel-design|2026-08-06-license-kernel-design]](설계) · [[projects/moveseye/2026-08-10-license-kernel-implementation|2026-08-10-license-kernel-implementation]](구현·검증)
> · [[projects/moveseye/2026-08-12-license-expiry-in-key|2026-08-12-license-expiry-in-key]](만료 정본 이관). 대비: [[topics/forge/forge-licensing|forge-licensing]](Atlassian 호스팅 앱 — 정반대 환경)

인터넷이 없는 고객사에 설치되는 제품은 **본사에 물어볼 수 없다.** 그래서 방향을 뒤집는다 —
**증명서에 미리 다 적어두고, 위조만 못 하게 만든다.** 여기서 오는 제약과 함정을 정리한다.

---

## 1. 대칭키(HS256)를 쓰면 안 되는 이유

로그인 토큰은 **만드는 쪽과 검증하는 쪽이 같은 서버**라 비밀문자열 하나로 충분하다.
라이선스는 **만드는 곳(본사)과 검증하는 곳(고객사)이 다르다.** 여기에 대칭키를 쓰면
검증용 비밀값을 제품에 넣어야 하는데, **그 값이 곧 키를 발급하는 능력**이다.

```
개인키(본사)   서명 O, 검증 O   →  발급기에만
공개키(제품)   서명 X, 검증 O   →  고객에게 줘도 안전
```

같은 JWT 규격이라도 **알고리즘 선택이 신뢰 경계 설계**다. 페이로드는 인코딩일 뿐 암호화가 아니므로
**내용을 숨기려 하지 말고 못 고치게** 만든다.

## 2. 🔴 판정 값의 정본을 한 곳으로 — DB는 표시용 사본

가장 흔한 구멍: 등급·기능은 매 요청 키에서 꺼내면서, **만료일만 등록 시점에 계산해 DB에 적는 것.**
`UPDATE ... SET expires_at = '2126-01-01'` 한 줄로 무한 연장된다.

> **값마다 "정본이 어디인가"를 표로 그려라.** 화면에서 나란히 보이는 값들이 서로 다른 신뢰 경계에서
> 온다는 사실은 코드를 훑어서는 안 보인다. 실제로 이 구멍은 *리뷰가 아니라 "쉽게 설명해 봐"* 요구에서 드러났다.

DB 컬럼을 지우지 말고 **표시·정렬용 사본으로 남기되, 컬럼 코멘트에 "판정은 키를 재검증한다"를 박아둔다** —
DBA가 스키마만 봐도 헛수고임을 알아야 한다.

## 3. 유연성은 제품이 아니라 발급 시점에 둔다

"계약 3월·설치 5월"의 손해를 막으려고 **등록일부터 기간 계산**을 넣고 싶어진다. 그 대가가 §2다.
대신 **발급기에 시작일 입력을 두고 미래 날짜로 발급**한다. 더 밀리면 재발급 — 우리가 하는 일이라 비용이 0.

> 일반 원칙: **런타임에서 계산해야 유연한 것처럼 보이는 값은, 발급 시점으로 옮기면 서명 아래로 들어간다.**

## 4. 🔴 표준 `exp`를 쓰면 유예 단계가 사라진다

만료 시각을 표준 `exp`에 담으면 **JWT 라이브러리가 서명 검증 단계에서 만료 토큰을 거부**한다.
만료 다음 날 곧바로 "유효하지 않은 키"가 되어, 유예·읽기 전용 같은 **단계적 축소가 통째로 증발**한다.
만료 판정은 애플리케이션 상태 머신의 몫이므로 **커스텀 클레임**에 담는다.

"표준인데 왜?"로 되돌려지기 쉬운 자리다 — **이유를 코드 주석 한 곳이 아니라 3곳(상수·발급기·운영 문서)에** 남긴다.

## 5. 검증 함수를 등록용/판정용으로 쪼갠다

| | 언제 | 무엇을 |
|---|---|---|
| 등록용 | 키를 넣을 때 | 서명 + **등록 기한**(발급 후 N일) |
| 판정용 | 요청마다 | 서명만 |

같은 함수를 쓰면 **등록 N+1일째 정상 고객이 전부 잠긴다**(영구 라이선스 고객까지).
등록 기한은 *미등록 키의 수명*이지 *등록된 라이선스의 수명*이 아니다.

## 6. 만료를 잠금이 아니라 축소로 — 단, 시간축을 넣는다

실시간 조회가 본질인 제품(모니터링 등)은 만료 즉시 차단하면 화면이 통째로 빈다. 그렇다고 영원히
열어두면 아무도 갱신하지 않는다. **시간축으로 가른다.**

```
만료 ── +30d 유예(전 기능) ── +30d 읽기전용(실시간 O) ── 영구(DB 과거기록만)
```

마지막 구간을 **영구히 열어두는 것이 핵심**이다 — 돈을 안 냈다고 고객 데이터를 인질로 잡지 않는다.
반대로 **고객이 스스로 해지한 경우는 완전 잠금**이다. 읽기 전용은 만료 고객에 대한 배려이지
자발적 철회에 대한 것이 아니다.

## 7. 게이트는 AOP가 아니라 컴파일러가 강제하게

전역 인터셉터 → 기능별 인터셉터 → **포트 데코레이터**(HTTP를 안 거치는 배치·스케줄러를 잡는다) 3층.
`@Aspect`로 하면 어노테이션 누락이 조용히 통과하지만, **데코레이터는 메서드를 빠뜨리면 컴파일이 깨진다.**

⚠️ 단 인터페이스에 `default` 메서드가 있으면 그 강제가 사라진다 —
**리플렉션으로 전 메서드가 위임되는지 훑는 테스트**를 함께 둔다. 상세: [[topics/backend/test-false-safety-nets|test-false-safety-nets]] ③

## 8. 캐시와 공개키 슬롯

- 판정은 매 요청이지만 **서명 검증까지 매번 하면 비싸다** → 짧은 in-JVM 캐시(예: 60초).
  Redis가 아니라 **JVM 로컬**로 두면 캐시 조작 경로가 하나 줄고, 등록·해지 시 즉시 무효화한다.
  캐시가 있으므로 **DB 조작 실험은 캐시 만료를 기다려야** 결론이 난다(안 그러면 오판).
- 공개키는 **처음부터 여러 슬롯**(`public-1.pem`, `public-2.pem` …)을 순차 시도하게 만든다.
  없으면 **개인키 유출 시 대응이 불가능**하다 — 공개키를 교체하는 순간 기존 고객 키가 전부 죽는다.

## 9. 막지 못하는 것을 문서에 적는다

폐쇄망에서 **키 복제(다중 설치)와 서버 시계 되돌리기는 막을 수 없다.** 대조할 기준이 없기 때문이다.
숨기지 말고 **정직하게 적고**, 대신 키마다 고객사명·`jti`를 박아 **유출 시 출처를 특정**한다.
기술이 아니라 계약·추적의 영역이다.

> 설계 원칙: **정직한 고객이 불편하지 않게, 대충 하는 우회는 막히게.**

## 10. 발급 도구는 제품 저장소와 분리한다

**개인키를 들고 도는 프로세스**의 기본값:

- 발급 도구를 **제품과 다른 저장소로** — 개인키를 다루는 코드가 고객에게 넘어가는 소스에 섞이면 끝난다.
- 웹 UI는 **루프백 고정**, `--host`를 바꾸려면 **토큰 강제**(없으면 기동 거부).
- 다운로드는 **발급 대장 화이트리스트**로만 — 아니면 `../keys/private-key.pem`이 그대로 나간다.
- 발급이 끝나면 **끈다.** 켜져 있는 동안 그 프로세스가 곧 발급 권한이다.
- ⚠️ 저장소를 나누면 **상수·enum 소스 공유가 끊긴다** → 양쪽에 **계약 테스트를 같은 커밋에** 넣는다.
  안 그러면 "발급은 됐는데 제품이 거부"가 난다.
