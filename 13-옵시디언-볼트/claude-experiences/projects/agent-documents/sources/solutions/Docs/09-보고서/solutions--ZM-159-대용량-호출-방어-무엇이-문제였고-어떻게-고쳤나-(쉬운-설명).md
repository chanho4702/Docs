## 0. 한 줄 요약

우리 제품은 자빅스에 **"조건에 맞는 거 전부 줘"**라고 묻는 곳이 많았다. 지금 고객사(호스트 76대)는 양이 적어 괜찮지만, **호스트 5천 대·아이템 1천만** 규모에서는 답 하나가 수백 MB~수 GB가 되어 **서버가 메모리 부족으로 죽거나, 잘린 데이터를 정답처럼 보여 준다.** 이번 작업은 그 조회들을 **나눠 받고, 쌓지 않고, 필요한 것만 받도록** 바꾼 것이다.

## 1. 왜 문제였나 — 네 가지 유형

| 유형 | 무슨 일이 일어나나 | 결과 |
|---|---|---|
| **① 한 번에 전부** | "30일치 알람 전부 줘" 같은 요청. 서버가 받은 걸 전부 들고 있다가 화면을 만든다 | 서버 메모리 부족 → **전체 서비스 정지** |
| **② 조용한 절단** | 자빅스가 한 번에 주는 양에는 상한이 있다. 상한에 닿으면 **말없이 잘린다** | 화면 숫자가 **틀린 채로** 보임 |
| **③ 하나씩 반복 호출** | 인터페이스마다·호스트마다 따로 물어봄 | 화면 한 번 여는 데 수백 콜, 수십 초 |
| **④ 개별 결함** | 규모와 무관하게 이미 틀린 동작 | 데이터 손실·화면 멈춤 |

## 2. 화면별로 — 어디가 문제였고 어떻게 고쳤나

### 2.1 홈 / 이벤트·알림 — 그룹별 문제 요약
- **문제:** 홈 화면을 열어 두면 **60초마다** 30일치 알람을 **전부** 받아 그룹별로 셌다. 실측으로 2.3만 건이 6MB였으니 30일 규모면 수 GB다.
- **수정:** 알람을 **1만 건씩 받아 세고 바로 버린다**(메모리에는 항상 1만 건만). 끝까지 읽은 결과만 **60초 캐시**해서 반복 조회를 줄였다. 한 알람이 같은 그룹의 호스트 둘에 걸려도 **한 번만** 세도록 바로잡았다.
- **못 읽었을 때:** 부분 합계를 보여 주지 않고 오류를 낸다(틀린 숫자보다 낫다).

### 2.2 호스트그룹 상세 — 알림추이 탭
- **문제:** 막대그래프의 숫자를 만들려고 기간 내 이벤트를 **전부, 전체 항목으로** 받았다.
- **수정:** 데이터를 받지 않고 자빅스에 **"몇 건이야?"만 물어본다.** 알람이 있는 구간만 등급별로 다시 센다.
- **부가:** 조회 기간 상한을 93일로 뒀다(화면은 항상 최근 7일이라 영향 없음).

### 2.3 호스트그룹 상세 — 리포트 탭(주간·월간)
- **문제:** 한 달치 알람을 전부 받아 집계했다.
- **수정:** 흘려보내며 센다. 순서 규칙(건수가 같으면 먼저 발생한 호스트가 위)은 그대로 유지했다.
- **못 읽었을 때:** 리포트를 저장하지 않는다. 한 번 잘못 저장하면 **영구히 틀린 리포트**가 남기 때문이다.

### 2.4 호스트그룹 상세 — 자원추이 탭 / 리포트의 자원 집계
- **문제:** 그룹 전체 호스트의 CPU·메모리·디스크 추이를 한 번에 받았다. 월간 디스크는 9천만 행 규모로 추정됐다.
- **수정:** 호스트를 **묶음으로 나눠**(CPU·메모리 200대, 디스크 50대, 트래픽 10대) 받고, 받는 족족 집계한 뒤 버린다. 그래프에는 상위 10대만 남긴다. 디스크·트래픽은 **필요한 항목만 골라서** 요청한다.

### 2.5 호스트그룹 상세 — 그룹 문제 상세
- **문제:** 기간 내 이벤트를 상한 없이 전부 받고, 거기에 트리거 조회·복구 조회를 더 붙였다(3중 조회).
- **수정:** 화면이 실제로 쓰는 값은 **헤더의 건수뿐**이어서(확인함), **등급별 개수 조회 6번**으로 끝낸다. 쓰지 않던 상세 목록은 폐기 표시를 하고 빈 값으로 둔다.

### 2.6 클라우드 — AWS(EC2)
- **문제 1:** EC2와 자빅스 호스트를 짝지으려고 **모든 호스트의 모든 아이템**을 받았다(아이템 1천만이면 그대로 1천만 행).
- **수정 1:** 짝이 될 수 있는 **후보 호스트만** 골라, 그 호스트들의 **CPU 지표 수집 시각 하나**만 500대씩 확인한다.
- **문제 2:** EC2가 한 리전에 100대를 넘으면 **그 리전 조회가 통째로 실패**했다(AWS 규격 위반).
- **수정 2:** 100대씩 나눠 조회한다.

### 2.7 호스트 상세 — 인터페이스 상태 차트
- **문제:** 데이터가 10만 건에서 잘리는데 **오래된 것부터** 채워져, 기간을 길게 잡으면 **최근 구간이 통째로 비어** 보였다. 포트가 멀쩡한데 장애처럼 읽혔다.
- **수정(1차, 09-17):** 6시간을 넘거나 포트가 많으면 **시간별 요약**으로 그린다. 그 시간에 한 번이라도 DOWN이었으면 DOWN으로 센다.
- **수정(2차, 09-19 — 이걸로 마무리):** 원시 데이터를 **기간과 장비 단위로 쪼개 끝까지** 받는다. 그래도 다 못 받으면 **잘렸다는 사실이 같이 넘어오고**, 차트는 잘린 값을 **버린 뒤** 시간 요약으로 바꾸거나 비워 둔다. 틀린 그림보다 빈 화면이 낫다는 판단이다.
- 🔴 **아직 눈으로 못 봤다** — 개발용 자빅스에 포트 아이템이 하나도 없어서(0개) 실제 그림은 확인하지 못했다.

### 2.7-b 호스트 상세 — CPU·메모리·디스크 차트 / 아이템 이력 *(09-19 추가)*
- **문제:** 같은 원인이다. 측정값이 많으면 앞부분만 받고 **"이게 전부입니다" 하고 그렸다.**
- **수정:** 위와 같은 쪼개 읽기가 적용된다. 아이템 이력 화면은 "끝까지 읽었는가"로 판단해, 못 읽었으면 잘린 원시를 버리고 시간 요약으로 대체한다(종전에는 "응답이 정확히 10만 건이면 잘린 것"이라고 **추측**했다).
- **확인됨(09-21, 개발 서버):** CPU 차트 1일치가 **1,440개**(1분 주기 × 1,440분) 한 점도 빠짐없이 들어왔다.

### 2.8 호스트 상세 — 네트워크 차트
- **문제 1:** 인터페이스 × 종류마다 따로 물어봤다(인터페이스 100개면 요청당 800~1,200콜).
- **수정 1:** 인터페이스를 지정하지 않으면 **트래픽 상위 10개**만, 10개씩 묶어서 조회한다.
- **문제 2:** eth0과 eth1 값이 **한 선으로 섞여** 그려지고 범례를 눌러도 반응이 없었다.
- **수정 2:** 인터페이스별로 분리했고 범례 토글이 동작한다.
- **문제 3:** IN+OUT 합계를 **순서대로** 더해, 수집 시각이 어긋나면 엉뚱한 시각끼리 더해졌다.
- **수정 3:** **가장 가까운 시각끼리** 더한다.

### 2.9 자빅스 관리 — 아이템 / 트리거 관리
- **문제:** 대상(호스트·템플릿) 없이 목록을 부르면 **전체 아이템**을 받아 와서 20개만 보여 줬다.
- **수정:** 대상 없는 조회를 거부한다(화면은 항상 대상을 지정해 부른다).

### 2.10 자빅스 관리 — 구성 현황
- **문제:** 관리자 여러 명이 동시에 열면 화면이 **영영 안 떴다.** 내부에서 작업들이 서로를 기다리는 교착 상태였다.
- **수정:** 작업 종류별로 처리 통로를 분리했고, 60초 안에 안 끝나는 항목은 중단하고 **그 항목만 "일부 실패"**로 표시한다.

### 2.11 설정 — 자산 동기화
- **문제:** 전 호스트와 인벤토리 전체를 한 응답으로 받았다.
- **수정:** 호스트 번호만 먼저 받고, 상세는 **500개씩** 나눠 받는다. DB 반영은 종전처럼 한 번에 처리한다.

### 2.12 이벤트·알림 — 문제 목록(이력 모드) *(09-18 추가)*
- **문제:** 기간을 길게 잡으면 2만 건에서 잘리는데 **잘렸다는 표시가 없었다.** 총 건수도, 심각도 칩도, 인과 관계 묶음도 전부 잘린 2만 건 기준인데 화면은 전체인 것처럼 보여 줬다.
- **수정:** 상한보다 1건 더 요청해 "딱 2만 건"과 "2만 건을 넘음"을 구분한다. 넘쳤으면 목록 위에 안내를 띄운다 — *"이 기간의 이력이 많아 최근 20,000건까지만 확인했습니다. 목록과 심각도 건수, 인과 관계 묶음이 모두 확인한 일부 기준입니다. 기간을 좁히면 전부 확인할 수 있습니다."*
- **하지 않은 것:** "전체 몇 건"까지 보여 주려 했으나, 억제·해소기간·심각도 필터가 우리 쪽에서 걸려 그 숫자가 화면 결과와 맞지 않는다. 숫자를 틀리게 보여 주느니 문장으로 설명하는 쪽을 택했다.

### 2.13 네트워크 맵 — 실시간 상태 *(09-18 추가)*
- **문제:** 지도에 올린 호스트마다 "이 호스트에 문제 몇 건?"을 따로 물어봤다. 500대면 50~150초가 걸린다.
- **수정:** 한 번에 물어 호스트별로 나눈다. 지리 맵은 이미 그렇게 하고 있었는데 네트워크 맵만 빠져 있었다.

### 2.14 알람 동기화(백그라운드)
- **문제:** 알람 조회가 1만 건에서 잘리면 갱신을 못 받은 알람이 생기는데, 우리 정리 배치가 **"이틀 동안 갱신 없음 = 없어진 알람"**으로 보고 **진짜 열려 있는 장애를 삭제**했다.
- **수정:** 조회가 잘린 회차는 정리를 건너뛰고, 동기화가 **최근 연속 3번 정상**일 때만 삭제한다. 재기동 직후·자빅스 장애·라이선스 차단 중에는 지우지 않는다.

### 2.15 설정 — 알람 동기화 범위 *(09-18 추가)*
- **왜:** 알림 벨과 문제 목록은 우리 DB 사본을 본다. 그 사본을 만드느라 15초마다 **열린 알람 전부**를 받는데, 열린 알람이 수만 건인 고객사에서는 그 자체가 부담이고 1만 건 상한에 걸려 초과분이 안 보인다.
- **무엇을:** 설정 > 데이터소스(자빅스) 화면에서 **담을 알람을 좁힐 수 있게** 했다 — 호스트 그룹, 최소 심각도, 억제(점검 중) 제외, 꺼진 규칙 제외.
- **주의:** 좁힌 알람은 벨·문제 목록(기본)·홈 위젯·이벤트 통계·AI 요약에서 보이지 않는다. 이력 모드·리포트·그룹별 문제 요약은 자빅스를 직접 보므로 그대로다.
- **기본값은 지금과 같다**(제한 없음). 필요한 고객사만 켠다.
- 🔴 검수에서 발견: "꺼진 규칙 제외"가 **실제로는 동작하지 않고 있었다**(건수 집계에만 걸려 있었다). 이번에 목록 조회에도 적용했다.

## 3. 눈에 안 보이는 기반 공사

| 무엇 | 왜 |
|---|---|
| 자빅스 호출을 **공통 유틸 하나로** 모음 | 26개 파일에 흩어져 있어 상한·분할 같은 보호 장치를 걸 자리가 없었다 |
| 호출 **상한·분할·예산** 장치 | 응답 크기·행 수·호출 수·시간에 상한을 두고, 넘치면 기간 → 대상 순으로 잘게 나눠 다시 받는다 |
| 메서드 **이넘화**(111개) | `"host.get"` 같은 문자열이라 오타가 실행 중에만 드러났다. 자빅스 API 버전이 올라가도 **한 곳만** 고치면 되게 했다 |
| **JVM 힙 설정 분리** | 컨테이너 메모리의 25%만 쓰던 기본값을 75%로. 배포 환경에서 환경 변수로 바꿀 수 있다 |

## 4. 쓰는 사람 입장에서 달라지는 점

| 화면 | 달라지는 점 |
|---|---|
| 네트워크 차트 | 인터페이스를 고르기 전 첫 화면은 **트래픽 상위 10개**만 그린다. eth0·eth1이 따로 보이고 범례가 동작한다 |
| 인터페이스 상태 차트(긴 기간) | 한 시간 안에 한 번이라도 DOWN이면 그 시간은 DOWN으로 센다 |
| AWS 연결 판정 | "에이전트 수집 중" 기준이 **아무 항목** → **CPU 지표**로 바뀐다. CPU 항목이 없는 호스트는 CloudWatch 값으로 표시된다 |
| 그룹 문제 상세 | 응답의 상세 목록 필드는 비어 온다(화면에서 쓰지 않던 값) |
