## 2. 핵심 결정

| # | 결정 | 이유 |
|---|---|---|
| 1 | **자빅스 아카이빙과 기반 공유** | 겹치는 12개 축 중 **10개가 공통**(ZIP·manifest·목록·삭제해도 행을 남기는 규칙·감사 로그 등). APM만의 것은 셋 — DROP 게이트, (데이터셋, 날짜) 단위, 파일만 남아도 읽히도록 사전(서비스 이름·히스토그램 경계·오류 원문) 동봉 |
| 2 | **DROP 게이트 = 아카이브 원장 조회** | 파티션마다 성공 기록과 **파일 실물 존재**를 확인한다. 게이트 조회가 실패하면 **지우지 않는 쪽**으로 넘어간다. 🔴 아카이브가 꺼져 있으면 보존 정리 동작은 지금과 똑같아야 한다 |
| 3 | 배치를 하나로 합치는 안 **기각** | 보존 정리가 아카이브 실패에 끌려가고, 스케줄러 잠금(30분)을 연장하는 장치가 없어 긴 내보내기 중 다른 노드가 같은 배치를 시작할 수 있다 |
| 4 | **DROP 2일 전부터 내보낸다**(`leadDays=2`) | 1m 데이터는 D+6일에 처음 시도하고 D+8일 삭제 전 재시도가 두 번 있다. 게이트가 있으니 두 배치의 실행 순서는 정합성이 아니라 "같은 날 지워지느냐"의 문제가 된다. 실행 시각은 00:30이 파티션 선생성과 겹쳐 **00:50**으로 |
| 5 | 형식은 데이터셋별 고정 | 평평한 표 CSV.gz, 스팬 JSONL.gz. Parquet 기각. **restore는 1차 제외**하되 되살릴 수 있게 쓴다. 원문 SQL은 기본 마스킹 |
| 6 | 경로는 **설치 시 정한 허용 루트 아래만** | 절대 경로·`..`·심볼릭 링크 검사, 파일을 실제로 써 보고 여유 공간 실측. 라이선스 만료에도 멈추지 않게 |

## 3. 🔴 조사에서 드러난 사실 (명세·백로그와 달랐던 것)

| # | 사실 | 영향 |
|---|---|---|
| 1 | **`normalizeQueueDir`에 절대 경로 강제와 `..` 금지가 없다.** 실제로 막는 것은 개행·큰따옴표·`${`·길이 512뿐이고, package-private이라 밖에서 못 부른다 | 명세는 "같은 규칙 재사용"이라고 적었는데 **틀린 전제였다**. 백로그 두 곳을 정정했다. 문자 규칙만 공용으로 떼고 경로 규칙은 새로 만든다 |
| 2 | 배치 실행 이력으로는 "그날 아카이브가 됐는지" 판정할 수 없다 | 기본 정책이 실패만 30건 남기고, 요약은 자유 문자열이다 → **전용 원장 테이블 필요** |
| 3 | 아카이브 경로를 스케줄러 옵션에 두면 **검증이 전부 우회된다** | 스케줄러 저장은 잡별 옵션을 검증하지 않고 통째로 바꾼다(ZM-153에서도 같은 이유로 읽을 때 자르게 했다) |
| 4 | 🔴 **배포 스크립트의 BE `docker run`에 볼륨(`-v`)이 없다** | 지금 켜면 **배포할 때마다 아카이브 파일이 사라진다.** 착수 전 인프라 조치 필요 |
| 5 | 공통 감사 로그가 코드에 없다. 기존 자빅스 설계가 전제한 `ENTITY_ARCHIVE`도 실재하지 않는다 | ZM-155·I7과 공유 과제 |
| 6 | 기존 자빅스 설계서의 마이그레이션 번호 V41은 낡았다 | 현재 V59까지 사용, ZM-151이 V60을 잡았다 |

## 5. 단계 (착수 시)

| 단계 | 범위 |
|---|---|
| S0 | 결정 5개 + **스팬·1m 내보내기 소요·용량 실측** |
| S1 | 공통 기반(원장·writer·경로 정책·감사) |
| S2 | DROP 게이트 — 🔴 **꺼진 상태에서 기존 동작 불변 테스트가 먼저** |

| S4 | 공통 화면에 APM 소스 |
| S5 | 1m·스팬 옵트인 + 마스킹 |
| S6 | 실측(게이트 거부→다음 날 DROP, NFS·컨테이너 볼륨, 크래시 후 정리, 다중 노드) |
