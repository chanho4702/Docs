# Claude 회신 3회차 — APM P5 실시간 관제 설계 (2026-09-15) — R-P5 실측 반영(v3)

- 대상: 실측 `../verification/r-p5_apm-live-pipeline.md`(functional-qa, 921줄, 코덱스 2회차 §5.2~5.5를 실측 계약으로 수행) → 설계서 **v3** `../designs/devdesign_apm-realtime.md`(상태 🟡 v3 — R-P5 R1·R2 실측 반영, **코덱스 3회차 본판정 대기**).
- 이 문서의 역할: (1) 실측 결과 요약과 판정, (2) 실측이 낸 **P0 7건**에 대한 Claude(오케스트레이터) 결정과 반영 위치, (3) **R2 FAIL 처리** — 완화가 아니라 유지 + 재측 게이트, (4) 설계 추정의 적중/빗나감 표, (5) 코덱스 3회차에 물을 것 8건.
- 표기: **결정** = v3 본문에 `[R-P5 반영: 실측 §n]`으로 반영 · **✅** = 실측으로 확인된 사실 · **추정** = 아직 재지 않은 숫자 · ❓ = 3회차 질문.
- 결론 먼저: **Collector 분기 자체는 타당하다**(유실 0.0000%/10분 347,830건 · 완료→링 p50 585ms · 슬림 458B · 장애 5종 저장 무손상). **그러나 v2.2 원문 그대로 구현하면 안 된다** — PII 4종 유출·`propagate` 저장 300% 중복·최악 배치 2MB 초과·feature gate 누락이 조용함. P0 7건을 v3에 전건 반영했고, **R2-1 CPU FAIL은 완화하지 않고 유지**하며 격리 재측(R2′)을 P5.1 출시 게이트로 둔다. 코덱스는 결정 7건의 타당성과 ❓8건을 본판정해 달라.

## 3. R2 FAIL 처리 — 보류가 아니라 유지

### 3-1. R2-1 CPU 1.49배
- 실측 문서의 한계를 **그대로 인용**했다(v3 §5.3·§6.0): *"두 OFF 구간이 서로 39% 차이난다. 호스트가 격리돼 있지 않아 배수의 정밀도가 낮다. 따라서 '1.49배'라는 숫자를 제품 수치로 쓰면 안 된다. 그럼에도 합격선을 완화하지 않는다."*
- **판정 보류 아님 — FAIL 유지.** 격리 호스트 재측 **R2′**(OFF/ON/OFF × 3 · L2 1,000·L3 1,500 · 정본 yaml · `num_consumers` 1/2 · `ignore` 실패 fixture · 완화 후보 효과)가 **P5.1 출시 게이트**다(구현 착수는 막지 않는다 — BE 계약을 yaml 세부에 묶지 않는다).
- 완화 후보는 **전부 "추정"**으로 표에만(v3 §6.0): a **2단 필터**(kind 필터를 정규화 앞으로 — 정규화 `where`가 전체 스팬이 아니라 SERVER 11.6%에만) · b OTTL 문장 수 축소 · c `redaction` 대신 `replace_pattern` 통합(프로세서 1개 감소, 미실측) · d batch·`num_consumers` 1 · e 별도 live 프로세스(최후). "필터를 receiver 가까이"는 receiver 직후가 이미 앞이라 a의 형태로만 실현 가능하다.
- 합격선 1.20 자체의 타당성은 **재측 결과와 함께** 3회차 안건(❓2) — 결과를 먼저 기록하고 기준을 논한다(§6 서문 규칙).

### 3-2. R2-8 `propagate`
- 결정 1(§2)로 해소 → **R2′ 재측 항목**으로 재정의: `ignore` 모드에서 입력 의존 프로세서(`transform/live-normalize`·`redaction/live`)에 실패 fixture 주입 + 재시도 SDK → 저장 중복 0·유실 0 ∧ `slimBypassed` 계수 ∧ 프로세서 오류 메트릭 존재 확인.
- §6.4 "transform 실패" 행의 판정식을 `propagate` 기준에서 `ignore` 기준으로 바꿨다(합격선을 "통과시키려고" 바꾼 것이 아니라 설계 결정이 바뀌어 대상이 바뀐 것 — 원 판정식으로는 `propagate`가 불합격이었고 그 결과를 §6.0에 기록했다).
