# 호출 병합과 캐시 (`ZM-124` `ZM-126`)

## 0. 한눈에

| | |
|---|---|
| **왜** | 같은 걸 쪼개서 여러 번 묻고(심각도 칩 7콜, 인터페이스 상세 9콜), 같은 질문을 1분에 수십 번 반복(호스트 목록) |
| **뭐를** | **묻는 횟수** 자체를 줄였다 |
| **어떻게** | 쪼개 묻던 건 1번에 받아 우리가 분류(7→1, 9→1). 반복 질문은 Redis 30~60초 캐시 — 단, 신선해야 하는 알람엔 캐시 안 씀(그건 사본 담당) |
| **결과** | 서버 목록 응답 1,056ms → **117ms** |

## 1. 문제 — 어디서, 무엇이

세 곳에서 성격이 다른 반복이 있었다:

- **심각도 칩(내용의 반복)** — 알람 화면·홈의 "재해 2 · 심각 5 · …" 칩이 심각도 등급마다
  problem.get countOutput을 따로 호출: **화면 하나에 7콜.** 결국 같은 알람 집합을 일곱 번
  나눠 센 것.
- **인터페이스 상세(N+1)** — 호스트 인터페이스 상세가 검색 키마다 item.get을 호출: **9콜.**
- **호스트 목록·가시 호스트 집합(시간의 반복)** — 서버/그룹 목록 화면과 권한 판정이 폴링마다
  같은 host.get류 조회를 반복: **1분에 수십 번 같은 질문**, 응답은 거의 항상 같다.

## 2. 어떻게 처리했나

### 2.0 AS-IS → TO-BE (API 단위)

| API/경로 | AS-IS (원래) | TO-BE (변경 후) |
|---|---|---|
| 심각도 칩 카운트(알람 목록 statusCounts·홈 KPI) | 등급별 problem.get countOutput × **7콜** | 경량 목록(output=severity만) **1콜** → 앱에서 등급별 집계 |
| 인터페이스 상세의 item.get | 검색 키마다 1콜 × **9콜** | `search.key_` 배열 + `searchByAny:true` **1콜** |
| `GET /hosts` (서버/그룹 목록) | 요청마다 host.get류 3~4콜 직행 | **Redis 30초 스냅샷**(사용자·필터 축별 키) — 미스일 때만 Zabbix |
| 가시 호스트 집합(사본 서빙의 권한 판정 재료) | 요청마다 계산 | **Redis 60초 캐시** |

### 2.1 카운트 병합의 처리 흐름 (7→1)

```
칩 카운트 요청
 ① 종전: for (등급 of 7등급) problem.get(countOutput, severity=등급) — 7왕복
 ② 변경: problem.get 1콜, output은 severity 필드만(본문 최소화)
 ③ 앱에서 등급별로 세어 7칸 채움
 ④ 🔴 축 맞춤: 억제 표시 토글·비활성 규칙 제외 같은 필터가 목록과 동일하게 걸리도록
    같은 질의 사본에서 심각도만 바꿔 집계 — 칩과 목록이 다른 수를 말하는 사고 방지
※ 포트 계약(countActiveBySeverity)은 중립 유지 — Zabbix 어댑터만 1콜 구현,
  다른 데이터소스는 기본 구현(등급별 반복)을 써도 됨
```

### 2.2 캐시의 처리 흐름 (30~60초)

```
GET /hosts (사용자 A, 필터 F)
 ① Redis 키 "HOST_LIST:{축}:{필터}" 조회 — 히트면 즉시 반환(Zabbix 0콜)
 ② 미스면 Zabbix 조회 → 응답을 30초 TTL로 저장 → 반환
 ③ 호스트를 생성·수정·삭제하는 쓰기 경로는 저장 직후 해당 키 즉시 무효화
※ 가시 호스트 집합도 동일 패턴(사용자별 키, 60초)
```

**설계 원칙 — "몇 콜인가"보다 "무엇이 반복되는가".** 내용의 반복(7콜·9콜)은 **병합**으로,
시간의 반복(같은 질문)은 **캐시**로 풀었다. 그리고 **신선도가 생명인 알람 데이터에는 캐시를
쓰지 않았다** — 그쪽은 [사본 서빙](solutions--ZM-125-%EC%95%8C%EB%9E%8C-%EC%82%AC%EB%B3%B8-%EC%84%9C%EB%B9%99%EA%B3%BC-%EA%B6%8C%ED%95%9C-%EC%9E%AC%ED%98%84.md)이 담당한다(캐시는 확률적
절감, 사본은 결정적 분리).

## 3. 적용 범위

| 경로 | 적용 |
|---|---|
| 알람 화면·벨의 심각도 칩, 홈 KPI 심각도 도넛 | ✅ 1콜 집계 |
| 호스트 인터페이스 상세 | ✅ item.get 1콜 |
| 서버/그룹 목록 화면 | ✅ 30초 스냅샷 캐시 |
| 알람 사본 서빙의 권한 판정(가시 호스트 집합) | ✅ 60초 캐시 |
| 알람 목록·벨 본문 | ❌ 캐시 아님 — 사본 서빙(별도 개선) |
| 메트릭 차트 | ❌ 캐시 없음 — 적응 조회(별도 개선)가 담당 |

## 4. 해결된 것

- dev 실측: 서버 목록 응답 **1,056ms → 117ms**(캐시 히트).
- 칩 7콜→1콜, 인터페이스 상세 9콜→1콜.
- 집계와 목록이 같은 모집단을 보도록 축 고정(과거 "칩 942 vs 목록 345" 실사고 재발 방지).

## 5. 트레이드오프와 우려점

**트레이드오프(의도한 대가):**

- **캐시 TTL 동안의 낡음** — 호스트 추가·삭제가 목록에 최대 30초, 권한 변경이 최대 60초 늦게
  반영(즉시 무효화가 있는 경로는 즉시). "목록성 데이터는 초 단위 신선도가 필요 없다"의 대가.
- **1콜 응답 본문 크기** — countOutput 7콜의 응답은 숫자 7개, 경량 목록 1콜은 활성 알람
  수만큼의 행. 활성 알람 수만 건 설치본이면 본문이 커진다 — 왕복 7회 절감과의 교환(계측
  로그로 관찰).
- **캐시 키 축의 복잡도** — 사용자·필터별 키라 조합이 다양하면 키 수가 늘고 히트율이 떨어짐
  (TTL이 짧아 총량은 묶임).

**우려점(지켜봐야 할 것):**

- **무효화 누락** — 새 쓰기 경로가 생길 때 캐시 무효화를 빼먹으면 TTL까지 낡은 데이터.
  쓰기 경로 추가 시 체크 항목.
- 집계 1콜의 필터 축(억제·비활성 규칙)이 화면 토글과 계속 일치하는지 — 어긋나면 "칩과 목록이
  다른 수" 재발.

## 6. 함정

- **searchByAny 없으면 조용한 0건** — 키 배열 search에 `searchByAny:true`가 없으면 조건이
  AND로 읽혀 **에러 없이** 빈 결과 → 테스트로 고정.
- **캐시 직렬화 왕복** — RedisClientService.set은 JSON 직렬화라 raw 조회(getRaw)와 짝이 안
  맞는다. 문자열 하나를 캐시해도 저장·조회를 같은 직렬화 쌍(get/set)으로 — 태그 필터 감지
  캐시에서 이 불일치로 검증이 조용히 꺼져 있던 실사고가 있었다.
- **집계 의미 동등성** — "7콜 합산 = 1콜 앱 집계"는 필터 축이 양쪽에 똑같이 걸릴 때만 성립 —
  축을 명시적으로 맞추고 테스트로 고정했다.
