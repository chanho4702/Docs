# 어플리케이션 모니터링 (APM)

> **사이드바** 모니터링 > 어플리케이션 모니터링 (PREMIUM · `APM` 기능)
> **경로** `/application-monitoring/overview` → 서비스·트레이스·수집기 등 하위 경로
> **상태** 메트릭(개요·서비스·수집기·알람) · 트레이스(트레이스 탐색·서비스 맵·에러·DB·외부 호출·배포) · 운영 심화(합성 감시·SLO·메시징/배치·리포트) · 브라우저(RUM)와 Kubernetes 옵션 · 실시간 관제(선택 기능)까지 구현되어 있다. 아직 없는 것은 **로그 탭**과 코드 프로파일링이다. 브라우저 화면 검증과 배포가 끝나지 않아 `review`다.

## 무엇을 하는 화면인가

고객이 운영하는 **애플리케이션(서비스)이 살아 있는지, 얼마나 빠른지, 얼마나 실패하는지**를 서비스 단위로 보여 주고, 나빠졌을 때 어느 엔드포인트·쿼리·외부 호출·런타임 자원이 원인인지 좁혀 주는 화면이다.

서버 모니터링과의 차이는 **주어가 호스트가 아니라 서비스**라는 점이다. "사내 Jira가 지금 느린가"에 답한다.

| 신호 | 무엇으로 계산하나 |
|---|---|
| 가용성 | 최근 수신이 이어지는지(수신 끊김) + 오류율, 합성 감시가 연결돼 있으면 밖에서 두드린 결과 |
| 응답시간 | HTTP 서버 요청 히스토그램 → p50 / p95 / p99 |
| 오류율 | 5xx 응답 ÷ 전체 × 100 (4xx는 세지 않는다) |
| 처리량 | 구간 요청 수 ÷ 초 (rps) |
| 런타임 | JVM 메모리·GC·스레드·CPU, DB 커넥션 풀 |
| 요청 하나의 경로 | 트레이스(스팬 워터폴) — 어느 스팬에서 시간을 썼나 |
| 사용자 체감 | 브라우저 Web Vitals(LCP·INP·CLS·TTFB·FCP)와 JS 오류 |

### 데이터가 오는 길

```text
 [고객 앱]             [고객 망 안]                    [MovesEye 서버]                          [화면]
 Java/.NET/Node… ──▶ OTel Collector ──HTTP/json──▶ POST /apm/otlp/v1/metrics ──▶ 1분 표 ──▶ 개요·서비스·알람·수집기
 (자동계측 붙임)      (모아서·거르고·토큰 붙임)      POST /apm/otlp/v1/traces  ──▶ 스팬·요약 ──▶ 트레이스·맵·에러·DB·외부 호출
                                                   (토큰·라이선스 검사 → 허용목록 → 적재)     5분·1시간 롤업 → SLO·리포트
 [브라우저] ── RUM 스니펫 ──────────────────────▶ POST /apm/rum/… (공개 토큰) ──▶ 5분 표 ──▶ 사용자 경험
                                                                                     │
                                                                          5분마다 알람 평가 → Zabbix로 push
```

- 앱에 **OpenTelemetry 자동계측**(Java는 `-javaagent` 한 줄)을 붙이면 지표와 트레이스가 표준 형식으로 나온다. 자체 에이전트·SDK는 없다.
- 고객 망 안의 **OTel Collector**(사이트당 1대)가 모아서 마스킹·샘플링한 뒤 수신 토큰을 붙여 MovesEye로 보낸다. 트레이스는 느린 것·실패한 것은 다 남기고 정상 요청은 일부만 남긴다(tail 샘플링).
- 다른 모니터링 소스(Prometheus·Datadog)에서 **가져오는 방식이 아니다.** 고객 앱이 **보내는** 방식이다.
- 설치 절차는 [수집기 설치](solutions--%EC%88%98%EC%A7%91%EA%B8%B0-%EC%84%A4%EC%B9%98.md)에 있다.

| 메뉴 | 한 줄 | 데이터 |
|---|---|---|
| APM 개요 | 모든 서비스가 지금 괜찮은지 한 화면에서 | 1분 메트릭 |
| 실시간 관제 (선택 기능) | 1초 단위로 흐르는 요청 관제·X-View. 진행 중 요청은 자바 확장 설치 서비스만 | 메모리(저장 안 함) |
| 서비스 | 서비스 목록 → 상세(탭 12개, 로그 탭만 미개방) | 메트릭 + 트레이스 |
| 서비스 맵 | 서비스·DB·외부 호출·큐가 누구를 부르는지 그림으로. 화살표 굵기 = 호출 수, 색 = 오류율 | 트레이스 롤업(5분) |
| 트레이스 탐색 | 요청 하나하나를 산점도에서 골라 스팬 워터폴·플레임으로 | 스팬(7일 보존) |
| 합성 감시 | Zabbix 웹 시나리오로 밖에서 URL을 두드려 본 가용성 | Zabbix |
| SLO | "30일 99.9%" 같은 약속을 지키고 있나, 에러 버짓이 얼마나 남았나 | 메트릭 롤업 |
| 수집기 (관리자 전용) | 토큰·설정 파일·설치 가이드·수신 확인·등록 정책·RUM 토큰 | — |
| 사용자 경험 (RUM) | 실제 사용자 브라우저에서 페이지가 얼마나 빨리 뜨나, JS 오류가 어디서 나나 | 브라우저 수신(5분 표) |

**알람 규칙**은 사이드바에 없고 설정 ⚙, 전역 검색, 개요의 '최근 알람'에서 들어간다. **에러 분석·DB 호출 분석·외부 호출 분석·메시징·배치**도 사이드바에 없다 — 서비스 상세의 같은 이름 탭과 본체가 같고, 전 서비스를 한 번에 볼 때 전역 검색이나 주소로 들어간다.

### APM 개요

- 위쪽 숫자 4개: 전체 트래픽 합계(초당 요청·오류율·p95·액티브 요청)와 비교 구간 대비 변화. 목록에서 숨긴 서비스도 포함하는 값이라 아래 상태 요약의 개수와 모집단이 다르다.
- 서비스 상태 도넛: 상태별 개수. 숫자 칩을 누르면 그 상태만 걸러진 서비스 목록으로 간다.
- 서비스 × 시간 히트맵: 행이 서비스, 칸이 시간 구간, 색이 오류율. **회색 칸은 오류가 없는 것이 아니라 요청이 없었다는 뜻**이다.
- 느린 서비스 Top 5 · 오류 많은 서비스 Top 5 · 최근 알람: 이름을 누르면 지금 보고 있는 시간 범위를 들고 상세로 이동한다.
- 아래 카드 3장: 최근 배포 스트립, SLO 위험 목록, 서비스 맵 미니. "지난주 리포트" 버튼은 설정 › 리포트 관리의 APM 리포트로 간다.
- **내보내기** 버튼으로 보고 있는 기간의 RED 지표를 CSV/JSONL로 받을 수 있다(서비스 상세 개요·트랜잭션·에러 화면에도 있다). 화면을 볼 수 있는 사람은 누구나 받을 수 있고, 기간이 길면 서버가 나눠 받으라고 안내한다.

### 서비스

**목록** — 서비스마다 상태·환경(env)·초당 요청·오류율·p95·인스턴스·버전·마지막 수신·추이를 한 줄로 본다. 카드/표 보기를 고를 수 있다.

- 상태는 **최근 5분** 판정이고, 초당 요청·오류율·p95는 **상단 시간 범위 전체** 합산이다. 둘의 창이 다르다.
- 정렬은 나쁜 상태부터(중단 → 성능 저하 → 수신 끊김 → 확인 불가 → 정상). 배지에 마우스를 올리면 판정 근거("오류율 10.1% > 5.0%")가 보인다.
- 숨긴 서비스는 '숨긴 서비스 포함'을 켜야 보인다. 숨겨도 수집은 계속된다. 수집을 멈추고 싶으면 설정 탭의 **수집 중지** 스위치를 쓴다(목록에는 남고 데이터만 안 쌓인다).
- 서비스가 하나도 없으면 온보딩 안내(수집기 설정 → 앱에 한 줄 → 수신 대기)가 뜬다.

**상세** — 헤더에 상태 배지·env·버전·인스턴스 수·마지막 수신·호스트가 있고, 탭 12개 중 11개가 열려 있다. **로그 탭만** "다음 단계" 배지가 붙은 채 비활성이다.

| 탭 | 무엇을 보나 | 주의 |
|---|---|---|
| 개요 | 요청수·오류율(알람 임계 점선)·응답시간 p50/p95/p99(배포 시점 표시)·응답시간 분포 히트맵·Apdex·액티브 요청·**24시간 가용성 띠**·느린/오류 엔드포인트 Top 5·인스턴스 미니카드 | 가용성 띠는 상단 시간 범위와 무관하게 항상 최근 24시간(5분 칸). 왼쪽 %는 "수신이 있었나"이며 SLA가 아니다 |
| 트랜잭션 | 엔드포인트(route)별 호출수·초당 요청·p50·p95·오류율 표. 행을 누르면 그 경로의 추이 3장과 응답시간 산점도 | `기타(__other__)`는 route 상한(서비스당 500)을 넘어 접힌 합. `/**`는 404, `/*`는 인증 필터에서 끊긴 요청이 모이는 자리 — 실제 코드 경로가 아니다. 상태코드·메서드 분포는 서비스 전체 값 |
| 트레이스 | 이 서비스를 지나간 요청의 산점도·목록 → 워터폴. '거쳐 간 것 포함'을 끄면 이 서비스에서 **시작한** 트레이스만 | 건수는 샘플이라 요청 수가 아니다. 7일 지나면 만료 |
| 에러 | 예외 그룹 표(타입·정규화 메시지·발생 추이·영향 엔드포인트·첫/마지막)와 스택·예시 트레이스 | 묶는 기준은 타입+메시지. 스택 원문은 관리자만, 그 외는 가려진다 |
| 데이터베이스 | 서비스→DB 흐름도, 쿼리 그룹 표(정규화 SQL·호출수·평균/p95·**총 소요**·오류), 커넥션 풀 | 기본 정렬은 총 소요 — 가장 느린 쿼리와 가장 오래 잡아먹는 쿼리는 다르고 고칠 가치는 대개 후자. 원문 SQL 보존을 끄면 리터럴이 `?`로 가려진 형태만 |
| 외부 호출 | 우리가 부르는 외부 주소별 호출수·p95·오류율·타임아웃 수 | 대상은 주소뿐(경로 없음). 타임아웃을 앱이 삼키고 폴백하면 오류로 안 잡힌다 |
| 런타임 | 힙·논힙 메모리, GC 시간·횟수, 스레드, CPU, 로드된 클래스, 커넥션 풀, 풀 대기 p95 | 실제 앱으로 확인된 것은 **JVM**이다. .NET·Node·Python·Go는 지표 자리는 있으나 오지 않으면 '계측 미제공' 배지가 보인다. Apdex T는 초, 나머지 지연은 ms |
| 인스턴스 | 인스턴스별 상태(정상/수신 끊김)·버전·호스트·초당 요청·p95·오류율, 최대 6대 추이 비교. Kubernetes 앱이면 파드·노드·네임스페이스·디플로이먼트·재시작 횟수·OOM 배지 | 인스턴스 지표는 1분 데이터(7일 보존)에만 있다 — **기간이 7일을 넘으면 값이 비어 온다**. 인스턴스가 멈춘 것이 아니니 기간을 좁힌다 |
| 배포 | 배포 목록(버전·시각·자동 감지/웹훅)과 선택한 배포의 전후 비교(p95·오류율·rps), 새로 생긴 예외 | 목록은 최근 30일 고정. 같은 버전 재배포·`service.version` 없는 앱은 자동 감지가 못 잡는다 — CI/CD에서 웹훅 한 줄을 부른다. 개선/악화 판정은 하지 않고 숫자만 보여 준다 |
| 로그 | (미개방) | 클릭하면 다음 단계 안내만 뜬다 |
| 합성 감시 | 이 서비스에 연결된 Zabbix 웹 시나리오의 마지막 결과·24시간 가용성·60분 p95, 연결/해제 | 연결은 "이 서비스의 감시"라는 표시일 뿐이라 해제해도 시나리오는 계속 돈다. 만들기·수정은 합성 감시 메뉴에서 |
| 설정 | 표시명·설명·태그·담당자·Apdex T(초)·느림 임계(ms)·호스트 수동 매핑·숨김·**수집 중지**·삭제, 적용 중인 알람 규칙(읽기), SLO 링크 | 관리자만 저장. 환경(env)은 앱이 보내는 값이라 여기서 못 바꾼다. 삭제는 숨긴 상태에서만 되고 되돌릴 수 없다 — 앱이 계속 보내면 새 서비스로 다시 등록된다 |

### 서비스 맵

서비스·DB·외부 HTTP·큐를 노드로, 호출을 화살표로 그린다. 화살표 굵기는 호출 수, 색은 오류율(초록 1% 미만·노랑 5% 미만·빨강 5% 이상·회색 0건), 라벨은 p95다. 화살표를 누르면 오른쪽에 호출 수·오류율·p50/95/99와 추이가 뜬다.

- 트레이스를 5분마다 접은 값이라 **최대 8분 늦다.** 방금 띄운 서비스가 없다고 장애로 읽지 않는다.
- 샘플링을 통과한 트레이스가 기준이라 오류 비중이 실제보다 크게 보일 수 있다. 정확한 비율은 서비스 화면의 메트릭이다.
- 점선 테두리 노드는 계측이 없어 상대편 스팬만 보고 그린 것이다.
- 서비스 선택은 이동이 아니라 **1홉 이웃 필터**다. 끌어 옮긴 위치는 저장되지 않는다.

### 트레이스 탐색

점 하나 = 트레이스 하나인 산점도(세로는 지연 로그 눈금, 붉은 점 = 오류)에서 드래그로 시간·지연 범위를 좁히고, 목록에서 골라 상세로 간다. 상세는 **워터폴**(스팬 트리·시간 막대·크리티컬 패스 강조)과 **플레임**(같은 이름 스팬을 합친 뷰), 서비스별 시간 비율, 브라우저에서 시작한 요청이면 맨 위 Browser 행을 보여 준다. 비동기로 이어진 다른 트레이스는 링크 표시로 오갈 수 있다.

- 목록 건수를 요청 수로 읽지 않는다 — 정본은 메트릭이다.
- `느림(추정)` 배지는 서버 고정 2초 기준이라 수집기의 느림 임계와 다를 수 있다.
- 7일이 지나면 "만료됨"으로 열리지 않는다. 에러 그룹·DB 그룹·배치 실패에서 오는 링크도 같다.
- 워터폴은 **끝난 스팬**만 보여 준다. "지금 몇 개가 병렬로 돌고 있나"는 실시간 관제의 진행 중 요청이 답한다.

### 합성 감시

Zabbix 웹 시나리오로 밖에서 URL을 주기적으로 두드려 "지금 열리나·얼마나 걸리나·어느 단계에서 막히나"를 본다. 계측을 붙일 수 없는 레거시·서드파티 앱의 가용성이나 "앱은 살아 있는데 밖에서 안 열린다"는 신고에 쓴다.

- 목록: 시나리오마다 마지막 결과·실패 사유(한글 분류 + Zabbix 원문)·24시간 가용성·60분 p95·주기·감시 위치(어느 프록시가 두드리나). 만들기·수정 서랍에서 단계별 URL·기대 코드·필수 문자열·헤더·인증·변수·본문을 넣는다.
- 상세: 단계별 응답 시간 누적 차트, 응답 코드 타임라인(칸 하나 = 실행 1회), 30일 가용성 캘린더, 같은 URL을 재는 형제 시나리오 비교.
- 서비스에 연결하면(서비스 상세 › 합성 감시 탭) 그 서비스의 **중단(DOWN)** 판정 근거가 된다.
- 정본은 우리 DB가 아니라 **Zabbix**다. Zabbix에서 바꾸면 바로 반영되고 지우면 취소선으로 남는다. 실행 위치는 시나리오가 아니라 호스트가 정한다(호스트의 프록시를 바꾸면 그 호스트의 감시가 전부 옮겨 간다).
- 가용성 24시간과 p95 60분은 **기간이 다르다.** 캘린더가 30일을 못 채우는 것은 Zabbix 이력 보존 때문이고 빈 날은 0%가 아니다. `—`도 0%가 아니라 미실행이다.
- 삭제하면 결과 이력까지 지워진다. 멈추려면 '사용'을 끈다. 쓰기는 편집 권한이 필요하다.

### SLO

서비스마다 "7일 또는 30일 동안 가용성(또는 지연) 99.9%" 같은 목표를 두고, 현재 SLI·남은 에러 버짓·소진 속도(번 레이트)·상태(정상/주의/위반/판정 불가)를 본다. 상세에는 에러 버짓 게이지, 번다운(단조 감소), SLI 추이, 30일 캘린더, 번 알람 설정이 있다.

- 번 알람을 켜면 알람 규칙에 `SLO 소진` 종류가 자동으로 생겨 Zabbix로 나간다. 알람 규칙 화면에서는 이 종류를 직접 만들 수 없다.
- `—`는 0%가 아니라 못 잰 것이다. 표(롤링 창)와 캘린더(자정 기준 날짜)는 정확히 같지 않다.
- 정의(목표·창)를 바꿔도 과거는 다시 계산하지 않는다. 삭제는 400일치 스냅샷까지 지우니 잠시 안 볼 거면 '사용'을 끈다.

### 수집기

탭 5개: **상태 / 토큰·설정 / 설치 가이드 / 등록·설정 / 브라우저(RUM)**. 관리자 전용이다.

- **상태**: 등록된 Collector마다 버전·마지막 수신·큐 적체·전송 실패 누계. `—`는 0이 아니라 그 지표가 오지 않은 것이다. 누계는 수집기를 재시작하면 0으로 돌아간다. 아래에 **최근 60초 수신 확인**('지금 확인' 버튼)과 **폐기·변형 통계**(받았지만 저장하지 않은 것과 그 이유)가 있다.
- **토큰·설정**: 수신 토큰 발급·회수, 설정 파일(yaml) 생성(서버 주소·큐 경로·느림 임계·정상 트레이스 표본 %·메모리 상한·원문 SQL 보존·Kubernetes 옵션). **토큰 원문은 발급 응답 한 번에만 보인다.** 서버는 해시만 갖고 있어 다시 알려 줄 수 없다.
- **설치 가이드**: OS(Windows/Linux/macOS) × 스택(Java/.NET/Node/Python/Go)별 Collector 설치·앱 계측·확인 절차와 출처 링크. 화면이 서버에서 받아 그대로 그리므로 설치본 설정(사내 미러 등)이 반영된다. 문서판은 [수집기 설치](solutions--%EC%88%98%EC%A7%91%EA%B8%B0-%EC%84%A4%EC%B9%98.md).
- **등록·설정**: 새 서비스 등록 방식(자동 / 승인 / 사전 등록만), 자동 숨김(일), 수신 끊김 판정(분), 기본 오류율·p95 임계, 서비스당 route 상한, SQL 마스킹·원문 SQL 보존, 승인 대기 목록, 이름 없는 앱 목록.
- **브라우저(RUM)**: 브라우저용 공개 토큰 발급(허용 origin·초당 상한·본문 상한·일 예산), origin 편집, 앱에 넣을 스니펫과 CSP·CORS 안내. Collector 토큰을 브라우저에 넣지 않는다.

### 사용자 경험 (RUM)

앱에 스니펫을 넣으면 실제 사용자 브라우저에서 Web Vitals(LCP·INP·CLS·TTFB·FCP)·페이지뷰·세션·JS 오류가 5분 단위로 들어온다. 목록에는 Vitals 분포 5카드(좋음/보통/나쁨 관측 수와 p75), PV·세션 추이, 브라우저/OS/국가 힌트 분포, 페이지 그룹 표가 있고, 그룹을 누르면 페이지 로드 timing(이름별 평균) 워터폴·리소스·JS 오류 그룹·연결된 백엔드 트레이스 링크를 본다.

- 세션은 GA와 정의가 다르다(5분 버킷별 고유 세션의 합). 다른 도구와 비교할 때는 PV로 비교한다.
- 국가는 GeoIP가 아니라 헤더·언어 **힌트**다.
- 눈금은 항상 5분이라 15분 창에는 점이 3개다.
- 브라우저가 보내는 공개 데이터라 서버 지표와 섞지 않는다.

### 실시간 관제 (선택 기능 — 기본 꺼짐)

메뉴 `실시간 관제`는 서버가 DB를 거치지 않고 메모리에서 1초마다 흘려 보내는 화면이다. 15분(진행 중 요청은 90초)이 지나면 사라지고 서버를 재시작하면 빈 화면에서 다시 시작한다. 켜려면 서버 설정·수집기 설정·앱 실행 옵션이 함께 필요하다(관리자 가이드 §8).

- **요청 관제 탭**: 전체 TPS·p95·오류율 게이지, 서비스 타일, 완료 요청 지연 구간 차트. 1초마다 움직이는 값은 **방금 끝난 요청**의 집계다.
- **진행 중 요청 카드**(요청 관제 탭 안): 앱 JVM에 MovesEye 자바 확장을 붙인 서비스에서만 값이 뜬다. 왼쪽 위 원판 3개(1초 미만·1~5초·5초 이상)와 요청 흐름 무대(왼쪽에서 들어오는 공 = 새 요청, 가운데 동전 = 처리 중 요청 하나, 오른쪽으로 나가는 공 = 끝난 요청 — 빨강은 오류), 아래에 처리 중 요청 목록(경과·주소·지금 실행 중인 DB 쿼리/외부 호출·trace). 확장이 없는 서비스는 "확장 없음"으로 뜬다 — 0건이 아니라 볼 수 없다는 뜻이다.
  - 동전과 원판 숫자는 "지금 떠 있는 요청 + 최근 1.5초 안에 들어왔거나 끝난 요청"이라 1초 스냅샷보다 조금 클 수 있다(옅은 점선 동전이 그 몫).
  - 공 하나가 요청 하나는 아니다(폭주 때는 공 하나가 여러 건). 정확한 양은 초당 건수 숫자다.
  - 주소의 ID·SQL 값은 가려져 있다.
- **X-View 탭**: 점 하나 = 끝난 요청 하나. 표시 n / 관측 m 배지가 항상 붙는다.
- **여러 명이 같이 봐도 된다.** 서버는 같은 화면 조건이면 한 번만 계산해 나눠 보낸다. 화면 위쪽에 "내 연결 n/4 · 전체 시청 a/40"이 보인다 — n은 이 계정으로 열어 둔 실시간 탭 수(숨긴 탭도 센다), 4와 40은 서버 설정값이다. 동시 시청 상한에 닿으면 "입장 대기 중" 안내가 뜨고 앞사람이 나가면 자동으로 시작한다 — 고장이 아니다. 안 쓰는 탭은 닫거나 헤더의 **연결 끊기**를 누르면 그 자리가 바로 돌아온다(누른 탭은 "다시 연결"을 눌러야 다시 받는다). 느린 회선에서는 그 화면만 간격이 성기어지거나 잠깐 재접속하며 다른 사람 화면에는 영향이 없다. 켜는 법과 상한 조정은 관리자 가이드 §8.

### 사이드바에 없는 화면 — 에러 분석 · DB 호출 분석 · 외부 호출 분석 · 메시징·배치

주소(`/errors`, `/db-calls`, `/dependencies`, `/messaging`)나 전역 검색으로 들어간다. 앞 셋은 서비스 상세의 같은 이름 탭과 본체가 같고 서비스 선택만 필터로 바뀐다 — 서비스를 고르지 않으면 같은 예외·같은 쿼리·같은 주소가 서비스별로 여러 줄 나오는데, 그 상태가 곧 "어느 서비스에서 문제인가"의 답이다.

**메시징·배치**는 서비스 탭이 없는 독립 화면이다. 큐·토픽별 처리량과 소비 지연, 배치 잡별 마지막 실행·성공률·간트를 보고 실패 실행에서 트레이스로 간다. 배치 화면이 비어 있으면 대개 앱이 `job.name` 규약대로 스팬을 안 보내는 것이다(빈 상태에 규약이 적혀 있다). 실행 중인 잡은 끝나야 나타난다.

## 공통으로 알아 둘 것

### 시간 범위와 눈금

- 프리셋 **15분·1시간·6시간·24시간·7일·30일** 또는 사용자 지정. 기본은 1시간.
- 점 간격은 창 길이로 자동 결정된다(6시간 이하 1분 · 7일 이하 5분 · 그 이상 1시간). 서버는 1분 데이터를 7일, 5분을 30일, 1시간을 400일 보존한다. 스팬은 7일이다. 보존 기간은 설정 › 리포트 관리 › APM 탭에서 바꾼다.
- 시간 범위·env·탭·선택 엔드포인트 등 **화면 상태는 URL에 실린다.** 주소를 복사해 넘기면 같은 화면이 열린다.
- 자동 새로고침: 끔(기본)·30초·1분·5분.

### `—`와 `0`은 다르다

- 값이 없는 구간은 `—`(표), 끊긴 선(차트), 빈 칸(히트맵·띠)이다. 0으로 채우지 않는다.
- 요청수 차트의 0은 "요청이 없었다"는 측정된 사실이고, 오류율·응답시간·Apdex는 요청이 없으면 계산이 안 되어 `—`다.
- 예외는 목록의 스파크라인 하나다 — 모양만 보는 칸이라 값 없음을 0으로 접어 그린다.

### 권한

- 조회: 역할의 애플리케이션 모니터링 › APM **보기** 권한. 라이선스에 `APM` 기능이 없으면 메뉴가 잠긴다.
- 쓰기(서비스 설정·삭제, 알람 규칙 **조회·편집**, SLO·합성 감시 만들기, 수집기 화면 전체): APM **편집** 권한(관리자 역할은 기본 포함). 내보내기는 보기 권한으로 된다. 편집 권한이 없으면 설정 탭은 읽기 전용이고 수집기 메뉴는 사이드바에서도 보이지 않는다.
- 스택 트레이스·SQL 원문 열람은 관리자 역할만.

최근 5분(설정 '수신 끊김 판정(분)', 기본 5) 데이터로 판정하며, 위에서 아래 순서로 첫 번째 맞는 것이 상태다.

| 상태 | 조건 | 조치 |
|---|---|---|
| **확인 불가** (UNKNOWN) | 이 서비스가 5분 이상 미수신인데 **등록된 수집기도 전부 5분 이상 미보고** | 앱이 아니라 **파이프라인**(Collector·네트워크·토큰·라이선스)을 먼저 본다. 이때 앱을 재기동하면 사고가 된다 |
| **수신 끊김** (STALE) | 5분 이상 미수신인데 수집기는 살아 있음. 새 버전 인스턴스가 처음 나타난 뒤 **10분은 유예** | 앱 프로세스·에이전트를 본다 |
| **성능 저하** (DEGRADED) | 수신은 있고 최근 5분 **오류율 > 임계(기본 5%)** 또는 **p95 > 임계(기본 2000ms, 서비스 설정의 '느림 임계'가 있으면 그 값)** | 배지 툴팁의 근거를 보고 트랜잭션 탭으로 |
| **중단** (DOWN) | 연결된 합성 감시 시나리오가 실패했을 때 | 합성 감시 탭에서 실패 사유를 본다. 시나리오를 연결하지 않은 서비스는 이 상태가 나오지 않는다 |
| **정상** (UP) | 위 어느 것도 아님 | — |

- 요청이 0건인 5분은 임계 판정을 건너뛴다 — 야간 저트래픽 서비스가 성능 저하로 찍히지 않게.
- 성능 저하와 수신 끊김은 같은 노랑이다. 색만 보지 말고 배지 안 문구를 본다.
- 확인 불가 판정은 전역이다. 수집기가 여러 대이고 한 대만 끊긴 환경에서는 그 서비스가 수신 끊김으로 보인다.
- 인스턴스 상태는 정상/수신 끊김 둘뿐이다.

## 알람 규칙 (설정 ⚙ > 알람 규칙)

**판정은 MovesEye가 5분마다 하고, 배달은 Zabbix가 한다.** 규칙을 만들면 Zabbix에 호스트 그룹·호스트 `MovesEye APM`(인터페이스 없는 가상 호스트) 아래 전용 트래퍼 아이템·트리거가 자동 생성되고, 평가 결과 값이 밀려 들어가 Zabbix Problem이 뜬다. 그래서 기존 Zabbix 액션·미디어(메일·Slack·Teams)·에스컬레이션·유지보수 창·이 앱의 Problem 화면이 그대로 붙는다. 알림 채널을 새로 만들지 않는다.

### 규칙 종류

| 종류 | 임계 단위 | 값의 뜻 | 범위 |
|---|---|---|---|
| 오류율 | % | 판정 창 안 5xx ÷ 전체 × 100 | 전역 / 서비스 |
| 응답시간 p95 | ms | 판정 창 안 p95 | 전역 / 서비스 |
| 수신 끊김 | 분 | 마지막 수신 이후 경과 분 | 전역 / 서비스 |
| 수집기 전송 실패 | 건 | Collector가 MovesEye로 보내다 실패한 누적 증분 | 전역 전용 |
| 액티브 요청 급증 | 배 | 최근 5분 평균 ÷ 직전 5분 평균 | 전역 / 서비스 |
| 요청 걸림 | ms | 처리 중인 요청 하나가 이 시간을 넘긴 채 아직 안 끝남(자바 확장 설치 서비스만). 5분 배치가 아니라 1초마다 판정 | 전역 / 서비스 |
| SLO 소진 | 배 | 에러 버짓 소진 속도(번 레이트). **SLO 화면의 번 알람을 켜면 자동 생성** — 여기서 직접 못 만든다 | 서비스(SLO) |

- 기본 시드: 전역 **오류율 5% / 5분**, **p95 2000ms / 5분**, **요청 걸림 60초**(셋 다 켜짐). 요청 걸림 60초는 앞단 프록시(nginx·ALB)가 연결을 끊는 시간에 맞춘 값이다 — 프록시 타임아웃을 바꿨으면 같이 맞춘다. 요청 걸림은 판정 창이 없다(넘긴 시간 자체가 지속 시간).
- 같은 종류의 서비스별 규칙이 있으면 그 서비스에서는 전역 규칙이 적용되지 않는다(같은 문제로 두 번 울리지 않게).
- 종류·범위는 수정할 수 없다(Zabbix 아이템 키에 들어간다). 바꾸려면 새로 만들고 지운다.
- 삭제하면 Zabbix 아이템·트리거도 지워진다. 발화 이력은 남는다.
- 규칙 편집 서랍의 **미리보기**는 최근 24시간 실제 값에 그 임계를 적용하면 몇 번 울렸을지 보여 준다. 저장과 무관하다.

### 탭 4개

- **규칙**: 규칙 표·사용 스위치·Zabbix 동기화 배지·재동기화·편집 서랍.
- **발화 이력**: 기간 안에 열려 있던 알람 띠 + 이벤트 표(종류·서비스·발화 값·발화/해소·지속·Zabbix 이벤트 링크). Zabbix 이벤트 id는 다음 평가 주기(5분)에 붙으므로 방금 발화한 것은 `—`다.
- **요청 걸림**: 임계를 넘긴 채 처리 중이던 **요청 한 건이 한 줄**인 장부(발화 이력은 서비스 단위다). 상태(걸림·끝남·관측 끊김·규칙 꺼짐), 요청 주소, 감지 시각, 경과(감지 시 / 최대), 그때 실행 중이던 DB 쿼리·외부 호출, 인스턴스, trace. "관측 끊김"은 끝났다는 뜻이 아니라 인스턴스나 확장이 사라져 더 볼 수 없었다는 뜻이다. 서비스에 걸린 요청이 생기면 발화 이력과 Zabbix Problem에도 서비스 단위 알람이 하나 열리고, 전부 풀리면 닫힌다. 90일 보관.
- **Zabbix 상태**: 배달 경로 진단. 아래 배너가 여기 뜬다.

### "알림 액션 없음" 배지 — Zabbix 액션 연결

이 배너가 있으면 **알람이 떠도 아무에게도 안 간다.** MovesEye는 액션·미디어를 절대 대신 만들지 않으므로 고객의 Zabbix에서 한 번 연결해야 한다.

1. Zabbix 프런트엔드 > 알림(Alerts) > 액션 > **트리거 액션**을 새로 만들거나 기존 것을 연다.
2. 조건에 다음 중 하나를 추가한다.
   - **호스트 그룹** = `MovesEye APM`
   - **이벤트 태그** `owner` = `moveseye-apm` (또는 태그 `owner`가 있기만 하면)
3. 오퍼레이션(보낼 사용자·미디어)은 기존 메일·Slack·Teams 미디어를 그대로 쓴다.
4. 액션을 **활성**으로 두고, MovesEye 알람 규칙 > Zabbix 상태 탭을 새로고침해 '알림 액션 수'가 1 이상인지 본다.

### Zabbix 동기화 배지 읽는 법

우선순위는 나쁜 쪽부터다: **생성 실패 > 설정 다름 > Zabbix 반영 중 > 정상**.

| 배지·배너 | 뜻 | 조치 |
|---|---|---|
| Zabbix 반영 중 | 방금 만든 아이템을 Zabbix 서버 설정 캐시가 아직 모른다(기본 10초 갱신) | 기다린다. 2분 넘으면 '생성 실패'로 바뀐다 |
| 설정 다름 | 누군가 Zabbix에서 트리거 표현식을 직접 바꿨다(매일 02:00 검사) | 자동으로 되돌리지 않는다. 규칙 탭 재동기화에서 OURS(우리 값 적용) / THEIRS(Zabbix 값 채택) 선택. 수신 끊김·SLO 소진은 THEIRS를 막는다 |
| 생성 실패 | 아이템/트리거를 못 만들었거나 첫 push가 2분 넘게 실패 | Zabbix 연결·API 계정 권한 확인. 트리거가 지워졌으면 배치가 재생성한다 |
| 연결 불가 | Zabbix API 호출 자체가 실패 | 판정은 계속되지만 알림은 안 나간다. 설정 > 데이터 소스의 Zabbix 주소·계정 확인 |
| 권한 의심 | 바인딩은 있는데 API 계정에 보이는 아이템이 0 | Zabbix API 계정에 호스트 그룹 `MovesEye APM` 읽기 권한 부여 |
| NOT_SUPPORTED 아이템 | Zabbix가 값 타입 불일치로 아이템을 중단 | push는 성공으로 보이지만 값이 안 쌓인다. 바인딩 오류의 원문을 본다 |

## 리포트 — 설정 › 리포트 관리

주간(매주 월요일)·월간(매월 1일) APM 리포트가 자동으로 만들어져 호스트 그룹 리포트와 한 표에 섞여 나온다('종류' 열로 구분). 본문은 기간 합계와 직전 기간 대비 증감, 서비스별 RED·가용성·배포·알람·SLO 성적·상위 예외 5개다. PDF·이미지로 저장할 수 있고 개요의 "지난주 리포트" 버튼이 여기로 온다.

- APM 데이터 보존 기간(1분·5분·1시간·스팬)도 이 화면의 APM 탭에서 정한다. 관리자 전용이다.

## 자주 묻는 것

**Q. 오류율이 높은데 404 때문인가?**
아니다. 오류율은 **5xx만** 센다. 404·401 같은 4xx는 클라이언트 오류로 보아 제외한다. 4xx가 많은지는 트랜잭션 탭의 상태코드 분포(노란 층)에서 본다.

**Q. '수신 끊김'과 '확인 불가'는 무엇이 다른가?**
둘 다 5분 이상 데이터가 안 온 상태다. 차이는 **수집기**다. 수집기가 살아 있으면 앱 쪽 문제로 보아 '수신 끊김', 수집기까지 조용하면 앱이 죽었는지 파이프라인이 끊겼는지 알 수 없어 '확인 불가'다. 확인 불가일 때는 앱을 재기동하지 말고 Collector·네트워크·토큰(401)·라이선스(403)를 먼저 본다.

**Q. 앱에 에이전트를 붙였는데 서비스가 안 보인다.**
순서대로 본다. (a) 수집기 > 상태 탭의 '최근 60초 수신 확인' — 수신이 없으면 Collector가 서버에 못 보내는 것이다(주소·토큰·방화벽). Collector는 401/403을 영구 실패로 보고 **즉시 폐기**하므로 토큰 오타·라이선스 만료는 조용히 데이터를 잃는다. (b) 등록·설정 탭의 등록 방식이 '승인'이면 서비스가 **승인 대기**에 쌓여 목록에 안 뜬다(기본은 자동). (c) 앱이 `OTEL_SERVICE_NAME`을 안 주면 `unknown_service`로 와서 등록이 거부된다 — 등록·설정 탭의 '이름 없는 앱'에 보인다. (d) '숨긴 서비스 포함'을 켜 본다(14일 미수신 시 자동 숨김). (e) 화면 전체가 잠겨 있으면 라이선스에 `APM`이 없는 것이다. (f) Collector 자기 지표(`otelcol-contrib`)는 서비스로 등록되지 않는다 — 정상이다. 자세한 절차는 [수집기 설치 — 문제 해결](solutions--%EC%88%98%EC%A7%91%EA%B8%B0-%EC%84%A4%EC%B9%98.md#문제-해결).

**Q. 요청수가 0 rps인데 죽은 것인가?**
요청수 차트의 0은 "그 구간에 요청이 없었다"는 측정값이다. 정말 수신이 끊겼는지는 헤더 상태(수신 끊김/확인 불가)와 24시간 가용성 띠의 색으로 가른다.

**Q. p95가 튀는데 '표본 부족' 배지가 있다.**
관측이 20건 미만인 구간이 있다는 뜻이다. 백분위는 히스토그램 버킷 안을 보간해 구하므로 관측이 적으면 오차가 크다. 기간을 넓혀 step을 키우거나, 트래픽이 적은 서비스면 p50을 함께 본다. 배지 없이 p95만 튀면 실제 꼬리 지연이다.

**Q. 인스턴스 탭 지표가 전부 `—`다.**
선택한 시간 범위가 **7일을 넘었을 때** 그렇다. 인스턴스 축은 1분 데이터에만 있고 1분 데이터는 7일 보존이다. 상단 배너가 안내한다. 기간을 7일 이내로 좁힌다.

**Q. 트레이스 탐색의 건수와 트랜잭션 탭의 호출수가 다르다.**
트레이스는 **샘플**이다. 느린 것·실패한 것은 다 남기고 정상 요청은 설정한 비율만 남긴다. 요청 수·오류율의 정본은 메트릭(개요·트랜잭션)이고, 트레이스는 "그중 하나를 파 보는" 용도다. 서비스 맵·에러·DB·외부 호출 화면의 숫자도 같은 이유로 실제보다 오류 비중이 크게 보일 수 있다.

**Q. 서비스 맵에 방금 띄운 서비스가 없다.**
맵은 5분마다 트레이스를 접어 그리고 최대 8분 늦다. 그 안에 요청이 한 번도 안 지나갔거나 샘플에 안 걸렸으면 아직 안 보인다. 서비스 목록에 있고 수신이 있으면 정상이다.

**Q. 알람이 '열림'인데 Slack/메일이 안 온다.**
MovesEye는 판정과 Zabbix 트리거 발화까지 책임지고 **배달은 Zabbix 액션**이 한다. 알람 규칙 > Zabbix 상태 탭에서 '알림 액션 없음' 배너를 확인하고 위 절차대로 액션 조건을 추가한다. '연결 불가'면 Zabbix API 자체가 안 되는 것, 동기화 배지가 '생성 실패'면 울릴 아이템이 없는 것이다.

**Q. 런타임 탭이 비어 있다(.NET / Node / Python 서비스).**
실제 앱으로 확인된 런타임은 JVM이다. 다른 런타임은 지표 자리가 있지만 에이전트가 그 이름으로 보내지 않으면 '계측 미제공' 배지가 보인다. HTTP·DB·트레이스는 정상이다.

**Q. 배포 탭에 배포가 안 잡힌다.**
자동 감지는 `service.version`이 바뀐 새 인스턴스를 보고 기록한다. 같은 버전을 다시 배포했거나, 앱이 `service.version`(`OTEL_RESOURCE_ATTRIBUTES`)을 안 보내면 못 잡는다. CI/CD 마지막 단계에서 배포 탭이 알려 주는 웹훅 한 줄(deploy 토큰)을 부르면 확실하다.

## 정직한 한계

- **로그 탭 없음**(다음 단계), **코드 레벨 프로파일링 없음**, SaaS 없음.
- 트레이스 기반 화면(맵·에러·DB·외부 호출·메시징)은 **샘플** 기준이다. 정본 숫자는 메트릭이다.
- 1차 목표 규모는 **서비스 50 · 트레이스 일 2천만 이하**. 그 이상은 저장소 승격이 필요하다.
- 런타임 탭은 **JVM**만 실제 앱으로 확인됐다.
- 진행 중 요청·요청 걸림은 **자바 + MovesEye 확장 jar를 붙인 서비스**에서만 된다. 다른 언어는 아직이다. 진행 중 요청은 저장하지 않으며(90초 뒤 사라짐) 임계를 넘긴 것만 장부에 남는다.
- Kubernetes는 인스턴스 탭의 파드·노드·재시작·OOM 정보까지다. 클러스터 자원 모니터링은 아니다.
- RUM의 세션·국가는 근사값이다(위 사용자 경험 절).
- 게이트웨이 Collector는 **사이트당 1대**만 지원한다(active-active 미지원 — 이유는 [수집기 설치](solutions--%EC%88%98%EC%A7%91%EA%B8%B0-%EC%84%A4%EC%B9%98.md)).
- 라이선스가 만료되면 수신이 403이 되고 Collector가 데이터를 **즉시 폐기**한다. 나중에 갱신해도 그 사이 데이터는 돌아오지 않는다.
- Collector 자체의 운영(업그레이드·모니터링 대행)은 하지 않는다. 설정 생성과 상태 가시화까지다.

## 지원 담당자를 위한 안내

- "메뉴가 잠겨 있다" → 라이선스에 `APM` 기능이 없는 것. 설정 > 라이선스에서 프리미엄 모듈 포함 여부 확인.
- "메뉴가 열리는데 서비스가 없다" → 수집기 설치 전이거나 수신이 안 되는 것. 위 FAQ 순서대로.
- "수집기 메뉴가 안 보인다" → 그 계정에 APM 편집 권한이 없는 것. 고장이 아니다.
- "서비스 맵·트레이스가 비어 있다" → 트레이스 수신이 안 되는 것. 수집기 설정에 트레이스 파이프라인이 있는지, 폐기 통계에 `SIGNAL_NOT_SUPPORTED`·샘플링 드롭이 쌓이는지 본다. 방금 띄운 서비스면 8분 기다린다.
- "로그 탭이 안 열린다" → 아직 제공하지 않는 화면. 고장이 아니다.
- "알람은 뜨는데 연락이 안 온다" → Zabbix 액션 연결(위 절차). MovesEye가 아니라 Zabbix 쪽 설정이다.
- "실시간 관제에 입장 대기가 뜬다" → 동시 시청 상한. 관리자 가이드 §8-3.
