# 백로그 — 클라우드 스냅샷 배치의 리전 팬아웃·주기 재검토

> 발견 2026-09-16 (로컬 APM 서비스 맵에서 EC2 노드 17개가 드러나면서) · 상태 **미착수(설계 전)** · 관련 [[aws-zero-cost-charting]]

## 1. 무엇이 문제인가

`cloud_snapshot` 배치가 **5분마다 활성 리전 전부**에 EC2 Describe 계열을 병렬 호출한다. 리전 화이트리스트가 없어서, 고객이 서울 한 곳만 쓰더라도 옵트인된 17개 리전을 모두 두드린다.

| 항목 | 현재 |
|---|---|
| 주기 | 5분 고정 (V28 시드 `interval 5`, `enabled=TRUE`) |
| 대상 리전 | `AwsReadOnlyGateway.enabledRegionNames()` — 미옵트인만 제외, 나머지 전부(표준 계정 ≈17) |
| 호출량 | 17리전 × 12회/시 = **시간당 204회, 하루 약 4,900회** |
| 수집 항목 | 인스턴스·인스턴스 상태·VPC·서브넷·보안그룹·라우트테이블 |
| 과금 | 0 (무료 `Describe*`만, CloudWatch 미호출) |

과금은 없지만 **응답 대기·스레드·네트워크는 실제로 쓴다.** 로컬 APM 서비스 맵에서 리전별 엣지 p95가 300~1,700ms로 잡혔다.

### 같은 문제를 반쯤만 고친 이력
`AwsReadOnlyGateway.enabledRegionNames()` 주석에 실측이 남아 있다 — 2026-08-25에 "34개 중 17개 리전이 헛돌며 응답만 늦췄다"를 확인하고 **미옵트인 리전을 거른 것이 지금의 17개**다. 즉 "안 쓰는 리전을 도는" 문제는 절반만 해결된 상태다.

## 2. 왜 이 배치가 존재하나 (없애자는 이야기가 아님)

V28 주석의 근거는 유효하다.

- CloudWatch에는 **상태의 역사가 없다** — "인스턴스가 언제부터 stopped였나", "SG에 22번이 언제 열렸나"는 지표가 아니라 구성 정보다. VPC는 기본 지표 자체가 없다.
- **CloudWatch를 안 쓰는 고객이 있다**는 것이 이 설계의 전제(사용자 하드 제약: 과금 0).
- 무료 `Describe*` 결과를 버리지 않고 쌓으면 상태 시계열이 과금 0으로 생긴다.

→ **목적은 유지하고 팬아웃만 줄이는 것**이 이 백로그의 범위다.

## 3. 고칠 방향 (초안, 확정 아님)

### A. 리전 화이트리스트 (효과 큼)
설정에서 수집 대상 리전을 고르게 한다. 미선택이면 현행대로 활성 리전 전체(하위호환).

- 저장 위치 후보: `Setting(CLOUD)` 또는 `scheduler_setting.options`의 `regions: []`
- 서울만 고르면 호출이 **17 → 1**
- 화면: 클라우드 설정에 리전 다중 선택. 첫 저장 전에는 "전체(권장: 쓰는 리전만 고르세요)" 안내

### B. 자원별 주기 분리 (효과 중간)
인스턴스 상태와 구성 정보는 변화 속도가 다르다.

| 대상 | 성격 | 제안 주기 |
|---|---|---|
| 인스턴스·인스턴스 상태 | 자주 바뀜 | 5분 유지 |
| VPC·서브넷·SG·라우트테이블 | 드물게 바뀜 | 30분~1시간 |

구현은 배치를 둘로 쪼개거나(`cloud_snapshot` / `cloud_snapshot_config`), 한 배치 안에서 N회마다 구성 항목을 수집하는 방식.

### C. 빈 리전 백오프 (효과 작음, 선택)
연속 N회 자원 0건인 리전은 수집 주기를 늘린다. A를 하면 대부분 불필요해지므로 **A의 대안이지 병행 과제가 아니다.**

### D. 변화가 없으면 같은 행을 다시 쓰지 않는다 🔴 효과 가장 큼 (2026-09-16 실측으로 추가)

#### 실측 — dev DB, 2026-08-24~09-16(23일치)

| 테이블 | 행 수 | 크기 |
|---|---|---|
| `cloud_instance_snapshot` | 1,745 | 512 KB |
| `cloud_vpc_snapshot` | **29,665** | **23 MB** |

VPC가 정확히 **17배**다 — 인스턴스는 실제 1대라 1,745행인데, VPC는 **리전마다 기본 VPC가 하나씩** 있어 `17 × 1,745 = 29,665`가 됐다. **94%가 쓰지도 않는 리전의 기본 VPC 기록**이다.

#### 🔴 그런데 진짜 문제는 중복이다

| 항목 | 값 |
|---|---|
| 전체 행 | 29,665 |
| **서로 다른 구성**(region·vpc_id·subnet_count·instance_count·critical·warning·findings 기준) | **18** |

29,665행 중 의미 있는 조합은 **18개**다. 나머지는 5분마다 **똑같은 내용을 다시 적은 것**이다. 한 행이 약 812바이트이고 그중 `findings` jsonb가 평균 547바이트(최대 966)라, **같은 진단 결과를 2만 9천 번 복사해 저장**했다.

#### 운영 환경 추산

개발 PC는 꺼져 있는 시간이 있어 23일 동안 1,745회(하루 76회)만 돌았다. 24시간 돌면 하루 288회다.

| | 값 |
|---|---|
| 하루 | 288회 × 17리전 ≈ 4,900행 |
| 30일 보존 | 약 147,000행 · **약 115 MB** |
| 리전 1개로 줄이면(A안만) | 약 7 MB |
| **A + D를 같이 하면** | **1 MB 미만** |

#### 무엇을 바꾸나

상태가 **바뀔 때만** 행을 남긴다. 같은 상태가 이어지면 마지막 관측 시각만 갱신한다.

- 방식 ①: `run_at`을 `valid_from`·`last_seen_at` 두 칸으로 — 직전 행과 내용이 같으면 `last_seen_at`만 UPDATE.
- 방식 ②: 지금 구조를 두고 **직전 행과 동일하면 INSERT를 건너뛴다** — 가장 작은 변경이고, 조회는 "이 시각 이전의 마지막 행"을 읽으면 된다.

🔴 **타임라인 화면이 원하는 모양이 원래 이것이다.** 지금은 5분 칸을 이어 붙여 밴드를 그리는데, 변화 시점만 있으면 그 계산이 사라지고 질의도 단순해진다.

⚠️ **주의**: "값이 안 변했다"와 "수집을 못 했다"가 구분돼야 한다. 배치가 멈춘 구간을 "계속 정상이었다"로 읽으면 안 된다 → `last_seen_at`이 그 역할을 한다(이 값이 오래됐으면 관측이 끊긴 것).

⚠️ 기존 데이터 이관은 필요 없다. 보존 30일이라 **한 달 뒤 자연히 새 구조만 남는다.**

## 4. 착수 전 확인할 것

1. `enabledRegionNames()`를 쓰는 **다른 호출부**도 같이 좁혀야 하는가(추정 비용 등 "전 리전을 도는 코드"가 더 있다 — 주석이 그렇게 말한다).
2. 리전을 좁히면 **다른 리전에 있던 기존 스냅샷 이력**은 어떻게 되나(조회는 되고 갱신만 멈추는 것이 맞다 — 화면에 "수집 중지됨" 표시 필요).
3. 주기를 늘린 구성 항목의 **최초 발견 시각**(VPC 진단의 `firstSeenAt`) 정확도가 떨어지는 것을 받아들일 수 있나.
4. 개발 환경 기본값 — 로컬에서 AWS 자격증명이 있으면 지금도 5분마다 나간다. dev 프로필 기본 `enabled=false`가 맞는지.
5. (D안) 변화 판정 기준에 `findings` jsonb를 통째로 넣을 것인가 — 순서가 흔들리면 매번 "변함"으로 잡힌다. **정렬·정규화 후 비교**가 필요할 수 있다.

## 5. 당장의 회피책 (개발 환경)

설정 › 스케줄러 관리에서 `cloud_snapshot`을 끄거나 주기를 늘린다. 코드 변경 불필요.
