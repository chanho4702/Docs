요약

이 장에서는 외부 조회 API의 구현 가능 여부와 주요 실측 결과를 살펴본다.

  • 결론: 구현 가능하며, 워크포스에 API를 열고 개발 환경에서 호출까지 확인했다. 외부 시스템(인사·그룹웨어·BI 등)은 사용자가 동의하여 발급받은 토큰으로 워크포스의 조직 정보를 읽는다.
  • 응답 범위는 토큰 소유자가 워크포스 화면에서 볼 수 있는 범위다. 외부 API도 기존 화면의 권한 검사 로직을 그대로 거친다. 토큰의 scope(권한 범위)가 사용자의 기존 권한을 넓히지는 않는다.
  • 고객 측 설정 작업이 필요하다. 사이트 관리자는 앱 REST API를 켜야 한다. 연동 담당자는 OAuth 앱 생성·권한 연결·Client Secret(앱 인증 비밀 값) 보관을 담당하고, 토큰 소유자는 접근에 동의해야 한다.
  • Preview(정식 출시 전 공개) 기능이다. Jira·Confluence 앱만 지원하며, 기능 폐기 예고 기간이 짧을 수 있다.

1.2 공식 문서의 제약사항과 대응

제약(공식) 출처 워크포스 영향·대응
Preview — "may be subject to shorter deprecation windows" App REST APIs · API route 외부 API는 /v1/ 버전 경로를 사용한다. 응답에는 명시적으로 허용한 필드만 포함한다. 변경 시 v2 경로를 추가한다.
Jira·Confluence 앱만 지원, Isolated Cloud 미지원 API route 워크포스는 Jira 앱이므로 지원 대상이다. Isolated Cloud 고객은 사용할 수 없다.
사이트마다 기본적으로 꺼져 있음. 사이트·조직 관리자가 연결된 앱 화면에서 켜야 한다. 끄면 즉시 모든 호출을 차단한다. Access REST APIs 고객 관리자 작업이므로 설치 안내에 포함한다. 고객 가이드 1장에서 다룬다.
인증 수단은 3LO만 명시됨. API 토큰 등은 언급이 없다. 토큰은 고객 동의 후에만 발급되며, 매 호출에 필요하다. App REST APIs 연동 서버가 토큰을 보관하고 refresh token을 회전해야 한다. 고객 가이드 3·4장에서 다룬다.
3LO 앱은 해당 사이트 구성원만 생성 가능. 외부 업체가 직접 만들 수 없다. App REST APIs · Access REST APIs 고객 측 담당자가 생성해야 한다. 외주 연동 업체가 생성하려면 고객 계정이 필요하다.
custom scope는 앱·환경당 20개. 이름은 …:custom 형식이며 최대 93자 + 접미다. 이름 변경·비활성화·삭제 불가. Expose REST APIs 현재 read:organization:custom 1개를 teams·users에서 공용으로 사용한다. 실험용 read:probe:custom은 삭제할 수 없어 apiRoute에 매핑하지 않은 상태로 둔다. 새 scope는 신중히 추가한다.
scope는 환경별로 등록해야 한다. 앱 관리자만 등록할 수 있으며, apiRoute에 매핑하기 전에 등록해야 한다. Expose REST APIs 개발 환경마다 등록해 확인한다. 운영 환경에는 배포 전에 등록한다.
수신 형식은 application/json만 지원한다. 지원 메서드는 GET·PUT·POST·DELETE·PATCH이며, 응답에 statusCode가 필수다. API route · Expose REST APIs GET만 선언했다. 다른 메서드는 플랫폼이 404를 반환하며, 핸들러에 도달하지 않는다(실측).
경로 와일드카드는 *(한 칸)·**(여러 칸)를 지원한다. query(쿼리 매개변수)는 정확한 경로에 붙는다. Access REST APIs 고정 경로에 query(offset·accountId)를 붙여 사용한다.
3LO 앱에 Forge 제품 scope read:forge-app:jira 추가 필요. 필요한 scope만 추가해야 한다. Access REST APIs 읽기 전용이므로 write:는 추가하지 않는다. 고객 가이드 2-3에서 다룬다.
마켓플레이스 배포 시 REST API와 scope의 대응 관계를 설명하는 개발자 문서 공개 필요 App REST APIs · Expose REST APIs 고객 가이드 4장(요청·응답·오류)을 공개 문서로 다듬어야 한다.
environment-id·app-id는 앱마다 달라 고객에게 제공 필요. cloudId는 https://<사이트>/_edge/tenant_info로 조회한다. Expose REST APIs · Access REST APIs 기본 URL은 관리 화면(1단계)에 표시된다. 토큰의 accessible-resources가 빈 목록을 반환하므로(실측), cloudId는 tenant_info로 조회한다.
apiRoute 앱도 다른 조건을 모두 만족하면 Runs on Atlassian 자격을 얻을 수 있다. App REST APIs 워크포스는 webtrigger(dynamic)·egress(외부로 나가는 통신) 때문에 이미 자격 요건을 충족하지 못한다(앱 간 채널 문서).
refresh token은 회전 방식이다. 재사용 허용 시간은 10분이며, 90일 동안 사용하지 않으면 만료된다. OAuth 2.0 (3LO) — Jira 회전 결과를 원자적으로 저장한다. 90일 동안 사용하지 않으면 다시 동의해야 한다.
Callback URL — OAuth 앱의 Authorization 화면에 등록(최대 30개, 한 줄에 하나). 동의 URL·토큰 요청의 redirect_uri 는 등록값과 일치해야 함. code 유효 시간·재사용 여부는 문서에 없음 OAuth 2.0 (3LO) — Jira · 콘솔 화면 로컬 http://localhost 주소도 동작(실측). 고객 가이드 2-4 에 등록·처리 순서·자주 나는 문제 정리
실행 시간·크기·호출 한도: apiRoute 문서에는 수치가 없다. Forge 공통 Invocation limits는 요청 5MB, 설치당 분당 7,000·초당 300, 사용자당 분당 1,200이다. Invocation limits 페이지 크기를 사용자 20명·팀 10개로 작게 유지한다. 429 응답을 받으면 X-Ratelimit-Reset까지 대기한다.

2.2 구현 항목

항목 내용
custom scope read:organization:custom의 표시 이름은 "Read organization teams and users"다. 설명에 "인증된 사용자의 기존 워크포스 팀·사용자 관리 권한 안에서"라고 명시했다. 이 설명은 동의 화면에 그대로 표시된다. scope 정의 파일로 환경마다 등록한다.
apiRoute GET /v1/organization/users, GET /v1/organization/teams를 선언했다. 수신 형식은 application/json이며, 두 경로 모두 위 scope 하나를 사용한다.
핸들러: 호출자 신원 플랫폼이 제공한 principal.accountId·installContext만 신원 판단에 사용한다. query의 accountId는 조회 대상일 뿐이다. 다른 사이트의 cloudId가 섞이면 401을 반환한다.
핸들러: query 검사 허용 목록으로 검사한다. offset은 20의 배수이고, accountId는 1명 조회용이다. 둘을 동시에 지정하거나 알 수 없는 키를 보내면 400을 반환한다.
핸들러: 권한 검사 화면과 같은 기존 권한 검사 로직을 거쳐 조회한다.
핸들러: 실패 응답 권한·라이선스 오류는 403, 조회 대상이 없으면 404, 그 밖의 오류는 503을 반환한다. 그 밖의 오류에는 원인 문구를 포함하지 않는다.
핸들러: 응답 필드 명시적으로 허용한 필드만 응답에 포함한다.
테스트 신원·query 검사, 권한 거부(권한 없음 → 403), 응답 필드 허용 목록을 확인한다.

설계 원칙은 새 권한 로직을 만들지 않는 것이다. 외부 API도 화면과 같은 권한 검사 로직을 거친다. 따라서 화면에서 볼 수 없는 정보는 API로도 볼 수 없다.

3.4 재검증 절차

  1. 고객 가이드 1~3장에 따라 App REST API를 켜고, OAuth 앱을 생성한 뒤 사용자 동의를 진행한다.
  2. 측정 도우미 스크립트로 동의·호출·갱신을 확인한다. 명령은 consent(동의 서버), call <이름> <token|none|bogus|nosns> <site|svc> <GET> <경로>, refresh다. 사용자가 Client ID·Client Secret을 별도 파일에 직접 저장해야 한다. 스크립트는 해당 값을 출력하지 않는다. Git Bash에서는 경로 인자가 변환되므로 MSYS_NO_PATHCONV=1을 설정한다.
  3. 검증을 마치면 검증용 OAuth 앱을 삭제하거나 Client Secret을 재발급한다. 사용자 동의를 철회하고 토큰 파일도 삭제한다.
