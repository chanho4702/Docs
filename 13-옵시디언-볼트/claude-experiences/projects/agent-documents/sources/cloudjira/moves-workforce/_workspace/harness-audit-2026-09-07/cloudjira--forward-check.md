# feature-harness 읽기 전용 드라이런 평가

평가일: 2026-09-07. 기준 HEAD: `6ff54d3a96989505317ce9dce53ff6e30c06d241`. 작업 트리에 기존 앱·번역·문서 변경이 있으므로 HEAD만으로 현재 상태를 대표하지 않는다. 이 평가는 실제 앱 구현 성공 여부가 아니라 현재 지침을 적용했을 때의 판단을 검토한다.

실제로 읽은 자료: 루트 `AGENTS.md`, `CLAUDE.md`, `.agents/skills/feature-harness/SKILL.md`, `references/verification.md`, `feature-design`, `forge-backend-dev`, `forge-frontend-dev`, `integration-verify`의 `SKILL.md`, `.codex/agents/`의 TOML 4개, 루트·프론트 `package.json`, manifest runtime 선언, 경험 INDEX 및 `moves-workforce-documentation-baseline-sync` 노트. `references/scenarios.md`는 읽지 않았다. 앱 소스 수정, 테스트·빌드·구조 검사 실행, 배포, 새 에이전트 호출은 하지 않았다. 허용된 이 보고서만 작성한다.

## 공통 적용 규칙

- 아래의 실행·위임 설명은 실제 기능 요청이 주어졌을 경우의 계획이다. 이번 드라이런에서 실행했다는 뜻이 아니다.
- `feature-harness` 적용과 설계→백엔드→프론트→검증의 전체 단계 실행은 다르다. 작은 수정은 리더가 담당 스킬로 직접 처리한다. 설계만 요청하면 설계와 검토만 수행한다.
- 실제 작업 전 현재 코드, 기존 diff, 산출물과 검증 증거를 대조한다. 같은 기능은 기존 `_workspace/<slug>/`에서 재개하고, 상태 파일에 HEAD·기존 diff·소유권·남은 일·계약·검증 범위를 갱신한다. 오래된 산출물은 나이만으로 폐기하거나 그대로 신뢰하지 않는다.
- 에이전트를 새로 부를 때는 `collaboration.spawn_agent`에 실제 지원되는 `agent_type`, `task_name`, `message`를 사용한다. 목적, 저장소 절대 경로 `C:\CloudJira\moves-workforce`, 읽을 스킬, 작업 디렉토리, 입력, 소유 파일, 완료 조건과 타인 변경 보존을 명시한다. 모델은 상속한다. 리더도 독립 작업이 있을 때만 새 에이전트를 만든다.
- 실행 중 전달은 `send_message`, 유휴 작업 재개는 `followup_task`다. 오래된 ID는 `list_agents` 등 현재 상태와 대조한다. 협업 도구는 `functions.exec` 내부에서 호출하지 않는다. 지원 타입이 없으면 기본 타입에 TOML 지침·스킬을 전달하고, 위임 자체가 금지되면 리더가 같은 계약으로 처리한다.
- 실제 기능 수정의 필수 검증은 backend test, frontend test, `CI=true` 프론트 빌드, 앱 루트 `pwd` 후 `forge lint`다. 명령·작업 디렉토리·종료 코드·소스 상태를 기록한다. 같은 소스 상태와 범위가 입증된 기존 증거만 재사용한다. 미실행은 미검증, 확인된 결함은 실패이며 통과로 바꾸지 않는다. 브라우저·Jira 설치 확인은 테스트 통과와 별도다.

## 사례 1: 기존 집계 화면의 프론트 빈 상태 문구만 수정

**판정:** 하네스의 축소 경로를 적용한다. 리더가 `forge-frontend-dev`로 직접 처리하며 architect·backend·별도 verifier 에이전트 생성은 필요하지 않다. 기존 산출물이 2주 전이라는 사실은 현재 계약·검증의 증거가 아니다.

**순서와 도구:** `rg`로 현재 빈 상태 렌더링, `t()` 키, 해당 kr/en 원본과 공용 EmptyState 사용처를 찾는다. 현재 생산자·훅을 읽어 성공한 빈 데이터와 오류·권한 거부의 구분을 확인한다. 기존 작업 디렉토리의 요구사항·상태·프론트/백엔드 보고서를 현재 코드와 대조하고 요청 범위와 생략 사유를 간결하게 기록한다. 원본 번역 또는 필요한 최소 프론트 참조만 수정하고 `static/ui`에서 merge를 수행한다. 생성 번역은 직접 편집하지 않으며 merge와 빌드 출력은 한 담당자가 순서대로 갱신한다.

**바로 가능한 작업:** 현재 문구·공유 키 영향 조사, 백엔드 계약 읽기, 프론트 번역 수정 및 영향 검증. 원문에서 원하는 최종 문구가 정해지지 않았다면 화면 목적에 맞는 합리적인 표현을 선택할 수 있다. 공유 키라면 형제 화면에서 부적절한 표현이 되는지 먼저 확인한다.

**보류·생략할 작업:** 신규 설계와 백엔드 재구현은 변경 필요가 없으므로 생략 사유를 남긴다. 백엔드 오류를 빈 상태 문구로 숨기는 변경은 하지 않는다. 실제로 별도 백엔드 결함을 발견하면 근거와 요청 범위를 넘는 영향을 알리고, 문구 수정과 독립적으로 다룬다. 커밋·푸시·배포·설치는 이 요청에 포함되지 않는다. 2주 전 보고서만으로 검증을 생략하지 않는다.

**완료 근거:** 현재 성공 빈 결과에 의도한 문구가 표시되고 kr/en 키와 merge 결과가 일치한다. 실패·권한 거부가 빈 성공으로 바뀌지 않고, 공유 키 소비 화면에도 의도하지 않은 의미 변경이 없다. 최종 diff가 요청 범위와 일치하며 프론트 영향 검증과 공통 필수 체크의 유효한 증거가 있다. 문구만 확인하는 새 테스트를 불필요하게 추가하지 않는다. 리더가 상태·프론트 보고서에 변경 효과와 검증/미검증을 기록한다.

## 사례 2: 집계 화면 계속 구현, 백엔드 2회 실패, 설계 items와 실제 rows 불일치

**판정:** 기존 하네스 작업을 재개한다. 실패 횟수가 2회라는 이유로 종료하지 않으며, 미확정 응답에 의존하는 프론트 구현을 먼저 진행하지 않는다.

**순서와 담당:**

1. 리더가 현재 에이전트 상태, 두 실패의 재현 조건·로그·실제 코드와 기존 요구사항/설계를 대조한다. `items`와 `rows`의 위치뿐 아니라 Service 반환과 resolver 래퍼, nullable·빈 데이터·오류 계약, 프론트와 내부 Service·큐·트리거 소비자까지 `rg`로 조사한다.
2. 어느 계약이 요구사항을 만족하는지 판정한다. 의도된 `rows` 변경이면 architect 담당 계약, 모든 소비자, 검증 기대값을 함께 갱신한다. `items`가 요구 계약이고 `rows`가 구현 결함이면 백엔드를 수정한다. 주어진 정보만으로 둘 중 하나를 정답으로 단정하지 않는다. `items ?? rows ?? []` 같은 임의 호환 분기로 결함을 숨기지 않는다.
3. 기존 backend 담당자가 유휴라면 원인·확정 계약·소유 파일·완료 조건을 담아 `followup_task`로 재개한다. 실행 중이면 `send_message`로 전달한다. 같은 시도의 반복을 피하고 새 근거로 접근을 바꾼다. 범위가 명확하면 리더가 백엔드 작업을 직접 인수할 수 있으며, 동시 편집이 없도록 소유권을 전환한다. 공용 응답 계약을 실제 변경할 때는 architect의 설계 단계를 포함한다.
4. 계약과 백엔드 선행 결과가 확정된 뒤 기존 유휴 frontend 에이전트에 `collaboration.followup_task`를 사용한다. 실제 백엔드 소스·새 보고서·확정 shape·소유 프론트 파일·i18n/캐시 요구·완료 조건을 입력으로 전달한다. 새 frontend 에이전트를 중복 생성하거나 `send_message`만 보내 재개된 것으로 간주하지 않는다.
5. 관련 모듈이 완성되면 `integration-verifier`가 실제 생산자와 전체 소비자를 교차 검증한다. 기존 verifier가 있으면 재사용하고, 없다면 독립적인 리더 작업과 소유권을 확보하여 `spawn_agent`를 사용하거나 리더가 검증 스킬로 직접 수행한다. verifier 기본 소유권은 읽기 검토·검증·보고서이며 앱 수정은 별도 배정이 있어야 한다.

**바로 가능한 작업:** 실패 원인 조사, 계약 차이와 소비자 목록 정리, 현재 권한·등록 조사, 입력과 무관한 번역·레이아웃 등 독립 작업. 독립 작업도 파일이 겹치지 않고 필요한 계약이 확정되어야 한다. 리더는 요구사항 판정·소유권·검증 기준을 정리할 수 있다.

**보류할 작업:** 미확정 API를 소비하는 훅·테이블 바인딩, 백엔드 실패 상태를 성공으로 가정한 프론트 인계, 최종 통과 판정. 배포나 임의의 계약 덮어쓰기로 문제를 우회하지 않는다. 필수 정보가 정말 부족한 경우 그 정보에 의존하는 부분만 보류하고 독립 작업은 계속한다.

**완료 근거:** 요구사항과 확정 설계·실제 반환 shape·모든 소비자가 일치하고, 두 실패 원인이 해결되었다는 재현/재검증 증거가 있다. 등록·PermissionMap·데이터 범위와 성공/실패/빈 데이터 분기, 캐시 무효화·i18n을 검증한다. 최종 변경 상태의 필수 test/build/lint 결과 및 `02_backend_report.md`, `02_frontend_report.md`, `03_verify_report.md`, 상태 기록이 정합해야 한다. 기존 보고서 존재나 backend 담당자의 완료 주장만으로 완료하지 않는다.

## 사례 3: 일반 사용자와 팀장 범위가 다른 새 팀 인력 리포트 설계

**판정:** 하네스의 설계→설계 검토 단계까지만 수행한다. `feature-architect`/`feature-design`이 적합하다. 구현·배포 담당 단계는 요청 밖이다.

**순서와 담당:** 리더가 `_workspace/team-workforce-report/` 같은 작업 경로와 요구사항·설계 파일 소유권을 정한다. 새 architect를 호출한다면 입력·스킬·허용 파일·완료 조건을 전달하고, 리더는 동시에 일반 사용자/팀장별 완료 조건과 검토 항목을 정리한다. 독립 리더 작업이 없다면 리더가 설계 스킬을 직접 적용한다. architect는 유사 리포트와 실제 `TeamAnalyticsScope.resolveTeamAnalyticsScope(principal)`, PermissionMap·등록·Controller→Service 흐름, 공용 UI·쿼리키를 조사하고 실제 `파일:라인`, export와 응답 shape를 설계 근거로 기록한다. 리더가 요구사항·권한·빈 결과·실패·캐시 시나리오를 설계와 대조하여 검토한다.

**설계에 반드시 포함:** 일반 사용자와 팀장 각각의 호출 권한 및 실제 인력 행 범위, 소속·리딩 팀 및 하위 팀 처리, principal 누락의 fail-close, 허용·민감 필드, 형제 resolver 직접 호출 우회 방지. 메뉴 숨김과 서버 데이터 필터를 분리한다. 기존 범위 함수를 단일 출처로 사용하며 단순히 “일반 사용자=본인, 팀장=자기 팀”이라고 추측하지 않는다. 급여·비용이 포함되면 CostAccess와 SalaryVisibility를 함께 적용하고 일반 resource DTO의 salary 제외 및 PROJECT_COST 경로를 지킨다. 성공·실패·빈 결과 예시, 내부 소비자, 권한/필터별 쿼리키와 무효화, kr/en 키, 계층별 소유 파일·의존성·검증 시나리오를 명시한다.

**바로 가능한 작업:** 현재 정책·유사 코드 조사, 재사용 대상과 권한 행렬·응답 계약 초안, schema 필요성 및 UI/캐시 설계, 설계 검토. 주어진 범위 차이는 현재 공용 정책과 실제 코드로 먼저 구체화한다.

**보류할 작업:** 정책 근거 없이 권한 범위를 발명하는 결정, 앱 코드·테스트 구현, 명령 실행을 동반하는 앱 검증, manifest 변경·배포·설치. 현재 정책만으로 결정할 수 없는 제품 의도는 질문 또는 명시적인 미확정 사항으로 남긴다. 설계만 요청된 상황에서 구현 승인 질문을 불필요하게 추가하지 않는다.

**완료 근거:** `01_architect_design.md`의 8개 구성 항목이 실제 소스 근거와 연결되고, 일반 사용자·팀장·무권한·principal 누락·형제 경로·민감 필드·권한 전환 캐시의 기대 동작이 검토되었다. 구현 가능한 계약과 남은 의문/가정이 분리되어 있다. 핵심 권한 결정이 미확정이면 해당 계약은 확정 완료로 보고하지 않는다. 설계 검토 완료를 앱 구현·런타임 검증 완료로 표현하지 않는다.

## 입력별 시작 여부

여기서 “시작”은 필요한 단계만 선택하는 feature-harness 작업 경로의 시작/재개를 뜻한다. 작은 수정에 전체 4단계나 새 에이전트를 강제한다는 뜻은 아니다.

| 입력 | feature-harness 파이프라인 시작 | 이유·실행 범위 |
|---|---|---|
| RFC 문서 표현만 다듬어줘 | 아니요 | 기능 변경 없는 일반 문서 편집 |
| 인력 리포트가 어떻게 동작해? | 아니요 | 동작 설명 |
| 권한 오류 메시지를 설명해줘 | 아니요 | 오류 의미 설명 |
| 하네스 프론트 담당 지침 검토 | 아니요 | 하네스 자체 감사 |
| 백엔드 구조 설명 | 아니요 | 구조 설명 |
| 검증 보고서 요약 | 아니요 | 기존 문서 요약 |
| 프론트 스킬 description 수정 | 아니요 | 스킬·하네스 유지보수 |
| 검증 절차 문서 오탈자 수정 | 아니요 | 문서 편집 |
| RFC 기능 구현 | 예 | 요구사항·계약 확인 후 해당 구현·검증 단계 |

## 지침의 모순·실행 가능성 평가

**핵심 세 사례를 수행 불가능하게 만드는 모순은 발견하지 못했다.** 커스텀 타입 4종과 collaboration 도구는 현재 세션에 노출되어 있고 TOML·담당 스킬 연결이 일치한다. 유휴 재개, 반복 실패 처리, 계약 불일치 판정, 설계 전용 중단점이 명시되어 있다. 다만 다음 문구는 해석을 보강할 여지가 있다.

| 항목 | 근거 | 판단 및 이번 평가의 처리 |
|---|---|---|
| 프론트 단독 수정의 검증 범위 | `feature-harness/SKILL.md:54`는 “프론트와 영향 검증만”, `AGENTS.md:60` 이하와 `references/verification.md:3`은 필수 앱 검증 요구 | 기능 단계 축소와 필수 검증을 분리해 읽으면 실행 가능하다. 현재 문구만 보고 backend test·Forge lint까지 자동 생략하면 안 된다. 필수 체크를 확보하거나 동일 상태의 증거를 재사용하고, 제한은 미검증으로 기록한다. 명시적 예외 조건을 추가하면 더 명확하다. |
| 작은 수정인데 선행 문서가 없는 경우 | `forge-frontend-dev/SKILL.md:11`은 설계·backend 리포트 읽기를 시작 조건으로 요구, `feature-harness/SKILL.md:9,50,60`은 작은 수정 직접 처리·간결 기록 허용 | 사례 1에는 기존 산출물이 있으므로 문제없다. 일반적인 작은 수정에서는 “기존 문서가 있으면 대조, 없으면 현재 계약의 간결 기록으로 대체”를 명시하면 불필요한 전체 파이프라인 생성을 막을 수 있다. 새 백엔드 구현을 강제로 만들 이유는 아니다. |
| 하네스 변경 때 앱 검증 요구 | `integration-verify/SKILL.md:94`는 하네스 변경에도 AGENTS의 앱 검증 생략 금지, `feature-harness/SKILL.md` 마지막 절은 구현 파이프라인 대신 구조·시나리오 검증 | 파이프라인 미시작과 앱 검증 실행은 논리적으로 양립한다. 다만 순수 하네스 수정에도 전체 앱 검증 비용이 발생하는 정책이다. 이번 읽기 전용 드라이런에는 테스트 금지 지시가 우선하며 앱 검증은 미실행이다. |
| content 예시의 과잉 일반화 위험 | `CLAUDE.md:206`의 `result: { success, content, error }` 예시와 `feature-design/SKILL.md:41`, `forge-frontend-dev/SKILL.md:43`의 content 조건부 규칙 | 스킬은 실제 계약을 확인하도록 명확히 제한하므로 사례 2에서 content/items/rows를 추정할 필요가 없다. 예시에도 동일한 단서를 달면 독해상 위험이 줄어든다. |

현재 평가는 정적 지침을 읽어 도출한 행동 계획이다. 파서 기반 구조 검사, 실제 에이전트 호출 성공, 테스트·빌드·Forge 인증 및 기능 동작은 검증하지 않았다. UTF-8을 명시하지 않은 첫 PowerShell 읽기에서 한글 출력이 깨져 해당 지침을 UTF-8로 다시 읽었으며, 이를 파일 손상으로 판정하지 않았다.
