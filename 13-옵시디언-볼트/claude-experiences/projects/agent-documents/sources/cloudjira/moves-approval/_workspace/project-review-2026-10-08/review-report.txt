Moves Approval 전체 로직·설계 검토
검토일: 2026-10-08
대상: C:\CloudJira\moves-approval의 현재 작업 트리(미커밋 라이선스·Sentry 변경 포함)

판정

계층 분리, 순수 도메인 함수, 중앙 권한 선언, 결정적 이벤트 ID, 사용자 권한을 이용한 페이지 조회는 좋은 기반이다.
그러나 결재 결과를 보장해야 하는 동시성·장애 복구 경계가 구현과 일치하지 않는다.
현재 상태를 중요한 결재 기록을 맡길 운영 준비 완료 상태로 평가하기 어렵다.
특히 “결정이 진실이고 status는 재계산 가능한 캐시”라는 설계는 재계산·복구 경로까지 존재해야 성립한다.
실제 구현은 종결 status를 먼저 확정하면 후발 결정을 재계산하지 않고, 복구를 담당한다고 주석에 적힌 리컨실러도 없다.

검토 방법과 한계

- Controller/PermissionMap, 승인·반려·회수, SQL, 영역 결재, 정책·위임·PIN, 업무함, 알림·스윕, 보관·내보내기,
  Flow 설정, 모달·요청 폼·서명·증명서, 라이선스 진입점과 테스트를 정적으로 검토했다.
- review.test.js는 실제 서비스/Repository 메서드를 호출하고 저장소·외부 API를 대역으로 바꾼 결함 재현이다.
  동시성은 Promise barrier로 실행 순서를 고정했다. 실제 Forge SQL 또는 운영 데이터에 장애를 주입한 것은 아니다.
- UUID·투영 테스트는 생성 SQL을 확인한다. 실제 TiDB에서 쿼리를 실행한 통합 검증은 수행하지 않았다.
- 실제 Confluence iframe 동작, production 라이선스, 설치 권한·대량 데이터의 성능은 이번 로컬 검증에 포함되지 않는다.
- 기능 코드는 수정하지 않았다. 검토 보고서와 재현 테스트만 _workspace에 추가했다. 배포·커밋·푸시는 하지 않았다.

검증 결과

- 기존 백엔드/계약 테스트: 28 suites, 193 tests 통과.
- UI 테스트: 13 suites, 82 tests 통과.
- 재현 테스트: 13건 추가 후 백엔드 전체 29 suites, 206 tests 통과.
  이 진단 테스트의 성공은 문제가 재현됐다는 뜻이며 수정 완료를 뜻하지 않는다.
- UI production build: 성공. Atlaskit source map 누락 2건과 postcss-calc 경고가 남는다.
- forge lint: exit 1. 코드 오류 0, 경고 0, MAJOR_VERSION_RULE 승인 항목 1.
  기존 작업 트리의 egress/data residency 변경으로 배포 시 major upgrade 승인이 필요하다는 결과다.
  이번 검토에서 배포하거나 권한 승인을 수행하지 않았다.

R01 [P1] 동시 승인·반려의 최종 상태가 결정 원본과 모순된다 — 동작 재현

조건: 승인자 A/B 중 1명 승인으로 통과하는 단계에서 A 승인과 B 반려가 같은 PENDING snapshot으로 출발한다.
두 결정 행은 각각 정상적으로 클레임된다. A의 aggregate CAS가 먼저 APPROVED를 쓰면 B는 CAS 실패 뒤

단순히 재시도 횟수를 늘리는 것으로는 종결 상태에서 반환하는 문제를 해결할 수 없다.

R13 [P1] Flow 갱신 중 실패하면 기존 결재선이 삭제된 채 남는다 — 동작 재현
근거: src/resolver/flow/FlowRepository.js:267, 293
      src/resolver/flow/FlowRepository.js:171
부모 rev CAS를 먼저 성공시킨 뒤 기존 단계 DELETE, 새 단계 INSERT를 별도 문장으로 수행한다.
INSERT 실패 시 기존 단계를 복구하지 않아 활성 Flow가 빈 결재선으로 남는다.
스페이스 범위도 DELETE 후 INSERT하며 “행 없음=전체 스페이스”이므로 중간 실패가 노출 범위를 넓힐 수 있다.
개선: 새 revision의 단계/범위를 별도 저장하고 완성된 revision 포인터만 CAS로 교체하는 방식이 적합하다.
성공한 부모 CAS만으로 자식 교체까지 원자적으로 완료됐다고 볼 수 없다.

R14 [P2] 동시 PIN 실패가 실패 카운터를 덮어 5회 잠금을 회피한다 — 동작 재현
근거: src/resolver/signature/PinService.js:61, 78
      src/resolver/signature/PinRepository.js:50
실패 횟수는 먼저 읽은 값에 1을 더해 절대값으로 UPDATE한다. 5개 요청이 failCount=0을 함께 읽으면
모두 1을 쓰고 잠금이 걸리지 않는다. 실제 5회 동시 실패 재현의 최종 failCount는 1, lockedUntil은 null이었다.
개선: SQL에서 원자적 증가와 임계 잠금 판정을 수행하거나 rev CAS로 충돌을 처리해야 한다.

R15 [P1] 성공하지 않은 회수·만료도 확정 감사 이벤트로 남는다 — 회수 경합 동작 재현

단순히 이벤트 INSERT를 CAS 뒤로 옮기면 그 사이 실패의 이벤트 누락 문제가 생기므로 R02와 함께 설계한다.

R16 [P2] 알림 생성 경로에 따라 정책·라이선스 검사가 다르다 — 호출 경로 검증

설계 보완 사항 — 위 확정 결함과 별도로 정할 계약

1. 내보내기 확정은 클라이언트 cutoff/count만 신뢰한다. 서버 측 export session, page 완료 증거,
   요청 ID manifest, 데이터 digest가 없어 완전한 사본과 삭제 대상을 대조하지 못한다.
2. 재상신은 기존 요청 회수 후 새 요청 생성 순서다. 새 생성 실패 시 원래 진행 건이 이미 닫힌다.
   동일 재상신 operation ID로 재개할 수 있는 saga가 필요하다.
3. 증명서·도장은 결정 당시 서명 snapshot이 아니라 현재 getSignatures 결과를 쓴다.
   서명을 바꾸거나 삭제하면 과거 결재의 표시도 바뀐다. 현재 장식 서명인지 역사적 증거인지 계약을 명확히 해야 한다.
4. 그룹 조회는 최대 5페이지×200명에서 남은 페이지가 있어도 부분 목록을 반환한다.
   전원 승인 규칙에 부분 그룹을 사용하면 의도한 전원의 의미가 달라진다. 완료 확인 또는 명시적 초과 거절이 필요하다.
5. 일괄 승인 50건은 단일 resolver에서 순차 수행하며 진행 커서·총 시간 예산이 없다.
   규모 검증 후 재개 가능한 배치로 바꾸는 것이 필요하다. 이번 검토에서 실제 timeout은 측정하지 않았다.
6. 관측 실패를 잡고 계속 진행하는 곳이 많지만 내구성 있는 재처리 표식이 없다.
   정상 없음, 권한 없음, 저장소 장애, 미완주를 같은 빈 결과로 취급하지 않는 응답 계약이 필요하다.

테스트 개선 방향

기존 테스트의 강점은 순수 도메인과 resolver 등록 계약이다. 약점은 외부 저장소를 성공하는 mock으로 바꾸거나
SQL 문구·호출 횟수만 확인해 실제 사용자 입력, 중간 실패, 여러 요청의 교차 실행을 놓친다는 점이다.
예를 들어 기존 테스트가 DRAFT를 남긴다는 사실은 검증하지만 그 DRAFT를 누가 언제 복구하는지는 검증하지 않는다.
새 회귀 테스트는 기대하는 정상 상태로 바꾸고, 실제 SQL 타입·권한 필터·후속 재시도까지 검증해야 한다.
