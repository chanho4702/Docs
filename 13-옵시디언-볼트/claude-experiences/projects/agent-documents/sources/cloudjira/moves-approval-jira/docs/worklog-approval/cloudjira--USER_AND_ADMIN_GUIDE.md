# 사용자·관리자 운영 가이드

## 1. 가장 짧은 시작 방법

작성자는 이슈의 워크로그 화면에서 날짜·시간·설명을 입력한다. 자동 요청이 켜져 있으면 저장 후 승인 대기가 된다. 팀장이 없으면 해당 기록의 상세에서 승인자를 선택한다. 승인자는 업무함에서 기록을 확인하고 한 건 또는 여러 건을 승인한다. 승인된 기록은 계속 볼 수 있지만 수정·삭제할 수 없다.

설정은 **언제 요청하는가 / 언제 마감하는가 / 누가 승인하는가**를 먼저 확인한다. 승인 후 수정 금지는 필수 규칙이며 끄는 토글이 없다. 일반 이슈·상태 전환·필드 변경 승인과 직접 인증은 현재 신규 업무의 진입점에서 제외한다.

## 2. 역할별 권한과 책임

| 역할 | 하는 일 | 자동으로 생기지 않는 권한 |
| --- | --- | --- |
| 작성자 | 본인 기록 작성, 가능한 승인자 선택, 소명, 본인 이력 확인 | 본인 승인, 다른 사람의 숨김 설명 열람 |
| 지정 승인자 | 배정된 요청 조회·승인·반려 | 모든 팀·모든 프로젝트의 워크로그 열람 |
| 팀장 | 소속 팀원의 기본 승인자, 허용 범위의 이력 확인 | Jira 이슈 열람 권한 우회 |
| Workforce 프로젝트 팀장 | 담당 프로젝트 연결 이슈의 요청·마감 정책 관리 | 정책 저장만으로 모든 기록의 승인자 지정 |
| Approval 관리자 | 기본 정책·연동 진단·데이터관리·감사 export | 일반 화면에서 삭제 이슈의 과거 내용을 무조건 열람 |

사용 가능한 버튼은 서버가 현재 상태와 권한으로 정한다. 화면을 오래 열어둔 사이 승인·마감·권한이 바뀌면 저장 시 다시 거부될 수 있다. 새로고침하고 최신 잠금 이유를 확인한다.

## 3. 단독과 연동의 작성 창구

| 사용 상황 | 작성 | 수정·소명·승인 이력 |
| --- | --- | --- |
| Approval 단독 | Jira 이슈의 Approval 워크로그 입력 | 같은 기록 상세 |
| Workforce와 연결한 Jira 이슈 | Approval 워크로그 패널 | Approval 상세 |
| Workforce 앱 내부 | 앱의 정상 워크로그 생성 폼 | Approval 이동 안내(handoff) |

연동 이슈의 Workforce Jira 패널은 Approval 이동 안내를 제공한다. 두 개의 다른 승인용 입력 폼을 고를 필요가 없다. Workforce 앱 내부의 정상 생성은 유지한다. 외부 도구나 Jira REST로 작성한 모든 로그가 자동으로 정상 출처가 되는 것은 아니다. 앱의 정상 입력 증명이 확인되어야 한다.

## 4. 저장 결과를 읽는 방법

| 화면 의미 | 해야 할 일 |
| --- | --- |
| 저장됨·승인 대기 | 추가 저장하지 않고 승인 결과를 기다린다. |
| 저장됨·승인자 선택 필요 | 기록 상세에서 승인자 후보를 검색하고 선택한다. |
| 저장됨·아직 요청하지 않음 | 수동 정책이면 승인 요청을 누른다. |
| 저장됨·승인 요청 실패 | 같은 기록 상세에서 재접수한다. 같은 시간을 새로 입력하지 않는다. |
| 처리 중 | Workforce 비동기 관찰·접수가 끝난 뒤 새로고침한다. 지속되면 관리자에게 기록 id와 오류 코드를 전달한다. |
| 마감됨 | 신규 일반 요청·수정을 반복하지 말고 허용되는 소명 절차를 확인한다. |

예를 들어 저장 버튼을 누른 뒤 “승인 요청 실패”가 나와도 목록에 2시간 기록이 보이면 Jira 저장은 성공한 것이다. 다시 2시간을 생성하면 중복 기록이 된다. 상세의 요청 동작만 재시도한다.

## 5. 승인자 선택·변경

기본 승인자는 현재 팀장이다. 수동으로 요청할 때 후보 목록에서 다른 승인자를 선택할 수 있다. 후보는 서버가 현재 정책과 이슈 접근 가능 여부로 제한한다. 이름이 검색되지 않는다고 accountId를 직접 입력하여 우회할 수는 없다.

요청이 대기 중이고 아무도 결정하지 않았을 때만 승인자 변경을 제공한다. 변경은 기존 회차를 덮어쓰지 않고 이전 요청을 종료하고 새 요청으로 남긴다. 이미 결정이 시작된 요청은 같은 버튼으로 바꿀 수 없다.

## 6. 승인자의 업무함과 일괄 승인

업무함의 워크로그 승인 목록에서 작성자, 이슈, 작업 일시, 기록 시간과 소명 여부를 확인한다. 필요하면 상세에서 원본·이력·사유를 읽는다. 여러 건을 선택해 일괄 승인할 수 있지만 각 건의 권한·상태는 실행 시 따로 확인한다.

10건 중 8건 성공, 2건 실패라면 성공 8건만 선택에서 빠지고 실패 2건은 남는다. 이를 전체 실패나 전체 성공으로 취급하지 않는다. 실패 상세를 확인하고 최신 상태를 새로고침한 뒤 필요한 건만 재시도한다. 결정 시점의 경합 때문에 이미 다른 승인자가 처리한 건은 다시 승인할 수 없다.

반려할 때는 이후 작성자가 이해할 수 있는 사유를 남긴다. 예: “10월 13일 기록의 업무 설명이 실제 회의와 다릅니다. 시간은 그대로 두고 설명을 확인해 주세요.” 개인정보나 비밀번호를 사유에 넣지 않는다.

## 7. 승인·마감·반려·소명

승인된 기록은 기간 정책과 관계없이 수정·삭제 금지다. 아직 미승인이어도 해당 월이 실제로 마감되면 일반 수정·신규 요청이 제한된다. **마감 일수 0은 자동 마감 OFF**이며 당일 마감이 아니다. 월이 지나면 반드시 자동 마감해야 하는 운영이라면 1일 이상 등 조직이 정한 유예기간을 설정하고 마감 결과를 확인한다.

반려는 승인과 다르다. 반려 이력은 보존하고 이후 수정 가능 여부는 현재 기간·통제 정책에 따라 정한다. 같은 내용을 매번 자동 요청해 승인자의 업무함을 채우지 않는다. 설명을 확인하고 필요한 수정과 명시적 재요청을 진행한다.

기존 승인과 인증 기준이 저장된 기록을 재검토하려면 상세의 소명 요청을 사용한다. 사유를 반드시 입력하고 필요하면 승인자를 선택한다. **소명 중에도 잠금과 기존 확정 시간은 유지된다.** 승인 투영이 아직 완료되지 않았거나 단순히 마감된 미승인 기록이면 소명 버튼을 열지 않는다. 마감 전에 접수된 승인 대기 건은 원래 내용을 재검증해 승인할 수 있다. 소명이 접수되었다는 이유로 원본을 수정하거나 삭제하는 기능은 아니다. 현재 구현에는 승인 원장을 유지한 채 자유 편집을 허용하는 예외 해제 절차가 없다.

## 8. 내 기록의 이력 확인

기록 상세에서 현재 승인 상태·잠금 이유, 승인/반려한 사람과 시각, 사유를 확인한다. 이전 이력 더 보기를 누르면 오래된 요청 회차를 이어서 조회한다. 생성·시간/설명 변경·삭제 관찰은 워크로그 변경 이력에서 확인한다. Workforce에서는 해당 기록의 Approval 이동 경로로 상세를 연다.

시스템이 실제 행위자를 확인하지 못한 변경을 특정 사용자 이름으로 추측해 표시하지 않는다. 설명 원문 보관을 켜지 않은 기간의 전체 이전 내용도 복구할 수 없다. 승인 당시 확정 시간과 현재 Jira 내용이 다를 수 있으므로 CHANGED 표시는 그냥 숨기지 않는다.

## 9. 팀장·관리자의 기본 설정

Approval 기본 승인 규칙에서 자동 요청 여부와 자동 마감 유예일을 설정한다. 누가 승인하는지는 기본 팀장 안내와 수동 후보 선택 정책으로 이해한다. 단독 팀/팀장 자료가 없으면 먼저 조직과 승인자 명부를 준비한다.

연동 프로젝트의 이슈별 요청·마감은 Workforce 프로젝트 설정에서 관리한다. 지원되는 연결 이슈를 선택하고 자동/수동 요청과 마감 일수를 지정한다. 여러 이슈에 적용할 때 “변경하지 않음”을 이용해 기존 값을 보존한다. Approval 화면에는 Workforce 관리임을 보여 주며 같은 값을 두 앱에서 중복 편집하지 않는다.

고급 설정에는 시간 상한·작성 가능 기간·이력 보관 등 운영 규칙을 둔다. 사전 승인 유형과 레거시 결재선 편집은 현재 흐름에서 숨기되 기존 저장값과 코드의 호환성은 보존한다. 고급 진단을 사용자에게 승인 요청 절차로 안내하지 않는다.

## 10. Workforce 통계 읽기

열린 기간과 마감된 기간은 집계 조건이 다르다. 마감 뒤에는 정상 경로의 승인 근거로 확정 시간을 집계한다. 기록별 표시는 승인/미승인/변경과 집계 제외를 유지한다. 원래 기록 시간과 확정 합계가 다른 것은 가능한 결과다.

외부에서 승인된 원문을 바꾸어 지문이 달라진 경우 확정된 승인 시간을 보존하면서 CHANGED로 표시한다. 새로 늘린 시간이 승인된 것으로 들어가지 않는다. 수동 마감·재개와 이슈별 정책을 변경하면 게시·수신·캐시 반영을 기다린 뒤 확인한다.

서명 문서는 크기 제한이 있다. `truncated` 상태로 일부 항목이 실리지 못하면 해당 추가 승인분을 추정하여 채우지 않고 알 수 없는 항목을 0으로 처리할 수 있다. 따라서 대량 월의 통계는 완전성을 확인해야 한다. 대량 문서 분할·외부 아카이브로 이 제한을 없애는 기능은 이번 범위에 없다.

## 11. 용량 경고와 감사 파일 관리

관리자 앱 진입·업무함·데이터관리에서 저장량을 확인한다. 값은 DB 테이블 통계의 추정치이며 실시간 청구값과 같다고 보장하지 않는다. 일반 사용자에게 관리자 저장량 API를 호출하지 않는다.

| 수준 | 의미 | 조치 |
| --- | --- | --- |
| 70% 주의 | 증가 속도와 보관 범위 점검 시점 | 표본을 확인하고 파일 보관 위치·담당자를 정한다. |
| 85% 내보내기 안내 | 여유가 줄어듦 | 보관 기간을 지난 감사 자료를 export하고 검증한다. |
| 95% 긴급 | 신규 저장 실패에 대비 | 정리 가능 범위를 확인하고 공급자와 잔여 용량을 검토한다. |

절차는 **사용량 확인→범위 선택·내보내기→파일 열기/행수·기간·식별자 확인→파일 보관 확인→허용 범위 정리→사용량 재조회**다. 파일은 조직의 접근 통제된 문서 보관소에 저장하고 다운로드 담당자·시각·대상 기간을 함께 관리한다. 앱이 사용자 PC 파일을 안전한 영구 저장소에 자동 업로드한 것으로 간주하지 않는다.

현재 APPROVED 승인 원장, 활성 인증, 정상 출처 근거는 삭제에서 보호한다. 따라서 파일을 받아도 이 핵심 행의 공간이 모두 회수되지는 않는다. 무기한 성장분을 작은 아카이브 행으로 치환하는 기능은 아직 없다. 기록량이 많은 조직은 1GiB에 도달하기 전에 공급자와 보관 아키텍처 확장을 계획해야 한다. 경고를 해결하기 위해 SQL을 임의 삭제하면 승인 잠금·집계 근거가 어긋날 수 있다.

알림은 단일 인라인 상태이며 같은 경고를 SQL 알림 행으로 계속 쌓지 않는다. 관리자 미접속 중 외부 알림을 보내지 않는다. 95%가 되어도 자동으로 기록을 삭제하거나 사용자 대신 파일을 확인하지 않는다.

## 12. 삭제된 이슈·용량 초과·연동 장애 대응

| 증상 | 확인·복구 |
| --- | --- |
| 이슈가 없어 기록 상세가 열리지 않음 | 삭제와 열람 권한 상실을 404 하나로 단정하지 않는다. 승인 export에서도 현재 권한 필터로 원본이 제외될 수 있다. 변경 이력 export의 가린 기본 metadata와 삭제 전에 보관한 파일을 별도로 확인한다. |
| 승인됐는데 Workforce가 아직 대기/미승인 | Approval 결정 상태, 게시 큐/서명 상태, 상대 앱 지원 버전과 수신, 캐시 갱신 순서로 확인한다. Approval을 다시 승인해 중복 요청을 만들지 않는다. |
| 저장은 됐고 승인 접수만 실패 | 목록에서 원래 worklogId를 확인하고 요청만 재시도한다. |
| 저장 자체가 용량 오류 | 성공 메시지가 없으면 생성 여부를 목록에서 확인한다. 관리자에게 오류 코드·시각을 전달하고 허용 export/정리로 공간을 확보한다. |
| export 확인/정리도 SQL 쓰기 실패 | 다운로드 파일을 먼저 안전하게 보관한다. 확인을 우회한 DELETE를 실행하지 말고 공급자 지원으로 저장소 상태와 재시도 경로를 확인한다. |
| 후보 없음 | 조직 팀장·명부·활성 계정·이슈 권한을 확인한다. 자기 승인으로 우회하지 않는다. |

지원 자료에는 issueKey/worklogId/requestId, 발생 시각, 오류 코드, 현재 승인/잠금 상태와 마지막 성공 단계를 포함한다. 개인키·토큰·민감한 설명·반려 사유 원문을 콘솔 로그나 공개 티켓에 붙이지 않는다.

## 모달·설명 서식·이슈 필드

이슈의 작업 로그 목록에서 작성 버튼을 누르면 입력 모달이 열린다. 설명은 Workforce와 같은 MDXEditor 기반 편집기를 사용하며 지원 서식을 ADF로 변환하여 저장한다. 기존 설명에 이미지·멘션 등 안전하게 재변환할 수 없는 요소가 있으면 읽기 전용으로 보존한다. 설명을 바꾸지 않은 수정은 comment를 전송하지 않아 기존 원문을 덮지 않는다. 변환 실패 시 저장을 멈추고 재시도를 안내한다.

연동 이슈의 Workforce 입력 activity는 Approval 통제 표식이 게시되면 숨겨진다. Jira 기본 Work log까지 하나로 정리하려면 관리자가 Moves Approval을 시간 추적 제공자로 선택해야 한다. Workforce 이슈 요약 영역은 유지한다. 표식 게시 전이나 제공자를 선택하지 않은 사이트에서는 탭이 중복될 수 있으므로 설치 후 실제 이슈에서 확인한다.

Workforce의 새 읽기 전용 필드는 계획작업량(원래 추정 시간), 기록공수(Jira timespent), 공수 기준 진행률(기록/계획 × 100)이다. 단위는 시간과 %다. 진행률은 실제 작업 완료율이 아니며 100%를 초과할 수 있다. 계획이 없거나 0이면 진행률은 빈 값이다. 승인 확정 공수와 Jira 원본 기록공수는 구분해서 읽는다. 관리자가 설치 업그레이드 후 이슈 화면에 필드를 배치해야 한다. 이슈 조회 때 계산되므로 JQL·REST 값은 마지막 조회 시점의 값일 수 있다.

## API 연결과 강제 차단 설치

앱 간 자동 연동은 [entity property 연동 설계](cloudjira--ENTITY_PROPERTY_INTEGRATION.md)를 따른다. Approval에는 App REST apiRoute가 없으며 관리자가 Workforce base URL이나 3LO access token을 입력할 필요도 없다. 팀 구성과 승인자 판정은 서명 검증된 조직 자료를 사용한다.

승인·마감 후 앱 수정 차단과 Jira 직접 REST 차단은 함께 검증해야 한다. [차단 검증 절차](cloudjira--LOCK_VERIFICATION.md)의 권한 스킴·일반 사용자 시험·HTTP 응답·원본 대조를 완료하기 전에는 강제 차단 설정 완료로 보지 않는다. 자동 마감이 0이면 기간 경과만으로 잠기지 않으므로 1~90일 또는 수동 CLOSED 운영이 필요하다.
