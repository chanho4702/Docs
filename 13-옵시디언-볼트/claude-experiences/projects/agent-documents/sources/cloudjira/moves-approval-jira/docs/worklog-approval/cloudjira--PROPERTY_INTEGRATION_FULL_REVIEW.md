# Workforce·Approval 프로퍼티 연동 전체 검토

검토일: 2026-10-15  
기준: Approval `0c52170`, Workforce `80e7d31` 및 검토 당시 작업 트리  
범위: 두 앱의 단독 사용, 연동, 장애, 보안, 승인 잠금, 조직 동기화, 통계, 운영 비용과 화면 구분

## 1. 결론

프로퍼티 방식은 유지할 수 있다. 다만 **각 앱의 DB를 원장으로 두고, 프로퍼티는 상대 앱에 전달하는 서명된 사본으로만 사용해야 한다.** 서명이 유효하다는 사실만으로 최신 정보이거나 지금도 해당 권한이 있다는 뜻은 아니다.

현재 구현에는 서명 검증, 사이트·대상 대조, 게시 아웃박스, 조회 권한 확인, SQL 기반 통제와 복구 작업이 있다. 처음부터 다시 만들 필요는 없다. 우선 다음 경계를 보완해야 한다.

1. 삭제된 프로퍼티를 실제로 복구한다. 누락 감지 이후 재전송이 생략되는 문제를 로컬 테스트로 재현했다.
2. 승인 확정과 Jira 잠금 적용 사이를 닫는다. 비동기 전파만으로 모든 입력 경로의 즉시 차단을 보장했다고 할 수 없다.
3. 예전의 정상 서명 문서를 다시 붙이는 행위와 오래된 팀장 정보 사용을 막는다.
4. 단독 모드, 연동 모드, 연동 장애를 서로 다른 상태로 취급한다.
5. Workforce 연결 이슈에만 승인 통계를 적용하고, 불완전한 집계를 완전한 합계처럼 보여 주지 않는다.

이 문서는 분석 결과와 개선 설계다. 아래 제안이 구현·배포되었다는 뜻이 아니다. 실사이트에 프로퍼티 삭제나 권한 우회 시험을 수행하지 않았다.

## 2. 사용 형태별로 무엇이 달라야 하는가

다음 표는 사용자가 요구한 동작을 정리한 목표 기준이다. 현재 구현과의 차이는 뒤에서 따로 설명한다.

| 항목 | Approval 단독 | Workforce 단독 | 두 앱 설치·미연동 | 연동·Workforce 연결 이슈 | 연동·Workforce 비연결 이슈 |
|---|---|---|---|---|---|
| 조직·기본 승인자 | Approval 자체 설정 | 승인 기능 없음 | 각 앱이 자기 설정 사용 | 검증된 Workforce 소속·팀장, 직접 요청 시 허용 후보 선택 | 연동 승인 대상 아님 |
| 승인 대상 | Approval 자체 정책이 정한 워크로그 | 해당 없음 | Approval 자체 정책 | Workforce에 연결된 이슈의 정상 경로 워크로그 | Approval 연동 승인에서 제외 |
| 정책 관리 | Approval 권한 체계 | Workforce 자체 업무 정책 | 각각 관리 | Workforce 프로젝트 책임 범위와 Approval 승인·통제 규칙 연결 | Workforce 연동 정책을 확대 적용하지 않음 |
| 기록 입력 | Approval 모달과 허용된 경로 | Workforce 입력 | 각 앱의 독립 정책 | Approval 모달 또는 검증된 Workforce 입력 경로 | 해당 앱의 일반 입력 정책 |
| 승인·마감 잠금 | Approval이 책임짐 | Approval 승인 잠금 없음 | Approval이 관리한 기록은 잠금 유지 | Approval 원장과 Jira 통제로 강제 | 연동 대상 제외와 기존 잠금 해제는 별개 |
| 통계 | 승인·미승인 상태 제공 | Workforce 일반 통계 | 각 앱 통계 기준 명시 | 마감 전 기록 통계, 마감 후 승인 기준 통계·건별 상태 | 비연결 기록에 승인 필터를 임의 적용하지 않음 |
| 감사 이력 | Approval 원장 | Workforce 자체 이력 | 각각 보존 | 승인 이력은 Approval 원장, Workforce는 허용된 요약 표시 | 이미 생성된 이력을 삭제하지 않음 |

두 앱이 설치되었다는 사실만으로 연동을 켜면 안 된다. 반대로 연동 중 프로퍼티가 사라졌다고 단독 모드로 자동 전환해서도 안 된다. 기존 승인·마감 잠금은 모드 OFF만으로 해제하지 않는다.

팀장이 본인 기록을 승인할 수 있다는 제품 요구는 명시적인 자가 승인 정책으로 표현해야 한다. 단독 모드는 Approval 자체 역할로, 연동 모드는 최신 검증된 Workforce 팀장 자격으로 판단한다. 자동 요청에서 본인을 제외하는 현재 후보 규칙과 직접 요청의 자가 승인 허용은 구분해서 안내해야 한다.

## 3. 데이터 책임과 실제 전달 경로

| 데이터 | 원장·책임 앱 | 상대 앱이 받는 것 |
|---|---|---|
| 팀·팀원·팀장, Workforce 프로젝트 연결 | Workforce | 서명된 조직·연결 정보 |
| 승인 요청·승인·반려·재승인 | Approval | 서명된 결재·인증 요약 |
| 승인 잠금·기간 잠금·통제 조치 | Approval | 입력 판단에 필요한 통제 사본 |
| Jira 워크로그 본문 | Jira, 별도 수집 이력은 각 앱 저장 정책 | 권한 확인 후 조회한 원본 또는 필요한 요약 |
| 감사 증거 | 해당 앱의 보존 원장 | 표시 목적의 제한된 사본 |

프로퍼티는 Jira 엔티티에 붙는다. 현재 방식은 이슈에만 붙는 것도, 앱 전용 공통 DB인 것도 아니다. 사용자·프로젝트·이슈·워크로그 등 문서 종류별 위치가 다르다.

Atlassian은 프로퍼티가 앱별로 격리되지 않고 다른 앱이나 해당 엔티티 수정 권한을 가진 사용자에 의해 변경될 수 있다고 설명한다. 동시 편집 충돌도 앱이 처리해야 한다. 따라서 잠금 여부와 감사 원장의 최종 판단을 프로퍼티에 맡기면 안 된다. [공식 설명](https://developer.atlassian.com/cloud/jira/platform/jira-entity-properties/)

현재 원칙인 ‘Approval 수정·삭제 판단은 Approval DB 기준’은 유지한다. Workforce에 전달된 값은 동일 시점의 DB 조회 결과가 아니라 지연될 수 있는 사본이라는 점을 설계와 화면에 반영해야 한다.

## 4. 발견 사항과 우선순위

증거 수준을 구분한다. **재현**은 로컬 모의 테스트로 해당 동작을 확인했다는 뜻이며, **코드 확인**은 읽은 경로에서 확인한 동작이다. **추가 검증**은 실제 경합·권한·호출 조건을 더 시험해야 한다는 뜻이다.

### P0-1. 누락을 발견해도 실제 재게시가 생략될 수 있다 — 재현

`WorkforcePublisher.verifyPublished`는 원격 문서가 없으면 `MISSING_REMOTE`로 기록하고 게시 대기 상태로 만든다. 하지만 다음 게시 작업은 이전 `contentDigest`, 서명 키, 게시 시각이 같으면 ‘변경 없음’으로 처리한다. 삭제된 원격 문서에 실제 PUT을 하지 않고 대기가 끝날 수 있다.

로컬 검증 순서는 최초 게시 → Jira 조회가 null 반환 → 누락 감지 → 원장 내용 변경 없이 다음 게시 실행이다. 결과는 `unchanged: 1`, `published: 0`, PUT 호출 없음이었다. 기존 감지 테스트와 변경 생략 테스트가 각각 통과해도 이 연결 경로는 놓칠 수 있다.

통제·결재선 문서에도 유사한 생략 분기가 있다. 정상 삭제를 끝낸 문서가 외부에서 다시 생성된 경우에도 과거 `DELETED` 기록만 보고 DELETE를 생략하는지 함께 고쳐야 한다.

**개선:** 일반 내용 변경과 원격 손상 복구를 구분하는 영속 상태를 둔다. 복구 작업은 동일 내용 최적화를 건너뛰고 PUT/DELETE 후 재조회한다. 완료 시에는 작업 중 발생한 새로운 `dirty_rev`를 지우지 않도록 CAS 조건을 유지한다.

근거: Approval `src/resolver/workforce/WorkforcePublisher.js`의 `drain`, `drainCtl`, `drainFlows`, `verifyPublished`; `WorkforceLinkRepository.js`의 `touchMany`, `markPublished`. 재현 파일: `tmp/property-audit-repro.test.js`.

### P0-2. 승인 직후 잠금 전파 지연 — 코드 확인·경합 검증 필요

Approval 인증 원장은 먼저 변경되고, 인증 게시와 Jira 통제는 후속 작업으로 이어진다. `WorkforceCertWake`에는 45초 묶음 지연이 있다. Workforce가 저장 직전에 프로퍼티를 다시 읽더라도 아직 게시되지 않은 승인 상태를 읽을 수는 없다.

따라서 ‘저장 직전에 재조회한다’만으로 승인 직후의 수정을 완전히 막았다고 설명할 수 없다. 오래된 정상 PENDING 문서가 유효한 동안 Workforce 직접 쓰기가 허용되고, Jira 제한 적용도 아직 끝나지 않은 조합을 시험해야 한다. 실제 수정 성공 여부는 Jira 권한·제한 적용 시점까지 포함한 실측이 필요하다.

**개선:** 최종 승인 완료를 선언하기 전에 대상 기록에 대한 쓰기 차단이 확인되는 단계를 둔다. 통제 적용 실패는 ‘승인 완료’와 구분하고 재시도한다. 엄격한 잠금이 필요한 수정·삭제는 Approval의 현재 원장을 확인하는 경로로 모은다. 프로퍼티만으로 즉시 동기식 권한 확인이 되는 것처럼 취급하지 않는다. 통계 게시 묶음 최적화와 보안 통제의 지연 예산도 분리한다.

이는 설계 제안이지 현재 구현의 보장 사항이 아니다. Jira 기본 UI·REST·다른 앱까지 막히는지는 실제 권한 스킴과 제한 방식으로 검증해야 한다. [워크로그 REST 권한 기준](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-worklogs/)

근거: `ApprovalCertificationProjection`, `WorklogControlWorker.reevaluate`, `WorkforceCertWake`; Workforce `LinkedWriteGate`.

### P1-1. 서명은 변조 방지이며 최신성 보장은 아니다 — 일부 재현

현재 서명에는 사이트·대상·본문이 포함된다. 본문을 임의로 고치고 기존 `sig`를 그대로 두면 검증에 실패하도록 설계되어 있다. 값이 읽을 수 있는 JSON으로 보이는 것은 정상이다. 서명은 암호화가 아니다.

다만 같은 사이트·같은 대상의 예전 정상 문서를 통째로 다시 붙이면 서명은 여전히 맞을 수 있다. Workforce 인증 문서 읽기 함수에 기존 테스트 서명 문서를 1년 뒤 시각으로 전달한 로컬 검증에서도 `ok: true`였다. 과거 인증 조회가 필요하므로 오래된 문서를 읽는 것 자체가 결함은 아니다. 문제는 이를 현재 수정 권한이나 최신 승인 상태로 쓰는 경우다.

Approval 수신에는 revision 역행 방어가 있지만, Workforce의 인증·통제 소비 경로에는 같은 수준의 영속적인 최신 버전 기억이 일관되게 적용되어 있지 않다. 과거 release 문서의 재사용도 점검 대상이다.

**개선:** 문서 대상별 발행 순번을 영속 저장하고 낮은 순번은 현재 판정에 사용하지 않는다. 같은 순번·다른 본문은 충돌로 기록한다. 만료·폐기·연동 해제도 버전을 가진 상태로 전달한다. 최초 수신 전에 삭제되거나 과거 문서만 남은 경우는 단순 revision 비교만으로 해결되지 않으므로 연결 초기 확인 절차와 유효기간이 필요하다. 과거 감사 조회와 현재 권한 확인 규칙을 분리한다.

근거: 양쪽 `signature.js`, Approval `WorkforceInbound`, Workforce `certification.readCertDoc`, `ApprovalControlLookup`.

### P1-2. 오래된 조직 정보가 새 승인 권한에 사용될 수 있다 — 코드 확인

Workforce 조직 게시에는 본인 접속을 중심으로 한 갱신과 6시간 메모가 있다. 팀 변경 시 epoch를 올려도 접속하지 않은 모든 사용자의 문서를 즉시 다시 게시하는 것은 아니다. Approval은 조회 실패나 문서 소실 시 마지막 검증값을 보존한다.

이 보존은 장애 때 데이터를 잃지 않게 하지만, 과거 팀장을 계속 현재 팀장으로 인정할 위험도 만든다. `WorkforceInbound.viewOf`는 저장된 VERIFIED 상태를 기준으로 반환하며, 그 경로에서 현재 신뢰 키와 최신성 조건을 모두 다시 검증하지 않는다. 모든 수신 경로가 같지는 않다. `LinkedIssueSettingSource`처럼 신뢰 키를 재확인하는 경로도 있다.

**개선:** 조직 변경의 영향 대상자를 게시 대기 목록에 넣고, 자가 승인·새 결재 결정처럼 권한을 부여하는 작업에는 최신성 기준을 둔다. 오래된 자료는 ‘마지막 확인 정보’로 표시하되 신규 권한 부여를 허용하지 않는다. 키 폐기 시 검증 캐시도 무효화한다. 다른 사용자 문서를 asApp으로 게시하려면 기존 보안 예외·권한을 명시적으로 설계해야 하며, 단순 호출 방식 변경으로 처리하지 않는다.

근거: Workforce `ApprovalLinkSignals.ensureOrgCap`; Approval `WorkforceInbound.orgOf`, `viewOf`, `WorkforceOrgSource.identityOf`.

### P1-3. 연동 OFF에서도 비용 통계에 인증 사본이 영향을 줄 수 있다 — 코드 확인

Workforce `ApprovalCertReader.certifyCostRows`는 OFF 분기에서도 기존 `applyCertToCostRows`를 사용한다. 남아 있는 유효 인증 문서가 있으면 그 결과를 적용할 수 있다. 반면 일반 워크로그 집계의 `applyWorklogApproval`은 OFF일 때 원래 목록을 반환한다.

이 동작이 과거 인증을 보존하려는 의도인지 먼저 구분해야 한다. 현재 상태로는 사용자가 같은 OFF를 보고도 일반 통계와 비용 통계에서 다른 기준을 경험할 수 있다.

**개선:** ‘현재 연동 사용 여부’, ‘과거 확정 월의 통계 기준’, ‘기존 기록의 잠금’을 별도 정책으로 정한다. OFF라는 이유로 잠금을 풀지 않되, 통계에는 적용된 기준과 기준 시점을 표시한다. 처음부터 단독 사용한 설치와 연동 해제한 설치를 같은 초기 상태로 취급하지 않는다.

### P1-4. 연결 이슈 범위와 통계 필터 범위가 일치하는지 확인해야 한다 — 조건부 위험

Approval 승인 대상 판정에는 연결 이슈 조건이 있다. Workforce의 일반 승인 통계 함수는 전역 ON 설정을 보고 입력 행에 인증 필터를 적용하며, 함수 내부에서 모든 행의 Workforce 연결 여부를 별도로 확정하지 않는다. 프로젝트 전용 호출자는 이미 범위를 좁힐 수 있지만, 일반 이슈 분석 등에서 비연결 행이 들어오는 경로는 추가 검증이 필요하다.

**개선:** 서버가 확인한 연결 범위를 집계에 전달한다. 확인된 비대상은 일반 집계에 남기고, 연결 대상인데 문서가 없는 경우는 ‘승인 확인 불가’로 구분한다. 프로퍼티가 없다는 사실만으로 비대상이라고 판단하면 삭제 공격 시 범위가 풀릴 수 있다.

근거: Workforce `ApprovalCertReader.applyWorklogApproval`, `judgeWithAppDocs`, `IssueAnalysisService.getIssueWorklogDetailService`.

### P1-5. 입력 출처도 재사용과 지연을 고려해야 한다 — 코드 확인·추가 검증

Workforce 생성 시점의 서명에는 아직 생성되지 않은 worklogId를 담을 수 없다. `LinkedWriteGate.freshOwnOf`는 작성자·이슈·시간·작업 정보 및 유효 시간대를 확인한다. 같은 작성자·같은 이슈·같은 값의 재사용은 후속 Approval 감지에서 op 중복과 연결해 판단하는 구조다.

**개선:** 생성 후 worklogId와 op를 묶은 확정 출처를 남긴다. 확정되지 않은 기록은 정상 출처 인증을 보류한다. 생성·출처 확정 사이 실패와 중복 이벤트를 재처리할 수 있어야 한다. 다른 사람의 기록을 임의로 서명할 수 있다는 의미는 아니며, 동일 대상 재사용과 후속 확인 지연의 문제다.

### P2-1. 복구 확인 처리량과 대기 시간이 맞지 않을 수 있다 — 코드 확인

게시 검증은 한 번에 최대 100개이며, 일일 작업의 첫 round에서 실행된다. 게시 후속 round가 검증 전체를 계속 순회하는 구조는 아니다. 사용자 200명에 월 인증 200개와 연간 문서 200개가 있으면 400개 이상이고, 하루에 100개를 모두 처리해도 전체 순회에는 최소 4일이 필요하다. 12개월 인증 2,400개와 연간 문서 200개라면 최소 26일이다. 실제 시간 예산에 걸리면 더 길어진다.

이는 해당 문서들이 모두 검증 대상에 남고 매일 최대 처리량을 채운다는 가정의 계산이다. 특정 삭제가 항상 그만큼 기다린다는 측정값은 아니다.

**개선:** 검증에도 커서와 제한된 후속 작업을 둔다. 최근 승인·조직 변경·손상 문서를 우선 확인하고, 과거 문서는 낮은 빈도로 확인한다. 목표 복구 시간과 가장 오래된 미확인 문서의 나이를 운영 지표로 둔다.

### P2-2. 용량·건수 상한을 조용한 누락으로 처리하면 안 된다 — 코드 확인

Jira 프로퍼티 값은 최대 32,768바이트다. 코드의 약 30,000바이트 예산은 여유를 둔 설계다. 워크로그 목록 최대 1,000건, 일부 계정 조회 300명, 숨김 기록 보충 1,000건 등 코드 자체 상한도 있다. 건수 제한보다 JSON 바이트 제한이 먼저 걸릴 수 있다. [공식 프로퍼티 제한](https://developer.atlassian.com/cloud/jira/platform/jira-entity-properties/)

월 전체 합계가 맞아도 개별 목록이 잘린 문서로 프로젝트별 비용을 정확하게 나눌 수는 없다. 합계를 누락 행에 임의 배분해서는 안 된다.

**개선:** `complete`, 총건수, 포함건수와 잘린 이유를 전달한다. 불완전 집계에는 경고와 확정 불가 상태를 표시한다. 분할이 필요하면 세대별 불변 조각을 먼저 게시하고 마지막에 목차를 바꾼다. 수신자는 한 세대의 모든 조각을 검증한 후 전환한다. 분할은 호출 수·고아 문서 정리·이전 세대 보존 비용을 늘리므로 압축할 필드를 먼저 검토한다.

## 5. 화면에서 단독·연동·장애를 구분하는 방법

Approval에는 이미 모드 요약과 팀장 표시 구성요소가 있다. 문제는 모드 이름이 없다는 것이 아니라, ON 설정과 실제 연결 정상 여부를 같은 의미로 보여 줄 수 있다는 점이다. `WorklogApprovalModeContext`는 설정 플래그로 모드를 표시한다. 조직을 확인하지 못한 경우도 단순 ‘팀 없음’처럼 보이면 재등록이 필요하다고 오해하게 된다.

| 화면 요소 | 단독 사용 | 정상 연동 | 확인 실패·지연 |
|---|---|---|---|
| 상단 상태 | ‘Approval 단독’ 또는 ‘Workforce 단독’ | ‘연동 사용 · 연결 정상’ | ‘연동 사용 · 확인 필요’ |
| 승인 대상 | 자체 정책 범위 표시 | ‘Workforce 연결 이슈만’ | 마지막 확인 범위와 실패 원인 |
| 팀장 | 자체 승인자 설정 | 이름·팀·마지막 확인 시각 | ‘팀장 정보를 확인할 수 없음’; ‘팀장 없음’과 구분 |
| 이슈 모달 | 입력·이력·승인 상태 | 연결 프로젝트·승인자·잠금 사유 | 입력 가능 여부와 복구 안내 |
| 통계 | 실제 사용한 일반/자체 승인 기준 | 기록 시간·승인 인정 시간·제외 사유 | 확인 불가 건수·집계 완전성 |
| 관리자 설정 | 자체 조직·결재 설정 | Workforce에서 관리하는 값은 읽기 전용 안내 | 게시 대기·검증 실패·복구 상태 |

‘운영 모드’, ‘연결 건강 상태’, ‘이 이슈의 승인 대상 여부’, ‘이 기록의 잠금 상태’는 서로 다른 값이다. 하나의 초록색 연동 배지로 합치지 않는다.

이슈 화면은 입력 버튼 하나, 내 기록 목록, 승인 상태, 수정 가능 여부와 이유, 승인자·반려 사유·이력으로 정리한다. 두 앱의 입력 UI를 중복 노출하지 않는 것은 UX 규칙이며 서버 권한 차단의 대체 수단은 아니다. 서명 검증 전 프로퍼티를 화면 표시 조건에 사용하더라도 실제 승인·수정 권한에는 사용하지 않는다.

## 6. 프로퍼티 방식을 유지하면서 보완할 구조

1. 원장 변경과 게시 필요 상태를 같은 일관성 경계에서 기록한다. 큐는 깨우기 수단이고 누락된 큐를 복구할 근거는 원장에 남긴다.
2. 문서마다 사이트·대상·발행자·버전·본문을 묶어 서명한다. 환경과 설치 구분도 신뢰 키·namespace 정책에 반영한다.
3. 수신자는 서명뿐 아니라 최신 수신 버전, 키 폐기, 유효기간, 문서 완전성을 검사한다.
4. 실패는 ABSENT, UNREADABLE, INVALID, STALE, REPAIR_PENDING 등 원인별로 관리한다. 모두 ‘미연동’으로 바꾸지 않는다.
5. 현재 권한을 확인할 수 없으면 신규 승인·수정 권한을 확대하지 않는다. 기존 이력 조회는 별도 열람 권한으로 계속 제공한다.
6. 게시 성공, Jira 재조회 성공, 상대 앱 수신 성공을 구분한다. 현재 시스템에 상대 수신 ACK가 모두 구현되어 있다고 가정하지 않는다. ACK를 추가한다면 ACK 자체의 서명·재전송·호출 비용도 설계한다.
7. 연동 해제는 버전 있는 해제 상태와 적용 확인으로 처리한다. 기존 잠금·감사 자료는 별도로 보존한다.

양쪽에 복제된 계약 코드는 공통 테스트 벡터와 정규화한 파일 해시를 CI에서 대조하는 편이 좋다. 줄바꿈 차이를 계약 차이로 오인하지 않는다. 한쪽만 먼저 업그레이드한 구버전 호환 테스트도 필요하다.

## 7. 200명 기준 성능·비용 최적화

200명이 한 달에 개인별 문서를 읽고 각자 키 문서 조회까지 필요하면, 캐시가 없는 한 집계에서 최대 약 400회의 개별 Jira 조회가 발생할 수 있다. 실제 횟수는 조회 경로·월 수·권한 필터·캐시 적중률에 따라 달라진다. 병렬도 제한은 동시 부하를 낮추지만 총 호출을 없애지는 않는다.

현재의 조회자별 캐시는 권한 분리를 위한 의미가 있다. 비용을 줄이려고 다른 조회자의 결과를 섞으면 안 된다. 실행 인스턴스의 메모리 캐시만으로 전체 설치의 호출 예산을 보장할 수도 없다.

권장 순서는 다음과 같다.

1. 누락 재게시와 잠금 정합성을 먼저 고친다. 잘못된 상태를 빠르게 캐시하는 최적화는 하지 않는다.
2. 요청 범위에서 동일 계정·월·이슈 조회를 합치고, 날짜 범위를 초기에 제한한다.
3. 신뢰 키 캐시와 문서 캐시를 분리하되 키 폐기 시 관련 검증 결과를 무효화한다.
4. 동일 요청의 권한 확인·숨김 기록 보충이 중복되는지 계측한다. 조회자 경계를 유지한다.
5. 변경 문서와 복구 대상 위주로 이벤트 처리하고, 일일 정합성 확인은 커서로 이어간다.
6. 문서 바이트 수, 잘림 건수, API 호출 수, 게시 지연, 복구 지연, 권한 거부를 계측한다. 사용자 설명·반려 사유 원문은 로그에 남기지 않는다.

프로퍼티의 건당 용량과 Approval SQL의 1GiB 저장 용량은 다른 제한이다. 200명이라는 숫자만으로 SQL 사용 가능 기간을 계산할 수 없다. 하루 워크로그 수 × 변경 횟수 × 이력 행 크기 × 보존 기간에 인덱스·승인 결정·통제 로그 용량을 더해 측정해야 한다. 감사 자료는 내보내기 파일 생성만으로 삭제하지 않고, 다운로드·무결성·보관 책임과 삭제 대상 범위를 확정한 뒤 정리한다.

이번 검토에서는 실측 호출·행 크기·유료 사용량이 없으므로 월 비용을 금액으로 확정하지 않는다. Forge 플랫폼 한도와 과금 기준은 배포 시점 공식 문서를 다시 확인한다. [Forge 한도](https://developer.atlassian.com/platform/forge/platform-quotas-and-limits/)

## 8. 승인 이력과 프로퍼티 삭제를 별도로 다뤄야 한다

프로퍼티 삭제는 원장의 승인 결정을 바로 삭제하지 않는다. 하지만 팀장 판정, 통계, 입력 통제가 오래된 상태로 남을 수 있다. 이슈 삭제는 원본 조회와 이력 표시 권한에도 영향을 준다. 원장이 남아 있다는 이유만으로 누구나 삭제된 이슈의 이력을 보게 하면 안 된다.

감사 원장에는 승인 대상 식별자, 당시 지문, 결정자, 시각, 결정 및 원인, 정책 버전, 통제 작업 결과를 보존해야 한다. Jira 원본이 없어진 뒤에도 무엇을 승인했는지 설명할 최소 증거가 필요하다. 단, 프로퍼티에 사용자 본문·반려 사유·민감 설정을 복사해 두는 방식으로 해결하지 않는다.

자세한 삭제 영향과 운영 대응은 [프로퍼티 삭제 영향 문서](cloudjira--ENTITY_PROPERTY_DELETION_IMPACT.md)를 함께 본다. [외부 저장소 문서](cloudjira--CUSTOMER_MANAGED_STORAGE_DESIGN.md)는 별도 선택지이며 이번 개선의 전제가 아니다.

## 10. 권장 작업 순서

첫 작업은 누락 복구의 동일 내용 생략 문제를 수정하고, 삭제→감지→재게시→수신까지 연결 테스트를 추가하는 것이다. 다음으로 승인 확정과 잠금 적용의 순서를 정하고 경합 시험을 통과시킨다.

그다음 조직 최신성·키 폐기·과거 문서 재사용을 정리한다. 모드별 통계 기준과 대상 범위를 고정한 뒤 설정·이슈 모달·통계 화면을 같은 상태 모델로 맞춘다. 마지막으로 실제 호출량과 문서 크기를 측정해 캐시·배치·분할 필요성을 결정한다.

완료 보고에서는 ‘기존에 구현됨’, ‘이번에 수정함’, ‘로컬 검증함’, ‘실사이트 검증 필요’를 나눠 적어야 한다. 특히 승인·마감 후 수정 불가를 증명하기 전에는 전체 요구사항이 끝났다고 보고하지 않는다.
