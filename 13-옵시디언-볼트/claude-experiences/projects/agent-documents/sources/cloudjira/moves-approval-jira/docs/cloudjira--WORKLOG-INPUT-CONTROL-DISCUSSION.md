# 워크로그 입력 통제 방식과 운영 부담 — 논의 기록

> 정리일: 2026-10-12 · 논의: 2026-10-11~12
> 상태: 비교 검토. 최종 방식 미선택. 이번 요청은 논의 저장이며 구현·배포 지시가 아니다.

## 1. 사용자가 원하는 것

Jira 기본 입력 대신 우리 앱의 등록 화면과 지원 가능한 이슈 수정 화면의 앱 필드를 통해 워크로그를 입력하게 하고, 우리 정책에 따라 특정 이슈의 생성을 허용하거나 거부한다.

논의 중 API 우회까지 차단하는 방식도 검토했지만, 모든 외부 경로 차단이 필수인지 아직 확정하지 않았다. 사용자가 최근 우려한 비용은 개발 일정뿐 아니라 **계속 발생하는 저장·API 호출·집계·장애 복구 부담**이다.

## 2. 기본 화면을 대체한다는 의미

- **Log work 버튼:** 새 작업 시간을 입력하는 진입점.
- **Work log 탭:** 이미 기록된 작업 시간 목록.

우리 앱을 Jira의 time tracking provider로 선택하면 기본 버튼과 탭을 숨기고 앱 모듈로 대체할 수 있다. 기본 시간 추적 필드의 Log work 동작도 비활성화되며 잔여 시간 입력은 유지된다. 설치만으로 적용되는 것이 아니라 관리자의 provider 선택이 필요하다. 이 기능은 사이트 단위 UI 설정이며 REST 생성 권한을 회수하는 기능은 아니다.

기존 저장소에는 provider·issueAction·issueActivity 구성이 있다. 실제 사이트의 선택 상태와 모든 입력 경로 동작은 별도 실측 대상이다.

## 3. 두 방식의 차이

| 항목 | A. asUser 유지 + 우리 입력 통제 | B. asApp 대행 + 사용자 권한 회수 |
|---|---|---|
| 우리 화면의 특정 이슈 입력 차단 | 가능. 서버에서도 정책 검증 | 가능. 서버에서도 정책 검증 |
| Jira 기본 입력 UI | provider로 대체 | provider로 대체 |
| 사용자 직접 REST 생성 | 권한이 남으므로 가능 | 프로젝트의 유효 생성 권한 회수 시 거부 |
| 다른 앱·자동화 | 별도 경로로 남음 | 해당 주체에 권한이 있으면 여전히 가능 |
| Jira에 남는 작성자 | 실제 사용자 | 앱 계정 |
| 실제 작업자 추가 정보 | 불필요 | 서명된 worklog properties 필요 |
| 사람별 통계 | 기존 Jira author 기반 유지 | properties 해석으로 우리 앱·워크포스 수정 |
| Jira 기본 작성자 통계 | 실제 사용자 기준 | 앱 계정 기준. properties를 자동 반영하지 않음 |
| 추가 운영 부담 | 기존 처리에 정책 검증·provider 운영 | 서명·추가 호출·두 단계 복구·키 수명 관리 |

**A에서도 버튼만 비활성화해서는 안 된다.** resolver의 서버 검증으로 우회 호출을 거부한다. 다만 우리 resolver를 거치지 않는 Jira REST 호출까지 막는 것은 아니다.

B의 권한 회수는 프로젝트 범위다. 특정 이슈만 우리 정책으로 다르게 처리할 수는 있지만, 같은 프로젝트에서 사용자의 직접 생성 권한을 남기면서 특정 이슈만 앱 전용 생성으로 강제할 수 있다고 보장하지 않는다. 상태 기반 금지 속성은 다른 방법이며 같은 워크플로의 해당 상태에 적용된다.

## 4. asApp 방식에서 실제로 부담하는 것

### 저장

워크로그 시간·설명은 Jira에 저장한다. 실제 작업자 ID와 서명도 워크로그 properties에 저장할 수 있으므로 별도 영구 소유권 SQL 테이블은 기본안에서 제외했다. 새 저장 서버를 도입하는 안도 아니다.

그러나 기존 Forge SQL의 승인·실행 op·중복 방지·통제 기록은 유지된다. 미해결 작업과 완료된 intent의 재실행 방지 정보도 필요하다. 따라서 우리 저장 비용이 0이 되는 것은 아니다. properties가 삭제되면 남아 있는 신뢰된 복구 자료가 필요하다.

### 생성 호출과 복구

검토한 설계는 워크로그 ID에 실제 작업자 서명을 결속한다. ID는 생성 후에 알 수 있으므로 기본 경로가 다음과 같다.

1. 워크로그 POST.
2. 확정된 ID를 포함한 identity property PUT.
3. 최종 property 재조회·검증.

기존 POST에 비해 추가 Jira 호출과 서버 실행이 발생한다. POST는 성공했지만 property 저장이 실패할 수 있으므로 확인 중 상태·재조회·보정 작업이 필요하다. 결과가 불명확한 POST를 다시 보내 중복 기록을 만들지 않도록 기존 op를 유지한다.

Jira 호출 횟수가 곧 API 호출당 별도 요금을 뜻하는 것은 아니다. 여기서 비용은 Forge 실행·SQL·응답 처리 자원, 지연, Jira rate limit과 운영 부담을 포함한다. 실제 청구액은 현행 요금과 사용량을 별도로 확인해야 하며 이번 논의에서 금액을 산출하지 않았다.

### 조회·통계

앱 명의 기록은 `worklogAuthor = 실제 사용자`로 찾을 수 없다. 후보 워크로그를 읽고 properties를 검증해 사람별로 분류해야 한다. expand가 동작하면 같은 응답에서 읽을 수 있지만, 미지원 시 개별 property GET이 늘 수 있다. 여러 사용자의 통계를 반복 조회하면 같은 후보를 다시 읽는 비용도 생긴다.

따라서 큰 부담 후보는 사용자 ID 문자열의 저장량보다 **사람별 후보 검색량, API 호출 수, 서명 검증·복구 실행량**이다. 데이터가 커지면 파생 인덱스나 캐시가 필요할 수 있고 그때는 추가 SQL 비용도 비교해야 한다.

### 연동·키 운영

워크포스는 서명된 실제 작업자 정보를 해석하도록 수정해야 한다. Jira 기본 보고서나 다른 외부 앱은 이를 자동으로 이해하지 않는다. 공개키 교체·폐기·과거 서명 검증·앱 제거/재설치·내보내기도 운영 대상이다.

## 5. 비용 판단에 필요한 측정

현재 자료만으로 월 비용이나 절감률을 확정하지 않는다. 최소한 다음을 측정한다.

- 월 신규·수정·삭제 건수, 기존 op 보관량.
- 개인/팀 통계 조회 빈도와 조회 기간, 후보 워크로그 수.
- properties expand 지원 여부, 페이지 및 개별 GET 수.
- Forge 실행량·SQL 읽기/쓰기·저장 증가량, 응답 크기와 p95 지연.
- timeout·429·미완료 작업 발생률과 보정 횟수.

A와 B를 동일한 데이터·권한 범위에서 비교한다. B가 저장 테이블을 줄인다고 전체 운영 비용도 낮아진다고 단정하지 않는다.

## 6. 결정 상태와 권고

| 내용 | 현재 상태 |
|---|---|
| asApp 사용 가능, Jira 작성자가 앱으로 표시됨 | 사용자 수용 |
| 실제 작업자 정보를 worklog properties에 저장하는 안 | 문서화 요청 완료 |
| 별도 영구 소유권 SQL 원장을 기본안으로 채택 | 채택하지 않음. properties 대안으로 변경 |
| REST·다른 앱까지 전면 차단 필수 | 미확정 |
| asUser/asApp 최종 선택 | 미확정 |
| 구현·배포 | 이 논의에서는 실행하지 않음 |

일반 사용자의 Jira 화면 입력을 우리 정책으로 통제하는 것이 목적이면 **A를 우선 검토**한다. 실제 사용자 작성자를 보존하고 추가 identity 저장·서명·두 단계 게시가 필요 없어 운영 부담이 작다. 이것은 검토 권고이며 사용자의 최종 선택으로 기록하지 않는다.

사용자 직접 REST 생성까지 막아야 한다면 B의 권한 분리 실측과 비용 측정을 먼저 수행한다. 다른 앱·자동화까지 포함한 우리 앱 전용 생성은 별도 검증 없이는 보장하지 않는다.

참고로 논의 중 나온 개발 일정은 A 약 2~4근무일, B 약 10~19근무일(1인 개발, 기존 코드 수정·테스트·실측 포함)의 거친 추정이었다. 새로운 이슈 수정 모달 필드 구현은 별도이며, 확정 견적이나 운영 비용 추정치가 아니다.

## 7. 관련 설계와 근거

- [asApp 입력 통제 설계 1판](cloudjira--APP-MANAGED-WORKLOG-DESIGN.md): 권한 분리·입력 정책과 대안 검토 이력.
- [properties 기반 실제 작업자 설계](cloudjira--WORKLOG-IDENTITY-PROPERTIES-DESIGN.md): B를 선택할 경우 적용할 저장·서명·복구 설계. 최종 방식 선택을 의미하지 않음.
- [Forge time tracking provider](https://developer.atlassian.com/platform/forge/manifest-reference/modules/jira-time-tracking-provider/): 기본 입력 버튼·목록 대체와 시간 추적 필드 동작.
- [Jira Worklogs API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-worklogs/): 생성·조회 권한 및 properties 입력 계약.
- [Worklog properties API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-worklog-properties/): 워크로그별 추가 데이터 저장·조회.
- [Forge requestJira](https://developer.atlassian.com/platform/forge/apis-reference/fetch-api-product.requestjira/): asUser와 asApp 실행 주체.

위 API 근거는 2026-10-11 대화 중 확인한 자료다. 문서/API 확인과 실제 사이트에서의 권한·성능 검증은 구별한다. 당시 CLI는 현재 앱의 설치 대상이 없다고 반환했으며 실제 생성 시험은 수행하지 않았다.
