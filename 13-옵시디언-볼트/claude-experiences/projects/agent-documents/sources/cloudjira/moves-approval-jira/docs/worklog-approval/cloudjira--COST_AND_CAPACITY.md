# 비용·저장 용량 계획

기준일: 2026-10-13. 대상은 200명 규모의 워크로그 승인 운영이다. 공식 가격과 플랫폼 한도, 현재 코드에서 확인한 비용 절감 구조, 아직 실측하지 않은 계획 가정을 구분한다. 아래 금액은 Marketplace 앱 이용료·Jira 구독료·세금·환율을 포함하지 않으며 실제 청구액 보장이 아니다.

## 1. 비용을 계산하는 단위

Forge 무료 사용량은 앱별 월 단위이며 동일 앱의 설치와 환경에서 공유한다. Approval과 Workforce의 서로 다른 app id에는 각각 무료 사용량이 적용된다. 한 고객의 200명 사용량이 무료 안에 있어도 같은 앱의 다른 고객 설치가 한도를 소비하면 비용이 발생한다. [현행 Forge 가격과 무료 사용량](https://developer.atlassian.com/platform/forge/forge-platform-pricing/)

| 자원 | 월 무료량 | 초과 단가, USD |
| --- | ---: | ---: |
| Functions | 200,000 GB-seconds | 0.000025 / GB-second |
| SQL 요청 | 100,000회 | 1.929 / 1,000,000회 |
| SQL 실행 시간 | 1시간 | 0.143 / 시간 |
| SQL 저장 | 730 GB-hours | 0.00076850 / GB-hour |
| KVS 읽기 | 0.1 GB | 0.055 / GB |
| KVS 쓰기 | 0.1 GB | 1.090 / GB |
| 로그 쓰기 | 1 GB | 1.005 / GB |

이 표는 2026-08-12 갱신된 [공식 요금표](https://developer.atlassian.com/platform/forge/forge-platform-pricing/)를 2026-10-13 확인한 값이다. 과거 안내의 Functions 100,000 GB-seconds를 현재 무료량으로 사용하지 않는다.

요청 수와 실행 시간은 SQL의 별도 과금 축이다. DB 저장비는 월말 크기에 한 번 요금을 곱하는 방식이 아니라 각 시간의 저장량을 누적한다. Jira REST 호출 수와 큐 이벤트 수에 이 표의 별도 단가를 임의로 만들지 않는다. 그 작업에 사용한 함수·SQL·KVS·로그를 계산하고 REST rate limit은 별도 제약으로 관리한다. [Jira rate limiting](https://developer.atlassian.com/cloud/jira/platform/rate-limiting/)

## 2. 현재 구현에서 비용을 줄인 구조

- 승인 원장과 인증 테이블을 재사용해 새 승인 테이블·마이그레이션을 추가하지 않았다.
- Approval의 예약 트리거는 일일 하나다. 작업은 큐로 분산하고 기능 OFF·미연결이면 SQL 전에 반환한다.
- 인증 변경 직후 아웃박스를 표시하고 이벤트 큐로 게시한다. 반복 변경은 45초 창에 합친다. 인증 없는 날의 이벤트 큐 작업은 없다.
- 게시 작업은 리스와 커서를 사용한다. 불완전한 배치를 완료로 처리하거나 무한 재시도하지 않는다.
- 업무함 워크로그 정보와 숨김 참여자 범위는 페이지 단위 일괄 조회한다. 각 행마다 요청·이벤트 전체를 다시 읽지 않는다.
- Workforce 집계에서 읽지 않는 KVS 캐시에 계속 쓰던 경로를 제거했다. 승인 상태·현재 권한을 확인한 집계를 사용한다.
- 자동 승인자 확인은 후보 한 명당 현재 이슈 id/key 확인과 issueKey 후보 검색, 최대 REST 2회다. 이 비용을 누락한 가정은 쓰지 않는다.

유휴 SQL 횟수는 Approval의 `idleSqlBudget.test.js`로 고정한다. 미연동 하루 27회, 연동 설치는 총 38회다. 30일 연동 설치는 1,140회다. 이 값은 활성 사용자 요청·변경 이벤트·재시도·다른 Workforce 기능의 비용을 포함하지 않는다. [Forge 비용 최적화 원칙](https://developer.atlassian.com/platform/forge/optimise-forge-costs/)

## 3. 200명 월 사용량의 계획 예시

월 20근무일로 가정하면 `월 기록 수 = 200 × 20 × 1인 하루 기록 수`다. 승인·결정·이력·통제·게시까지를 한 건의 처리로 묶은 아래 자원량은 **아직 계측하지 않은 가정**이다.

| 가정 | 값 | 실제 확인할 지표 |
| --- | ---: | --- |
| 기록 한 건의 SQL | 50회 | 생성·관찰·접수·결정·투영·게시 요청 수 |
| SQL 한 요청의 실행 | 평균 10ms | SQL compute duration; REST 대기 시간과 구분 |
| 기록 한 건의 함수 | 8회 × 2초 × 0.5GB | invocation duration × configured memory |
| 기록 한 건의 KVS | 읽기 16KiB, 쓰기 8KiB | 실제 읽기/쓰기 청구 크기 |
| 월 화면·기타 처리 | SQL 12,000회, 함수 5,000GB-s, KVS 읽기0.01GB/쓰기0.002GB | 업무함·설정·권한 재확인 등 |
| Approval 연동 유휴 | SQL 1,140회/30일 | 해당 회귀 테스트의 빈 상태만 |

현재 두 manifest와 실제 실행 수치는 별도로 확인해야 한다. 0.5GB는 비용 민감도 계산용이며 모든 함수의 실제 메모리 설정을 주장하는 값이 아니다.

위 가정을 한 앱에 적용하고 다른 설치 사용량이 없으며 저장·로그가 무료량 안에 있으면 다음과 같다.

| 1인 하루 기록 | 월 기록 | SQL 요청 | SQL 실행 시간 | 함수 GB-s | 계산상 월 초과 비용 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1건 | 4,000 | 213,140 | 약0.59시간 | 37,000 | 약$0.22 |
| 3건 | 12,000 | 613,140 | 약1.70시간 | 101,000 | 약$1.09 |
| 5건 | 20,000 | 1,013,140 | 약2.81시간 | 165,000 | 약$2.10 |

SQL 요청비는 `max(0,요청수−100000)/1000000×1.929`, 실행비는 `max(0,시간−1)×0.143`이다. 함수비는 `max(0,GB-s−200000)×0.000025`다. KVS는 각 읽기/쓰기 초과량에 단가를 적용한다. 계산은 KiB=1024bytes, 계획표의 GB=10^9bytes로 환산했다. 공식 청구 화면의 실제 사용량을 최종 기준으로 삼는다.

**이 금액을 Approval+Workforce 전체 운영비라고 안내하면 안 된다.** Workforce의 대시보드·달력·그래프·원가 계산, 다른 설치·개발 환경, 대량 과거 동기화, 긴 REST 대기, 재시도, 소명 회차 증가가 빠져 있다. API가 빠르게 응답하는 정상 처리의 계획 예시다. [Forge 사용량·비용 모니터링](https://developer.atlassian.com/platform/forge/monitor-usage-metrics/)

건당 SQL을 30/50/100회로 바꾸면 월 12,000건의 요청 수만 약37만/61만/121만회로 달라진다. SQL 평균 실행 시간이 10ms에서 50ms로 늘면 실행 시간비도 크게 달라진다. 예상 비용을 고정 계약값으로 쓰기 전에 실제 트래픽을 계측해야 한다.

## 4. 1GiB가 얼마나 버티는가

Forge SQL의 설치별 저장 한도와 앱별 무료 저장 사용량은 서로 다르다. 공식 제한은 production 1GiB, staging 256MiB, development 128MiB다. 현재 StorageService의 1GiB 기본 기준은 production 계획 값이며 개발 환경의 실제 한도를 늘리지 않는다. [Forge SQL와 제한](https://developer.atlassian.com/platform/forge/storage-reference/sql/)

한 기록의 SQL 원장·요청·결정·이벤트·인증·통제·변경 이력·인덱스를 합쳐 **4.5–9KiB/건**으로 계획한다. 이는 부하 시험 결과가 아니다. 긴 설명 원문 보관 옵션, 반복 수정, 승인 단계·소명 횟수, 인덱스와 DB 공간 통계에 따라 달라진다. 이전의 생성 기록만 센 148MB 추정은 새 건별 승인 원장까지 포함한 용량 추정으로 사용하지 않는다.

연 240근무일, 200명이 동일 빈도로 기록할 때:

| 1인 하루 기록 | 연 기록 | 연 증가량 | 빈 DB에서 95%에 도달하는 단순 추정 |
| ---: | ---: | ---: | ---: |
| 1건 | 48,000 | 211–422MiB | 약2.3–4.6년 |
| 3건 | 144,000 | 633–1,266MiB | 약0.77–1.54년 |
| 5건 | 240,000 | 1,055–2,109MiB | 약0.46–0.92년 |

95%는 972.8MiB이며, 표는 기존 데이터가 0이고 모든 데이터가 이 기능에서만 증가한다고 가정했다. 기존 팀·정책·알림·서명·다른 이력과 변경 회차가 있으면 기간은 짧아진다. 모든 사용자가 매일 작성한다는 보장도 없으므로 숫자를 실제 남은 날짜로 표시하지 않는다.

## 5. 경고와 내보내기의 정확한 의미

| 사용률 | 앱에서 제공하는 안내 | 관리자의 행동 |
| ---: | --- | --- |
| 70% | 보관 관리 안내 | 증가 추세와 정책 검토, 파일 보관 준비 |
| 85% | 경고·내보내기 권고 | 데이터관리에서 export, 파일 건수·기간·해시 확인 |
| 95% | 긴급 관리 안내 | 새 저장 실패 위험 관리, 허용 범위 정리 및 보호 원장 비중 확인 |

관리자가 앱에 접속했을 때 캐시된 저장 사용량의 인라인 배너를 보여 준다. 동일 경고 알림을 SQL에 반복 적재하지 않는다. 외부 이메일/push, 서버 자동 파일 생성·저장, 용량이 찼다는 이유의 자동 DELETE는 구현하지 않았다. 테이블 통계는 추정이며 정리 후 지표 반영 지연이 있을 수 있다.

**내보내기는 백업 파일을 만드는 행위이며 원장 삭제 허가와 다르다.** 현재 승인된 워크로그의 승인 근거와 신규 인증·출처 핵심 행은 보관 정리에서도 보호한다. 따라서 export를 해도 그 공간은 회수되지 않는다. 일반 변경 이력·보관 기간이 지난 허용된 자료만 export 확인 후 관리자 정리 대상이 된다.

1GiB에서 승인 핵심 원장을 영구히 쌓는 설계로 무기한 운영을 보장할 수 없다. 검증된 파일 아카이브와 최소 불변 증빙만 남기는 압축 보관, 월 문서 분할, 별도 감사 보관함은 향후 구현 범위다. 현재 존재하는 기능으로 설명하지 않는다.

## 6. 출시 후 계측·운영 절차

1. 승인 전/후, 마감, 반려 재요청, 소명, 외부 변경, 재시도 사례를 포함해 대표 사용량을 수집한다.
2. SQL table별 건수·저장량, compute requests/duration, Functions GB-s, KVS bytes, 로그량을 Developer Console에서 확인한다. 사용자 사유·설명 원문을 계측 로그에 남기지 않는다.
3. `추가 저장 bytes / 신규 worklog 수`와 `총 SQL 요청 / 신규 worklog 수`를 구하되 화면 조회·과거 보정 사용량을 따로 기록한다.
4. 7–30일 실제 증가량으로 70/85/95% 도달 예상과 비용을 다시 계산한다. 앱의 다른 설치가 무료량을 소비하는지도 확인한다.
5. export 파일을 열어 건수·기간·manifest를 확인하고 조직이 관리하는 저장소에 보관한다. 허용 정리 후 보호된 승인 행과 조회/집계가 유지되는지 확인한다.
6. 삭제 이슈 승인 원본은 현재 권한 필터로 export에서도 제외될 수 있다. worklog 변경 이력의 가린 기본 metadata export와 구분하며, 중요 감사 자료는 삭제 전에 보관한다. [상세 운영 가이드](cloudjira--USER_AND_ADMIN_GUIDE.md)

비용 감시와 저장 안전성을 함께 판단한다. 초과 비용이 작더라도 설치별 저장 한도에 닿으면 쓰기가 실패할 수 있다. 반대로 파일이 있다고 일반 사용자의 조회 권한이나 승인 잠금을 완화하지 않는다.

## 추가 API·화면 기능의 비용

위 계획표에는 신규 Jira effort custom field 3개의 value function, 외부 조직 API 호출, rich-text 설명 크기 증가가 포함되어 있지 않다. 필드는 이슈 조회 때 각각 계산되므로 화면 조회 빈도와 묶음 크기에 따라 함수 호출·실행 시간이 늘어난다. 조직 조회는 팀 페이지 10개·팀당 100명·전체 500명 상한이며 기존 팀 resolver가 SQL을 사용한다. 실제 사용량으로 별도 측정해야 한다.

설명 ADF 최대 크기와 서식은 실제 워크로그 및 변경 이력 크기에 영향을 준다. 1GiB 보관 기간은 평균 행 크기·기록 빈도·설명 저장 정책을 실측해 다시 계산한다. 수동 API access token 만료 후에는 관리자 재연결 작업이 필요하며 현재 자동 갱신 운영을 제공하지 않는다.
