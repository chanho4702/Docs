# status-rule-kvs — 상태 변경 승인: 규칙 KVS 이전 · 막힐 때 자동 요청 · 프로젝트 초기 세팅

> 2026-10-21 · 사용자 요청 대화 요약. 선행: `_workspace/product-polish-2026-10-20/`(상태 변경 승인 재활성화, 커밋 002ad3c·fdb0abe·3fe95ae)

## 배경
- 상태 변경 승인(전환 승인)은 `statusChangeApprovalEnabled`(기본 꺼짐)로 다시 열었다. validator 는 함수형(`transition-approval-validator`).
- T1 실측(2026-10-21, dev): validator payload = `context, contextToken, issue{id,key}, modifiedFields, transition{from,to}, user`.
  **목적 상태(to)·출발 상태(from)·이슈 id/key·accountId 는 온다. projectId·issueTypeId·transitionId·locale 은 없다.**
- 지금 검사는 전환마다 SQL `transition_rule` 조회(`rules.findByStatus`) + 테이블 준비 확인을 한다 — 규칙 없는 전환도 SQL 을 쓴다.
- 사용자: "DB 많이 쓰는 거 좀 그래서" — 설정류는 SQL 말고 Forge 커스텀 엔티티(KVS, 앱 전용)로. 이미 `channel-state` 엔티티를 쓴다.
  Jira 엔티티/프로젝트 프로퍼티는 쓰지 않는다(불변식 9 — 타인이 쓸 수 있음).

## 요구
1. **규칙 저장소 KVS 이전** — `transition_rule`(프로젝트×이슈 유형×목적 상태 → 결재선 flow_id, enabled)을 Forge 커스텀 엔티티/KVS 로 옮긴다.
   - 검사 경로: 목적 상태 키로 한 번 읽어 규칙이 없으면 **SQL 0·Jira 0** 으로 통과. 규칙이 있을 때만 이슈 조회(프로젝트·유형)·SQL 승인 확인.
   - 화면 경로: 프로젝트별로 읽고 쓴다. 저장 시 두 보기(프로젝트별·목적 상태별)를 함께 갱신. 원자성 방법(KVS transact 등)은 설계에서 정하고 미검증이면 스파이크 목록에.
   - 기존 `transition_rule` 테이블은 미사용으로 남긴다(고객 배포 전, 데이터 이관 불필요 — dev 규칙은 다시 만들면 됨. 단 간단한 1회 복사가 싸면 해도 됨). SQL 마이그레이션 추가 없음.
   - 요청·결재·이력·감사(`transition_request`, `approval_*`)는 SQL 그대로.
   - 테이블 준비 확인(tableReady)도 규칙이 있을 때만.
2. **막힐 때 승인 요청 자동 생성** — 사람이 전환을 시도해 validator 가 `REJECT_NO_REQUEST` 로 막을 때, 규칙의 결재선으로 요청을 그 자리에서 만들고 거부 문구를 "승인 요청을 올렸습니다. 승인되면 자동으로 '{상태}'(으)로 바뀝니다" 류로 바꾼다.
   - 설정: **프로젝트 기본값 + 규칙별 덮어쓰기**(규칙에 값이 없으면 프로젝트 기본값). 사이트 기본값 끔.
   - 요청자 = payload `user.accountId`. 자동화·앱 계정 등 사람이 아닌 실행자는 자동 요청하지 않는다(판별 방법 설계, 모르면 안 만든다).
   - transitionId 가 payload 에 없다 → 자동 적용용 전환은 출발→목적 조합으로 찾되, 하나로 정해지지 않으면 자동 적용 없이(수동 적용 안내) 요청만.
   - validator 시간 예산 안에서. 늦거나 실패하면 기존 `REJECT_NO_REQUEST` 문구로 후퇴(요청 생성 실패가 전환 통과가 되면 안 된다). 열린 요청은 대상당 하나(불변식 1)라 반복 시도는 기존 요청 안내.
   - 사유 없음(자동 생성 표시), 승인자 선택 없음(규칙 결재선).
   - 불변식 8: validator 는 사용자 컨텍스트 없는 경로. 요청 생성이 asUser 를 부르면 안 된다 — 생성 경로의 Jira 호출 지도 확인.
3. **프로젝트 초기 세팅** — Jira 프로젝트 설정 > Moves Approval 페이지에 시작 순서: 목적 상태 고르기 → 결재선 → 자동 요청 → 검사 연결 안내.
   - 사이트 관리자가 "새 프로젝트 기본 템플릿"(결재선·자동 요청 기본값)을 정할 수 있다.
4. **검사 연결 상태 감지** — 규칙의 목적 상태로 가는 전환 중 validator 가 붙지 않은 것을 Jira 워크플로 조회 API 로 찾아 "검사 연결됨 / 누락 N개" 표시. 앱이 워크플로를 고치지는 않는다(안내만). 필요한 scope 가 manifest 에 없으면 설계에서 비용(재동의·major) 판단 — 큰 비용이면 이 항목은 후속으로 미루고 수동 확인 안내 유지.

## 완료 기준
- 검사: 규칙 없는 전환 SQL 0회(쿼리 수 테스트 고정), 규칙 있는 전환의 기존 판정 표 동일.
- 자동 요청: 켬이면 막힘과 동시에 PENDING 요청 1건, 재시도는 같은 요청, 실패는 기존 거부, 끔이면 기존 동작.
- 유휴 SQL 예산 테스트 그대로 통과. BE·UI 테스트·빌드 통과. resolver 3단계 등록 계약 통과.
- 개발 사이트 배포 후 WORK 전환 21(validator 연결됨)로 확인 가능해야 한다(기능 켜기는 사용자 확인 후).
