# field-change-approval — 이슈 필드 변경 승인(요청형)

> 로드맵 8번(2026-10-04 사용자 지시). 근거: `docs/DESIGN.md` §2 ③ "기타 변경 — 요청형".

## 핵심 제약 (수용 기준에 그대로 적는다)

- Jira 에는 필드 변경을 **미리 막는 장치가 없다.** 우리 화면을 거친 변경만 승인 후 적용되고, Jira 화면·REST·자동화로 직접 바꾼 것은 **사후 감지**만 된다.
- 차단을 원하는 고객은 해당 필드를 편집 화면에서 빼거나 권한으로 막아야 한다 — 가이드 문구를 설정 화면에 둔다.

## 목표

관리자가 정한 필드(예: 마감일·담당자·우선순위·스토리 포인트 등)를 바꾸려면 **요청 → 결재 → 승인 시 적용**.

## 해야 할 것

1. **규칙**: 프로젝트 × 이슈 유형[또는 전체] × 필드 → 결재 Flow. 지원 필드 타입을 설계에서 한정한다(1차: date·user·priority·number·single select 정도. 다중값·리치텍스트는 범위 밖 — 이유를 적는다).
2. **요청**: 이슈 화면에서 "필드 변경 요청" — 현재 값(요청 시점 스냅샷)·새 값·사유. `scopeKey = FIELD_CHANGE:{issueId}:{fieldId}`(필드당 열린 요청 하나).
3. **적용 주체**: 최종 승인 시점에 **최종 결재자의 asUser** 로 적용하는 것을 우선 검토(이력의 수정자가 앱이 아니라 사람이 된다). 결재자에게 편집 권한이 없으면 정책에 따라 asApp 적용(이력 수정자 = 앱 계정, `AGENTS.md` asApp 허용 목록에 사유 추가) 또는 적용 실패로 요청자에게 넘김. 설계에서 장단을 비교해 기본값을 정한다.
4. **충돌**: 적용 직전 필드의 현재 값이 요청 시점 스냅샷과 다르면 적용하지 않고 요청을 만료(사유 `FIELD_CHANGED`) + 알림. 조용히 덮어쓰지 않는다.
5. **우회 감지**: 기존 `onIssueChanged` 트리거에서 규칙 대상 필드가 우리 경로 밖에서 바뀐 것을 감지 → 감사 기록 + 알림. 되돌리기는 기본 꺼짐(opt-in, asApp).
6. **표시·감사**: 이슈 요약·업무함·증명서에 "필드: 이전 값 → 새 값". 감사 이벤트 결정적 id.

## 완료 기준

테스트·빌드 통과. 충돌(스냅샷 불일치) 시 적용하지 않음, 같은 필드 열린 요청 하나, 적용 재시도 시 이중 적용 없음(멱등)을 테스트로 증명.

## 범위 밖

다중값·리치텍스트 필드, 이슈 생성·삭제 승인, 배포.
