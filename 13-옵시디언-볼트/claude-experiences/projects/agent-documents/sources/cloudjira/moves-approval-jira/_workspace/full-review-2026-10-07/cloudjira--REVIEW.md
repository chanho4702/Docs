# Moves Approval Jira 전체 검수와 개선

검수 기준: 2026-10-07 현재 작업 트리. 기존 수정과 신규 파일을 포함해 검토했으며 커밋·푸시·배포는 수행하지 않았다. 이 보고서는 이번에 수정한 사항과 남은 설계 문제를 구분한다.

## 수정한 문제

상세 JSON 시트는 서버가 반환한 자료를 보존한다. recordKind+recordIndex별 part를 순서대로 연결해 JSON.parse하면 원본 레코드를 복원할 수 있다. 셀마다 30,000자 이하로 나누며 UTF-16 surrogate pair를 보존한다. 이 파일은 전체 DB 복원이나 자동 재수입을 보장하는 백업 계약은 아니다.

## 남은 설계·운영 문제

다음 항목은 이번 수정으로 해결됐다고 보지 않는다. 재현 조건과 코드 근거는 [설계 검수 보고서](cloudjira--01_architect_design.md)에 있다.

1. **내보낸 집합과 삭제 집합을 서버에서 고정하지 않는다.** 현재 완료 기록은 클라이언트가 보낸 cutoff/count다. 외부 적용 대기 상태가 풀리면 부모 updated_at이 같아도 예전 cutoff 안에 새 삭제 대상이 들어올 수 있다. 서버에서 내보내기 세션과 요청 ID 집합을 고정하는 방식이 필요하다.
2. **PIN 실패 횟수가 동시 요청에서 유실된다.** 읽은 failCount+1을 덮어쓰기 때문에 실제 실패 5회와 잠금 기준이 달라질 수 있다. 실패 증가·잠금과 성공 초기화를 동일 PIN 세대의 조건부 SQL로 처리해야 한다.
3. **필드 변경의 timeout은 전환 승인보다 약하게 관리된다.** PUT 결과 불명확을 FAILED로 만들고 현재 값 비교로 재시도한다. 성공 뒤 사용자가 원래 값으로 되돌린 경우와 실패를 구분하지 못하고, 조회와 PUT 사이의 타 사용자 변경도 원자적으로 보호되지 않는다. UNKNOWN과 changelog 대조를 도입할지 결정해야 한다.
4. **실패한 스윕 페이지를 24회 뒤 건너뛴다.** 트리거도 실패를 삼키므로 건너뛴 ID를 영속 재처리 큐에 보존하지 않으면 이력·무효화·변경 감지가 누락될 수 있다. 실패를 버린 완주와 정상 완주를 구분해야 한다.
5. **임박·독촉 후보 첫 100건에 반복해서 묶일 수 있다.** SQL LIMIT 뒤 이미 발송한 후보와 비활성 정책을 제거하며 다음 페이지가 없다. 키셋 커서·공통 예산·다음 실행 재개가 필요하다.
6. **카운트와 목록의 권한 범위가 다르다.** 목록은 현재 대상 가시성을 적용하지만 업무함·미읽음 집계는 SQL 참여 범위만 집계한다. 권한을 잃은 요청이 숫자에 남는 기존 선택이다. 정확한 가시 건수와 조회 비용 중 무엇을 보장할지 정해야 한다.
7. **미적용 필드 변경의 보관 보호가 다른 대상과 다르다.** worklog/transition의 APPLYING·UNKNOWN·대기는 보호하지만 field_change_request에는 같은 조건이 없다. 미적용 승인도 기간 후 삭제할지 적용 생명주기 기준을 통일해야 한다.
8. **보관 파일이 모든 세부 근거를 포함하지는 않는다.** fieldChange 공유 조회는 적용자·실패 코드·충돌 값 등을 모두 반환하지 않고, TIMESHEET findSubmission은 일부 연동 metadata를 별도 메서드로 읽는다. 상세 시트는 반환 자료 보존을 해결했으며 모든 부속 테이블 컬럼의 보존은 별도 계약이 필요하다.
9. **관리자 보관 내보내기의 Jira 권한 경계를 명시해야 한다.** 워크로그 이력 export는 볼 수 없는 이슈를 가리지만 approval export는 같은 가시성 필터가 없다. 앱 관리자 권한과 현재 Jira 이슈 열람 권한을 어느 데이터까지 구분할지 정하고, 새 스냅샷을 포함한 모든 대상에 일관된 정책을 적용해야 한다.

우선순위는 삭제 허가 집합·PIN 동시성·관리자 내보내기 권한을 먼저 정리하고, 외부 쓰기 결과 불명확과 스윕 누락 복구를 이어서 다루는 순서다.

## 검수 범위와 한계

| 영역 | 확인한 경계 |
|---|---|
| 승인·대상 어댑터·증명서 | 결정과 적용 분리, 대상 재열람 검사, fingerprint 생산자/소비자 계약 |
| 권한·업무함·알림 | SELF 신원 고정, 종류별 fail-close, 페이지 이동, 집계와 목록의 차이 |
| 타임시트·워크로그·정책 계층 | 제출 지문·잠금 검사, 팀 범위, 정책 권위, 트리거/스윕 실패 처리 |
| 전환·필드 변경 | POST UNKNOWN 재전송 금지, SQL fencing과 외부 변경 경계 |
| 보관·서명/PIN·라이선스 | 내보내기/삭제 계약, 정책 장애, 알림 생성 경계 |
| Workforce·마이그레이션·UI | 서명 게시와 커서, 준비 상태, 번역·엔트리·쿼리키 계약, 번들 |

정적 검토와 로컬 테스트로 현재 경계를 확인했다. 실제 Forge SQL의 binary UUID 조회, 설치된 Jira의 권한 조합·오프라인 impersonation·트리거 누락률, 운영 호출량과 지연 시간은 배포·실환경 검증 대상이다. 모든 코드 경로와 플랫폼 조합에 문제가 없다는 보증은 아니다.

구현 상세는 [백엔드 결과](cloudjira--02_backend_report.md), [프론트 결과](cloudjira--02_frontend_report.md), 최종 실행 결과는 [검증 결과](cloudjira--03_verify_report.md)를 참고한다.

최종 검증: 백엔드 1437개·UI 409개 테스트 통과, UI 빌드 성공(의존성 경고 있음), Forge lint 통과.
