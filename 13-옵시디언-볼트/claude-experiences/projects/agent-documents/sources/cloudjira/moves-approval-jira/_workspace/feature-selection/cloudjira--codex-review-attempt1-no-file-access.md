## 결론

**코드에 근거한 독립 검토는 완료하지 못했습니다.** 파일 읽기 도구가 실행 단계에서 실패했습니다. PowerShell은 `setup refresh had errors`, Node 읽기 도구는 `trusted Node process exited unexpectedly`를 반환했습니다. 따라서 `CLAUDE.md`, 실제 `AGENTS.md`, `docs/DESIGN.md`와 소스 내용을 읽지 못했고, `파일:행` 근거를 제시할 수 없습니다. 파일은 수정하지 않았습니다.

**제공된 설명만을 바탕으로 한 잠정 권고는 “기능 선택은 도입하되, 비상 해제와 분리하고, 기존 기록·잠금 해제 경로는 남긴다”입니다.** 아래는 코드 검증 결과가 아닌 설계 의견입니다. 현재 구현에 관한 추측은 별도로 표시했습니다.

## 모델 검증

세 축은 사용자에게 설명하기 위한 출발점으로 적절하지만, 다음 두 가지를 구분해야 합니다.

- **제품 기능과 설정 메뉴 묶음:** 이슈 승인·타임시트 승인은 기능 이름이고, 워크로그 이력·인증·통제는 별도의 동작과 수명주기를 가질 수 있습니다. **추측:** 이를 두 기능에 일괄 종속시키면 타임시트 승인만 끄려다가 인증이나 통제 복구 화면까지 사라질 수 있습니다.
- **운영 모드와 결재자 원천:** 사용자 설명에 있는 “워크포스 지정 팀장, 없으면 명부 팀장”이 실제 동작이라면, “결재자는 워크포스 팀장이 합니다”라는 문장은 대체 동작을 누락합니다. “워크포스의 팀장 정보를 우선 사용합니다”와 보충 설명이 더 정확합니다.

“이슈 **상태 변경** 승인”이라는 첫 질문은 제안이 포함하려는 필드 변경 승인·일반 이슈 승인을 설명하지 못합니다. 이들을 포함한다면 “이슈 승인을 사용합니다”로 쓰고, 지원하는 승인 종류를 아래에 풀어야 합니다.

`isProjectEnabled` 소비처 전수, 타임시트 수집 범위까지의 간접 영향, 각 승인 종류의 프로젝트 범위는 **미확인**입니다. “적용 프로젝트는 이슈 승인과 워크로그 이력에만 적용된다”는 진단을 이번 검토에서 확정하지 못했습니다.

## 겸용 위험

**`transitionApprovalEnabled`를 비상 해제와 기능 선택에 겸용하는 안은 분리하는 것을 권고합니다.** 사용자 설명대로 끄면 validator가 모두 통과한다는 전제에 따른 판단입니다.

| 문제 | 권고 |
|---|---|
| “사용하지 않음”과 “장애 때문에 검사를 우회함”을 같은 값으로 표현 | 기능 선택과 비상 해제를 별도 정책으로 저장 |
| 변경 이력에서 관리자의 의도를 구별하기 어려움 | 기능 사용 변경과 비상 해제를 서로 다른 감사 사건으로 기록 |
| 기존 워크플로의 validator는 남는데 승인 화면만 사라질 수 있음 | 끄기 전에 실제 영향과 남아 있는 validator를 표시 |
| 다시 켤 때 기존 요청·규칙의 처리 의미가 불명확 | 재활성화 시 기존 요청·규칙 처리 방침 명시 |

키 후보는 `issueApprovalEnabled`, `timesheetApprovalEnabled`입니다. 다만 첫 키가 상태 변경·필드 변경·일반 이슈 승인을 모두 뜻할지는 먼저 결정해야 합니다.

기존 `transitionApprovalEnabled`는 의미를 보존한 채 비상 해제 영역으로 옮기는 것이 안전합니다. 기능을 끌 때 validator를 통과시킬지, 워크플로에서 제거해야 하는지는 별도 제품 계약입니다. 확인 모달에는 **“이미 설정된 승인 검사에 어떤 일이 생기는지”**를 구체적으로 적어야 합니다.

## 타임시트 끔 전수표

다음은 **전수 조사 결과가 아닌 권고 초안**입니다. resolver·서비스·큐 진입점과 행 번호는 확인하지 못했습니다.

| 경로 | 권고 | 꺼졌을 때의 의미 |
|---|---|---|
| 새 제출·재제출 | **막는다 + 숨긴다** | 서버에서 거절하고 제출 버튼 숨김 |
| 진행 중 요청의 결재·반려 | **그대로 둔다** | 기존 요청을 정리할 수 있도록 유지 |
| 신규 승인 기간 생성·승인 업무용 마감 | **막는다** | 승인 업무의 새 상태 전이 중단 |
| 기존 기간 재개·잠금 해제 | **그대로 둔다** | 운영 복구 경로 유지 |
| 자동 마감 스윕 | **조건부로 막는다** | 신규 승인 업무 생성은 중단; 다른 기능이 공유하면 분리 |
| 워크포스 결재 상태 게시 | **조건부로 막는다** | 새 승인 상태 생성은 중단; 기존 게시물 정합·정리 작업은 유지 |
| 인증 문서·통제 설정 게시 | **그대로 둔다** | 해당 기능이 별도로 켜져 있다면 유지 |
| 시간 추적 제공자의 승인 UI | **숨긴다** | 승인 제출·처리 영역만 숨김 |
| 일반 워크로그 작성·조회·수정 | **그대로 둔다** | 타임시트 승인 사용 여부와 분리 |
| 인증·재인증·관찰 | **그대로 둔다** | 인증 기능의 독립 정책에 따름 |
| 워크로그 통제의 제한·삭제·해제 | **그대로 둔다** | 기존 잠금·통제 상태를 승인 토글로 일괄 무효화하지 않음 |
| 과거 승인·감사 기록 조회·내보내기 | **그대로 둔다** | 기록 접근 유지 |
| 승인 관련 신규 알림·독촉 | **막는다** | 비활성 기능의 신규 업무 알림 중단 |

특히 “기간 마감”이 승인 업무 외에 인증·통제에도 쓰이는지 확인하기 전에는 전체 경로를 차단하면 안 됩니다.

`idleSqlBudget.test.js` 영향은 **미확인**입니다. 설계상 기능 OFF 판정을 각 작업의 SQL 호출 전에 수행해야 하며, 토글 확인을 위해 작업마다 SQL을 추가하면 유휴 비용이 증가할 수 있습니다. 기존 상태의 정합 작업이 남으므로 OFF의 기대 SQL 횟수를 무조건 0으로 정해서도 안 됩니다.

## UX 대안

**일반 첫 화면에 기능 선택을 두고, 각 묶음 머리에는 현재 상태와 변경 링크를 표시하는 조합을 권고합니다.**

| 방식 | 평가 |
|---|---|
| 기능 선택 페이지 | 두 기능과 운영 모드를 함께 설명하기 좋음 |
| 첫 설치 위저드 | 최초 설정에는 유용하지만 이후 변경 장소가 별도로 필요 |
| 각 묶음 머리의 토글 | 변경 위치는 가깝지만 전체 관계를 파악하기 어려움 |

위저드는 같은 설정 화면을 안내하는 선택적 도움말로 두는 편이 좋습니다.

관리자 화면에서는 **묶음 제목과 “사용 안 함” 표시를 남기고 상세 메뉴를 접는 방식**을 권고합니다. 다시 켜는 위치와 저장된 설정의 존재를 발견할 수 있어야 합니다. 업무함에서는 신규 작업 UI를 숨기되, 진행 중 요청과 과거 기록에 접근할 수 있어야 합니다.

운영 모드와는 “값 유지·접기·미확인 상태에서 숨기지 않기”를 일관되게 적용할 수 있습니다. 다만 관리자 복구 메뉴까지 같은 규칙으로 숨기면 안 됩니다.

## 라벨 15

**네 locale 파일을 읽지 못해 실제 라벨 상위 15개를 선정할 수 없습니다.** 존재 여부가 확인되지 않은 라벨을 만들어 목록을 채우지 않겠습니다.

요청에 직접 제시된 문구에 대해서만 제안하면:

- “전환 승인 강제(끄면 모든 validator가 통과)” → **“승인 없이 상태 변경 허용”** — 비상 해제 영역에 배치하고 적용 범위 설명.
- “이슈 상태 변경 승인을 사용합니다” → **“이슈 승인을 사용합니다”** — 필드 변경·일반 승인까지 포함할 경우.
- “타임시트 승인을 사용합니다” → **“월별 작업 시간 승인을 사용합니다”** — 실제 기간 단위 확인 필요.
- “타임시트 결재자는 워크포스에서 지정한 팀장이 합니다” → **“워크포스의 팀장 정보를 우선 사용합니다”** — 명부 팀장 대체 동작이 맞다는 전제.

## 비용·순서

파일 수는 소비처를 읽지 못해 신뢰할 만하게 추정할 수 없습니다.

**백엔드 최소안:** 정책 키·검증·단일 판정 함수, 신규 제출 차단, 승인 업무를 새로 만드는 배치 차단, 기존 요청·기록·복구 유지. UI만 숨기는 안으로 끝내면 서버 기능 OFF가 아닙니다.

**전체안:** 위 변경에 비활성화 전 영향 확인, 기존 요청 처리 정책, 워크포스 게시 정합, 재활성화 동작, 모든 진입점과 화면의 일관된 판정을 추가합니다.

권장 순서는 다음과 같습니다.

1. 승인·인증·통제·이력의 기능 경계와 프로젝트 범위 확정.
2. 끄기·다시 켜기·진행 중 요청 처리 계약 확정.
3. 정책 키와 서버 판정 구현.
4. resolver·배치·게시 경로 적용.
5. 관리자 기능 선택과 업무함 표시 적용.
6. 라벨 정리와 계약·유휴 SQL 검증.
7. 변경 시 저장소가 요구한 `check:bundle` 및 검증 순서 실행.

## 리더 제안에서 뒤집어야 할 것

제공된 설명 기준으로 다음은 수정하는 것이 좋습니다.

- **비상 해제 스위치의 기능 스위치 겸용:** 의미와 감사 사건을 분리합니다.
- **워크로그·타임시트 묶음 전체 숨김:** 인증·통제·복구·기록의 독립성을 먼저 확인합니다.
- **끄면 모든 결재 경로 차단:** 신규 제출 중단과 기존 요청 정리를 구분합니다.
- **워크포스 팀장이 결재한다는 단정:** 대체 결재자 동작을 문구에 반영합니다.
- **프로젝트 범위 진단 확정:** `isProjectEnabled` 직접·간접 소비처 전수 확인 전에는 보류합니다.

요청하신 **코드 대조, 행 번호 근거, 전수 목록, 실제 라벨 15개, 영향 파일 수**는 파일 읽기 실행 환경이 복구되어야 완료할 수 있습니다.
