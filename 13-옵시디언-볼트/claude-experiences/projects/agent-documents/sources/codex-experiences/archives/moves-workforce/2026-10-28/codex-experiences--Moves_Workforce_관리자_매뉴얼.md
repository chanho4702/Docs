## 1. 관리자 개요

이 매뉴얼의 대상은 **Settings(백오피스) 접근 권한을 가진 운영자/관리자**입니다.

관리자가 책임지는 영역:

- **초기 셋업**: 설치 후 권한·기준정보·전역 설정을 조직에 맞게 구성
- **사용자·조직 관리**: 워크포스 사용자 등록(단건/엑셀 대량), 팀·역할·등급·급여·권한 부여
- **기준정보 관리**: 팀(Team)·역할(Role)·등급(Level)·스킬(Skill)·프로젝트 상태(Status)·공휴일(Holiday)
- **전역 계산 기준값**: 1Day 근무 시간, 가동률 band, 통화, 급여 정책 — 모든 MD/MM/가동률/비용 계산의 기준
- **권한 설계**: 페이지별 읽기/쓰기 권한 묶음(Permission) 운영
- **자동화 모니터링**: DB 마이그레이션, 통합 대시보드 스냅샷 등 스케줄 동작 이해

> 관리자 화면 대부분은 좌측 **Settings**(`/backoffice/*`) 메뉴 아래에 있으며, 각 항목은 해당 페이지의 **쓰기 권한**이 있어야 편집됩니다(읽기만 있으면 조회 전용).

## 2. 설치 및 초기화

### 2.0 시작하기 전에 — 필요한 Jira 계정 권한

앱의 권한 묶음(Permission)을 설정하기 **전에**, Jira 쪽에서 갖춰야 할 조건이 따로 있습니다. 여기가 어긋나면 "앱은 설치됐는데 아무도 관리자로 들어가지 못하는" 상태가 됩니다.

#### 역할별 요건 한눈에

| 역할 | Jira에서 필요한 것 | 왜 필요한가 |
|---|---|---|
| **앱 설치자** | Jira **사이트 관리자**(Administer Jira 전역 권한) 또는 조직 관리자 | Marketplace에서 Forge 앱을 설치하고 앱 권한(scope)에 동의하려면 필요합니다 |
| **최초 관리자(첫 진입자)** | Jira **전역 관리 권한(`ADMINISTER`)** | 앱은 이 권한만으로 **전권 Admin**을 부여합니다. 앱에 사용자로 등록돼 있지 않아도 됩니다 (아래 설명) |
| **일반 사용자** | Jira **제품 라이선스**(Jira 사용자 계정) + 대상 프로젝트의 **Browse Projects** | 라이선스가 없으면 앱 화면 자체에 접근할 수 없고, 프로젝트 열람 권한이 없으면 이슈가 비어 보입니다 |
| **워크로그 작성자** | 대상 프로젝트의 **Work On Issues(작업 기록)** | 워크로그 등록이 Jira에 기록됩니다 |
| **작업 편집자** | **Edit Issues / Schedule Issues / Assign Issues / Link Issues** | 트리·간트·목록의 편집이 각각 이 권한으로 최종 판정됩니다 |

#### 최초 접근은 이렇게 열립니다 (중요)

앱에는 "최초 관리자"를 지정하는 설정이 **없습니다.** 대신 서버가 매 요청마다 다음 순서로 판정합니다.

```
① Jira 전역 관리 권한(ADMINISTER) 보유?
      └ 예 → 전권 Admin (모든 권한 키 읽기·쓰기, 프로젝트 범위 ALL)
              ※ 앱의 인력 목록에 등록돼 있지 않아도 통과합니다
      └ 아니오 ↓
② 앱의 인력(users)으로 등록돼 있는가?
      └ 아니오 → 모든 권한 false (화면은 열리지만 아무 데이터도 보이지 않음)
      └ 예 ↓
③ 개인 권한 세트 → 없으면 소속 팀(상위 팀) 권한 세트 상속
      └ 어느 쪽도 없으면 모든 권한 false
```

여기서 나오는 실무적 결론:

- **설치 직후 앱에 처음 들어가야 하는 사람은 반드시 Jira 전역 관리 권한 보유자여야 합니다.** 그 사람이 [4장 사용자 관리](#4-사용자-관리)에서 다른 운영자를 등록하고 `Admin` 권한 묶음을 부여해야 비로소 일반 계정으로도 관리가 가능해집니다.
- Jira 관리자는 **앱 권한 설정과 무관하게 항상 전권**입니다. 권한 묶음으로 Jira 관리자를 제한할 수 없습니다.
- Jira 관리자는 **프로젝트 조회 범위도 항상 `ALL`** 입니다. `MEMBER_ONLY` / `TEAM_ONLY`를 부여해도 적용되지 않습니다.
- 반대로 **앱에 등록되지 않은 일반 사용자는 fail-close**입니다. 화면에는 들어와지지만 메뉴·데이터가 전부 비어 보입니다. "설치했는데 아무것도 안 보인다"는 문의의 대부분이 이 경우입니다.
- 권한 판정 결과는 약 30초 캐시됩니다. 권한을 바꾼 직후에는 잠시 기다렸다가 새로고침하세요(팀 관련 변경은 최대 약 90초).

#### 설치 시 승인하는 앱 권한(scope)

Forge 앱 설치 화면에서 사이트 관리자가 아래 권한에 동의해야 설치가 완료됩니다.

| scope | 앱에서 쓰는 곳 |
|---|---|
| `read:jira-user` | 사용자 검색·아바타·담당자/협업자 표시 |
| `read:jira-work` | 이슈·워크로그·프로젝트 조회, JQL 검색, 분석 리포트 |
| `write:jira-work` | 워크로그 작성, 이슈 일정·담당자·연결·시간 추적 수정 |
| `manage:jira-configuration` | 앱 전용 커스텀 필드와 이슈 엔티티 프로퍼티(`movesRms`) 관리 |
| `write:app-data:jira` | 앱이 이슈에 저장하는 데이터(협업자·상위 지정 등) |
| `storage:app` | 앱 저장소(Forge SQL / KVS) — 프로젝트·인력·권한·기준정보 |

> **업그레이드로 scope가 추가되면 사이트 관리자의 재승인이 필요합니다.** 승인 전까지 새 기능이 동작하지 않을 수 있으니, 배포 후 Jira 관리 화면에서 앱 상태를 확인하세요.

#### 사용자 동작은 "그 사용자의 Jira 권한"으로 실행됩니다

앱은 대부분의 Jira 호출을 **사용자 컨텍스트(asUser)** 로 실행합니다. 따라서 앱에서 쓰기 권한을 줘도 **Jira 권한이 없으면 저장이 거부**됩니다.

| 앱에서 하는 일 | 필요한 Jira 프로젝트 권한 |
|---|---|
| 이슈 목록·분석·간트 조회 | Browse Projects |
| 워크로그 작성 | Work On Issues |
| 내 워크로그 수정·삭제 | Edit Own Worklogs / Delete Own Worklogs |
| 시작일·기한 변경(막대 드래그 포함) | Edit Issues + Schedule Issues |
| 담당자 지정·작업 배정 | Assign Issues |
| 선후행 연결 | Link Issues |
| 계획 작업량(MD) 입력 | Edit Issues **+ 해당 프로젝트의 시간 추적(Time Tracking) 활성화** |

- 앱은 저장 전에 이 권한들을 확인하고, **확정 거부(false)** 인 경우에만 차단합니다. 판정 불가(응답 실패 등)는 통과시키고 Jira의 최종 응답에 맡깁니다.
- 시간 추적이 꺼진 프로젝트에서는 계획 작업량 저장이 Jira 400으로 실패하며, 화면에 "시간 추적 비활성화" 안내가 표시됩니다.

#### 초기 접근 체크리스트

1. **사이트 관리자**가 앱을 설치하고 scope에 동의했다.
2. 그 관리자(또는 다른 Jira 전역 관리 권한 보유자)가 앱 글로벌 페이지에 접속해 **Settings 메뉴가 보이는지** 확인했다.
   - 보이지 않는다면 그 계정에 Jira 전역 관리 권한이 없는 것입니다.
3. [4장 사용자 관리](#4-사용자-관리)에서 **운영자 계정을 등록**하고 `Admin` 권한 묶음을 부여했다.
4. 운영자 계정으로 로그인해 Settings 접근을 확인했다(권한 변경 후 30초 대기).
5. 일반 사용자들이 **Jira 제품 라이선스**를 갖고 있고, 대상 프로젝트의 Browse Projects 권한이 있다.
6. 워크로그를 쓸 사용자에게 **Work On Issues** 권한이 있다.

> 앱 **라이선스**가 만료(INACTIVE)되면 권한과 무관하게 기능이 차단되고 안내 화면이 표시됩니다. 라이선스 판정을 할 수 없는 일시 장애 상황에서는 앱이 차단하지 않고 통과시킵니다.

### 2.1 자동 초기화(시드)

앱 설치/업그레이드 시 **설치 트리거**(`src/trigger/onInstall.js`)가 자동으로 다음을 수행합니다.

1. **DB 마이그레이션 실행** — 스키마를 최신으로 보장(멱등)
2. **시드 버전 확인** — KVS에 저장된 `seed_version`을 현재 `SEED_VERSION`과 비교
3. 저장된 버전이 현재보다 낮을 때만 **기본 데이터 시드** 실행 후 버전 기록 (이미 최신이면 건너뜀 → 재설치/업그레이드 시 기존 데이터 보존)

> 시드는 **멱등(idempotent)** 하게 설계되어 있어, 업그레이드로 다시 실행돼도 **기존에 등록한 설정·기준정보·커스텀 권한은 안전하게 유지됩니다.** 권한 영역은 업그레이드 시 다음이 자동 수행됩니다:
> - 시스템 권한 **Admin/Member**는 최신 권한 키 목록 기준으로 재생성됩니다(단, Member에 설정한 **프로젝트 조회 범위**는 보존).
> - **커스텀 권한 묶음**에는 새 버전에서 추가된 권한 키가 기본값으로 자동 병합되고, 폐기된 키는 정리됩니다. 관리자가 설정한 기존 읽기/쓰기 값은 바뀌지 않습니다.

### 2.2 설치 시 생성되는 기본 데이터

| 영역 | 기본 시드 내용 |
|---|---|
| **권한(Permission)** | `Admin`(전 권한 키 읽기·쓰기), `Member`(조회 위주) — 두 묶음 모두 **시스템 권한**(페이지 권한 수정 불가, 프로젝트 조회 범위만 설정 가능. 아래 3장 참조) |
| **프로젝트 상태** | `To Do` → `IN PROGRESS` → `DONE` (3단계, 색상·순서 지정) |
| **상태 전이(흐름)** | `To Do → IN PROGRESS`, `IN PROGRESS → DONE` |
| **일반 설정** | 통화 `KRW`, 1Day 근무 시간(Jira Time Tracking 설정 기반, 조회 실패 시 8h), 가동률 band(0.7 / 1.1 / 1.3), 진척 임계값 5%p, 급여 정책 `INDIVIDUAL` |
| **권한 묶음 프리셋** | PM / PMO / Team Lead / Team Member. `permission` 엔티티에 최초 1회만 생성되며 이후 관리자의 수정·삭제를 시드가 되돌리지 않음 |

> **팀·역할·등급·스킬은 조직에 맞게 등록해야 합니다.** 역할·등급은 빠른 추가 프리셋을 활용할 수 있습니다(5장 참조).

### 2.3 DB 마이그레이션

- 스키마/마이그레이션 정의: `src/rdb/schema/migrate.js`(`runMigration`)
- 대상은 Forge SQL 13개 테이블입니다: `project`, `users`, `projectusers`, `user_schedule`, `project_dashboard`, `portfolio_project_snapshot`, 간트 3종, 스킬 매핑 2종, `project_team`, `project_subscription`.
  - v015는 포트폴리오 스냅샷의 집계 당시 급여정책을, v016은 스페이스/보드 구독 규칙을, v017은 구독 기본 예상 시간(`default_estimate_seconds`)을, v018은 프로젝트 대시보드 위젯 필터(`filter_json`)를, v019는 포트폴리오 스냅샷의 스페이스별 이슈 상태 롤업(`spaces_json`)을 추가합니다.
- 실행 시점:
  - **설치/업그레이드**(onInstall)에서 1회
  - **시간 단위 스케줄 트리거**(`init-db`)로도 주기 실행 → 이중 보험
- 마이그레이션은 멱등하며, 실패 시 오류가 기록되고 설치가 실패할 수 있습니다. 설치 직후 화면에 데이터가 비정상이라면 마이그레이션/시드 로그를 먼저 확인하세요.

### 2.4 설치 직후 권장 셋업 순서

0. **Jira 전역 관리 권한 보유자**로 앱에 접속해 Settings가 열리는지 확인하고, 운영자 계정을 인력으로 등록해 `Admin` 권한을 부여 ([2.0](#20-시작하기-전에--필요한-jira-계정-권한))
1. **일반 설정**에서 통화·1Day 근무 시간·급여 정책 확인/조정 (모든 계산의 기준)
2. **공휴일** 등록 (근무일·가동률·진척도 분모에 직접 영향)
3. **팀·역할·등급·스킬** 기준정보 구성. 등급 기반 정책이면 모든 사용 등급의 급여 밴드 입력
4. **프로젝트 상태/전이**를 조직 워크플로에 맞게 조정
5. **사용자 등록** 후 팀·역할·등급·권한 부여. 인원별 정책이면 개인 연봉 입력
6. 시드 프리셋과 **커스텀 권한 묶음**의 projectScope·민감정보 권한을 검토

## 3. 권한(Permission) 관리

`/backoffice/permission` — `PERMISSION_MANAGEMENT` 권한 필요.

### 3.1 권한 모델

- 권한은 **기능 영역(권한 키)별 읽기(read)/쓰기(write)** 조합인 **권한 묶음(Permission)** 단위로 관리합니다.
- 사용자에게는 권한 묶음을 부여합니다(사용자 관리에서 지정, 미지정 시 기본 **Member**).
- **읽기** = 화면/탭 조회, **쓰기** = 추가·수정·삭제. 읽기만 있으면 조회는 되지만 편집 버튼이 보이지 않습니다.
- **서버 검증:** 권한은 화면 노출 제어에 그치지 않고 **모든 요청이 서버에서 검증**됩니다. 화면을 우회해 API를 직접 호출해도 권한 밖 작업은 거부되며("이 작업을 수행할 권한이 없습니다"), 권한 정의가 없는 신규 기능은 **기본 거부(deny-by-default)** 됩니다.
- **Jira 관리자 예외:** Jira 사이트 관리(ADMINISTER) 권한 보유자는 항상 Admin과 동일한 전체 권한을 갖습니다(권한 설정 실수로 인한 앱 잠금 방지).
- 권한 키는 페이지와 1:1이 아니라 **권한 경계 단위**로 묶여 있습니다(민감도·대상 사용자군·쓰기 의미가 다를 때만 키를 분리). 권한 관리 화면의 각 항목에는 **그 권한이 어떤 페이지/탭/기능을 제어하는지 설명**이 함께 표시됩니다.

### 3.3 시스템 권한(edit:false) vs 커스텀 권한

- 시드된 **Admin / Member**는 **시스템 권한**으로, 이름과 페이지별 읽기/쓰기 설정의 **편집·삭제가 잠겨(`edit:false`)** 있습니다. 조직 표준을 보호하기 위함입니다.
  - **예외:** 시스템 권한도 **프로젝트 조회 범위(3.4)** 는 설정할 수 있습니다(단, Admin은 항상 "전체"로 고정).
- 조직별로 다른 접근 범위가 필요하면 **새 권한 묶음을 추가**(커스텀)하여 권한 키별 읽기/쓰기와 조회 범위를 자유롭게 설정하고, 사용자에게 부여하세요. 커스텀 권한은 수정·삭제할 수 있습니다(단, 사용 중인 사용자가 있으면 삭제 불가).

### 3.4 프로젝트 조회 범위 (Project Scope)

권한 묶음마다 **프로젝트 데이터의 조회 범위**를 설정할 수 있습니다.

| 값 | 의미 |
|---|---|
| **전체 (ALL)** — 기본값 | 모든 프로젝트 정보를 조회할 수 있습니다 (기존 동작) |
| **소속 프로젝트만 (MEMBER_ONLY)** | **본인이 인력으로 등록된 프로젝트만** 조회할 수 있습니다 |
| **내 팀 프로젝트 (TEAM_ONLY)** | 아래의 scope team 소속 인원이 참여한 프로젝트와 scope team이 `project_team` 담당 팀인 프로젝트의 합집합 |

**범위를 제한하면:**

- 프로젝트 목록·칸반·상세·전사 대시보드는 해당 범위로 축소됩니다. 범위 밖 상세 주소로 직접 접근해도 서버가 거부합니다.
- `MEMBER_ONLY`의 소속 기준은 프로젝트 인력 명단입니다. 이슈 담당자여도 인력으로 등록되지 않았다면 비소속입니다.
- `TEAM_ONLY`의 **scope team**은 `(내 소속 팀 + 그 하위 팀) ∪ (내가 팀장인 모든 팀 + 각 하위 팀)`입니다. 이 팀 소속 인원의 프로젝트 참여와 이 팀들의 담당 팀 배정을 모두 사용합니다. 유효한 소속 팀도 리딩 팀도 없으면 0건으로 fail-close됩니다.

**적용 규칙:**

- **Jira 관리자(ADMINISTER)와 Admin 권한 묶음은 항상 "전체"** 입니다 (변경 불가).
- Member 등 시스템 권한도 이 항목만은 관리자가 켜고 끌 수 있습니다.
- 업그레이드/설치 시 기존 권한 묶음에는 "전체"가 기본 적용되어 **기존 동작이 바뀌지 않습니다.** 필요할 때 의도적으로 켜세요.
- 일반 권한 변경은 저장 후 **약 30초 이내** 반영됩니다. 팀 이동·팀장·팀 권한 상속 변경은 60초 팀 인덱스 캐시와 30초 principal 캐시가 연속으로 남을 수 있어 **최대 약 90초** 후 재확인하세요.

> **활용 예:** 내부 운영자(전체) / 외주·협력사(소속 프로젝트만) / 팀장·팀원(내 팀 프로젝트) 권한을 분리할 수 있습니다.

### 3.5 권한 묶음 프리셋과 팀장 권한

설치/업그레이드 시 PM·PMO·Team Lead·Team Member 프리셋을 **최초 한 번만** 제공합니다.

| 프리셋 | 범위 | 기본 성격 |
|---|---|---|
| PM | ALL | Workforce 읽기·쓰기, 비용 포함, Settings 없음 |
| PMO | ALL | Workforce 읽기 전용, 비용 포함, Settings 없음 |
| Team Lead | TEAM_ONLY | Workforce 읽기 전용, 비용 제외 |
| Team Member | TEAM_ONLY | 일반 Workforce 읽기 전용, 비용·자원관리 제외 |

프리셋은 `permission` 엔티티의 `edit:true` 권한 묶음 출발점이므로 조직이 수정할 수 있고, 삭제해도 다음 시드에서 되살리지 않습니다. **Team Lead 프리셋을 사용자에게 부여하는 것만으로 실제 팀장이 되지는 않습니다.** 실제 팀장 여부는 `team.leaderAccountId` 관계에서 파생됩니다. 팀장은 마이페이지에서 자신이 이끄는 팀의 업무 분석과 허용된 필드(예: 팀원 스킬)를 관리하며, 재무·계정·팀 구조 관리 권한을 자동으로 얻지는 않습니다.

## 4. 사용자 관리

`/backoffice/users` — `USER_MANAGEMENT` 권한 필요.

상단에 **Permission / Role / Level 별 인원 통계** 카드가 표시됩니다.

### 4.1 단건 추가

**+ 사용자 추가** 모달에서 등록합니다.

| 항목 | 필수 | 설명 |
|---|:---:|---|
| Jira 사용자 | ✅ | 이름/이메일로 Jira 사용자 검색·선택 |
| 역할(Role) | | 역할 관리에서 정의한 값 |
| 등급(Level) | | 등급 관리에서 정의한 값 |
| 팀(Team) | | 사용자의 단일 현재 소속 팀 |
| 권한(Permission) | | 미지정 시 기본 **Member** |
| 급여(Salary) | | `INDIVIDUAL` 정책에서만 입력·응답. 등급 기반에서는 숨김 |

행에서 기존 사용자의 역할·등급·팀·권한을 수정할 수 있습니다. 개인 급여는 `INDIVIDUAL` 정책일 때만 수정할 수 있습니다. `LEVEL_BAND`에서는 저장값을 삭제하지 않지만 화면과 API 응답에서 개인 금액을 제거합니다.

### 4.2 엑셀 대량 업로드

다수 사용자를 한 번에 등록할 때 사용합니다. **큐 기반 비동기 처리**로, 업로드 후 진행률이 폴링됩니다.

**입력 파일 형식**
- `.xlsx` 엑셀 파일
- **1행은 헤더**, 2행부터 데이터
- **`Email` 컬럼 필수** — 각 행의 이메일로 Jira 사용자를 조회해 등록합니다.
- 이메일은 형식 검증(`user@domain.tld`)을 거치며, 형식이 틀리거나 Jira에서 찾을 수 없는 이메일은 **실패 항목**으로 분류됩니다.

**처리 방식**
- 이메일 목록을 **약 20개 단위 배치**로 나눠 큐에 넣고, **동시 워커 3개**로 처리합니다(대량 업로드 시 rate limit 보호).
- 처리 결과는 **완료 / 부분 완료**로 구분됩니다.
- Jira API 호출이 일시적 오류(429/timeout 등)를 만나면 자동 재시도합니다.

**실패 항목 확인**
- 실패가 있으면 **실패 목록** 버튼이 노출됩니다. 실패한 이메일과 사유를 확인한 뒤, 해당 사용자만 보정해 다시 업로드하면 됩니다.

> **운영 팁:** 대량 업로드는 사용자를 **등록**만 합니다. 팀·역할·등급·권한·급여 등 세부 정보는 업로드 후 사용자 관리 화면에서 보정하세요.

## 5. 기준정보 관리

### 5.1 팀(Team) 관리 (`/backoffice/team`)

현재 조직 구조와 팀장을 정의합니다.

- 필드: 팀명, 상위 팀, 팀장, 팀 권한 세트, 설명, 정렬 순서
- 사용자는 `users.team_key`로 한 팀에 소속됩니다. 하위 팀은 임의 깊이가 아니라 최대 깊이 10, 최대 팀 500개 한도 내에서 관리합니다.
- 쓰기 권한이 있으면 트리에서 팀을 드래그해 다른 팀 아래 또는 최상위로 옮길 수 있습니다. 자기 자신·자기 하위로 이동하거나 깊이 한도를 넘는 이동은 차단됩니다.
- 팀 권한 세트는 가장 가까운 상위 팀 설정을 상속할 수 있지만, 사용자 권한 세트와 팀장 관계가 맡는 역할을 혼동하지 마세요.

### 5.2 역할(Role) 관리 (`/backoffice/role`)

프로젝트 인력의 **직무**를 정의합니다.

- 폼: **이름(필수)**, 설명(선택)
- **+ 역할 추가**(개별) 또는 **빠른 추가**(프리셋 일괄 등록)
- 제공 프리셋: **IT / Finance / Manufacturing / Marketing / 공통(Common)** 도메인별 직무 묶음(예: Backend Developer, Financial Analyst, Production Engineer, Product Manager, Project Manager 등)

### 5.3 등급(Level) 관리 (`/backoffice/level`)

인력의 **레벨**을 정의합니다.

- 폼: **이름(필수)**, 설명(선택), 급여 하한·상한·대표값(선택)
- **+ 등급 추가**(개별) 또는 **빠른 추가**(프리셋)
- 제공 프리셋: **일반(Junior~Fellow), 등급체계(G1~G5), 한국 직급(사원~임원), Band(1~5)**

`LEVEL_BAND` 정책에서는 대표값을 연봉 원천으로 사용합니다. 대표값을 비우고 하한·상한을 모두 입력하면 중앙값을 자동 사용합니다. 음수와 `하한 > 상한`은 저장할 수 없고, 대표값이 범위를 벗어나면 경고 후 저장은 허용합니다. 사용자 등급이 없거나 그 등급에서 대표값·중앙값을 결정할 수 없으면 해당 인원의 인건비가 0이 됩니다.

### 5.4 스킬(Skill) 관리 (`/backoffice/skill`)

자원관리의 인력 적합도에 쓰는 스킬 사전을 정의합니다. 스킬명·카테고리·설명을 관리하고, 사용자 보유 스킬과 프로젝트 요구 스킬은 자원관리·프로젝트 화면에서 매핑합니다.

### 5.5 프로젝트 상태(Status) 관리 (`/backoffice/project-status`)

프로젝트의 **상태(칸반 컬럼)** 와 **상태 전이 흐름**을 정의합니다.

- 폼: **상태명(필수)**, **색상(필수)**
- **연결 편집(Pipeline)** — 상태 간 전이를 시각적 다이어그램으로 편집
  - **순환(루프) 금지**: 상태가 자기 자신으로 되돌아오는 흐름은 만들 수 없습니다.
  - **단일 경로 강제**: 한 상태에서 나가는 전이, 한 상태로 들어오는 전이는 각각 1개만 허용됩니다(직선형 파이프라인).
- 기본 시드: `To Do → IN PROGRESS → DONE`

> 칸반 보드의 컬럼·드래그 가능한 이동 경로는 여기서 정의한 상태·전이를 따릅니다.

### 5.6 공휴일(Public Holiday) 관리 (`/backoffice/public-holiday`)

근무일·MM·가동률·진척도 계산의 **휴일 기준**을 관리합니다.

- 폼: **공휴일명(필수)**, **날짜(필수)**, 근무 비율(`workRatio`, 기본 0)
  - `workRatio = 0` → 완전 휴무, `0.5` → 반일 근무 등으로 부분 근무일도 표현 가능
- 상단에 **월별 MM 요약**(근무일 기준)이 표시됩니다.

> **중요:** 여기 등록된 휴일은 **목표 시간·가동률·진척도의 "근무일 분모"에서 제외**됩니다. 공휴일을 정확히 등록하지 않으면 가동률이 낮게(분모 과대), 진척도 일정률이 왜곡될 수 있으니 **연초/분기 초에 갱신**하는 것을 권장합니다.

## 6. 일반 설정 (`/backoffice/setting`)

`SETTINGS` 권한 필요. **모든 MD/MM/가동률/비용/목표 시간 계산의 전역 기준값**입니다.

| 항목 | 기본값 | 범위/형식 | 영향 |
|---|---|---|---|
| **통화 단위** | KRW | KRW / USD / JPY / EUR / GBP | 비용·급여·인건비 표시 통화 |
| **1Day 근무 시간** (`1MD`) | 8h | 0.5~24h, 0.5 단위 | MD/MM 환산, My Work 목표 시간, 가동률·진척도 공수 환산 |
| **가동률 — 과소 경계** | 0.7 | 0~2 | 이 값 **미만**은 '과소(저활용)' 분류 |
| **가동률 — 과부하 경계** | 1.1 | 0~3 | 이 값 **이상**은 '과부하' 분류 |
| **가동률 — 심한 과부하 경계** | 1.3 | 0~5 | 이 값 **이상**이면 신호등 적색(위험) |
| **진척도 임계값** | 5 | 0~100 %p | 완성률−일정률의 정상/주의/지연 판정 |
| **범위 경계** | 0.3 / 0.6 | 비율 | 잔여 이슈 비중 기반 T/S/R의 S축 판정 |
| **급여 정책** | INDIVIDUAL | `INDIVIDUAL` / `LEVEL_BAND` | 개인 금액 또는 등급 대표값을 인건비 원천으로 선택 |

> **가동률 band** 는 통합 대시보드의 **가동률 분포 차트**와 **종합 개요 신호등(자원 축)** 색상 판정에 함께 쓰입니다. 가동률 1.0 = 100%(기준 가동).

> **주의:** **1Day 근무 시간**을 바꾸면 과거를 포함한 모든 MD/MM 환산과 목표 시간이 함께 재계산됩니다. 운영 중 변경은 분석 수치 비교에 혼선을 줄 수 있으므로 신중히 결정하세요.

### 6.1 급여 정책 전환 절차

1. 비용 산정 대상 전원에게 유효한 등급이 지정됐는지 확인하고, 사용 중인 모든 등급에 대표값을 입력하거나 하한·상한을 모두 입력합니다.
2. 일반 설정의 급여 정책 카드에서 대상을 선택하고 전환 확인 문구를 검토합니다.
3. 프로젝트 급여 화면에서 **미산정 인원 0명**인지 확인합니다. 프로젝트 비용은 최대 10분 캐시 후, 통합 대시보드는 다음 배치 또는 수동 재집계 후 새 정책으로 맞춰집니다.

`LEVEL_BAND`로 전환하면 기존 개인 연봉·투입 급여는 즉시 화면과 API 응답에서 숨겨지지만 저장값은 유지됩니다. `INDIVIDUAL`로 되돌리면 기존 값이 다시 사용됩니다. 다만 등급 기반 운영 중 신규 등록된 사용자는 개인 연봉이 `null`일 수 있으므로, 개인 연봉과 프로젝트 인력별 투입 급여·`salaryType`을 함께 점검하세요. 정책이 다른 시점에 생성된 포트폴리오 스냅샷은 재집계 전까지 비용 축이 마스킹됩니다.

## 7. 자동화 · 스케줄 · 커스텀 필드

관리자가 알아두면 좋은 백그라운드 동작입니다(`manifest.yml` 정의).

### 7.1 스케줄 트리거

| 트리거 | 주기 | 동작 |
|---|---|---|
| `init-db` | 매시간 | DB 마이그레이션 재확인(멱등) — 스키마 안전망 |
| `portfolio-snapshot` | 매일 | 통합 대시보드용 전사 스냅샷 집계 |
| `subscription-reconcile` | 매시간 | 프로젝트 구독 소스를 오래된 순서로 스윕해 이벤트 유실·보드 조건·이슈 이동 보완 |

> 통합 대시보드의 **기준 시각**은 이 일일 스냅샷 기준입니다. 즉시 최신화가 필요하면 대시보드 상단 **지금 재집계** 버튼을 사용하세요. 큐 등록만으로 완료 처리하지 않고 기준 시각 변경을 15초 간격으로 확인해 완료 시 자동 갱신하며, 대기는 최대 10분입니다.

### 7.2 이벤트·큐 자동화

- `avi:jira:created:issue` 이벤트는 구독한 **스페이스**의 새 이슈를 빠르게 편입합니다. 보드·추가 JQL처럼 생성 이벤트에서 확정할 수 없는 조건은 시간별 리컨실에 맡깁니다.
- 기존 이슈 백필은 `subscription-backfill-queue`로 처리합니다. 백필 자체의 안전 상한은 5,000건이지만 공용 scanner가 1회 2,000건에서 먼저 중단하므로, **현재 생성 요청에서 즉시 고정·큐잉되는 최대치는 2,000건**입니다. 상한·시간/요청 예산을 넘은 나머지는 후속 리컨실 대상입니다.
- 이벤트 경로는 실패를 throw하지 않아 재시도 폭주를 막고, 정확성의 최종 원천은 리컨실입니다.

### 7.3 Jira 커스텀 필드·이슈 프로퍼티

앱은 여섯 개의 Jira 커스텀 필드를 사용합니다.

| 필드 | 용도 |
|---|---|
| `moves_RMS_projectId` (문자열, 읽기전용) | 이슈를 Moves 프로젝트에 편입할 때 설정. 작업 관리의 "작업 추가"가 이 값을 세팅 |
| `moves_RMS_coworkers` (사용자 목록) | 이슈의 **동료(협업자)** — 담당자와 별개로 여러 명 지정. My Work의 협업 이슈 집계 근거 |
| `moves_RMS_projectAssignedDate` | 프로젝트 편입 시각 |
| `moves_RMS_projectAssignedById` | 편입 실행 사용자 accountId |
| `moves_RMS_wbsParent` | Workforce WBS 상위 이슈 키 |
| `moves_RMS_predecessors` | 일정 선후행 JSON |

팀 관리형 프로젝트 호환을 위해 issue entity property `movesRms`에도 coworkers·assignedAt·assignedById·wbsParent를 read-merge-write합니다. 이 필드와 프로퍼티는 앱이 관리하므로 수동 수정하지 마세요.

### 7.4 프로젝트 구독 운영

- 구독 목록·미리보기는 `PROJECT` read, 생성·수정·해제·**지금 동기화**는 `PROJECT` write가 필요합니다.
- 한 소스는 전체 RMS에서 한 프로젝트만 구독할 수 있고 프로젝트당 최대 10개입니다.
- 구독 생성자는 해당 스페이스/보드에 실제 접근 가능한지 `asUser` 검증을 통과해야 합니다.
- 추가 JQL은 최대 1,000자이며 `ORDER BY`, `currentUser()` 같은 사용자 의존 함수는 허용하지 않습니다.
- 구독 해제는 앞으로의 자동 편입만 멈추며 이미 편입된 이슈를 되돌리지 않습니다.
- 보드 API가 현 scope에서 거부되면 `AGILE_UNAVAILABLE`로 표시됩니다. granular Agile scope를 추가하려면 앱 전역 scope 전환과 재동의 영향을 별도 검토해야 합니다.

| 동기화 상태 | 의미와 대응 |
|---|---|
| `PARTIAL` | 실행 예산 또는 2,000건 상한으로 일부만 처리. 다음 주기에 cursor로 재개하지만 현재 후보 집합 축소에 따른 누락 위험이 있으므로, 반복되는 대규모 구독은 운영 완료로 간주하지 말고 Forge 로그와 표본 이슈를 대조 |
| `SOURCE_FORBIDDEN` | 앱 또는 사용자에게 소스 접근권한이 없음. 소스 권한과 앱 접근 범위를 수정한 뒤 지금 동기화 |
| `AGILE_UNAVAILABLE` | Jira Software/Agile API·보드 설정 또는 현 scope에서 보드 JQL을 읽을 수 없음. 사이트·scope·보드 필터 확인 |
| `ERROR` | JQL, rate limit, 일시적 Jira API 오류 등. `last_error`와 Forge 로그를 확인하고 원인 제거 후 재시도 |

### 7.5 앱 권한 범위(scopes)

설치 시 사이트 관리자가 동의하는 Jira 권한입니다. 각 scope의 용도와 재승인 조건은 [2.0 설치 시 승인하는 앱 권한(scope)](#설치-시-승인하는-앱-권한scope)에 정리돼 있습니다.

| scope | 용도 |
|---|---|
| `read:jira-user` · `read:jira-work` | 사용자·이슈·워크로그·프로젝트 조회 |
| `write:jira-work` · `write:app-data:jira` | 워크로그 작성, 이슈 일정·담당자·연결 수정, 앱 저장 데이터 |
| `manage:jira-configuration` | 앱 커스텀 필드·이슈 엔티티 프로퍼티 관리 |
| `storage:app` | Forge SQL / KVS 앱 저장소 |

- 앱은 Jira 호출을 원칙적으로 **사용자 컨텍스트(asUser)** 로 실행합니다. 앱 권한이 넓어도 **개별 사용자의 Jira 권한을 넘어서 동작하지 않습니다.**
- 예외적으로 앱 컨텍스트(asApp)를 쓰는 곳은 이슈 엔티티 프로퍼티(`movesRms` — 협업자·상위 지정) 읽기/쓰기입니다. 프로퍼티 write 권한이 앱 컨텍스트에서만 동작하기 때문입니다.
- 보안 검토 시 `manifest.yml`의 `permissions.scopes`를 원본으로 확인하세요.
- 보드 구독은 현재 classic scope 세트를 쓰므로 Agile API 접근이 사이트 설정에 따라 실패할 수 있습니다(`AGILE_UNAVAILABLE`). 스페이스 구독은 영향받지 않습니다.

## 8. 운영 점검 & 트러블슈팅

### 8.1 초기 접근·Jira 권한 문제

| 증상 | 원인과 대응 |
|---|---|
| 설치 후 **누구도 Settings에 못 들어감** | 접속한 계정에 **Jira 전역 관리 권한(ADMINISTER)** 이 없습니다. 사이트 관리자 계정으로 먼저 진입해 운영자를 등록하세요 ([2.0](#20-시작하기-전에--필요한-jira-계정-권한)) |
| 로그인은 되는데 **모든 화면이 비어 있음** | 앱 인력(users)으로 등록되지 않은 계정입니다(fail-close). [4장](#4-사용자-관리)에서 등록 후 권한 묶음을 부여하세요 |
| 권한을 줬는데 **여전히 안 보임** | 판정 캐시(약 30초, 팀 관련 최대 약 90초) 대기 후 새로고침. 개인 권한이 비어 있으면 팀 권한을 상속하므로 소속 팀의 세트도 확인 |
| Jira 관리자에게 **범위 제한이 안 걸림** | 정상입니다. Jira 관리자는 항상 전권이며 프로젝트 범위도 `ALL`로 고정됩니다 |
| 앱 화면 자체에 **접근 불가** | Jira **제품 라이선스**가 없는 계정입니다(비라이선스/고객 포털 계정 등) |
| 이슈 목록이 **비어 보임** | 그 사용자에게 대상 프로젝트의 **Browse Projects** 권한이 없습니다 |
| 워크로그 저장 실패 | **Work On Issues** 권한 확인. 본인 워크로그 수정·삭제는 Edit/Delete Own Worklogs |
| 일정 드래그·담당자 지정·연결 실패 | 각각 **Schedule/Edit Issues · Assign Issues · Link Issues** 확인. 앱 쓰기 권한이 있어도 Jira에서 거부되면 저장되지 않습니다 |
| 계획 작업량(MD) 저장 실패 | 해당 Jira 프로젝트의 **시간 추적(Time Tracking) 비활성화**가 대부분의 원인입니다 |
| 업그레이드 후 새 기능이 동작 안 함 | scope가 추가된 배포라면 **사이트 관리자의 재승인**이 필요합니다 |
| 앱 전체가 안내 화면으로 막힘 | 앱 **라이선스 만료(INACTIVE)**. 라이선스 갱신 후 재확인 |

### 8.2 데이터·설정 문제

| 증상 | 점검 포인트 |
|---|---|
| 가동률이 비정상적으로 낮음/높음 | **공휴일** 등록 누락, **1Day 근무 시간** 설정 확인 |
| 목표 시간(My Work)이 이상함 | 1Day 근무 시간 + 공휴일/주말 근무일 계산 기준 확인 |
| 진척도 계산 안 됨 | 이슈에 **계획 작업량(Original Estimate)** 입력 여부 확인 |
| 엑셀 업로드 일부 실패 | **실패 목록** 확인 — 이메일 형식 오류 또는 Jira 미등록 사용자 |
| 특정 사용자가 백오피스 접근 불가 | 부여된 **권한 묶음**의 해당 권한 키 읽기/쓰기 설정 확인 |
| "이 작업을 수행할 권한이 없습니다" 오류 | 서버 권한 검증 거부 — 권한 묶음의 해당 키 **쓰기** 여부 확인. 권한 변경 직후라면 캐시 반영(~30초) 대기 |
| 특정 사용자에게 프로젝트가 일부만 보임 | `MEMBER_ONLY`면 프로젝트 인력 등록, `TEAM_ONLY`면 소속/리딩 팀 계층·팀원 참여·담당 팀 배정을 확인 |
| 공휴일 권한이 있는데 메뉴가 안 보임 | 현재 Sidebar는 `PERMISSION_MANAGEMENT` 읽기로 메뉴를 노출하는 known mismatch. 직접 `/backoffice/public-holiday` 접근 후 `PUBLIC_HOLIDAY_MANAGEMENT` 쓰기 여부 확인 |
| 비용 탭이 안 보임 | `PROJECT_COST` 읽기 권한 확인 (시드 Member는 기본 비노출 — 민감정보) |
| 대시보드에 **총 인건비 카드**가 없음 | `PROJECT_COST` 읽기 권한 확인. 급여 정책이 *등급 밴드*여도 숨겨집니다 (0원으로 표시되지 않고 카드 자체가 사라집니다) |
| 등급 목록에 **급여 밴드 금액**이 안 보임 | `PROJECT_COST` 읽기 또는 `LEVEL_MANAGEMENT` 읽기 권한 확인 |
| 인력 현황에 **일부 인원만** 보임 | 정상일 수 있습니다 — 팀장은 자기 팀만 보입니다. 전사가 필요하면 권한 세트의 **프로젝트 범위**를 `ALL`로 변경 |
| 등급 기반 전환 후 비용이 0원 | 사용자 등급 지정 여부와 해당 등급의 대표값 또는 하한·상한 쌍 확인. 미산정 인원 경고 수 확인 |
| 급여 정책 변경 후 통합 대시보드 비용이 안 보임 | 스냅샷의 `salary_policy`가 현재 정책과 다르면 마스킹됨. **지금 재집계** 실행 |
| 간트에서 드래그·편집이 안 됨 | 프론트와 서버 모두 `PROJECT` 쓰기를 사용. `PROJECT` 권한과 Jira 이슈 편집 권한 확인 (`PROJECT_GANTT`는 legacy 미사용) |
| 자원관리/팀 분석이 안 보임 | `RESOURCE_MANAGEMENT` 읽기 및 팀 분석 scope 확인. 팀장은 마이페이지 진입점도 확인 |
| 팀장에게 다른 팀이 보임/내 팀이 안 보임 | `team.leaderAccountId`, 사용자 `team_key`, 하위 팀을 포함하는 `TEAM_ONLY` 범위 확인 후 팀 캐시+principal 캐시가 만료되는 최대 약 90초 뒤 재확인 |
| 구독한 이슈가 안 들어옴 | 구독 상태·추가 JQL·소스 접근권한 확인 후 **지금 동기화**. 보드는 최대 다음 시간별 리컨실까지 지연 가능 |
| 보드 구독만 실패 | 구독 상태의 `AGILE_UNAVAILABLE` 확인. 현재 classic scope에서 Agile API 접근 가능 여부를 사이트에서 검증 |
| 통합 대시보드가 옛 수치 | 일일 스냅샷 기준 — **지금 재집계** 실행 |
| 설치 직후 데이터 비정상 | DB 마이그레이션/시드 실행 로그 확인 |

## 9. 관리자 권한 요약

### 9.0 Jira 계정 권한 (앱 권한보다 먼저 충족돼야 하는 것)

| 상황 | 필요한 Jira 권한 |
|---|---|
| 앱 설치·scope 승인·업그레이드 재승인 | 사이트 관리자(전역 **Administer Jira**) 또는 조직 관리자 |
| **최초 관리자로 앱 진입** | 전역 관리 권한(`ADMINISTER`) — 앱 등록 없이 전권 Admin, 프로젝트 범위 `ALL` 고정 |
| 앱 화면 접근 | Jira 제품 라이선스 보유 계정 |
| 이슈·분석·간트 조회 | 대상 프로젝트 **Browse Projects** |
| 워크로그 작성 / 본인 워크로그 수정·삭제 | **Work On Issues** / Edit·Delete Own Worklogs |
| 일정 변경 · 담당자 지정 · 선후행 연결 | **Edit Issues + Schedule Issues** · **Assign Issues** · **Link Issues** |
| 계획 작업량(MD) 입력 | Edit Issues + 프로젝트 **시간 추적 활성화** |

> 앱은 Jira 호출을 사용자 컨텍스트로 실행하므로, **앱 권한이 Jira 권한을 대신하지 않습니다.** 두 층이 모두 충족돼야 저장됩니다. 자세한 내용은 [2.0](#20-시작하기-전에--필요한-jira-계정-권한).

### 9.1 앱 권한(권한 묶음)

| 작업 | 필요 권한 |
|---|---|
| 일반 설정 변경 | `SETTINGS` 쓰기 |
| 사용자 등록/수정 | `USER_MANAGEMENT` 쓰기 |
| 팀 구조·팀장 관리 | `TEAM_MANAGEMENT` 쓰기 |
| 역할/등급/스킬 관리 | `ROLE_MANAGEMENT` / `LEVEL_MANAGEMENT` / `SKILL_MANAGEMENT` 쓰기 |
| 프로젝트 상태/전이 편집 | `PROJECT_STATUS_MANAGEMENT` 쓰기 |
| 권한 묶음 관리(조회 범위 포함) | `PERMISSION_MANAGEMENT` 쓰기 |
| 공휴일 관리 | `PUBLIC_HOLIDAY_MANAGEMENT` 쓰기 |
| 프로젝트 추가·수정·삭제 | `PROJECT` 쓰기 |
| 간트 편집(일정/계층/선후행/폴더) | 프론트·서버 모두 `PROJECT` 쓰기 (`PROJECT_GANTT`는 legacy 미사용) |
| 비용 탭 열람 | `PROJECT_COST` 읽기 |
| 자원관리·팀 분석·프로젝트 배정 | `RESOURCE_MANAGEMENT` 읽기/쓰기 (`REPORT`, `PROJECT_COST`에 따라 일부 축 추가) |
| 저장 공간(DB 사용량) 확인 | `STORAGE_MONITORING` 읽기 |

> 시드된 **Admin** 권한은 위 전부를 포함합니다. 운영자 계정에는 Admin 또는 동등한 커스텀 권한을 부여하세요.
