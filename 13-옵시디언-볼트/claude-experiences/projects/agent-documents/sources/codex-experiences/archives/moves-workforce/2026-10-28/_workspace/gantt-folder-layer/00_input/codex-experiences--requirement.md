# 요구사항: 간트 폴더 레이어 (2026-07-02)

## 사용자 요구 (원문 요지)
"작업들을 묶을 만한 폴더 레이어가 필요. 하위 작업들을 포함하는 개념으로 기간을 다 담아야 함. 수행율도 계산. 행(컬럼) 색이 달라야 함."

## 확정 결정 (사용자 답변)
1. **폴더 실체 = 앱 전용 가상 엔티티** — Jira 이슈 아님. Forge SQL 저장. Jira 화면에는 안 보임(간트 전용).
2. **임의 중첩** — 폴더 안 폴더 허용 (순환 방지 필수).
3. **수행율 = 계획 작업량(MD) 가중 평균** — Σ(하위 leaf 처리율 × 계획MD) ÷ Σ(계획MD). MD 없는 작업은 동일 가중치 폴백.

## 기능 요건
- 폴더 CRUD: 생성(이름), 이름 변경, 삭제 (삭제 시 내용물은 폴더의 부모/루트로 이동 — 이슈는 절대 삭제 안 함)
- 이슈를 폴더에 넣기/빼기 (이슈는 최대 1개 폴더 소속). 이슈의 기존 WBS 하위트리는 통째로 따라감
- 폴더 막대 = 하위(이슈+하위폴더) 기간 전체를 감싸는 롤업 막대 (포함 개념)
- 폴더 수행율 = 위 가중 평균 (그리드 처리율 컬럼 + 막대 진행 채움에 표시)
- 폴더 행은 색상으로 구분 (그리드 행 배경 + 막대 색 — 일반 이슈·네이티브 summary와 구별)
- 폴더 행에서 이슈 전용 컬럼(담당자/협업자/일정편집/계획MD 등)은 '-' 또는 집계값 표시, 편집 불가
- 권한: canWrite(PROJECT_GANTT) 게이트 (기존과 동일)

## 기존 구조 제약 (설계 시 준수)
- 간트 응답 계약: `getProjectGanttData → content { tasks, links, meta }` — 폴더를 어떻게 실어보낼지(별도 folders 배열 권장, 어댑터에서 합성) 설계
- 트리 렌더: `ganttAdapter.toSvarTasks`가 effectiveParent 기반 SVAR 트리 합성. 폴더는 합성 노드(id 충돌 방지 — 예: `folder:<id>`)로 끼워넣는 방식 검토
- 부모 막대 정책(2026-07-02 확정): 네이티브 하위이슈 부모=summary(초록 롤업), WBS 부모=독립 task 막대. **폴더는 제3의 시각 유형** — SVAR 무료빌드는 per-task css 미지원 → placeholder 막대의 DOM 클래스 부착 패턴(`data-task-id` `:` 접두 디코드) 재사용. 그리드 행 배경은 react-grid `rowStyle` prop 활용 검토
- Forge SQL(TiDB): FK 미강제·CASCADE 무효·트랜잭션 미지원 → 앱 레벨 순차 멱등 DELETE (프로젝트 삭제 cascade에 폴더 테이블 추가 필수 — RFC-150 패턴, ProjectService 삭제 로직)
- Jira write 없음(폴더는 앱 DB만) → search 인덱스 지연 이슈 무관. 폴더 CRUD 후엔 일반 invalidate 가능
- 이슈→폴더 소속 저장은 앱 DB(매핑 테이블) — Jira 커스텀필드 아님
- 상위 지정 모달(GanttParentModal)과의 관계: 부모 후보에 폴더 포함(선택 시 폴더 소속 변경) vs 별도 "폴더 지정" UI — 설계에서 결정
- SVAR 함정: open:true는 자식 있는 노드만 / 필터 부분집합에서 부모 재판정(ganttAdapter 참조)
- 필터(담당자/상태)와 폴더의 상호작용: 필터로 폴더 내용물이 비면 폴더 표시 정책 설계
