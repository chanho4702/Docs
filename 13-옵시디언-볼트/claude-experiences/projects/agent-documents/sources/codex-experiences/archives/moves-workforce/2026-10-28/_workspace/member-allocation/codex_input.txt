## 0. 배경과 목표

### 0.1 문제

- `projectusers`에는 **투입·철수 기간 컬럼이 없다**(`role_key`·`level_key`·`salary`·`salary_type`뿐). 문서에서 말하는 "참여 기간"은 전원에게 **프로젝트 기간을 그대로 적용**한 값이다.
  - 급여 월할: `(연봉/12) × projectMonths` — 프로젝트 개월 수.
  - 소진 추정(AC): `Σ유효급여 × 프로젝트 일정 경과율`.
  - 전사 가동률 분모: 참여 **프로젝트 기간**의 합집합 근무일.
  - 프로젝트 인력 분석 분모: **조회 기간** 근무일(전원 동일).
  - 참여 프로젝트 수·참여 이력·배정 관계도: 프로젝트 `end_date` 기준.
- 그래서 (1) 중간 투입·중도 철수 인원의 가동률·인건비가 왜곡되고, (2) "다음 달에 누가 비나"를 답할 수 없고, (3) **워크로그가 없는 조직에서는 인력·공수 축이 통째로 0**이 된다.

### 0.2 목표

1. 인원별 **참여 기간**(`joined_at`~`left_at`)과 **투입률**(`allocation_pct`)을 프로젝트 인력에 기록한다.
2. 기존 지표(가동률·월할 급여·소진 추정·참여 수)가 **개인 기간을 분모로** 쓰도록 소비처를 전부 교체한다 — 한 곳만 바꾸면 화면마다 값이 갈린다(지표 감사 교훈).
3. 워크로그 없이도 채워지는 **계획 지표**(계획 MD·계획 부하·계획 소진율)를 추가해, 관리자만 쓰는 조직에서도 자원 계획 앱으로 동작하게 한다. 실적(워크로그)이 있으면 계획 대비 실적으로 확장된다.

### 0.3 비범위 (이번 RFC에서 하지 않는 것)

- 한 사람의 **다중 참여 구간**(나갔다 다시 들어옴) — 단일 구간만. 집계 코드 전부가 단일 구간 전제라 다중 구간은 별도 RFC.
- 날짜별로 달라지는 투입률(Tempo 플랜의 일별 %) — 구간 내 단일 %.
- 계획 워크로그 자동 생성, 상태 전이 기반 추정 공수 — 별도 RFC.
- Jira 측 변경(필드·프로퍼티·manifest·scope) — 없음. 앱 데이터만 바뀐다.
- 조회 범위(`MEMBER_ONLY`/`TEAM_ONLY`)에 기간 반영 — 명단 기준 유지(§9 결정 D4).

## 1. 용어

| 용어 | 정의 |
|---|---|
| 참여 기간 | `joined_at` ~ `left_at`. null이면 프로젝트 시작·종료를 상속. 계산 시 항상 프로젝트 기간으로 **클램프** |
| 투입률 | `allocation_pct` 0~100 정수. 기본 100. 0 허용(대기·명목 배정) |
| 유효 참여 기간 | `[max(joined_at ?? p.start, p.start), min(left_at ?? p.end, p.end)]`. 프로젝트 `end_date`가 null이면 `left_at ?? null`(무기한) |
| 경과 참여 기간 | 유효 참여 기간의 종료를 오늘로 클램프한 구간(진행 중 프로젝트의 "지금까지") |
| 계획 MD | 구간 근무일(공휴일 제외) × 투입률/100. **연차는 빼지 않는다**(계획은 배정 의도) |
| 실적 MD | 워크로그 합 ÷ 1일 근무시간 (기존 정의 그대로) |
| 실효 가용 MD | 경과 참여 기간 근무일 − 연차·반차 차감 (기존 정의에서 "프로젝트 기간"만 "참여 기간"으로 교체) |
| 가동률 | 실적 MD ÷ 실효 가용 MD (**투입률 미적용**, §9 D2) |
| 계획 소진율 | 실적 MD ÷ 계획 MD (신규) |
| 계획 부하 | 특정 시점에 한 사람이 참여 중인 전 프로젝트의 투입률 합. 100 초과 = 과할당 (신규) |

## 2. 데이터 모델

### 2.1 DDL (v024, 멱등 ALTER)

```sql
ALTER TABLE projectusers
  ADD COLUMN IF NOT EXISTS joined_at DATE NULL,
  ADD COLUMN IF NOT EXISTS left_at   DATE NULL,
  ADD COLUMN IF NOT EXISTS allocation_pct TINYINT UNSIGNED NOT NULL DEFAULT 100;
```

- `salary_type` 추가 전례(`ALTER_PROJECTUSERS_ADD_SALARY_TYPE`)와 같은 방식. `migrate.js`에 `v024_alter_projectusers_add_period_allocation` enqueue.
- TiDB: FK 미강제·트랜잭션 없음 → 컬럼 추가만이라 영향 없음. 인덱스 추가 없음(기간 조건은 기존 `INDEX(account_id)`·`INDEX(project_id, account_id)`로 충분).
- 기존 행: 전부 null/100 → **계산 결과가 변경 전과 동일**(하위호환 계약, §8 테스트로 고정).

### 2.2 단일 해석 지점 — `MemberPeriod.js`

`src/resolver/project/MemberPeriod.js` (순수 함수, Forge 의존 없음):

```js
resolveMemberPeriod({ joined_at, left_at }, { start_date, end_date })
  → { start, end }            // 유효 참여 기간(클램프 적용, end는 null 가능)
resolveElapsedPeriod(period, today)
  → { start, end }            // 경과 참여 기간
memberWorkdays(period, holidayMap)            // 근무일
plannedMd(period, allocationPct, holidayMap)  // 계획 MD
memberMonths(period)                          // 급여 월할용 개월 수 — computeProjectMonths 와 같은 산식(달력일/30.4375)
```

**모든 소비처는 이 모듈만 쓴다.** `p.start_date/end_date`를 직접 멤버 기간으로 쓰는 코드는 이번 RFC에서 전부 제거한다(§4 매트릭스가 목록).

### 2.3 검증 규칙 (서버, 쓰기 경로 공통)

| 규칙 | 처리 |
|---|---|
| `joined_at > left_at` | 거부 (`LogicalError`, `PROJECT_MEMBER_PERIOD_INVALID`) |
| `allocation_pct` 정수 0~100 아님 | 거부 |
| 기간이 프로젝트 기간 밖 | **허용하되 클램프**. 응답에 `periodClamped: true`를 실어 UI가 경고 (§9 D3) |
| 프로젝트 `start_date` 없음 | `joined_at` null 불가 → 거부 (기간을 유추할 수 없음) |

## 3. 계산 변경 원칙

1. **참여 기간은 분모, 워크로그는 분자.** 참여 기간 밖의 워크로그도 투입(분자)에는 넣는다. 돈이 든 사실을 지울 수 없다. 대신 인력 분석에 `outOfPeriodMd`를 실어 "기간 외 기록"을 경고한다.
2. **투입률은 계획에만 곱한다.** 가동률 분모에는 곱하지 않는다. 가동률의 뜻("사람이 얼마나 찼나")을 바꾸지 않기 위해서다. 투입률이 반영된 값은 계획 MD·계획 소진율·계획 부하다.
3. **급여 월할에는 참여 기간과 투입률을 모두 곱한다.** ANNUAL·LEVEL_BAND 원천은 "월 단위 인건비"이므로 `(월급여) × memberMonths × pct/100`. PROJECT 원천(투입급여)은 이미 협의된 총액이라 **둘 다 곱하지 않는다**(§9 D1).
4. **소진 추정(AC)은 인원별 경과율로.** `Σ member.effectiveSalary × memberScheduleRate` (memberScheduleRate = 경과 참여 근무일 ÷ 유효 참여 근무일). 프로젝트 단위 경과율은 헤더 표시용으로만 남긴다.
5. **하위호환 = 기존 행 무변경.** null·100인 행은 모든 산식이 변경 전 값과 일치해야 한다.

## 5. 신규 지표 정의 (계획 기반 모드)

| 지표 | 산식 | 표시 위치 |
|---|---|---|
| 인원 계획 MD | `memberWorkdays(유효 참여 기간) × pct/100` | 인력 목록·인력 분석·인력 상세 |
| 프로젝트 계획 MD | Σ 인원 계획 MD | 프로젝트 대시보드 헤더·통합 대시보드 범위 축(선택) |
| 계획 소진율 | 실적 MD ÷ 계획 MD (계획 0 → null) | 인력 분석 컬럼, 프로젝트 인력 분석 상단 차트 |
| 계획 부하(오늘) | Σ pct over 참여 중 프로젝트 | 작업 배정·프로젝트 배정 후보 행, 인력 현황 컬럼 |
| 계획 부하(기간) | 월별 Σ pct (달력) | 팀 분석 위젯(P3, 선택) |

워크로그 0인 조직: 가동률·MM·실적 열은 비고, 계획 MD·계획 부하·계획 인건비·소진 추정은 채워진다. 화면은 실적이 없을 때 계획 열을 앞에 두고 "계획" 배지를 붙인다.

## 6. 경계면 계약

### 6.1 resolver (기존 함수 확장, 신규 함수 없음)

```
insertProjectusers        payload: { project_id, jiraUser, joinedAt?, leftAt?, allocationPct? }
updateProjectUsersByKey   payload: … + { joinedAt?, leftAt?, allocationPct? }   // undefined = 미변경, null = 상속으로 되돌림
addTeamMembersToProject   payload: … + { joinedAt?, leftAt?, allocationPct? }   // 팀 전원 동일값
getProjectUsers…          응답 행: + { joinedAt, leftAt, allocationPct, effectivePeriod:{start,end}, periodClamped, plannedMd }
getResourceAnalysisList   응답 members[]: + { periodStart, periodEnd, plannedMd, planBurnRate, outOfPeriodMd }
getWorkAssignmentBoard/Pool  company: + { plannedLoadPct }
```

- `undefined ≠ null` 계약은 `updateGanttSchedule` 전례([[project-work-bulk-apply]])와 동일.
- 응답 필드는 전부 **additive**. 프론트는 없으면 "집계 전"으로 다루고 `?? 0`으로 채우지 않는다(비용 캐시 `byTeam` 교훈).

### 6.2 캐시 무효화

| 캐시 | 키 | 조치 |
|---|---|---|
| 비용(`ProjectCostService`) TTL 10분 | projectId·정책 | 인력 기간·투입률 저장 시 해당 프로젝트 키 삭제(급여 저장과 같은 경로) |

## 7. UI

- 인력 목록: 참여 기간(시작~종료 인라인 날짜)·투입률(%) 컬럼. 프로젝트 기간 밖이면 경고 아이콘 + 툴팁 "계산은 프로젝트 기간으로 잘립니다".
- 추가 모달: 기본값 = 프로젝트 기간·100. "팀 전체 추가"는 팀 전원 같은 값 → 이후 개별 편집.
- 인력 분석: 상단 기준값 줄에 "분모 = 조회 기간 ∩ 참여 기간" 문구. 계획 MD·계획 소진율 컬럼. 기간 외 기록 경고.
- 배정 화면: 후보 행에 "계획 부하 120%" 배지(빨강), "투입 가능만" 필터 정의 갱신.
- 인력 상세: 참여 이력 기간을 개인 기간으로, 투입률 표시.

## 11. 리스크

- **소급 변경**: 기간·투입률을 바꾸면 과거 가동률·인건비가 바뀐다. 스냅샷 화면은 재집계 전까지 옛 값. 변경 이력(감사 로그)은 이번 범위 밖이나 `updated_id/updated_at`은 이미 있다.
- **분모 불일치 재발**: 소비처 하나라도 `p.start_date`를 직접 쓰면 화면마다 가동률이 갈린다. §4 매트릭스 + `src/` 전역 grep(`start_date`/`end_date` 사용처)로 검증.
- **캐시 stale**: 비용 10분·인력 분석 캐시. 저장 경로에서 무효화하지 않으면 "고쳤는데 그대로" 문의가 온다.
- **투입률 0 인원**: 계획 MD 0·계획 소진율 null. 가동률은 정상 계산(분모는 기간). 화면에서 "명목 배정"으로 구분.
- **PPT·문서 문구**: "워크로그가 원천" → "실적은 워크로그, 계획은 배정". 소개서 §3 산식 표에 계획 MD 추가.

const MS_PER_DAY = 86400000;
const AVG_MONTH_DAYS = 365.25 / 12; // 30.4375 (윤년 평균)

/**
 * 프로젝트 기간의 개월수(소수). 종료일 포함(inclusive).
 * 총 달력일수 ÷ 평균 월길이(30.4375). 네이티브 Date만 사용(dayjs 불필요).
 *  - 1년(Jan1~Dec31, 365일) → 11.99 ≈ 12
 *  - 월 중간 시작/종료: 달력일수 기반이라 자연 처리
 *  - 1개월 미만: 예 15일 → 0.49
 *  - start==end: 1일 → 0.03
 *  - end < start / 누락 → 0
 * @param {string} startDate 'YYYY-MM-DD'
 * @param {string} endDate   'YYYY-MM-DD'
 * @returns {number} 개월수(소수 2자리). 무효 입력 → 0
 */
export const computeProjectMonths = (startDate, endDate) => {
    if (!startDate || !endDate) return 0;
    const start = new Date(startDate + 'T00:00:00');
    const end = new Date(endDate + 'T00:00:00');
    if (isNaN(start) || isNaN(end) || end < start) return 0;
    const inclusiveDays = Math.round((end - start) / MS_PER_DAY) + 1; // 종료일 포함
    return Math.round((inclusiveDays / AVG_MONTH_DAYS) * 100) / 100;   // 소수 2자리
};

/**
 * 멤버 1인 유효급여(투입 총단가 환산, 월할).
 *
 * ⚠ 무회귀 계약: 2번째 인자를 `{projectMonths}` 만으로 호출하면 **기존과 완전히 동일한 값**을 낸다
 *   (`policy` 기본값이 'INDIVIDUAL' 이므로 기존 호출부는 LEVEL_BAND 분기에 진입 자체를 못 한다).
 *
 * @param {{salaryType?:string, salary?:number, annualSalary?:number|null, levelKey?:string|null}} member
 * @param {{projectMonths:number, policy?:string, levelBands?:Object|null}} ctx
 * @returns {number} 유효 인건비(정수). 항상 number(NaN 금지).

export const computeEffectiveSalary = (
    { salaryType, salary, annualSalary, levelKey },
    { projectMonths, policy = 'INDIVIDUAL', levelBands = null } = {}
) => {
    /*
     * ── LEVEL_BAND 분기 ────────────────────────────────────────────────────
     * 급여 **원천**만 바뀐다. 월할 환산식((annual/12) × projectMonths)은 아래 ANNUAL 경로와
     * 문자 그대로 동일하다. salary(투입급여)·annualSalary(개인 연봉)는 **읽지 않는다**.
     * 등급 미지정 / 밴드 미설정 / 대표값 0 → 0 (기존 `annual <= 0 → 0` 규약과 동일. 새 규약 없음)
     */
    if (policy === 'LEVEL_BAND') {
        const annual = resolveLevelBandAnnual(levelKey, levelBands) ?? 0;
        const months = projectMonths || 0;
        if (annual <= 0 || months <= 0) return 0;
        return Math.round((annual / 12) * months);
    }

    // ↓↓↓ 아래는 한 글자도 수정하지 않는다 (INDIVIDUAL = 기존 동작 그대로) ↓↓↓
    const invest = salary || 0;
    if ((salaryType || 'PROJECT') !== 'ANNUAL') return Math.round(invest); // PROJECT: 기존 그대로
    const annual = annualSalary || 0;
    const months = projectMonths || 0;

    return Math.round((annual / 12) * months);
};

// 비용 분석(cost-analysis) 순수 계산 로직 (Forge 의존성 없음 → jest 단위 테스트 가능)
// 설계서 §1(안분 확정식)·§2-A(응답 shape)·§3-1을 그대로 구현한다.
//
// 안분 기준 (설계 §1):
//   actualCost = totalSalary × scheduleRate
//   EV(획득가치) = totalSalary × completionRate
//   CPI = EV / AC   (AC=0 가드 → null)
//   EAC = BAC / CPI (cpi null/0 가드 → null)
//   A8 issueCost = Σmember( salary × scheduleRate × issueSec / memberTotalSec )

const round1 = (n) => Math.round(n * 10) / 10;
const round2 = (n) => Math.round(n * 100) / 100;

/**
 * AC(실집행) = totalSalary × scheduleRate (시간경과 안분, 설계 §1-1).
 * @returns {number} 원 단위 정수
 */
export const allocateActualCost = (totalSalary, scheduleRate) => {
    const ts = totalSalary || 0;
    const sr = scheduleRate || 0;
    return Math.round(ts * sr);
};

/**
 * A1/A2 예산 블록.
 *   plannedBudget(BAC) = totalSalary
 *   actualCost(AC)     = totalSalary × scheduleRate
 *   remaining          = plannedBudget − actualCost
 *   earnedValue(EV)    = totalSalary × completionRate
 * @returns {{plannedBudget:number, actualCost:number, remaining:number, earnedValue:number}}
 */
export const computeBudget = (totalSalary, scheduleRate, completionRate) => {
    const plannedBudget = Math.round(totalSalary || 0);
    const actualCost = allocateActualCost(totalSalary, scheduleRate);
    const earnedValue = Math.round((totalSalary || 0) * (completionRate || 0));
    return {
        plannedBudget,
        actualCost,
        remaining: plannedBudget - actualCost,
        earnedValue,
    };
};

/**
 * A6/A7 EVM 블록 (가드 포함, 설계 §1-1).
 *   CPI = EV / AC            (AC=0 → null)
 *   EAC = BAC / CPI          (cpi null/0 → null)
 *   ETC = EAC − AC           (eac null → null)
 *   overBudget = eac > plannedBudget (null 이면 false)
 *   overrunAmount = max(eac − plannedBudget, 0) (null 이면 0)
 * @returns {{cpi:number|null, eac:number|null, etc:number|null, overBudget:boolean, overrunAmount:number}}
 */
export const computeEvm = (plannedBudget, actualCost, earnedValue) => {
    const ac = actualCost || 0;
    const cpi = ac > 0 ? round2(earnedValue / ac) : null;
    const eac = (cpi != null && cpi > 0) ? Math.round((plannedBudget || 0) / cpi) : null;
    const etc = eac != null ? eac - ac : null;
    const overBudget = eac != null ? eac > (plannedBudget || 0) : false;
    const overrunAmount = eac != null ? Math.max(eac - (plannedBudget || 0), 0) : 0;
    return { cpi, eac, etc, overBudget, overrunAmount };
};

/**
 * A3 월별 비용 소진 — monthlyEffort(md) 비중으로 actualCost 안분.
 * monthlyEffort: [{ month:'YYYY-MM', md }]
 * Σmd=0 가드 → 각 월 actual=0 (균등 0), cumulative 0.
 * @returns {[{month:string, actual:number, cumulative:number}]}
 */
export const allocateMonthlyCost = (monthlyEffort, actualCost) => {
    const list = Array.isArray(monthlyEffort) ? monthlyEffort : [];
    const totalMd = list.reduce((acc, m) => acc + (m.md || 0), 0);
    const ac = actualCost || 0;
    let cumulative = 0;
    return list.map((m) => {
        const actual = totalMd > 0 ? Math.round(ac * ((m.md || 0) / totalMd)) : 0;
        cumulative += actual;
        return { month: m.month, actual, cumulative };
    });
};

/**
 * A5 역할/레벨별 비용 분포.
 * members: [{ salary, roleKey|levelKey(=keyField로 지정) }]
 *   planned = Σsalary
 *   actual  = Σsalary × scheduleRate
 * keyField 값이 없으면 key=null 그룹으로 묶음.
 * @param {Array} members
 * @param {number} scheduleRate
 * @param {string} keyField 'roleKey' | 'levelKey'
 * @returns {[{key:string|null, planned:number, actual:number, memberCount:number}]}
 */
export const groupCostByKey = (members, scheduleRate, keyField) => {
    const sr = scheduleRate || 0;
    const map = new Map();
    for (const m of (members || [])) {
        const key = m[keyField] ?? null;
        if (!map.has(key)) map.set(key, { key, planned: 0, memberCount: 0 });
        const g = map.get(key);
        g.planned += (m.salary || 0);
        g.memberCount += 1;
    }
    return Array.from(map.values()).map((g) => ({
        key: g.key,
        planned: Math.round(g.planned),
        actual: Math.round(g.planned * sr),
        memberCount: g.memberCount,
    }));
};

/**
 * 기간 구간 배열 병합 (겹친/인접 구간 1회로). 입력 [[start,end], …] (YYYY-MM-DD).
 * 반환 [{start, end}] 정렬·병합. 이중계상 분모 제거의 핵심.
 */
export const mergeIntervals = (intervals = []) => {
    const valid = intervals
        .filter(iv => iv && iv[0] && iv[1] && iv[0] <= iv[1])
        .map(iv => ({ start: iv[0], end: iv[1] }))
        .sort((a, b) => (a.start < b.start ? -1 : a.start > b.start ? 1 : 0));

    const merged = [];
    for (const cur of valid) {
        const last = merged[merged.length - 1];
        if (last) {
            // 인접/겹침: 다음 시작이 직전 끝 +1일 이내면 병합
            const lastEndPlus = new Date(last.end + 'T00:00:00');
            lastEndPlus.setDate(lastEndPlus.getDate() + 1);
            const curStart = new Date(cur.start + 'T00:00:00');
            if (curStart <= lastEndPlus) {
                if (cur.end > last.end) last.end = cur.end;
                continue;
            }
        }
        merged.push({ start: cur.start, end: cur.end });
    }
    return merged;
};

// 사용자별 연차/반차 차감 Map: accountId → { days, deduction }
// 근무일(평일·비공휴일)에 대해서만 차감한다.
//   work_ratio=0(연차)  → 근무일 1일당 1 MD 차감
//   work_ratio=0.5(반차) → 근무일 1일당 0.5 MD 차감
//   work_ratio=1(출장/기타) → 차감 없음
export const computeLeaveDeductionMap = (schedules, startDate, endDate, holidayMap) => {
    const rangeStart = new Date(startDate + 'T00:00:00Z');
    const rangeEnd   = new Date(endDate   + 'T00:00:00Z');
    const map = new Map();

    // 같은 사용자의 일정이 겹치면 날짜별 최소 work_ratio만 적용한다.
    // 일정별 deduction을 합산하면 한 날짜의 base workday보다 많이 차감될 수 있다.
    const ratioByAccountDate = new Map();

    for (const sched of schedules) {
        const { account_id, schedule_start_date, schedule_end_date, work_ratio } = sched;
        if (!account_id || !isValidYmd(schedule_start_date) || !isValidYmd(schedule_end_date)) continue;
        const wrNumber = Number(work_ratio ?? 0);
        const wr = Number.isFinite(wrNumber) ? Math.min(1, Math.max(0, wrNumber)) : 0;
        if (wr >= 1) continue;

        const schedStart = new Date(schedule_start_date + 'T00:00:00Z');
        const schedEnd   = new Date(schedule_end_date   + 'T00:00:00Z');
        const s = schedStart > rangeStart ? schedStart : rangeStart;
        const e = schedEnd   < rangeEnd   ? schedEnd   : rangeEnd;
        if (s > e) continue;

        for (let d = new Date(s); d <= e; d = addUtcDay(d)) {
            if (workdayValue(d, holidayMap) <= 0) continue;
            const date = d.toISOString().slice(0, 10);
            const dates = ratioByAccountDate.get(account_id) ?? new Map();
            const previous = dates.get(date);
            dates.set(date, previous == null ? wr : Math.min(previous, wr));
            ratioByAccountDate.set(account_id, dates);
        }
    }

    for (const [account_id, dates] of ratioByAccountDate) {
        if (!map.has(account_id)) map.set(account_id, { days: 0, deduction: 0 });
        const entry = map.get(account_id);
        for (const [date, ratio] of dates) {
            const baseDay = workdayValue(new Date(`${date}T00:00:00Z`), holidayMap);
            entry.days += baseDay;
            entry.deduction += Math.min(baseDay, baseDay * (1 - ratio));
        }
    }

    return map;
};

/**
 * 부하 분산 비율 = 이 프로젝트 잔여 / 전사 잔여. 분모 0 → null.
 * @returns {number|null}
 */
export const computeLoadSplitRatio = (projectRemaining, companyRemaining) =>
    (companyRemaining ?? 0) > 0 ? (projectRemaining ?? 0) / companyRemaining : null;

// EXTERNAL_OVERLOAD_ESTIMATED — 가동률 실적 없이 잔여량으로만 추정할 때의 배수 기준.
const ESTIMATED_OVERLOAD_MULTIPLIER = 2.5;

/**
 * 괴리 신호 산출 (§3.3 표).
 * company === null(권한 마스킹) 이면 항상 빈 배열.
 *
 * @param {{project:Object, company:Object|null, loadSplitRatio:number|null}} ctx
 * @param {{externalLoadRatio:number, projectFocusRatio:number, multiProjectMin:number}} th
 * @returns {string[]}
 */
export const computeSignals = ({ project, company, loadSplitRatio } = {}, th = DEFAULT_ASSIGNMENT_THRESHOLDS) => {
    if (!company) return []; // 전사 스코프 마스킹 → 판단 근거 없음

    const signals = [];
    const projectRemaining = project?.remainingSeconds ?? 0;
    const companyRemaining = company.remainingSeconds ?? 0;
    const projectCount = company.projectCount ?? 0;
    const band = company.utilBand ?? 'unknown';

    // ① 전사 과부하 + 이 프로젝트 비중 낮음 = 핵심 탐지 목표
    if ((band === 'over' || band === 'red')
        && loadSplitRatio != null && loadSplitRatio <= th.externalLoadRatio) {
        signals.push('EXTERNAL_OVERLOAD');
    }

    // ② 가동률 실적이 없어 잔여량으로만 추정한 약한 신호
    if (company.util == null
        && companyRemaining >= projectRemaining * ESTIMATED_OVERLOAD_MULTIPLIER
        && projectCount >= th.multiProjectMin) {
        signals.push('EXTERNAL_OVERLOAD_ESTIMATED');
    }

    // ③ 다중 프로젝트 분산
    if (projectCount >= th.multiProjectMin) {
        signals.push('MULTI_PROJECT');
    }

    // ④ 이 프로젝트 집중
    if (loadSplitRatio != null && loadSplitRatio >= th.projectFocusRatio) {
        signals.push('PROJECT_FOCUSED');
    }

    // ⑤ 판단 근거 부족
    if (company.util == null && companyRemaining === 0) {
        signals.push('NO_CAPACITY_DATA');
    }

    return signals;
};

// utilBand 서열 — 여유한 쪽이 먼저. company null 은 unknown(1)로 취급.
const BAND_ORDER = { idle: 0, unknown: 1, normal: 2, over: 3, red: 4 };
const bandRank = (candidate) => BAND_ORDER[candidate?.company?.utilBand ?? 'unknown'] ?? 1;
