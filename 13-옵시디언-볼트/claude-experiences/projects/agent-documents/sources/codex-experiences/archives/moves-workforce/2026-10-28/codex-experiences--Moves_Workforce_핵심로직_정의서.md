## 1. 목적·범위

Moves Workforce가 보여주는 **핵심 지표의 계산 방식과 그 근거**를 한 곳에 정의한다. 화면·문서마다 지표를 재설명하지 않고 이 문서를 단일 기준으로 삼는다. 대상: 공수(MD/MM)·가동률·진척도 3층·이슈 진행률·지연·T/S/R 신호등·계획 인건비·팀 집계.

**공통 원칙 3가지** (모든 지표에 적용):
1. **같은 개념이면 분모도 같다.** 같은 이름의 지표가 화면마다 다른 분모를 쓰지 않는다.
2. **라벨은 실체를 정확히 부른다.** (예: `Σsalary`는 "예산"이 아니라 "계획 인건비".)
3. **근사치는 숨기지 않고 화면에 명시한다.** (진행 중 이슈 진행률 등은 ⓘ로 근사임을 고지.)

## 2. 지표 정의

### 2.1 근무일과 기준 공수 (base MD)

하루의 "근무 가치"를 다음과 같이 정의한다:

| 날짜 유형 | 근무 가치 |
|-----------|-----------|
| 주말 | 0 |
| 공휴일 | `workRatio` (0=휴무, 0.5=반휴, 1=정상) |
| 평일 | 1 |

- 어떤 기간의 **기준 공수(base MD) = 그 기간 각 날짜의 근무 가치를 모두 더한 값**. 비례식이 아니라 근무일을 직접 센다.
- 모든 단위가 "근무일 1일 = 1MD"로 통일되어, 공휴일·연차 차감과 단위가 정확히 맞는다.
- `hourRate`(1일=N시간)로 시간↔MD를 변환한다.

### 2.2 MM (절대 공수)

```
1MM(해당 월) = 그 달의 실제 근무일 수 (평일 − 공휴일)
MM = totalMD ÷ 그 달 1MM 근무일
```

- 1MM은 **관리자 입력값이 아니라 캘린더·공휴일로 자동 계산**된다.
- 여러 달에 걸친 기간의 MM 분모는 걸친 달들의 1MM **평균**을 쓴다(월별 차트는 달마다 정확한 값 사용).
- 의미: "이 인원/프로젝트가 **얼마나 일했나**"라는 절대량.

### 2.3 가동률 (Utilization, 상대)

```
가동률(%) = totalMD ÷ effectiveMD × 100
effectiveMD = min(오늘, 종료일)까지의 가용 근무일 (연차 등 차감)
```

**규칙 2가지:**
1. **분모에 미래를 넣지 않는다.** 분모는 프로젝트 전체 기간이 아니라 `min(오늘, 종료일)`까지의 경과 근무일. 투입(분자)은 과거에만 쌓이므로, 분모에 미래가 들어가면 진행 중 프로젝트의 가동률이 항상 낮게 나온다.
2. **전사 가동률은 배치에서 계산한다.** 한 사람이 같은 기간에 여러 프로젝트에 걸치면, 프로젝트별 가용일을 단순 합산한 분모는 그 사람을 이중 계산해 과소평가된다. 올바른 분모는 **인원별 기간의 합집합**이며, 이는 프로젝트별 숫자를 더해 복원할 수 없으므로 원본에 접근하는 배치 시점에 계산한다.

**경계값 계약:** backend는 `effectiveEndDate=min(requestedEndDate, today)`를 강제한다. 미래 전용 구간 또는 공휴일·휴가 차감 후 가용 근무일이 0이면 `effectiveMD=null`이며 UI는 `N/A`로 표시한다. 계산 편의를 위해 0을 0.1일로 치환하지 않는다.

**일정 겹침 계약:** 같은 사용자·같은 날짜에 일정이 겹치면 그날의 `work_ratio` 최솟값을 적용한다(연차 0과 반차 0.5가 겹치면 0). 일별 차감은 해당 날짜 base workday를 초과할 수 없으며 일정별 deduction 단순 합산을 금지한다.

> **MM vs 가동률 (왜 둘 다 있나)**
> | | MM (절대) | 가동률 (상대) |
> |---|---|---|
> | 질문 | 얼마나 일했나 | 가용 대비 얼마나 채웠나 |
> | 분모 | 그 달 1MM 근무일(월 기준 고정) | effectiveMD(연차 뺀 가용일) |
> 예: 1.6MD 일했고 가용 1.4MD → MM≈0.08(절대량 적음), 가동률≈114%(가용 초과). 한 숫자로 합치면 "3일 일했는데 1MM 초과" 같은 모순이 생긴다.

### 2.4 진척도 3층

성격이 다른 세 질문을 **절대 한 숫자로 합치지 않는다**(EVM의 AC/EV/PV).

| 층 | 질문 | 산식 | EVM |
|----|------|------|-----|
| **층1 · 공수** | 얼마나 일했나(소진율) | 계획 누적(선형) vs 실제 누적(워크로그 일별 합) | AC |
| **층2 · 완성** | 얼마나 끝났나(진척) | `Σ(이슈 진행률 × 계획MD) ÷ Σ(계획MD)` | EV |
| **층3 · 일정** | 시간이 얼마나 흘렀나 | `경과 근무일 ÷ 전체 근무일` | PV |

- 상태 판정(정상/주의/지연)의 **주 신호 = 완성 vs 일정** 비교(±`progressThreshold`, 기본 5%p), 보조 신호 = 공수 vs 완성.
- 진척도 화면에 **기간 필터가 없는** 이유: "지금 이 순간 프로젝트 전체가 어디까지 왔나"의 스냅샷이라, 일부 지표만 기간으로 자르면 화면 내 지표끼리 모순되기 때문. 캐시 키도 `ProjectProgress:{projectId}` 하나.

### 2.5 이슈 진행률

| 상태 카테고리 | 진행률 |
|---------------|--------|
| 완료(Done) | **100% 고정** (공수 초과 투입해도 100%로 캡) |
| 진행 중 | `min(실투입MD ÷ 계획MD, 100%)` |
| 할 일(To Do) | 0% |

- 계획MD가 없는 이슈는 가중 평균의 **분모에서 제외**한다.
- ⚠️ **근사 고지**: Jira에 진행률 필드가 없어 진행 중 이슈의 진행률은 "공수를 얼마나 썼나"로 근사한 값이다. 이 근사가 쓰이는 지표(완성률·CPI·신호등 T)에는 ⓘ로 근사임을 명시한다.

### 2.6 지연

| 구분 | 대상 | 산식 |
|------|------|------|
| **확정 지연** | 완료 이슈 | 실제 완료일(Done + 마지막 워크로그일) − 마감일(duedate). **지연(>0)만** 평균. 조기 완료는 `avgLeadDays`로 분리. |
| **예측 지연** | 미완료 이슈 | 남은 공수 `max(계획−실투입, 0)` 기준 이슈별 예상 종료일의 최댓값 vs 프로젝트 종료일. **낙관적 근사**(이슈마다 전 인원 투입 가정). |

> 확정 지연에서 조기 완료를 섞으면 평균이 상쇄돼 둘 다 안 보이므로 분리한다.

### 2.7 T / S / R 신호등 (포트폴리오 종합개요)

| 축 | 의미 | 기준 |
|----|------|------|
| **T (Time)** | 완성률 − 일정률 | `progressThreshold`(기본 5%p)보다 뒤처지면 빨강 |
| **S (Scope)** | 잔여 작업 비중(todoRatio) | `scopeTodoAmberRatio/RedRatio`(기본 0.3 / 0.6) |
| **R (Resource)** | 가동률 | 가동률 밴드(기본 0.7 / 1.1 / 1.3) — 너무 낮아도(놀림) 너무 높아도(과부하) 경고 |

> ⚠️ 신호등 R은 **그 프로젝트 내 인원 평균**이고, 헤더의 전사 가동률(합집합 분모)과는 **의도적으로 다른 지표**다. ⓘ에 설명.

### 2.8 계획 인건비 (비용)와 급여 정책

```
계획 인건비 = Σ effectiveSalary

INDIVIDUAL 정책
  PROJECT 모드: effectiveSalary = round(프로젝트 투입 급여)
  ANNUAL 모드 : effectiveSalary = round((개인 연봉 ÷ 12) × 프로젝트 개월수)

LEVEL_BAND 정책
  effectiveSalary = round((등급 대표값 ÷ 12) × 프로젝트 개월수)
  프로젝트 개월수 = round((종료일 포함 달력일수 ÷ 30.4375), 2)

비용 분석 파생값
  실제 소진(AC) = round(계획 인건비 × 일정진척률)
  획득가치(EV) = round(계획 인건비 × 완성률)
```

- `INDIVIDUAL`은 기존 방식이다. 프로젝트 인력마다 **투입 급여 기준(`PROJECT`)** 또는 **개인 연봉 월할(`ANNUAL`)**을 선택한다.
- `LEVEL_BAND`는 개인 금액 대신 등급에 설정한 급여 하한·상한·대표값 중 **대표값**을 연봉으로 간주해 월할한다. 대표값이 비어 있고 하한·상한이 모두 있으면 중앙값을 사용한다.
- 등급이 없거나 대표값을 결정할 수 없으면 해당 인원의 유효 인건비는 0이며 `unpricedMemberCount`에 포함한다. 음수 및 `하한 > 상한`은 저장을 거부하고, 대표값이 범위를 벗어난 경우에는 경고하되 저장을 허용한다.
- 이 값은 승인된 "예산(BAC)"이 아니므로 화면 라벨은 **"계획 인건비"**로 부른다(예산이라 부르면 "예산 대비 소진율" 해석이 오염됨).
- 현재 비용 KPI의 실제 소진(AC)은 워크로그 기반 원가가 아니라 **계획 인건비를 일정진척률로 안분한 값**이다. 워크로그는 이슈별 비용 배분에 사용되며, 이를 AC 전체 산식과 혼동하지 않는다.
- 프로젝트 급여·비용 resolver/DTO는 `PROJECT_COST`로 제어한다. 백오피스 사용자 관리의 개인 연봉은 `USER_MANAGEMENT` 경계이므로 `PROJECT_COST`가 모든 급여 데이터의 유일한 권한 키는 아니다. 일반 자원관리의 `ResourcePersonDTO`에는 `salary`·단가 계열 필드를 포함하지 않는다.
- `LEVEL_BAND`에서는 개인 연봉과 프로젝트 투입 급여를 화면에서만 숨기는 것이 아니라 **서버 응답에서 키 자체를 제거**한다. 전환 전에 존재한 DB 값은 삭제하지 않지만, 이 정책 중 신규 등록된 사용자의 개인 연봉은 NULL일 수 있어 `INDIVIDUAL` 복귀 시 자동 복원할 값이 없을 수 있다. 표시 정책 조회 실패 시에는 숨김으로 fail-close하고, 계산 정책 조회 실패 시에는 잘못된 0원 계산 대신 오류를 반환한다.
- 포트폴리오 스냅샷에는 집계 당시 `salary_policy`를 저장한다. 현재 정책과 다르면 비용 축을 `costMasked` 처리하며, 재집계 후 다시 표시한다.
- 수동 재집계의 완료 신호는 큐 등록 응답이 아니라 `lastAggregatedAt`의 변경이다. UI는 시작 시각의 값을 기준선으로 잡아 15초 간격으로 확인하고 최대 10분 뒤 대기를 해제한다. 실패 응답에는 기준 시각이 없으므로 완료로 판정하지 않는다.

### 2.9 팀 집계

팀 분석은 사람의 **현재 소속 팀(`users.team_key`)**을 기준으로 프로젝트 기여를 묶는다. 프로젝트 담당 팀(`project_team`)은 계획·책임 축이며 실제 기여 축과 자동 동기화하지 않는다.

| 지표 | 집계 규칙 |
|------|-----------|
| 참여 인원 | 선택한 프로젝트의 `accountId` 중복 제거 수 |
| 투입 공수·인건비 | 프로젝트×인원 기여의 합. 한 사람이 여러 프로젝트에 참여하면 프로젝트별 기여를 각각 더함 |
| 팀 가동률 | `Σ investedMD ÷ Σ availMD`. 전 프로젝트 참여 기간 합집합 기준이라 프로젝트 상태 필터와 무관 |
| 팀 진척률 | `Σ(프로젝트 완성률 × 팀 투입MD) ÷ Σ 팀 투입MD` |
| 하위 팀 롤업 | 직속 값과 하위 팀 값을 구분해 제공. 비율은 단순 평균이 아니라 분자·분모를 다시 합산 |

- `null`은 집계 전·권한 없음 등 **알 수 없음**을 뜻한다. 이를 0으로 바꾸어 차트에 표시하지 않는다.
- 팀별 이슈 건수는 동일 이슈에 여러 팀원이 참여해도 팀 소계에서 한 번만 센다.
- 담당 팀 대비 실제 기여는 `담당·기여 / 담당만 / 기여만`으로 대조한다. 어긋남은 자동 보정 대상이 아니라 운영 인사이트다.

## 3. 설정 연동 (settings)

지표에 영향을 주는 주요 설정값:

| 설정 키 | 영향 지표 |
|---------|-----------|
| `hourRate` | 시간↔MD 변환 |
| `progressThreshold` | 진척 상태 판정 / 신호등 T |
| `scopeTodoAmberRatio` / `scopeTodoRedRatio` | 신호등 S |
| `utilizationUnderBand` / `OverBand` / `RedBand` | 신호등 R / 가동률 경고 |
| `salaryPolicy` | 계획 인건비 원천(`INDIVIDUAL` / `LEVEL_BAND`) |
| 공휴일(holiday) | 근무일·1MM·가동률·일정률 전반 |

`progressThreshold`의 단위는 percentage point(%p), 기본값은 5이며 유효 범위는 0~100이다. KVS `settings` schema, seed, `updateSetting`, 설정 UI, `ProjectProgressService`, `PortfolioDashboardService`가 이 값을 공유한다. 판정 결과를 캐시에 박제하지 않고 read-time에 현재 임계값을 적용한다.

## 4. 데이터·권한 불변식

- 개인 일정 update/delete는 `context.accountId`를 SQL owner predicate에 포함한다. 0행은 존재 여부를 노출하지 않는 `SCHEDULE_NOT_FOUND_OR_FORBIDDEN`이다.
- Forge SQL DML 영향 행 수의 raw source는 `result.rows.affectedRows`이며 공통 query 계층이 `rowsAffected` alias로 정규화한다.
- 명시적인 context license의 `active:true/false`를 환경보다 우선한다. inactive는 `LICENSE_INACTIVE`로 차단한다. license 부재는 development/staging에서만 적용 대상 아님으로 허용한다.
- **차단 대상은 `INACTIVE` 하나뿐이다(2026-08-10 정책).** 상태를 확정하지 못한 경우(`UNAVAILABLE`)는 통과시킨다 — 이 판정이 모든 resolver를 감싸므로, 판정 불가를 차단으로 다루면 아틀라시안 상류 장애 한 번이 앱 전면 정지가 된다. 매출 보호는 "확정된 비활성"이 담당하고, 확정하지 못한 순간의 비용은 가용성 쪽으로 넘긴다.
- 단 **호출 실패와 라이선스 부재는 다르게 다룬다.** 네트워크·5xx로 물어보지 못한 경우만 `UNAVAILABLE`(통과)이고, License API가 200으로 답했는데 활성 라이선스가 없으면 `INACTIVE`(차단)다.
- 비동기 job status 응답은 `{success:true,content:{job}}`다. transient 오류에서는 server job을 삭제하지 않는다.
- 프로젝트 구독은 한 소스를 한 RMS 프로젝트만 소유하도록 `(source_type, source_id)` PK로 강제한다. 구독 해제는 이미 편입된 이슈를 소급 해제하지 않는다.
