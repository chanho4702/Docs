# APM 독립 검토 의견 (BE e55948c / FE 9dfcbe8)

제 근거는 전부 소스 열람이며, 실행·재현은 하지 않았습니다. 아래에서 "실행 증거"는 호출자의 JShell 재현과 문서에 적힌 시험 결과를 뜻하고, 제가 재실행한 것이 아닙니다. 경로는 `premium/apm/` 기준입니다.

## 1. 전반 완성도 판단

| 축 | 판단 | 증거 수준 |
|---|---|---|
| 핵심 기능 | 수집·RED·트레이스·오류/DB/외부호출·SLO·합성·RUM·내보내기까지 폭은 넓습니다. | 소스 |
| 신뢰성 | 동일 본문 재전송 원자성은 갖췄습니다. CUMULATIVE 차분의 정확성(발견 2·3)이 가장 큰 구멍입니다. | 원자성은 PG IT 실행 증거(문서 기재), 차분 결함은 소스+호출자 재현 |

한 줄로 줄이면, 단일 BE·DELTA 송신·수십 서비스 조건에서는 쓸 수 있는 수준이고, 그 밖의 조건은 보증할 근거가 없습니다.

## 2. 발견별 판정

**1. 원문 노출 — 동의. 메커니즘 확정, 실노출은 조건부.**
- `trace/query/ApmRawTextPolicy.java:52`가 설정 off일 때 비관리자에게 RAW를 주는 것이 맞습니다.
- 이 클래스 javadoc의 근거("한 번 더 마스킹하면 두 번 접힌다", 20~23행)는 `export/ApmExportService.java:55~58`의 "소급 마스킹 없음, 마스킹은 멱등"과 정면으로 모순됩니다. 같은 레포가 이미 반박해 둔 셈입니다.
- 심각도는 낮춰 읽어야 합니다. 관리자가 opt-in했다가 끈 설치본에 한정되고, 노출 기간은 해당 데이터의 보존기간까지입니다. `sample_stack`이 스팬보다 오래 남는지는 확인하지 않았습니다.
- 놓친 점: MASKED 뷰도 `ApmSqlPolicy.applyToFreeText/StackTrace`(`trace/ingest/ApmSqlPolicy.java:120~148`)라서 SQL처럼 보이는 텍스트만 가립니다. 비-SQL PII는 설정과 무관하게 통과하므로 "마스킹 뷰 = 안전"도 과신입니다.
- 수정은 비관리자를 항상 MASKED로 돌리는 한 줄이라 비용이 거의 없습니다.

**2. 누적계열 충돌 — 메커니즘 확정. 범위는 과소, 심각도는 조건 누락.**
- 코드로 추적해도 재현과 같습니다. `CumulativeDeltaTracker.java:247`의 값 감소=리셋 판정 때문에 20<100은 통째 20, 110−20=90, 22<110은 통째 22가 되어 112입니다.
- 사고가 아니라 설계 오류입니다. 같은 파일 178~180행 javadoc이 "정규화 뒤 해시여야 한다"고 거꾸로 못 박고 있어, 기존 테스트가 틀린 계약을 고정하고 있을 가능성이 큽니다.
- 범위는 200/201보다 훨씬 넓습니다. `ApmMetricAllowlist.java:261~300`이 버리는 모든 속성이 충돌원입니다.
  - `http.client.request.duration`은 method를 버려 같은 호스트의 GET/POST가 충돌합니다.
  - `db.client.operation.duration`은 collection·summary 세부를 버립니다.
  - 그 밖에 `url.scheme`, 프로토콜 버전, `error.type`, `__other__`로 접힌 route 전체가 해당합니다.
- 오차는 유계가 아닙니다. 매 export마다 큰 계열의 누적값 근처가 더해져 가동 시간에 비례해 커지고, RED·알람·SLO에 그대로 전파됩니다.
- 누락된 방어: DELTA는 추적기를 우회하고(188행), `collector/install/ApmInstallGuideService.java:680~723`의 네 곳이 `TEMPORALITY_PREFERENCE=delta`를 권장합니다(어느 런타임인지는 미열람). 따라서 노출은 CUMULATIVE 송신원에 한정됩니다.
- 다만 서버가 delta를 강제할 수 없고, `MetricIngestor.java:537` 주석은 스스로 "기본 자바 에이전트가 CUMULATIVE라 다수 경로"라고 적고 있습니다. 실설치의 CUMULATIVE 비율은 미검증입니다.

**3. 역순 도착 — 메커니즘 확정, 빈도 미검증.**
- `Last`에 관측 time이 없고(305행) 감소를 리셋으로 보므로 150이 맞습니다.
- 발생 조건은 같은 인스턴스의 export가 뒤바뀌는 경우입니다. Collector 송신 큐의 다중 consumer·재시도나 BE 동시 요청이 해당합니다. stripe 잠금은 직렬화만 하고 순서는 보장하지 않습니다.
- 2번과 같은 delta 완화가 적용되므로 우선순위는 2번보다 아래입니다.
- 수정 비용은 낮습니다. 누적값은 늦은 점을 버려도 다음 점이 덮으므로 손실이 없습니다. 단 startTime을 안 주는 SDK용 안전망(더 새 시각에서 값 감소 = 리셋)은 유지해야 합니다.

**4. FE env·새로고침 — 동의, 일부 수정.**
- 확인한 위치: `errors/ApmErrorsPage.tsx:22,47`, `db/ApmDbCallsPage.tsx:20,47`, `dependencies/ApmDependenciesPage.tsx:20,45`. Explorer는 `from, to`만 꺼냅니다(`ApmErrorExplorer.tsx:38`, `ApmDbExplorer.tsx:37`, `ApmDependencyExplorer.tsx:56`).
- 수정할 점: 트레이스는 새로고침만 고쳐졌습니다(`ApmTracesPage.tsx:27~31`). `ApmTraceExplorer.tsx`에는 `env` 문자열이 아예 없어 env 미전달은 트레이스에도 남아 있을 가능성이 높습니다. 훅 내부는 미확인입니다.
- BE의 해당 엔드포인트가 env를 받는지는 미검증입니다. 받지 않으면 BE+FE 작업입니다.
- 심각도는 중간입니다. 주기 갱신(`refreshMs`)은 Explorer에 전달되므로 수동 모드에서만 새로고침이 죽습니다. 본질은 "prod만 보고 있다"는 오인입니다.

**5. 알람 — 동의, 심각도를 둘로 나눠야 합니다.**
- 확인한 위치: `alert/evaluate/ApmAlertEvaluationService.java:367~370`의 조회 후 생성, `V38__apm_p1.sql:388~402`에 UNIQUE 없음, `:281` 트랜잭션 안의 `ensureProvisioned`(324)·`pushAll`(395).
- 중복 생성은 동시 평가가 있어야 생기므로 다중 BE나 수동+스케줄 겹침에 한정된 조건부입니다. 스케줄러 락 유무는 확인하지 않았습니다.
- 트랜잭션 내 외부 I/O는 단일 BE에서도 현재 위험입니다. Zabbix가 느리면 커넥션을 붙잡고, 후반 예외 시 이벤트는 전부 롤백되는데 이미 나간 push는 남습니다.
- 두 번째 생성 경로와 종료 알람 보존 공백은 제가 읽지 않아 미검증입니다.
- 기존 결정은 유지하는 것이 맞습니다. 다만 다중 BE가 알림 재설계보다 먼저 오면 부분 유니크 인덱스만 선행하기를 권합니다.

**6. 규모 — 동의, 한 가지 추가.**
- `service/list/ApmServiceQueryService.java:179~190`과 `overview/ApmOverviewQueryService.java:164`의 전량 로딩이 맞습니다.
- 추가: FE 12개 페이지가 이 가장 무거운 overview를 드롭다운 옵션용으로 호출합니다. 4번과 6번은 경량 옵션 API 하나로 같이 풀립니다.
- dims 저장 효율은 스키마 변경 비용이 크므로, 실측에서 저장이 제약으로 확인된 뒤에 손대는 것이 맞습니다.

**7. 시험 해석 — 전면 동의.**
- 덧붙이면 521개 통과는 2번 같은 의미 오류를 잡지 못합니다. 테스트가 틀린 계약을 고정하고 있기 때문입니다.
- 문서 127행의 "초기 실행 실패 1건, 원인 미확정"도 미결로 추적해야 합니다.

## 4. 가장 과장되거나 놓친 부분

1. **2·3번에서 delta 권장 완화가 빠졌습니다.** 설치 가이드를 따른 설치본은 영향이 없으므로 "전 설치본 수치 오류"로 읽히면 과장입니다. 반대로 영향 범위를 200/201로 든 것은 과소입니다. method·DB collection·route 접힘까지 포함되고, 원인은 주석으로 못 박힌 설계 오류입니다.
2. **1번의 "보안" 표제는 조건이 좁습니다.** 관리자 opt-in 이력이 있고 보존기간 안일 때만 해당합니다. 대신 MASKED 뷰가 SQL 휴리스틱뿐이라는 점은 빠져 있습니다.
3. **4번에서 트레이스를 통째로 제외한 것은 절반만 맞습니다.** env 미전달은 남아 있을 가능성이 높고, 12개 화면이 overview를 옵션용으로 부르는 규모 측면도 빠졌습니다.
