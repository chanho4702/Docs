- 방법: 현재 구현, 최근 커밋, 기존 설계·검수·런타임 기록 대조 및 기존 테스트 선별 실행.

## 판정

**핵심 관제·트레이스 분석 기능의 범위가 넓고, 단일 BE와 검증된 계측 조합을 대상으로 통제된 파일럿을 진행할 가치가 있다. 대규모·HA 운영을 보증하거나 모든 언어에서 같은 수준의 심층 진단을 제공한다고 평가할 근거는 부족하다.**

특히 10월 6일 평가를 현재 상태로 그대로 읽으면 부정확하다. 누적 지표 정확성, 환경 필터, 지연 집계의 완전성, 알람 전송·이력 보존 등이 이후 보완됐다. 현재의 주요 과제는 기능 목록 확대보다 지원 범위와 운영 성능을 입증하고, 장애 조사 흐름을 끝까지 연결하는 것이다. 아래 등급은 완료율이나 벤치마크 점수가 아닌 정성 판단이다.

## 남아 있는 제약과 개선 우선순위

### 1. 대규모·다중 BE 지원 범위부터 확정

- `CumulativeDeltaTracker.java:29`는 JVM 로컬 checkpoint이며 교차 수신·프로세스 재시작 연속성을 보장하지 않는다고 명시한다. 실제 상태도 `ConcurrentHashMap`이다. 이는 CUMULATIVE 입력의 제약이며 모든 DELTA·GAUGE 데이터가 잘못된다는 뜻은 아니다.
- `RumRateLimiter.java:13`의 RPS·일 예산은 재기동 시 초기화되는 노드별 상태다. `LiveSpanRing`과 실시간 런타임 상태도 메모리에 있다.
- 서비스 수 하나로 규모를 정하지 말고 활성 시계열, 초당 span, 동시 관제, 보존 기간을 함께 정해야 한다. 실 수집·rollup·화면 조회·SSE를 동시에 구동하고 재시작·적체 해소까지 측정해야 지원 사양을 말할 수 있다.
- 단일 BE를 지원 범위로 정하면 범위가 명확해진다. HA를 요구한다면 시계열 소유권·checkpoint, live 데이터 전달, 공유 예산에 대한 설계·시험이 먼저 필요하다.

### 2. 큰 데이터에서 조사 화면이 느려질 경로

- `service/list/ApmServiceQueryService.java:179`는 전체 서비스를 읽고, 필터를 통과한 모든 후보의 RED·spark 등을 조립한다(`:189`). `ApmIncidentsPage.tsx`의 서비스 선택 옵션도 이 API를 사용한다.
- `trace/query/ApmTraceQueryService.java:201`은 offset의 하한만 제한하며 `LIMIT/OFFSET`을 사용한다(`:217`). 참여 서비스 필터는 `ANY(service_ids)`다(`:148`).
- 이는 이번에 응답 지연을 재현한 결과가 아니라 코드로 확인한 규모 위험이다. 경량 선택 API와 목록 서버 페이지화, 실제 데이터의 EXPLAIN·깊은 페이지 지연 측정을 우선한다. 인덱스나 keyset 도입은 측정과 조회 정렬 요구를 확인한 뒤 결정한다.

### 3. 장애 원인 분석의 연결과 깊이

- `collector/ingest/receive/ApmOtlpLogSignalHandler.java:26`은 수집기 자기 상태와 Java 확장 요청 목록 이외의 애플리케이션 로그를 저장하지 않는다. 일반 로그는 `SIGNAL_NOT_SUPPORTED` 대상으로 처리한다.
- `trace/query/ApmTraceQueryService.java:430`의 flame은 저장된 span 트리를 접어 만든다. `ApmFlameDto`의 시간도 합친 span의 지속시간·자기 시간이다. 이를 메서드 CPU 샘플링으로 설명하면 안 된다.
- 느린 서비스·DB·외부 호출 구간을 찾는 데는 유용하다. 그 뒤 실제 애플리케이션 로그로 넘어가는 연결과 코드 수준 진단은 추가 과제다. 로그 전량 저장 시스템을 곧바로 만드는 것 외에 기존 로그 시스템으로 traceId 연결을 제공하는 선택지도 있다.

### 4. 독자 알림은 기반 구현과 실제 기능을 구분

- `alert/notify/AlertChannelRegistry.java:14`는 운영 채널 빈 목록을 명시한다. production 소스에서 `implements AlertChannel` 구현도 찾지 못했다.
- outbox·재시도·채널 인터페이스 구현은 완료된 진척으로 인정한다. 다만 이것이 APM 자체 이메일·Webhook 등의 사용 가능한 채널을 뜻하지는 않는다. 현재 Zabbix 연계와 독자 알림 기반을 구분해야 한다.
- 실제 채널은 기존 사용자 결정으로 보류된 범위다. Zabbix를 유지하는 고객에는 제약이 작고, 독립 APM으로 사용하려는 경우에는 제품 기능의 공백이 된다.

### 5. Java 확장 지원 범위와 민감정보 경계

- `moveseye-otel-extension/README.md:32`의 기준은 Agent 2.31.1, JDK 17, Spring MVC/Tomcat 시험 조합이다. 다른 Agent·프레임워크는 추가 호환성 검증이 필요하다고 명시한다. 일반 OTLP 수신 범위와 진행 중 요청 확장의 지원 범위를 혼동하면 안 된다.
- `ActiveRequestListIngestor.java:147`은 상류에서 마스킹된 것으로 가정한 `currentOp`를 길이 제한만 적용해 받는다. `LiveSpanRuntimePayload.java:57`은 이를 SSE 데이터에 넣는다.
- 서버 재가림(B13-②)은 10월 22일 결정으로 보류됐다. 확장·수집기가 민감 값을 남기거나 유효한 토큰으로 가림 없는 값을 보내는 경우 추가 방어 공백이 있다. 실제 고객 정보 유출을 관측한 것은 아니다.
- 지원 조합별 설치→첫 수신→느린 요청→trace 조사→알람→복구 시나리오와 민감정보 입력 검증을 묶어 수행하는 것이 다음 제품 검증에 유용하다.

## 활용 판단

- **적합 후보:** 기존 Zabbix 인프라 관제에 애플리케이션 성능·분산 trace 관측을 추가하는 통제된 단일 BE 파일럿.
