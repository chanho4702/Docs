## T1. `[PERF] 알람 심각도 카운트 조회 7콜 → 1콜 통합`

**문제 (쉽게)**
알람 화면 상단에 "전체 24건 · 재해 1 · 심각 3 · …" 같은 배지가 있다. 이 배지 한 줄을 그리기 위해
지금은 자빅스에 **"전체 몇 건?" 1번 + "심각도 X는 몇 건?" 6번 = 총 7번** 따로 물어본다.
자빅스 DB 입장에서는 거의 똑같은 COUNT 쿼리를 연달아 7번 받는 셈이다.
더 나쁜 건, 헤더의 알림 벨이 **모든 사용자 화면에서 60초마다** 이 경로를 태운다는 것 —
접속자 10명이면 이 배지 하나 때문에 **분당 70콜**이 상시로 나간다.

**해결 방안**
- `EventService.getStatusCounts()` (`EventService.java:173`) 수정
- 문제 목록을 **1번만** 받아온 뒤, 심각도별 집계는 우리 서버의 자바 코드에서 센다 (스트림 groupingBy 한 줄 수준)
- 어차피 같은 화면에서 목록도 조회하므로, 목록 결과를 재사용하면 추가 호출 0도 가능

**기대 효과**
- 이 경로의 자빅스 호출 **1/7** (접속자 10명 기준 분당 70콜 → 10콜)
- 화면 응답도 빨라진다 — 자빅스 왕복 7번 기다리던 게 1번이 됨
- 코드 몇 줄 수정으로 끝나는 **가성비 최고 항목**. 첫 태스크로 추천

## T2. `[PERF] 알람 목록 조회를 event_problems 사본 읽기로 전환`

**문제 (쉽게)**
우리는 이미 1분마다 배치를 돌려 자빅스의 문제 목록을 **우리 PostgreSQL(`event_problems` 테이블)에 복사해 두고 있다.**
그런데 정작 알람 목록 화면은 이 사본을 안 읽고, 사용자가 화면을 열 때마다 자빅스에 처음부터 다시 물어본다.
사본을 만드는 비용(배치)은 매분 내면서, 혜택은 통계 화면만 보고 있는 상태 —
**돈은 내고 있는데 물건의 절반만 쓰는 것**과 같다.

**해결 방안**
- `EventService`의 목록 조회 경로를 자빅스 직접 호출 대신 `event_problems` DB 조회로 전환
- 참고 구현이 바로 옆에 있다: 통계 화면(`EventStatsService`)이 이미 같은 테이블을 읽는다
- 필터(심각도·호스트그룹·기간)·페이징을 SQL로 옮긴다

**기대 효과**
- **트래픽이 가장 많은 화면이 자빅스에서 완전히 분리**된다 — 사용자가 몇 명이든, 새로고침을 몇 번 누르든 자빅스는 모른다
- 응답 속도도 빨라진다 (같은 테이블을 쓰는 통계 화면이 0.16초 실측 선례)
- 사본의 신선도 = 배치 주기이므로, T4(주기 15초)와 합치면 신선도 손해도 사실상 없다

## T3. `[PERF] 알람·호스트 목록에 Redis 단기 캐시 도입`

**문제 (쉽게)**
서버 목록·호스트그룹 목록 화면은 캐시가 전혀 없어서, **접속자 수가 곧 부하 배수**다.
아침에 팀원 20명이 각자 대시보드를 띄우면 자빅스는 같은 질문을 20번 받는다.
받는 답은 20개 다 똑같은데도.

**해결 방안**
- 첫 번째 사람의 질문에 대한 답을 Redis에 30~60초 적어두고, 그 사이 다른 사람에게는 적어둔 답을 준다
- **새로 만들 것 없음** — 홈 요약(`HomeService.java:51`), 그룹 추이(`HostService.java:103`)가 이미 쓰는
  `RedisClientService` 패턴을 `getServers`(`HostService.java:1501`)·`getHostGroup`(`:1376`)에 복사
- 알람 목록은 T2(사본 전환)가 되면 캐시 불필요 — T2가 늦어질 경우의 보험으로도 유효

**기대 효과**
- 접속자 수와 자빅스 부하의 **비례 관계가 끊긴다** (사용자 N명 → TTL당 1콜)
- 신선도 손해는 최대 60초 — 실측상 아이템 99.5%가 수집 주기 30초 이상(대표 1분, dev 자빅스 11,714개 전수 — 분석 문서 §2 덧붙임)이라 체감 차이 거의 없음. 초 단위(delay 1s~) 수집이 주력인 환경만 해당 조회 TTL을 예외 조정

## T3.5. `[FEAT] 모니터링 화면 자동 새로고침 주기 설정 (APM 셀렉터 이식)`

**문제 (쉽게)**
모니터링 제품의 핵심 화면 3개 — 문제/알람 목록(`ProblemList.tsx`), 서버 모니터링(`ServerMonitoring.tsx`),
네트워크 모니터링(`NetworkMonitoring.tsx`) — 에 **주기 갱신이 아예 없다**. `staleTime: 0`이라
화면 이동·포커스 복귀 때는 다시 불러와서 살아있는 것처럼 보이지만, **띄워놓고 가만히 두면
(관제 모니터에 걸어두는 바로 그 사용 방식에서) 영영 안 바뀐다.** 새 장애가 나도 화면은 그대로다.

**해결 방안**
- APM 화면의 새로고침 셀렉터를 이식: **off / 30초 / 60초 / 5분** (`constants/apm.ts`의 `APM_REFRESH_MS` 패턴)
- `useDmoveQuery`가 `refetchInterval`을 그대로 통과시키므로 화면에서 선택값만 꽂으면 됨
- 선택값은 localStorage에 저장(사용자별 기억), 공용 셀렉터 컴포넌트로 3화면 적용
- 🔴 **T1(카운트 1콜화)·T3(Redis 캐시)와 같은 마일스톤으로 묶는다** — 캐시 없이 폴링만 켜면
  접속자 수 × 주기만큼 자빅스를 때린다(문제 목록은 카운트 7콜 동반). 캐시가 앞에 있으면
  사용자 100명이 30초 폴링을 켜도 자빅스는 TTL당 1콜
- T5(SSE) 도입 후에는 이 셀렉터를 **폴백으로 강등** — SSE 연결이 끊긴 환경에서만 폴링

**기대 효과**
- "띄워놓으면 안 바뀌는 화면" 문제를 SSE(3~5일)보다 먼저 하루 만에 해소하는 quick win
- 사용자 가시적 개선 — 부하 절감 태스크 사이에서 체감되는 항목

## T4. `[PERF] 이벤트 동기화 증분화 및 주기 단축 (1분 → 15초)`

**문제 (쉽게)**
이벤트 동기화 배치(`EventSyncService.java:83`)가 **1분마다 "최근 30일 문제 전부 주세요"**라고 묻는다.
1분 사이에 실제로 바뀐 건 많아야 몇 건인데, 매번 30일치 전체(limit 10000)를 다시 받는다.
매일 아침 신문을 사면서 지난 한 달치를 전부 다시 사는 격이다.
그리고 이 전량 조회가 무거워서 주기를 1분보다 짧게 못 돌린다 → **알람이 화면에 뜨기까지 최대 1분**이 걸리는 원인이기도 하다.

**해결 방안**
- "지난 동기화 이후 새로 생기거나 바뀐 것만 주세요"로 변경 (마지막 시각/eventid 기준 증분)
- 놓침 방지용 **전체 보정(reconcile)은 낮은 빈도로 별도 유지** (예: 시간당 1회 — 기존 reconcile 로직 재활용)
- 증분 쿼리는 아주 가벼우므로 주기를 1분 → **10~15초**로 단축

**기대 효과**
- 최대 상시 부하원의 쿼리 범위가 30일 → 15초로 — **부하가 줄면서**
- 알람이 우리 DB에 도착하는 지연이 최대 60초 → 15초로 — **신선도는 올라간다**
- "부하 절감과 신선도가 충돌한다"는 우려를 정면으로 뒤집는 항목. T5(SSE)의 품질을 결정하는 선행 작업

## T5. `[FEAT] SSE 알람 실시간 스트림 (벨·문제목록·홈 위젯)`

**문제 (쉽게)**

- 알림 벨은 **사용자마다 각자** 60초 폴링 — 접속자 수만큼 중복 요청이고, 그때마다 T1의 카운트 7콜이 딸려간다
- 새 장애가 나도 사용자는 최대 1분+α 뒤에야 안다

**해결 방안**
- 동기화 배치(T4)가 끝날 때마다 변경분을 **서버가 접속자 전원에게 밀어주는(push)** SSE 스트림 1개 신설
- BE: `SseEmitter` 허브 — APM Live 스트림이 이미 같은 구조로 돌고 있어 선례 있음
- FE: `useApmLive.ts`(305줄, EventSource+쿠키 인증+재연결+병합 완비)가 그대로 템플릿.
  알림 벨·문제 목록·홈 알람 위젯이 구독하고 기존 폴링 제거
- 웹소켓(양방향)은 불필요 — 알림은 단방향이라 SSE로 충분하고, LB 설정 부담도 적다

**기대 효과**
- **부하**: 사용자별 폴링 소멸 — "사용자 수 × 60초 폴링"이 "배치 1회 계산 → 전원 배달"로 바뀜
- **신선도**: 새 알람 발생 → 화면 반영이 수동 새로고침/최대 1분 → **몇 초 이내**
- 모니터링 제품의 체감 완성도를 올리는 사용자 가시적 개선 (부하 절감 태스크 중 유일하게 "보이는" 항목)

## T6. `[PERF] ZabbixClient 커넥션 풀 + 호출 계측 도입`

**문제 (쉽게)**
자빅스로 나가는 모든 호출이 `ZabbixClient.callRaw()` 한 곳을 지나는데, 이 수도꼭지에 **밸브도 계량기도 없다**:
- 호출마다 연결을 새로 만든다 (전화할 때마다 전화선을 새로 깔고 철거하는 격)
- 동시 호출 상한이 없다 — 사용자가 몰리면 Tomcat 스레드 수만큼 그대로 자빅스로 쏟아진다
- 호출량 기록이 없다 — 고객사가 "자빅스 느려진 거 무브즈아이 탓 아니냐"고 하면 **반박할 데이터가 없다**

**해결 방안** (전부 우리 코드, `ZabbixClient.java:41-52` 한 파일)
1. `SimpleClientHttpRequestFactory` → `HttpComponentsClientHttpRequestFactory`(Apache HttpClient 풀) 교체.
   `maxTotal` 설정값이 곧 **동시 호출 상한** 역할을 겸한다 (풀이 차면 우리 쪽에서 대기)
2. `callRaw()`에 메서드별 호출 수·소요시간 계측 (로그 또는 Micrometer)
3. **순서 주의**: 계측을 먼저 배포해 평소 동시 호출 수를 실측 → 그 수치를 보고 상한값 결정
   (M1 태스크들이 끝나면 호출량 자체가 줄어 상한을 낮게 잡아도 화면이 안 느려진다)

**기대 효과**
- "우리 제품이 자빅스에 줄 수 있는 최대 부하 = 동시 N콜"이라는 **문서·계약에 적을 수 있는 숫자**가 생긴다
- 분쟁 시 "지난 1시간 호출 내역" 로그로 수치 방어 가능
- 연결 재사용으로 자빅스 서버의 연결 수립 비용도 감소

## T7. `[PERF] 긴 기간 차트 trends 전환을 전 메트릭으로 확산`

**문제 (쉽게)**
자빅스 DB에는 같은 데이터가 두 벌 있다: 원시값 전부(`history`, 괴물 크기)와 시간당 요약(`trends`, 1/60 크기).
일주일짜리 차트는 화면에 점 몇백 개만 찍으므로 요약 테이블이면 충분한데,
현재 이 분기가 **CPU에만** 구현돼 있다 (`CpuService.java:134` — 1시간 초과 시 trends로 전환).
메모리·디스크·네트워크·인터페이스 차트는 기간이 아무리 길어도 괴물 테이블을 긁는다.

**해결 방안**
- `CpuService.java:134`의 기간 기반 RAW/HOURLY_TREND 스위칭 패턴을
  `MemoryService`·`DiskService`·`NetworkService`·`InterfaceService`로 복사
- 모델 레벨 분기(`Rollup.RAW`/`HOURLY_TREND`)와 trend 어댑터는 이미 있으므로 **소비자 쪽 분기만 추가**

**기대 효과**
- 긴 기간 차트의 자빅스 쿼리가 원시 테이블 → 1/60 요약 테이블로
- 부수 효과로 차트 로딩 속도도 개선 (받는 데이터량 자체가 급감)

## T8. `[FIX] history.get 무제한 조회 상한 + item.get N+1 제거`

**문제 (쉽게)**
인터페이스 상세 화면(`HostService.getInterfaceDetails()`, `HostService.java:1862`)이 두 가지를 동시에 저지른다:
1. 아이템 키 9개를 **9번의 개별 `item.get`으로** 찾는다 (한 번에 물으면 될 것을)
2. 찾은 아이템들의 원시값을 **limit 없이** 조회 — 사용자가 기간을 한 달로 잡으면
   괴물 테이블에서 한 달치를 통째로 긁는 SQL이 된다. **단건으로는 자빅스 DB를 제일 아프게 할 수 있는 호출**

**해결 방안**
- `ZabbixItemServiceImpl.getByListKey()`를 1콜화 (`searchByAny: true` 또는 `filter.key_` 배열)
- `history.get`에 limit 상한 상수 도입 — 초과가 예상되는 긴 기간은 trends로 강등(T7과 연계)
- 같은 문제가 있는 `ItemsService.java:103`도 함께 적용

**기대 효과**
- "사용자의 기간 선택 하나로 자빅스 DB가 휘청이는" 최악 시나리오가 **구조적으로 불가능**해진다 (안전핀)
- 화면 1회당 item.get 9콜 → 1콜

## T9. `[DOCS] 자빅스 성능 책임 경계 문구를 설치 가이드에 명시`

**문제 (쉽게)**
자빅스 DB가 느려지는 원인에는 우리가 통제할 수 없는 것들이 있다 —
보존 기간(housekeeping)을 과하게 잡아 테이블이 비대해진 경우, DB 서버 사양 부족, 초 단위 수집 주기 남용 등.
이 경계가 문서에 없으면, 고객사 자빅스가 느려질 때마다 **원인과 무관하게 우리가 소명 책임**을 지게 된다.

**해결 방안**
설치 가이드·운영 문서(`moveseye-docs`)에 한 섹션 추가:
- 본 제품은 Zabbix API만 사용하며 DB에 직접 접근하지 않는다
- API 호출은 동시 최대 N건으로 제한되며(T6의 숫자), 호출량은 로그로 확인 가능하다
- `history`/`trends` 보존 기간, DB 서버 사양, 수집 주기는 Zabbix 운영(고객) 영역이다
- 수집 주기는 "1분 고정"으로 쓰지 않는다 — **아이템별 설정(1초~1일, 공식 템플릿 기본 1분)**으로 명시 (실측 근거: 분석 문서 §2 덧붙임)
- 권장 문구 초안은 분석 문서 §7에 있음

**기대 효과**
- 영업·계약·장애 대응에서 **"제품 문제 vs 자빅스 운영 문제"를 가르는 기준선**이 생긴다
- T6의 계측 데이터와 결합하면 분쟁을 데이터로 종결할 수 있다

## T10. `[FEAT] 초 단위 라이브 메트릭 관제 (Zabbix Connector 수신 + SSE)` — 백로그

> **착수 조건**: 고객이 초 단위 실시간 관제(예: 핵심 회선 트래픽)를 실제로 요구할 때.
> 착수 전 명세받을 숫자 두 개 — ① 진짜 필요한 주기(1s? 5s? 대부분 5~10초로 충족) ② 대상 아이템 수.

**문제 (쉽게)**
1초 실시간을 폴링으로 하면 시청자마다 1초에 한 번 자빅스를 두드려야 한다 — 이 계획이 없애려는
패턴의 극단이라 성립하지 않는다. 방향을 뒤집어야 한다: **우리가 묻는 게 아니라 자빅스가 보내게** 한다.

**해결 방안**
```
[에이전트들] → 평소처럼 → [자빅스 서버] → Connector 푸시(HTTP NDJSON) → [우리 BE] → SSE → [화면 전원]
```
- Zabbix 7.0 공식 스트리밍 기능 **Connector** 사용 — 자빅스 서버가 값을 저장하는 순간 사본을
  우리 BE 수신 엔드포인트로 푸시. **에이전트 무변경**, 자빅스 서버 설정만
  (`StartConnectors` + 프론트엔드 Connector 등록 + **태그 필터로 대상 아이템 한정**)
- BE: 수신 엔드포인트 신설 + T5의 SSE 허브로 중계 (APM Live 스트림이 구현 선례)
- 폴백(고객이 서버 설정 변경 불가 시): BE 단일 라이브 폴러가 1초마다 `item.get` lastvalue(value cache
  메모리 조회라 history 안 긁음) → SSE. 사용자별 폴링 금지 — 시청자 수 무관 초당 1콜 고정
- 제품화: "핵심 아이템 N개 선택 실시간 관제" 기능으로 부하 상한을 설계에 내장
- 공식 근거: https://www.zabbix.com/documentation/7.0/en/manual/config/export/streaming

**기대 효과**
- 초 단위 요구를 **자빅스 조회 부하 0**으로 충족 (자빅스는 우리 서버 한 곳에만 보냄)
- 단, 1초 수집의 DB 쓰기 60배는 자빅스(고객) 쪽 비용 — 소수 아이템 한정+history 보존 단축이 전제이며,
  이 경계는 T9 문구에 포함시킨다
