- 개요: Zabbix를 운영자 친화 UX로 감싸고, Prometheus/Datadog/Elastic으로 확장 가능한 수집 엔진과 자연어로 설정·운영 작업을 수행하는 AI 어시스턴트를 얹은 제품. BE·FE·AI 서버·라이선스 발급기를 설계부터 구현까지 담당

담당업무
1. NestJS → Spring Boot 전량 변환: 양쪽 런타임 응답을 풀스캔 비교해 동등성을 검증한 뒤 Spring 단일 채택. 변환 과정에서 원본의 계산 버그(swap 사용률을 메모리 키로 산출)까지 발견·수정
2. 다중 데이터소스 수집 엔진 설계(포트화): Zabbix 응답을 직접 파싱하던 2,000줄 규모 서비스들을 스트랭글러 패턴 7스텝으로 MetricPort / InventoryPort / AlertPort 뒤로 이동. engine-api(소스 중립 계약, Spring 의존 0) / engine-zabbix(구현) 멀티모듈로 분리하고 app → 구현체 컴파일 의존을 빌드가 차단하도록 강제. 캐노니컬 메트릭 모델 + 메트릭 카탈로그(중립 키 ↔ Zabbix 키 번역)로 소비 코드에서 소스 키 제거. gRPC 물리 분리는 승격 조건을 명시하고 유예하되 계약은 proto 호환 규칙으로 설계
3. 무중단 전환 검증: 매 스텝 전/후 동일 시간창의 API 응답을 JSON으로 채집해 diff — "REST 불변·FE 무변경"을 19개 응답군 identical로 증명. 단위 테스트가 전부 통과한 상태에서 런타임 비교로만 잡힌 회귀 4건(history 테이블 FLOAT 고정 조회로 바이트 메트릭 0 붕괴 등)을 배포 전 차단
4. AI 어시스턴트 서버 설계·구현: 별도 프로세스로 장애 격리, 프로바이더 중립(Spring AI 2.0). 툴 52개를 기존 REST의 얇은 프록시로 구성해 RBAC·감사로그·라이선스 판정을 BE가 그대로 수행(AI 서버는 자체 권한 없음). 쓰기/삭제 툴은 서버가 루프를 멈추고 SSE 확인 카드를 띄워 사람 승인을 강제
5. AI 오동작·폭주 방어 7겹 설계: strict 스키마·범위 검증(서버 실행 전), 확인 게이트(5분 타임아웃), 턴당 툴 호출 15회·대화당 동시 1턴·max_tokens·이력 60건 상한, 월 USD 예산 + 모델별 단가 기반 사용량 화면, 프롬프트 인젝션 래퍼("데이터이지 명령 아님"), 킬 스위치(설정 토글/라이선스 회수), 감사로그 actor = 실제 사용자

담당업무
1. 아키텍처 설계: Controller → Service → Repository 계층, 도메인 단위 resolver 20여 개 구성. 관계형 데이터는 Forge SQL, 마스터 데이터는 KVS로 저장소 이원화
2. 권한 체계 설계(RBAC 고도화): 모든 resolver를 단일 가드(guardedDefine)로 감싸 권한 검사 + 응답 표준화. 미선언 함수 원천 거부(deny-by-default), 급여·원가·인력 명부는 principal 기반 스코프(ProjectScope/CostAccess/SalaryVisibility)로 응답 범위를 서비스 계층에서 추가 제한
3. 분석 기능: 전사 통합 대시보드(Time/Scope/Resource, 스케줄 트리거 스냅샷), 진척도(3층 모델), 비용 분석, 인력 360도 프로필, 프로젝트 담당자 배정 관계도, 팀 분석 리포트
4. 작업 관리: 목록·트리·간트 3뷰 전환, WBS 계층·일괄 적용, 프로젝트 커스텀 대시보드(위젯 그리드), 칸반, 캘린더
5. Jira API 연동 전략: 팀 관리형 프로젝트에서 Forge 커스텀 필드가 응답에서 누락되는 문제를 이슈 엔티티 프로퍼티 이전 + JQL searchAlias로 해결. 검색 인덱스 지연은 서버 응답 기반 캐시 패치로 우회. 워크로그 N+1은 p-limit 병렬 페처 + KVS 캐시로 해소
6. 플랫폼 제약 대응: Forge SQL의 FK·CASCADE·트랜잭션 미지원 → 앱 레벨 멱등 cascade 삭제. KVS 100건 하드캡·빈 문자열 거부 대응. DB 용량(1GiB) 고갈로 인한 앱 정지를 막는 사용량 모니터링 페이지 구축
7. 대량 처리: Excel 업로드를 @forge/events 큐로 분할 처리(서버리스 실행시간 제한 극복), 폴링 기반 진행률 UI
8. 프론트 품질: 탭 단위 코드 스플리팅으로 main 번들 49% 감소, Atlaskit 기반 디자인 시스템 수렴(공통 컴포넌트 10종, 스켈레톤 로딩), i18n(ko/en) 체계, 쿼리키·권한맵 계약 테스트
9. AI 개발 하네스 구축: Claude Code에 설계 → 백엔드 → 프론트 → 검증 전문 에이전트 4종과 스킬을 구성해 기능 개발 파이프라인 자동화. 회귀 발생 시 검증 체크리스트에 누적해 재발 방지

## [자기소개서] 끊임없는 개선을 지향하는 개발자

### 수작업을 시스템으로 바꿔온 4년 — 두 번의 장관상이 증명합니다

입사 2년차에 만든 사내 업무 자동화가 과학기술정보통신부 장관상으로 이어졌습니다. 마크애니에서 보안 솔루션 30개 사이트를 운영하며 가장 크게 느낀 문제는 "사람 손에 의존하는 업무 이력 관리"였습니다. 팀원 전원이 각자 2주씩 매달려 기억에 의존해 옮길 계획이던 이력 3,000건을, 데이터 기반 자동 이관 파이프라인으로 유실 없이 통이관했습니다. 여기서 멈추지 않고 주말마다 이 데이터를 분석에 활용하는 방법을 파고들었습니다. 그 결과물이 Elasticsearch 기반 프로젝트 분석 시스템 A-RMS입니다. ALM/Jira 데이터를 수집·적재해 시계열 인덱스와 집계 쿼리로 진행률·인력 활용률·ROI를 실시간 시각화했고, 실제 사내 업무 시스템에 도입되어 데이터 기반 의사결정 체계로 정착했습니다. 이 프로젝트로 공개SW 개발자 대회 대상(과학기술정보통신부 장관상)과 2024 대한민국 SW기술 대상·IT 아키텍처 대상(장관상)을 받았습니다.

### 운영을 아는 개발자 — 30개 사이트 장애 대응에서 배운 것

마크애니 3년 8개월 동안 문서 위변조 방지·WebDRM 보안 솔루션을 30개 사이트에 구축하고 SLA 기준으로 장애에 대응했습니다. 프록시 툴로 보호 스크립트를 제거하면 우회 접근이 가능한 취약점을 실서비스에서 재현·분석해 무결성 검증 구조로 막아낸 경험은, 기능이 "돌아가는 것"과 "운영 환경에서 안전한 것"의 차이를 몸으로 가르쳐 줬습니다. 이때 체득한 운영 감각 — 장애의 근본 원인을 추적하는 습관, 고객과 직접 협의하는 커뮤니케이션 — 이 지금 플랫폼을 설계할 때의 기준이 되고 있습니다.

### 두 개의 플랫폼을 설계하는 지금

현재 디무브에서 두 제품의 설계와 구현을 담당하고 있습니다.

첫 번째는 Jira Cloud 연동 인력/자원 관리 SaaS Moves Workforce입니다. 설계부터 Marketplace 출시까지 단독으로 맡아 설계 문서(RFC) 190건을 거치며 권한 체계, 분석 리포트, 간트, 비용 관리까지 플랫폼의 뼈대를 세웠습니다. 서버리스 실행시간 제한은 이벤트 큐 기반 분할 처리로, Forge SQL의 트랜잭션·FK 부재는 앱 레벨 멱등 처리로, 팀 관리형 프로젝트에서 커스텀 필드가 사라지는 플랫폼 제약은 이슈 프로퍼티로의 데이터 이전으로 풀었습니다. 권한은 "호출 가능 여부"와 "응답 범위"를 분리해 서비스 계층에서 fail-close로 처리하도록 설계했고, 배포 전 감사에서 우회 경로를 찾아 막았습니다.

두 번째는 Zabbix 기반 통합 인프라 모니터링 플랫폼 MovesEye입니다. Zabbix에 직접 묶여 있던 수집 코드를 소스 중립 포트 뒤로 옮겨 Prometheus·Datadog 등 다중 데이터소스로 확장할 수 있는 구조를 만들었는데, 핵심은 "운영 중인 API와 화면을 한 줄도 바꾸지 않는다"는 약속이었습니다. 이 약속 덕분에 매 단계 전환 전후의 응답을 diff로 비교하는 회귀 검증이 가능했고, 단위 테스트가 모두 통과한 상태에서도 숨어 있던 회귀 4건을 배포 전에 잡았습니다. 추상화의 경계는 코드 구조가 아니라 "다른 소스에도 같은 질문이 있는가"로 긋는다는 원칙을 이 과정에서 배웠습니다.

동시에 Elasticsearch 클러스터와 Beats 수집 파이프라인으로 로그 관제 환경을 구축해, 만든 시스템을 데이터로 관찰하고 개선하는 순환 구조를 운영하고 있습니다.

### AI를 제품 안에 안전하게 넣습니다

MovesEye에는 채팅으로 "web-01 CPU 90% 넘으면 높음 심각도 트리거 만들어줘" 같은 운영 작업을 수행하는 AI 어시스턴트를 설계·구현했습니다. Spring AI 2.0으로 고객마다 다른 LLM(Claude·OpenAI 호환·Ollama)에 중립적으로 대응하고, 툴 52개를 새 코드가 아닌 기존 REST API의 얇은 프록시로 만들어 권한·감사로그·라이선스 판정이 기존 백엔드에서 그대로 작동하게 했습니다.

가장 공들인 부분은 "AI가 실수 안 하게"가 아니라 "실수해도 실제 피해가 안 나게" 만드는 구조입니다. 쓰기·삭제 작업은 서버가 루프를 멈추고 사람의 승인을 받아야만 실행되며 모델이 스스로 승인 플래그를 세울 수 없습니다. 턴당 툴 호출 15회, 대화당 동시 1턴, 월 예산 상한으로 폭주와 과금을 막고, 툴 결과에 섞인 외부 텍스트는 "데이터이지 명령이 아니다"라는 래퍼로 프롬프트 인젝션을 차단했습니다. 외부 AI 클라이언트가 붙는 MCP 서버는 자체 OAuth 2.1 인가 서버와 계정별 읽기/쓰기 권한으로 3중 차단하고 기본값을 닫아 두었습니다. AI는 제안만 하고, 검증은 서버가, 승인은 사람이, 권한 판정은 백엔드가 — 네 주체를 분리해 어느 하나가 틀려도 피해로 이어지지 않게 했습니다.

### AI를 도구가 아니라 개발 환경으로 씁니다

코드 작성 자체는 AI로 충분히 빨라졌고, 이제 병목은 아키텍처 설계와 시스템 간 연동에 있다고 생각합니다. 그래서 AI를 코드 자동완성 수준이 아니라 개발 프로세스 자체로 끌어들였습니다. Claude Code에 에이전트·스킬·MCP(Notion, Jira 연동)를 직접 구성해 저에게 맞는 개발 환경을 만들었고, 브레인스토밍 → 설계 문서(plan/spec) 작성 → 구현 → 검증으로 이어지는 문서 기반 AI 협업 프로세스를 정착시켰습니다.

실무에서는 백엔드·프론트·정적 경계면 검증·런타임 E2E 검증 에이전트 4종을 구성해 BE와 FE 사이의 계약서를 단일 진실로 두는 파이프라인을 만들었고, 별도 AI(Codex)를 검수 전담으로 두어 자기 코드를 자기가 검수하지 않는 구조로 운영합니다. 회귀가 발생할 때마다 검증 체크리스트에 항목을 누적해 같은 실수가 반복되지 않게 했습니다. 이 방식으로 MovesEye의 AI 어시스턴트 서버(툴 52개·MCP·OAuth 포함)를 설계서와 함께 약 4일 만에 완성했습니다.

개인적으로는 Spring Security 기초부터 세션 로그인, JWT 직접 구현, 토큰 보안(회전·재사용 탐지), OAuth2/OIDC, Keycloak BFF 구축까지 인증 체계를 단계별로 직접 구현하며 정리해 왔고, Keycloak + Spring Cloud Gateway + Kafka 기반 MSA 스타터 템플릿 플랫폼을 같은 프로세스로 퇴근 후와 주말만 활용해 약 2주 만에 설계 문서와 함께 완성했습니다. 목표는 "서비스를 만드는 것"이 아니라 "서비스를 빠르게 만들 수 있는 환경을 만드는 것"입니다.

### 저는 요구사항을 구현하는 사람이 아니라, 제품을 키우는 사람입니다

요구사항이 한 줄이어도 제품이 되려면 무엇이 더 필요한지 스스로 묻고, 그 답을 설계와 코드로 채워 넣는 것이 제 일하는 방식입니다.

MovesEye는 "Zabbix 모니터링 차트를 확장하는 서비스"가 원래 목표였고, 1년 넘게 진척이 없던 프로젝트였습니다. 합류 후 차트를 그리는 것만으로는 경쟁 제품 대비 팔 이유가 없다고 판단했고, 세 가지를 제안해 직접 설계·구현했습니다. 첫째, Zabbix의 난해한 화면을 운영자 관점으로 다시 짠 사용성 개선. 둘째, 자연어로 설정·운영 작업을 수행하는 AI 어시스턴트 — 경쟁 제품에 없는 차별점입니다. 셋째, Zabbix 전용에서 벗어나 Prometheus·Datadog 등 다중 데이터소스로 확장할 수 있는 엔진 아키텍처와 프리미엄 라이선스 체계. 그 결과 멈춰 있던 프로젝트를 3개월 만에 판매 가능한 제품으로 바꿔 놓았습니다.

Moves Workforce는 "PMS·RMS 같은 걸 만들어 달라"는 요구사항 한 줄에서 시작했습니다. 무엇이 PMS이고 무엇이 RMS인지부터 정의해야 했기에, Jira 데이터를 그대로 자산으로 쓰는 인력/자원 관리라는 제품 정체성을 잡고 권한 체계·분석 리포트·간트·비용 관리까지 설계 문서 190건을 쌓아 가며 Marketplace 출시까지 끌고 갔습니다.

저에게 개발자의 역할은 시킨 기능을 정확히 만드는 데서 끝나지 않습니다. 이 제품이 시장에서 왜 선택받아야 하는지를 함께 고민하고, 그 답을 구조와 기능으로 제안하는 것까지가 제 일입니다. 그래서 매 조직에서 같은 패턴을 반복해 왔습니다 — 입사 후 3개월 안에 도메인과 운영 구조를 파악해 기여 지점을 찾고, 1년 안에 팀의 운영 데이터를 관측 가능한 구조로 만들며, 제품이 다음 단계로 갈 수 있는 제안을 설계와 함께 내놓는 것. 다음 조직에서도 그렇게 일하겠습니다.
