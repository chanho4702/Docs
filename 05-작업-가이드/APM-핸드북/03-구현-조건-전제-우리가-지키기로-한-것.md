## 3. 구현 조건·전제 — 우리가 지키기로 한 것

> 이 장을 읽으면: ① 수집 경로·설치 부담·응답 규약처럼 **한 번 정하면 되돌리기 어려운 전제**가 무엇이고 왜 그렇게 정했는지, ② 라이선스·권한·보존·용량·보안의 **숫자**가 어디에 박혀 있는지, ③ 이 프로젝트가 일부러 하지 않는 것과 개발 규약을 알게 된다.

### 3.1 수집기는 OTel 단일

| | |
|---|---|
| **무엇을** | 앱 → Collector → BE, 이 한 길만. 자체 SDK·자체 에이전트·자체 프로토콜을 만들지 않고, 상용 APM 에이전트 호환도 하지 않는다. 앱 → BE **직송도 불허**(Q12) |
| **어떻게** | 우리 산출물은 **Collector 설정 템플릿**(`src/main/resources/apm/collector-template.yaml`, `validate` 통과본)과 그것을 채워 주는 생성기(`POST /apm/collector-config`), 그리고 검증 화면(수집기 탭)뿐. Collector 소스 수정·포크 없음 |
| **왜** | v1 A안(에이전트 직송)을 버린 이유 — Java SDK는 protobuf만 보내 BE에 의존이 생기고, head 샘플링만 가능해 **오류 트레이스를 놓친다**. Collector가 JSON 변환·tail 샘플링·마스킹·디스크 큐·재시도를 **한 자리에서** 해결한다 |
| **조건·전제** | 버전 고정 `otelcol-contrib 0.159.0` · `opentelemetry-javaagent 2.31.1`(코드 상수 `ApmInstallVersions` — 프로퍼티가 아니다, 실측한 조합이라서). **게이트웨이 1대**: tail 샘플링은 한 트레이스의 모든 스팬이 같은 Collector에 와야 한다. HA는 active-standby만(전환 중 유실 허용), active-active는 `loadbalancing` 2계층으로 승격 항목 |
| **함정·교훈** | 상용("에이전트 하나")보다 **설치 단계가 하나 많다** — yaml 생성기·서비스 등록 스크립트·60초 검증으로 상쇄한다. 앱은 MovesEye 주소를 몰라도 된다(`localhost:4317`만) |

### 3.2 Collector ↔ BE 응답 규약 — 500 금지

| | |
|---|---|
| **무엇을** | OTLP 수신 컨트롤러(`ApmOtlpController`, `/apm/otlp/v1/{metrics,traces,logs}`)가 낼 수 있는 상태는 **200 `{}` / 400·415(형식) / 401(토큰) / 403(용도·라이선스) / 413(상한) / 503(적재 예외·DB 장애)** 뿐. 판정 순서 자체가 계약: `415 → 크기 → gzip 스트리밍 해제 → 401 → 403(용도) → 403(기능) → 400(JSON) → dedup 판정 → ingest → 영수증 → 200` |
| **어떻게** | 전역 `GlobalExceptionHandler`에 닿지 않게 컨트롤러 안에서 전부 잡는다. `consumes=`도 쓰지 않는다(그 예외는 핸들러 선정 **전**에 나서 전역 catch-all이 500으로 만든다) |
| **왜** | ✅ R11 실측: exporter가 **재시도하는 코드는 429·502·503·504뿐**. 500은 Permanent error — 60초에 31배치가 통째로 사라졌다. "적재 실패=500이면 재시도한다"는 기존 AI 모니터링 주석은 틀렸었다 |
| **조건·전제** | 401/403/413도 즉시 폐기다. 그래서 **라이선스 만료(403) = 그 순간부터 손실**(프리미엄 P17과 일치) — D-14/7/1 배너·"수집기 중지·토큰 회수" 버튼·FAQ가 대신 한다. AI 계정 모니터링의 같은 자리는 **503**(재시도로 버팀)이며 의도된 차이 — 두 컨트롤러를 "통일"하지 말 것 |
| **함정·교훈** | 형식·크기를 인증보다 먼저(토큰 모르는 상대에게 파싱 비용을 안 든다) · **gzip은 스트리밍으로 풀며 상한 초과 순간 중단**(압축률 5~9배라 다 풀고 재면 공격 표면) · **dedup 판정은 적재 앞, 영수증 기록은 적재 뒤**(뒤집으면 503 후 재전송이 영수증에 걸려 조용히 버려진다) · 트레이스·로그를 아직 안 받을 때도 **404가 아니라 200 + `SIGNAL_NOT_SUPPORTED`**(404는 영구 실패로 로그를 뒤덮어 메트릭 문제를 가린다) |

**더 보기**: 응답 코드 표·판정 순서 = `contract_apm.md` §2.4(`ApmOtlpController`) · R11 실측(500 = 60초 31배치 손실) = `verification/r1_apm-collector-roundtrip.md` §3 · 8MB 스트리밍 상한 = `reviews/review_apm-p1_codex.md` 🔴1 · 만료 403 정책 = `designs/devdesign_apm.md` §4.1(코덱스 A6) · AI 모니터링과의 의도된 차이 = `analysis/apm-p1-logic-analysis.md` §12 A9.

### 3.3 프리미엄 라이선스 게이트

| | |
|---|---|
| **무엇을** | APM 전부가 `Feature.APM`(PREMIUM). 조회·관리 EP는 `@RequiresFeature(APM)`(인터셉터), 수신 EP는 `@LicenseExempt` + 컨트롤러가 `LicenseProvider.current().allows(APM)`를 **직접** 판정해 403 |
| **어떻게** | ArchUnit `LicenseArchitectureTest` A1~A5가 강제한다: A1 **premium 밖 코드는 premium에 의존하지 않는다**, A2 premium 컨트롤러는 `@RequiresFeature` 필수, A3 premium은 app 리포지토리를 참조하지 않는다, A5 라이선스 면제 허용목록. 수신·RUM·웹훅 컨트롤러는 `MACHINE_CLIENT_CLASSES`에 FQN이 박혀 있다("MACHINE"은 실행 환경이 아니라 **세션 화면이 아닌 exporter의 실제 HTTP 계약**이라는 뜻) |
| **왜** | 프리미엄을 들어낸 빌드가 성립해야 한다(분리 배포·모듈 승격). A1이 실제로 빨갛게 뜬 사례가 리포트 편입([6.5절](10-%EB%8B%A8%EA%B3%84%EB%B3%84-%EC%83%81%EC%84%B8-P3-SLO-%ED%95%A9%EC%84%B1-%EA%B0%90%EC%8B%9C-%EB%A9%94%EC%8B%9C%EC%A7%95-%EB%B0%B0%EC%B9%98-%EB%A6%AC%ED%8F%AC%ED%8A%B8-AI-%EC%84%A4%EC%B9%98-%EC%B6%9C%EC%B2%98.md)) — 의존을 `ManagedReportSource` SPI로 뒤집었다 |
| **조건·전제** | 만료 중에도 **배치 4종은 돈다**(`apm_partition_maintain`·`apm_rollup`·`apm_retention`·`apm_trace_rollup` — `requiresActiveLicense()=false`). 가르는 기준은 "수집 소스에 나가는가"이며 셋 다 우리 DB만 읽고 쓴다. 롤업이 true였던 것이 결함이었다 — 보존은 계속 돌아 7일 지난 1m을 DROP하는데 롤업만 멈추면 그 구간의 5m/1h가 **영영 빈다**. 알람 평가는 true(프리미엄 동작 그 자체) |
| **함정·교훈** | SSE 스트림은 연결 시점에만 라이선스를 본다 → 열린 연결은 만료 뒤에도 최대 `stream-timeout-seconds`(600)까지 흐른다. 승인된 노출 창 10분 |

### 3.4 권한 축 — DMOVE 권한 `applicationMonitoring / apm`

| | |
|---|---|
| **무엇을** | 역할 편집 화면의 체크박스 한 줄: 모듈 `applicationMonitoring`, 기능 `apm`, 칸은 **view**(조회 36 EP + P3 18)·**edit**(관리 26 EP + P3 8). 원문(SQL 원문·스택트레이스) 열람만 **관리자 역할 축**(`canViewRawText`, ADMIN∪SUPER_ADMIN). 리포트 관리는 편입의 대가로 **관리자 축**(`ReportAdminAccess`) |
| **어떻게** | BE `ApmAccessChecker.requireRead/requireEdit`(@Component, 컨트롤러 첫 줄) → `DmovePermissionChecker.has()` 한 곳에서 관리자 우회. FE `useApmPermissions().{canView, canEdit}` 단일 진입점, 사이드바·검색 13·설정 2·라우트 15는 `view`, 수집기·알람 규칙 화면은 **조회부터** `edit`. V48이 기존 역할을 `view=true·edit=false`로 백필 |
| **왜** | 세 단계 사연: ① P1부터 조회 EP에 판정이 **없었다**(설계 🅞가 코드에 없어 일반 USER가 트레이스·스택·SQL을 읽을 수 있었다) ② 09-02 ADMIN 일괄 잠금(우리 역할 축엔 "운영자"가 없다) ③ 09-03 "관리자가 켜고 끌 수 없는 잠금"이라 하루 만에 권한 옵션으로 전환 — **코드가 아니라 데이터로 답한다** |
| **조건·전제** | 🔴 view/edit을 가르는 축은 HTTP 메서드가 아니라 **"관리 화면의 데이터인가"** — 토큰 목록·설정 GET·설치 가이드는 `edit`, `POST /traces/compare`는 `view`. `edit`은 `view`를 함축하지 않는다. 🔴 배포 순서 **BE 먼저**(코드+V48) — FE `grantAll`은 BE가 내려준 키만 채우므로 FE만 먼저 올리면 관리자에게도 메뉴가 사라진다 |
| **함정·교훈** | 🔴 **V48은 V27 복제가 아니다**: `dmove_permission` 기본값이 `'{}'`(객체)라 V27식 `jsonb_array_elements`는 마이그레이션 자체가 실패한다 → UPDATE 3문(비배열 세우기 → 모듈 append → 기능만 채움), 멱등. 🔴 `t("apm")`은 로케일 루트 객체와 충돌해 라벨만 `apm_permission`으로 우회(권한 키는 BE `feature.name`과 동일 유지). 라우트에 `adminOnly`를 같이 주면 `PageWrapper` OR 단락으로 권한 게이트가 죽는다 |

- ⚠️ 7일이 지나면 트레이스가 사라지는데 그것을 가리키는 링크(에러 그룹 `sampleTraceId` 90일·exemplar 최대 400일)는 더 오래 산다 → `APM_TRACE_NOT_FOUND`는 정상이고 화면은 "만료됐습니다"로 안내한다. exemplar는 여기에 더해 **처음부터 저장된 적이 없는** 경우(tail 2%)가 있어 `stored` 플래그를 따로 준다.

### 3.7a P5 실시간(라이브 스팬)의 조건 — 다른 장과 전제가 다르다

P1~P4는 전부 "DB에 굳힌 값을 읽는" 화면이라 §3.5 보존 표·§3.6 용량 예산이 그대로 적용된다. **P5 라이브는 그 표에 한 줄도 들어가지 않는다** — DB를 쓰지 않기 때문이다. 대신 아래 다섯이 그 자리를 대신하며, 이것을 모르면 화면을 오독한다. 전체는 [18-p5-realtime.md](18-P5-%EC%8B%A4%EC%8B%9C%EA%B0%84-%EA%B4%80%EC%A0%9C-%EC%A7%80%EA%B8%88-%EC%9D%B4-%EC%88%9C%EA%B0%84%EC%9D%84-%EB%B3%B4%EB%8A%94-%EA%B8%B8%28%EB%9D%BC%EC%9D%B4%EB%B8%8C-%EC%8A%A4%ED%8C%AC-X-View-%EC%9A%94%EC%B2%AD-%EA%B4%80%EC%A0%9C-%EB%B9%84%EB%8F%99%EA%B8%B0%29.md).

| 조건 | 무엇 | 🔴 그래서 |
|---|---|---|
| **휘발** | 라이브 스팬은 **DB에 저장되지 않는다**(인메모리 전역 슬롯 arena). 영수증도, 폐기 통계 표도, 파티션도 없다 | **BE를 재시작하면 창이 비어서 시작한다**(정상 동작 — 화면이 `coverageFrom`으로 "이 노드가 언제부터 본 것"인지 말한다) · 과거 조회 불가 · 다중 BE 합산 불가(한 프로세스의 메모리다) · 🔴 저장 관문과 **아무것도 공유하지 않는다** — 공유하면 라이브 장애가 저장을 503으로 만들고 재전송이 1m을 두 배로 만든다 |
| **15분 창** | 링은 **907칸 = 900초 + 경계 7칸**, 귀속 기준은 **스팬 종료 시각(`endTs`)** | 15분 지난 것은 없다 → 과거는 **트레이스 탐색(샘플·7일)**의 일 · 1,000 SERVER/초면 라이브 관측이 **86.4M건/일**이라 저장은 애초에 선택지가 아니었다 |
| **HTTP SERVER만** | Collector filter가 `kind==Server ∧ HTTP 판별`로 거른다(✅ 실측 SERVER 비율 **11.6%**) | CLIENT·INTERNAL·PRODUCER·CONSUMER는 **점이 되지 않는다** · 🔴 메시징을 "SERVER만으로 지원한다"고 말하지 않는다 · RPC/OTHER는 **P5.5 후속**(`stats`가 서비스별 하나라 섞으면 TPS·p95가 오염된다) |
| **동시 요청은 개수만** | `http.server.active_requests`는 **UpDownCounter 하나**다. 목록도 경과도 없다 | 🔴 **진행 중 요청 목록은 원리적으로 불가** — 스팬은 **끝나야** export된다. 가능한 유일한 길은 Java 에이전트 확장(P5.3b)이고 그건 **고객 JVM에서 우리 코드가 도는 지원 범위**가 새로 생기므로 제품 결정이 따로 필요하다 · 🔴 **관측 0은 "관측 없음"**이지 0이 아니다 |
| **export 주기가 지연의 하한** | 종단 지연의 지배항은 우리 코드가 아니라 **상류 설정**이다 — SDK BSP(`OTEL_BSP_SCHEDULE_DELAY`) + Collector `batch/live 1s`. 메트릭(동시 요청·CPU·heap)은 **export 주기 10~60초** | ✅ 실측: 완료→캡처 p95가 고트래픽 **1.23~1.52초**인데 **저트래픽(10/초) + BSP 기본 5,000 ms면 5,727 ms**다 → 설치 가이드가 **`OTEL_BSP_SCHEDULE_DELAY=1000`을 설정 요건**으로 안내하고 화면 문구는 반드시 **"권장 설정 시"**를 단다(빼면 거짓) · 🔴 **초 단위 CPU·메모리는 원리적으로 불가** — 1초 갱신되는 스팬 집계와 같은 속도로 보이게 **꾸며서는 안 된다**("약 1분 이내") |

⚠️ 그리고 **기본 꺼짐이 조건의 일부다** — BE `app.apm.live.spans.enabled`도, 수집기 설정 생성의 `liveSpans` 옵션도 기본이 꺼짐이고, Collector 실행줄에 `--feature-gates=ottl.set.allowNil`이 없으면 PII 방어가 **조용히** 반쯤 꺼진다. 켜는 절차는 [18-p5-realtime.md](18-P5-%EC%8B%A4%EC%8B%9C%EA%B0%84-%EA%B4%80%EC%A0%9C-%EC%A7%80%EA%B8%88-%EC%9D%B4-%EC%88%9C%EA%B0%84%EC%9D%84-%EB%B3%B4%EB%8A%94-%EA%B8%B8%28%EB%9D%BC%EC%9D%B4%EB%B8%8C-%EC%8A%A4%ED%8C%AC-X-View-%EC%9A%94%EC%B2%AD-%EA%B4%80%EC%A0%9C-%EB%B9%84%EB%8F%99%EA%B8%B0%29.md) §10.9.
