## 프로젝트 필요 스킬 등록·변경

**경로:** 프로젝트 관리 → 프로젝트 추가 또는 기존 프로젝트 수정 → **필요 스킬(Required skills)**. 프로젝트 관리 쓰기 권한으로 변경합니다.

필요 스킬은 프로젝트에 필요한 역량을 지정해 인력 후보의 스킬 적합도를 비교하는 기준입니다. 선택 사항이므로 나중에 추가·변경할 수 있습니다. 조직의 스킬 사전에 이미 등록된 항목을 선택하며, 이 창에서 새 스킬 사전을 만들지는 않습니다. 필요한 항목이 없으면 스킬 관리 권한이 있는 관리자에게 등록을 요청합니다.

### 스킬 선택부터 저장까지

1. **직군(Job category)**을 선택하거나 **전체 직군(All categories)**으로 후보를 표시합니다. **스킬 검색(Search skills)**은 스킬 이름·직군 문자열을 검색합니다. 검색 결과가 없으면 검색어와 직군 조건을 함께 확인합니다.
2. **선택 가능한 스킬(Available skills)**에서 항목을 누릅니다. 선택한 항목에는 체크가 표시되고 **선택한 스킬(Selected skills)** 목록과 개수가 갱신됩니다. 여러 항목을 선택할 수 있습니다.
3. 같은 후보를 다시 누르거나 선택 목록의 **×**를 누르면 프로젝트의 선택 목록에서 제외됩니다. 조직의 스킬 사전이나 사용자의 보유 스킬을 삭제하지 않습니다.
4. 필요한 스킬과 기본 정보를 확인하고 **프로젝트 저장(Save project)**을 누릅니다. 선택만 한 상태는 저장 전입니다. 예를 들어 React와 SQL을 선택한 뒤 프로젝트를 저장하면 두 스킬이 그 프로젝트의 요구 역량으로 반영됩니다.
5. 저장 성공 후 같은 프로젝트의 수정 창을 다시 열어 선택한 스킬을 확인합니다. 인력 후보 화면에서 해당 프로젝트의 필요 스킬과 후보의 일치·부족 스킬을 함께 확인합니다. 적합도는 검토 기준이며 자동 배정 결과나 채용 판단을 뜻하지 않습니다.

### 스킬 조회·저장에 문제가 있을 때

- **등록된 스킬 없음:** 관리자에게 스킬 사전 등록을 요청합니다. 정상 조회된 빈 사전과 조회 실패는 다른 상태입니다.
- **스킬 목록을 불러오지 못함:** **다시 시도(Try again)**로 사전을 다시 조회합니다. 수정 창에서 기존 프로젝트 정보나 스킬 연결을 읽지 못하면 **다시 불러오기(Reload)**를 사용합니다. 기존 값 보호를 위해 조회가 완료되기 전에는 선택·저장이 제한될 수 있습니다.
- **현재 목록에 없는 스킬:** 기존에 연결된 ID가 사전에 없을 때 표시됩니다. 필요 여부와 사전 상태를 확인한 뒤 처리하며, 조회 오류를 이유로 기존 선택 전체를 지우지 않습니다.
- **프로젝트 정보는 저장했지만 스킬 저장이 완료되지 않음:** 선택은 유지됩니다. 열린 창에서 **프로젝트 저장**을 다시 눌러 재시도합니다. 프로젝트 기본 정보는 이미 저장됐을 수 있으므로 새 프로젝트를 중복 생성하지 않습니다.
- **저장 결과를 확인하지 못함:** 같은 창에서 다시 저장하면 같은 생성 요청으로 확인합니다. 확인 전 새 프로젝트의 기본 입력이 잠길 수 있습니다. 요청 충돌 안내가 나오면 목록에서 저장된 프로젝트를 확인하고, 스킬 재저장 권한이 없다는 안내가 나오면 프로젝트 관리자에게 반영을 요청합니다.

## 협업 모드 설정과 적용 범위

**경로:** 프로젝트 관리 → 기존 프로젝트 수정 → **협업 모드(Collaboration mode)**. 새 프로젝트 생성 창에는 표시되지 않으므로 먼저 프로젝트를 저장한 뒤 수정 창을 엽니다. 변경에는 해당 프로젝트의 조회 범위와 프로젝트 관리 쓰기 권한이 필요합니다.

협업 모드는 해당 프로젝트에 연결된 Jira 작업과 워크로그를 앱이 조회할 수 있는 범위에서 프로젝트 참여 인원에게 보여주는 설정입니다. 적용되는 작업 관리·간트·프로젝트 캘린더·대시보드 조회에서, 개인의 Jira 조회 권한 때문에 서로 다른 작업을 보는 문제를 줄입니다. 다른 사람의 워크로그도 보일 수 있으므로 켜기 전에 공유 대상을 확인합니다.

### 켜기·끄기와 저장 방식

1. 먼저 프로젝트 구성원 명단을 확인합니다. 프로젝트 명부에 등록된 참여 인원이며 해당 프로젝트의 앱 조회 범위를 통과해야 협업 조회를 사용할 수 있습니다. 팀 지정만으로 참여 인원으로 등록되지는 않습니다. 관리 권한이 있어도 프로젝트에 참여하지 않으면 협업 조회 대상이 아닙니다.
2. 수정 창에서 협업 모드 토글을 켭니다. **협업 모드를 켤까요?(Turn on collaboration mode?)** 확인 영역에서 연결 작업·타인의 워크로그 공유 안내와 제한 범위를 읽습니다.
3. **켜기(Turn on)**를 누르면 설정 변경을 요청합니다. 확인 영역의 **취소(Cancel)**는 켜기를 취소합니다. 범위 확인이 진행 중일 때는 완료를 기다립니다. 확인 실패 후 켜기가 가능해져도 모든 작업이 보인다고 보장하는 상태는 아닙니다.
4. 성공 안내와 토글 상태, **마지막 변경(Last changed)**의 변경자·시각을 확인합니다. 관련 화면으로 이동해 협업 모드 배지와 작업 표시를 확인합니다.
5. 끄기는 토글을 끄는 즉시 변경을 요청하며 켜기 확인 영역은 나타나지 않습니다. 성공 후 조회는 각 사용자의 Jira 권한 기준으로 돌아갑니다. 작업이나 워크로그를 삭제하는 동작은 아닙니다.

**협업 모드는 기본 정보·스킬 저장과 별도로 즉시 적용됩니다.** 토글 변경이 성공하면 **프로젝트 저장**을 추가로 누를 필요가 없습니다. 프로젝트 수정 창을 닫아도 이미 성공한 협업 모드 변경은 취소되지 않습니다. 반대로 이름·기간·필요 스킬의 미저장 변경은 프로젝트 저장이 필요합니다. 협업 설정을 되돌리려면 토글을 직접 원래 상태로 바꾸고 성공 결과를 확인합니다.

### 협업 모드에서도 유지되는 제한

- **화면 접근·구성원·프로젝트 범위:** 앱 기능의 읽기 권한과 해당 프로젝트 접근 조건은 계속 적용됩니다. 켜는 사람의 쓰기 권한과 협업 조회를 이용하는 참여자의 조건을 구분합니다.
- **Jira 편집 권한:** 조회가 가능해져도 상태·일정·담당자·워크로그를 변경할 권한이 추가되는 것은 아닙니다. 각자의 Jira 권한으로 편집하며, 수정 거부 시 해당 작업의 권한을 확인합니다. Jira 원본 링크를 열 때에도 본인의 Jira 조회 권한이 필요합니다.
- **앱이 볼 수 없는 작업:** 앱이 접근하지 못하는 스페이스나 이슈 보안 수준이 있는 작업은 여전히 제한될 수 있습니다. 제한 스페이스는 Jira 관리자에게 앱 역할의 Browse Projects 권한 확인을 요청합니다. 팀 관리형·회사 관리형 등 프로젝트 유형에 따라 관리 경로와 권한 설정 방식은 다를 수 있습니다.
- **확인 못 함·일부 확인·본인에게만 보임:** 범위 확인 실패는 제한이 0이라는 뜻이 아닙니다. 일부 확인 안내가 있으면 전체 점검으로 해석하지 않습니다. 본인에게만 보이는 작업은 다른 참여자에게 동일하게 표시되지 않을 수 있습니다.
- **본인 권한 기준의 조회:** 진척 추이·비용 소진 위젯과 작업 상세의 연관관계 영역은 본인의 Jira 권한으로 조회합니다. 분석·비용·Confluence 문서 등 다른 기능의 권한을 협업 모드가 일괄 확장한다고 해석하지 않습니다.

설정을 불러오지 못했거나 변경 실패 안내가 나오면 토글의 실제 상태를 다시 확인합니다. 설정 확인 불가를 꺼짐으로 단정하거나 성공 안내 없이 적용됐다고 판단하지 않습니다.
