# 하네스 드라이런

스킬 수정 시 아래 입력을 현재 지침으로 처리해 선택한 역할·순서·소유 파일·실패 시 행동을 확인한다. 읽기 전용 평가에서 앱 코드 작성, 배포, 커밋은 하지 않는다. 정적 검사만 했다면 실제 실행으로 표기하지 않는다.

## 실행 시나리오

| 입력/조건 | 기대 행동 |
|---|---|
| “프로젝트별 워크로그 집계 화면 추가해줘.” | 요구사항과 권한·응답 계약을 확정하고 백엔드→프론트→검증. 새 resolver의 가드·권한 등록과 소비 경로 확인 |
| “기존 결과에서 프론트 빈 상태 문구만 고쳐줘.” | 기존 코드·상태를 확인하고 프론트/i18n만 수정. 설계·백엔드를 재생성하지 않음 |
| “백엔드만 다시. 배열 응답을 rows 객체로 바꿔줘.” | 백엔드 내부 import와 프론트 소비자를 모두 조사. 소비자 불일치를 숨기지 않고 범위와 계약 정합성 해결 |
| 백엔드 작업이 재호출 후에도 실패하고 응답 계약은 미확정 | 의존 UI 구현을 시작하지 않음. 원인을 해결하거나 리더가 인수. 독립 작업만 계속 |
| 설계는 items, 실제 응답은 rows | 요구사항 기준으로 결함/의도한 변경을 판정하고 계약·소비자를 함께 맞춤. 실제 구현을 무조건 정답으로 취급하지 않음 |
| 유휴 frontend 에이전트에 QA 수정 요청 | 기존 ID가 유효하면 followup_task로 재개. send_message만으로 시작됐다고 가정하지 않음 |
| 다른 작업자가 PermissionMap.js를 수정 중 | 기존 diff를 보존하고 소유권을 조율. 테스트 실패를 이유로 해당 변경을 되돌리지 않음 |
| 빌드 통과, Forge CLI 인증 실패 | 빌드는 통과, Forge 검증은 미검증. 전체 검증 완료나 배포 성공으로 보고하지 않음 |
| 기존 _workspace 기능에 새 요구사항 도착 | 상태와 코드를 대조해 재개하거나 새 runs 디렉토리 사용. 기존 디렉토리 자동 이동 없음 |

## 트리거 경계

| feature-harness 사용 | 구현 파이프라인을 시작하지 않음 |
|---|---|
| “RFC 기능 구현해줘.” | “RFC 문서 표현만 다듬어줘.” |
| “인력 리포트를 추가해줘.” | “인력 리포트 화면이 어떻게 동작해?” |
| “팀 권한 기능 보완해줘.” | “팀 권한 오류 메시지를 한국어로 설명해줘.” |
| “프로젝트 화면 필터 수정해줘.” | “하네스의 프론트 담당자 지침 검토해줘.” |
| “백엔드만 다시 구현해줘.” | “백엔드 구조를 설명해줘.” |
| “기존 결과 기반으로 개선해줘.” | “이전 검증 보고서 요약해줘.” |
| “프론트만 수정해줘.” | “프론트엔드 스킬 description을 고쳐줘.” |
| “검증 다시 해줘.”(기능 작업 후속) | “검증 절차 문서 오탈자를 고쳐줘.” |

설계만 요청하면 feature-harness를 사용하되 설계와 검토에서 종료한다. 작은 기능 수정은 스킬을 적용해도 전체 에이전트 파이프라인을 강제하지 않는다.
