## 3. 접점 — API 계약서 하나

BE와 FE의 **유일한 공식 접점은 `_workspace/features/<영역>/<기능>/contract_{feature}.md`** 다.

```
Codex ──> moveseye-be-spring/     (컨트롤러·서비스·DTO·Flyway·테스트)
             │
             └─ _workspace/features/<영역>/<기능>/contract_{feature}.md   ← 단일 진실 원천(SSOT)
             │
Claude ──> moveseyee_fe/          (services/*.api.ts · types · hooks · 컴포넌트)
```

### 진행 순서 (BE 선행)

1. **Codex**: BE 엔드포인트 구현 → 빌드·테스트 통과 확인 → `_workspace/features/<영역>/<기능>/contract_{feature}.md` 작성/갱신 → 사용자에게 "계약 산출 완료" 보고.
2. **Claude**: 계약서를 읽고 FE 연동(types → api → hook → 화면). 계약서에 없는 필드를 **추측해서 만들지 않는다**.
3. **Claude**: FE 완료 후 경계면·런타임 검증 → 결과를 `_workspace/features/<영역>/<기능>/qa_{feature}.md` / `e2e_{feature}.md`에 기록.

### 계약서 작성 규칙 (Codex)

- 형식은 기존 계약서를 그대로 따른다 (예: `_workspace/features/infra/host-checks/contract_host-livecheck.md`).
- 반드시 포함: 메서드·경로·인증/권한·요청 파라미터·**응답 payload shape(주석에 타입·nullable·생략 여부)**·에러 케이스·상태코드.
- FE는 `useDmoveQuery`가 **2겹 언랩**하여 `data` payload를 직접 수신한다. 계약서의 shape은 **언랩 후 payload 기준**으로 적는다.
- 에러는 HTTP 코드가 아니라 **200 + 바디 `code`** 로 표현되는 기존 계약을 따른다.

### 계약 변경이 필요할 때 (Claude → Codex)

FE 연동 중 계약이 틀렸거나 부족하면, 직접 BE를 고치지 말고 계약서 하단의 **`## 🔄 FE 요청사항`** 섹션에 추가한다:

```markdown
## 🔄 FE 요청사항
- [ ] (2026-08-02, Claude) `hostname` 필드가 응답에 없음 — 목록 화면에 필요. 추가 요청.
- [x] (2026-08-02, Codex) 반영 완료 — v2 shape 참조.
```

그리고 사용자에게 "코덱스 쪽 작업 필요" 라고 보고한다. Codex는 작업 시작 시 담당 계약서의 이 섹션을 먼저 확인한다.

## 5. 런타임(서버 기동) 규칙

FE 검증에는 BE(:3000)가 필요하므로 기동 권한이 겹친다.

- **BE(:3000) 기동/재기동/재빌드는 Codex 담당.** Claude는 **이미 떠 있는 BE를 사용**한다.
- BE가 안 떠 있어서 FE 검증이 막히면, Claude는 **읽기 전용으로 기동만** 할 수 있다(코드 수정·빌드 산출물 변경 없이 `bootRun`). 이 경우 자기가 띄운 프로세스는 자기가 내린다.

- FE(:5173, 포트 auto-increment 주의) 기동은 Claude 담당.
- 기동 전제(JDK17 매번 지정, dev 프로필=5433 도커 DB, API 호출 시 `x-visitor-id` 헤더 필수)는 기존 규약을 따른다.

## 6. Claude 측 하네스 연동

기존 하네스(`fullstack-feature` 등)는 BE·FE를 한 세션에서 처리하도록 설계됐다. 협업 모드에서는 다음이 우선한다:

- **`be-engineer` 에이전트를 스폰해 BE에 쓰기 작업을 시키지 않는다.** BE는 Codex 몫이다.
- `fullstack-feature` 실행 시 BE 단계는 **"계약서 대기"** 로 대체한다 — 계약서가 있으면 FE부터, 없으면 "코덱스에 BE 선행 필요" 로 보고하고 멈춘다.
- `be-engineer`는 **읽기 전용 조사**(BE 코드 확인, 계약 해석) 용도로만 쓸 수 있다.
- `integration-qa` / `functional-qa` 는 그대로 사용한다(검증은 읽기+실행이라 소유권을 침범하지 않음). 단 결함이 BE에 있으면 **고치지 말고 §3의 FE 요청사항으로 넘긴다**.

1. **인수인계 확인 먼저.** 상대가 작업하다 만 것이 남아 있을 수 있다:
   ```bash
   git -C C:/solutions/moveseye-be-spring status --porcelain
   git -C C:/solutions/moveseye-be-spring log --oneline -5
   ```

   - 미커밋 변경이 있으면 **지우거나 리셋하지 말고** 무엇이 남았는지 사용자에게 먼저 보고한다(중단 지점일 수 있음).
   - `_workspace/features/**/contract_*.md`의 `## 🔄 FE 요청사항` 중 미처리(`[ ]`) 항목이 남았는지 확인 — 그게 곧 인계받을 잔여 작업이다.

3. **그 즉시 이렇게 바뀐다** (다른 파일 수정 불필요):

   - `be-engineer` 정상 스폰 가능(읽기 전용 제한 해제), `fullstack-feature`는 Phase -1을 건너뛰고 원래 파이프라인(BE 구현 → 계약 → FE → QA)으로 실행.

   - 계약서(`contract_*.md`)는 **계속 쓴다** — 협업용이기 이전에 하네스의 SSOT다.

1. 자기 소유가 아닌 레포에 **단독 기간 중 만든 변경이 미커밋으로 남아 있지 않은지** 확인하고, 있으면 커밋하거나 사용자에게 보고한다(그대로 두면 상대가 그 위에 작업하다 충돌).
2. 그 기간에 바뀐 BE 엔드포인트가 계약서에 반영됐는지 확인 — 단독 작업 중엔 계약서를 건너뛰기 쉽다.
3. 스위치를 `ACTIVE`로 되돌리고 전환 이력에 기록.

## 8. 검수 모드 (`SOLO-CLAUDE` 기간의 Codex 역할)

2026-08-03부터 Codex는 **영역 소유자가 아니라 검수자**다. 구현은 Claude가 BE·FE 모두 맡는다.

| | 담당 |
|---|---|
| 구현(BE·FE·마이그레이션·테스트) | **Claude** |
| 검수(설계 적합성·회귀 위험·계약 정합·놓친 케이스) | **Codex** |

### 검수 요청 방법

Claude는 기능 단위가 끝나면 **`_workspace/features/<영역>/<기능>/review_{feature}.md`** 를 만들어 아래를 적는다:

- **범위**: 무엇을 바꿨나(기능 한 줄 + 변경 파일 목록)
- **의도**: 왜 이렇게 했나(선택한 설계와 버린 대안)
- **중점 확인 요청**: 스스로 불안한 지점 — 여기를 비우지 말 것. 검수의 값어치는 대부분 여기서 나온다
- **검증 현황**: 통과한 것(빌드·테스트·런타임)과 **검증 못 한 것**을 나눠 적는다

Codex는 같은 파일 하단 `## 검수 결과`에 기록한다. 결함은 심각도(🔴/🟡/🟢)와 근거를 붙인다.
Claude가 반영한 뒤 항목을 `[x]`로 닫는다.

### 원칙

- **자기 코드는 자기가 검수하지 않는다.** Claude가 구현한 것을 Claude가 리뷰해 통과시키지 않는다.
- 검수 지적은 **계약서 요청과 같은 무게**로 다룬다 — 반영하거나, 반영하지 않는 이유를 파일에 적는다.
- ⚠️ **검수 트리거는 수동이다**(사용자가 Codex 세션을 연다). 협업 모드에서 요청이 하루 묵었던 것과 같은 병목이므로,
  Claude는 검수 요청을 만든 즉시 **사용자에게 "검수 넘길 것 있음"을 보고**한다. 쌓아두지 않는다.
