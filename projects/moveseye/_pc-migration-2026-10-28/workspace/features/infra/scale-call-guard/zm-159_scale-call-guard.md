## 1. 무엇이 문제였나

**한 줄 요약: 자빅스 API를 "전부 한 번에" 부르는 곳이 많아, 호스트·아이템이 늘면 응답 하나가 수백 MB가 되어 BE가 OOM으로 죽거나, 상한에 조용히 잘린 결과를 정답처럼 보여줬다.** (전수 감사: 🔴36 · 🟠87 · 보안 4)

| 분류 | 대표 사례 | 결과 |
|---|---|---|
| 한 번에 전부 | AWS 매처가 **전 호스트의 전 아이템**을 붙여 받음(1천만 행), 그룹 월간 리포트가 전 호스트 트렌드를 1콜로 받음 | 응답 수백 MB → OOM |
| 조용한 절단 | history 10만 행 상한이 오름차순으로 잘려 **긴 기간 차트의 최근 구간이 사라짐**, 알람 1만 건 상한 | 틀린 화면 |
| N+1 | 네트워크 차트가 인터페이스 × 타입마다 1콜(인터페이스 100개 → 요청당 수백 콜) | 자빅스 부하·지연 |
| 무스코프 조회 | 아이템·트리거 관리 목록을 대상 없이 부르면 전 아이템을 받아 앱에서 20개로 자름 | OOM |
| 독립 결함 | 알람 사본의 **열린 장애가 이틀 뒤 좀비로 삭제**(T-A), 구성 현황 화면 **영구 정지**(X1), EC2 100대 초과 리전 **전체 실패**(X6), 네트워크 차트 **인터페이스 값 섞임·합계 오류**(X2·N2) | 데이터 손실·장애 |
| 호출 코드 산만 | 자빅스 호출부 26파일이 "callRaw → 배열 확인 → 변환"을 제각각 구현, 메서드 이름은 문자열 | 보호 장치를 한 곳에 걸 수 없음 |

> 사용자 방향(09-17): "아이템·호스트 1천만은 **총 개수**일 뿐 한 번에 다 가져올 일은 없다 — 과하게 하지 말고, **전부 가져오던 곳만** 고친다. OOM은 막는다."

## 2. 무엇을 바꿨나

### 2.1 공통 호출 유틸 (C1·C2) — `engine-zabbix/.../client/`
- **`ZabbixApiTemplate`**: 모든 서비스가 이것만 쓴다 — `raw`·`call`·`list`·`object`·`count`·`firstId`·`exec`. count 파싱·배열 확인·타입 변환을 한 곳에서.
- **`ZabbixParams`**: 요청 파라미터 빌더(깊은 복사, 허용 타입 외 거부).
- **`ZabbixClient` 직접 사용 금지**: `ZabbixClientAccessTest`가 **바이트코드 상수 풀**을 검사해 템플릿 밖의 직접 참조를 막는다(소스 정규식은 URL·문자열에 속아서 폐기).
- 롬복: 신규 클래스에만 적용(기존 수동 생성자 일괄 치환은 하지 않음 — 설정 주입·초기화 로직 보존).

### 2.2 보호 층 (C3)
| 부품 | 역할 |
|---|---|
| `ZabbixCallLimits` | 설정 키 `zabbix.call.*` — 응답 바이트 상한(64MiB), 받은 행 예산(50만), 보유 행 상한(1만), 호출 수(2000), 시간(120초), 메서드별 `policy.{method}.max-ids / max-rows / window-seconds`. 잘못된 설정은 **기동 실패** |
| `ZabbixQueryExecutor` | id 분할 · 기간 창 분할 · eventid 커서 분할. `limit = maxRows + 1`로 초과를 판정하고, 넘치면 기간 → id 순으로 반분. 더 못 나누면 `NO_PROGRESS`. 예산 초과·불완전은 `ZabbixScanResult`로 **숨기지 않고** 돌려준다 |
| `ZabbixClient` 응답 상한 | Apache HttpClient로 직접 읽으며 바이트를 세고, 넘으면 **응답을 닫기 전에 요청을 취소**(닫기가 남은 본문을 끝까지 읽어 멈추는 문제) |

### 2.3 메서드 이넘 (C4) — 사용자 요청 "API 버전이 바뀌어도 바꿔 끼우기 쉽게"
- **`ZabbixMethod`**: 사용하는 JSON-RPC 메서드 **111개** — `rpcName`, 성격(`READ`/`WRITE`/`AUTH`/`INFO`), `docUrl()`(공식 문서 링크).
- 버전은 `DOCS_VERSION = "7.0"` **한 곳**, 링크는 `DOCS_URL_FORMAT` 틀로 조립 → 버전을 올릴 때 한 줄만 바꾼다.
- 조사표 `engine-zabbix/src/test/resources/zabbix/api-reference-7.0.json`(공식 문서 원문 확인)과 `ZabbixMethodTest`가 이넘을 대조.
- 보호 층은 **READ 메서드만** 받는다(쓰기 메서드를 분할 재시도하지 않도록).

### 2.8 알람 동기화 범위 설정 (운영 회피책, 09-18 추가)
사본에 담을 알람을 **자빅스에 물을 때** 좁힌다(설정 `EVENT_SYNC`, V63). 기본값은 제한 없음(종전과 동일).

| 축 | 효과 |
|---|---|
| 호스트 그룹 | 지정 그룹의 알람만 |
| 최소 심각도 | 그 등급 이상만 |
| 억제 제외 | 점검 중 억제 알람 제외 |
| 꺼진 규칙 제외 | 비활성 트리거 알람 제외 |

- 좁히면 **사본을 읽는 화면에서 사라진다**(벨·문제 목록 기본·홈 위젯·이벤트 통계·AI 요약). 자빅스 직접 조회 경로(이력 모드·리포트·그룹 요약)는 영향 없음.
- 🔴 검수에서 발견: `enabledRulesOnly`가 **목록 조회에는 적용되지 않던 결함**(집계 경로에만 존재) — 이번에 3경로 모두 적용(`objectids` 500개씩).
- 범위 밖 사본 행은 되짚기 후보에서 제외(헛조회 방지). 이미 담긴 범위 밖 행은 **2일 뒤 정리 배치가 제거**한다(즉시 제거는 범위 밖).
- 이 설정으로 열린 알람이 1만 건 상한 안에 들어오면 **A-2(구조 변경) 없이 누락을 피할 수 있다**.

### 2.10 원시 시계열 완전성 (C5 + C7 잔여, 09-19 추가)
종전 원시 조회(`history.get`)는 1콜 상한(10만 행)에 닿으면 **경고 로그만 남기고 잘린 값을 그대로 올렸다.**
차트는 "구간이 비어 있는 그림"을 정답처럼 보여줬다(인터페이스 상태 차트에서 장애로 오해될 수 있었다).

| 층 | 변경 |
|---|---|
| 조회 | `ZabbixHistoryServiceImpl`이 `ZabbixQueryExecutor.scanWindows`로 **기간 창 × itemid 묶음** 분할 조회(trend.get과 같은 경로). 창 크기는 묶음이 덜 찼으면 넓힌다 — `창 = clamp(1콜 행 상한 × 가정 주기(60초) ÷ 묶음 크기, 정책 창, 하루)` |
| 계약 | `HistoryScanResult(points, complete, stopReason)` · `SeriesResult(series, complete, stopReason, deliveredPoints)` · `MetricPort.querySeriesResult`(구현 정본, `querySeries`는 얇은 통로) |
| 예산 | `zabbix.call.max-history-rows`(기본 10만) 신설. **실행기의 확정 전 창 버퍼와 소비자 누적이 이 예산을 나눠 쓴다**(`maxWindowRows`는 남은 자리를 돌려주는 공급자), 전달한 페이지는 즉시 해제. 1콜 상한은 이보다 작아야 하며(`history.get` 10만 → **1만**) 기동 시 검증한다 |
| 정책 정합 | `history.get` 창 3,600 → **3,000초** — `200개 × 3,000초 ÷ 1분 = 1만 행`(= 1콜 행 상한). 어긋나면 꽉 찬 묶음이 매 창 넘쳐 헛읽기 후 분할한다 |
| 화면 | `InterfaceService`를 단방향 상태 기계로: 긴 창=요약→원시→빈 결과 / 짧은 창=원시→요약 1회→빈 결과. **잘린 원시는 앞 묶음까지 버린다**(부분 반영 금지) |
| 소비자 | `ItemsService`는 "응답이 정확히 10만이면 잘림" 추정 대신 **완전성 판정**으로 이전 |

🔴 **기존 1콜 계약은 건드리지 않았다** — `getHistoryByItemids`·`getRange`는 종전 그대로다. 두 소비자가 그 성질에 기대고 있다:
`ItemsService`의 절단 판정(당시)과 `HostService`의 DESC 최신 구간 유지. 분할은 완전성을 함께 돌려주는 새 API에만 있다.

코덱스 검수 **5회 왕복**(설계 1 + 구현 4) 후 "병합 승인 가능(필수 0건)". 차단으로 잡힌 실제 결함은
① 1콜 상한 == 보유 상한이라 분할 완주가 논리적으로 불가능 ② 분할이 기존 소비자 2곳을 깨뜨림
③ 실행기 창 버퍼가 예산 밖(최대 2배) ④ 어댑터가 설정값 대신 상수 사용 — 상세는 `features/infra/scale-call-guard/review_zm-159-c5.md`.

## 7. 개발 중 교훈
- **대량 기계 치환은 python + `cmp`로** — 정규식이 대입문 연속 줄을 바꾸거나 빈 줄을 삼켰고, sed는 한글·이모지 패턴을 못 맞춰 변이 검사가 "생존"으로 오판됐다.
- **변이 검사의 "실패"는 결과 XML로 사유를 확인** — 한 번은 컴파일 오류를 교착 재현으로 착각할 뻔했다.
- **교착 테스트는 `@Timeout(threadMode = SEPARATE_THREAD)` + 기한 있는 `get`** — 아니면 테스트 워커가 영구 정지한다(남은 `GradleWorkerMain`은 워크트리 경로를 확인하고 종료).
- **포트 인터페이스 default 메서드에 람다 금지** — 합성 private static 메서드를 `LicenseGuardedPortTest`가 리플렉션으로 호출해 깨진다.
- **요청별로 예산을 넓히지 말 것** — 전역 상한이 무력화된다(C6 검수 R1).
- **codex exec는 git 저장소 안에서** 실행(`C:/worktrees`처럼 저장소가 아닌 곳은 거부).
