## 1. 배경과 목표

`audit_scale-5000-hosts.md`는 호스트 5,000·아이템 1,000만 규모를 **코드 감사(읽기 전용)**로만 판정했다 — "확인"은 코드를 읽어 확인한 것이고, "추정"은 데이터 분포·실행 시간에 좌우되는 계산값이며, **부하 시험은 미실시**라고 명시돼 있다. 이 설계는 그 추정 항목들을 실측으로 승격하고, 이후 ZM-159(대용량 호출 방어) 적용 전/후를 비교 가능한 형태로 만드는 것이 목표다.

**목표**
1. 감사에서 나온 구체적 병목(§3)을 재현하는 부하 시나리오를 만든다.
2. 실제 Zabbix 서버 없이, 합성(synthetic) mock으로 같은 규모의 응답을 재현한다.
3. "느리다/빠르다"뿐 아니라 **조용한 절단(R2)**을 직접 탐지하는 판정 기준을 둔다.
4. ZM-159 적용 전(기준선)과 후(회귀)를 같은 시나리오로 비교할 수 있게 한다.

**비목표**
- 지금 당장 실행하지 않는다 — 이 문서는 설계만 남긴다.
- 실제 Zabbix 서버 규모 구축·검증(2단계, 후속)은 다루지 않는다.
- FE 렌더링 부하(F3·F11 등)는 별도 — 이 설계는 BE·엔진 계층만 다룬다.

## 2. 왜 합성 mock인가

| 방식 | 비용 | 재현성 | 놓치는 것 |
|---|---|---|---|
| 실 Zabbix 5,000대 구축 | 데이터 생성만 며칠, 반복 실행마다 비쌈 | 낮음(환경마다 편차) | (놓치는 것 없음 — 가장 현실적) |
| 합성 mock | 파라미터만 바꾸면 즉시 재현 | 높음(결정적) | 실제 Zabbix DB 쿼리 최적화·인덱스 특성, 네트워크 특성 |

감사의 병목은 대부분 **"자빅스가 이만한 크기의 JSON을 돌려주면 BE가 어떻게 되는가"** 문제(R1 분할 없음, R2 절단, R6 N+1)이지 Zabbix 자체의 쿼리 성능 문제가 아니다. 따라서 1단계는 mock으로 충분하고, 실 Zabbix 검증은 필요성이 확인된 후 2단계로 미룬다.

---

## 3. 시나리오 = 감사 발견 항목 매핑

호출 진입점은 `engine-zabbix`의 `ZabbixClient.callRaw` 한 곳(ZM-159 설계서 §2 확인)이므로, mock은 이 레이어의 JSON-RPC 메서드만 스텁하면 BE 상위 코드는 그대로 둘 수 있다.

| # | 시나리오 | 겨냥하는 감사 항목 | 판정 포인트 |
|---|---|---|---|
| 1 | 그룹 디스크/트래픽 월간 추이 조회 | H1=C5=B1 — `trend.get` 분할·상한 없음, 월간 디스크 5,000×5마운트×5서브키×720h ≈ 9천만 행 1응답 | 응답 시간 + 반환 행 수가 기대치와 일치하는지(절단 탐지) |
| 2 | 그룹 알람 이력 30일 조회 | H2 — `event.get` limit 0 + extend, 30일 3천만 건 | 동일 |
| 3 | `/hosts/hostgroup-problems` 전체 기간 스캔 | H3 — 의도적으로 절단 없음, 실측 22,832건=6MB → 30일 약 8GB 추정 | 메모리·응답시간, OOM 여부 |
| 4 | 그룹 문제 상세 화면 | H4 — 무제한 event.get + distinct 없는 trigger.get + 페이징 없음 | 응답시간, 자빅스 콜 횟수 |
| 5 | 관리자 3명 동시 구성현황 진입(캐시 미스 유도) | X1 — `OverviewCallExecutor` 6스레드 고정 풀에서 부모가 같은 풀에 자식 작업을 넣고 무기한 대기 → 교착 | **동시성만으로 재현**(mock 응답 크기와 무관) — 요청이 전부 멈추는지 확인 |
| 6 | 네트워크 맵 로딩(호스트 500대) | R6 — N+1, "네트워크 맵 500콜" | 자빅스 콜 횟수(호스트 수에 비례하는지) |
| 7 | 알림 벨 30일 진입 | R3 — 전부 받아서 앱에서 거르기·페이징, 30일 사본 전량 적재 | 응답 크기·시간 |

시나리오 1·2·3·4·7은 mock 응답 **크기**로 재현, 5는 **동시성**으로 재현, 6은 **콜 횟수**로 재현 — 세 축을 구분해 둔다.

## 4. Mock 서버 설계

- 형태: WireMock(권장 — 매핑 파일만으로 시나리오별 응답 프로파일 전환 가능) 또는 가벼운 Node/Express 스텁. BE dev profile의 Zabbix API URL만 이 mock으로 돌리면 됨(`ZabbixClient` 설정 한 곳).
- 스텁 대상 메서드: `host.get`, `item.get`, `trend.get`, `history.get`, `event.get`, `problem.get`, `trigger.get`, `hostinterface.get` — 감사에서 지목된 것 위주.
- 데이터 생성기: 호스트 수·호스트당 아이템 수·기간(일)을 파라미터로 받아 각 메서드 응답 크기를 계산해 생성. 감사 가정치를 기본값으로 둔다:
  - 호스트 5,000 / 아이템 1,000만(호스트당 ~2,000) / 하루 이벤트 100만 / 열린 알람 1만+ / 그룹 500 / 템플릿 1,000
- 지연 주입(latency injection): 실 Zabbix의 대량 쿼리 응답 지연을 흉내내기 위해 응답 크기에 비례한 인공 지연을 넣는 옵션. 시나리오 5(교착)는 지연 없이도 동시성만으로 재현되므로 필수는 아님.
- **분할 호출 대응**: ZM-159 적용 후에는 BE가 `trend.get`을 청크로 나눠 여러 번 호출하게 되므로, mock은 청크 파라미터(예: itemids 500개 단위)를 받아 부분 응답을 합쳐도 원본과 동일한 총량이 나오게 만들어야 회귀 비교가 성립한다.

## 5. 부하 도구 — k6

- **k6**(JS 시나리오, threshold 기반 pass/fail, VU 모델)를 사용한다. Gatling(JVM)은 BE와 같은 머신에서 리소스를 다투게 되어 결과를 왜곡할 수 있어 제외.
- VU(가상 사용자) 수는 감사 가정치 "동시 사용자 200"을 상한으로, 시나리오별로 하위 단계(10 → 50 → 200)로 올려 병목이 나타나는 지점을 찾는다.
- 스크립트는 BE REST 엔드포인트를 호출한다(자빅스가 아니라 BE가 대상 — mock은 BE 뒤에서 자빅스 역할만 대신함).

## 6. 판정 기준 — 조용한 절단(R2) 탐지가 핵심

감사 R2: "상한(history 10만·이력 2만·AI 500·APM 500)에 닿아도 결과에 표시가 없다." 즉 **"응답 200 + 빠름"만으로는 통과 판정이 될 수 없다** — 절단된 채로 빠르게 돌아온 것과 정상 처리된 것을 구분 못 하기 때문이다.

각 시나리오는 다음 두 층의 어서션을 둔다:
1. **성능층**: p95 응답시간, 오류율(4xx/5xx), 타임아웃 여부, (가능하면) BE 프로세스 메모리·GC.
2. **정합층**: mock이 실제로 준 데이터량(생성기가 알고 있는 값) 대비 BE 응답에 실린 데이터량을 비교. 둘이 다르면 "느리지만 정확" 또는 "빠르지만 잘림" 중 무엇인지 구분해서 기록한다.

기준선(ZM-159 이전) 실행에서는 시나리오 1·2·3·4가 **잘림 또는 실패**로, 시나리오 5가 **교착**으로 나오는 것이 "정상적으로 재현됨"이다. ZM-159 이후 재실행에서는 잘림이 "명시적 상한 + 안내(4xx 등)"로 바뀌는지, 교착이 사라지는지를 확인한다.

## 7. 환경 격리

- 전용 Zabbix mock + **전용 DB 프로필**로 돌린다. dev DB(도커, 76호스트)를 공유하면 다른 작업과 충돌한다 — `zm-151-156` 작업 중 워크트리·IT DB 공유 충돌이 이미 한 번 발생한 바 있다(메모리 `zm-151-156-backlog-sprint`).
- 그림: `_tools/run_be_loadtest.ps1`(신규) + 별도 docker-compose 프로필(load-test 전용 DB 포트) + `_tools/mock-zabbix/`(mock 서버·데이터 생성기) + `_tools/k6/`(시나리오 스크립트).
- 워크트리는 필요 시 `C:/worktrees/loadtest-be` 형태로 격리(다른 BE 작업과 build/classes 공유 금지 — 동일 이유로 이미 문서화된 원칙).

## 8. 진행 단계

1. **기준선(Phase 1)** — 현재 코드(ZM-159 병합 전)로 §3 시나리오 전부 실행 → 추정을 실측으로 승격. 특히 X1 교착, H1/H3 대량 응답 시 OOM/타임아웃 여부를 확인.
2. **회귀(Phase 2)** — ZM-159(청크·상한 유틸) 병합 후 동일 시나리오 재실행 → 실패가 "정상적인 상한 응답"으로 바뀌었는지, 교착이 사라졌는지 확인.
3. **실 Zabbix 검증(Phase 3, 선택·후속)** — Phase 1·2에서 못 잡는 것(실제 쿼리 지연 특성 등)이 남는다고 판단되면, 소규모(예: 호스트 200~500대) 실 Zabbix로 표본 검증. 착수 필요성 여부는 Phase 2 결과를 보고 결정한다.

## 9. 열린 결정 (착수 시 확인)

- mock 서버를 WireMock으로 할지 커스텀 Node 스텁으로 할지 — WireMock은 설정만으로 되지만 "청크 요청 합치면 원본과 동일" 같은 상태 유지 로직은 커스텀 쪽이 짜기 쉬움.
- Phase 1 기준선을 몇 %/몇 단계 VU로 볼지 — 이 문서는 상한만 못박음(200), 단계 구간은 착수 시 정한다.
- 지연 주입(latency injection) 파라미터의 기준값 — 실측 자료가 없어 임의값으로 시작하고 Phase 3에서 보정할지 여부.
