# 자빅스 DB 부하 — 우리 제품이 주는 부하의 실태와 줄이는 방법

- 작성일: 2026-09-02
- 범위: `moveseye-be-spring`이 자빅스 서버(API→DB)에 주는 부하
- 방법: 코드 실물 조사 (호출 지점·캐시·배치 전수 확인)
- 대상 독자: 이 코드를 처음 보는 사람도 읽을 수 있게 씀

---

## 한 줄 요약

> **API를 거쳐도 결국 자빅스 DB에 SQL이 날아간다.** 부하를 0으로 만들 수는 없지만,
> ① 같은 질문을 반복하지 않고(캐시) ② 우리 DB 사본에서 읽고(롤업) ③ 물을 때 싸게 묻고(trends·limit)
> ④ 최대 부하에 상한을 걸어 "숫자로 약속할 수 있는 상태"로 만드는 것 — 이 네 가지가 전부다.

---

## 1. 기본 원리 — API도 결국 DB다

우리 제품은 자빅스 DB에 직접 SQL을 날리지 않고, 전부 자빅스 API(JSON-RPC)를 부른다.
하지만 API는 부하를 없애주는 마법이 아니다. **API 서버가 우리 대신 SQL을 짜서 자기 DB에 날려줄 뿐이다.**

```
[우리 화면] → [우리 BE] → problem.get (API 호출) → [자빅스 서버] → SELECT ... (SQL) → [자빅스 DB]
```

그래도 API를 거치는 게 맞는 이유:
- 자빅스가 버전업으로 DB 스키마를 바꿔도 우리는 안 깨진다 (API는 호환을 지켜줌)
- 우리가 짠 SQL이 자빅스 DB에 락을 걸거나 잘못 긁는 사고가 원천 차단된다
- 권한·감사도 자빅스 쪽 체계를 그대로 탄다

즉 **"어떻게 묻느냐"의 책임은 자빅스가 지지만, "얼마나 자주·얼마나 크게 묻느냐"의 책임은 우리에게 있다.**
이 문서는 후자를 다룬다.

또 하나 다행인 점: 우리 쪽 호출은 전부 한 곳을 통과한다.
`engine-zabbix/.../zabbix/client/ZabbixClient.java`의 `callRaw()` — **수도꼭지가 하나**라서,
계측이든 제한이든 여기 한 군데에 걸면 전체에 적용된다.

## 2. 자빅스 DB에서 뭐가 무거운가

자빅스 DB의 테이블은 크기가 극단적으로 다르다. 같은 "API 1콜"이라도
어느 테이블을 건드리는 호출이냐에 따라 부하가 하늘과 땅 차이다.

| 테이블 | 뭐가 들어있나 | 크기 감각 |
|---|---|---|
| `history*` | **수집된 원시값 전부**. 아이템 1개가 1분 주기면 하루 1,440행 | 🔴 괴물. 호스트 76대 × 아이템 수백 개면 수억 행 이상 |
| `trends` | history를 **시간당 1행**(min/avg/max)으로 요약한 것 | 🟠 history의 약 1/60~1/300 |
| `events`, `problem` | 장애 발생/해소 기록 | 🟡 수만~수십만 행 |
| `hosts`, `items`, `triggers` | 설정 정보 | 🟢 작음 (단, 횟수가 많으면 문제) |

API 호출을 이 표로 번역하면:

- `history.get` = **괴물 테이블에 SELECT** → 기간·limit 관리 필수
- `trend.get` = 요약 테이블에 SELECT → 같은 기간이어도 훨씬 쌈
- `problem.get`, `event.get` = 중간
- `item.get`, `host.get` = 개별로는 가벼움. 반복 호출(N+1)이 문제

**비유**: 도서관에서 "이 책 어디 있어요?"(item.get)는 사서가 바로 답하지만,
"지난 한 달간 대출된 책 전부 목록으로 뽑아주세요"(history.get 무제한)는 사서가 창고에 들어가야 한다.
우리가 후자를 아무 제한 없이, 여러 명이 동시에 시키고 있는 게 현재 상태다.

### 덧붙임: 수집 주기 실측 — "1분"의 근거 (2026-09-02)

캐시·사본 전략의 전제인 "자빅스 수집 주기 ≈ 1분"을 dev 자빅스(7.0.6)에서 전수 실측했다. 모니터링 중 아이템 11,714개:

| delay | 개수 | 비율 |
|---|---|---|
| 0 (dependent/trap — 자체 주기 없음, 마스터 아이템 수집 시점에 함께 갱신) | 7,636 | 65.2% |
| **1m** | **2,903** | **24.8%** |
| 3m / 5m / 1h / 15m / 10m / 30m 등 | 약 1,060 | 약 9.0% |
| 30s | 53 | 0.5% |
| 10s | 4 | 0.0% |

- 자체 주기를 가진 4,078개 중 **1m = 71%**, 1분 이상이 98.6%. **1분 미만은 57개(0.5%)뿐**이다.
- 정확한 명제: 수집 주기는 서버 전역값이 아니라 **아이템별 `delay` 설정이며 1초~1일 범위**다.
  즉 초 단위 수집도 가능하다 — 다만 1s 아이템은 하루 86,400행(1m의 60배)을 쓰므로
  자빅스 DB 비용 때문에 실무에서는 소수 핵심 아이템에만 쓴다.
- **"기본 1m"의 근거 사슬**: 공식 문서에 "기본값 1m"이라는 명문은 없다. 대신
  ① 공식 Linux 템플릿 YAML은 아이템 126개 중 88개에서 delay를 생략하는데(템플릿 내보내기는 기본값 필드를 생략),
  ② 그 생략된 아이템들이 서버에는 전부 `1m`으로 저장돼 있음을 실측으로 확인했다
  (`agent.ping`, `system.cpu.load[all,avg1]` 등 — Linux/Windows/macOS/SNMP 전 템플릿 공통).
- **설계 함의**: 30~60초 캐시가 깎는 신선도는 아이템의 99.5%에서 수집 주기 이하다.
  초 단위 수집이 화면의 주 대상인 고객이 나타나면 해당 조회만 TTL을 delay에 맞춰 내리면 된다(현재는 불필요).

## 3. 지금 우리가 자빅스 DB에 시키고 있는 일 (부하원 목록)

### 🔴 A. limit 없는 원시 데이터 조회 — 단건으로 제일 위험

| 위치 | 무슨 일이 벌어지나 |
|---|---|
| `HostService.getInterfaceDetails()` (`HostService.java:1862`) | 인터페이스 상세 화면. 사용자가 기간을 한 달로 잡으면 **괴물 테이블에서 한 달치 원시값을 limit 없이 전부** 긁는 SQL이 된다. 게다가 아이템 키 9개를 **9번의 `item.get`으로 따로따로** 찾는다(N+1) |
| `ItemsService` 차트 조회 (`ItemsService.java:103`) | 마찬가지로 limit 없는 `history.get`. 화면엔 점 몇백 개만 그리는데 원시값을 통째로 받는다 |

### 🔴 B. 같은 질문 반복 — 횟수로 때리는 유형

| 위치 | 무슨 일이 벌어지나 |
|---|---|
| `EventService.getStatusCounts()` (`EventService.java:173`) | 알람 화면의 "전체 N건 / 심각도별 N건" 배지 하나를 위해 `problem.get countOutput`을 **7번**(전체 1 + 등급 6) 부른다. 자빅스 DB는 거의 같은 COUNT 쿼리를 7번 받는다. 알림 벨(60초 폴링)에도 딸려가므로 **상시 부하** |
| 알람 목록 `/event/problems`, 호스트 목록 `/hosts/server` 등 | **캐시가 전혀 없어서** 사용자가 화면을 열 때마다, 새로고침할 때마다 자빅스에 그대로 전달된다. 접속자 20명 = 부하 20배 |

### 🔴 C. 배치가 매번 전체를 다시 묻기

| 위치 | 무슨 일이 벌어지나 |
|---|---|
| `EventSyncService.syncEventProblems()` (`EventSyncService.java:83`) | **1분마다** "최근 30일 문제 전부 줘"(`problem.get` time_from=now-30일, limit 10000) + `trigger.get` 2단 호출. 1분 사이 바뀐 건 몇 건인데 매번 30일치를 다시 받는다. **최대 상시 부하원** |

### 🔴 D. 만들어 놓은 사본을 안 쓰는 낭비

위 C의 배치가 받아온 데이터를 우리 PostgreSQL `event_problems` 테이블에 **잘 저장하고 있다.**
그런데 이 사본을 읽는 건 통계 화면(`EventStatsService`)뿐이고,
**정작 알람 목록 화면(`EventService`)은 사본을 안 읽고 매번 자빅스에 다시 물어본다.**
비용은 이미 내고 있는데 이득의 절반만 챙기는 상태.

### ❌ E. 방어선 자체가 없음

`ZabbixClient.java:41-52`를 보면:
- 타임아웃은 있다 (connect 10초 / read 30초) ✅
- **커넥션 풀 없음** — 요청마다 새 연결
- **동시성 제한 없음** — 사용자가 몰리면 Tomcat 스레드 수만큼 그대로 자빅스로 쏟아진다
- **재시도·서킷브레이커 없음**

즉 "우리 제품이 자빅스에 줄 수 있는 최대 부하는 얼마인가?"라는 질문에 지금은 **답이 없다.** 상한이 없으니까.

### 🟡 F. 요약 테이블을 놔두고 원시 테이블을 읽는 차트

기간이 길면 `history`(원시) 대신 `trends`(요약)를 읽는 분기가 **CPU에만** 있다(`CpuService.java:134`).
메모리·디스크·네트워크·인터페이스는 일주일짜리 차트를 그려도 원시 테이블을 긁는다.

## 4. 이미 잘 하고 있는 것 (다 나쁜 건 아니다)

| 항목 | 내용 |
|---|---|
| 캐시가 있는 화면 | 홈 요약(60초), 홈 시스템 상태(30초), 그룹 리소스/알람 추이(60초), 자빅스 구성 개요(60/300초), 자산 현황(60초) — 전부 Redis. **접속자가 늘어도 자빅스 부하가 안 느는 구조가 이미 절반은 깔려 있다** |
| 우리 DB에서 읽는 화면 | 이벤트 통계(`event_problems`), 그룹 리포트(`host_group_report`), 자산(`asset`) — 자빅스를 안 때리는 경로 3곳 존재 |
| 배치 호출 최적화 | 메트릭 어댑터(`ZabbixMetricAdapter`)는 "호스트 40 × 메트릭 2 = 80콜을 1콜로" 묶는 `BatchResolver`가 이미 구현돼 있다 |
| trends 사용 | 리포트·그룹 추이는 `trend.get`을 쓴다 |

→ 필요한 건 새 발명이 아니라 **이미 있는 패턴을 안 깔린 곳에 복사하는 것**이다.

## 5. 개선 전략 4가지 — 원리부터

### 전략 A. 같은 질문을 여러 번 하지 않기 (캐시)

사용자 100명이 같은 화면을 봐도 자빅스엔 60초에 1번만 묻고, 나머지 99명에겐 Redis에 적어둔 답을 준다.

- **효과의 본질**: 자빅스 쿼리 수가 "사용자 수"가 아니라 "TTL당 1번"이 된다. **접속자가 늘어도 부하가 일정.**
- 적용 대상: 알람 목록, 호스트/호스트그룹 목록 (현재 캐시 0인 최다 트래픽 화면)
- 트레이드오프: 최대 30~60초 늦은 정보. 실측상 아이템 99.5%가 수집 주기 30초 이상(§2 덧붙임)이라 통상 수용 범위

### 전략 B. 아예 우리 DB에서 읽기 (사본/롤업)

배치가 주기적으로 자빅스를 1번 털어 우리 PostgreSQL에 저장하고, 화면 조회는 전부 우리 DB가 받는다.

- **효과의 본질**: 자빅스 부하가 "사용자 수·화면 수와 무관한 상수(배치 주기당 쿼리 몇 개)"가 된다.
- 적용 대상 1순위: **알람 목록** — 사본(`event_problems`)이 이미 1분 주기로 채워지고 있으므로 **읽는 곳만 바꾸면 된다.**
- 이미 이 구조인 곳: 이벤트 통계·리포트·자산. APM도 자체 PG 롤업 구조. 제품 전체가 이 방향으로 수렴 중.

### 전략 C. 물을 때 싸게 묻기

같은 정보를 얻어도 더 싼 방법이 있으면 그걸 쓴다.

1. **카운트 7콜 → 1콜**: 목록을 한 번 받아 우리 서버 메모리에서 심각도별로 세면 끝
2. **item.get 9콜 → 1콜**: 키 9개를 한 번의 검색으로 (`searchByAny` 또는 `filter` 배열)
3. **긴 기간 차트는 trends로**: CPU에만 있는 "1시간 초과 → 요약 테이블" 분기를 메모리·디스크·네트워크·인터페이스로 복사
4. **`history.get`에 limit 상한**: 실수로도 괴물 테이블을 통째로 못 긁게 하는 안전핀
5. **배치 30일 → 증분**: "지난번 이후 새로 생긴/바뀐 것만 줘"로 변경. 쿼리 범위가 30일 → 1분

### 전략 D. 최대 부하를 "약속할 수 있는 숫자"로 만들기 (책임 경계)

부하를 줄이는 것과 별개로, **부하에 상한과 증거를 만드는** 작업. 고객사 대응에서 제일 중요하다.

1. **세마포어(동시성 상한)**: 자빅스로 나가는 동시 호출을 예컨대 10개로 제한. 초과분은 우리 서버 안에서 줄 세운다.
   → 그 순간부터 "본 제품은 자빅스에 동시 최대 10쿼리 이상 보내지 않습니다"를 **문서·계약에 적을 수 있다.**
2. **호출 계측**: `callRaw()` 한 곳에서 메서드별 호출 수·소요시간을 기록.
   → 고객사에서 "자빅스 느려진 거 무브즈아이 탓 아니냐"가 나왔을 때
   "지난 1시간 동안 우리는 이 쿼리를 이만큼, 평균 N ms로 했다"라고 **수치로 방어**할 유일한 수단.
3. **커넥션 풀**: 요청마다 새 연결 대신 keep-alive 재사용 (`HttpComponentsClientHttpRequestFactory`).
   자빅스 서버의 연결 수립 비용도 함께 줄어든다.

### 전략 E. 초 단위 실시간은 "묻지 말고 받는다" (Zabbix Connector — 요구 발생 시)

고객이 1초 단위 실시간 관제(예: 핵심 회선 트래픽)를 요구하는 경우의 노선. **폴링으로는 성립하지 않는다** —
1초마다 사용자별로 자빅스를 두드리는 건 이 문서가 없애려는 패턴의 극단이다. 방향을 뒤집는다.

```
[에이전트들] → 평소처럼 → [자빅스 서버] → Connector 푸시 → [우리 BE] → SSE → [화면 전원]
```

- **Zabbix 7.0 공식 스트리밍 기능(Connector)** 사용: 자빅스 서버가 값을 수집·저장하는 순간
  사본을 우리 BE 수신 엔드포인트로 HTTP 푸시(NDJSON)한다. **에이전트는 무변경** —
  바뀌는 건 자빅스 서버의 출구뿐(`zabbix_server.conf`의 `StartConnectors` + 프론트엔드 Connector 등록,
  **태그 필터로 대상 아이템 한정** 필수).
- 우리 BE는 받은 값을 SSE로 접속자 전원에게 중계한다(T5 허브 재사용, APM Live 스트림이 유사 선례).
  **자빅스 조회 부하 0** — 시청자가 100명이어도 자빅스는 우리 서버 한 곳에만 보낸다.
- **폴백**(고객이 자빅스 서버 설정을 못 바꾸는 경우): BE에 라이브 폴러 1개를 두고 1초마다
  `item.get` lastvalue만 조회(자빅스 value cache 메모리 조회라 history 테이블을 안 긁음) → SSE 중계.
  이때도 사용자별 폴링은 금지 — **시청자 수와 무관하게 초당 1콜 고정**.
- 대가는 수집·저장 쪽에 남는다: 1초 아이템은 하루 86,400행(1분의 60배)이라
  **소수 핵심 아이템 한정 + 해당 아이템 history 보존 단축**이 전제. 이 비용은 자빅스 운영(고객) 영역이다(§7).
- 제품화 형태: "핵심 아이템 N개 실시간 관제" 기능으로 만들어 **부하 상한을 기능 설계에 내장**한다.

## 6. 실행 계획 — 손대는 순서

싸고 효과 큰 것부터. 1~3번만 해도 화면발 부하의 대부분이 잡힌다.

| 순서 | 작업 | 전략 | 공수 감각 | 효과 |
|---|---|---|---|---|
| 1 | 심각도 카운트 7콜 → 1콜 (`getStatusCounts`) | C | 몇 시간 | 알람 화면·알림 벨 부하 1/7 |
| 2 | 알람 목록을 `event_problems` 사본 읽기로 전환 | B | 1~2일 | 최다 트래픽 화면이 자빅스에서 분리됨 |
| 3 | 알람·호스트 목록에 Redis 30~60초 캐시 | A | 1일 | 접속자 수 → 부하 비례 관계가 끊김 |
| 4 | `event_sync` 배치 30일 전량 → 증분 | C | 1~2일 | 최대 상시 부하원이 상수화 |
| 5 | `ZabbixClient`에 세마포어 + 커넥션 풀 + 계측 | D | 1~2일 | 최대 부하가 "문서에 적을 수 있는 숫자"가 됨 |
| 6 | trends 분기 확산 + `history.get` limit 상한 | C | 2~3일 | 괴물 테이블 접근이 요약 테이블로 대체 |

### 완료 후의 모습

- 화면 트래픽은 캐시와 사본이 흡수한다 → 접속자가 늘어도 자빅스는 모른다
- 자빅스가 받는 것 = **배치 주기당 증분 쿼리 몇 개 + 동시 최대 N콜** (둘 다 숫자로 명시 가능)
- 분쟁이 나면 계측 로그가 증거가 된다

이게 "책임을 던 상태"다.

## 7. 우리가 통제할 수 없는 것 — 문서로 경계 긋기

자빅스 DB가 느려지는 원인 중 우리 소관이 아닌 것들이 있다. **설치 가이드·운영 문서에 미리 명시**해서 책임 경계를 긋는다:

| 항목 | 내용 |
|---|---|
| Housekeeping (보존 기간) | `history`/`trends`를 얼마나 오래 쌓을지는 자빅스 설정이며 **고객 운영 몫**이다. 보존 기간이 과하면 테이블이 비대해져 어떤 조회든 느려진다 |
| 자빅스 DB 사양·튜닝 | DB 서버 리소스, 인덱스, 파티셔닝은 자빅스 설치의 일부 |
| 수집 주기·아이템 수 | 아이템을 초 단위 주기로 수천 개 돌리면 쓰기 부하만으로도 DB가 바쁘다 — 우리 제품과 무관 |
| 권장 문구 예시 | "본 제품은 Zabbix API만 사용하며 DB에 직접 접근하지 않습니다. API 호출은 동시 최대 N건으로 제한되며, 호출량은 로그로 확인할 수 있습니다. Zabbix DB 자체의 성능(보존 기간, 서버 사양)은 Zabbix 운영 정책을 따릅니다." |

## 8. 자주 나올 질문 (FAQ)

**Q. 자빅스 DB를 직접 읽으면(SQL) 더 빠르지 않나?**
빠를 수 있다. 하지만 자빅스 버전업 때마다 스키마 호환을 우리가 책임져야 하고, 우리가 짠 SQL이
고객 자빅스 DB에 락·풀스캔 사고를 낼 수 있으며, "자빅스가 느려진 게 무브즈아이 SQL 탓"이라는
공격에 방어 논리가 사라진다. **API 경유는 성능 선택이 아니라 책임 경계 선택**이다.

**Q. 부하를 아예 0으로 만들 수는 없나?**
없다. 모니터링 데이터의 원천이 자빅스 DB다. 가능한 건 "사용자에 비례하는 부하"를
"배치 주기당 상수 부하"로 바꾸는 것까지이고, 그게 위 전략 B다.

**Q. 캐시를 붙이면 정보가 늦게 보이지 않나?**
최대 TTL(30~60초)만큼 늦는다. 실측(§2 덧붙임) 기준 아이템의 99.5%가 수집 주기 30초 이상(대표 1분)이라
캐시 지연은 대부분 수집 주기 안에 묻힌다. 정말 초 단위가 필요한 건 알람 발생 알림인데,
그건 캐시가 아니라 서버 푸시(SSE)로 푸는 게 맞다.

**Q. 자빅스는 1초 수집도 되는데?**
맞다 — delay는 아이템별로 1초까지 내릴 수 있다. 다만 ① 초 단위 수집은 자빅스 DB 쓰기가 60배로 늘어
고객 쪽 비용이 먼저 커지는 설정이라 실무에선 드물고(우리 서버 0.5%), ② 알람 경로는 트리거 평가를
자빅스가 수집 즉시 하므로 아이템 주기와 무관하게 15초 증분+SSE로 흐른다. 영향은 캐시 경로 하나뿐이며,
초 단위 아이템이 주력인 환경에서는 그 조회만 TTL을 짧게 조정하면 된다.

**Q. 고객이 네트워크 트래픽을 1초 단위 리얼타임으로 보고 싶다면?**
가능하다 — 단 폴링이 아니라 **전략 E(Connector 스트리밍)**로 푼다. 자빅스 서버가 값을 받는 즉시
우리 BE로 밀어주고(에이전트 무변경, 서버 설정만), 우리는 SSE로 화면에 중계한다.
전제는 "모든 아이템"이 아니라 "핵심 아이템 몇 개만" — 1초 수집의 DB 비용(60배)은 자빅스 쪽에 남기 때문이다.
착수 전 명세받을 숫자 두 개: ① 진짜 필요한 주기(1s? 5s? — 대부분 '즉시 움직이는 느낌'은 5~10초로 충족)
② 대상 아이템 수.

**Q. 웹소켓/SSE를 붙이면 자빅스 부하가 늘지 않나?**
반대로 줄어든다. 지금은 알림 벨이 사용자마다 60초 폴링(그때마다 카운트 7콜 동반)인데,
SSE로 바꾸면 서버가 1분 배치 결과를 한 번만 계산해서 접속자 전원에게 밀어준다.
사용자 수 × 폴링이 → 배치 1회로 바뀐다.

**Q. 고객 자빅스가 원래 크고 느리면?**
그래서 전략 D(상한+계측)가 필요하다. 우리 부하가 상수임을 숫자로 보여줄 수 있으면
"제품 문제 vs 자빅스 운영 문제"를 데이터로 가를 수 있다. §7의 문구를 계약·설치 문서에 미리 넣어두는 것도 같은 이유다.
