# APM P1.5 — 실시간 관제(Live) 설계

- 작성: 2026-09-01. 상태: 🟢 **설계 + BE 구현 완료**(FE 미착수). 이 문서가 Live의 정본이다.
- 동반 문서: 아키텍처 `devdesign_apm.md` v3.1 · 화면/WBS `devdesign_apm-screens-wbs.md` · 범위 산정 `../backlog/apm-scope-reestimate.md` §2 · 계약 `../core/contract_apm-read-api.md` **§9**.
- 발단(사용자, 2026-09-01): *"실시간 유입량·액티브 트랜잭션·지금 어디서 장애가 나는지를 초 단위로."* 현행은 1분 버킷 + 30초 새로고침이라 **화면이 1~2분 전을 보여 준다**.

---

## 1. 목적 · 비목적

### 목적 — 이 화면이 답하는 세 가지
1. **지금 얼마나 들어오나** (rps, 10초 해상도)
2. **지금 몇 개가 처리 중인가** (액티브 트랜잭션)
3. **지금 어디서 터지고 있나** (최근 60초 오류·느린 엔드포인트)

### 🔴 비목적 — 일부러 안 하는 것
| 안 하는 것 | 이유 |
|---|---|
| **과거 조회** | 창은 15분뿐이고 **재기동하면 비어서 시작**한다(인메모리). 과거는 개요·서비스 화면의 일이다. |
| **DB 저장** | 10초 칸을 저장하면 행이 6배가 되는데, 그 6배는 15분만 살면 되는 데이터다. 파티션·롤업·보존을 다 통과시켜 가며 6배를 쓸 값이 아니다. |
| **모든 메트릭** | 링이 보는 것은 `http.server.request.duration`·`http.server.active_requests` **둘뿐**. JVM·DB·프로세스 지표는 10초 해상도가 필요한 값이 아니다(1분 차트로 충분하고, 링에 넣으면 메모리만 몇 배가 된다). |
| **다중 인스턴스 합산** | P1.5는 단일 인스턴스 전제(§6). |
| **알람** | 실시간 표는 보는 화면이다. 알람은 P1 알람 엔진(1분 집계 기반)이 그대로 한다. |

### 🔴 "초 단위"가 아니라 "30초 이내"다 — 문구까지 포함한 설계 결정
| 구간 | 지연 | 누가 정하나 |
|---|---|---|
| 앱 → 수집기 (`OTEL_METRIC_EXPORT_INTERVAL`) | **10초**(권장). 기본값은 **60초** | 🔴 고객 서버 설정 |
| 수집기 batch processor | 5초 | 우리가 생성하는 yaml |
| BE 버킷 폭 | 10초 | `app.apm.live.bucket-seconds` |
| SSE push · 전송 | ~0 | — |
| **합계** | **약 25~35초** | |

- 🔴 **에이전트가 기본 60초면 이 링은 60초마다 한 칸만 채워진다.** `bucket-seconds`를 1초로 줄여도 소용없다 — 알갱이를 정하는 것은 상류다. 설치 가이드가 `OTEL_METRIC_EXPORT_INTERVAL=10000`을 안내해야 하고, **안 하면 "실시간인데 왜 안 움직이나"가 된다**.
- 🔴 그래서 화면 문구는 **"실시간(약 30초 이내)"**이어야 한다. "실시간"만 적으면 계약 위반이다.

## 2. 데이터 흐름

```
 앱(OTel 자동계측)
   └─(10초)→ Collector ─(5초 batch)→ POST /apm/otlp/v1/metrics
                                        └→ OtlpMetricsReader
                                             └→ MetricIngestor
                                                  ① 수집기/앱 분리
                                                  ② 서비스 귀속
                                                  ③ 허용목록 + 구 semconv 정규화
                                                  ④ 차원 정규화(route 상한·status_class)
                                                  ⑤ CUMULATIVE 차분
                                                  ⑥ ApmMetric1mStore.store()  ← DB(1분)
                                                  ⑦ 🔴 stored > 0 이면 LiveBuffer.offer()
                                                                     │
                    GET /apm/live/snapshot ←── ApmLiveSnapshotService ┘
                    GET /apm/live/stream (SSE, 10초 tick)
```

### 🔴 훅이 ⑥ **뒤**에 있는 이유
저장이 실패한(=503으로 답할) 배치를 링에 먼저 넣으면, exporter가 재전송한 같은 배치가 한 번 더 더해져 **실시간 rps가 실제의 두 배**가 된다. 반대로 늦게 넣어 잃는 것은 없다 — 링은 "방금 저장된 것"을 보여 주는 창이다.

### 🔴 훅은 절대 던지지 않는다
`LiveBuffer.offer`는 모든 `RuntimeException`을 삼키고 WARN 한 줄만 남긴다. 여기서 예외가 올라가면 **이미 DB에 저장된 배치가 503**이 되고, exporter가 그것을 재전송해 1m UPSERT(덧셈)가 값을 두 배로 만든다. 실시간 화면 하나 때문에 저장된 데이터를 오염시킬 수는 없다.

### 관측 하나가 링에 담기기까지 (`LivePoint`)
`MetricIngestor.toRow`의 ⑤ **직후**에서 뽑는다. 그 자리에만 셋이 다 모여 있기 때문이다:
- **정규화된 차원** — route 상한 적용(`__other__`)·`status_class` 파생이 끝난 값. 한 걸음 앞에서 뽑으면 원시 route(카디널리티 무제한)를 받는다.
- **차분·단위 환산이 끝난 값** — 구 semconv(ms)도 여기서는 초. 뒤에서 다시 곱하면 1000배.
- **1분으로 자르기 전 관측 시각** — `ApmMetric1mStore.Row.bucketStart`는 이미 1분이라 10초 칸을 만들 수 없다.

> 이를 위해 `ApmDimsNormalizer.Dims`에 `values`(불변 맵) + `value(key)`를 추가했다. canonical JSON을 되파싱하지 않기 위한 것이고, 되파싱하면 절단·NFC·route 접힘 **이전** 값을 쓸 위험이 생긴다.

## 3. 링 구조

### 3.1 축이 둘인 이유 — 메모리
| 축 | 창 | 칸 수 | 무엇을 먹여 살리나 |
|---|---|---|---|
| **서비스 링** | `window-seconds` 900 | 90 | 흐르는 차트 3(rps·active·오류율) + p95 |
| **route 링** | `route-window-seconds` 60 | 6 | "지금 오류 나는 엔드포인트" 표 |

최악 어림(기본값):
```
서비스 링 : 200서비스 × 90칸 × 약 200B                 ≈  3.6 MB
route 링  : 200서비스 × 6칸 × 200route × 약 112B        ≈ 27   MB
```
🔴 **route를 창 전체(90칸)로 들면 같은 계산이 약 400MB다.** 그런데 그 표가 보는 창은 60초뿐이다 — 이 분리가 이 설계에서 메모리를 지키는 유일한 장치다. 실측 서비스의 route는 수십 개 수준이라 평소 점유는 한 자릿수 MB.

### 3.2 상한과 그 초과 처리
| 상한 | 기본 | 넘으면 | 왜 그 정책인가 |
|---|---|---|---|
| `max-services` | 200 | **LRU 축출** | 서비스는 실재하는 유한한 것이라 밀어내도 새는 것이 없다. 잃는 것은 그 서비스의 과거 15분뿐. |
| `max-routes-per-service` | 200 | **`__other__`로 접기(축출 아님)** | 🔴 밀어내면 새 route가 항상 들어올 수 있어 시간이 지나면 무제한이 된다 — 상한이 막으려던 바로 그 일이다(`ApmDimsNormalizer`와 같은 판단). |

⚠️ 적재 쪽 route 상한(`apm_setting.route_limit`, 기본 500)과 **다른 값**이다. 저쪽은 DB 카디널리티를, 이쪽은 힙을 지킨다. 이쪽이 더 작은 것이 정상이다.

### 3.3 버킷 정렬 · 회전
- `bucketStart = floorDiv(epochMs, bucketMs) × bucketMs` — 🔴 **에폭 기준 절대 정렬**(시간대·기동 시각 무관). 그래야 인스턴스·클라이언트가 달라도 같은 관측이 같은 `ts`를 갖고, 화면이 `ts`만 보고 덮어쓸 수 있다.
  - ⚠️ `apm_metric_1m.bucket_start`는 반대로 **KST 벽시계**다. 두 축을 섞지 말 것.
- 회전 = **덮어쓰기**. 같은 인덱스를 재사용하되 칸의 시각이 다르면 통째로 새 칸이다(시각 확인을 빠뜨리면 15분 전 값이 지금 값에 더해진다 — `LiveBufferTest`가 이것만 보는 테스트를 갖고 있다).
- **창 밖 관측은 버린다.** 과거 쪽은 회전이 현재 칸을 지우고, 미래 쪽은 아직 오지 않은 칸을 선점한다. 미래로 **한 칸**은 봐준다(에이전트 시계가 몇 초 빠른 것은 흔하다). 이 손실은 실시간 화면에만 있고 DB에는 이미 다 들어갔다.

### 3.4 집계 규칙
| 값 | 규칙 | 🔴 함정 |
|---|---|---|
| `requests` | 히스토그램 count 합 | |
| `errors` | `status_class == "5xx"`인 관측의 count 합 | 4xx는 오류가 아니다(클라이언트 잘못). 판정은 `MetricIngestor`가 끝내고 링에는 boolean으로 온다 — 수신 어휘가 개요 메뉴로 새지 않게. |
| `errorRatePct` | `errors/requests × 100`, **요청 0이면 `null`** | 0%로 칠하면 죽은 서비스가 초록으로 보인다. |
| `rps` | `requests / bucketSeconds`, **빈 칸은 0** | 여기만 null이 아니다 — 흐르는 차트에 구멍을 내면 조용한 구간이 장애처럼 보인다. |
| `activeRequests` | 그 칸의 **마지막 관측값** | 🔴 UpDownCounter라 **합이 아니다**. 더하면 인스턴스 수만큼 부푼다. 관측 없으면 null. |
| `p95Ms` | 정규 duration 격자(14단, 초)로 벡터를 합쳐 보간, ×1000 | 관측 0건이면 **null**(0이 아니다 — "p95 = 0ms"는 훌륭한 성능으로 읽힌다). 기록된 min·max로 추정을 **가둔다**(D2). |

### 3.5 🔴 p95는 접을 수 있을 때만 — D2와 같은 규칙
링은 여러 배치·인스턴스의 벡터를 **더해서** 들고 있으므로 칸마다 경계가 같아야 한다. 그래서 정규 duration 격자로 접는데, **접는 것이 분할이면 접지 않는다**(`HistogramRebucketer.mergesExactlyInto`). 그때는 **히스토그램만 버리고 `requests`·`errors`는 그대로 센다** — p95 하나 때문에 유입량을 잃는 쪽이 훨씬 나쁘다.

### 3.6 동시성
링 객체를 모니터로 삼는 `synchronized` 한 겹. 수신 스레드는 여럿(HTTP 워커), 읽는 쪽은 SSE tick 스레드와 조회 요청이다. 무잠금 구조는 "칸을 회전시키면서 동시에 읽는" 순간이 정확히 위험한데 그 순간을 값으로 증명하기 어렵다 — 임계 구역이 배열 인덱싱 수준이라 락 하나가 정직하다.

⚠️ 바깥 맵(`serviceId → Ring`)은 **접근 순서 LRU**라 읽기도 구조를 바꾼다. 순회 전에 `entrySet()`을 복사한다(안 하면 조회가 `ConcurrentModificationException`으로 수신을 죽인다).

## 4. 전달 — SSE

| | |
|---|---|
| `GET /apm/live/snapshot?serviceUid=&env=` | 창 전체 한 벌. 진입·수동 새로고침·스트림을 안 쓰는 경로 |
| `GET /apm/live/stream?serviceUid=&env=&visitorId=` | `text/event-stream` |

### 이벤트
| event | 언제 | 페이로드 |
|---|---|---|
| `snapshot` | **연결 즉시 1회** | 창 전체(90칸) |
| `bucket` | `bucket-seconds`(10초)마다 | 뒤쪽 `tick-buckets`(6칸=60초) |
| `heartbeat` | `heartbeat-seconds`(30초)마다 | `{ts}` |

- 🔴 **`snapshot`과 `bucket`은 같은 타입**(`ApmLiveDto`)이다. 다른 것은 `buckets` 길이뿐. 증분 전용 타입을 따로 두면 FE가 병합 코드를 두 벌 갖게 되고, 그 둘이 어긋나면 "새로고침하면 맞는데 실시간으로는 틀린" 화면이 된다. 병합 규칙은 한 줄 — **`(serviceUid, ts)`로 덮어쓴다.**
- 🔴 **증분이 1칸이 아닌 이유**: 파이프라인 지연이 25~35초라 방금 닫힌 칸은 대개 비어 있다. 뒤로 6칸을 겹쳐 보내고 화면이 `ts`로 덮어쓰면(멱등) 늦게 도착한 값이 자연스럽게 채워진다. **원안(1칸)에서 바꾼 유일한 지점**이고, 안 바꾸면 "실시간 차트가 항상 0"이 된다.
- `endpoints`는 순위표라 **증분에도 매번 전체가 실린다** — 한 행만 바뀌어도 순서가 통째로 달라질 수 있어 부분 갱신이 성립하지 않는다.
- 하트비트는 데이터가 없어도 보낸다. 프록시·LB가 조용한 연결을 끊는다(대개 60초).
- `tick` 스레드는 **연결 수와 무관하게 하나**다. 연결마다 타이머를 두면 100명이 볼 때 100스레드가 각자 링을 읽고 DB를 친다. 하나로 모으면 모든 사용자가 **같은 순간**의 창을 본다.
- 보는 사람이 0명이면 tick은 **DB도 안 읽는다**(야간 유휴 부하 0).

### 🔴 인증 — SSE의 두 함정
1. **`@VisitorIdCheck`를 스트림에 못 건다.** 브라우저 `EventSource`는 커스텀 헤더를 못 싣는다 → `x-visitor-id`를 **헤더로** 요구하면 이 EP는 브라우저에서 아예 못 부른다.
   - 인증 자체는 그대로다: `accessToken` **쿠키**를 `EventSource`가 자동으로 싣고 `JwtAuthFilter`가 검사한다(쿠키 우선 경로가 이미 있다). 미인증이면 컨트롤러에 도달하지 못한다.
   - 세션 바인딩은 **`visitorId` 쿼리 파라미터**로 받는다. 🔴 **2026-09-01 정정(4차 검수 🔴1): 필수다.** 쿼리 `visitorId` 또는 헤더 `x-visitor-id` 중 **하나는 반드시 있어야 하고**, 둘 다 없으면 401이다.
     - **원안이 틀렸다.** "주면 검사, 안 주면 통과"로 설계했는데, 그 한 줄이 세션 바인딩을 통째로 우회시켰다 — 다른 기기 로그인으로 Redis 세션이 교체돼도 `accessToken` 쿠키만 살아 있으면 스트림은 수명이 다할 때까지 흘렀다. 브라우저가 막힐 것을 걱정했지만 **FE는 언제나 `visitorId`를 붙인다**(쿼리 통로를 연 이유가 그것이다).
     - 판정은 **복제하지 않는다.** `VisitorIdCheckInterceptor`에서 검사 메서드를 `VisitorSessionChecker`로 뽑아 **둘이 같은 코드를 부른다** — 복제본이 갈라진 것이 이 결함의 원인이었다.
   - 헤더로 와도 같은 판정을 한다(`fetch` + `ReadableStream` 클라이언트 대응). 쿼리 우선, 없으면 헤더.
2. 🔴 **액세스 토큰을 쿼리로 받지 않는다.** SSE 인증에서 가장 흔한 사고 — 그 순간 토큰이 프록시·액세스 로그에 평문으로 남는다. `visitorId`는 토큰이 아니라 브라우저 식별자라 로그에 남아도 그 자체로는 인증에 못 쓴다(액세스 토큰과 **둘 다** 있어야 한다).

### ⚠️ 라이선스는 연결 시점에만 본다 — **최대 노출 10분(승인된 정책)**
`@RequiresFeature(APM)`은 인터셉터라 **연결을 여는 요청**에만 걸린다. 스트림이 열려 있는 동안 라이선스가 만료·회수되면 그 연결은 최대 `stream-timeout-seconds`까지 흐른다. tick마다 다시 읽으면 초당 조회가 되므로 그 지연은 감수한다.

**🔴 정책 결정(2026-09-01, 4차 검수 🟡5):** 감수하는 노출 창을 **30분 → 10분**으로 좁힌다. `stream-timeout-seconds` 기본값을 `1800 → 600`으로 내렸다.

- **왜 이 방법인가.** tick마다 재검사(초당 조회) · 라이선스 변경 시 전 연결 강제 종료(전역 이벤트 배선 필요) 두 대안보다, **수명을 줄이는 것**이 코드를 한 줄도 안 늘리고 창만 줄인다.
- **FE 영향 0.** 만료되면 브라우저 `EventSource`가 스스로 재접속하고, 그 재접속이 라이선스를 다시 검사한다. 사용자에게는 끊김도 보이지 않는다.
- **비용.** 사용자 한 명당 재연결이 30분에 1회 → 10분에 1회로 는다(연결 재수립 + 스냅샷 1회). 실시간 화면을 동시에 보는 사람이 수십 명 규모라 무시할 만하다.
- **이보다 더 줄이려면** 재연결 비용이 눈에 띄기 시작한다(스냅샷은 창 전체 90칸이다). 즉시 회수가 요구사항이 되면 그때는 timeout이 아니라 **라이선스 변경 이벤트에 열린 emitter를 닫는** 쪽으로 간다.

## 5. 설정 — `app.apm.live`

| 키 | env | 기본 | 의미 |
|---|---|---|---|
| `enabled` | `APM_LIVE_ENABLED` | `true` | 끄면 수신 훅 즉시 반환 + 조회는 `enabled:false` + 빈 목록(**404가 아니다**) |
| `window-seconds` | `APM_LIVE_WINDOW_SECONDS` | 900 | 링이 담는 시간 |
| `bucket-seconds` | `APM_LIVE_BUCKET_SECONDS` | 10 | 칸 폭 |
| `route-window-seconds` | `APM_LIVE_ROUTE_WINDOW_SECONDS` | 60 | route 축 창 — 🔴 메모리 지렛대 |
| `tick-buckets` | `APM_LIVE_TICK_BUCKETS` | 6 | tick이 겹쳐 보내는 뒤쪽 칸 수 |
| `max-services` | `APM_LIVE_MAX_SERVICES` | 200 | 링 보유 서비스 상한(LRU) |
| `max-routes-per-service` | `APM_LIVE_MAX_ROUTES_PER_SERVICE` | 200 | route 축 상한(`__other__` 접기) |
| `stream-timeout-seconds` | `APM_LIVE_STREAM_TIMEOUT_SECONDS` | **600** | SSE 연결 수명 — 🔴 라이선스 회수 반영이 늦어지는 최대 창(위 §4) |
| `heartbeat-seconds` | `APM_LIVE_HEARTBEAT_SECONDS` | 30 | 하트비트 주기 |
| `max-heap-mb` | `APM_LIVE_MAX_HEAP_MB` | 64 | 🔴 **조합의 상한**(2026-09-01 신설) |

- 🔴 **프로퍼티로 올린 기준**은 레포 규칙 그대로 "고객사마다 달라야 하는가"다 — 이 값들은 **힙 점유를 정한다**. 서비스 30개짜리와 300개짜리 설치본이 같은 숫자를 쓸 이유가 없다.
- ⚠️ 범위를 벗어난 값은 조용히 접지 않고 **기동을 실패시킨다**(`@Min`/`@Max`). 링 크기를 잘못 적으면 그 사실이 배포 뒤 힙에서 드러나는데, 그때는 이미 늦다.

### 🔴 값 하나씩이 아니라 조합을 검증한다 (2026-09-01, 4차 검수 🔴4·🟡6)

`@Min`/`@Max`는 값을 **하나씩만** 본다. 그래서 개별 최댓값을 전부 적으면 `2,000 × 5,000 × 600 = 60억` route 슬롯이 **검증을 통과한 채** 기동하고, 위 §3.1의 "최악 27MB" 어림은 그 조합에서 아무 의미가 없다 — 결과는 기동 직후 OOM이다. `ApmLiveProperties`의 컴팩트 생성자가 두 가지를 더 본다:

| 검사 | 규칙 | 실패 시 |
|---|---|---|
| **힙 예산** | `maxServices × slots × 200B` + `maxServices × maxRoutesPerService × routeSlots × 112B` ≤ `max-heap-mb` | 기동 실패. 메시지에 **추정치·상한·계산식·줄일 값**이 나온다 |
| **창 정렬** | `window-seconds % bucket-seconds == 0`, `route-window-seconds % bucket-seconds == 0` | 기동 실패. `slots()`가 내림이라 배수가 아니면 실제 창이 적어 둔 값보다 짧아지고(route 10초·bucket 60초 → 실제 60초) 그 차이는 화면·로그 어디에도 안 나온다 |

- **왜 WARN 후 내림이 아니라 기동 실패인가.** 그 WARN을 읽는 사람은 이미 이상을 눈치챈 사람이다. 설정값과 동작이 다른 상태는 몇 달을 조용히 간다.
- ⚠️ **슬롯당 바이트는 어림이다**(필드 수로 셌고 객체 헤더·정렬은 안 셌다). 이 검사는 "여기까지 안전"이 아니라 **"이 조합은 명백히 과하다"를 잡는 그물**이다. `max-heap-mb`를 실제 `-Xmx`의 절반 이상으로 잡지 말 것.
- 기본값 조합의 추정치는 **약 29MB**(서비스링 3.6 + route링 26.9)로 64MB 예산 안이다.

## 6. 다중 인스턴스 — P1.5는 안 한다, 승격 조건은 이것

**현재:** 링은 그 프로세스가 받은 것만 안다. BE를 두 대로 늘리면 수집기가 붙은 쪽에만 데이터가 있어 **화면이 절반만 움직인다**(그리고 그 사실이 화면에 안 드러난다 — 가장 나쁜 종류의 고장).

**승격 조건 — 하나라도 참이면 그때 한다:**
1. BE를 2대 이상으로 띄우는 설치본이 실제로 생긴다.
2. 수집기가 로드밸런서 뒤로 들어가 배치가 인스턴스에 흩어진다.
3. 실시간 화면을 무중단 배포 중에도 유지해야 한다(롤링 중 링이 반으로 갈린다).

**대안 설계(그때 착수):** Redis Stream — `XADD apm:live:<serviceId>`에 10초 칸 증분을 쓰고, 각 인스턴스가 `XRANGE`로 창을 읽어 합산. 링 자료구조는 그대로 두고 `offer`/`snapshot`만 뒤에 Redis를 붙인다(인터페이스가 이미 그 모양이다).
- ⚠️ **지금 Redis로 가면 안 되는 이유**: 수신 경로에 네트워크 왕복이 하나 붙는다. Redis가 느려지면 그것이 **적재 지연**이 되고, 적재 지연은 exporter 재전송 → 값 두 배로 이어진다. 단일 인스턴스에서 얻는 것이 없다.

## 7. FE 화면 스케치 (미착수)

**위치:** 개요(메뉴 1) 상단의 **"실시간" 토글**. 켜면 아래가 뜨고, 끄면 SSE를 끊는다(연결을 남기지 않는다).

```
┌─ 개요 ────────────────────────────────────────────────────┐
│  [실시간 ●]  약 30초 이내 · 15분 창          연결됨 ●     │  ← 문구가 "초 단위"라고 말하지 않는다
├───────────────────────────────────────────────────────────┤
│  ┌ 유입량(rps) ─────┐ ┌ 액티브 ────────┐ ┌ 오류율(%) ──┐ │
│  │  흐르는 라인      │ │  흐르는 라인    │ │ 흐르는 라인 │ │  ← 90점, 10초 간격
│  └──────────────────┘ └────────────────┘ └─────────────┘ │
├───────────────────────────────────────────────────────────┤
│  지금 오류 나는 엔드포인트 (최근 60초)                     │
│  서비스   METHOD  route        요청  오류  오류율  최대   │
│  주문     POST    /orders       412    37   9.0%   1.2s ⚠ │  ← topError
│  결제     GET     /pay/{id}      88     0     —    7.4s ⏱ │  ← topSlow
├───────────────────────────────────────────────────────────┤
│  서비스 카드 …  ● (실시간 점: 최근 칸에 트래픽이 있으면 켬) │
└───────────────────────────────────────────────────────────┘
```

**FE 구현 메모(계약이 아니라 권고):**
- 이벤트 병합은 **`(serviceUid, ts)` 덮어쓰기** 한 줄. 같은 `ts`가 여러 번 오는 것은 정상이다.
- ECharts 라인에 `append`가 아니라 **ts 키 맵 → 정렬 배열**을 쓴다. append는 늦게 도착한 값을 뒤에 붙여 시간축을 꼬이게 한다.
- `enabled:false`면 토글 자체를 비활성 + "이 설치본은 실시간이 꺼져 있습니다"를 보여 준다(빈 차트가 아니라).
- `route === "__other__"`는 **링크로 만들지 않는다** — 특정 경로가 아니라 상한에 걸려 접힌 묶음이다.
- `EventSource`는 끊기면 스스로 재접속한다. 재접속 시 서버가 `snapshot`을 다시 주므로 FE가 `/snapshot`을 따로 부를 필요는 없다.
- 서버 시각은 `serverTime`을 쓴다 — 브라우저 시계가 몇 분 어긋난 PC가 실제로 있다.

5. **재기동 후 빈 창** — 화면이 "데이터 없음"을 장애로 오인하지 않는가.
