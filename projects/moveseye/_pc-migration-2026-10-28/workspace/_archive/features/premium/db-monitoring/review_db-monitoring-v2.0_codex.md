**v2.0은 P0 실측의 출발 문서로는 조건부 사용 가능하지만, P1a 구현 기준으로 승인하기에는 부족합니다.** v2 델타에서 생긴 중대 보강 사항은 **중복을 합쳐 🔴 7건**입니다. 사용자 결정의 큰 방향은 타당하게 반영했으나, J2의 제어·보안·복구 계약과 §17의 종료 기준이 닫히지 않았습니다.

검수 범위는 [「검수 요청 4」](C:/solutions/_workspace/features/premium/db-monitoring/review_db-monitoring-design.md:173)에 지정된 델타와 기존 계약의 접점으로 한정했습니다. v1.3까지의 검수 완료 사항은 다시 문제 삼지 않았습니다.

## B. 중점 확인 요청 1~8 답변

### 1. D21 J2와 기존 계약의 정합성

#### (a) lease·fencing·J1/J2 인계 — 🔴

[§3.6](C:/solutions/_workspace/features/premium/db-monitoring/devdesign_db-monitoring.md:184)은 `collector_id` 소유와 J1/J2 동시 소유 금지를 적었지만, [§5.2](C:/solutions/_workspace/features/premium/db-monitoring/devdesign_db-monitoring.md:270)의 PG 기반 획득·10초 갱신을 J2가 어느 API로 수행하는지 없다. config pull 30초는 lease TTL 30초·갱신 10초 계약을 대신할 수 없으며, §5.8의 “BE 1대 사망 시 다른 노드가 인계”도 J1에 한정되지 않았다. fencing은 적재 차단이고, 고립된 옛 수집기의 DB 폴링 정지를 자동으로 보장하지 않는다.

**수정 문장:**

> “J1은 BE 노드 사이에서 자동 인계하며 수집 RTO ≤30s를 적용한다. J2는 할당된 수집기만 실행하며 자동 대기 수집기 인계는 제공하지 않는다. J2 lease 획득·갱신은 BE API가 PG에서 원자적으로 처리하고, 수집기는 갱신 실패 또는 실행 허가 만료 시 신규 tick을 중단한다.”

> “J1↔J2 전환·수집기 교체는 소유권 세대와 fencing token을 변경한다. 수신기는 인증된 수집기·대상 할당·소유권 세대·token을 적재 트랜잭션에서 확인한다.”

추가로 같은 `collector_id`를 복제한 두 프로세스의 동시 실행을 구별할 **실행 식별자와 재등록·교체 규칙**이 필요합니다.

#### (b) 마스킹·큐·로그·플랜 — 🔴

§3.6은 이미 **“§5.5 전부”와 수집기 측 `keep_raw_sql` pull**을 명시했으므로, 이 두 항목 자체가 누락된 것은 아니다. 그러나 “원문이 망을 건너지 않는다”와 원문 opt-in을 동시에 만족시키는 정책은 없고, “플랜 파싱은 BE”를 그대로 구현하면 마스킹되지 않은 플랜 XML의 파라미터·리터럴이 전송될 수 있다. 수집기 로그·진단 번들, BE HTTP 수신 로그와 수신 큐까지 실제 검사 지점을 지정해야 한다.

**수정 문장:**

> “수집기는 SQL·플랜·데드락 XML의 민감 필드를 제거한 뒤에만 디스크 큐와 전송 배치에 기록한다. BE의 플랜 처리는 이미 보호된 구조의 검증·저장·비교이며, 원본 플랜의 민감정보 제거를 BE까지 미루지 않는다.”

> “수집기와 BE의 예외 로그·진단 번들·수신 로그에는 SQL 원문·바인드·자격증명·토큰을 기록하지 않는다.”

**Q34 신설 제안:** J2에서 `keep_raw_sql`을 금지할지, 별도 승인된 원문 전송을 허용할지 결정해야 합니다. 현재의 무조건적인 “원문 비전송”을 유지하려면 J2에서는 해당 설정을 비활성화하고 이유를 표시해야 합니다.

#### (c) 공개키 재암호화와 §5.6 키 운영 — 🔴

BE 저장 암호화와 수집기 전달 암호화는 서로 다른 경계이므로 **방식 자체는 충돌하지 않는다.** 다만 [§5.6](C:/solutions/_workspace/features/premium/db-monitoring/devdesign_db-monitoring.md:316)의 BE key ID·복수 키·재암호화·롤백만으로 수집기 공개키·로컬 키스토어의 수명주기가 해결되지는 않는다. 공개키 등록의 소유 증명, 전달 봉투의 버전·무결성·대상 귀속, 키 교체 ACK와 폐기 절차가 없다.

**수정 문장:**

> “`enc:v2:<keyId>`는 BE 저장 암호화 형식이다. 수집기 전달에는 별도의 버전·수신 키 ID·대상 ID·자격증명 버전을 가진 암호화 봉투를 사용하며, BE 마스터 키는 배포하지 않는다. 공개키 등록·교체·폐기와 수집기 적용 ACK를 감사한다.”

> “자격증명 교체는 BE의 저장 성공과 수집기의 적용 성공을 구분하며, 풀 재생성·실패 롤백·옛 자격증명 폐기 시점을 정의한다.”

Q33의 **기본 보관 방식은 P1a 자격증명 모델 설계 전에** 결정해야 합니다.

#### (d) 시간 축 — 🔴

수집기 clock offset과 DB clock offset을 분리한 방향은 맞지만, §3.6의 **수집기 관측 시각 보정**은 §5.8의 **BE 수신 시각 기준**과 직접 충돌한다. 지연 배치를 수신 시각에 배치하면 과거 재생·AAS·알람 시점이 이동한다. heartbeat로 skew를 측정한다는 설명만으로는 RTT·보정 오차·보정값 유효기간을 알 수 없고, DB offset의 비교 기준도 BE인지 수집기인지 불명확하다.

**수정 문장:**

> “`observed_at`은 실제 채집 시각을 UTC 기준으로 표현한 값이며 `received_at`과 구별한다. J2는 수집기 원시 시각·적용 보정값과 보정 버전 또는 동등한 추적 정보를 보존하고, 재전송 시 `observed_at`을 변경하지 않는다.”

> “`db_clock_offset_ms`의 기준 시계를 명시하고 수집기 보정과 중복 적용하지 않는다. 시간 보정이 신뢰 범위를 벗어나면 품질 저하를 표시하며 세션 경과는 DB 보고값을 우선한다.”

### 2. GA 324~440과 코어 공유 전제 — 🟡

산술은 맞으며 Phase별 합도 **324~440**이다. [최초 독립 제안](C:/solutions/_workspace/_archive/features/premium/db-monitoring/proposal_db-monitoring_codex.md:156)은 동일 코어를 명시하고 원격형을 GA 215~315에 포함했지만, 읽은 최초 제안·협의서에는 **J2만의 25~35 증분 분해표가 없다**. 3차 검수는 이 수치를 기존 계획 계약으로 인정했으므로 철회할 이유는 없지만, “코덱스 1차 어림 그대로”를 독립 산출 근거처럼 사용하면 부정확하다. P1a 경계 설계·교체 테스트는 필요한 조건이나, 실제로는 lease·checkpoint·비밀정보·설정·시간까지 분리해야 하며 그 비용의 배정도 보이지 않는다.

**수정 문장:**

> “J2 25~35일은 동일 코어 재사용을 가정한 기존 계획상 증분 추정이다. P1a WS-2에 외부 의존 인터페이스 설계·검증 비용을 배정하고, R11·P3b·P4의 J2 작업을 분해한 뒤 총공수를 재확정한다.”

특히 **P0 R11은 추가됐는데 P0 22~34는 그대로**입니다. 25~35 안에 R11·P4 증가분이 들어 있는지, 기존 여유에 흡수한 것인지 밝혀야 합니다.

### 3. D17과 라이선스 커널·4파일 사본 규칙 — 🟢, 구현 세부 보강 필요

용량 초과 상태에서 기존 대상을 유지하는 정책과 만료·Feature 거부는 서로 다른 판단이므로, D17은 원칙 8 위반이 아니다. `LICENSE_LIMIT`는 DBM 알람 kind이고 `/dbm/license/usage`는 제품 API이므로 그것만으로 라이선스 enum 3개를 변경할 이유도 없다. **라이선스 계약 4파일 중 변경을 `LicenseClaims`에 한정**한다는 설명은 맞지만, 발급기 UI·검증·BE admission·API·테스트 등 실제 변경 파일까지 하나라는 뜻은 아니다.

**수정 문장:**

> “`OVER_LIMIT`는 DBM 용량 판정 결과이며 커널 상태가 아니다. 기존 활성 유지보다 상태·Feature 게이트를 먼저 적용한다. 라이선스 계약 사본 중 변경은 `LicenseClaims`에 한정하며, 발급기와 BE의 관련 구현·테스트는 함께 변경한다.”

추가로 다음을 닫아야 합니다.

- `0`·무제한 표현·음수·형식 오류의 의미.
- 라이선스 교체와 활성화 요청 사이의 원자성.
- 비활성 대상 재활성화와 J1↔J2 이동의 계산 방식.
- 상한 복귀 시 배너·알람 회복, 거부 이벤트의 중복 억제.
- 설치본 전체 `LICENSE_LIMIT`와 수집기 단위 알람의 subject 및 Zabbix 키. 현재 §7.2의 `dbm.<kind>[<target_uid>]`만으로는 부족합니다.

### 4. D20·RAC 시험 환경·P2 DoD — 🔴

RAC를 P2 구현 범위로 넣는 것과 제한적인 지원을 선언하는 것은 양립할 수 있다. 그러나 독립 인스턴스 두 개에서는 동일 RAC DB의 실제 원격 blocker·인스턴스 번호·SID 수명·시차 조건을 검증할 수 없으므로, §17.1의 모의 시험으로 D20 지원표까지 확정해서는 안 된다. 머리 변경 이력의 “완전 지원 선언은 R10 뒤”도 R10이 모의 시험일 수 있는 현 상태에서는 위험하다.

**지원표 문구 제안:**

> “RAC: 노드별 수집 및 원격 blocker 연결을 구현한다. 원격 노드 미등록·관측 시차·세션 수명 불일치 등으로 연결할 수 없으면 `unresolved`로 표시한다. **실제 RAC 인증 완료 전에는 미인증·PoC 대상으로 제공하며, 인증된 버전·구성만 지원표에 등재한다.**”

`GV$` 보강 여부는 조인 성공률만이 아니라 **오조인 0, unresolved 사유 분류, 추가 권한·조회 비용**을 함께 보고 결정해야 합니다.

### 5. D22와 config pull 만료 통지 — 🔴

GA에서 현 커널을 유지한다는 결정은 D10·§9와 일치하지만, D10·§9 앞부분·§16.3의 확정 상태 갱신은 남아 있다. §8.1·§9는 `/dbm/**` 전부 Feature 검사라고 하므로, 만료 시 config가 어떤 오류 본문을 반환하고 수집기가 이를 어떻게 구별하는지 적어야 한다. 또한 30초 config pull이 끊겼을 때 수집을 무기한 계속할 수 없으며, 토큰 폐기 “즉시 중단”도 원격 프로세스에는 그대로 보장할 수 없다.

**수정 문장:**

> “기존 Feature 거부 응답을 수집기 프로토콜의 `LICENSE_EXPIRED` 등 구조화된 사유로 매핑한다. 이는 자격증명이나 실행 설정을 반환하는 허용 경로가 아니다. 수집기는 유효기간이 있는 실행 허가와 만료 정보를 적용하며, 갱신하지 못하면 허가 만료 시 폴링을 중단한다.”

> “토큰 폐기는 BE의 수신·설정 발급을 즉시 차단한다. 원격 수집 중단의 최대 지연은 실행 허가 유효기간으로 한정한다.”

큐 보존 기간·라이선스 복구 후 재전송·보존 창을 지난 배치·옛 fencing token의 처리도 함께 정해야 합니다.

### 6. §17 착수 계획 — 🔴

R1~R11은 체크리스트에 모두 등장하고 WS 번호도 맞지만, **P0 종료 기준은 R1~R4와 R11 패키징 가능만 필수**여서 R5~R10이 미완료여도 P1a로 넘어갈 수 있다. R3의 큐·로그·번들 원문 0, R8·R11의 정량 기준, R9의 버전별 시험 등이 §17에서 축소됐고 R11 공수 배정도 없다. “J1 30 + J2 20”은 총 50 대상 검증으로는 맞지만 J2의 30 대상 상한이나 두 토폴로지의 동등성을 인증하지는 않는다.

**수정 문장:**

> “P0는 R1~R11 각각에 대해 통과 근거 또는 명시적인 차단·후속 게이트를 기록해야 종료한다. 미실시 항목을 통과로 처리하지 않으며, 해당 결과가 필요한 구현·지원 선언은 게이트 해소 전 진행하지 않는다.”

세부 사항은 D에 정리했습니다.

### 7. §16 v2 반영 누락 — 🟡

§16.2 J2 행과 §16.3 네트워크 행은 반영됐으며, “DB 서버 설치 없음”도 **별도 수집 서버에 설치하는 설계라면 사실상 맞다**. 다만 §16.3 도입부의 “설치가 없다”는 표현, 수집 서버 운영 요건, I6의 수집기 장애 원인과 P3b Phase, 라이선스 확정 상태·시간·드라이버 배포 설명이 남았다. §16.5-3의 Q26 미결 표현은 명백한 갱신 누락이다.

**수정 문장:**

> “J1은 별도 MovesEye 수집 프로세스를 설치하지 않는다. J2는 고객 수집 서버에 서비스를 설치하며, 대상 DB 서버에는 MovesEye 프로세스를 설치하지 않는다.”

> “J2 대상의 `STALE`에는 수집기 heartbeat 공백·버전 불일치·수신 인증 실패 등 원인을 연결한다. 수집기 장애는 `COLLECTOR_DOWN`으로 묶고 대상별 DOWN·STALE 알람 중복을 억제한다.”

§16.5에는 **J2 자동 HA 없음·수동 교체, 지연 재전송은 실시간 관측과 구별, 원문 정책**을 반영해야 합니다.

### 8. Q32·Q33 추천의 근거 — 🟡

Q32의 런타임 번들 권고는 폐쇄망 설치와 버전 고정을 단순하게 하므로 합리적이지만, **≈60MB·OS 3계열 GA·JDK 17+**는 아직 패키징·의존성 검증 결과가 아니다. Q33의 중앙 저장은 교체·감사 집중이라는 운영상 장점이 있으나, “망분리 금융”을 전제로 한 설계에서 금융 고객의 비밀정보 보관 정책 확인 없이 이를 기본값으로 확정할 근거는 부족하다. 그렇다고 금융이라는 이유만으로 로컬 보관을 일괄 강제할 근거도 없다.

**수정 문장:**

> “Q32는 재배포 조건을 확인한 특정 Java 배포판·버전·OS/아키텍처별 런타임 번들을 우선 검증한다. 실제 패키지 크기·서비스 등록·업데이트·롤백 결과로 지원 범위를 확정한다.”

> “Q33은 중앙 보관형과 수집기 로컬 보관형의 고객 보안 요구를 P0에서 확인하고, P1a 자격증명 모델 확정 전에 GA 기본 구성을 결정한다. 로컬 입력을 지원하지 않는 경우 해당 고객 제약을 명시한다.”

예를 들어 Temurin은 공식적으로 사용·수정·공유에 적용되는 라이선스를 안내하지만, 이것이 모든 JDK의 재배포 조건이나 이 제품의 패키징 검증을 대신하지는 않습니다. [Adoptium 공식 FAQ](https://adoptium.net/docs/faq?jvmVariant=hotspot&variant=openjdk17)

## C. §3.6 J2 설계의 구현 착수 적합성

“착수 가능”은 해당 행의 계약을 기준으로 구현해도 된다는 뜻입니다. “보강 필요”는 제품 결정을 다시 받을 사안보다 **설계자가 구현 계약을 완성해야 할 사안**입니다.

| §3.6 행 | 분류 | 필요한 보강·결정 |
|---|---|---|
| **1. 코어 공유** | **보강 필요** | writer 외에 lease·checkpoint·설정·비밀정보·시간·명령 전달 의존을 분리한다. 공유 코어가 PG·BE 빈·JPA·Spring에 직접 의존하지 않도록 경계와 검증 범위를 정한다. |

| **3. 인증** | **보강 필요** | enrollment의 1회 소비·공개키 결합·등록 권한, 토큰 회전 중 중첩 유효기간·재시도·폐기 지연을 정한다. 수집기 ID·할당 대상·실행 세대까지 인가한다. |
| **4. 자격증명** | **결정 필요—기존 Q33** | GA 기본 보관 방식의 결정 기한을 P1a 전으로 앞당긴다. 공개키·전달 봉투·로컬 키스토어·교체 ACK·롤백·폐기 계약을 추가한다. |
| **5. 마스킹 위치** | **결정 필요—Q34 신설** | J2 원문 보존/전송 허용 여부를 결정한다. 검사 지점을 로컬 큐 이전으로 고정하고, 플랜·데드락 XML·로그·진단 번들의 보호를 명시한다. |

| **7. lease·HA** | **보강 필요** | J1 자동 인계와 J2 수동 교체를 분리한다. BE 매개 lease API, 갱신 주기, 고립 시 정지, 동일 ID 중복 프로세스, 배정 변경 fencing을 정의한다. |
| **8. 버전 호환** | **보강 필요** | 제품 minor와 wire schema 버전을 구별한다. 엄격한 minor 일치 정책 아래 BE 업그레이드 시 중단·큐 호환·롤백·진단 heartbeat 유지 절차를 정한다. |
| **9. 시간** | **보강 필요** | §5.8과 `observed_at` 정의를 통일한다. offset 부호·RTT·불확실성·보정 유효기간·재전송 불변·DB offset 기준을 정한다. |
| **10. 배포 형태** | **결정 필요—기존 Q32** | Java 배포판/버전·OS/아키텍처·Windows 서비스 방식·설치 권한·오프라인 검증·업데이트/롤백을 R11로 확인한다. |
| **11. 관리** | **보강 필요** | 원격 대상의 접속 테스트·capability 검사·자격증명 교체가 어느 실행자에서 수행되는지 정한다. 비동기 작업 상태·수집기 감사·장애 원인·알람 subject를 추가한다. |

### 빠진 구현 계약

아래는 표의 보강 사항을 실제 설계 항목으로 풀어 쓴 목록입니다.

| 빠진 계약 | 구체적으로 정해야 할 내용 |
|---|---|
| **실행 허가와 설정 전파** | `config_version`·`assignment_generation`·적용 ACK·최대 지연·허가 만료·갱신 실패 시 정지. config pull 30s와 lease 갱신 10s는 별도 계약이어야 한다. `304 Not Modified` 때도 실행 허가 갱신 여부가 명확해야 한다. |
| **보안 설정 변경 중 배치** | 마스킹 강화·승인 키 변경·`keep_raw_sql` OFF·대상 비활성화 이후, 이전 설정으로 생성된 큐 데이터를 재검사·폐기·수락하는 기준. 배치에 적용 정책 버전을 추적해야 한다. |
| **수집기 로그·진단 번들** | 애플리케이션 로그뿐 아니라 JDBC 예외, HTTP 요청/응답, 서비스 시작 오류, 로컬 진단 번들, BE 수신 로그까지 보호 범위와 검사 위치를 지정한다. |
| **수집기 측 `keep_raw_sql`** | 설정 pull은 이미 있다. 빠진 것은 허용 범위·전송 여부·원문 저장 위치·열람권한·감사·정책 변경 시 큐 처리이다. |
| **플랜·데드락 XML의 전처리** | raw XML/JSON을 먼저 보내지 않는다. 수집기에서 민감 필드 제거가 완료된 표현을 만들고, BE가 재검사한다. 구조 파싱 실패 시 전송·보존 방식도 정한다. |
| **키 수명주기** | BE 저장 키, 수집기 전달용 키, 로컬 저장 키, API 토큰을 구별한다. 각 키의 ID·회전·복구·폐기·서비스 계정 접근·키 손실 진단을 정의한다. |
| **재시작 시 checkpoint** | 현재 §5.4는 PG checkpoint와 BE 재시작을 설명한다. J2에서 누적값 차분을 한다면 로컬 durable checkpoint가 필요하며, 큐 기록과 checkpoint 전진을 원자적으로 처리해야 한다. 복구가 불확실하면 baseline/partial로 처리한다. |
| **멱등 키와 ACK 원자성** | J2 전송 키는 `(collector_id,target,kind,epoch,seq)`, 저장 키는 `(target,kind,epoch,seq)`이다. 둘이 반드시 충돌하는 것은 아니지만 **epoch의 전역 유일 범위와 변환 규칙**이 필요하다. 데이터·수신 영수증을 함께 커밋하고 같은 키의 다른 payload는 오류로 처리한다. |
| **식별자·차원·quota** | 수집기에서 생성한 query/native/client 식별자를 BE surrogate ID와 어떻게 연결하는지, 차원 quota와 `__overflow__`를 어디서 적용하는지 정한다. BE PG에 직접 접근하는 코어는 J2에서 쓸 수 없다. |
| **배치 크기·압축** | 최대 행 수·압축 전후 바이트·flush 간격·단일 항목 상한·최대 동시 전송·분할·압축 방식·잘못된 payload 격리를 정한다. 수치는 R11로 정하되 계약 항목은 먼저 필요하다. |
| **백프레셔·큐 최종 포화** | 429/일시적 실패의 재시도 간격·jitter·최대 대기·대상 간 공정성을 정한다. 세션을 모두 버린 뒤에도 카운터·락만으로 256MB가 차면 어떻게 할지와, 폐기량을 잃지 않는 별도 기록 경로가 필요하다. |
| **BE 수신 인증 실패 분류** | 잘못된/폐기된 토큰, 할당되지 않은 대상, 만료·Feature 거부, 옛 lease, 버전 불일치, schema 오류, 과부하를 구별한다. DB 계정 `AUTH_FAILED`와 혼동하지 않고, 재시도 중단·설정 재조회·운영 개입을 각각 연결한다. |
| **수집기↔대상 수 상한** | ≤30은 초기 시험값의 근거는 있지만 MovesEye 인증값은 아니다. 엔진 혼합·세션 수·샘플 간격·namespace·플랜 크기·TLS·CPU/heap·네트워크 조건을 고정한 인증 프로필과 초과 할당 처리가 필요하다. |
| **원격 작업 전달** | 등록 마법사의 접속 테스트·capability 검사, on-demand 캐시 플랜, 자격증명 교체·재개를 outbound-only 환경에서 전달할 작업 모델이 없다. 작업 ID·대상 귀속·TTL·결과·취소·멱등 규칙을 추가한다. |
| **늦은 데이터와 상태·알람** | 재전송 배치를 과거 버킷에 반영하는 기한, 롤업 재계산, 만료 파티션 처리, 과거 데이터로 현재 장애를 다시 여는 문제를 정의한다. 수집기 장애·수신 거부·라이선스 중단은 대상 DB DOWN과 구별한다. |
| **배포·운영 동등성** | J2의 JDBC 드라이버·DB TLS trust store·BE TLS 신뢰·프록시 설정·업데이트 순서·큐 schema 호환·폐기 시 비밀정보 정리를 명시한다. BE 재시작만 적힌 기존 드라이버 안내를 J2에도 적용 가능하게 바꿔야 한다. |

Datadog의 **Agent당 최대 30 DB 인스턴스 권고는 실제 공식 근거가 있습니다.** 다만 그 문서도 DB 복잡도에 따른 Agent 과부하·수집 지연을 이유로 들므로 MovesEye의 성능 보증을 대신하지 않습니다. [Datadog DBM 문제 해결 문서](https://docs.datadoghq.com/database_monitoring/troubleshooting/?tab=postgres)

### P0 순서·완료 기준·공수

| **R4** | `<1s`는 일치한다. §11의 WAL·APM 동시 부하·파티션 DROP 검증이 빠졌다. | bytes/row 외 WAL·롤업·동시 부하·정리 안전성 및 J2 추가 메타데이터 비용을 결과표에 포함한다. |

| **R6** | “ojdbc 재배포 조항 1줄”은 §11의 법무 확인·실제 로딩보다 축소됐다. J2 런타임 번들도 추가됐다. | 배포물 목록·적용 조건 확인·로딩 결과를 요구한다. R11 패키지에 포함될 Java/드라이버도 검토 범위에 넣는다. |
| **R7** | “Q11 확정 자료”만으로 실제 출력·마스킹·큐/로그·완전성 비교 완료를 판정할 수 없다. | §11 R7의 비교 항목을 완료 기준으로 연결한다. |
| **R8** | §11의 RTO ≤30s·이중 적재 0·가짜 급증 0이 §17에 없다. | 정량 기준을 유지하고, J1 자동 인계와 J2 고립·수동 교체 시험을 구별한다. |
| **R9** | §11은 2016·2019·2022 시험인데 §17 환경은 2022만 있다. | 누락 버전 시험을 확보하거나 미실시 상태와 해당 지원표 확정 게이트를 명시한다. 2022 결과로 전 범위를 통과시키지 않는다. |
| **R10** | 독립 인스턴스 두 개로 실제 RAC 조인 성공률을 산출할 수 없다. | 모의 fixture 결과와 실제 RAC 인증 결과를 분리하고, 실제 환경 확보 기한을 P2/P4 게이트에 둔다. |
| **R11** | §11의 **중복 0·회전 중단 <10s·30 대상 CPU 1코어 미만** 대신 §3.6의 시험 목록만 참조한다. memory 통과값도 없다. | 수치·workload·하드웨어·메모리/큐 기준을 명시한다. 토큰 회전과 폐기는 구별해서 시험한다. |
| **P0 종료** | R5~R10을 닫지 않고도 종료할 수 있다. “패키징 가능”은 R11 전체 통과도 아니다. | R별 판정표와 후속 차단 게이트를 필수 산출물로 한다. 미실시·실패·조건부 통과를 구별한다. |

### 코드 골격·첫 스프린트·Phase DoD

| **계약서** | `contract_db-monitoring.md`를 먼저 산출하는 것은 적정하다. J2를 고려한 배치 식별·시간·오류·소유권 필드를 P1a 데이터 모델 전에 포함해야 한다. |

| **D17 경고와 배달 Phase** | WS-26은 P1a인데 공통 알람 평가는 P1b다. P1a의 배너·거부·상태 API와 P1b의 외부 알람 배달을 구분해서 DoD에 적는다. |

| **P4 HA ≤30s** | J1 수집 자동 인계에 한정한다. J2 수동 교체와 BE 수신 API의 장애 복구를 하나의 HA RTO로 표현하면 안 된다. |

| **Flyway V90** | **재확인 절차는 적정하다.** §17.1·17.2·17.5가 번호 선점 가능성을 인정한다. `V90__...`은 예시임을 명시하고 실제 migration 생성·병합 직전 최신 번호를 다시 확인하면 된다. 이번 검수에서는 코드를 읽거나 번호를 재검증하지 않았다. |

첫 스프린트 문구는 다음 수준으로 구체화하면 됩니다.

> “첫 스프린트는 PG 대상 1개의 등록→수집→보호→적재→조회 최소 흐름과 라이선스 admission을 목표로 한다. 공통 식별·시간·소유권·정책 버전 계약을 먼저 고정하며, 각 WS의 이번 스프린트 완료 범위와 이월 범위를 별도 표로 제시한다.”

| **Q32** | P0 중 / P1a 전 | 서로 모순되지 않는다. 다만 OS 전체 지원은 실제 패키징·운영 검증으로 확정한다. |
| **Q4·Q6·Q31** | 후속 기한·결정 불필요 | 현재 제외 상태를 유지하면 착수 차단이 아니다. 이후 결정으로 기존 GA 범위에 조용히 편입하지 않도록 변경 절차만 유지한다. |

## E. 종합 판정

### 중복을 합친 🔴 7건

| ID | 중대 보강 사항 | 닫아야 할 시점 |
|---|---|---|
| **V4-1** | J2 소유권·lease 갱신·고립 시 정지·토큰 폐기·라이선스 거부의 제어 계약 부재 | P0 시험 계약에 반영하고 **P1a 공통 모델 전에 확정** |
| **V4-2** | 원문 비전송과 `keep_raw_sql`, 전송 전 플랜 보호와 BE 파싱 문구 충돌 | **P1a 보호 계약 전**, Q34 결정 |
| **V4-3** | 수집기 키·자격증명 수명주기 및 Q33 기본 방식 미확정 | **P1a 자격증명 모델 전** |
| **V4-4** | J2 관측 시각과 §5.8 수신 시각 정의 충돌·보정 기준 부재 | **P1a 배치·파티션·API 계약 전** |
| **V4-5** | J2 checkpoint·큐·ACK·epoch·멱등 키·늦은 배치 복구 계약 부재 | P0 R8/R11 시험 기준에 반영, **P1a 코어 경계 전에 확정** |
| **V4-6** | §17 P0 종료 기준 축소와 R11 공수·완료 기준 미배정 | **P0 종료 판정 전** |
| **V4-7** | 모의 RAC 시험·일부 J2 엔진 시험이 GA 인증으로 이어지는 게이트 부족 | 인증 계획은 P0 종료 전, **해당 지원 선언 전 실환경 검증** |

이 7건은 본문 곳곳의 같은 문제를 중복 집계하지 않은 수입니다. 확정 대기 문구 잔존·Phase 표기·공수 출처 표현·Q 기한 등은 별도 편집·계획 보강 사항입니다.

### P0 실측 착수 기준으로 사용할 수 있는가

**🟡 조건부 가능입니다.** 환경 확보, 최소 권한, 마스킹 fixture, 용량 시험, 코어 경계 prototype을 시작할 정보는 있습니다. J2의 계약 공백을 확인하는 것 자체도 R11의 타당한 목적입니다.

다만 다음 조건이 필요합니다.

- 미정인 J2 계약은 **시험 가정**으로 표시하고 운영 계약 확정으로 취급하지 않는다.
- 실제 자격증명을 전달하거나 원문·플랜을 전송하는 시험 전에 해당 보호 경계를 먼저 정한다.
- R1~R11 결과표와 미실시 항목의 후속 차단 게이트를 마련한다.
- 독립 인스턴스 두 개의 결과를 RAC 인증으로 기록하지 않는다.
- R11 및 J2 검증 비용의 Phase 배분을 P0 종료 때 재산정한다.

따라서 현재 머리의 **“P0 실측 착수 가능”은 유지할 수 있지만, “v2 필수 결정이 끝났으므로 구현 계약도 준비됐다”는 의미로 사용하면 안 됩니다.**

### P1a 구현 기준으로 사용하려면

**현재 상태로는 승인하지 않습니다.** V4-1~V4-5의 공통 데이터·보안·실행 계약을 먼저 닫고, V4-6의 P0 종료 판정을 충족해야 합니다. V4-7의 실제 인증 완료는 해당 Phase까지 남길 수 있지만, 시험 환경·기한·지원 제한은 P0 종료 전에 확정해야 합니다.

구현 기준 문서에는 최소한 다음이 필요합니다.

1. **J1/J2 실행·제어 계약:** 소유권, lease, 설정 버전, 허가 만료, 교체, 라이선스 차단.
2. **배치·복구 계약:** 시간, epoch/seq, checkpoint, 큐 원자성, ACK, fencing, 늦은 데이터.
3. **보안 계약:** Q33 기본 구성, 키 운영, 전송 전 보호, Q34 원문 정책, 로그·진단 범위.
4. **검증·계획 정합본:** R1~R11 판정표, Phase별 인증표, 앞당긴 Q 기한, 공수 배분, 수정된 DoD.

설계서·검수서·경험 Vault는 변경하지 않았으며, 코드도 열람하거나 작성하지 않았습니다.
