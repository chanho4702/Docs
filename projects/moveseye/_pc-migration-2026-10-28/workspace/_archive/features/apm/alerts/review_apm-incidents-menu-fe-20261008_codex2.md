## 🟡 권장

- 비배수 `offset` 테스트는 첫 요청 정렬과 URL 보정 호출을 고정하지만, 1차 의견에서 언급한 “다음 페이지가 `offset=40`으로 이동하는지”까지 직접 검증하지는 않습니다. 페이지 전환 테스트와 `updateParamsMock` 1회 호출 단언을 추가하면 회귀 방지력이 더 높아집니다.
- `limit=20 → 30`, `offset=40 → 30` 재정렬 테스트도 권장합니다. 현재 구현은 정상 동작하지만 이 경로는 테스트되지 않았습니다.

## 🟢 참고

- 요청 걸림 `open=1` 빈 상태는 `apm.incidents.empty_stuck_open`으로 분기되며 kr/en 문구와 켬·끔 테스트가 모두 맞습니다.
- `apmAlertEventsPath()`는 `open=0`을 포함하며 개요의 개별 행·전체 보기와 홈 위젯 더보기 세 곳에서만 사용됩니다. 메뉴는 원시 `/incidents` 경로이므로 기본 “열린 것만”을 유지합니다.
- 홈 위젯 목록은 “시간 창 안에 발화한 알람”이므로 더보기를 현재 열린 알람이 아닌 발화 이력(`open=0`)으로 보내는 판단이 맞습니다.
- `useAlignedPagination`은 렌더 중 정렬값을 계산하므로 첫 API 요청부터 `offset=20`입니다. URL 보정은 effect에서 `replace`로 수행되고, 정렬 완료 후 문자열 비교로 중단되어 무한 replace나 history 누적 가능성은 없습니다.
- `limit`이 바뀌면 계산된 `offset`도 다시 정렬됩니다. `offset=0`으로 정렬될 때만 URL 키를 삭제하며, `DmoveTable`의 페이지 번호·다음 페이지 계산과 일치합니다. 알람·걸림 두 탭 모두 동일한 훅을 사용합니다.
- 권한 축 관련 주석 두 곳도 실제 가드와 훅별 권한에 맞게 정정되었습니다.
- 신규 테스트는 빈 상태와 해소 알람 링크를 직접 고정하며, 비배수 `offset`의 핵심 원인인 첫 요청 정렬도 두 탭에서 고정합니다.
- 제공된 diff와 실제 작업 트리를 읽기 전용으로 검토했으며 파일은 수정하지 않았습니다. 테스트 결과는 요청서 §8의 실행 결과를 기준으로 확인했습니다.
