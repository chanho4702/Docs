## 부록 C. 자주 하는 질문

**Q1. 서비스 목록에 내 앱이 안 뜬다.** 순서대로: ① `OTEL_SERVICE_NAME`을 줬나(없으면 `unknown_service:*`로 격리, 수집기 › 등록 탭의 "이름 없는 앱") ② 등록 모드가 APPROVE면 승인 대기 ③ 수집기 › 상태 탭 "최근 60초 수신"이 있나(없으면 Collector·토큰·방화벽) ④ 폐기 표에 `NOT_ALLOWLISTED`로 구 semconv 이름이 쌓이나(Node·Python opt-in) ⑤ AI '/apm 수집 안 되는 원인'.

**Q2. 실시간 화면과 1분 표 숫자가 다르다 — 버그인가?** 아니다. 다른 저장소·다른 시각 축(링은 exporter 시각 에폭 10초 칸, 1m은 KST 벽시계 닫힌 분). 정본은 1분 표. 링은 저장된 것을 조금 일찍 보여 주는 창일 뿐(적재 성공 후 훅).

**Q3. p95 칸이 `—`다.** `mixedBounds`(경계 혼재 — SDK 교체 과도기) 또는 관측 0. 건수·오류율은 정확하다. "해상도 조정됨" 배지(`rebucketed`)는 값이 있되 근사.

**Q4. 404가 오류율에 왜 안 들어가나?** 4xx는 클라이언트 잘못. 오류율·SLI·알람 전부 5xx만. 상태 코드 원값은 저장하지 않는다(`status_class`).

**Q5. 가용성 스트립에 빈칸이 있다.** "답할 수 없는 칸"(보존 밖이거나 읽는 단의 버킷이 칸보다 굵다). `UNKNOWN`(수집기도 조용했다)과 다르고 둘 다 분모에서 뺀다. 판정된 칸 0이면 `null`.

**Q6. exemplar 링크가 회색이다.** `stored:false` — 메트릭은 100%인데 트레이스는 tail 2%라 처음부터 저장된 적이 없다. 만료(`APM_TRACE_NOT_FOUND`)와 다르다.

**Q7. 에러 화면 건수가 창보다 많아 보인다.** 1시간 버킷 합이라 "발생(1시간 단위 근사)". 목록·정렬은 정확.

**Q8. 알람은 떴는데 Slack이 안 온다.** 알람 규칙 › Zabbix 상태 탭: "알림 액션 없음" 배지면 고객이 Zabbix 액션(호스트 그룹 `MovesEye APM` 조건)을 만들어야 한다. `drift` 배지면 사용자가 트리거를 고쳤다. `state=1`이면 잘못된 값 타입.

**Q9. SLO를 껐는데 Zabbix Problem이 남아 있다.** 09-08 이전 빌드. 지금은 끄기 직전 `−1`을 밀어 회복 이벤트를 만든다(2회차 QA 실증).

**Q10. 합성 감시 캘린더가 30일을 못 채운다.** `coveredDays` — Zabbix history 보존에 잘린 것. 빈 날을 0%로 읽지 말 것.

**Q11. 배치 화면이 빈다.** `job.name` 규약(루트·INTERNAL·속성) 미준수가 대부분. 실행 중인 잡은 스팬이 끝나야 오므로 안 보인다.

**Q12. RUM 세션 수가 GA보다 훨씬 많다.** 정의가 다르다(페이지·브라우저·OS·국가·5분 버킷별 distinct의 합). 비교하려면 PV.

**Q13. RUM 요청이 브라우저에서 막힌다.** 순서: CSP `connect-src`에 MovesEye origin → 토큰의 origin allowlist에 **정확 문자열**(포트·대소문자 포함) → 회수 여부 → 상한(429 `Retry-After`).

**Q14. 체크박스를 껐는데 APM 메뉴가 보인다.** 관리자 역할(우회 세 겹) → 역할 행 `apm` 두 벌 → 라우트에 역할 prop. 반대는 V48 적용 여부·FE 키 이름.

**Q15. 라이선스가 만료되면 무슨 일이?** 수신 403 → Collector가 즉시 폐기(디스크 큐에도 안 남음). 조회 잠김. 파티션·롤업·보존·리포트 배치는 계속. 갱신하면 그 순간부터 복구(만료 중 데이터는 없다).

**Q16. K8s 재시작 배지가 5분 뒤 꺼진다.** 배지는 "이 창에서 최근", 시각(`restartedAt`)은 이력. 시각은 텔레메트리 관측 시각이지 실제 종료 시각이 아니다.

**Q17. Collector를 두 대 두면?** tail 샘플링이 갈라져 무의미. active-standby만. active-active는 `loadbalancing` 2계층(승격 항목).

**Q18. 화면이 느리다 — 승격인가?** 먼저 PG `work_mem`([7.8절](12-operations.md)). 그 다음 [3.6절](03-constraints.md) 3축(목록 cold 3초·6h RED 1.5초·1m 20M행/일).

**Q19. 실시간 관제에 "진행 중인 요청" 목록이 왜 없나?** OTel 스팬은 `end()` 시점에야 배치 큐로 들어가 export된다 — 시작 이벤트 자체가 없어서 어떤 exporter에도 "처리 중"인 요청은 아직 안 나타난다. 지금 볼 수 있는 것은 "몇 개가 처리 중인가"(`http.server.active_requests` **개수**만, 10~60초 리듬)뿐이고, "그 요청들이 얼마나 오래 걸리고 있나"는 Java 에이전트 확장이 시작 이벤트를 새로 만들어야 하는 P5.3b 몫이라 아직 없다. [18-p5-realtime.md](18-p5-realtime.md) §10.5.

**Q20. 서버를 재시작했더니 실시간 화면이 텅 비어 있다 — 데이터가 날아갔나?** 그 자체가 설계다. 라이브는 DB를 안 쓴다 — arena·ring·사전이 전부 BE 한 프로세스의 인메모리이고 창은 15분(907칸)뿐이다. 재시작·재배포 순간 그 15분이 통째로 사라지고 다음 스팬부터 새로 채워진다. 지난 데이터가 필요하면 트레이스 탐색(샘플·7일 보존)으로 간다. [06-data-path.md](06-data-path.md) §5.3 · [18-p5-realtime.md](18-p5-realtime.md) §10.2·§10.5.

**Q21. X-View 배지의 "표시 n / 관측 m"이 무슨 뜻인가?** `m`은 그 시간 창 버킷의 `stats.count` 합(수신·집계 **전체**), `n`은 화면이 실제로 그린 고유 `(traceId, spanId)` 수(서버 보관 예산과 브라우저 표시 한도를 통과한 **표본**)다. 어느 부하에서도 "화면 전량"은 약속하지 않고, 이 줄은 상시 표시라 접히지도 숨지도 않는다. `base.observed`와 `emphasis.observed`를 단순히 더하면 같은 요청을 두 번 세는 함정도 있다(v0가 실제로 그렇게 셌다). [18-p5-realtime.md](18-p5-realtime.md) §10.2·§10.4.

**Q22. 제니퍼처럼 초당 유입 곡선(TPS 게이지)은 왜 없나?** 우리가 셀 수 있는 것은 "끝난" 요청뿐이라 속도계·이퀄라이저는 전부 **완료 처리량**이다. 긴 요청이 한꺼번에 몰리면 실제 유입은 늘어도 완료 곡선은 오히려 내려간다 — 유입 자체를 세려면 Q19와 같은 시작 이벤트가 필요하다. [18-p5-realtime.md](18-p5-realtime.md) §10.5.

**Q23. "실시간"인데 왜 화면에 몇 초씩 늦게 뜨나?** 스팬이 끝나 SDK 배치 큐에 들어가고(기본 지연 5초) Collector가 1초 배치로 export하고 BE가 1초 tick으로 집계·발행하는 각 단계가 전부 하한을 보탠다. 권장 SDK 설정(`OTEL_BSP_SCHEDULE_DELAY=1000`) 없이는 저트래픽 서비스의 완료→캡처 p95가 5.7초까지도 나온다 — 그래서 화면 문구가 항상 "권장 설정 시"를 달고 있다. [12-operations.md](12-operations.md) §7.12 · [18-p5-realtime.md](18-p5-realtime.md) §10.3·§10.9.

**Q24. 라이브를 켜면 저장 경로(트레이스 저장)가 느려지나?** 같은 Collector receiver에서 두 파이프라인으로 갈라지는(fan-out) 구조라 CPU·메모리가 완전히 격리되지는 않는다. 비격리 호스트 실측에서 정상 CPU 증가율이 합격선(1.20배)을 넘겨(1.49배) **FAIL로 남아 있고**, 저장 처리량·지연은 관측 범위 안에서는 PASS였지만 더 엄격한 계약 기준(ID 집합·DB 대조)으로는 아직 안 쟀다. 즉 지금 시점에는 "느려지지 않는다"고 단정할 수 없다 — 격리 환경 재측(R2′)이 출시 게이트로 남아 있다. [18-p5-realtime.md](18-p5-realtime.md) §10.7 R2.

**Q25. 동시 요청 타일이 0인데 실제로는 요청이 들어오고 있다 — 버그인가?** 아니다. 값이 없거나 마지막 관측이 90초를 넘은 인스턴스는 "0"이 아니라 **"관측 없음"**이고, 타입도 `number | null`로 둘을 가른다. stale 인스턴스는 합계에서 빼고 "⚠ j 인스턴스 관측 없음"을 같이 보여준다 — 화면 전체에 걸친 원칙("관측 없음 ≠ 0")이 여기서도 그대로 적용된 것뿐이다. [18-p5-realtime.md](18-p5-realtime.md) §10.4 (1).

### P5.3b 진행 중 요청·요청 걸림 `[2026-09-23 추가]`

**Q. 요청 관제 탭 "진행 중 요청"이 "확장 없음"이다.** — 고장이 아니다. 이 카드는 **앱 JVM에 붙인 자바 확장 jar**(`-Dotel.javaagent.extensions=moveseye-otel-extension-0.2.0.jar`)가 보내는 값만 그린다. 스팬은 끝나야 export되므로 확장 없이는 진행 중 요청을 볼 방법이 없다([18](18-p5-realtime.md) §10.5·§10.10). 자바가 아닌 서비스도 같다(다른 언어 확장은 미착수).

**Q. 원판 숫자·동전 수가 1초 스냅샷과 다르다(조금 크다).** — 의도된 것이다. 확장은 1초마다 그 순간의 분포 한 장을 보내는데 0.3초짜리 요청은 그 사이에 끝나 스냅샷에 안 걸린다. 그래서 무대는 들어온 공이 닿으면 동전을 **최소 1.5초** 놓고, 원판·합계도 동전과 같은 수를 적는다(사용자 결정). 스냅샷보다 많은 몫은 **옅은 점선 동전**이다. 도움말이 "지금 + 최근 1.5초 안에 들어왔거나 끝난 요청"이라고 적는다.

**Q. 공 개수 = 요청 수인가?** — 아니다. 초당 8개 상한이라 폭주 때는 공 하나가 여러 건이다. 정확한 양은 레일 아래 **초당 건수** 숫자다.

**Q. 처리 중 요청이 5초 넘게 빨간 동전으로 계속 남는다.** — SSE·long-polling·웹소켓 업그레이드처럼 **원래 오래 열리는 연결**일 가능성이 크다. 확장 옵션 `exclude-paths`에 그 경로 접두를 넣는다([12](12-operations.md) §7.14). 안 넣으면 요청 걸림 규칙이 60초마다 그것을 장애로 적는다.

**Q. 요청 걸림 탭의 "관측 끊김"은 무슨 뜻인가?** — 그 요청이 끝났다는 뜻이 **아니다**. 인스턴스나 확장이 사라져 15초 넘게 목록을 못 받았을 뿐이다. "끝남"은 새 목록에 그 요청이 없을 때만 적는다.

**Q. 요청 걸림 알람은 왜 5분 배치가 아니라 바로 뜨나?** — 근거(처리 중 목록)가 메모리에 90초만 살아서 5분 배치가 보면 그 사이 걸렸다 풀린 요청을 놓친다. 그래서 1초 감시기가 판정한다. Zabbix에도 그 순간 값(최대 경과 ms)을 밀고 풀리면 0을 민다. 다른 5종 규칙은 그대로 5분이다.

**Q. 부하가 있을 때만 처리 중 목록이 비고, 한가하면 빈 목록이 잘 들어온다.** — 2026-09-23에 겪은 실제 결함의 증상이다. 수집기 `redaction/pii`의 카드번호 패턴(`\d{13,16}`)이 목록 로그 본문의 13자리 숫자를 가려 JSON이 깨지고 BE가 통째로 버렸다. 지금 확장은 본문에 13자리 이상 숫자를 두지 않는다. 같은 증상이 다시 보이면 BE DEBUG 로그 "처리 중 요청 목록 본문 파싱 실패"를 본다.

**Q. "서비스별 지금 처리 중" 막대 차트가 없어졌다.** — 2026-09-23에 뺐다. 무대의 서비스 줄이 같은 정보를 동전으로 보여 줘 중복이었다.

**Q. BE 기동이 `max-heap-mb` 예산 초과로 실패한다.** — 2026-09-23부터 예산식에 진행 중 요청의 1초 이력·목록이 들어와 기본값이 192→384MB가 됐다. `APM_LIVE_MAX_HEAP_MB`를 명시적으로 낮게 둔 설치본은 그 값을 올리거나 `max-services`·`max-routes-per-service`를 줄인다(메시지가 어느 항이 큰지 적어 준다).

### 실시간 관제 동시 시청 `[2026-09-23 추가]`

**Q. 실시간 통신은 웹소켓인가?** — 아니다. **SSE**(Server-Sent Events, `EventSource`)다. 서버→브라우저 한 방향만 필요하고 재접속·`Last-Event-ID`를 브라우저가 알아서 해 주며 아파치·방화벽 설정이 일반 HTTP와 같다. 브라우저→서버 방향은 기존 REST 호출이 한다. 웹소켓이었다면 프록시 업그레이드 설정이 하나 더 필요했을 뿐 성능 차이는 없다([18](18-p5-realtime.md) §10.6 5단계).

**Q. 여러 명이 동시에 실시간 관제를 보면 서버가 힘들어지나?** — 기본 상한 안(활성 40·대기 10·계정당 4)이면 아니다. 직렬화는 **화면 조건(viewKey)마다 한 번**이고 바이트는 연결들이 공유하며, 느린 브라우저 하나는 그 연결만 끊긴다(코덱스 의견 `_archive/features/apm/realtime/review_apm-live-sse-concurrency_codex.md`). 인원이 늘 때 먼저 느는 것은 힙이 아니라 **송신 대역폭**과 아파치 worker 점유다. 상한은 2026-09-23부터 설정(`app.apm.live.spans.stream.*`)이지만 [12](12-operations.md) §7.12a의 🔴 확인 없이 숫자 하나만 올리지 않는다. 아파치 경유 부하 시험은 아직 안 했다(백로그 B7).

**Q. "대기 n번째"가 떴다 — 고장인가?** — 아니다. 활성 상한이 찼거나 새 화면 조건(서비스·환경·창 길이 조합)이 동시 snapshot 상한(2)보다 많이 열린 것이다. 연결은 살아 있고 앞 연결이 빠지면 자동으로 시작한다. 15초마다 재시도되는 `429 APM_LIVE_TOO_MANY_CONNECTIONS`는 대기열도 찼거나 **그 계정이 이미 탭 4개**(숨긴 탭 포함)를 연 것 — 다른 탭부터 닫는다. 증상→원인→손댈 키 표는 [12](12-operations.md) §7.12a.

**Q. 지금 몇 명이 보고 있는지 어디서 보나?** — 실시간 관제 화면 헤더의 "내 연결 n/4 · 전체 시청 a/40"(15초 갱신), 자세한 수는 `GET /apm/live/spans/stats`(계약 §5.2a — 연결 분포·상한·거절 누적, 계정 식별자 없음), 기동 직후 유효 상한은 BE 로그 한 줄. 2026-09-23 밤 신설(B7 #4).

**Q. 안 보는 탭이 내 슬롯을 잡고 있다.** — 요청 관제 탭 헤더의 **연결 끊기**를 누르면 그 탭의 슬롯이 즉시 돌아온다("다시 연결"만 남는다). 대기 배너에도 같은 버튼이 있고, 이 계정의 연결이 2개 이상이면 "탭 m개" 안내가 붙는다. 브라우저 탭끼리 연결 하나를 나눠 쓰는 것(SharedWorker)은 아직 안 했다(B7 #2 ①).
