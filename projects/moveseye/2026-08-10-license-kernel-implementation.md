## 이 세션의 한 줄

**"테스트가 green인 것"과 "동작하는 것"이 다른 자리를 여섯 번 만났다.** 그중 넷은 테스트를 일부러 망가뜨려서, 둘은 서버를 띄워 DB를 열어 봐서 찾았다. 기능을 만든 시간보다 **"이 테스트가 진짜 뭔가를 막고 있나"를 확인한 시간이 더 값어치 있었다.**

## 1. 🔴 안전망이 가짜였던 세 가지

### ① P18 테스트가 순서 결함을 못 잡았다 — 뒤집어도 통과

라이선스 인터셉터는 **인증·권한 뒤**에 서야 한다(P18). 앞에 두면 만료된 토큰이 401 대신 잠금 화면으로 보여 FE의 자동 refresh가 끊긴다. 그래서 "인증 없이 호출 → 401" 테스트를 짰다.

`WebConfig`에서 순서를 **일부러 뒤집었더니 테스트가 그대로 통과했다.**

> 👉 **Spring Security 필터 체인은 `DispatcherServlet`보다 앞이다.** 인증되지 않은 요청은 인터셉터를 어디에 등록하든 필터가 먼저 401을 낸다. 즉 그 테스트는 **순서와 무관한 것을 검증하고 있었다.**

실제로 순서가 갈리는 것은 **인터셉터끼리 겨루는** 경로였다 — `VisitorIdCheckInterceptor`는 필터가 아니라 인터셉터라, 라이선스를 앞에 두면 세션 불일치(401)가 `LICENSE_REQUIRED`(403)로 가려진다. **유효 JWT + 틀린 `x-visitor-id`** 로 다시 짜니 뒤집었을 때 정확히 그 1건이 실패한다.

**교훈: "A가 B보다 먼저다"를 테스트할 때, A와 B가 정말 같은 링에서 겨루는지부터 확인하라.** 다른 계층이 이미 결론을 내고 있으면 그 테스트는 아무것도 지키지 않는다.

### ② 게이트를 켜자 권한 테스트가 거짓 통과로 바뀌었다

라이선스 게이트를 켜니 기존 IT 6건이 막혔다(게이트가 동작한다는 증거). 그런데 **"일반 USER는 거부된다"류 권한 계약 테스트는 전부 통과**하고 있었다.

> 👉 **라이선스 잠금도 바디 `code=403`이다.** 권한 검사를 통째로 지워도 라이선스가 대신 403을 내주므로 green이 유지된다. 그 순간 `AuthorizationContractIT`는 권한을 검증하지 않는 테스트가 됐다.

`IntegrationTestSupport`가 **실제 서명된 키를 실제 테이블에 심어** 게이트를 열도록 했다. 테스트 전용 우회 스위치는 만들지 않았다(P11 — dev·QA도 실제 키를 등록해 쓰는 것이 방침).

**교훈: 전역 게이트를 추가하면 그 게이트와 같은 코드로 실패하던 기존 테스트가 전부 무의미해진다.** 게이트를 켠 직후 "무엇이 여전히 통과하는가"를 의심할 것.

### ③ 컴파일러는 "구현했는지"만 알지 "검사를 불렀는지"는 모른다

엔진 포트 데코레이터 3종(14메서드)에서 `queryLatestFamily`·`queryTrendFamily` **두 개를 빠뜨렸고 컴파일러가 잡았다.** 운이 좋았던 것이다 —

> 👉 **포트에 `default` 메서드가 하나라도 있었으면 컴파일도 통과했다.** 그 경로만 게이트 없이 조용히 열린 채 남는다. 더 흔한 실수는 오버라이드는 했는데 **위임만 하고 `check()`를 빠뜨리는 것**인데, 이건 어떤 컴파일러도 못 잡는다.

그래서 테스트를 메서드 나열이 아니라 **리플렉션으로 인터페이스 전 메서드를 훑도록** 짰다. 포트에 메서드가 추가되면 자동으로 따라간다. `queryLatest`에서 게이트 한 줄을 빼니 **그 메서드 이름을 지목해** 실패한다.

**교훈: 데코레이터·프록시처럼 "N개를 빠짐없이 감싸야 하는" 구조는 개별 테스트가 아니라 목록을 훑는 테스트로 지켜라.**

## 2. 🔴 런타임에서만 드러난 결함 2건 (775건 green인 상태에서)

T7까지는 전부 테스트 레벨이었다. T8에서 BE를 실제로 띄우고 **발급기가 만든 실물 키**로 등록해 보니 둘이 나왔다.

### F-1. `registered_by`가 항상 null — 감사 추적이 통째로 비어 있었다

판정 6(재사용 방지)을 확인하려고 dev DB의 `license` 테이블을 열었더니 `registered_by`가 **전 행에서 비어 있었다.** API는 정상 200을 내고 있었다.

원인은 **액세스 토큰 JWT에 `username` 클레임이 없다**는 것이었다(`id`·`userRole`·`roleid`·`userid`만 실린다). 즉 `currentUser.getUsername()`은 인증된 요청에서 **언제나 null**이다.

> 🔴 **이건 이미 알려진 함정에 다시 빠진 것이다.** 과거 `asset_activity`의 actor가 null이던 것이 같은 원인이었고, 그때 만든 `ActorResolver`(username 클레임 우선 → 없으면 id로 조회)가 이미 코드베이스에 있었다. 새 코드가 그걸 모르고 `getUsername()`을 직접 썼다.

**왜 테스트가 못 잡았나: IT는 응답 shape과 상태 전이를 봤지 DB 컬럼 값을 보지 않았다.** null이 들어가도 INSERT는 성공하고 API는 200이다.

**교훈: "기록한다"는 기능은 응답이 아니라 저장된 값을 봐야 검증된다.** 그리고 **한 번 만든 resolver/헬퍼는 새 코드가 모른다** — 같은 함정이 재발하면 그건 개인의 실수가 아니라 발견 장치가 없다는 뜻이다.

### F-2. 잘못된 본문이 HTTP 500 `Internal server error`

검증 스크립트에서 PowerShell `ConvertTo-Json`이 문자열을 `{"value":…,"Length":675}` 객체로 감싸는 바람에 `licenseKey`에 객체가 갔고, 서버가 500을 냈다. **검증 도구의 실수가 서버 결함을 노출한 경우다.**

`HttpMessageNotReadableException`에 전용 매핑이 없어 catch-all로 빠진 것이었다. 이 API의 계약은 **200 + 바디 `code`**인데 실제 500이 나갔고, 무엇보다 **사용자가 고칠 수 있는 입력 오류**다 — 등록 화면이 "서버 내부 오류"만 받으면 재시도 외에 안내할 것이 없다.

**교훈: 에러 계약을 정해 둔 프로젝트에서 catch-all로 빠지는 예외는 곧 계약 위반이다.** "정상 shape만 보내는 테스트"는 이걸 영원히 못 잡는다.

부수로 **없는 경로도 404가 아니라 500**(`NoResourceFoundException` 미매핑)임을 발견했다. 같은 부류이고 라이선스 범위 밖이라 기록만 남겼다.

## 3. 설계가 실제와 부딪힌 곳

### 등록 기한을 판정에 쓰면 등록 8일째에 정상 고객이 잠긴다

`activationDeadline`은 M5로 "발급 후 7일"이 기본이다. 그런데 `LicenseKeyVerifier.verify()`가 그 검사를 포함하고 있었고, 판정 경로(매 요청 재검증)에서 같은 메서드를 쓰려던 참이었다.

> 🔴 그대로 갔으면 **등록 8일째에 모든 고객이 통째로 잠긴다.** 영구 라이선스도 예외가 아니다.

기한은 **미등록 키의 수명**이지 등록된 라이선스의 수명이 아니다. 등록용 `verify()`와 판정용 `parse()`로 갈랐고, 테스트가 판정 경로에서 `verify()`가 불리면 실패시킨다.

**교훈: 같은 "검증"이라도 등록 시점 검증과 상시 판정은 조건이 다르다.** 메서드 하나를 재사용할 때 "이 조건이 두 경로 모두에서 참이어야 하나"를 물어야 한다.

### ArchUnit A5를 설계서 원안대로 지킬 수 없었다

원안은 `@LicenseExempt`를 `license..`·`auth..`로 제한하는 것이었다. 실제로 붙여 보니 **FE 부팅 경로 둘**(`GET /users/my-profile`·`/users/role/permission`)이 `user` 패키지에 있었고, 이 둘이 막히면 사용자 정체성을 못 받아 **잠금 화면조차 그리지 못한다.**

패키지로 열면 `user` 전체가 열리므로 **메서드 이름 허용 목록**으로 좁혔다. 목록을 늘리려면 테스트를 고쳐야 하고 그러면 리뷰에 걸린다 — "면제는 의도적 결정이어야 한다"는 A5의 목적은 유지된다.

**교훈: 구조 규칙은 실제 코드에 붙여 보기 전엔 범위를 확정할 수 없다.** 원안을 고집하면 규칙을 끄게 되고, 그게 규칙이 죽는 경로다.

### 배치 게이팅의 기본값은 "막는 쪽"

`SchedulerJob.requiresActiveLicense()`의 default를 `true`로 뒀다. 새 배치를 추가하며 잊으면 "만료 고객 서버에서 수집이 계속 도는" 쪽이 아니라 **"만료되면 멈추는" 쪽으로 기운다.** 열려면 명시적으로 `false`를 적어야 한다.

`cleanup` 계열만 `false`다 — 보존 기간 정리까지 멈추면 만료된 설치본의 디스크가 무한정 찬다. 건너뛴 실행은 **이력에 남기지 않는다**(성공으로 적으면 거짓 성공, 실패로 적으면 만료 기간 내내 알람).

## 4. 설계서가 SSOT로 실제 작동했다

작업 중 **다른 세션이 라이선스 FE를 독립적으로 만들고 있었다.** 내 BE 커밋은 미푸시라 그쪽은 내 코드를 볼 수 없었는데, 계약을 대조해 보니:

| | 결과 |
|---|---|
| 응답 필드 9개 | 전부 일치 |
| 경로 3개 (`GET /features`, `POST/DELETE /settings/license`) | 일치 |
| multipart 파라미터명 `file` | 일치 |
| 등록 에러코드 5종 | 일치 |
| 파일 상한 64KB | 일치 |

양쪽이 설계서 §5.4를 정본으로 따랐기 때문이다.

> 👉 **"설계서를 SSOT로 둔다"가 추상적 구호가 아니라 실제로 두 구현을 맞춘 사례다.** 단 **설계서에 없는 것은 맞지 않았다** — 게이트 errorCode 4종(`LICENSE_REQUIRED`·`READ_ONLY`·`FEATURE_REQUIRED`·`LIVE_BLOCKED`)이 FE에 전혀 없다(grep 0건). 등록 화면은 완성돼도 **잠금 화면·배너·업셀이 뜨는 조건이 바로 그 넷**이다. §5.4가 등록 API만 상세히 적고 게이트 응답은 §5.3에 흩어져 있던 탓으로 보인다.

**교훈: 계약 문서의 커버리지가 곧 구현 일치의 커버리지다.** 문서에서 덜 눈에 띄는 자리에 있는 계약은 양쪽에서 똑같이 누락된다.

## 5. 런타임 검증에서 확인한 상태 머신 (실측)

| `expires_at` | state | mode | 실시간 | 쓰기 | DB 조회 |
|---|---|---|---|---|---|
| +200d | `ACTIVE` | FULL | ✅ | ✅ | ✅ |
| +10d | `EXPIRING` | FULL | ✅ | ✅ | ✅ |
| −5d | `GRACE` | FULL | ✅ | ✅ | ✅ |
| −40d | `EXPIRED` | READ_ONLY | **✅ 유지** | ❌ | ✅ |
| −100d | `ARCHIVED` | READ_ONLY | ❌ `LICENSE_LIVE_BLOCKED` | ❌ | ✅ |

[[2026-08-06-license-kernel-design]]에서 실측(엔진 포트 20개 클래스)이 만들어낸 M8의 답 — **시간축을 넣어 단계적으로 차단** — 이 런타임에서 그대로 동작한다. `EXPIRED`와 `ARCHIVED`는 `mode`로 구분되지 않고 **실시간 조회 하나로만 갈린다.**

그 외 실측으로 닫힌 것: 발급기 공개키 == 제품 번들 `public-1.pem`, 기동 로그 `라이선스 공개키 1개 로드`(classpath 스캔 — **테스트는 검증기 빈을 갈아끼워 이 경로를 안 탄다**), 발급 키 클레임에 **`exp` 없음**(P12가 발급기에서도 지켜짐), 재등록 시 `activated_at`이 **마이크로초까지 동일**.

## 6. 도구에서 겪은 함정 (Windows/PowerShell 5.1)

[[2026-08-06-license-kernel-design]]의 `.bat` 한글 함정에 이어, 검증 스크립트에서 또 걸렸다.

| | |
|---|---|
| `ConvertTo-Json` | 문자열을 `{"value":…,"Length":…}` 객체로 감쌀 때가 있다 → JSON 직접 조립 |
| **BOM 없는 `.ps1`** | PS 5.1이 MS949로 읽어 **스크립트 본문의 한글이 깨진다** → 검증 스크립트는 ASCII로 |
| `-SkipHttpErrorCheck` | PS 7+ 전용. 5.1은 `$_.Exception.Response`에서 본문을 직접 읽어야 |
| `$x = Call ...` | 할당 우변의 명령 호출은 **괄호 필요** |
| 판정 캐시 60초 | DB를 직접 고치는 경로는 캐시를 모른다 → 63초 대기 |

👉 **한글 인코딩 함정이 이 프로젝트에서만 세 번째다**(`curl -d` cp949 → `.bat` cmd 파싱 → `.ps1` MS949). Windows 도구로 한글을 다루는 경로는 **처음부터 ASCII로 우회**하는 게 빠르다.

## 7. 발급기 웹 UI (별도 저장소, 커밋 `6692f69`)

BE 커널을 끝낸 뒤 발급 쪽 마지막 빈칸을 채웠다. `issue.bat --web` → `http://127.0.0.1:877`,
폼 입력 → `.lic` 다운로드 → 발급 대장 조회.

**만든 이유가 곧 이 프로젝트의 반복 문제다** — CLI로 발급하려면 고객사명을 `.bat` 인자로 넘겨야 하는데
Windows에서 한글이 들어가는 순간 사고가 난다(§6). **브라우저 폼은 UTF-8이라 그 경로가 통째로 사라진다.**
실측으로 `"주식회사 한글고객사"`가 클레임 → 제품 등록 → DB(28바이트)까지 온전히 왕복했다.

**Spring Boot를 넣지 않았다.** 더블클릭으로 쓰는 사내 도구라 기동이 빨라야 하고, 무엇보다
**개인키를 들고 도는 프로세스일수록 의존성이 적은 편이 낫다.** HTTP는 JDK 내장 `HttpServer`,
템플릿은 Thymeleaf 하나만 추가했다(자동 이스케이프 때문 — 고객사명이 화면에 다시 나온다).

**서명·대장을 `LicenseIssuerCore`로 추출**해 CLI와 웹이 공유한다. 진입점이 둘로 갈린 뒤
한쪽만 고치면 "CLI로 낸 키와 웹으로 낸 키가 다르게 서명되는" 사고가 나므로 구조로 막았다.

### 개인키를 들고 있는 서버의 기본값

| | |
|---|---|
| 바인딩 | 기본 `127.0.0.1` — 같은 PC만 |
| `--host` 변경 | **`--token` 없으면 기동 거부** (실수로 여는 쪽이 훨씬 흔하다) |
| 다운로드 | **발급 대장에 있는 파일명만** 허용 — 아니면 `../keys/private-key.pem`에 개인키를 그대로 내준다 |

👉 **"사내 도구니까"가 보안 기본값을 낮출 이유는 아니다.** 이 프로세스는 실행 중인 동안
발급 권한 그 자체다. 거부는 기동 시점에 해야 한다 — 열어두고 조심하는 것은 방법이 아니다.

### 여기서도 한글에 걸렸다 (네 번째)

`Content-Disposition`에 한글 파일명을 raw로 넣었더니 **HTTP 헤더가 깨져 브라우저가
"프로토콜 위반"으로 거부**했다("CR 뒤에는 LF가 와야 합니다"). HTTP 헤더는 ASCII만 담는다 —
RFC 6266대로 ASCII 대체명 + `filename*=UTF-8''`를 함께 보내야 한다.

그리고 **정리하다 방금 문서화한 함정에 스스로 빠졌다** — PowerShell로 UTF-8 대장 CSV를
읽고 쓰면서 한글을 깨뜨렸다(복구함). 👉 **함정을 아는 것과 안 밟는 것은 다르다.**
UTF-8 텍스트 파일은 PowerShell로 편집하지 말 것.

곁가지: Thymeleaf `@{...}` 링크 표현식은 `IWebContext`(서블릿)를 요구해 순수 `TemplateEngine`
에서는 못 쓴다. URL을 서버에서 조립해 넘겼다(파일명 인코딩도 서버에서 해야 안전).

## 8. 08-11~12 — 배치 분산 잠금 · FE 게이트 · 브라우저 검증

### 배치 분산 잠금 (커밋 `57c63e5`, 라이선스와 별건)

배포 전 필수로 등재돼 있던 항목. 중복 실행 가드가 `volatile boolean isRunning`, 즉 **JVM 로컬
플래그**라 인스턴스가 둘이면 같은 배치가 겹쳐 돌고 리포트 upsert가 서로를 덮어썼다.
`scheduler_lease`(V21) + `SchedulerLeaseService`로 바꾸고 `SchedulerManager.execute` 한 곳에서
잡고 `finally`로 반납한다.

🔴 **획득은 조건부 UPDATE + PK 충돌로 원자화한다.** "SELECT로 비었는지 보고 INSERT"는 두
인스턴스가 같은 순간에 보면 **둘 다 통과**한다 — 잠금이 아니라 잠금처럼 보이는 것이 된다.
8스레드 동시 획득 IT로 검증했고, 그 구현으로 바꾸면 실제로 실패한다.

🔴 **release는 소유자를 확인하고 지운다.** 확인 없이 지우면 TTL이 지나 다른 인스턴스가 정당하게
회수한 lease를 **뒤늦게 끝난 이전 소유자가 삭제**해 버린다(그 순간 셋째가 들어온다).

👉 **`ReportSchedule`의 volatile 플래그 2개를 제거했다.** lease에 덮여 도달 불가한 죽은 코드가
되는데, 남기면 "중복 방어가 있다"고 오해하고 실제로는 어느 쪽이 막았는지 헷갈린다.

⚠️ heartbeat은 없다 — TTL 30분 + 종료 시 즉시 반납. 크래시하면 최대 30분 잠긴다.
짧게 잡으면 **실행 중 잠금을 잃어 두 인스턴스가 동시에 시작**하므로 그쪽이 더 위험하다고 봤다.

### FE 게이트 (커밋 `8389c08`·`b0cbfc6`)

BE가 라이선스로 막아도 화면이 반응하지 못하던 것을 채웠다. 잠금 화면·배너·업셀·실시간 차단 안내.

👉 **잠금 화면에 등록 폼을 복제하지 않았다.** 설정 화면이 이미 두 경로를 갖고 있고 잠금
상태에서도 열려 있으므로(BE 면제), `/setting/license`만 게이트에서 통과시키고 그리로 보낸다.
**이 통과 규칙이 없으면 키 없는 설치본은 등록 화면에 닿지 못해 영원히 잠긴다.**

👉 **로딩 중에는 잠그지도 업셀을 띄우지도 않는다.** 상태를 받기 전에 판단하면 정상 고객에게
매번 잠금 화면과 구매 안내가 깜빡인다.

🔴 **테스트 설계를 한 번 고쳤다.** `useLicenseStatus`만 mock하는 방식은 통하지 않는다 —
`useLicense`가 **같은 모듈 안에서 직접 부르므로** export를 갈아끼워도 원본이 호출된다
(react-query Provider 없다고 터졌다). 파생 규칙을 순수 함수 `deriveLicense`로 분리해 훅 없이
검증하도록 바꿨고, 설계도 그쪽이 낫다.

### 브라우저 검증 — 판정 19 (2026-08-12)

BE `:3001` + FE `:5173`, 실물 발급 키로 전 구간 확인. **화면 문구와 실제 데이터가 함께 갈린다.**

| 상태 | 화면 | 실시간 |
|---|---|---|
| 잠금 | "라이선스가 필요합니다" + 등록 버튼 | — |
| 등록 직후 | 재기동 없이 해제 | 알람 950건 |
| EXPIRING / GRACE | 각각 다른 경고 문구 | 950건 |
| EXPIRED | "실시간 모니터링은 계속…" | **950건 유지** |
| ARCHIVED | "실시간 수집이 중단…" | **`-`로 끊김** |

🟡 **여기서 결함 하나를 더 잡았다.** BE 로그에 `INVALID_TOKEN`이 찍혀 추적하니, 게이트 훅을
`PageWrapper`에 걸었는데 **로그인 화면(AuthLayout)도 `PageWrapper`로 감싸져** 있어 인증 전에
`/features`를 부르고 있었다. `useAuth`는 이미 `enabled`로 막고 있었는데 내 훅만 빠진 것.
👉 **기존 코드가 이미 쓰고 있는 가드를 새 코드가 모른다** — F-1(`ActorResolver`)과 같은 부류다.

### 검증 도구에서 또 걸린 것

- **Ant Design 폼에 자동 입력이 안 먹는다.** `useForm` 내부 상태라 DOM native setter로는
  Form 값이 안 바뀐다(제출 시 빈 값으로 validate 실패). 사람 입력은 정상.
- **CORS 허용 목록**이 `5173`·`3000`뿐이라 `5174`로 띄웠더니 전부 막혔다. 제품 결함이 아니라
  실행 환경 문제였는데, 증상이 "로그인이 안 된다"로 나타나 한참 헤맸다.
- **PowerShell `Set-Content -Encoding UTF8`은 BOM을 넣는다** — 커밋 제목에 보이지 않는 문자가
  박혔다(amend로 정정). 한글 인코딩 함정 다섯 번째.
