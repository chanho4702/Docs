# 자빅스 프록시 관리 — 태스크 목록 (이슈 등록용)

- 작성일: 2026-09-16 · 상태: **착수 전(설계·이슈 등록 단계)**
- 요청: 사용자 — "자빅스 관리 하위에 프록시 관리 메뉴"
- 원칙: **[[zabbix-wrapper-principle]] — Zabbix를 쓰기 쉽게 감싸는 것이 목표. 우리 로직을 얹지 않는다.**
  프록시의 진실은 Zabbix에 있고 우리는 화면만 낸다. 자체 테이블을 만들지 않는다.
- 배경: [[zabbix-wrapper-gaps]]에서 Proxy는 **후순위**로 분류돼 있던 항목이다. 이번에 승격.
- 이슈 이름은 커밋 관례(`#ZM-XX [TYPE] 제목`)에 맞춰 `[TYPE] 제목` 형태로 추천.

## 지금 있는 것 / 없는 것

| | 현황 |
|---|---|
| ✅ 있음 | `ZabbixProxyService.getProxies()` — **`proxy.get`으로 `proxyid`·`name` 둘만** 읽는 포트(engine-api 계약 + engine-zabbix 구현) |
| ✅ 있음 | `GET /hosts/manage/proxies` — 위를 그대로 내보내는 EP(관리자 전용). 호스트 등록 폼의 **선택 목록 용도** |
| ✅ 있음 | 합성 감시·액션 관리·구성 현황이 같은 포트를 참조 중 |
| ❌ 없음 | 상태·버전·마지막 접속·할당 호스트 수 등 **운영에 필요한 필드 일체** |
| ❌ 없음 | 생성·수정·삭제(`proxy.create/update/delete`) |
| ❌ 없음 | 프록시 ↔ 호스트 할당 변경 |
| ❌ 없음 | 화면·메뉴·라우트 |
| ❌ 없음 | 프록시 그룹(Zabbix 7.0 `proxygroup.*`) |

실 연동 환경(dev, `dmove.co.kr`) 확인: 프록시 **1대**(`ZabbixProxyDemo`, proxyid=1).

## 🔴 착수 전에 답해야 할 것 5가지

이슈를 쪼개기 전에 이것부터 정하는 편이 낫다. 답에 따라 T2·T5의 크기가 달라진다.

1. **PSK·TLS 자격을 화면에서 다루는가.**
   프록시는 `tls_psk_identity`·`tls_psk`를 갖는다. **PSK는 비밀값**이고 Zabbix는 조회 시 돌려주지 않는다.
   → 다루면 "쓰기 전용 필드 + 마스킹 + 감사 로그"가 따라온다(자격증명 암호화 정책 [[vault-secrets-management]]와 같은 축).
   → **1차에서는 제외**하고 "TLS 설정은 Zabbix에서" 안내만 두는 선택지도 있다. **권고: 1차 제외.**

2. **능동(active) / 수동(passive) 프록시를 둘 다 만들 수 있게 하는가.**
   Zabbix 7.0은 `operating_mode`로 가른다. 수동이면 주소·포트가 필수이고, 능동이면 `allowed_addresses`가 의미를 갖는다.
   → 폼이 모드에 따라 갈린다. 둘 다 지원하면 T5가 커진다.

3. **프록시 그룹(7.0 신규)을 범위에 넣는가.**
   `proxygroup.*`은 **별도 객체**다. 프록시에 `proxy_groupid`·`local_address`·`local_port`가 붙는다.
   → 넣으면 사실상 화면이 하나 더 생긴다. **권고: T9 백로그로 분리.**

4. **호스트 재할당을 어디서 하는가.**
   프록시 상세에서 옮기는가, 호스트 관리에서 옮기는가, 둘 다인가. 지금 호스트 등록 폼은 이미 프록시를 고를 수 있다.
   → 중복 경로가 생기면 "어디서 바꿔야 하나"가 생긴다.

5. **삭제 시 할당된 호스트를 어떻게 하는가.**
   Zabbix는 프록시를 지우면 그 호스트들이 **서버 직접 감시로 돌아간다**. 조용히 일어나면 사고다.
   → 최소한 "이 프록시에 N대가 붙어 있습니다"를 보여주고 확인받아야 한다(T6의 핵심).

## T1. `[FEAT] 프록시 조회 API — 목록·상세(상태·버전·마지막 접속·할당 호스트 수)`

**문제 (쉽게)**
지금 우리가 프록시에 대해 아는 것은 **이름과 ID 둘뿐**이다. 호스트 등록 폼의 드롭다운을 채우려고 만든 것이라 그렇다. 운영자가 "우리 프록시가 지금 살아 있나, 언제 마지막으로 연결됐나, 버전이 서버와 맞나"를 물으면 답할 데이터가 없다.

**할 일**
- `ZabbixProxyService`(engine-api 계약)에 조회 메서드 확장. 🔴 기존 `getProxies()`는 **호출처 4곳**(호스트 등록·합성 감시·액션 관리·구성 현황)이 쓰고 있으므로 **깨지 않게 추가**한다.
- `proxy.get`에서 운영 필드를 받아 온다 — 상태·마지막 접속 시각·버전·서버와의 호환성·모드·주소·설명.
- 할당 호스트 수는 `selectHosts` 계열로 같이 받거나 별도 집계. **N+1을 만들지 않는다**(프록시마다 host.get 금지).
- 읽기 전용 EP 2개: 목록 / 상세.

**착수 시 실측할 것** 🔴
Zabbix 7.0에서 프록시 필드 이름이 6.x와 **다르다**(`host`→`name`, `status`→`operating_mode` 등). 문서만 보고 쓰지 말고 **실 연동 환경(7.0.x)에서 `proxy.get` 응답을 먼저 찍어 필드를 확정한다.** 같은 이유로 과거에 실측 주석이 여럿 남았다(`ZabbixScriptServiceImpl` 7.0.6 주석 참고).

**완료 기준**
- 목록이 프록시 1대(`ZabbixProxyDemo`)에 대해 상태·마지막 접속·버전·호스트 수를 반환한다.
- 기존 호출처 4곳이 그대로 동작한다.
- 프록시 N대에서도 Zabbix 호출 수가 **N에 비례하지 않는다**.

## T2. `[FEAT] 프록시 등록·수정·삭제 API`

**할 일**
- `proxy.create` / `proxy.update` / `proxy.delete` 포팅(engine-api 계약 + engine-zabbix 구현).
- 입력 검증은 **Zabbix가 하게 두고 오류를 그대로 전달**한다. 우리 규칙을 얹지 않는다(래핑 원칙).
- 🔴 **round-trip 함정 주의**: 조회 응답을 그대로 update에 되돌리면 Zabbix가 거부하는 사례가 이 레포에 이미 있다([[zabbix-action-filter-roundtrip]] — `-32602`). 프록시도 같은 검증을 한다.

**결정 의존**: 위 확인사항 1(PSK)·2(모드)의 답에 따라 필드 수가 달라진다.

## T3. `[FEAT] 프록시 ↔ 호스트 할당 변경 API`

**할 일**
- 호스트 여러 대를 한 프록시로 옮기는 경로. Zabbix에서 이 관계의 **주인이 어느 쪽인지 실측으로 확인**하고(프록시 쪽 update인지 호스트 쪽 update인지) 그쪽으로 쓴다.
- 🔴 이 레포의 선례: 템플릿 link/unlink는 **전부 host-side**였다([[item-template-management-feature]]). 프록시도 같은 모양일 수 있으니 먼저 확인한다.
- 🔴 `host.update`의 배열 필드는 **전체 교체**인 경우가 많다([[host-classification-tags-feature]]) — 부분 갱신으로 착각하면 다른 설정이 날아간다.

## T4. `[FEAT] 프록시 관리 화면 — 목록·상태 + 메뉴/라우트/권한`

**할 일**
- 자빅스 관리 › **시스템 그룹**(`zabbix-group-system`)에 매크로 관리와 나란히 추가. 권한 축은 그 메뉴들과 같은 `isSuperRole`.
- 라우트 `/zabbix-management/proxy-management`, 사이드바 + **모바일 사이드바 둘 다**(둘의 순서가 갈리면 기기마다 다른 구조로 보인다).
- 목록 표: 이름 · 모드 · 상태 · 마지막 접속 · 버전/호환성 · 할당 호스트 수 · 주소.
- 🔴 **상태를 색과 글자로 함께** 준다. "온라인/오프라인"만 쓰면 "한 번도 접속 안 함"과 "끊김"이 같아 보인다.
- 🔴 **마지막 접속을 상대 시간으로**("3분 전") 보여주되 절대 시각을 툴팁에. 프록시 장애 판단의 핵심 값이다.

**참고 구성**: 매크로 관리(`pages/zabbix-management/macro-management/`)와 같은 뼈대 — 표·Drawer·삭제 Modal·`services/*.api.ts`·`types/*.ts`·`hooks/*`.

## T5. `[FEAT] 프록시 등록·수정 패널`

**할 일**
- `ResizableDrawer` 사용(🔴 새 패널은 이것만 — [[resizable-drawer-common]]).
- 모드(능동/수동)에 따라 필드가 갈리는 폼. 수동이면 주소·포트 필수.
- 🔴 **수정은 round-trip 폼**으로 — 조회한 값을 폼에 채우고 전체를 다시 보낸다(부분 갱신 착각 방지).

## T6. `[FEAT] 프록시 삭제 — 할당 호스트 영향 확인 후 실행`

**할 일**
- 삭제 전 **"이 프록시가 감시 중인 호스트 N대"**를 보여주고, 지우면 그 호스트들이 **서버 직접 감시로 돌아간다**는 것을 명시한다.
- N이 0이 아니면 한 단계 더 확인받는다. 되돌릴 수 없다.

**왜 별 이슈인가**: 조용히 일어나면 "감시가 끊긴 줄도 몰랐다"가 된다. T2에 묻으면 확인 절차가 빠진 채 머지될 가능성이 크다.

- 여러 대를 골라 다른 프록시로 이동 / 서버 직접 감시로 해제.

## T8. `[DOCS] 프록시 관리 화면 도움말·설명 문구`

**할 일**
- 화면 제목 아래 한 줄 설명(`page_guide.<key>.summary`) + 도움말 본문.
- "프록시가 무엇이고 언제 쓰는가"(원격지·방화벽 너머 수집, 서버 부하 분산)를 운영자 말로.

## T9. `[FEAT] 프록시 그룹(Zabbix 7.0) 관리` — 백로그

Zabbix 7.0이 추가한 `proxygroup.*`. 프록시를 그룹으로 묶어 **부하 분산과 장애 시 자동 재배치**를 맡긴다. 프록시에 `proxy_groupid`·`local_address`·`local_port`가 붙는다.

별도 객체라 화면이 하나 더 생긴다. **T1~T7을 먼저 하고, 고객이 프록시를 여러 대 쓰는 것이 확인되면 착수**한다. 지금 dev 환경은 1대다.
