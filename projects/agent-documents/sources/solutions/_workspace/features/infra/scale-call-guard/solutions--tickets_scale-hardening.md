## T-A. 알람 동기화 1만 건 상한 — 응급 조치 + 근본 해결

### 현상 (코드 확인)
- 보정(5분)·증분(15초) 모두 `problem.get`을 `limit 10000`으로 한 번만 호출한다(`EventSyncService.java:141`, `:254`). 도달하면 경고 로그만 남긴다(`:522`).
- `problem.get`에 **정렬 지정이 없다**(`ProblemGetParams`에 sortfield 없음). 1만 건 중 **어느 것이 잘리는지 보장되지 않는다.**

### 실제 위험 (09-16 정정)
> 앞선 설명의 "잘린 알람을 해소로 오판"은 **틀렸다**. 되짚기(`reconcileResolved`, `:355`)는 자빅스 `event.get`에서
> **복구 이벤트가 확인된 건만** 해소로 표시한다. 잘렸을 뿐 열린 알람은 복구 이벤트가 없어 해소로 바뀌지 않는다.

실제 위험은 세 가지다.
1. **상한 밖 신규 알람이 사본에 안 들어온다** → 알람 목록·벨에 보이지 않는다.
2. **이미 사본에 있던 장기 장애가 이틀 뒤 삭제된다** — 좀비 정리는 "마지막 갱신 후 2일"(`EventProblemRepository.java:38`)이다. 잘려서 보정 upsert를 못 받으면 `updated_at`이 멈추고, 진짜 열린 장애가 좀비로 지워진다. 🔴 가장 심각.
3. **되짚기 대기열 낭비** — 잘린 열린 알람이 매 회차 "사라진 후보"로 뽑혀 500건 배치(`:39`)를 차지한다. 실제로 해소된 알람의 해소 시각 기록이 밀린다(코덱스 R3).

### A-1. 응급 조치 (작음)
- 응답이 상한에 닿은 회차는 **"완전하지 않은 회차"로 표시**한다.
  - 그 회차에서는 되짚기(`reconcileResolved`)를 건너뛴다.
  - 좀비 정리(`cleanupOldEvents`)는 **최근 N회 보정이 모두 완전했을 때만** 실행한다.
- 사이드 이펙트
  - 상한에 닿아 있는 동안은 **해소된 알람의 해소 시각 기록이 늦어진다**(화면에는 미해소로 남음).
  - 좀비 행이 정리되지 않고 쌓인다. 상한 해소 후 자동으로 정리된다.
  - 증상이 조용해지지 않도록 경고 로그는 유지하고, 스케줄러 화면에 "불완전" 상태를 노출하는 것을 검토한다.

### A-2. 근본 해결 (중간)
- `problem.get`을 **eventid 순 정렬 + 커서 분할**로 끝까지 받는다(1만 건 단위).
  - 🔴 구현 전 확인: 대상 자빅스 버전에서 `problem.get`의 `sortfield=eventid`·`eventid_from`(또는 동등 수단) 지원 여부. 미지원이면 `groupids` 단위 분할로 대체한다.
- 전체 상한(예: 20만 건)을 따로 두고, 넘으면 A-1의 "불완전 회차" 규칙을 적용한다.
- 사이드 이펙트
  - 한 회차가 15초를 넘길 수 있다. 이전 회차가 끝나기 전에는 다음 회차를 시작하지 않는지 스케줄러 동작을 확인한다.
  - 분할 경계에서 생기는 누락·중복은 eventid 커서와 기존 upsert(해소 역행 방지 포함, `:431`)로 흡수한다.
  - 자빅스 호출 수가 **열린 알람 수에 비례**해 늘어난다. 사용자 수와는 무관하다.
  - 보정 1회에 수만 행 upsert가 나간다. 실제 변경된 행만 쓰는 현재 방식을 유지한다.

### 검증
- 단위 테스트: 상한 도달 회차에서 되짚기·좀비 정리를 건너뛰는지, 분할 수집이 경계에서 누락·중복 없이 합쳐지는지.
- 통합 테스트: 1만 1건 픽스처로 장기 장애 행이 이틀 뒤에도 남는지(A-1의 핵심 회귀).

## T-B. AWS 매처가 전체 호스트의 아이템을 통째로 받는 문제

### 현상 (코드 확인)
- `Ec2ZabbixMatcher.hosts()`(`Ec2ZabbixMatcher.java:228`)가 **전체 호스트**에 `LAST_CHECK`(= `selectItems` lastclock)를 붙여 조회한다(`ZabbixInventoryAdapter.java:98`).
- 5,000대 × 2,000개 = **1,000만 행이 한 응답**에 실린다. 자빅스 PHP 메모리 한도 또는 응답 30초 제한에 걸려 실패할 가능성이 높다.
- 실패하면 fail-closed(`:262`)로 **모든 EC2가 CloudWatch 폴백** 또는 `unavailable`로 표시된다. 에이전트가 있어도 "없음"으로 보인다.
- 경위: `LAST_CHECK`는 ZM-92(07-27)에서 **자산 상세 1대용**으로 만들었다. 08-26 EC2 소스 매트릭스에서 전체 호스트 대상으로 재사용됐다.

### 수정 방향
1. 1단계: 전체 호스트는 **태그·인터페이스만** 조회한다(아이템 없음). 짝짓기(instanceId·IP)는 현행 규칙 그대로 둔다.
2. 2단계: **짝지어질 수 있는 후보 호스트만** 신선도를 조회한다.
   - 후보 = instanceId를 주장하는 호스트 ∪ EC2 주소 색인(`ec2AddressIndex`)에 있는 AGENT 주소를 가진 호스트.
3. 신선도 신호는 후보가 수천 대여도 작아야 한다. **후보 제한만으로는 부족하다**(EC2 2,000대 × 2,000개 = 400만 행).
   - 권장: 전 아이템의 최대 lastclock 대신, 품질 게이트가 실제로 보는 **CPU 사용률 지표의 최신값 시각**(`metricPort.queryLatest` → `LatestValue.epoch`)을 쓴다. 호스트당 1행이다.
   - 이 신호는 "에이전트가 CPU·메모리 시계열을 주고 있나"라는 판정 목적에 오히려 더 가깝다. 설계서에도 LAST_CHECK는 "느슨한 프록시"로 적혀 있다.
   - 후보는 수백 대 단위로 나눠 조회한다.

### 사이드 이펙트
| 항목 | 내용 | 대응 |
|---|---|---|
| 판정 기준 변경 | "아무 아이템이나 최근 수집" → "CPU 지표 최근 수집". CPU 아이템이 없거나 꺼진 호스트는 `zabbix-agent`에서 CloudWatch 폴백으로 바뀐다 | 어차피 품질 게이트에서 걸러지던 호스트라 시계열 결과는 같다. 목록 표시(`monitoredBy`)만 바뀌므로 변경 이력에 명시 |
| 수집 주기가 긴 템플릿 | CPU 수집 주기가 신선도 허용(기본 30분)보다 길면 영원히 폴백 | 기존 설정 `app.cloud.agent-freshness-minutes`로 동일하게 조정 가능 |
| 색인 콜드 | 스냅샷 배치 전에는 IP 후보를 모른다 | 현행도 콜드면 IP 근거를 안 쓴다(fail-closed). 동일 |
| 색인 갱신 시점 | 캐시(5분) 도중 색인이 갱신되면 새 IP 후보의 신선도가 최대 5분 비어 폴백으로 보인다 | 수용 가능. 필요하면 색인 갱신 시 캐시 무효화 |
| 호출 수 | 1콜 → 2콜 + 분할 N콜 | 5분 캐시 + single-flight 유지 |
| 자산 상세(1대) | `AssetService.resolveLive`는 `LAST_CHECK`를 1대에 쓴다 | 영향 없음. 단 호스트당 2,000행이라 상세도 같은 신호로 바꿀지 별도 판단 |

### 검증
- 단위 테스트: 1단계 조회에 `selectItems`가 없는지, 후보만 2단계 대상인지, 분할 경계, 신선도 판정(기존 `isFresh` 경계값) 유지.
- 기존 매칭 규칙 테스트(유일성·AGENT 인터페이스만·useip=0 제외·fail-closed)가 전부 통과해야 한다.
- 런타임: dev 호스트 `10635` 태그 부착 시나리오(`features/cloud/aws-monitoring/review_ec2-monitoring-sources.md:94`) 재현.
