# 백엔드 기술 스택 전환 보고서: NestJS → Java(Spring Boot)

**제품:** 무브스아이(MovesEye) — Zabbix 기반 인프라 모니터링 대시보드(DMOVE)
**대상:** 백엔드 API 서버
**전환:** NestJS 10 (TypeScript) → Spring Boot 3.3.5 (Java 17)
**작성일:** 2026-06-17
**문서 성격:** 의사결정 보고 / 전환 결과 및 트레이드오프 분석

---

## 1. 요약 (Executive Summary)

무브스아이 백엔드를 기존 **NestJS 10 + TypeORM** 스택에서 **Spring Boot 3.3 + JPA** 스택으로 전환하였다. 전 모듈 포팅이 완료되었으며, 실 Zabbix 7.0.6 연동 환경에서 End-to-End 동작 검증을 마쳤다. 전환은 **기존 프론트엔드(React)와의 API 계약을 1:1로 완전 보존**하는 것을 최우선 원칙으로 수행하여, FE 측 변경 없이 백엔드만 교체 가능한 상태이다.

**결론:** 본 전환은 무브스아이를 **B2B 인프라 모니터링 제품으로 장기 운영·확장**하는 방향에 부합하는 합리적 선택이다. 타입 안전성·동시성 처리·운영 성숙도·인력 수급 측면에서 명확한 이득을 확보하였으며, 전환 과정에서 불필요한 의존성을 정리하는 부수 효과도 얻었다. 다만 **자동화 테스트 커버리지 복원**이 잔여 과제로 남아 있다.

## 3. 전환 결과 현황

### 3.1 기술 스택 매핑

| 영역 | NestJS (이전) | Spring (전환 후) |
|------|--------------|------------------|
| 프레임워크 | NestJS 10 (Express) | Spring Boot 3.3.5 (MVC) |
| 언어/런타임 | TypeScript / Node | Java 17 / JVM |
| 빌드 | npm | Gradle 9 (Kotlin DSL) |
| ORM | TypeORM 0.3 | Spring Data JPA / Hibernate |
| DB 마이그레이션 | TypeORM migrations | Flyway (baseline, `ddl-auto: none`) |
| 인증 | passport-jwt + Guards | Spring Security Filter + Interceptor |
| JWT | @nestjs/jwt | auth0 java-jwt 4.4.0 (Node 토큰 호환) |
| 예외 처리 | ExceptionFilter | `@RestControllerAdvice` |
| API 문서 | @nestjs/swagger | springdoc-openapi 2.6 |
| AWS 연동 | @aws-sdk (EC2/CloudWatch) | AWS SDK v2 |

### 3.2 정량 비교

| 항목 | NestJS (이전) | Spring (전환 후) | 비고 |
|------|---------------|------------------|------|
| 소스 파일 수 | 271 | 311 | — |
| 소스 라인 수 | 27,776 | 17,084 | **약 38% 감소** |
| 자동화 테스트 | 22 spec | 5 | ⚠️ 복원 필요 |

## 4. 기대 효과 (이득)

### 4.1 타입 안전성 및 데이터 정합성 강화
모니터링 제품의 핵심인 Zabbix 응답 파싱·메트릭 집계·DTO 매핑에서, JVM의 정적 타입 시스템이 **컴파일 시점에 오류를 차단**한다. 런타임에 타입이 소거되는 TypeScript 대비 데이터 정합성 보증이 강화된다.

### 4.2 동시성 및 처리량 모델 개선
주기적 동기화(`@Scheduled`), 다중 호스트 메트릭 집계 등 I/O 대기·병렬 처리가 많은 워크로드에서, JVM의 멀티스레드 + 스레드풀 모델이 Node 단일 이벤트 루프보다 유리하다. 모니터링 대상 호스트 증가에 따른 확장에 강점을 가진다.

### 4.3 운영·마이그레이션·보안 성숙도
JPA/Hibernate, Flyway(명시적 baseline), Spring Security 등 엔터프라이즈 표준이 프레임워크에 내장되어 있다. 특히 Flyway 기반 스키마 관리는 운영 DB 변경을 명시적·안전하게 통제한다.

### 4.4 인력 수급 및 장기 유지보수
B2B 인프라 백엔드 시장에서 Spring 경험 인력 풀이 NestJS 대비 크게 넓어, 채용 및 장기 유지보수 측면에서 유리하다.

### 4.5 의존성 위생 개선
불필요한 외부 의존성 제거로 공급망(supply chain) 공격 표면과 보안 점검 부담이 감소하였다.

## 5. 트레이드오프 및 감수 비용

### 5.1 (높음) 자동화 테스트 커버리지 후퇴
이전 22개 테스트 중 현재 **5개만 포팅**된 상태이다. 동작 검증으로 정상 동작은 확인하였으나, 회귀를 자동으로 차단하는 안전망이 축소되었다. **전환의 본질적 손실이 아닌 잔여 과제이며, 최우선 보강 대상이다.**

### 5.2 (높음) 원본 동작의 1:1 보존에 따른 기술 부채
FE 계약 보존을 위해 이전 구현의 우발적 동작(예: 권한 거부 시 HTTP 403 대신 200 + body code 403 반환)까지 의도적으로 유지하였다. 다수의 동작 quirk가 사양으로 동결되어, 향후 정상화 시 FE와 동반 수정이 필요하다.

### 5.3 (중간) 풀스택 개발 시 언어 분리 비용
프론트엔드(React/TypeScript)와 백엔드(Java) 간 언어가 분리되어, 동일 언어 풀스택의 인지적 이점이 감소하였다. TS↔Java 간 타입·계약 정합을 위한 별도 동기화 절차가 필요하다.

### 5.4 (중간) 런타임 리소스 풋프린트
JVM은 Node 대비 기동 시간과 idle 메모리 사용량이 크다. 단, 상주형 서비스인 모니터링 대시보드 특성상 영향은 제한적이다.

### 5.5 (중간) 코드베이스 이중 존재
전환기 동안 이전(NestJS)·신규(Spring) 코드베이스가 공존한다. 정본 혼선을 막기 위해 조기에 이전 코드베이스를 폐기(deprecated) 처리해야 한다.

## 8. 결론

무브스아이 백엔드의 Java(Spring Boot) 전환은 **제품의 장기 운영·확장·인력 수급 방향에 부합하는 타당한 의사결정**이다. 타입 안전성, 동시성 처리, 운영 성숙도에서 명확한 이득을 확보하였고, FE 무중단 전환이라는 까다로운 제약을 충족하였으며, 부수적으로 코드베이스를 38% 경량화하였다. 잔여 과제인 **테스트 커버리지 복원**을 조기에 완료하면 전환의 가치는 온전히 실현될 것이다.
