# 알람 사본 서빙과 권한 재현 (`ZM-125`)

## 0. 한눈에

| | |
|---|---|
| **왜** | 접속한 모든 사용자의 알람 목록·벨이 1분마다 Zabbix에 직접 물었다(50명=시간당 3,000회+, 전부 같은 질문). 부하가 접속자 수에 비례하고, Zabbix 순단 = 알람 화면 전멸 |
| **뭐를** | 알람 목록·벨이 읽는 **데이터의 출처**를 바꿨다 |
| **어떻게** | 우리 DB에 알람 사본 테이블을 만들고 화면은 그것만 읽게. Zabbix가 해주던 권한 필터는 우리가 재현(fail-closed) |
| **결과** | 알람 화면의 Zabbix 호출 **0건** — 접속자가 늘어도 부하 불변, Zabbix가 죽어도 화면 유지 |

## 1. 문제 — 어디서, 무엇이

**발생 지점: 알람 목록·알림 벨 API의 조회 경로**(BE `EventService` → Zabbix 직행). 전 화면
공통인 알림 벨과 알람 목록이 1분 폴링마다 problem.get(알람) + trigger.get(규칙) + 조치 이력 +
사용자 이름까지 한 벌을 Zabbix에 직접 물었다.

- 사용자 50명 = **시간당 3,000번 이상**, 내용은 전부 같은 질문. **부하가 접속자 수에
  비례**하는 구조라 "고객사 접속자가 늘면 Zabbix DB가 느려진다"는 인과가 우리 코드에 있었다.
- Zabbix가 순단하면 **알람 화면이 통째로 죽었다** — 모니터링 제품이 장애 순간에 알람을 못
  보여주는 역설.

## 2. 어떻게 처리했나

### 2.0 AS-IS → TO-BE (API 단위)

| API | AS-IS (원래) | TO-BE (변경 후) |
|---|---|---|
| `GET /event/problems` (알람 목록, RECENT) | 요청마다 Zabbix에 problem.get + trigger.get(규칙) + selectAcknowledges(조치) + 사용자 조회 — **요청당 Zabbix 4~5콜** | `event_problems` 사본 SELECT + 화면에 보이는 페이지만 조치 하이드레이션 — **요청당 Zabbix 0~1콜** |
| `GET /event/bells` (알림 벨) | 요청마다 problem.get 한 벌 직행 — 전 사용자 1분 폴링이 전부 Zabbix로 | 사본 SELECT — **Zabbix 0콜** |
| 위 두 API의 권한 처리 | Zabbix가 사용자 토큰으로 알아서 필터 | 앱이 재현: 가시 호스트 집합 AND 판정 + (태그 필터 설치본만) 사용자 토큰 재검증 1콜 |

**기술: 읽기 전용 사본 테이블(로컬 PostgreSQL) + 배치 동기화 + 앱 레벨 권한 재현.**

**왜 캐시가 아니라 사본인가.** TTL 캐시는 만료되면 다시 Zabbix 직행이라 절감이 확률적이고
순단 보호도 안 된다. 사본은 서빙(화면)과 수집(배치)이 완전히 분리돼 둘 다 결정적이다.

### 2.1 사본 테이블 — 뭘 실었나

`event_problems` 한 테이블에 **목록을 그리는 데 필요한 전부**를 실었다(V49): 알람 id·이름·
심각도·발생/해소 시각(clock/r_clock) + 억제 여부·원인 알람·규칙 활성 여부·소속 그룹(JSON)·
조치 수·**관련 호스트 전체(host_ids JSON)**. "목록 한 번에 조인 없이"가 컬럼 설계 기준이다.
채우는 쪽은 [동기화 이원화](solutions--ZM-127-%EB%8F%99%EA%B8%B0%ED%99%94-%EC%9D%B4%EC%9B%90%ED%99%94%EC%99%80-%EB%8D%B0%EC%9D%B4%ED%84%B0-%EC%B2%AD%EC%86%8C.md)가 담당한다.

### 2.2 목록 요청의 처리 흐름 (한 건이 들어오면)

```
GET /event/problems (사용자 A, 기간·필터 포함)
 ① EventService가 event_problems에서 기간(clock 범위)으로 행 조회 — Zabbix 호출 없음
 ② 사본이 15분 이상 안 갱신됐으면 warn 로그(감지선) — 화면은 계속 서빙
 ③ 사용자 A의 "가시 호스트 집합" 로드 — Redis 60초 캐시, 미스면 계산 후 캐시
 ④ 행마다 필터를 순서대로:
    - 해소된 지 5분(recent 창) 지난 행 제외 — Zabbix recent:true 화면과 같은 축
    - 권한(호스트 축): host_ids의 호스트를 전부 볼 수 있어야 통과(AND).
      host_ids가 비면 숨김(fail-closed), NULL(구버전 행)이면 단일 host_id로 유예 판정
    - 비활성 규칙 제외(rule_enabled=false), NULL은 다음 동기화까지 유예 포함
    - 키워드(이름 부분일치·대소문자 무시)·호스트·그룹·심각도·처리일시 필터
 ⑤ 태그 축 검증(조건부): ProblemTagFilterGuard가 "이 설치본에 usergroup tag_filters가
    있나"를 5분 캐시로 판정 → 있을 때만 후보 알람 id들을 사용자 A의 토큰으로 Zabbix에
    재조회(event.get 1콜)해서, Zabbix가 태그 기준으로 걸러준 부분집합만 남김.
    없는 설치본(대부분)은 이 단계가 통째로 생략 — 추가 콜 0
 ⑥ 정렬·페이지 슬라이스
 ⑦ 화면에 보이는 페이지의 행만 조치 타임라인을 실시간 조회(1콜)로 덮음 —
    "방금 내가 한 조치"는 즉시 보여야 해서. 나머지 값은 전부 사본
```

### 2.3 권한 재현 — 이 개선의 진짜 비용

예전엔 사용자 토큰으로 물었으니 Zabbix가 알아서 걸렀다. 사본은 관리자 권한으로 만드니 그
필터를 앱이 재현해야 하고, Zabbix의 알람 가시성은 **두 축**이다:

- **호스트 축**(④): 다중 호스트 알람은 전부 볼 수 있어야 노출 — Zabbix와 동일한 AND 판정.
- **태그 축**(⑤): usergroup tag_filters. 감지→조건부 검증 구조라, 안 쓰는 설치본은 비용이
  0이고 쓰는 설치본만 요청당 1콜을 낸다.

판정이 불가능한 상황(host_ids 없음, 태그 검증 콜 실패)은 전부 **숨기는 쪽**(fail-closed)으로
넘어진다 — 권한 누출보다 일시적 빈 목록이 낫다는 일관된 선택.

## 3. 적용 범위

| 경로 | 사본? |
|---|---|
| 알람(이벤트) 화면 RECENT 목록 · 심각도 칩 | ✅ 사본 |
| 헤더 알림 벨(뱃지·목록) | ✅ 사본 |
| 알람 **이력(HISTORY) 모드** | ❌ Zabbix 직행 유지 — 이력은 사본 보존 범위(해소 후 30일) 밖까지 조회한다 |
| 알람 상세의 조치 타임라인 | ❌ 실시간 하이드레이션(1콜) — 의도적 예외 |
| 홈 KPI·그룹 현황 등 **집계** | ❌ Zabbix 직행([1콜 병합](solutions--ZM-124-126-%ED%98%B8%EC%B6%9C-%EB%B3%91%ED%95%A9%EA%B3%BC-%EC%BA%90%EC%8B%9C.md) 적용) — 집계 축이 다양해 사본 필터 재현 범위 밖 |
| 지도·자산의 라이브 상태 배지 | ❌ Zabbix 직행(recent 포함 실시간 판정) |

## 4. 해결된 것

- 알람 목록·벨의 Zabbix 콜 **0**(dev 실측) — 접속자가 늘어도 Zabbix 부하 불변.
- Zabbix 순단 시에도 알람 화면 유지(멈춘 사본이라도 빈 화면보다 낫다 + 15분 경과 시 warn).
- 검수 산물로 권한 재현이 Zabbix 원 동작과 맞춰짐(다중 호스트 AND·태그 축·fail-closed).

## 5. 트레이드오프와 우려점

**트레이드오프(의도한 대가):**

- **실시간 직행을 포기** — 신선도가 동기화 주기(15초)에 종속된다. "1분 폴링보다 신선하다"로
  상쇄했지만, 구조적으로 사본은 항상 원본보다 최대 한 주기 늦다.
- **권한을 앱이 재현** — Zabbix가 공짜로 해 주던 것을 우리 코드가 진다. 실제로 검수 3회에
  걸쳐 권한 구멍(다중 호스트 AND, 태그 축, 캐시 인코딩)이 나왔다 — **이 축은 Zabbix 권한
  모델이 바뀔 때마다 재점검 대상**이다.
- **스케줄러가 단일 생명선** — event_sync가 죽으면 화면이 멈춘 사본을 보여준다. 감시 장치
  (15분 stale warn)로 보완했지만 구조적 의존은 남는다.
- **저장 공간** — 알람 사본이 로컬 DB에 쌓인다(해소 후 30일 보존·좀비 2일 정리로 상한).

**우려점(지켜봐야 할 것):**

- 태그 필터 설치본 + Zabbix 순단 = 알람 목록이 잠시 빈다(fail-closed의 대가). 태그 필터를
  실제 쓰는 서버에서의 round-trip은 **미실측**.
- 열린 알람 1만 건 초과 설치본은 동기화 상한에 걸려 일부 누락(경고 로그로 감지, 커서 청크는
  그때 확장).
- 사본과 Zabbix 화면을 나란히 보는 사용자는 최대 15초의 불일치를 볼 수 있다 — 문의 소지.

## 6. 함정 (검수에서 잡힌 것들)

- **다중 호스트 알람의 AND 판정 누락** — 대표 host_id 하나로만 판정해 일부만 볼 수 있는
  사용자에게 노출될 뻔 → host_ids 전체 AND로 정정.
- **태그 축 자체를 몰랐다** — 호스트 축만 재현하고 끝난 줄 알았는데 통합 검수가 tag_filters
  축을 지적. **Zabbix가 토큰으로 해 주던 걸 앱이 대신하는 순간, 그 권한 모델의 전 축을 알아야
  한다.**
- **호스트 필터도 같은 함정** — 화면의 호스트 필터가 대표 host_id와만 비교해 두 번째 호스트로
  필터하면 알람이 빠짐 → host_ids 포함 판정으로 정정.
- **태그 감지 캐시의 직렬화 불일치** — 저장은 JSON(`"1"`→`"\"1\""`), 조회는 raw라 비교가 항상
  실패 → 캐시 히트 5분 동안 태그 검증이 조용히 꺼져 있었다. **모킹 유닛 테스트는 인코딩
  결함을 못 잡는다** — 캐시 왕복은 같은 직렬화 쌍으로.
