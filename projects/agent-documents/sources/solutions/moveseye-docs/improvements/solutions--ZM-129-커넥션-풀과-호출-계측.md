# 커넥션 풀과 호출 계측 (`ZM-129`)

## 0. 한눈에

| | |
|---|---|
| **왜** | Zabbix로 나가는 요청에 동시 제한이 없어 화면 요청 100개 = 연결 100개가 그대로 몰려감. 호출 기록도 없어 "느려진 게 우리 탓이냐"에 답 못 함 |
| **뭐를** | Zabbix로 가는 **관문 하나**를 만들었다 |
| **어떻게** | 모든 호출이 커넥션 풀(동시 최대 10, 설정 가능)을 지나게. 꽉 차면 5초 대기 후 실패. 같은 관문에 계량기(60초 요약 로그) |
| **결과** | "최대 부하 = 동시 10건"을 고객에게 숫자로 약속 가능. 호출량은 로그로 증명 |

## 1. 문제 — 어디서, 무엇이

**발생 지점: BE→Zabbix HTTP 클라이언트(`ZabbixClient`)의 전송 계층.** Spring `RestClient`가
기본 요청 팩토리(SimpleClientHttpRequestFactory)를 쓰고 있었다:

- **요청마다 새 TCP 연결, 동시성 제한 없음** — 화면 요청 100개가 동시에 오면 Zabbix로 연결
  100개가 그대로. "MovesEye가 Zabbix에 줄 수 있는 최대 부하"를 아무도 통제·보장 못 함.
- **호출 기록 없음** — 고객이 "Zabbix DB가 느려졌는데 MovesEye 때문 아니냐" 물으면 근거 없음.
- 타임아웃도 기본값 방치 — Zabbix가 느려지면 우리 쪽 대기가 어디까지 늘어나는지 미정의.

## 2. 어떻게 처리했나

### 2.0 AS-IS → TO-BE (전송 계층 — 전 API 공통)

| 대상 | AS-IS (원래) | TO-BE (변경 후) |
|---|---|---|
| 연결 방식 | 요청마다 새 TCP 연결 | Apache HttpClient5 **커넥션 풀** — 연결 재사용(keep-alive) |
| 동시성 | 무제한(요청 수 = 연결 수) | **동시 최대 10**(`ZABBIX_CLIENT_MAX_CONNECTIONS`) |
| 풀 포화 시 | (해당 없음) | **5초 대기 후 실패** — 무한 대기로 BE 전체가 잠기지 않게 |
| 타임아웃 | 기본값 방치 | 연결 수립 10s · 풀 대기 5s · 응답 30s 명시 |
| 호출 기록 | 없음 | 모든 호출을 계측 — **60초마다 `[zabbix-calls]` 요약 로그**(메서드별 횟수·소요·실패) |

### 2.1 호출 한 건의 처리 흐름

```
어느 서비스든 Zabbix 호출 → ZabbixClient.callRaw() 단일 관문
 ① 계측 시작(시각 기록)
 ② 커넥션 풀에서 연결 요청
    - 여유 있으면 즉시(재사용 연결 우선 — TCP 수립 비용 0)
    - 10개가 모두 사용 중이면 최대 5초 대기 → 그래도 없으면 그 요청만 실패
      (무한 대기 금지: Zabbix가 느릴 때 Tomcat 스레드까지 줄줄이 잠겨 BE 전체가
       마비되는 것을 차단 — 요청 하나의 실패 < 서버 전체의 마비)
 ③ JSON-RPC 본문 전송 — 문자열 본문(Content-Length 확정). Zabbix의 api_jsonrpc.php는
    chunked(스트리밍) 전송을 못 읽으므로 이 성질이 필수(§함정)
 ④ 응답 파싱(에러 코드 -32602/-32500은 인증 오류로 변환)
 ⑤ 계측 종료 — 메서드명·소요 ms·실패 여부를 창(window)에 기록.
    성공이든 실패든 무조건 기록(실패도 부하다)
별도 스케줄: 60초마다 창을 비우며 `[zabbix-calls]` 요약 로그 출력
 (메서드별 횟수·총/평균 소요·실패 수 — 실제 경과 시간 기준)
```

### 2.2 왜 이 수치들인가

- **동시 10** — "이 제품이 Zabbix에 줄 수 있는 최대 동시 부하"라는 **계약 가능한 숫자**.
  [「Zabbix 성능·부하 책임 경계」](../operations/solutions--%EC%9E%90%EB%B9%85%EC%8A%A4-%EC%84%B1%EB%8A%A5-%EC%B1%85%EC%9E%84-%EA%B2%BD%EA%B3%84.md)의 계약 문구와 세트.
  적정성은 계측 로그(풀 대기 실패 빈도)를 보고 조정한다 — 계량기와 상한이 같은 관문에 있어
  이 운영 루프가 로그만으로 돈다.
- **풀 대기 5초** — 0이면 순간 피크에 너무 공격적으로 실패, 무한이면 마비 전파. 중간값.

## 3. 적용 범위

- **BE에서 Zabbix로 나가는 모든 호출** — 화면 조회·동기화 배치·관리 쓰기 전부 이 풀과 계측을
  지난다(engine-zabbix의 단일 클라이언트라 우회 경로가 없다).
- **안 타는 곳**: Zabbix 외 외부 호출(AWS SDK 등)은 각자의 클라이언트·상한. 이 풀은 Zabbix 전용.

## 4. 해결된 것

- 동시 부하 상한이 **설정값으로 보장**(계약 문구 가능) + keep-alive로 콜마다 TCP 수립하던
  비용 소멸.
- `[zabbix-calls]` 로그로 호출량 실측 가능(dev 정상 출력 확인) — 이 에픽의 개선 수치도 이
  로그로 쟀다.

## 5. 트레이드오프와 우려점

**트레이드오프(의도한 대가):**

- **보호 vs 응답성** — 상한 10을 넘는 동시 수요는 5초 후 **실패**한다. Zabbix를 지키는 대신
  피크 시점의 화면 오류 가능성을 수용. 상한을 올리면 반대로 기움 — 그래서 설정값이다.
- **풀 대기 5초의 스레드 점유** — 대기 중 요청은 Tomcat 스레드를 잡는다.
- **계측의 잠금 비용** — 기록·배출을 단일 잠금으로 묶어(유실 방지) 호출마다 잠금 비용.
  현 호출량(초당 수십)에선 무시 가능.

**우려점(지켜봐야 할 것):**

- **풀 포화 시나리오 미실측** — 동시 10건 초과 시 5초 대기·실패가 화면에 어떻게 보이는지
  실측 안 함. 계측 로그의 실패 카운트가 감지선.
- 대시보드성 화면이 병렬 호출을 늘리면(위젯 동시 로드) 상한에 먼저 닿는 건 사용자 화면 —
  화면별 호출 수를 계측으로 관찰.

## 6. 함정

- **Zabbix는 chunked 전송을 못 읽는다** — JDK HttpClient의 스트리밍 전송을 api_jsonrpc.php
  (php://input)가 못 읽어 "Invalid JSON"이 났던 역사적 함정. Apache HttpClient의 문자열
  본문(StringEntity)은 Content-Length가 확정되므로 안전 — **HTTP 클라이언트를 갈 때마다 본문
  전송 방식을 확인할 것.**
- **계측의 창 교체 경쟁(검수 지적)** — 기록과 60초 배출(drain)이 다른 잠금이면 창이 바뀌는
  순간의 기록이 유실 → 단일 잠금으로 정정. 요약 로그는 가정된 60초가 아니라 **실제 경과
  시간**을 표기(공유 스케줄러 지연 반영).
