# SSE 알람 푸시 (`ZM-128`)

## 0. 한눈에

| | |
|---|---|
| **왜** | 브라우저가 1분마다 우리 서버에 "바뀐 거 있어요?"라고 물었는데(폴링) 응답의 99%가 "없는데요". 헛질문은 많은데 새 알람은 최대 1분 늦게 보임 |
| **뭐를** | 물어보는 **방향**을 뒤집었다 |
| **어떻게** | 브라우저마다 SSE 연결을 열어 두고, 동기화가 실제 변화를 감지한 순간에만 서버가 "바뀜!" 신호 → 브라우저가 그때만 재조회. 안전망 5분 폴링은 유지 |
| **결과** | 재조회가 "1분마다 무조건" → "실제 변화 있을 때만". 새 알람이 몇 초 만에 화면에 |

## 1. 문제 — 어디서, 무엇이

**발생 지점: 알림 벨·알람 화면의 폴링 주기(FE→BE 구간).** 전 사용자의 브라우저가 1분 주기로
알람 목록·벨·통계를 다시 조회했다. Zabbix 직행은 [사본 서빙](solutions--ZM-125-%EC%95%8C%EB%9E%8C-%EC%82%AC%EB%B3%B8-%EC%84%9C%EB%B9%99%EA%B3%BC-%EA%B6%8C%ED%95%9C-%EC%9E%AC%ED%98%84.md)이
먼저 끊었지만, 폴링 자체의 약점이 남았다:

- 사용자 50명 = **분당 50번**의 헛질문(이제 우리 BE·DB가 받는) — 알람은 하루에 몇 번 안 바뀐다.
- 그런데도 새 알람은 **최대 1분 늦게** 보인다. 헛질문은 많은데 반응은 느린, 폴링의 전형.

**SSE가 뭔가.** 브라우저가 HTTP 요청을 하나 보내 놓고 **끊지 않고 열어 두는** 표준 기술.
서버가 원할 때마다 그 통로로 한 줄씩 흘려보낼 수 있다. 전화(WebSocket, 양방향)와 달리
**라디오(서버→브라우저 단방향)** — 우리 용도는 "알려주기"뿐이라 이걸로 충분하고, 브라우저
내장 `EventSource`가 재연결까지 해 줘서 훨씬 단순하다.

## 2. 어떻게 처리했나

### 2.0 AS-IS → TO-BE (API 단위)

| API | AS-IS (원래) | TO-BE (변경 후) |
|---|---|---|
| `GET /event/stream` | **없었음** | 신설(SSE). 연결을 열어 두고 변화 시 `events-changed` 신호 푸시 |
| `GET /event/problems`·`/event/bells`·통계·홈 위젯 조회 | FE가 **1분마다 무조건** 폴링 | **신호 수신 시에만** 재조회 + 안전망 폴링 5분(연결 없으면 1분 복귀). API 자체는 불변 — 호출 "시점"만 바뀜 |

### 2.1 끝에서 끝까지 처리 흐름 (알람 발생 → 화면)

```
10:00:07  Zabbix가 장애 감지, 알람 발생
10:00:15  [BE] 15초 증분 동기화가 새 알람을 사본에 적재(→ 동기화 이원화 문서)
          → "이번 사이클에 실제 변화 있음" 판정(신규·해소·조건부 UPDATE 영향 행)
          → DB 반영이 전부 끝난 뒤 EventStreamHub.broadcastChanged() 1회:
             열려 있는 모든 SSE 연결에  event: events-changed / data: {}  한 줄씩
10:00:15  [브라우저] useEventStream이 신호 수신(2초 스로틀)
          → 알람 관련 쿼리 키 7종 무효화 → TanStack Query가 화면에 보이는 것만 재조회
10:00:15  화면에 새 알람 표시 (발생 후 약 8초)
```

조용한 날은 **아무 일도 안 일어난다** — 신호가 없으니 재조회도 없다.

### 2.2 연결의 수명 주기 (BE `EventStreamHub`)

```
 ① 연결: GET /event/stream?visitorId=... → 세션 대조(불일치면 401) → 연결 목록에 등록
    → 등록 직후 초기 신호 1회(접속 시점 상태를 바로 당겨오게)
 ② 유지: 25초마다 하트비트(주석 한 줄) — 두 가지 목적:
    · 중간 프록시/방화벽이 "조용한 연결"을 끊지 않게 살아 있음을 알림
    · 보낼 때마다 그 연결의 세션 유효성 재검사 — 로그아웃했으면 끊음(fail-closed)
 ③ 발송: 동기화가 변화 판정한 사이클에만 broadcastChanged() — 전 연결에 한 줄씩,
    전송 실패한 연결은 그 자리에서 정리
 ④ 만료: 30분 수명 → 브라우저 EventSource가 자동 재연결(우리 코드 없이)
```

### 2.3 FE 동작 (`useEventStream`)

- 헤더 알림 벨 컴포넌트가 마운트(로그인 후 전 화면 공통 → 앱 전역 연결 1개).
- 신호 수신 → 정해진 쿼리 키 무효화: 알림 목록·이벤트 목록·문제 목록·이벤트 통계·그룹별
  현황(+상세)·홈 문제 위젯. **2초 스로틀** — 장애 폭풍 때 재조회 폭풍 방지.
- 연결 살아 있으면(`isLive`) 폴링을 1분 → **5분 안전망**으로, 죽으면 1분으로 자동 복귀.

### 2.4 설계 결정 — 왜 이렇게

- **신호에 내용이 없다(빈 신호).** 내용을 실으면 연결마다 권한을 따져 다른 페이로드를 만들어야
  한다. 빈 신호 + "권한 걸린 API로 재조회"면 권한 처리가 사본 서빙 한 곳에 남는다.
- **변화가 있던 주기만, 주기 끝에 한 번.** 매 주기 신호는 폴링과 다를 게 없고, 주기 중간
  발송은 브라우저가 반영 전 데이터를 읽게 만든다.
- **안전망 폴링을 없애지 않았다.** SSE 연결은 절전·네트워크 전환·프록시로 **소리 없이** 죽는다
  — 5분 폴링이 "최악에도 5분 안엔 따라잡는다"의 하한.

## 3. 적용 범위

**연결 지점은 한 곳**: 헤더 알림 벨(`src/components/Notification`)의 `useEventStream` 마운트.

| 신호로 갱신되는 것 | 화면 |
|---|---|
| 알림 목록 | 헤더 알림 벨(뱃지·드롭다운) |
| 이벤트 목록·문제 목록 | 이벤트(알람) 화면 RECENT |
| 이벤트 통계 | 이벤트 현황 차트 |
| 호스트그룹별 알람(+상세) | 그룹 현황 화면 |
| 홈 문제 위젯 | 홈(랜딩) 열린 문제 카드 |

**안 타는 곳**: 메트릭 차트·자산·설정 등 알람 외 데이터(각자 주기 유지), 알람 "상세" 화면
(목록 재진입 시 갱신).

## 4. 해결된 것

- 브라우저 재조회: "1분마다 무조건" → **"실제 변화가 있던 15초 주기당 최대 1회"**.
- 새 알람 반영: 최대 1분 → **~15초 + 즉시 푸시**. 조치(ack)는 표적 재동기화로 즉시.
- dev 실측: 접속 즉시 초기 신호 ✓, visitorId 없는 연결 401 ✓, 무변화 주기 신호 없음 ✓.

## 5. 트레이드오프와 우려점

**트레이드오프(의도한 대가):**

- **빈 신호 → 재조회 1회는 여전히 필요** — 내용 푸시 대비 왕복 1회를 더 쓰지만, 권한 이원화
  위험과 페이로드 버전 관리를 피했다.
- **연결 유지 비용** — 접속자 수만큼 열린 HTTP 연결(비동기 SseEmitter라 스레드는 안 잡지만
  소켓·메모리는 잡는다). 폴링의 순간 부하를 상시 연결로 바꾼 것.
- **30분 수명 재연결** — 만료 순간 몇 초 공백 가능(그 사이 신호 유실 — 다음 신호나 5분 폴링이
  따라잡음). 무한 수명 대신 죽은 연결 청소를 얻었다.

**우려점(지켜봐야 할 것):**

- **프록시 버퍼링** — 실서버 FE는 아파치 뒤. SSE 응답이 버퍼링되면 신호가 모였다가 한꺼번에
  도착해 실시간성이 사라진다. **배포 시 버퍼링 해제 확인 필수.**
- **브라우저 연결 상한** — HTTP/1.1은 도메인당 동시 6연결. 같은 사용자가 탭을 많이 열면
  탭마다 SSE 1개씩 먹어 6탭 이상이면 일반 API까지 줄을 선다. 현 규모(운영자 소수)에선 실질
  문제 아님, 근본 해법은 HTTP/2.
- **하트비트 25초와 프록시 궁합** — 타임아웃이 그보다 짧은 중간 장비가 있으면 재연결이 잦아짐
  (동작은 함, 비효율) — 재연결 빈도로 드러난다.

## 6. 함정 (검수에서 잡힌 것들)

- **세션 재검 누락** — 최초 구현은 연결 시에만 인증 → 로그아웃한 브라우저가 30분간 신호 수신.
  하트비트마다 재검으로 정정.
- **중간 발송** — 처리 도중 여러 번 push하면 FE 2초 스로틀과 겹쳐 **마지막 상태가 화면에 못
  닿는** 경우 발생(스로틀이 마지막 신호를 삼킴) → 주기 끝 단일 발송으로 정정.
- **스로틀의 leading-only(ZM-147로 해소)** — 창 안 마지막 신호가 버려져 장애 폭풍의 마지막
  상태가 다음 안전 폴링(최대 5분)까지 못 닿았다 → 창 끝에 1회 실행하는 trailing 보장 +
  언마운트 시 예약 타이머 정리. 스로틀은 leading+trailing이 세트다.
- **조치(ack) 순서** — ① 읽음 저장 → ② 표적 재동기화 → ③ 신호. ③이 ①보다 앞서면 내 다른
  탭에서 방금 확인한 알람이 "안 읽음"으로 부활.
- **SseEmitter 콜백은 비동기** — 컨테이너 없는 단위 테스트에선 complete 콜백 타이밍이 달라,
  연결 정리 검증을 "전송 실패 시 정리" 경로로 바꿔야 했다.
