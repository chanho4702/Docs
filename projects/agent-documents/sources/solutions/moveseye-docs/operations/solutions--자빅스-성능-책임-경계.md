- 근거 구현: ZM-123 에픽(ZM-124~ZM-131), 분석 정본 `_workspace/features/events/zabbix-load-relief/analysis_zabbix-db-load-relief.md`

> 한 줄 요약 — **MovesEye는 Zabbix API만 사용하며 DB에 직접 접근하지 않는다. API 호출은 동시
> 최대 N건(기본 10)으로 제한되고, 호출량은 서버 로그로 확인할 수 있다. Zabbix DB 자체의
> 성능(보존 기간·서버 사양·수집 주기)은 Zabbix 운영 정책을 따른다.**

---

## 1. MovesEye가 Zabbix에 주는 부하 — 구조


| 경로            | 주기/조건       | Zabbix 콜                                               |
| ------------- | ----------- | ------------------------------------------------------ |
| 이벤트 동기화(증분)   | 15초         | 경량 problem.get 1콜 (+신규·해소분 소량)                         |
| 이벤트 동기화(보정)   | 5분          | problem.get+trigger.get+acknowledges+user.get 한 벌      |
| 알람 목록·알림 벨 화면 | 요청 시        | **Zabbix 직행 없음** — 자체 DB 사본 + 페이지 조치 상세 1콜             |
| 서버/그룹 목록 화면   | 30초 캐시 미스 시 | host.get 등 3~4콜(사용자·그룹필터별 스냅샷)                         |
| 메트릭 차트        | 요청 시        | history.get(48시간 미만 창) 또는 trend.get(이상) — limit 상한 10만 |
| 자산 동기화        | 60분         | host.get 1콜                                            |
|               |             |                                                        |


핵심: **접속자 수와 Zabbix 부하가 비례하지 않는다.** 화면 트래픽은 자체 DB 사본과 30~60초
캐시가 흡수하고, Zabbix가 받는 것은 배치 주기당 상수 콜이다.

## 2. 부하 상한 — 계약 가능한 숫자

- 모든 Zabbix 호출은 단일 커넥션 풀을 지난다. **동시 호출 상한 = `ZABBIX_CLIENT_MAX_CONNECTIONS`
(yml `zabbix.client.max-connections`, 기본 10)**. 포화 시 `zabbix.client.pool-wait-ms`(기본 5초)
대기 후 실패한다 — 어떤 상황에서도 상한을 넘는 동시 부하가 Zabbix로 나가지 않는다.
- 타임아웃: 연결 10초 · 응답 30초.

## 3. 호출량 증명 — 계측 로그

서버 로그에 60초마다 요약이 남는다(호출이 있었던 창만):

```
[zabbix-calls] last 60s: 42 calls, 0 errors — item.get×8 avg=120ms max=310ms; problem.get×4 avg=95ms ...
```

"Zabbix가 느려진 것이 MovesEye 탓인가"라는 문의가 오면 **이 로그가 1차 근거다** — 메서드별
호출 수·평균/최대 소요·실패 수를 시간대별로 재구성할 수 있다.

## 4. 고객(Zabbix 운영) 책임 영역

다음은 MovesEye가 통제할 수 없으며, Zabbix 운영 정책의 영역이다:


| 항목                  | 설명                                                               |
| ------------------- | ---------------------------------------------------------------- |
| Housekeeping(보존 기간) | `history`/`trends` 보존 기간이 과하면 테이블이 비대해져 모든 조회가 느려진다              |
| DB 서버 사양·튜닝         | 인덱스·파티셔닝(TimescaleDB 등)은 Zabbix 설치의 일부                           |
| 수집 주기·아이템 수         | 아이템별 delay는 1초~1일 — 초 단위 수집은 그 자체로 DB 쓰기를 수십 배 늘린다(MovesEye와 무관) |
| Zabbix 서버 HA        | 전체 모니터링 체인의 가용성은 고객 Zabbix 가용성에 종속된다                             |


## 5. 운영 필수 전제 (설치 시 확인)

- 🔴 `**event_sync` 스케줄러는 꺼서는 안 된다** — 알람 목록·알림 벨이 자체 DB 사본을 읽으므로,
동기화가 멈추면 화면이 멈춘 사본을 보여준다(서버 로그에 `event_problems copy looks stale` 경고).
- `event.recent-window-seconds`(기본 300) — Zabbix 서버 설정 *Display OK triggers for N minutes*
(ok_period)와 다르게 운영 중이면 값을 맞춘다(알람 목록의 "최근 해결분" 표시 창).
- Redis는 캐시가 아니라 필수 의존성이다(인증·목록 캐시) — 백업·가용성 대상에 포함.

## 6. 권장 계약/제안서 문구

> 본 제품은 Zabbix 공식 API만 사용하며 Zabbix 데이터베이스에 직접 접근하지 않습니다.
> API 호출은 동시 최대 N건(기본 10, 설정 가능)으로 제한되며, 호출량과 소요 시간은 서버 로그로
> 상시 확인할 수 있습니다. Zabbix 데이터베이스 자체의 성능(데이터 보존 기간, 서버 사양, 수집
> 주기)은 고객의 Zabbix 운영 정책을 따릅니다.
