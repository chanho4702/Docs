# 차트 조회 다이어트 (`ZM-130` `ZM-131`)

## 0. 한눈에

| | |
|---|---|
| **왜** | 30일 차트도 초 단위 원본(수억 행 테이블)을 **제한 없이** 통째로 요청(수십만 행). 잘려도 경고 없이 잘린 차트를 그림 |
| **뭐를** | 긴 기간 조회가 읽는 **테이블과 조회량**을 바꿨다 |
| **어떻게** | 48시간 이상은 원본 대신 시간당 요약본(trends, 1/60 크기). 원본엔 10만 행 상한 + 상한에 걸리면 잘린 데이터를 버리고 요약본으로 다시 |
| **결과** | 3일 차트 수만 행 → 71점. "조용히 틀린 차트"가 구조적으로 소멸 |

## 1. 문제 — 어디서, 무엇이

**발생 지점: 호스트 상세의 메트릭 차트·요약 API들**(CPU·메모리·네트워크·디스크·세션 +
사용자 지정 아이템 차트). Zabbix는 데이터를 두 벌 갖고 있다 — 초 단위 **원본**(history,
수억 행)과 시간당 **요약본**(trends, 1/60 크기). 그런데:

- 30일 차트도 원본을 **무제한** 요청 — 항목 9개 × 30일 × 1분 수집 ≈ **39만 행**.
- 응답이 잘려도 **경고 없이** 잘린 데이터로 그렸다 — 잘린 차트는 틀린 차트인데 티가 안 난다.
- "긴 기간이면 요약본" 분기가 CPU 요약 한 곳에만 있었고 나머지는 전부 원본 직행.
- 부수: 인터페이스 상세가 검색 키마다 item.get을 따로 불러 **9콜**(N+1).

## 2. 어떻게 처리했나

### 2.0 AS-IS → TO-BE (API 단위)

| API | AS-IS (원래) | TO-BE (변경 후) |
|---|---|---|
| `GET /host/{id}/cpu·memory·network·disk/line-charts` (라인차트) | 창 길이와 무관하게 history.get **무제한** | **48h 미만**: history.get(상한 10만) / **48h 이상**: trend.get(1/60) / 요약 비면 원본 폴백 |
| `GET /host/{id}/…/summary` (min·max·avg 요약) | history.get 원본 전체 | **1h 이하**: 원본 / **1h 초과**: trend.get. CPU에만 있던 분기를 전 메트릭 공용화 |
| `GET /host/{id}/items/history` (사용자 지정 아이템 차트) | history.get 무제한, 잘려도 그대로 응답 | 48h 이상 trends 직행 + **상한 도달 그룹은 원시 폐기 후 trends 재조회** + trends 빈 아이템은 원본 보완 |
| 인터페이스 상세의 item.get | 검색 키마다 1콜 × 9 = **9콜** | `search.key_` 배열 + `searchByAny` **1콜** |
| history.get 전반(engine 계층) | limit 미지정 = 무제한 | limit 미지정 시 **기본 상한 10만 행** 강제 + 도달 warn + clock 정렬 |

### 2.1 차트 요청의 처리 흐름 (`AdaptiveSeriesQuery`)

```
차트 요청(항목·기간) 도착
 ① 창 길이 판정: 48시간 미만? → history.get(원본, 상한 10만) 그대로 응답
 ② 48시간 이상 → trend.get(시간당 min/max/avg 버킷) 조회
 ③ 버킷이 하나라도 있으면 → avg를 점으로 접어 같은 응답 모양으로 반환
    (아이템 식별자(itemid)는 요약 경로에서도 보존 — 소비자의 아이템 매칭이 깨지지 않게)
 ④ 버킷이 전부 비었으면(요약 미보존 항목·housekeeping 직후) → 원본으로 자동 폴백
※ 통계(min/max/avg)는 문턱이 1시간 "초과" — 정확히 1시간 창은 진행 중 버킷이 아직 저장 전이라
  trends가 구조적으로 비므로 원본 직행
```

**문턱이 왜 48h/1h인가.** trends는 시간당 1버킷 — 6시간 차트에 쓰면 점 6개로 선이 망가진다.
48h면 버킷 48개 이상 = 선 유지, 그쯤이면 원본은 어차피 화면 픽셀보다 점이 많다. 통계는
해상도가 필요 없어 1시간 초과부터.

### 2.2 아이템 차트의 절단 방어 (`ItemsService`)

```
 ① 48h 미만 창: 값 타입별 그룹으로 history.get →
    응답이 상한(10만)에 닿은 그룹은 "잘렸을 가능성" → 그 원시를 통째로 폐기
    (여러 항목 배치가 잘리면 항목마다 잘린 위치가 제각각 —
     그대로 그리면 어떤 선은 3일치·어떤 선은 하루치가 된다)
 ② 원본이 비었거나 폐기된 아이템만 모아 trend.get 1콜로 채움
 ③ 48h 이상 창: 원본 생략, trends 직행 → trends가 빈 아이템만 원본(상한 내)으로 보완
```

## 3. 적용 범위

| 경로 | 적용 |
|---|---|
| 호스트 상세 CPU·메모리·네트워크·디스크 라인차트, 세션 히스토리 차트 | ✅ chartSeries(48h 문턱) |
| 메모리/스왑 요약, 트래픽 iface 요약, 세션 요약(min/max/avg) | ✅ statsSeries(1h 초과 문턱) |
| 사용자 지정 아이템 이력 차트 | ✅ 48h 직행 + 절단 폐기 + 보완 |
| **인터페이스 UP/DOWN 상태 카운트** | ❌ 의도적 제외 — 이산값 등장 횟수 집계라 평균이 의미를 파괴, 원본 유지 |
| CpuService.getSummary의 기존 1h 분기 | ❌ 동작 검증된 기존 코드 불변(같은 축이라 결과 동일) |

## 4. 해결된 것

- dev 실측: 3일 차트 원본 수만 행 → **trends 정각 버킷 71점**(아이템 식별 보존).
- 원본 무제한 조회 경로 소멸 — 전부 상한 또는 trends. "조용한 절단" 소멸.
- 인터페이스 상세 9콜 → 1콜.

## 5. 트레이드오프와 우려점

**트레이드오프(의도한 대가):**

- **스파이크가 뭉개진다** — trends 점은 시간버킷 평균이라 순간 피크가 낮아 보인다(min/max는
  보존되지만 라인차트는 avg). Zabbix 자체 UI도 같은 방식.
- **avg는 비가중 근사** — "시간버킷 avg의 단순 평균"이라 버킷별 표본 수가 다르면 원본 평균과
  미세하게 어긋난다. CPU 요약이 도입 때부터 써 온 축이라 **승인된 근사**로 문서화. 필요 시
  Zabbix `num`(표본 수) 가중 확장 지점을 남겨 둠.
- **48h 경계의 해상도 점프** — 47h 창은 분 단위, 48h 창은 시간 단위. 연속적 다운샘플링 대신
  단순한 이분 규칙의 대가.
- **절단 시 정밀도 포기** — 부분 원본(정밀·불완전)보다 요약(성김·온전)을 택함.

**우려점(지켜봐야 할 것):**

- **trends=0 항목 + 상한 도달이 겹치면** 빈 차트(원본은 잘렸고 요약은 없음) — 희귀 조합이지만
  존재.
- 1h 초과~2h 창의 trends는 버킷 1~2개라 성김(수용, 문의 소지).
- 10만 상한의 적정성은 경고 로그 빈도로 계속 관찰.

## 6. 함정 (검수에서 잡힌 것들)

- **trends 응답에 itemid가 없었다** — 요약 모델에 식별자가 빠져 차트 소비자의 "아이템 미해석"
  분기가 전부 참 → **긴 기간 차트가 조용히 빈 응답**될 뻔. 모델 필드 추가로 정정.
- **정렬 없는 조각** — 범위 조회가 무정렬로 "임의의 10만 조각" 반환 → clock 정렬+경고 추가.
- **정확히 1시간 창의 빈 통계** — 문턱을 "이상"으로 잡으면 가장 흔한 "최근 1시간"이 구조적으로
  빈 trends를 읽는다 → "초과" 판정으로 정정.
- **searchByAny 누락 = 조용한 0건** — 키 배열 search에 이 옵션이 없으면 AND로 읽혀 에러 없이
  빈 결과 → 테스트로 고정.
