# 동기화 이원화와 데이터 청소 (`ZM-127`)

## 0. 한눈에

| | |
|---|---|
| **왜** | 사본을 채우는 배치가 1분마다 알람+규칙+조치+사용자를 **전부 다시** 읽었다 — 대부분 1분 전과 같은 데이터. 사본 도입으로 "더 자주"가 필요한데 무거운 걸 더 자주 돌릴 순 없었다 |
| **뭐를** | 동기화의 **주기와 무게**를 나눴다 |
| **어떻게** | 15초마다 "뭐가 열렸고 뭐가 꺼졌나"만 가벼운 1콜 + 5분마다 규칙·조치까지 꼼꼼한 한 벌 + 조치 직후엔 그 알람만 즉시 |
| **결과** | 무거운 호출 1/5로, 알람 반영은 1분 → **15초 이내**로 오히려 빨라짐 |

## 1. 문제 — 어디서, 무엇이

**발생 지점: BE 백그라운드 배치 `EventSyncService`(스케줄러 event_sync).** 1분마다
알람·규칙·조치 이력·Zabbix 사용자 목록까지 **전부 다시** 읽는 무거운 사이클이 돌았다.
대부분은 1분 전과 똑같은 데이터다 — "바뀐 게 있나?"만 물으면 되는데 매번 전집을 복사했다.

[사본 서빙](solutions--ZM-125-%EC%95%8C%EB%9E%8C-%EC%82%AC%EB%B3%B8-%EC%84%9C%EB%B9%99%EA%B3%BC-%EA%B6%8C%ED%95%9C-%EC%9E%AC%ED%98%84.md)으로 알람 화면이 전적으로 이 배치에 의존하게 되면서
요구가 상충했다: 화면 신선도를 위해선 **더 자주**, Zabbix 부하를 위해선 **더 가볍게** —
무거운 한 벌을 더 자주 돌리는 건 답이 될 수 없었다.

## 2. 어떻게 처리했나

### 2.0 AS-IS → TO-BE (배치 단위)

| 대상 | AS-IS (원래) | TO-BE (변경 후) |
|---|---|---|
| event_sync 배치의 Zabbix 조회 | **1분마다** problem.get(30일 창)+trigger.get+acknowledges+user.get **전체 한 벌** | **15초마다** 경량 problem.get **1콜**(시간창 없음·recent 포함) + **5분마다** 전체 한 벌 |
| 사본 갱신 방식 | 매번 전 행 upsert(변화 유무 모름) | 신규만 표적 완전 동기화, 기존은 `IS DISTINCT FROM` 조건부 UPDATE(변화 집계 → SSE 신호 조건) |
| 해소 반영 | 다음 전체 동기화까지 대기(최대 1분+) | 창 내 해소 즉석 채움 + 사라진-사건 되짚기 — **≤15초** |
| 조치(ack) 반영 | 다음 주기까지 대기 | 그 알람만 즉시 표적 재동기화 |
| 오래된 미해소 행 청소 | 발생 시각 기준 삭제(장기 장애 오삭제 위험) | **updated_at(마지막 갱신) 기준 2일** — 살아 있는 행은 절대 안 걸림 |

**기술: 주기 이원화(경량 증분 + 전체 보정) + 조건부 UPDATE + 표적 재동기화.** "자주 바뀌는
축은 자주·싸게, 무거운 축은 가끔·제대로"로 쪼갠 것이다. 스케줄러는 15초마다 이 서비스를
부르고, 서비스가 "마지막 보정 후 5분이 지났나"로 증분/보정을 스스로 고른다.

### 2.1 증분 사이클의 처리 흐름 (15초마다)

```
 ① Zabbix에 가벼운 problem.get 1콜 — 규칙·조치·사용자 안 붙임.
    시간창 없음(30일 전에 발생해 아직 열린 장애도 포함) + recent:true(최근 해소분 포함)
    응답이 1만 건 상한에 닿으면 경고 로그(조용한 누락 금지)
 ② 응답의 알람 id를 사본과 대조해 세 갈래로:
    [처음 보는 알람] → 그것만 골라 규칙·조치 포함 완전 조회(표적 재동기화) 후 적재.
      발생하자마자 해소된 것이면 복구 사건 시각까지 2단 조회로 채움
    [아는 알람] → 이름·심각도·억제·원인이 실제로 바뀐 행만 UPDATE
      (SQL IS DISTINCT FROM — "무엇이 바뀌었나"의 판정이 곧 ③의 신호 조건)
    [아는 알람이 해소 표시로 돌아옴] → 복구 사건 시각을 조회해 즉석에서 r_clock 채움.
      단, 이미 해소 확정(r_clock>0)인 행은 절대 되돌리지 않음(CASE 가드)
 ②′ 사본엔 열려 있는데 응답에 없는 알람 → "Zabbix에서 사라짐 = 해소"로 판정,
    복구 사건을 찾아 해소 시각을 채움. 기준 집합은 미해소 부분집합만(recent 포함 후
    "응답에 있음=열려 있음"이 아니므로)
 ③ 이 사이클에 신규·해소·값 변화가 하나라도 있었으면, DB 반영이 전부 끝난 뒤
    SSE 신호 1회(→ SSE 알람 푸시 문서) — 조용한 사이클은 신호 없음
```

### 2.2 보정 사이클 (5분마다)

규칙·조치 이력·Zabbix 사용자·읽음 상태까지 전부 다시 맞추는 종전의 무거운 한 벌. 증분이 못
보는 축(규칙 비활성화, 타인 조치, 그룹 변경)을 따라잡고, 사라진-사건 되짚기도 같이 돈다.

### 2.3 조치 직후 (즉시)

사용자가 알람을 확인(ack)하면 다음 주기를 기다리지 않는다: ① 조치자의 읽음 기록 저장 →
② 그 알람만 표적 재동기화 → ③ SSE 신호. **이 순서가 계약이다** — ③이 ①보다 앞서면 같은
사용자의 다른 탭에서 방금 확인한 알람이 "안 읽음"으로 되살아난다.

### 2.4 데이터 청소 — 지울 것과 절대 지우면 안 되는 것

- 해소된 알람: 30일 후 삭제(화면 조회 범위 밖).
- **좀비**(Zabbix에서 원본이 삭제돼 해소 시각을 영영 못 받는 미해소 행): "발생 N일"이 아니라
  **"마지막 갱신(updated_at) 2일"** 기준 — 살아 있는 알람은 보정이 5분마다 upsert하므로 절대
  안 걸리고, 아무도 안 건드리는 행만 걸린다. **청소 기준은 "얼마나 오래됐나"가 아니라
  "시스템이 아직 이 행을 보고 있나"다.**

## 3. 적용 범위

- 이 배치가 채우는 것: `event_problems` 사본 = **알람 목록·알림 벨·심각도 칩**의 데이터 원천,
  그리고 SSE 신호의 발원지.
- 주기는 스케줄러 화면의 event_sync 항목에서 조정 가능(기본 15초, V50 — 화면에서 저장하면
  마이그레이션 기본값 대신 저장값이 우선).
- **안 타는 곳**: 알람 이력(HISTORY) 모드·홈 KPI·그룹 집계·지도 배지 — 전부 Zabbix 직행 유지.

## 4. 해결된 것

- 무거운 한 벌의 빈도 1분 → **5분**(1/5), 그 사이를 경량 1콜이 메움.
- 알람 발생·해소의 화면 반영 최대 1분 → **≤15초**.
- dev 실측: 증분 "0 new 0 changed"(무변화 시 무갱신·무신호), 보정 1.6초/56건.

## 5. 트레이드오프와 우려점

**트레이드오프(의도한 대가):**

- **이원화 = 복잡도** — 한 덩어리 동기화가 증분/보정/표적/되짚기/즉석 채움의 다섯 경로가
  됐다. 실제로 통합 검수 결함 8건 중 3건(시간창·recent 의미 전이·업서트 역행)이 이 복잡도에서
  나왔다 — **부하 절감의 상당 부분을 검증 비용으로 지불**했다.
- **규칙·조치 축의 신선도** — 규칙 비활성화·타인 조치는 여전히 최대 5분 늦게 반영된다
  (종전 1분보다 느려진 유일한 축 — 목록 노출 여부가 아니라 부가 정보라 수용).
- **recent 포함의 의미 전이** — "응답에 있음=열려 있음"이 깨져 되짚기·업서트 로직이 미해소
  부분집합 기준으로 전부 재조정됐다(함정 §6).

**우려점(지켜봐야 할 것):**

- **열린 알람 1만 건 초과** 설치본은 상한 절단(경고 로그로 감지) — 커서 청크 적재는 그런
  설치본이 나오면 확장.
- **스케줄러 정지 = 화면 정지** — 15분 stale warn이 감지선이지만, 운영자가 로그를 봐야 안다.
- 좀비 기준 2일은 "보정이 2일 내내 죽어 있으면 열린 행도 좀비 판정"과 등가 — 동기화 장기
  정지 운영이 생기면 기한 재고.

## 6. 함정 (검수에서 잡힌 것들)

- **경량 조회의 모델 필드 누락(HIGH)** — 증분용 경량 응답 모델에 억제·원인·복구 필드가 없어
  매 15초 UPDATE가 그 컬럼들을 NULL로 훼손할 뻔했다. **응답에 값이 있어도 모델이 안 담으면
  조용히 소실된다.**
- **"응답에 있음=열려 있음" 가정의 붕괴** — recent 포함 순간 이 가정이 깨진다. 되짚기 기준을
  미해소 부분집합으로 좁히지 않으면 사라진-사건 탐지가 왜곡된다.
- **해소 확정 행의 역행** — 복구 시각 조회가 일시 실패하면 upsert가 확정된 해소 시각을 0으로
  되돌릴 수 있었다 → "r_clock>0 행은 되돌리지 않는다" CASE 가드(Zabbix에서 같은 사건 재개는
  없으므로 안전).
- **되짚기 후보의 앞 블록 정체(ZM-145로 해소)** — 복구 사건을 못 찾는 후보가 오래된-순 첫
  500건을 차지하면 뒤가 영영 처리되지 않았다 → clock 진행 커서 + 끝 도달 시 0 되감기 재순회.
- **읽음 상태의 두 가지 축 결함(ZM-146으로 해소)** — ① 동기화가 읽음 행을 Zabbix userid로
  만들었는데 벨·조치 기록은 내부 사용자 id 축(두 값이 같은 설치본에서만 우연히 동작) → 내부
  id로 통일, 내부 계정 없는 사용자는 행 미생성. ② upsert가 conflict 시 is_read를 안 바꿔
  "조치자=읽음"이 기존 unread를 영영 못 뒤집음 → OR 승격 + read_at COALESCE. 🔴 기존 DB의
  Zabbix-id 축 잔재 행은 판별 불가라 정리하지 않음(에픽 보고서 ZM-146 절 참조).
