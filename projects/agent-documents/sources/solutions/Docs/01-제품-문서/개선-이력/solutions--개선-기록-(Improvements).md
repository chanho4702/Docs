# 개선 기록 (Improvements)

제품을 고치면서 **구조적으로 좋아진 것들**을 하나씩 기록하는 폴더다. 기능 문서(`features/`)가
"이 기능은 무엇인가"에 답한다면, 여기는 **"어디서 무엇이 문제였고, 어떤 기술로 어떻게 바꿨고,
무엇을 얻고 무엇을 포기했나"**에 답한다. 나중에 비슷한 문제를 만났을 때 같은 답을 다시
발명하지 않고, 같은 트레이드오프를 다시 고민하지 않는 것이 목적이다.

## 문서 양식 (전 문서 공통)

frontmatter에 **`issue:`** 필드로 Jira 이슈 태그를 단다(복수면 배열). 본문은:

0. **한눈에 — 왜 / 뭐를 / 어떻게 / 결과** : 4행 요약 표. 바쁜 독자는 여기서 끝
1. **문제 — 어디서, 무엇이** : 문제가 발생한 지점(화면/배치/라이브러리)과 증상, 가능하면 숫자
2. **어떻게 처리했나** : 맨 앞에 **AS-IS → TO-BE 표**(어떤 API가 원래 어떻게 동작했고
   어떻게 바뀌었나, API 단위) + 채택한 기술 + **단계별 처리 흐름**(요청/이벤트가 들어오면
   어떤 컴포넌트가 순서대로 뭘 하는지) — 이 절이 문서의 본체다. 뭉뚱그리지 말 것
3. **적용 범위** : 이 개선을 실제로 타는 화면·API·배치가 어디인지 (안 타는 곳도 명시)
4. **해결된 것** : 실측 수치와 사라진 문제
5. **트레이드오프와 우려점** : 얻은 것의 대가로 포기한 것, 남아 있는 걱정
6. **함정** : 구현·검수에서 밟았거나 밟을 뻔한 것 (다음 사람이 안 밟게)

## 추가 규칙

- 새 개선을 하면 여기에 한 문서를 추가하고 이 표에 한 줄을 늘린다. 위 양식 0~6절을 다 채운다 —
  특히 **§2 처리 흐름**(단계별)과 **적용 범위**(안 타는 곳 포함), **트레이드오프**는 생략하지 않는다.
- frontmatter `issue:`에 Jira 태그를 달아 이슈↔문서를 양방향으로 찾을 수 있게 한다.
- 코드 위치는 파일 경로 수준까지만 적는다(라인 번호는 금방 낡는다).
- 검수(코드 리뷰)에서 잡힌 결함과 그 교훈도 해당 문서의 "함정"에 남긴다 — 결함은 부끄러운 게
  아니라 다음 사람이 안 밟게 하는 자산이다.
