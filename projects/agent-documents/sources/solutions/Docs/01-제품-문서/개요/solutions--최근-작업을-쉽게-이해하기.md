# 최근 작업을 쉽게 이해하기

[읽기 안내](solutions--MovesEye-%EC%B5%9C%EA%B7%BC-%EC%9E%91%EC%97%85%EA%B3%BC-APM-%EC%9D%BD%EA%B8%B0-%EC%95%88%EB%82%B4.md) · 다음: [APM 개념](solutions--APM-%EA%B0%9C%EB%85%90%EA%B3%BC-%EC%9A%B0%EB%A6%AC-%ED%99%94%EB%A9%B4.md)

최근 변화는 세 가지로 묶입니다. **기존 인프라 모니터링의 부하를 줄이도록 조회 구조를 개선했고, APM으로 애플리케이션의 처리 과정을 보기 시작했으며, 운영자가 데이터 상태를 이해하고 보관할 수 있도록 보강했습니다.**

아래의 완료 표시는 소스 기준입니다. 커밋은 변경 근거이며 고객 환경에서의 동작 보증은 아닙니다.

## 1. 기존 인프라 모니터링을 더 가볍게 만들었다

예전에는 여러 사용자가 화면을 열 때 비슷한 Zabbix 조회가 반복될 수 있었습니다. 최근 성능 작업은 필요한 정보를 사본과 캐시에서 제공하고, 같은 요청을 합치며, 바뀐 구간을 중심으로 갱신하는 방향입니다.

**캐시**는 최근 조회 결과를 잠시 보관하는 것입니다. **SingleFlight**는 동시에 들어온 같은 조회를 한 번만 실행하고 결과를 나누는 것입니다. **증분 조회**는 이미 확보한 시간 구간을 매번 다시 받지 않는 것입니다. 세 가지는 서로 다른 문제를 해결합니다.

SSE는 서버가 화면에 변경 소식을 보내는 연결입니다. 화면이 알림을 빨리 받게 해 주지만, 알림 자체가 전체 데이터의 저장소는 아닙니다. 연결이 끊겼다가 돌아올 때에는 조회로 현재 상태를 맞춰야 합니다.

성과는 Zabbix 요청량과 반복 다운로드를 줄일 수 있는 구조를 갖춘 것입니다. 대가는 사본의 신선도, 권한별 캐시 분리, 끊긴 구간 복구를 정확하게 처리해야 한다는 점입니다.

## 2. 권한을 서버에서 강제하도록 보강했다

메뉴를 숨기는 것만으로 접근 권한이 보장되지는 않습니다. 사용자가 API를 직접 호출해도 서버가 동일한 권한을 검사해야 합니다.

권한 작업은 역할별 설정을 BE 검사와 연결하고, 본인 정보 수정과 관리자 수정을 나누며, 권한 회수 이후의 세션 사용을 통제하는 방향으로 진행됐습니다. 예를 들어 화면에서 수정 버튼을 보지 못하는 계정은 API로 우회해도 수정할 수 없어야 합니다.

이 작업은 APM에도 중요합니다. 모니터링 조회, 수집기 관리, 원문 조회, 아카이브 다운로드는 동일한 권한이 아닙니다. 새 API를 추가할 때 이 경계를 계속 유지해야 합니다.

근거: [권한 강제와 세션 회수](../%EA%B8%B0%EB%8A%A5/solutions--%EA%B6%8C%ED%95%9C-%EA%B0%95%EC%A0%9C%EC%99%80-%EC%84%B8%EC%85%98-%ED%9A%8C%EC%88%98.md), [권한 설계 결정](../%EA%B2%B0%EC%A0%95%EA%B8%B0%EB%A1%9D/solutions--ADR-0002-%EC%97%AD%ED%95%A0-%EA%B6%8C%ED%95%9C-BE-%EA%B0%95%EC%A0%9C%EC%99%80-%EC%84%B8%EC%85%98-%EC%84%B8%EB%8C%80.md).

## 3. APM을 단계적으로 구현했다

서버 CPU가 정상이어도 사용자의 주문 요청은 느릴 수 있습니다. 외부 결제 API나 SQL 하나가 지연되는 경우가 있기 때문입니다. APM은 이 빈틈을 메웁니다.

| 단계 | 해결하려던 질문 | 구현 내용 |
|---|---|---|
| P1 메트릭 | 요청이 얼마나 많고 느리며 실패하는가 | 서비스·인스턴스 등록, OTLP 수신, 지표 정규화·저장·집계, 개요·런타임 |
| P2 트레이스 | 요청 안에서 어디가 느렸는가 | span 저장, 워터폴, 서비스 맵, 오류·DB 호출·외부 의존 그룹 |
| P3 운영 기능 | 장애 기준과 반복 점검을 어떻게 운영하는가 | SLO, 합성 점검, 메시징·배치 조회, 리포트, AI 조회 도구 |
| P4 사용자·환경 관측 | 브라우저와 컨테이너 맥락은 어떤가 | RUM 수신·집계·조회, Kubernetes 관련 속성과 수집 옵션 |
| P5 실시간 관제 | 최근 완료 요청과 지금 진행 중인 요청은 어떤가 | 완료 span 별도 스트림·X-View, 진행 중 요청 Java 확장, 걸림 장부 |

P1~P5는 작업 이름입니다. 숫자가 크다고 앞 단계의 모든 결함과 운영 검증이 끝난 것은 아닙니다.

특히 P5에는 **완료된 요청**을 보여 주는 경로와 **아직 끝나지 않은 요청**을 보여 주는 경로가 있습니다. 일반적인 span 전송만으로는 진행 중 요청의 현재 상태를 얻기 어려워 Java 확장이 추가됐습니다.

## 4. 9월 말에는 기능보다 신뢰성과 설명을 보강했다

표의 UPSERT는 “행이 없으면 추가하고 있으면 갱신하는 저장 방식”, 히스토그램 family는 “분포가 어떤 종류의 측정값인지 구분하는 분류”, 걸림 장부는 “임계 시간보다 오래 진행된 요청의 기록”입니다.

| 시기 | 변화 | 사용자에게 주는 의미 | 확인 근거 |
|---|---|---|---|
| 9월 22~28일 | APM 내보내기와 화면 자기설명 | 조회 범위·보존 경계·데이터 없음의 이유를 이해하고 결과를 파일로 받음 | BE `213d875`, `43570e6`; 기능 문서 |
| 9월 28~29일 | 수집 회복력 | 수신 과부하 제한, 종료 처리, 큐·재시도 설정과 관측 보강 | BE `78cd40b`, FE `ed4df58` |
| 9월 30일 | RUM·수집기 로그 UPSERT 정렬 | 동시에 같은 행을 갱신할 때 서로 기다리는 교착 위험 감소 | BE `5b6d5a0` |
| 9월 30일 | RUM 예산 환급·히스토그램 family 확인 | 서버 저장 실패로 일 예산만 소진되는 문제와 경계 조회의 모호함 보강 | BE `85d9e9d`, `92e6857` |
| 9월 30일 | 서비스·걸림 요청 조회 개선 | 전체 인스턴스 로드와 행마다 추가 조회하는 비용 감소 | BE `79becc0`, `c1d14fb` |

## 5. 10월 2일에는 콜드 아카이브가 소스에 반영됐다

보존 기간이 지난 데이터를 DB에서 삭제하기 전에 파일로 보관하는 기능입니다. 파일 생성 결과를 **원장**에 남기고, 삭제 전에 원장과 파일을 확인하는 **DROP 게이트**를 붙였습니다. 공통 파일 관리 기반과 APM 데이터 추출 부분을 분리했습니다.

현재 기본 대상은 1시간 메트릭, 트레이스 요약, SLO 스냅샷입니다. 1분 메트릭과 span 원본은 선택적으로 켜는 대상입니다. 기능은 기본 꺼짐입니다.

여기서 세 가지를 구분해야 합니다.

1. **내보내기:** 사용자가 지금 조회할 수 있는 데이터를 파일로 받습니다.
2. **콜드 아카이브:** 정리 예정 데이터를 파일로 남깁니다.
3. **복원·장기 상세 조회:** 파일 데이터를 다시 검색·분석할 수 있게 만드는 별도 기능입니다. 보류 상태입니다.

또한 “보관에 실패하면 절대 삭제하지 않는다”는 설명은 정확하지 않습니다. 기능이 켜진 대상에 보류 정책이 적용되지만, `onFailure=continue`이거나 유한한 `maxHoldDays`를 넘으면 보관 없이 삭제가 허용될 수 있습니다.

BE `3637c77`, FE `2ed84f7`을 확인했습니다. 기존 기록에는 관련 테스트 통과가 있으나 브라우저·Linux/NFS·실제 배포 환경 검증은 미실시로 적혀 있습니다. 이번 작업에서도 이를 새로 실행하지 않았습니다.

## 6. 주변 기능의 진행 상태

클라우드 스냅샷은 보관량 정리와 수집 주기 분리가 구현됐습니다. 자주 바뀌는 성능 지표와 덜 바뀌는 구성 정보를 같은 주기로 계속 수집하지 않도록 비용을 나눈 작업입니다. [적재량 정리](../%EA%B8%B0%EB%8A%A5/solutions--%ED%81%B4%EB%9D%BC%EC%9A%B0%EB%93%9C-%EC%8A%A4%EB%83%85%EC%83%B7-%EC%A0%81%EC%9E%AC%EB%9F%89-%EC%A0%95%EB%A6%AC.md), [수집 주기 분리](../%EA%B8%B0%EB%8A%A5/solutions--%ED%81%B4%EB%9D%BC%EC%9A%B0%EB%93%9C-%EC%8A%A4%EB%83%85%EC%83%B7-%EC%88%98%EC%A7%91-%EC%A3%BC%EA%B8%B0-%EB%B6%84%EB%A6%AC.md)에서 확인할 수 있습니다.

GPU/LLM 모니터링은 현재 문서에서 설계·보류 작업으로 관리됩니다. 9월 30일에는 수집 경로를 다시 설계했습니다. 이번 정리에서는 제품 기능으로 완료됐다고 판단하지 않습니다. [GPU 후속 기록](../../03-%EA%B8%B0%ED%9A%8D-%EB%B0%B1%EB%A1%9C%EA%B7%B8/solutions--GPU-%EB%AA%A8%EB%8B%88%ED%84%B0%EB%A7%81-%ED%9B%84%EC%86%8D-%EC%9E%91%EC%97%85.md).

## 7. 최근 작업에 대한 평가

좋아진 점은 수집에서 화면까지 기능이 이어지고, “값이 없다”는 상황을 설명하며, 보존과 수집 장애까지 다루기 시작했다는 것입니다.

미흡한 점은 **구현 완료·시험 완료·배포 완료를 한눈에 구분하기 어렵고, 실패 후 재시도와 동시성 같은 경계 조건에 남은 위험이 있다는 것**입니다. 문서에서도 9월의 미착수 기록과 10월의 구현 기록이 함께 보여 현재 상태를 독자가 직접 추적해야 했습니다.

다음 우선순위는 [APM 부족점 리포트](solutions--%ED%98%84%EC%9E%AC-APM-%EA%B5%AC%ED%98%84%EC%9D%98-%EB%B6%80%EC%A1%B1%EC%A0%90-%EB%B6%84%EC%84%9D-%EB%A6%AC%ED%8F%AC%ED%8A%B8.md)에 근거와 완료 조건을 함께 적었습니다.
