# 현재 APM 구현의 부족점 분석 리포트

[읽기 안내](solutions--MovesEye-%EC%B5%9C%EA%B7%BC-%EC%9E%91%EC%97%85%EA%B3%BC-APM-%EC%9D%BD%EA%B8%B0-%EC%95%88%EB%82%B4.md) · [설계·구현 지도](solutions--%EC%84%A4%EA%B3%84%EC%99%80-%EA%B5%AC%ED%98%84%EC%9D%98-%EC%97%B0%EA%B2%B0-%EC%A7%80%EB%8F%84.md)

> **2026-10-06 후속:** 메트릭 원자성·SSE 송신 큐·조회 포인트 상한·RUM Web Vitals를 보완했습니다. 이 문서의 본문은 10월 5일 분석 기준을 보존하며, 최신 구현·검증 범위와 잔여 대규모 과제는 [APM 대규모 운영 준비 상태](solutions--APM-%EA%B5%AC%ED%98%84-%EB%B3%B4%EC%99%84%EA%B3%BC-%EB%8C%80%EA%B7%9C%EB%AA%A8-%EC%9A%B4%EC%98%81-%EC%A4%80%EB%B9%84-%EC%83%81%ED%83%9C.md)를 먼저 확인하세요.

**판정: APM의 주요 기능은 폭넓게 구현됐지만, 데이터 정확성과 운영 신뢰성을 보강해야 합니다.** 우선순위는 새 화면을 늘리는 것보다 메트릭 재전송 멱등성, 알람 생성의 동시성, 실시간 송신 용량을 정리하고 실제 설치 환경에서 증명하는 것입니다.

“APM 기준”은 특정 경쟁 제품의 기능 수가 아니라 다음 질문으로 평가했습니다. 요청의 양·속도·실패를 볼 수 있는가, 원인을 추적할 수 있는가, 장애 중에도 데이터 의미가 유지되는가, 고객 환경에서 지속적으로 운영할 수 있는가. 아래 우선순위는 이 기준에 따른 **분석 제안**이며 기존 보류 작업을 자동으로 착수한다는 뜻은 아닙니다.

## 1. 분석 범위와 증거 수준

기준일은 2026-10-05, BE HEAD는 `3637c77`, FE HEAD는 `9dfcbe8`, Flyway 소스는 V69까지입니다. 두 저장소의 현재 브랜치는 master입니다. BE 수집기 Controller에 기존 미커밋 변경이 있으므로 HEAD만으로 작업 폴더 전체를 재현할 수는 없습니다.

- **코드 확인:** 이번에 현재 구현과 호출 순서·설정을 확인한 사실입니다.
- **기존 기록:** 설계·QA·검수 문서에 있는 결과입니다. 이번 테스트 실행 결과가 아닙니다.
- **추론:** 확인한 구조에서 예상되는 영향입니다. 발생 빈도·실제 손실량은 실측하지 않았습니다.
- **제안:** 수정 방향과 검증 완료 조건입니다.

이번에는 서비스 재기동·DB 변경·동시 요청 재현·부하 시험을 하지 않았습니다. 따라서 아래 위험은 코드 구조에 근거한 판단이며 운영 장애 발생 사실로 단정하지 않습니다.

## 2. APM 기능 범위 평가

| 평가 항목 | 상태 | 현재 제공 범위와 부족점 |
|---|---|---|
| 서비스·endpoint 성능 | 현재 | 처리량·오류·지연·런타임 조회 기반. 집계 정확성 경계 보강 필요 |
| 분산 trace 분석 | 현재 | 워터폴·서비스 맵·오류·DB·외부 의존. 계측·샘플링된 데이터 범위 |
| 실시간 완료 요청 | 현재 | 별도 수신·링·SSE·X-View. 운영 규모 송신 검증 부족 |
| 진행 중 요청·걸림 | 부분 | Java 확장과 장부 존재. 모든 언어·프레임워크 동등 지원은 아님 |
| SLO·합성·알람 | 현재 | 운영 기능 존재. 알람 원자성·외부 I/O 경계 개선 필요 |

| 메시징·비동기 | 부분 | span·link·배치 조회 기반. 실제 브로커 계측의 종단 검증 증거 부족 |
| Kubernetes | 부분 | 환경 속성·수집 옵션. 실제 RBAC·TLS·다중 클러스터 검증 부족 |
| 로그와 trace의 종합 조사 | 부분 | 특수 목적 로그 수신 존재. 범용 애플리케이션 로그 저장·검색은 확인되지 않음 |
| 코드 수준 원인 분석 | 부분 | 계측된 작업 구간은 보임. CPU·메모리 연속 프로파일, 함수별 비용 분석은 확인되지 않음 |
| 장기 상세 조사 | 부분 | 파일 아카이브 구현. 검색·복원·pin과 30/90일 상세 정책은 보류 |
| 다중 BE 운영 | 부분 | DB 기반 경로와 노드 로컬 라이브·예산 상태가 혼재. 배치 분산 방어와 라이브 HA는 별개 |
| 자체 수집 상태 관측 | 현재 | 큐·마지막 수신·폐기 사유 등 존재. 종단 수량 보존과 고객별 용량 기준은 보강 필요 |

“확인되지 않음”은 이번 조사에서 제품 경로·완료 근거를 찾지 못했다는 뜻입니다. 해당 기능이 모든 APM 제품의 필수라는 뜻은 아닙니다. 예를 들어 프로파일링은 깊은 코드 진단을 목표로 할 때의 확장 과제입니다.

## 3. 가장 먼저 해결할 데이터 정확성 문제

아래에서 **멱등성**은 같은 입력을 다시 보내도 최종 결과가 달라지지 않는 성질, **트랜잭션**은 여러 DB 변경을 함께 성공하거나 함께 취소하는 단위입니다. **원자성**은 그 묶음이 반만 반영되지 않는 성질이며, **UPSERT**는 없으면 추가하고 있으면 갱신하는 저장 방식입니다.

### R1. 메트릭 중복 확인과 저장이 하나의 작업으로 묶이지 않는다

**중요도: 높음 · 코드 확인 · 배포 확대 전 우선 검증 제안**

현재 수신 흐름은 `isDuplicate`로 확인 → `pipeline.ingest`로 적재 → `receiptService.record`로 처리 기록을 남깁니다. 기록은 `REQUIRES_NEW`의 별도 트랜잭션이고, 메트릭 저장에는 더하기 방식의 UPSERT가 있습니다.

동일한 본문 A와 B가 거의 동시에 도착하면 둘 다 “아직 처리 기록 없음”을 볼 수 있습니다. 이후 둘 다 값을 더하고 마지막 기록만 중복으로 판정될 수 있습니다. 이미 저장했는데 기록이 남지 않은 실패 경로에서도 다음 전송을 다시 더할 위험이 있습니다.

**영향 추론:** 요청 수·오류 수·히스토그램 집계가 부풀 수 있습니다. APM은 숫자를 근거로 장애를 판단하므로 화면 오탈자보다 우선순위가 높습니다. 모든 메트릭과 모든 재전송이 반드시 중복된다는 뜻은 아니며, 누적형 지표 처리 등 세부 경로의 재현이 필요합니다.

**개선 제안:** 파싱·파티션 준비 이후, 영수증 선점과 해당 데이터 갱신을 하나의 트랜잭션으로 처리합니다. 영수증만 별도 커밋하고 실패 시 삭제하는 방식은 피합니다.

**완료 조건:** 동일 본문 동시 요청, 적재 중간 실패, 영수증 실패, 응답 유실 후 재전송에서 최종 집계가 정확히 한 번 반영됨을 실제 PostgreSQL로 검증합니다. 부분 실패가 있었던 배치도 포함해야 합니다.

[기존 전체 검토](../../09-%EB%B3%B4%EA%B3%A0%EC%84%9C/solutions--APM-%EC%A0%84%EC%B2%B4-%EA%B2%80%ED%86%A0-%EB%B3%B4%EA%B3%A0-%EC%BD%94%EB%93%9C-%EA%B8%B0%EB%B0%98-%EC%BD%94%EB%8D%B1%EC%8A%A4-3-%EC%9E%90%EC%B2%B4-%EA%B0%90%EC%82%AC-3-%EB%B3%91%EB%A0%AC-%282026-09-28%29.md)와 현재 구조가 일치합니다.

### R2. 요청 걸림 알람을 두 경로에서 열 수 있다

**중요도: 높음 · 코드 확인 · 실제 중복 발생 빈도 미측정**

1초 감시기의 `ApmStuckRequestLedger.fire`와 주기 평가기의 `ApmAlertEvaluationService`가 각각 열린 이벤트를 조회하고 없으면 저장합니다. Flyway의 `apm_alert_event`에는 이 두 경로를 묶는 열린 이벤트 부분 UNIQUE 제약이 확인되지 않았습니다.

“조회했을 때 없었다”는 사실만으로 다음 순간에도 다른 실행자가 생성하지 않았다고 보장할 수 없습니다. 서로 같은 시점에 빈 결과를 보면 두 행을 만들 수 있습니다.

**영향 추론:** 같은 상황의 알람 이력이 중복되거나, 해제 시점과 감시기 상태가 어긋날 수 있습니다.

**개선 제안:** 이벤트 생성·해제의 소유자를 하나로 정하고, DB에서도 규칙·서비스별 열린 이벤트의 유일성을 보장합니다. 전역 규칙의 null 서비스 처리, 기존 중복 행 정리, 충돌 시 응답도 함께 설계해야 합니다.

**완료 조건:** 두 경로를 동시에 실행해 열린 이벤트가 한 개만 남는지, 복구·규칙 비활성·재시작 뒤에도 일관되는지 검증합니다.

근거: [Ledger](../../moveseye-be-spring/src/main/java/com/dmove/moveseye/premium/apm/alert/evaluate/ApmStuckRequestLedger.java) `fire`, [평가기](../../moveseye-be-spring/src/main/java/com/dmove/moveseye/premium/apm/alert/evaluate/ApmAlertEvaluationService.java) `findOpen`·`events.save`, [V38](../../moveseye-be-spring/src/main/resources/db/migration/V38__apm_p1.sql). 기존 백로그의 V69+라는 안내는 현재 V69가 아카이브에 사용됐으므로 새 작업 시 다시 번호를 확인해야 합니다.

### R3. RUM 저장 실패가 브라우저 재전송으로 이어지지 않는다

**중요도: 중간~높음 · 코드 확인**

`rum-snippet.js`는 `fetch(..., keepalive: true)`를 기다리지만 HTTP 응답의 `ok`를 확인하지 않고 재시도 큐도 두지 않습니다. HTTP 503은 fetch의 네트워크 예외와 같지 않으므로 `catch`만으로 처리되지 않습니다.

최근 BE의 예산 환급은 저장 실패 때 예산을 돌려주는 개선입니다. 브라우저가 잃어버린 관측값을 다시 보내는 기능은 아닙니다.

**영향 추론:** 일시적 서버 장애나 제한 상황에서 사용자 경험 데이터가 누락될 수 있습니다. 누락된 데이터를 정상 0으로 해석하면 안 됩니다.

**개선 제안:** 제품이 허용할 손실 범위를 먼저 정하고, 응답별 처리·유한 재시도·클라이언트 버퍼 상한·종료 시 동작을 설계합니다. 무제한 저장이나 재시도는 피합니다.

**완료 조건:** 429·503·네트워크 단절·페이지 종료를 시험하고 재시도 중복 방지와 일 예산 규칙이 함께 유지되는지 확인합니다.

근거: [RUM snippet](../../moveseye-be-spring/src/main/resources/apm/rum-snippet.js) 63~67행.

## 4. 실시간 관제와 운영 규모의 부족점

### R4. 연결 수 설정과 실제 송신 처리 용량이 분리되어 있다

**중요도: 높음, 상한 확대 시 특히 중요 · 코드 확인**

동시 시청 설정은 활성 500·대기 200까지 허용하지만 `LiveSpanStreamService`의 writer는 4개 스레드와 100개 대기 작업으로 고정되어 있습니다. 거절된 작업은 연결 종료 경로로 갑니다.

연결 한 개가 항상 작업 한 개를 점유한다고 단순 계산할 수는 없습니다. 다만 설정만 늘려도 송신 능력이 함께 늘어나는 구조가 아니며, 느린 연결이 쌓일 때 거절 가능성이 있습니다. 기본 설정에서 반드시 장애가 난다는 판정은 아닙니다.

**개선 제안:** 허용할 연결 수와 송신 예산을 함께 산정하고, 지원하지 않는 조합은 기동 시 거부하거나 송신 구조를 개선합니다. 프록시와 네트워크 대역폭도 같이 측정합니다.

**완료 조건:** 기본·확장·과부하 조합에서 정상 클라이언트 지연, 느린 클라이언트 격리, 재연결 빈도, writer 거절 수를 측정합니다.

근거: [writer](../../moveseye-be-spring/src/main/java/com/dmove/moveseye/premium/apm/overview/live/spans/LiveSpanStreamService.java) 103~104행·504행, [연결 설정](../../moveseye-be-spring/src/main/java/com/dmove/moveseye/premium/apm/overview/live/spans/ApmLiveStreamProperties.java).

### R5. 알람 판정의 락과 DB 작업 안에 외부 호출이 있다

**중요도: 중간~높음 · 코드 확인**

`ApmStuckRequestMonitor`의 `synchronized(lock)` 안에서 Ledger를 호출하고, Ledger는 트랜잭션 안에서 Zabbix 준비·push를 수행합니다. 주기 평가기도 외부 push를 포함합니다.

**영향 추론:** Zabbix 응답이 느려지면 알람 갱신이 밀리고 DB 커넥션을 오래 쥘 수 있습니다. 메모리 감시기의 처리 간격도 흔들릴 수 있습니다.

**개선 제안:** DB에서 판정·전송 의도를 기록 → 락 밖에서 외부 전송 → 결과 기록으로 분리합니다. R2의 알람 단일 소유권과 함께 설계해야 합니다. I/O만 밖으로 빼면 중복 실행 위험을 키울 수 있습니다.

**완료 조건:** Zabbix 지연·실패를 주입해 감시 주기, DB 풀 점유, 중복 알람과 재전송 수를 확인합니다.

근거: [감시기](../../moveseye-be-spring/src/main/java/com/dmove/moveseye/premium/apm/alert/evaluate/ApmStuckRequestMonitor.java) 121~232행, 위 Ledger·평가기.

### R6. 일부 조회·보존 비용은 계속 누적될 수 있다

**중요도: 중간 · 코드 확인과 추가 실측 필요**

호스트 연결기는 이름별 반복 중 자산 조회를 호출합니다. 캐시 미스와 대상 증가 시 반복 조회 비용이 커질 수 있습니다. 또한 현재 보존 Job에서 걸림 요청 정리는 확인되지만 `apm_alert_event` 자체의 보존 단계는 확인되지 않았습니다.

**개선 제안:** 호스트 연결은 이름 집합 단위 조회를 검토하고 실제 SQL 계획으로 효과를 확인합니다. 알람 이력은 법적·운영 요구에 맞는 보존 정책을 정하고 종료된 이벤트부터 정리합니다. 열린 알람을 날짜만 보고 삭제하면 안 됩니다.

**완료 조건:** 대상 수 증가에 따른 쿼리 수·p95를 비교하고, 보존 시험에서 열린 알람과 필요한 조사 이력이 유지되는지 확인합니다.

근거: [호스트 연결기](../../moveseye-be-spring/src/main/java/com/dmove/moveseye/premium/apm/service/hostlink/ApmZabbixHostLinker.java) 99~171행, [보존 Job](../../moveseye-be-spring/src/main/java/com/dmove/moveseye/premium/apm/core/batch/retention/ApmRetentionJob.java).

## 5. APM 제품 관점의 기능 공백

### 깊은 원인 분석

현재 span은 “어느 작업 구간이 느린가”를 알려 줍니다. “어느 함수가 CPU를 소비하는가”, “DB가 어떤 실행 계획과 락 때문에 느린가”는 별도의 관측이 필요합니다.

**제안:** 일반적인 서비스 지연 조사까지가 목표라면 현재 범위를 먼저 안정화합니다. 코드 수준 진단까지 목표로 확장할 때 프로파일링, DB 진단 연결, 애플리케이션 로그 상관 검색을 각각 별도 과제로 둡니다. OTel 도입만으로 자동 제공되는 기능으로 홍보하지 않습니다.

### 지원 언어와 환경의 깊이 차이

Java 진행 중 요청 확장은 구체적인 검증 조합이 있습니다. 다른 언어에서 OTLP를 보낼 수 있어도 동일한 런타임 카드·진행 중 목록·비동기 연결을 보장하지 않습니다.

**제안:** 언어·버전·프레임워크별로 HTTP 지표, trace, 런타임, 진행 중 요청, 메시징, 수동 계측 요구를 표로 관리합니다. “지원”은 설치 가능·수신 가능·화면 검증을 나눠 표시합니다.

근거: [확장 README](../../12-%EC%98%A8%EB%B3%B4%EB%94%A9-%EA%B7%9C%EC%95%BD/solutions--OTel-%ED%99%95%EC%9E%A5-%EC%86%8C%EA%B0%9C.md), [기존 검증 현황](../../05-%EC%9E%91%EC%97%85-%EA%B0%80%EC%9D%B4%EB%93%9C/APM-%ED%95%B8%EB%93%9C%EB%B6%81/solutions--13-%EA%B2%80%EC%A6%9D-%ED%98%84%ED%99%A9%EA%B3%BC-%EB%82%A8%EC%9D%80-%EA%B2%83-%EB%B0%A9%EB%B2%95%EB%A1%A0-QA-%EC%88%98%EC%B9%98-%EB%AF%B8%EA%B2%80%EC%A6%9D-%EC%97%B4%EB%A6%B0-%EA%B2%B0%EC%A0%95-%EC%A0%95%EB%B3%B8-%EB%B6%88%EC%9D%BC%EC%B9%98-14.md).

### 장기 상세 조사와 아카이브

콜드 아카이브는 **이미 구현됐습니다.** 그러나 파일 보관과 화면 복원은 다릅니다. 기본 대상에 span 원본이 포함되는 것도 아닙니다. 원본을 선택 보관하더라도 검색·복원기는 별도입니다.

**제안:** 장기 상세가 제품 요구라면 복원할 데이터, 복원 시간 목표, 용량, 접근 권한, 파일 무결성, 복원 후 삭제 정책을 먼저 확정합니다. 30/90일 정책은 현재 확정된 제공 기간으로 안내하지 않습니다.

근거: [콜드 아카이브](../%EA%B8%B0%EB%8A%A5/solutions--APM-%EC%BD%9C%EB%93%9C-%EC%95%84%EC%B9%B4%EC%9D%B4%EB%B8%8C.md), [보존 정책 보류](../../03-%EA%B8%B0%ED%9A%8D-%EB%B0%B1%EB%A1%9C%EA%B7%B8/solutions--%EB%B3%B4%EB%A5%98-%EC%9E%91%EC%97%85-APM-%EB%B3%B4%EC%A1%B4-%EC%A0%95%EC%B1%85%EA%B3%BC-%EC%9E%A5%EA%B8%B0-%EC%83%81%EC%84%B8-%EC%A1%B0%ED%9A%8C.md).

### 다중 노드와 장애 복구

메트릭·trace의 DB 저장과 실시간 메모리 상태는 다른 복구 특성을 가집니다. DB가 공유되어도 실시간 링, 연결, 일부 예산이 자동으로 공유되지는 않습니다.

**제안:** 단일 BE 설치를 우선 지원한다면 제한을 명시하고 재시작 후 빈 창을 설명합니다. 다중 BE를 지원할 때 수신·조회 라우팅, 세션 회수, 예산 공유, 롤링 배포, 노드 장애를 하나의 시나리오로 검증합니다.

## 9. 문서 자체의 부족점과 이번 정리

첫 허브의 기준선은 8월인데 신규 기능은 10월까지 존재했습니다. APM 종합 안내서는 단계별 참고서로 풍부하지만 처음 읽는 사람에게 많은 계약·검수 회차를 동시에 보여 줍니다. 일부 코드 주석도 현재 구현을 “골격”으로 설명해 오해를 줄 수 있습니다.

이번에는 쉬운 설명과 검수 근거를 분리하고, 현재 코드로 다시 확인한 위험에만 현재 판정을 붙였습니다. 기존 문서를 삭제하거나 일괄 이동하지 않고 [읽기 안내](solutions--MovesEye-%EC%B5%9C%EA%B7%BC-%EC%9E%91%EC%97%85%EA%B3%BC-APM-%EC%9D%BD%EA%B8%B0-%EC%95%88%EB%82%B4.md)를 공통 입구로 연결합니다.

장기적으로는 기능 문서의 상태를 한 곳에서 갱신하고, 설계·QA·계약에는 그 상태 페이지를 연결해야 합니다. 동일한 “완료/보류” 문장을 여러 곳에서 수동 관리하면 다시 어긋납니다.
