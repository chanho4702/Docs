# MovesEye 관리자 가이드

> 이 문서는 **제품을 설정하고 운영하는 관리자**를 위한 것이다. 일반 사용자의 화면 사용법은 [사용자 가이드](solutions--%EC%82%AC%EC%9A%A9%EC%9E%90-%EA%B0%80%EC%9D%B4%EB%93%9C.md)를, 서버 설치·기동은 [설치·배포 가이드](../%EC%9A%B4%EC%98%81/solutions--%EC%84%A4%EC%B9%98-%EB%B0%B0%ED%8F%AC-%EA%B0%80%EC%9D%B4%EB%93%9C.md)를 본다.
>
> 상태 표기 규칙: **[구현]** 은 2026-08-11 소스에 존재하는 기능, **[진행]** 은 일부만 반영된 기능, **[계획]** 은 설계만 확정되고 코드가 없는 기능이다. 배포 환경에서의 동작은 별도로 확인해야 한다.

## 1. 관리자가 책임지는 범위

MovesEye는 여러 모니터링 데이터소스(현재 Zabbix, 향후 Prometheus·Datadog·Elasticsearch)를 통합하는 제품이며, 수집된 데이터를 **그대로 보여 주는 뷰어가 아니다.** 제품이 자체적으로 소유하는 것이 있고, 데이터소스가 원천인 것이 있다. 이 경계를 모르면 "고쳤는데 원복되는" 현상을 겪는다.

| 데이터 | 원천 | 관리자가 바꾸는 곳 |
|---|---|---|
| 호스트·아이템·트리거·템플릿 | **데이터소스**(Zabbix) | 소스 관리 메뉴(제품에서 원천에 씀) |
| 메트릭 값·이벤트 발생 | **데이터소스** | 바꿀 수 없음(수집 결과) |
| 자산 보강 필드·비용·감가상각 | **MovesEye DB** | 자산 관리 메뉴 |
| 네트워크 맵·지리 맵 클러스터 | **MovesEye DB** | 자산 관리 > 지도 |
| 호스트 좌표 | **Zabbix 인벤토리** | 지리 맵에서 편집하면 Zabbix에 기록됨 |
| 사용자·역할·기능 권한 | **MovesEye DB** | 사용자·권한 메뉴 |
| 기기 분류(device_type) | **호스트 태그가 진실**, 분류 메타는 DB | 설정 > 장비 분류 |
| 배치 주기 | **MovesEye DB** | 설정 > 스케줄러 |

원칙 하나만 기억하면 된다. **데이터소스가 원천인 값은 다음 동기화가 덮어쓴다.** 제품에서 영구히 유지하고 싶은 값은 MovesEye 소유 필드에 넣어야 한다.

### 1-1. 데이터소스 구성 **[진행]**

설정 > 데이터소스에서 연결된 소스와 상태를 확인하고, 소스별 관리 워크스페이스로 진입한다.

| 소스 | 관리 워크스페이스 | 상태 |
|---|---|---|
| **Zabbix** | 호스트 · 템플릿 · 아이템 · 트리거 | **[구현]** |
| Prometheus | 타깃 · 서비스 디스커버리 · 규칙 · 레이블 | [계획] |
| Elasticsearch | 인덱스 · 파이프라인 · 스트림 · 질의 | [계획] |
| Datadog | 통합 · 모니터 · 호스트 · 태그 | [계획] |

> **화면에 4개 소스가 보이는 것과 실제 연결 가능한 것은 다르다.** 현재 동작하는 어댑터는 Zabbix뿐이며 나머지는 화면 골격만 있다. 고객에게 안내할 때 이 점을 분명히 한다.

소스마다 할 수 있는 일이 다르므로, 제품은 각 소스가 선언한 **능력(capability)** 에 따라 메뉴를 조정한다. 예를 들어 메트릭만 제공하는 소스를 붙이면 대상 관리 메뉴는 나타나지 않는다. 특정 메뉴가 보이지 않는다면 고장이 아니라 **연결된 소스가 그 능력을 갖고 있지 않은 것**일 수 있다.

## 2. 최초 도입 순서

새로 설치한 뒤 이 순서대로 진행한다. 앞 단계를 건너뛰면 뒤 단계에서 대상이 비어 보인다.

### 2-1. 라이선스 등록 **[진행]**

설정 > 라이선스에서 발급받은 키를 등록한다. 라이선스가 없으면 기능이 제한된다(§7 참조).

### 2-2. 데이터소스 연결 확인

설정 > 연동 정보에서 데이터소스 접속 정보와 전용 계정을 확인한다(현재 Zabbix API URL·계정). 계정은 **제품 전용으로 분리**한다 — 사람이 같이 쓰는 계정을 넣으면 비밀번호가 바뀔 때 제품 전체가 멈추고, 감사 로그에서 누가 한 일인지 구분되지 않는다.

연결 확인 방법은 화면 어디든 호스트 목록이 뜨는지 보는 것이다. 전 화면이 동시에 비면 연동 실패, 특정 호스트만 비면 권한이나 아이템 문제다.

### 2-3. 자산 최초 동기화

자산 관리 > 목록에서 동기화를 실행한다. Zabbix 호스트가 자산으로 올라온다.

> ⚠️ **지리 맵을 쓸 계획이면 이 동기화를 반드시 먼저 한 번 돌린다.** 동기화 전에는 `linked_hostid`가 비어 있어 지리 맵의 호스트 후보가 0건으로 나온다. 기능 고장으로 오인하기 쉽다.

### 2-4. 장비 분류 정의

설정 > 장비 분류에서 조직이 쓰는 분류 체계를 만든다(서버/네트워크/스토리지 등). 분류는 **호스트 태그**로 호스트에 붙고, 이 테이블은 표시명·순서·메타만 갖는다. 그래서 분류를 지워도 호스트 데이터는 파괴되지 않는다 — 모르는 분류 코드는 "미분류"로 폴백한다.

### 2-5. 사용자와 권한

§3을 따라 역할을 먼저 만들고, 사용자를 만들면서 역할을 붙인다. 반대로 하면 사용자마다 권한을 개별 조정하게 되어 관리가 무너진다.

### 2-6. 스케줄러 활성화

설정 > 스케줄러에서 필요한 배치를 켜고 주기를 정한다(§5).

### 2-7. 리포트 보존 정책

설정 > 리포트 관리에서 자동 삭제 보존 기간을 정한다. 정하지 않으면 리포트가 무한 누적된다.

## 3. 사용자·역할·권한 관리

### 3-1. 두 층위의 권한

MovesEye의 권한은 **두 축이 곱해진다.** 하나만 설정하고 다른 쪽을 잊는 것이 가장 흔한 실수다.

| 축 | 무엇을 통제하나 | 설정 위치 |
|---|---|---|
| **기능 권한** | 어떤 메뉴·기능을 쓸 수 있나 | 역할(Role) |
| **데이터 범위** | 어떤 호스트 그룹의 데이터를 볼 수 있나 | 사용자 그룹 ↔ 호스트 그룹 권한 |

기능 권한만 주고 데이터 범위를 안 주면 **메뉴는 보이는데 목록이 텅 빈다.** 사용자는 "고장났다"고 신고한다. 반대로 데이터 범위만 주고 기능 권한을 안 주면 메뉴 자체가 안 보인다.

### 3-2. 기능 권한 키

역할 편집 화면에서 다루는 권한 키다. 각 키에 조회(view)·편집(edit)·삭제(delete)·다운로드(download) 단위를 준다.

| 영역 | 권한 키 |
|---|---|
| 모니터링 | `hostGroup`, `serverMonitoring`, `networkMonitoring` |
| 클라우드 인프라 | `hostGroupCI`, `serverMonitoringCI`, `networkMonitoringCI` |
| 이벤트·알람 | `byHost`, `byTemplate` |
| 리포트 | `generatingReport`, `reportHistory` |
| 알림 | `history`, `externalNotification`, `externalNotificationSettings` |
| 맵 | `integratedControlMap`, `mapList` |
| 자산 | `asset` |
| 설정 | `zabbixInfo`, `cloudInfraInfo`, `myPage` |
| 사용자 | `user`, `userGroups`, `userRoles`, `hostGroupUR` |
| 커스텀 대시보드 **[계획]** | `customDashboard`, `customDashboardSettings` |

> **표의 모든 키가 실제로 무언가를 막지는 않는다.** 체크박스별 실제 효과는 §3-6을 본다. 이 밖에 클라우드 인프라 `awsResources`, 애플리케이션 모니터링 `apm` 키가 있다. 위 표의 `asset` 키는 현재 역할 데이터에 없으며, 자산·비용 편집은 관리자만 할 수 있다(2026-09-17 소스 확인).

### 3-3. 역할 설계 권고안

처음부터 세밀하게 쪼개지 말고 3~4개로 시작한다. 실제 불편이 생긴 지점만 나중에 분리하는 편이 유지 가능하다.

| 역할 | 기능 권한 | 데이터 범위 |
|---|---|---|
| 시스템 관리자 | 전체 | 전체 호스트 그룹 |
| 운영자 | 모니터링·이벤트 조회 + acknowledge, 리포트 | 담당 호스트 그룹만 |
| 자산 담당자 | 자산·비용 편집, 모니터링 조회 | 전체 또는 담당 사업장 |
| 조회 전용 | 전 영역 view만 | 담당 호스트 그룹만 |

### 3-4. 계정 비활성화와 삭제

퇴사·전배는 **삭제가 아니라 비활성화**가 기본이다. 삭제하면 그 사용자가 남긴 감사 로그·자산 변경 이력의 행위자 추적이 끊긴다. 비활성화는 로그인만 막고 이력을 보존한다.

**[구현 — ZM-157, 배포 전]** 비활성화하거나 삭제하면 그 사용자가 로그인해 있던 **모든 기기에서 곧바로 로그아웃**되고, 연결된 앱(MCP)도 다음 요청부터 거부된다(§3-9·§3-10).

### 3-5. Zabbix 사용자 동기화 **[구현·기본 비활성]**

`user_sync` 배치는 Zabbix 사용자와 MovesEye 사용자를 맞춘다.

> 🔴 **`SYNC_ENABLED` 기본값이 `false`인 데는 이유가 있다.** 이 동기화는 Zabbix에 없는 로컬 사용자를 **제거할 수 있는 파괴적 작업**이다. MovesEye에서만 만든 계정을 쓰고 있다면 켜는 순간 사라진다. 켜기 전에 반드시 사용자 테이블을 백업하고, 로컬 전용 계정이 있는지 확인한다.

> **아래 §3-6 ~ §3-11은 ZM-157(2026-09-17) 변경이다.** 소스에 구현됐지만 아직 배포·실환경 확인 전이다. 설명의 근거는 [권한 강제와 세션 회수](../%EA%B8%B0%EB%8A%A5/solutions--%EA%B6%8C%ED%95%9C-%EA%B0%95%EC%A0%9C%EC%99%80-%EC%84%B8%EC%85%98-%ED%9A%8C%EC%88%98.md) 기능 문서다.

### 3-6. 역할 편집 체크박스가 실제로 막는 것 **[구현 — ZM-157, 배포 전]**

역할에서 끈 기능은 **메뉴만 숨겨지는 것이 아니다.** 서버가 모든 요청에서 역할을 다시 확인하므로 주소를 직접 입력해도, AI 어시스턴트나 연결된 앱(MCP)으로 요청해도 같은 권한이 적용된다. 역할을 바꾸면 서버 판정은 그 사용자의 다음 요청부터 바뀌며, 화면의 메뉴 표시는 새로고침하면 확실히 반영된다.

각 칸에는 보기·편집·삭제·다운로드 체크가 있지만, 현재 판정에 쓰는 것은 **보기와 편집**뿐이다.

| 역할 편집 칸 | 체크가 막는 것 | 상태 |
|---|---|---|
| 모니터링 > 호스트 그룹 | 보기: 호스트 그룹 화면(상세·추이·상위 호스트·리포트) | 현재 |
| 모니터링 > 서버 모니터링 · 네트워크 모니터링 | 보기: 목록과 호스트 상세. 편집: 호스트 상세의 **사용자 정의 차트** 추가·편집·삭제·배치 변경(§3-7) | 현재 |
| 이벤트 > 호스트별 | 보기: 이벤트/알림 메뉴, 문제 상세, 이벤트 통계 | 현재 |
| 이벤트 > 템플릿별 | 편집: 문제 확인(Acknowledge) 저장 | 현재 |
| 클라우드 인프라 > AWS 리소스 | 보기: 클라우드 인프라 화면, 비용의 Cloud 탭 | 현재 |
| 애플리케이션 모니터링 > APM | 보기: APM 조회 화면. 편집: 수집기·알람 규칙 등 관리 | 현재 |
| 클라우드 인프라의 나머지 3칸, 커스텀 대시보드, 리포트, 알림, 맵, 설정 | **사용처 없음** — 체크를 바꿔도 달라지는 것이 없다 | 현재 |
| 사용자 관리 4칸 | **관리자 전용** — 체크해도 일반 사용자에게 열리지 않는다 | 현재 |

"사용처 없음" 칸에 해당하는 화면은 대부분 관리자 전용이거나(리포트 관리·알림 관리·설정), 로그인한 사용자 모두에게 열려 있다(네트워크 맵·지리 맵 보기).

**관리자는 사용자 유형(userRole)이 관리자 계열인 계정이다.** 관리자는 역할 체크와 무관하게 모든 화면을 쓴다. Zabbix 쪽 역할(예: Zabbix Super admin)은 MovesEye 관리자 메뉴를 열지 않는다.

**Zabbix와 연결되지 않은 일반 계정**은 Zabbix 데이터를 보여 주는 화면에서 "권한이 없습니다" 안내를 받는다. 자산·비용·네트워크 맵처럼 MovesEye가 직접 관리하는 기능은 그대로 쓸 수 있다.

화면 흐름에서 권한이 없으면 사용자는 다음을 보게 된다.

- 메뉴와 버튼이 나타나지 않는다.
- 주소로 직접 들어가면 404(페이지 없음) 화면으로 이동한다.
- 데이터 조회가 거부되면 "이 작업을 수행할 권한이 없습니다." 안내가 뜬다.
- 권한 정보를 불러오지 못하면 "권한 정보를 불러오지 못했습니다" 화면과 [다시 시도] 버튼이 나온다.

### 3-7. 호스트 상세 차트 편집 권한 **[구현 — ZM-157, 배포 전]**

호스트 상세의 사용자 정의 차트는 **그 호스트를 보는 모든 사용자가 함께 쓰는 화면**이다. 한 사람이 편집하면 다른 사람의 화면도 바뀐다. 그래서 차트 추가·편집·삭제·배치 변경에는 **서버 모니터링 또는 네트워크 모니터링의 편집 권한**이 필요하다.

- 기본 역할에서 편집 권한은 관리자에게만 켜져 있다. 따라서 **업데이트 후 일반 사용자는 차트를 편집할 수 없다**(2026-09-17 결정).
- 일반 사용자에게 편집을 허용하려면 역할에서 서버 모니터링 또는 네트워크 모니터링의 **편집**을 체크한다.
- 편집 권한이 있어도 그 호스트를 볼 수 있는 데이터 범위(§3-1)가 있어야 한다.

### 3-8. 지리 맵 좌표 편집 **[구현 — ZM-157, 배포 전]**

지리 맵에서 호스트 좌표를 바꾸면 Zabbix 인벤토리에 기록된다(§1). 이 편집은 **관리자만** 할 수 있다. 일반 사용자는 지리 맵을 보고 클러스터를 둘러볼 수 있지만, 핀 이동과 좌표 입력은 비활성화된다.

### 3-9. 연결된 앱(MCP) 권한 **[구현 — ZM-157, 배포 전]**

연결된 앱은 사용자 관리에서 준 MCP 권한(사용 안 함·조회만·조회+변경)으로 통제한다. 변경은 **다음 요청부터 바로** 반영된다. MCP 연동을 켜는 방법, 프록시 설정, 사용자별 연결 절차는 [MCP 연결 가이드](solutions--MCP-%EC%97%B0%EA%B2%B0-%EA%B0%80%EC%9D%B4%EB%93%9C.md)에 있다.

| 관리자 조치 | 연결된 앱에서 일어나는 일 |
|---|---|
| MCP 권한을 없음으로 회수 | 모든 요청 거부 |
| 쓰기 → 읽기로 낮춤 | 조회는 계속되고 변경 요청만 거부 |
| 사용자 비활성화·삭제 | 인증이 끊어져 다시 연결해야 한다 |
| 사용자 유형(관리자↔일반) 변경 | 인증이 끊어져 다시 연결해야 한다 |

연결된 앱에서는 **호스트·아이템·트리거 삭제, 자산 제외, 템플릿 연결 해제 중 데이터까지 지우는 작업이 기본으로 막혀 있다.** 연결된 앱에는 MovesEye 화면의 확인 카드가 없기 때문이다. 허용이 꼭 필요하면 AI 서버 운영자가 설정을 바꾼다([MCP 연결 가이드 §13](solutions--MCP-%EC%97%B0%EA%B2%B0-%EA%B0%80%EC%9D%B4%EB%93%9C.md), [로컬·검증 Runbook §11](../%EC%9A%B4%EC%98%81/solutions--%EC%9A%B4%EC%98%81%EC%9E%90-%EB%9F%B0%EB%B6%81.md)). 화면 안의 AI 어시스턴트는 확인 카드 승인 후 삭제를 실행한다.

### 3-10. 비밀번호 변경과 로그인 세션 **[구현 — ZM-157, 배포 전]**

| 조치 | 결과 |
|---|---|
| 사용자가 비밀번호를 바꾸거나 재설정 | 그 사용자의 **다른 기기는 곧바로 로그아웃** |
| 관리자가 사용자 비밀번호를 바꿈 | 그 사용자의 모든 기기 로그아웃 |
| 사용자 비활성화·삭제 | 그 사용자의 모든 기기 로그아웃 |

관리자가 **마이 페이지에서 자기 비밀번호를 바꾸면 지금 쓰는 기기도 다시 로그인해야 할 수 있다**(소스 기준 판단, 실환경 미확인).

🔴 **업데이트 직후에는 모든 사용자가 한 번 다시 로그인한다.** 로그인 유지 방식이 바뀌어 이전에 받은 로그인 정보를 더 이상 받지 않기 때문이다. 사용 중인 사용자는 최대 30분 안에 로그인 화면으로 돌아간다. 업데이트 전에 사용자에게 공지한다.

### 3-11. 관리자 계정 이메일 등록 **[구현 — ZM-157, 배포 전]**

설치 시 만들어지는 기본 관리자 계정(`admin`)의 이메일이 **초기 설치값 그대로이면 업데이트 때 비워진다.** 이미 실제 주소로 바꾼 설치본은 영향이 없다.

이메일이 비어 있는 계정은 **비밀번호 찾기를 쓸 수 없다**("계정의 이메일 주소가 아직 등록되지 않았습니다" 안내). 업데이트 후 관리자 계정에 실제로 받을 수 있는 이메일을 등록한다(마이 페이지 또는 사용자 관리). 이메일을 바꿀 때는 이전에 받은 인증 코드가 모두 무효가 된다.

로그인 자체는 이메일과 무관하게 계속 된다. 관리자 비밀번호를 잊었는데 이메일도 없다면 다른 관리자가 사용자 관리에서 비밀번호를 초기화한다.

## 4. 대상 관리 (Zabbix)

제품에서 데이터소스의 객체를 직접 CRUD할 수 있다. **여기서 한 변경은 원천 시스템에 그대로 반영된다** — 연습용이 아니다.

이 영역은 소스마다 개념이 달라 공통화되지 않는다. 아래는 `ZABBIX_ADMIN` 능력을 가진 소스, 즉 Zabbix가 연결됐을 때 나타나는 메뉴다. 다른 소스가 붙으면 그 소스에 맞는 관리 화면이 따로 제공된다.

| 메뉴 | 할 수 있는 일 |
|---|---|
| 호스트 관리 | 호스트 등록·수정, 그룹·인터페이스·템플릿 연결, 분류/태그 지정, 일괄 지정 |
| 템플릿 관리 | 템플릿과 템플릿 그룹, 링크 관리 |
| 아이템 렌즈·관리 | 아이템 조회·생성·수정·상태 전환, 정의처와 전파 범위 확인 |
| 트리거 렌즈·관리 | 트리거 정의·심각도·상태 관리 |
| 사용자 관리 | Zabbix 사용자와 MovesEye 사용자 연결 |

### 4-1. 배열 전체 교체 함정

> 🔴 **Zabbix API의 `update`는 부분 수정이 아니다.** 태그와 템플릿 링크는 **보낸 배열로 통째 교체**된다. 태그 하나를 추가하려고 그 하나만 보내면 **나머지 태그가 전부 지워진다.**
>
> 제품 화면은 현재 값을 읽어 폼에 채운 뒤 전체를 다시 보내는 방식(round-trip)으로 이를 막고 있다. 그러므로 **화면에서 폼을 열었다면 보이는 값을 임의로 비우지 말 것.** 특히 다건 일괄 변경 전에는 대상 호스트의 현재 태그를 먼저 확인한다.

### 4-2. 렌즈(Lens) 화면의 용도

아이템·트리거 렌즈는 "이 정의가 **어디서 와서 어디까지 퍼졌는지**"를 보는 화면이다. 템플릿에서 상속된 것인지 호스트에 직접 만든 것인지, 몇 개 호스트에 전파됐는지를 확인한 뒤 수정한다. 템플릿 쪽을 고치면 연결된 호스트 전체가 함께 바뀐다.

기본 뷰는 디스커버리로 자동 생성된 항목을 숨긴다(노이즈 제거). 자동 생성분을 봐야 하면 뷰를 전환한다.

### 4-3. 트리거 수정 시 주의

트리거는 대상 호스트를 별도로 지정하지 않는다 — **expression 안의 `/host/key`가 곧 대상**이다. expression을 고치면 트리거가 다른 호스트를 보게 될 수 있다. 심각도 변경은 알람 흐름 전체에 영향을 주므로 운영 시간대를 피한다.

## 5. 스케줄러 관리 **[구현]**

설정 > 스케줄러에서 배치의 활성 여부·주기를 바꾸고, 수동 실행과 실행 이력을 볼 수 있다. cron이 코드에 박혀 있지 않고 DB 설정을 따르므로 **재기동 없이** 주기를 조정할 수 있다.

| job_key | 하는 일 | 성격 | 라이선스 필요 |
|---|---|---|---|
| `asset_sync` | Zabbix 호스트 → 자산 동기화 | 수집 | 예 |
| `event_sync` | 이벤트·문제 동기화 | 수집(짧은 주기) | 예 |
| `event_cleanup` | 오래된 이벤트 정리 | 정리 | 아니오 |
| `report_weekly` | 주간 리포트 생성 | 집계 | 예 |
| `report_monthly` | 월간 리포트 생성 | 집계 | 예 |
| `report_cleanup` | 보존 기간 지난 리포트 삭제 | 정리 | 아니오 |
| `user_sync` | Zabbix 사용자 동기화 | 수집 | 예 |

### 5-1. 주기 설계

- `event_sync`는 짧게(1분 수준) 돌아야 장애를 빨리 잡는다. 대신 무겁다.
- 리포트 집계는 오래 걸린다. **이벤트 동기화와 겹치는 시간대를 피한다.**
- 배치 스레드 풀은 `SCHEDULER_POOL_SIZE`(기본 4)다. 등록 배치가 7개이므로 전부 동시에 겹치면 대기가 생긴다. 풀이 1이면 무거운 집계 뒤에 이벤트 동기화가 줄줄이 밀린다.

### 5-2. 정리 배치는 왜 라이선스와 무관한가

`event_cleanup`·`report_cleanup`은 라이선스가 만료돼도 계속 돈다. 멈추면 **만료된 설치본의 디스크가 무한정 찬다.** 이 두 배치는 외부 수집을 하지 않고 자기 DB만 정리하므로 계속 도는 것이 안전하다.

### 5-3. 실행 이력 읽는 법

- 부분 실패는 예외가 아니라 요약으로 남는다: `ok=38 fail=2`. **성공으로 찍혔다고 전건 성공이 아니다** — 요약 문자열을 읽는다.
- 전건 실패는 실패로 기록되고, **다음 실행은 취소되지 않는다.** 원인을 고치면 다음 주기에 자연 복구된다.
- 실행이 밀리거나 멈춘 것 같으면 수동 실행을 연타하지 않는다. 이전 실행이 아직 도는 중일 수 있다.

## 6. 자산·비용 관리

### 6-1. 자산의 두 출처

- `source=zabbix` — Zabbix 호스트에서 유래. Zabbix 원천 필드는 동기화가 덮어쓴다.
- `source=custom` — MovesEye에서 직접 만든 자산. Zabbix에 없는 것(비품·회선 등)을 관리할 때 쓴다. `linked_hostid`로 Zabbix 호스트를 참조할 수 있다.

삭제는 물리 삭제가 아니라 `excluded` **soft delete**다. 동기화 대상에서 숨겨질 뿐 이력은 남는다.

### 6-2. 비용·감가상각 **[진행]**

취득가액·취득일을 입력하면 감가상각(정액법·정률법)을 계산한다. 한국 세무 기준(월할, 잔존가액 0)을 따른다. 기기 유형별 기본 내용연수를 두고 자산별로 예외를 줄 수 있다.

- 파라미터를 바꾸면 **현재 파라미터 기준으로 소급 재계산**된다. 과거 시점 스냅샷을 보존하지 않는다.
- CSV 일괄 업로드는 **비동기**다. 업로드 성공 응답은 "접수됨"이지 "처리 완료"가 아니다. 작업 상태를 따로 확인한다. 파일 상한은 10MB.
- 미입력 자산 큐를 활용해 빈 항목을 채운다.

## 7. 라이선스와 에디션 **[진행]**

### 7-1. 에디션 구성

| 에디션 | 포함 기능 |
|---|---|
| **STANDARD** | 기본 모니터링·자산·맵·리포트 |
| **PREMIUM** | STANDARD + GPU 모니터링, DB 모니터링, APM |

기능 판정은 `에디션 기본값 ∪ 개별 부여 기능`이다. STANDARD에 특정 기능만 추가 부여할 수 있다.

### 7-2. 등록과 갱신

설정 > 라이선스에서 키 문자열을 붙여넣거나 파일로 등록한다. 유효 기간은 **등록일부터** 계산된다(발급일이 아니다) — 발급받고 며칠 뒤 등록해도 손해가 없다. 영구 라이선스도 지원한다.

### 7-3. 만료되면 무엇이 멈추나

만료를 무 자르듯 차단하지 않는다. 모니터링 화면 전부가 죽으면 운영자가 장애 상황을 볼 수단을 잃기 때문에, **단계적으로** 좁힌다.

| 단계 | 기간 | 상태 |
|---|---|---|
| 정상 | 유효 기간 내 | 전 기능 |
| **EXPIRED** | 만료 후 약 30일 | **읽기 전용.** 실시간 조회는 유지, 쓰기 차단 |
| **ARCHIVED** | 그 이후 | DB에 쌓인 데이터만 조회. 외부 수집 중단 |

정리 배치는 어느 단계에서도 계속 돈다(§5-2).

> 관리자 조치: 만료 30일 전부터 갱신을 준비한다. EXPIRED 구간에 들어가면 설정 변경·자산 편집 같은 쓰기가 막히므로, 갱신 전에 진행 중인 편집 작업을 마무리한다.

## 8. APM 실시간 관제와 자바 확장 (선택 기능)

APM의 `실시간 관제` 메뉴(요청 관제·X-View)와 그 안의 진행 중 요청 카드·요청 걸림 알람은 **기본으로 꺼져 있다.** 켜려면 서버·수집기·앱 세 곳을 함께 바꿔야 한다. 하나라도 빠지면 조용히 안 되거나, 더 나쁘게는 마스킹이 빠진 데이터가 전송된다.

### 8-1. 실시간 관제 켜기 — 네 가지를 전부

| # | 어디서 | 무엇을 | 빠뜨리면 |
|---|---|---|---|
| ① | MovesEye 서버 환경변수 | `APM_LIVE_SPANS_ENABLED=true` 뒤 재기동 | 화면이 "실시간 수신이 꺼져 있습니다" 안내를 띄우고 수집기 로그에 거절이 쌓인다 |
| ② | 수집기 > 토큰·설정 > 설정 파일 다시 만들기 | **실시간 스팬 전송**을 켜고 새 yaml을 받아 교체 | 설정 파일에 실시간 전송 구간이 없어 아무것도 오지 않는다 |
| ③ | Collector 실행줄 | `--feature-gates=ottl.set.allowNil` (설치 가이드의 서비스 등록 명령에 이미 들어 있다) | 🔴 가장 위험한 누락 — 예외 메시지·스택트레이스 정리가 **오류 없이 무시**되어 개인정보가 그대로 전송될 수 있다 |
| ④ | 앱 실행 환경변수 | `OTEL_BSP_SCHEDULE_DELAY=1000` (+ `OTEL_BSP_MAX_QUEUE_SIZE=2048`) | 트래픽이 적은 서비스는 화면 도착이 5초 이상 늦어져 "실시간"이 아니게 된다 |

- 이미 설치된 Collector를 실시간용으로 바꿀 때는 ②의 새 yaml 교체와 ③의 실행줄 확인, 그리고 **서비스 재시작**까지 셋 다 한다. yaml만 바꾸거나 실행줄만 바꾸면 반쪽이 된다.
- 켠 뒤에는 수집기 > 상태 탭의 실시간 카드에서 규칙 실패·차단 수·전송 실패가 쌓이는지 본다. 값이 비어 있으면 0이 아니라 아직 관측이 없다는 뜻이다.
- 실시간 데이터는 서버 메모리에만 있어 15분(진행 중 요청은 90초)이 지나면 사라지고 서버를 재시작하면 빈 화면에서 다시 시작한다. 정상이다.
- 메모리 예산 `APM_LIVE_MAX_HEAP_MB`(기본 384)는 컨테이너 힙(`-Xmx`)이 768MiB 미만일 때만 줄인다. 예산을 넘는 설정이면 기동이 실패하고 메시지가 조정 방법을 알려 준다.

### 8-2. 진행 중 요청·요청 걸림 — 자바 확장 jar

요청 관제 탭의 진행 중 요청 카드(원판·요청 흐름·처리 중 목록)와 알람 규칙 **요청 걸림**은 **앱 JVM에 MovesEye 자바 확장을 붙인 서비스**에서만 값이 있다. 없는 서비스는 "확장 없음"으로 보인다 — 0건이 아니라 볼 수 없다는 뜻이다. 다른 언어(.NET·Node·Python·Go)는 아직 지원하지 않는다.

앱 실행줄(에이전트와 같은 자리, 배포 파일은 `C:\ProgramData\moveseye\otel\` 또는 `/opt/otel/`):

```text
-javaagent:<경로>/opentelemetry-javaagent.jar
-Dotel.javaagent.extensions=<경로>/moveseye-otel-extension-0.2.0.jar
-Dotel.instrumentation.http.server.emit-experimental-telemetry=true
```

확장 옵션(전부 선택, 시스템 프로퍼티):

| 옵션 | 기본 | 뜻 |
|---|---:|---|
| `moveseye.active-requests.exclude-paths` | `/apm/live/stream,/apm/live/spans/stream,/event/stream,/events/stream` | 🔴 SSE·long-polling처럼 **원래 오래 열리는 연결**의 경로 접두(쉼표 구분). 안 넣으면 그 연결이 5초 이상 빨간 동전으로 영원히 남고 요청 걸림 알람이 60초마다 장애로 기록한다. 앱에 그런 경로가 있으면 여기 추가한다 |
| `moveseye.active-requests.slow-threshold-millis` | 2000 | 끝난 요청을 "느림"으로 셀 기준. 수집기 설정의 느린 요청 임계와 같게 둔다 |
| `moveseye.active-requests.list.size` | 30 | 1초마다 보내는 가장 오래된 처리 중 요청 수(최대 100). 0이면 목록을 안 보낸다 |
| `moveseye.active-requests.max-active` | 10000 | 동시 추적 상한. 넘치는 요청은 세지 못하고 "불완전" 표시가 붙는다 |
| `moveseye.active-requests.tracking-ttl-millis` | 600000 | 이만큼(10분) 안 끝나면 추적을 포기한다(끝난 것으로 치지 않는다) |
| `moveseye.active-requests.metrics.enabled` | true | false면 확장이 아무것도 보내지 않는다 |

- **요청 걸림 임계**는 설정 ⚙ > 알람 규칙의 전역 `요청 걸림` 규칙(기본 60초)이다. 앞단 프록시(nginx·Apache·ALB)가 연결을 끊는 시간에 맞춘 값이니 프록시 타임아웃을 바꿨으면 같이 맞춘다. 서비스별 규칙으로 덮어쓸 수 있다.
- 장부(알람 규칙 > 요청 걸림 탭)는 90일 보관한다(설정 > 리포트 관리 > APM 탭). 스팬은 7일이라 오래된 행의 trace 링크는 열리지 않는다.
- 켠 뒤 확인 순서: 요청 관제 탭의 진행 중 요청 카드가 "확장 없음"에서 숫자로 바뀌는가 → 느린 요청 하나를 만들면 동전이 파랑·주황·빨강으로 옮겨 가고 목록에 "지금 하는 일"이 뜨는가 → 60초를 넘기면 요청 걸림 탭·발화 이력·Zabbix Problem에 각각 하나가 생기고 끝나면 닫히는가.

### 8-3. 동시 시청 상한

실시간 화면은 서버가 계산한 데이터를 연결마다 나눠 보낸다. 같은 화면 조건이면 한 번만 계산하므로 여러 명이 봐도 서버 메모리는 늘지 않고 **송신 대역폭**과 프록시(아파치)의 연결 수만 는다. 기본 상한은 활성 40명·대기 10명·계정당 탭 4개이고 환경변수 `APM_LIVE_STREAM_*`(설치·배포 가이드 §4-4)로 바꾼다.

- 상한에 닿은 사람 화면에는 "입장 대기 중" 안내가 뜨고 앞 연결이 빠지면 자동으로 시작한다. 고장이 아니다.
- 화면 위 "내 연결 n/4"가 2 이상이면 그 사람이 탭을 여럿 연 것이다. 숨긴 탭도 센다. 안 쓰는 탭을 닫거나 헤더의 **연결 끊기**를 누르면 자리가 바로 돌아온다.
- 지금 몇 명이 보는지는 `GET /apm/live/spans/stats`가 수만 돌려준다(계정 식별자 없음). 기동 로그에 적용된 상한이 한 줄 찍힌다.
- 숫자 하나만 올리지 않는다. 활성 연결을 올리면 아파치가 그 수만큼 장기 연결을 잡으므로 아파치 MPM 한도 안인지 먼저 본다. 계정당 연결은 활성 상한을 넘을 수 없다(기동 실패).

## 10. 관리자가 자주 오해하는 것

| 증상 | 실제 원인 |
|---|---|
| 메뉴는 보이는데 목록이 비었다 | 기능 권한은 있고 **호스트 그룹 데이터 범위가 없다**(§3-1) |
| 지리 맵에 호스트 후보가 0건 | 자산 최초 동기화 미실행(§2-3) |
| 태그를 하나 추가했더니 나머지가 사라졌다 | Zabbix `update`의 배열 전체 교체(§4-1) |
| 자산을 고쳤는데 원복됐다 | 데이터소스 원천 필드를 고쳤고 동기화가 덮어썼다(§1) |
| 특정 관리 메뉴가 안 보인다 | 연결된 소스가 그 능력(capability)을 갖고 있지 않다(§1-1) |
| 데이터소스 화면에 4개가 보이는데 연결이 안 된다 | 현재 동작하는 어댑터는 Zabbix뿐이다(§1-1) |
| 로컬 계정이 사라졌다 | `SYNC_ENABLED=true` 상태에서 `user_sync` 실행(§3-5) |
| 차트가 비었다 = 장애다 | **관측값 없음과 실제 0은 다르다.** 아이템 키와 수집 상태를 먼저 본다 |
| CSV 업로드 성공했는데 반영이 안 됐다 | 비동기 처리. 접수 ≠ 완료(§6-2) |
| 배치가 성공인데 데이터가 일부만 | 부분 실패는 성공으로 찍히고 요약에만 남는다(§5-3) |
| 역할에서 체크했는데 아무것도 안 바뀐다 | 그 칸은 현재 사용처가 없거나 관리자 전용이다(§3-6) |
| 일반 사용자가 차트 편집 버튼이 없다고 한다 | 서버·네트워크 모니터링 편집 권한이 필요하다(§3-7) |
| 업데이트 후 전원이 로그아웃됐다 | 로그인 유지 방식 변경으로 1회 재로그인이 필요하다(§3-10) |
| 관리자 비밀번호 찾기가 안 된다 | 관리자 계정에 이메일이 없다(§3-11) |
| APM 실시간 관제에 "입장 대기 중"이 뜬다 | 고장이 아니다. 동시 시청 상한에 닿았다(§8-3) |
