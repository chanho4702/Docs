## 1. A-2 — 열린 알람 1만 건 초과분 🔴 별도 티켓 권고

### 지금 상태
- `EventSyncService`는 보정(5분)·증분(15초) 모두 `alertPort.listActive(... withLimit(10_000))` **1콜**이다.
- 열린 알람이 1만 개를 넘는 설치본에서는 **상한 밖 알람이 사본에 들어가지 않는다** → 목록·알림 벨에서 안 보인다.
- **데이터 손실은 막아 뒀다**(A-1, `8fa5ec2`): 잘린 회차에서는 삭제·되짚기를 하지 않는다. 남는 증상은 "안 보인다"뿐이다.
- **운영 우회 가능**: 설정 > 알람 동기화 범위(그룹·최소 심각도·억제 제외·꺼진 규칙 제외)로 좁히면 상한 안으로 들어올 수 있다.

### 왜 ZM-159에서 안 했나
설계 v1([`../designs/devdesign_zm-159-ta2-problem-cursor.md`](../02-%EC%84%A4%EA%B3%84/ZM-159-T-A-A-2-%EC%97%B4%EB%A6%B0-%EC%95%8C%EB%9E%8C-1%EB%A7%8C-%EA%B1%B4-%EC%83%81%ED%95%9C-%EC%A0%9C%EA%B1%B0%28%EC%BB%A4%EC%84%9C-%EB%B6%84%ED%95%A0%29-%EC%84%A4%EA%B3%84-v1.md))까지 쓰고 코덱스 검토를 2회 받았으나 **치명 4건이 남았다**:

| # | 남은 문제 |
|---|---|
| ① | **재개(continuation) 계약이 없다** — 포트·실행기의 스캔은 항상 처음부터다. 불완전하게 끝난 회차를 다음 회차가 이어받을 방법이 없어, 앞부분만 반복하고 뒤쪽이 굶는다 |
| ② | **회차 식별자가 필요하다** — 표시자를 앱 시각으로 쓰면 회차가 겹칠 때 역행한다. DB가 발급하는 run id가 있어야 한다 |
| ③ | **첫 회차 후보 폭증** — 기존 미해소 사본이 많으면 `last_open_at`이 전부 NULL이라 첫 완전 회차의 되짚기 후보가 폭증한다 |
| ④ | **증분 쓰기 폭증** — 표시자만 갱신해도 매 15초 전 행을 쓰게 된다 |

### 착수하려면 필요한 것
- `event_sync_run`(논리 회차) 테이블 + **run id 표시자**
- 정렬에 맞는 **부분 인덱스** + 온라인 생성 전략(운영 중 DDL)
- 포트의 **opaque continuation**(재개 토큰) 계약
- 보강 호출(규칙·조치자·복구 시각) **공유 예산**
- 스캔 중 새로 생긴 알람(new-head) 처리 정책
- **feature flag 단계 배포**

## 2. 인터페이스 차트 "일부만 표시" 문구

- **지금**: 조회가 불완전하면 차트가 **그냥 빈다**. 로그에는 남지만 화면에는 아무 말이 없다.
- **문제**: 보는 사람이 ⓐ 정말 데이터가 없는 것 ⓑ 못 가져온 것 ⓒ 시간 요약으로 **대체된 것**(값의 뜻이 "그 시간의 최악 상태"로 바뀐다)을 구분할 수 없다.
- **필요**: 응답 DTO에 완전성·해상도 메타데이터 추가(BE) + 배너(FE). 문제 목록 이력 모드는 C7에서 같은 방식으로 이미 했다 —
  [`../designs/devdesign_zm-159-c7-truncation-notice.md`](../02-%EC%84%A4%EA%B3%84/ZM-159-C7-%EC%9E%98%EB%A6%BC-%ED%91%9C%EC%8B%9C-%28%EB%AC%B8%EC%A0%9C-%EB%AA%A9%EB%A1%9D-%EC%9D%B4%EB%A0%A5-%EB%AA%A8%EB%93%9C%29-%EC%84%A4%EA%B3%84-v1.md)의 계약을 그대로 따르면 된다.
- 근거: C5 5차 검수 R8(참고).

## 3. 인터페이스 차트 실물 확인

- ZM-159에서 **가장 많이 고친 화면인데 한 번도 못 봤다.** 개발용 자빅스(`dmove.co.kr`)에 oper/admin 인터페이스 아이템이 **0개**라 빈 응답만 확인됐다.
- 필요: 포트가 여러 개인 장비(스위치 등)가 등록된 환경.
- 확인할 것: ① 6시간 이하 → 원시 ② 6시간 초과 → 시간 요약(최악 상태 기준) ③ 포트 수가 많을 때 요약 전환 ④ 잘린 경우 빈 차트(틀린 그림이 아님).

## 4. C5 후속 3건 (비차단, 5차 검수 권장)

| # | 내용 | 왜 |
|---|---|---|
| 1 | **전달한 페이지가 실행기 목록에서 해제되는지** 고정하는 테스트 | 지금은 구현의 참조 해제 순서로만 보장된다. 2배 중복 구현으로 되돌아가도 테스트가 통과한다. 관측 지점(결과에 최대 버퍼량을 싣는 등)이 필요 |
| 2 | 아이템 **200개 희소 조회**의 실제 RPC 수 실측 | 정책 창을 3,000초로 맞춰 주 경로(1분 밀도)는 하루 72콜 → 29콜로 줄었지만, 희소 데이터에서는 약 20% 늘 수 있다 |
| 3 | **요청 단위 공통 RPC 예산** | `InterfaceService.MAX_RAW_CALLS(20)`는 **포트 호출 수**이지 자빅스 RPC 수가 아니다. app 모듈은 엔진 정책(창·묶음 크기)을 볼 수 없어(빌드가 의존을 차단) 정확히 셀 수 없다 — 포트 계약에 예산을 싣는 설계 변경이 필요 |

## 5. 응답 상한 64MiB → 16MiB

- 지금 `zabbix.call.max-response-bytes`는 **64MiB**다. 낮추려면 전체 조회 경로(자산 동기화의 `host.get`+`selectInventory` 등)를
  나눠 받게 고치고 **대규모 환경에서 힙을 실측**해야 한다(C4 검수 R3).
- 실측 환경이 없어 ZM-159 내내 보류했다.
