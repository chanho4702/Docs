## ZM-151 클라우드 스냅샷 적재량 정리

**문제** — AWS VPC 구성을 5분마다 17개 리전 전부에서 읽어 매번 새 행으로 저장했다. 29,665행 23MB를 뒤져 보니 서로 다른 구성은 18개뿐이었다. 같은 내용을 1,600번 넘게 복사해 둔 셈이다.

**한 것**
- VPC 스냅샷을 "구성이 바뀌었을 때만 새 행, 같으면 마지막 확인 시각만 갱신"하는 구간 저장으로 바꿨다(V64).
- 설정 화면에 "수집 리전 범위"를 두어 쓰는 리전만 고르게 했다. 비우면 전체.
- 인스턴스 스냅샷은 **일부러 손대지 않았다**. 회차마다 한 행 있는 것이 "가동 시간 × 단가" 비용 추정의 근거라, 중복 제거하면 비용이 조용히 0이 된다.

**좋아진 것** — VPC 행 증가가 하루 수천 행에서 "바뀔 때만"으로 줄었다. 리전을 좁히면 AWS 호출도 그만큼 준다.

**트레이드오프**
- 구간 저장은 "그 시각에 정확히 무엇이 있었나"를 행 하나로 못 본다. 구간의 시작·끝 시각으로 추론해야 한다.
- 옛 행 5만여 개는 보존 정리 배치가 지울 때까지 남아 있다.
- 롤백 이미지(옛 코드)가 같은 DB에 INSERT해도 깨지지 않게 새 열을 NULL 허용으로 뒀다. 그래서 코드가 두 가지 행 모양을 다 읽어야 한다.

## ZM-152 APM 화면 자기설명

**문제** — 지표 칸이 비면 `—`만 보였다. 요청이 없던 건지, 에이전트가 안 보낸 건지, 보존 기간이 지난 건지, 수집기가 버린 건지 사용자는 알 길이 없었다. 이 네 가지는 조치가 전부 다르다.

**한 것**
- FE 선행(09-21): 빈 값 이유 부품 하나를 만들어 화면 9곳에 붙이고, 보존 안내 배지·배너와 지표 한 줄 뜻을 붙였다. 다만 FE가 추정으로 판정했다.
- BE(10월 병합분 09-28): 서버가 사실을 내려주도록 8가지를 추가했다. 런타임 슬롯이 왜 없는지(허용목록 밖 vs 안 옴), 액티브 요청을 한 번이라도 보냈는지, 실제 보존 일수, 보존 경계 시각, 서비스별 폐기 건수, 요청 0건과 수신 없음 구분, SLO 미측정 사유, 인스턴스 지표 가능 여부.
- FE 연동(09-28): 서버값이 있으면 그것을, 없으면(구 BE) 종전 추정을 쓴다.

**좋아진 것** — "에이전트 옵션 필요"와 "요청 없음"처럼 조치가 다른 경우를 화면이 바로 가른다. 운영에서 보존 일수를 바꿔도 안내가 따라간다. 보존 배치의 0 이하 설정값이 응답과 삭제 범위를 다르게 만들던 결함도 이때 잡혔다.

**트레이드오프**
- 서비스별 폐기 건수는 **메모리 카운터**다. 재기동하면 0부터, 서버 한 대 안에서만, 메트릭 폐기만 센다. DB에 쌓지 않은 대가로 가볍다.
- 보존 안내는 서버 경계에 5분 여유를 둔다. 프리셋 정렬 오차(초 단위)로 매번 경고가 뜨는 것을 막는 대신 5분 미만 결손은 안내하지 않는다.
- 판정 규칙이 FE에도 폴백으로 남아 있어 "서버값 우선 → 없으면 계산"의 두 경로를 유지해야 한다.

## ZM-153 클라우드 구성 수집 주기 분리

**문제** — VPC 같은 구성 정보는 거의 안 바뀌는데 인스턴스 상태와 같은 5분 주기로 전 리전을 조회했다. 시간당 72콜 중 상당수가 헛수고였다.

**한 것** — 구성 정보만 별도 주기(기본 30분, 화면에서 0~24시간)로 돌린다. 배치는 하나 그대로 두고 "이번 회차에 구성도 볼 차례인가"만 판정한다(마지막 구성 수집 시각 + 1분 여유).

**좋아진 것** — 시간당 AWS 호출 72 → 32. dev 실측에서 인스턴스는 5분마다 7회, 구성은 30분 간격 2회만 수집됐다.

**트레이드오프**
- 새로 열린 포트 같은 **보안 노출을 최대 30분 늦게 안다**(전에는 5분). 그래서 1시간이 아니라 30분을 기본으로 골랐다.
- 스케줄러 옵션 저장이 값을 검증하지 않아서 "읽을 때 0~1440으로 자른다". 틀린 값이 DB에 남을 수 있다.
- 성공 회차는 이력에 안 남아 "이번엔 구성을 건너뛰었다"를 DB에서 못 본다. 스냅샷 행의 시각으로만 안다.

## ZM-154 APM 데이터 기간 지정 내보내기

**문제** — 감사·보고용으로 APM 데이터를 파일로 꺼낼 길이 없었다.

**한 것**
- v1(09-22): RED 시계열·엔드포인트·예외 그룹 3종을 CSV/JSONL(gzip 선택)로. **계획 → 다운로드 2단계**: 먼저 행 수·해상도·보존 승격을 보여 주고(상한 넘으면 거절), 그다음 받는다. 스트리밍 중 실패는 파일 끝 표지로 알린다.
- 후속(09-28): 엔드포인트 필터(검색어·메서드)를 화면 표와 같은 규칙으로 파일에 반영. **계획 고정 토큰**(HMAC 서명, 30분)으로 계획과 다운로드 사이에 보존 경계를 넘어도 해상도가 바뀌지 않게. 보존 결손 헤더·CSV 표지. 취소하면 요청이 실제로 끊기게(공통 인터셉터 수정). 개요 화면에서 전체 서비스 내보내기.

**좋아진 것** — "받았는데 비었다/다르다"가 사라진다. 계획에서 본 것과 같은 파일이 온다. 필터 건 표를 그대로 파일로 가져간다.

**트레이드오프**
- 토큰은 창 끝과 해상도만 고정한다. 데이터 자체는 다운로드 시점 기준이라 그 사이 보존 삭제가 있으면 비는 구간이 생길 수 있고, 그걸 헤더·표지로 알린다.
- 토큰에 계정을 넣지 않았다. 권한은 매번 다시 판정하니 남의 토큰으로 얻는 건 "그때 그 조건의 창·해상도"뿐이다. 대신 링크 공유가 된다.
- 공통 axios 인터셉터를 건드렸다. 호출부 신호를 이어 붙이는 로직이라 앱 전체에 걸치고, 그만큼 테스트(실제 인스턴스+가짜 전송 계층)를 늘렸다.
- CSV는 엑셀 수식 주입 방어로 `=`로 시작하는 칸 앞에 `'`를 붙인다. 원본 그대로가 필요하면 JSONL.

## ZM-155 메트릭 허용목록 확장 (설계만)

**문제** — 수집기가 받아 주는 메트릭 이름이 코드에 박혀 있어 고객이 커스텀 지표를 보낼 수 없다.

**상태** — 설계서(472줄)만 있다. 착수 전 결정 4개가 남아 있다: 공통 감사 로그를 먼저 만들지, 커스텀 지표 상한 기본값(서비스당 200이면 최악 하루 약 5.9GB), 그 밖 2건. ZM-156에서 감사 로그는 "일단 로그 기반"으로 정했으므로 같은 답을 쓰면 하나는 닫힌다.

## ZM-156 APM 콜드 아카이브

**문제** — APM 보존 배치는 기한이 지나면 파티션을 통째로 지우고 어디에도 남기지 않는다. 트레이스는 7일, 5분 지표는 30일, 모든 지표는 400일 뒤 영영 사라진다.

**결정(10-01, 대화로 확정)** — 보관 의무 고객은 아직 없다는 전제로(A안) 가볍고 오래 가는 것만 기본 대상(SLO 일 스냅샷·1시간 지표·트레이스 요약), 1분 지표·스팬은 옵트인. 아카이브가 7일 연속 실패하면 기록을 남기고 지우되 첫날부터 알람. 자빅스 아카이브와 공유할 공통 기반을 이번에 같이 만들고(공용 폴더), 파일은 데이터 종류별로 지워지기 직전에 하나씩.

**한 것**
- **DROP 게이트**: 보존 배치가 지우기 전에 "그 날짜 파일이 원장에 성공으로 기록돼 있고 실물이 있는가"를 확인한다. 없으면 지우지 않고 보류한다. 아카이브가 꺼져 있으면(기본) 보존 배치는 예전 코드 그대로 돈다. 다른 코드가 게이트를 건너뛰고 지우지 못하게 아키텍처 테스트로 막았다.
- **공통 기반**: 원장 테이블, ZIP 작성기(임시 파일 → SHA-256 재읽기 → 원자적 게시), 경로 정책(설치 때 정한 허용 루트 아래만, 심볼릭 링크 거절), 파일 목록·삭제·무결성 검사 화면.
- **배치**: 매일 00:50, 지워지기 2일 전부터 시도. 25분 예산 안에서 돌고 넘기면 다음 날로 이월.
- **화면**: 관리 콘솔 > 운영 > 데이터 아카이브. 보류가 생기면 APM 화면 상단에 배너. 알람 규칙 `ARCHIVE_HOLD`는 켜고 끄기만.
- 코덱스가 5번 왕복하며 잡은 것: 설정 오류 시 게이트가 열리는 경로, 관리자 삭제와 DROP의 경쟁, 다중 실행 시 임시 파일 충돌·덮어쓰기, 봉인 중 시간 예산 미검사, 원장 경로 미검증, 설정 저장 lost update, 보호 규칙 우회. 전부 고쳤다.

**좋아진 것** — "지워졌는데 복구할 수 없다"가 "지우기 전에 파일이 있고, 없으면 안 지운다"로 바뀐다. 켜기 전까지는 아무것도 달라지지 않는다.

**트레이드오프**
- **보류가 쌓이면 DB가 큰다.** 1분 지표는 하루 약 9.6GB(추정). 그래서 7일 상한을 기본으로 두고 첫날부터 알람. 무기한 보류(0)는 보관 의무 고객용이며 디스크를 스스로 지켜야 한다.
- **배포 전제**: 컨테이너에 아카이브 경로를 볼륨으로 마운트해야 한다. 안 하면 배포마다 파일이 사라진다. 파이프라인과 설치 가이드에 넣었지만 실제 서버 작업은 사람 몫이다.
- 복원(restore) 기능은 없다. "되살릴 수 있게 쓴다"(사전 동봉, CSV 수식 방어 끔)까지만.
- 잠금을 두 겹(설정·날짜) 걸어 안전을 샀다. 날짜당 최대 30초 대기, 못 얻으면 지우지 않고 넘긴다. 아카이브가 느리면 보존 정리도 그만큼 늦는다.
- 1분·스팬 하루치 내보내기 소요·용량은 **실측하지 않았다**. 켜 보고 재야 한다.
- 로컬/NFS 경로만 받는다. S3 같은 원격 저장소는 없다(NAS 마운트로 우회).

## 공통으로 감수한 것

- 전부 **런타임 실측이 부분적**이다. 151·153은 dev DB로 확인했고, 154 v1은 curl 실측, 152·154 후속·156은 BE 재기동 전이라 코드·테스트·코덱스 검수까지만이다.
- 코덱스 검수 왕복(이슈당 2~5회)이 시간을 많이 썼지만, 데이터 손실급 결함을 10건 넘게 잡았다. 특히 156에서는 사람이 놓치기 쉬운 경쟁 조건이 대부분이었다.
- master에서 원래 깨져 있던 테스트 2종(`LicenseArchitectureTest` A5-c, `apmHelpContent` 3건)과 스케줄러 시각이 서버 현지 시각에 `Z`만 붙는 결함은 이번 범위 밖으로 남겼다.
