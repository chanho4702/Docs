## 0. 한 줄

제니퍼·와탭의 "지금 처리 중인 요청"을 만들려면 **요청이 시작될 때** 알려 주는 신호가 필요하고,
그 신호를 만들 수 있는 자리는 **고객 앱 JVM 안**뿐이다. 이 문서는 그 신호를 어떻게 얻고,
무엇을 대가로 치르며, 어디까지 하지 않을 것인지를 정한다.

🔴 **확장 대상은 수집기가 아니다.** 수집기(otelcol)를 고쳐도 풀리지 않는다 — 진행 중인 요청의
기록은 수집기에 **도착하지 않기** 때문이다. 손대는 것은 `opentelemetry-javaagent.jar` 쪽이다.

## 1. 왜 지금 방식으로는 안 되는가

OpenTelemetry 스팬은 `end()` 시점에 배치 큐로 들어간다. 그래서 exporter가 보는 것은 **끝난
요청뿐**이다. 우리가 지금 셀 수 있는 것도 완료 처리량 하나다.

지금까지 시도한 우회 셋과 그 한계:

| 우회 | 무엇을 주나 | 🔴 왜 부족한가 |
|---|---|---|
| `http.server.active_requests` 메트릭 | 동시 처리 중인 **개수** | 개수 하나뿐이라 **경과 구간별로 쌓을 수 없다**. 해상도도 10~60초라 1초 화면과 리듬이 다르다 |
| 완료 스팬으로 과거 동시성 역산 | "T 시점에 몇 건이 떠 있었나" | 🔴 오래 걸리는 요청일수록 늦게 보이므로 **"지금"을 말할 수 없다**. 현재 액티브로 쓰면 거짓이다 |
| 완료 요청 지연 구간 차트(2026-09-17 구현) | 끝난 요청의 시간대별 분포 | 모양은 비슷하지만 **진행 중이 아니다**. 지금 이것으로 버티고 있다 |

## 2. 무엇을 만드나

### 2.1 신호 — 🔴 `SpanProcessor`가 **아니다**

⚠️ **v1은 `SpanProcessor.onStart`를 쓰려 했고 그건 틀렸다**(astra 검수 §6-4).

**왜 안 되나 — 숫자가 거짓이 된다.** 샘플러가 버린(`DROP`) 스팬은 `onStart`가 **아예 불리지
않는다**. APM은 비용 때문에 일부만 기록하므로, 실제로 50건이 떠 있어도 화면은 5건을 말한다.
원격 부모가 비샘플이면 통째로 빠진다. 🔴 **관측 없음을 0으로 그리는 것보다 나쁘다** —
0이 아니라 **그럴듯하게 틀린 수**가 나오기 때문이다.

**대신 쓸 것**: `InstrumenterCustomizerProvider` → `OperationMetrics` → `OperationListener`.
대상 버전(2.31.1)의 `Instrumenter`는 스팬 기록 여부와 무관하게 이 리스너를 부르므로,
**실제로 시작된 계측 operation**을 잡는다. `HTTP_SERVER` 유형만 고를 수도 있다.

🔴 **대가**: 이 확장 지점은 `incubator`에 있고 소스가 **"불안정 API이며 언제든 바뀔 수 있음"**을
명시한다. 에이전트를 올릴 때마다 깨질 수 있다는 뜻이다 — §4.3 호환 정책이 그래서 더 중요하다.

⚠️ **아직 모르는 것**: Servlet·WebFlux·Netty 각 조합에서 이것이 **요청당 정확히 한 번**
시작·종료되는지. 비동기 dispatch·예외·취소·스트리밍에서 확인해야 한다. **PoC의 1번 목표다.**

우리가 여기서 하는 일은 **최소한**이어야 한다(§4 위험).

- SERVER 스팬만 본다(`SpanKind.SERVER`). 나머지는 즉시 반환.
- 프로세스 안 맵에 `{traceId, spanId, startNanos, route, method}`를 넣는다.
- `onEnd`에서 지운다.
- **주기적으로(1초)** 그 맵의 스냅샷을 요약해 내보낸다.

### 2.2 무엇을 내보내나 — 🔴 요청 목록이 아니라 **요약**부터

두 단계로 나눈다. 1단계만으로도 화면의 핵심(경과 구간별 스택)이 선다.

**1단계 — 경과 구간 히스토그램 (권장 선출시)**
매초 한 번, 현재 떠 있는 요청을 경과 시간대로 센 벡터 하나.
```
{ ts, serviceInstance, buckets: [n(<100ms), n(<500ms), n(<1s), n(<5s), n(5s+)] }
```
- 🔴 구간 경계는 **완료 요청 지연 구간 차트와 같은 값**을 쓴다. 두 화면이 다른 경계를 쓰면
  "완료는 1초 구간인데 진행 중은 왜 다른 칸이냐"가 된다.
- 크기가 요청 수와 **무관**하다(항상 5칸). 이것이 1단계를 먼저 하는 이유다.

**2단계 — 진행 중 요청 목록 (후속)**
개별 요청 N건(`traceId`·`spanId`·`route`·경과). 상한이 필요하고 PII 위험이 커진다(§4).

### 2.3 어떻게 내보내나 — 🔴 새 프로토콜을 만들지 않는다

**OTel 메트릭으로 내보낸다.** 확장이 자기 `Meter`로 게이지/히스토그램을 올리면 기존 파이프라인
(에이전트 → 수집기 → 우리 BE)을 **그대로 탄다**.

- 새 포트·새 엔드포인트·새 인증이 **없다**.
- 수집기 설정도 그대로다(메트릭은 이미 흐른다).
- BE는 메트릭 이름 하나를 더 읽으면 된다.

⚠️ 대안(확장이 직접 우리 BE로 HTTP)은 **채택하지 않는다**: 고객 방화벽·인증·재시도·큐를
우리가 다시 만들게 되고, 그 코드가 고객 JVM 안에서 돈다.

🔴 **v1의 "1초 칸을 여러 개 실어 보낸다"는 안 된다**(astra 검수 §6-1). 메트릭은 이력을 나르는
물건이 아니다 — 게이지는 마지막 값만 남고, 히스토그램에 매초 기록하면 export 구간이 뭉개지며
**오래 사는 요청이 여러 번 세어진다**.

**대신 "지금 이 순간의 분포"를 게이지로 보낸다.** 고정된 `age_bucket` 5종을 속성으로 둔
게이지 하나다. 🔴 `timestamp`·`traceId`·요청 ID를 속성에 넣어 이력을 흉내 내지 **않는다**
(카디널리티가 터지고 그건 메트릭의 용법이 아니다).

그래서 화면이 말할 수 있는 것은 **"마지막 관측 시점의 분포"**이지 1초 흐름이 아니다.
§3 문구가 그렇게 바뀐다.

| 선택 | 판정 |
|---|---|
| 기존 export 주기(기본 60초) 유지 | 가능. 화면이 "마지막 관측 N초 전"을 적는다 |
| 공유 reader 주기를 짧게 | 가능하나 **다른 메트릭도 함께 짧아진다** — 그 비용을 재고 결정 |
| 확장 전용 reader | 후보. 초기화·종료·exporter 소유권을 따로 설계해야 한다 |

⚠️ export 주기를 1초로 줄여도 **화면까지 1초가 보장되지 않는다**. 수집기 batch와 재시도가 더 붙는다.

✅ **Meter 획득은 공식 경로가 있다**(astra 확인). `AgentListener.afterAgent(AutoConfiguredOpenTelemetrySdk)`
에서 에이전트 SDK를 받아 만든다 — **별도 SDK를 만들지 않는다**.
🔴 SDK 구성 중에 `GlobalOpenTelemetry.get()`을 부르면 no-op 전역이 박힌다. 부르지 말 것.

## 3. 화면

요청 관제 탭(`?tab=active`)에 카드를 하나 더 얹는다. **완료 요청 지연 구간 차트 바로 위**다.

- 제목은 "진행 중 요청"으로 완료 쪽과 **분명히 가른다**.
- 🔴 **"실시간"이라고 쓰지 않는다.** 메트릭으로 오므로 화면이 보는 것은 **마지막 관측 시점의
  분포**다(§2.3). "N초 전 기준"을 값 옆에 상시 적는다.
- 🔴 **완료 건수와 순간 동시 건수를 같은 축에 섞지 않는다.** 모집단이 다르다 — 완료는 구간 동안
  끝난 수이고 이쪽은 한 순간에 떠 있던 수다. 시간축을 줄일 때 **스냅샷을 단순 합산하면 안 된다**.
- 1초 스냅샷은 그 사이 시작하고 끝난 **짧은 요청을 놓친다**. 이것도 적는다.
- 보강할 값: 인스턴스별 보기 · 총 진행 건수 · **가장 오래된 경과 시간** · 마지막 관측 시각 ·
  관측 완전성(상한에 걸렸는지).
- 🔴 확장이 없는 서비스는 "0건"이 아니라 **"이 서비스에는 확장이 없습니다"**로 적는다.
  자바가 아닌 서비스도 마찬가지다. 관측 없음을 0으로 그리지 않는다는 이 절의 규칙 그대로다.
- 🔴 완료 차트와 **같은 색·같은 구간**을 쓰되, 진행 중 쪽은 테두리만 있는 막대로 갈라 보이게 한다.

## 4. 🔴 대가 — 여기가 이 설계의 본체다

### 4.1 고객 JVM 안에서 우리 코드가 돈다
지금까지 우리 코드는 서버 쪽에만 있었다. 확장을 넣는 순간 **고객 애플리케이션 장애 조사에
우리 jar가 등장**한다. 느려지거나 죽으면 "혹시 너희 것 때문 아니냐"를 따져야 하는 관계다.

🔴 **두 종류의 비용을 가른다.** 사용자 결정(2026-09-21)으로 **우리 인프라 비용은 설계 축에서
뺀다**(나중에 분리·증설로 해결). 하지만 **고객 앱 프로세스 안의 부담은 우리 인프라와 무관**하다 —
여기 제약은 그대로다.

**규모가 요청 수가 아니라 `동시 진행 건수 × 수명`에 좌우된다**(astra 검수 §6-2).
5,000 RPS·평균 100ms면 약 500개지만, 장애로 평균 5초가 되면 약 **25,000개**다.
🔴 **하필 이 기능이 필요한 순간이 그때다.** 감시하려고 넣은 것이 장애를 키우면 안 된다.

코드에 거는 제약:
- 리스너에서 하는 일은 **엔트리 하나 등록**. IO·로깅·정규식·전역 잠금 금지.
  ⚠️ v1의 "잠금 금지"는 구현 불가능한 요구였다 — `ConcurrentHashMap`도 변경 연산에 잠금이 있다.
  **"전역 잠금·대기·IO 금지 + 측정 가능한 지연 예산"**으로 다시 쓴다.
- 1단계에는 `route`·`method`가 **필요 없다**. 처음부터 담지 않는다(메모리·PII 둘 다 준다).
- 🔴 상한은 **동시 삽입에도 지켜져야 한다**. `size() < limit` 확인 후 put은 부족하다.
- 🔴 종료·만료·중복 호출이 겹쳐도 슬롯을 **한 번만** 반환한다.
- 매칭은 `(traceId, spanId)`나 요청별 토큰으로. 🔴 **스레드 ID 기반 금지**(비동기에서 어긋난다).
- 🔴 어떤 예외도 **밖으로 던지지 않는다**. 확장이 죽어도 고객 앱은 멀쩡해야 한다.
- 진단값을 따로 센다: `droppedStarts`·`expiredTracking`·집계 실패.
  🔴 **누락 건수를 현재 활성 건수에 더해 보정하지 않는다** — 그중 무엇이 이미 끝났는지 모른다.
- 우리 코드의 CPU·메모리 몫을 **측정해서 문서에 적는다**(추정치 금지). PoC 2번 목표.

### 4.2 언어마다 따로 만들어야 한다 — 🔴 "자바 전용"이 아니다

⚠️ **이 절의 초안은 "자바 전용이라 다른 스택은 영영 빈다"고 적었는데 사실이 아니다**(2026-09-21
사용자 지적으로 정정). 요청 시작을 잡는 지점(`SpanProcessor`의 시작 훅)은 OTel **명세에 모든
언어용으로 정의**돼 있다. 갈리는 것은 **코드 수정 없이 붙일 수 있느냐**다.

| 언어 | 코드 수정 없이 붙나 | 비고 |
|---|---|---|
| 자바 | 된다 | 에이전트 확장 jar를 실행 옵션에 추가 |
| .NET | 된다 | 자동 계측에 플러그인 지점이 있다 |
| Node·Python | 대체로 된다 | 시작 모듈에 등록 |
| **Go** | 🔴 **안 된다** | 컴파일 시점 계측이라 **고객 코드를 고쳐야 한다** |

그래서 정확한 서술은 **"언어마다 포팅이 필요하고 Go만 성격이 다르다"**이다.

**자바부터 하는 이유** — 지금 감시 대상이 자바이고, 확장 방식이 가장 안정적으로 문서화돼 있다.
자바로 값어치가 확인되면 다음 언어는 같은 설계의 포팅이 된다(새 설계가 아니다).

🔴 **그래도 화면은 정직해야 한다.** 확장이 없는 서비스에 "0건"을 그리지 않고 "이 서비스에는
확장이 없습니다"라고 적는다(§3). 그 문구가 **"영영 안 된다"로 읽히지 않게** 쓴다 — 아직 포팅을
안 한 것과 원리상 불가능한 것은 다르다.

### 4.2.5 추적 만료는 "완료"가 아니다 `[astra 검수 §6-3]`

종료 콜백이 안 오는 항목이 상한을 채우면 **새 요청을 계속 놓친다**. 그렇다고 오래된 항목을
TTL로 지우면 🔴 **정작 멈춰 있는 가장 중요한 요청이 화면에서 사라진다** — 이 기능을 만든 이유가
그 요청인데 말이다.

그래서 셋을 **구분해서 표시**한다.
| 사유 | 뜻 |
|---|---|
| 종료 콜백 관측 | 진짜로 끝났다 |
| TTL·상한에 의한 제거 | **종료를 확인하지 못했다 / 추적을 포기했다** |
| 프로세스 재시작 | 그 인스턴스의 관측이 끊겼다(새 epoch) |

TTL을 넣는다면 "완료 처리"가 아니라 **추적 보장 시간의 상한**으로 정의한다. 제거가 생긴 뒤의
분포는 **불완전하다고 화면에 적고**, 언제 완전성이 회복되는지도 정한다.

### 4.3 버전 호환
에이전트 2.31.1 기준으로 만들고, 고객이 에이전트를 올리면 확장이 안 붙을 수 있다.
🔴 **호환 범위를 명시하고, 안 붙으면 조용히 실패하지 말고 로그 한 줄을 남긴다.**

### 4.4 PII
2단계(목록)에 `route`·`traceId`가 실린다. 🔴 URL 경로에 고객 데이터가 들어가는 서비스가 있다 —
지금 수집기에서 하는 마스킹이 **확장 경로에는 없다**. 2단계를 하려면 마스킹을 확장 쪽에도
넣거나, 수집기를 통과하도록 만들어야 한다(§2.3대로 메트릭으로 보내면 자동으로 통과한다).

### 4.5 배포
고객이 jar를 하나 더 받아 `-Dotel.javaagent.extensions=`에 붙여야 한다. 설치 가이드가 늘고,
**끄는 방법**도 같이 줘야 한다(문제가 생겼을 때 되돌릴 길).

## 5. 하지 않는 것

- 메서드 단위 프로파일링. OTel profiling 시그널이 실험 단계다(기존 판단 그대로).
- 확장이 우리 BE로 직접 통신하는 것(§2.3).
- 자바 외 언어 **이번 범위에서는** 하지 않는다. 원리상 막힌 것이 아니라 포팅을 미루는 것이다(§4.2). Go만 성격이 달라 별도 판단이 필요하다.
- 진행 중 요청을 **저장**하는 것. 화면용이고 지나가면 없다.
- 🔴 1단계로 **"어느 요청이 오래 걸리는가"에 답했다고 말하는 것**. 1단계가 답하는 것은
  **"적체가 생기고 있는가·어느 인스턴스인가"**까지다(astra 검수 §6-5). 개별 요청은 2단계다.

## 6. PoC — 🔴 제품 구현 전에 이것부터

astra 검수 판정은 **"현재 초안대로의 제품 착수는 보류하고 확장 지점·전송 경로를 검증하는
제한된 PoC만"**이었다. 사용자가 확장 방향을 확정했으므로 **PoC를 그 첫 단계로 삼는다.**

**범위를 좁힌다** — 에이전트 2.31.1 한 버전, JDK 17 한 버전, **Spring MVC/Tomcat 한 조합**.
WebFlux·virtual thread·다중 WAR는 검증 전까지 지원 범위에 넣지 않는다.

### 확인할 것 둘

**P1. `OperationListener`가 요청당 정확히 한 번 시작·종료되는가**
- 정상 요청 · 예외 · 클라이언트 취소 · 타임아웃 · Servlet 비동기 dispatch · 스트리밍 응답
- 🔴 **샘플링을 꺼도 켜도 같은 수가 나오는가** — 이게 이 지점을 고른 이유다.
- 시작만 있고 종료가 없는 경우가 실제로 있는가(있다면 얼마나)

**P2. 실제 비용이 얼마인가 — 추정 금지**
- 같은 부하에서 **확장 없음 / 있음**을 A/B
- 정상 · 장기 요청 · 높은 동시성 · 상한 포화 · 수집기 단절 다섯 상황
- 처리량 · 요청 p99 · 요청당 할당 바이트 · GC 일시정지 · 보유 heap · 집계 소요
- 🔴 **export 주기 단축 비용과 요청 추적 비용을 분리해서 잰다**(섞이면 원인을 못 가른다)

### PoC 합격선
- P1: 여섯 상황 전부에서 시작·종료가 1:1이고, 샘플링 on/off에 수가 흔들리지 않는다.
- P2: 확장 있음의 요청 p99 증가가 **측정 가능하게 작다**. 🔴 합격선 숫자는 **PoC에서 정한다** —
  지금 정하면 그 숫자에 맞춰 측정하게 된다.

⚠️ PoC가 P1에서 막히면 이 접근 자체를 다시 본다. 대안은 §1의 표와 "과거 동시 실행"(아래).

### 곁가지 — 과거 동시 실행 차트(확장 없이 지금 가능)
이미 저장하는 스팬에 `start_ts`·`duration_ns`가 있으므로 **겹치는 구간을 세면** 동시 실행 수가
나온다. 🔴 단 **"지금"은 못 센다** — 기록이 끝나야 도착하고, 느린 요청일수록 늦게 온다.
**"N분 전 기준"으로만 정직하게** 쓸 수 있다. 용량 산정·사후 분석에는 오히려 이쪽이 정확하다.
확장과 **경쟁하지 않는다**(답하는 질문이 다르다). 별도 과제로 남긴다.

## 7. 규모 추정 (초안)

| 단계 | 내용 | 일 |
|---|---|---|
| 1 | 확장 뼈대 + `onStart`/`onEnd` + 맵 + 상한 | 1.0 |
| 2 | 1초 집계 → 메트릭 export | 1.0 |
| 3 | BE 수신·링 반영 | 0.5 |
| 4 | 화면 카드 + "확장 없음" 문구 | 1.0 |
| 5 | 자기 비용 측정 + 설치 가이드 + 끄는 법 | 1.0 |
| 0 | 🔴 **PoC(§6) — 확장 지점 검증 + 비용 측정** | **2.0** |
| | **PoC + 1단계 합계** | **6.5** |
| 후속 | 2단계(목록) — 상한·마스킹·화면 | 별도 산정 |

⚠️ 1~5단계 숫자는 **PoC가 끝난 뒤에야** 의미가 있다. 특히 P1(요청당 1:1 여부)이 막히면
접근 자체를 다시 봐야 하므로 이 표가 통째로 바뀐다.
⚠️ 불안정 API(§2.1)를 쓰므로 **에이전트 버전을 올릴 때마다 재검증 비용**이 붙는다 — 일회성이 아니다.
