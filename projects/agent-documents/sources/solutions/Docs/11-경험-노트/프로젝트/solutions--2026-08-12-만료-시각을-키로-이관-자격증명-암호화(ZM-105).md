## 이 세션의 한 줄

**비개발자에게 쉽게 설명하려고 그림을 그리다가, 판정 값의 출처가 두 군데로 갈려 있는 것이 드러났다.**
코드 리뷰도 테스트도 못 잡은 것을 *"그래서 만료일은 어디서 오나요"* 한 문장이 잡았다.
설계 감사는 검증 도구가 아니라 **설명 요구**로도 일어난다.

---

## 1. 🔴 어떻게 발견했나 — 설명이 감사였다

사용자가 원리를 단계적으로 캐물었다: 전자서명이 맞나 → 매 요청마다 확인하나 → 캐시는 왜 → **"정책은
키에서 가져오고 만료일은 디비에서 가져온다는거?"** → **"아 그러면 마냥 늘려버리면 무한정 사용할 수 있는 거야"**

그 자리에서 실기동으로 확인했다. `update license set expires_at = '2126-01-01'` 한 줄 + 캐시 60초.
**정말로 무한 연장됐다.**

등급·기능은 매 요청 키를 재검증해서 꺼내는데(그래서 DB를 고쳐도 안 통한다), **만료일만 DB가 정본**이었다.
[[projects/moveseye/2026-08-06-license-kernel-design|2026-08-06-license-kernel-design]]의 M-P12 결정 — *"기간은 발급일이 아니라 등록일부터"* — 의 대가였고,
당시에는 이 뒷면을 아무도 적어두지 않았다.

> 교훈: **"이 값의 정본은 어디인가"를 값마다 물어라.** 같은 화면에서 나란히 보이는 값들이 서로 다른
> 신뢰 경계에서 온다는 사실은, 코드를 훑어서는 잘 안 보이고 **표로 그려야 보인다.**

## 2. 결정 — 등록 시점 계산을 포기하고 시작일로 흡수한다

P12의 문제의식(계약 3월·설치 5월인데 발급일부터 시계가 돌면 고객이 두 달을 잃는다)은 옳았다.
그래서 문제의식을 버리지 않고 **해결 수단만 바꿨다.**

```
before   키: "365일짜리"        →  등록하는 순간 제품이 만료일 계산 → DB
after    키: "2026-09-01 ~ 2027-09-01"  →  서명 아래. DB는 표시용 사본
```

**성립 조건은 발급기의 시작일 입력**이다. 지연이 예상되면 발급할 때 시작일을 미래로 잡고,
더 밀리면 재발급한다 — 우리가 클릭 몇 번 하는 일이라 비용이 0이다.
**제품에서 유연성을 빼서 발급 시점으로 옮긴 것**이고, 그래야 서명 아래로 들어간다.

사용자의 판단이 이 방향을 정했다 — *"복잡하게 가지 말고 걍 발급일 기준으로 며칠 이런 식으로 가자"*,
*"시작일 두자"*. 대안(만료일 서명 + 등록일 계산 병행, HMAC 봉인 컬럼)은 전부 더 비쌌다.

## 3. 🔴 표준 `exp`를 쓰지 않는다 — 되돌리기 쉬운 지점

만료 시각을 키에 넣으면 JWT 표준 필드 `exp`를 쓰고 싶어진다. **쓰면 안 된다.**

`exp`를 쓰면 java-jwt가 **서명 검증 단계에서** 만료 토큰을 거부한다. 그러면 만료 다음 날 곧바로
`INVALID`(=잠금)이 되어 **`GRACE`→`EXPIRED`→`ARCHIVED` 4단계 축소가 통째로 사라진다.**
만료 판정은 상태 머신이 해야 하므로 라이브러리가 먼저 손대면 안 된다.

> "표준인데 왜 안 써요?"로 미래의 누군가가 되돌리기 딱 좋은 자리라, **`LicenseClaims.EXPIRES_AT`
> 주석 · 발급기 `Core` · 운영 가이드 3곳에 이유를 남겼다.** 주석 한 곳은 리팩터링 때 지워진다.

## 4. 방어가 로직에서 서명으로 옮겨갔다 (jti 재사용 방지 삭제)

"만료 임박하면 지웠다 재등록"을 막던 `resolveActivatedAt()`(jti로 최초 등록 시각 조회)을 **삭제했다.**
만료일이 키에 있으면 몇 번을 등록하든 같은 날짜가 나오므로 불필요하다.

**기능이 사라진 게 아니라 방어 위치가 바뀐 것**이다. 이런 삭제는 리뷰에서 "보호 장치를 지웠다"로
읽히기 쉬워서, 커밋 메시지와 테스트(`LicenseServiceIT`)에 대체 관계를 명시했다.
`activated_at`은 남지만 의미가 *"최초 활성화 시각"*(판정 입력) → *"이 설치본에 등록된 시각"*(감사 기록)으로 바뀌었다.

## 5. 검증 — 뮤테이션이 "정확히 2건"을 깨뜨렸다

새 방어에 테스트를 붙였다고 끝이 아니라, **일부러 되돌려서 그 테스트만 실패하는지** 확인했다
([[topics/backend/test-false-safety-nets|test-false-safety-nets]] 규율).

판정을 DB 기준으로 되돌리는 뮤테이션 → **정확히 2건만 실패**:
- `LicenseGateIT` — DB `expires_at`을 미래로 늘려도 기간은 연장되지 않는다
- `SignedKeyLicenseProviderTest` — 유예·만료 모두 DB가 아니라 키를 따른다

실기동(dev)도 돌렸다. 시작일 `2026-09-01` + 365일 키를 8/12에 등록 → 만료 `2027-09-01`, 잔여 384일
(**등록일 기준이 아님이 눈으로 확인된다**). 그 상태에서 `expires_at=2126-01-01`, `grace_days=99999`로
UPDATE하고 캐시 만료(60초)까지 기다려도 **여전히 2027-09-01**. 887 green.

> 실기동을 한 이유: 뮤테이션은 *"테스트가 지키고 있다"*를 증명하지만 *"실제 DB에서 무시된다"*는
> 증명하지 않는다. 캐시가 끼어 있어 특히 그렇다.

## 6. 곁가지 — 자격증명 암호화(ZM-105)

라이선스와 무관한 별개 건. Zabbix·AWS 접속 비밀번호가 `setting` 테이블에 **평문**이던 것을
AES-256-GCM으로 감쌌다(`enc:v1:` 접두사, 읽을 때 접두사 없으면 평문으로 간주 → 무중단 이행).

- 키는 `CREDENTIAL_ENCRYPTION_KEY` 환경변수. **설치본마다 다른 값이고 우리는 알지 않는다.**
- 라이선스 키쌍과 **완전히 다른 목적**이다 — 이쪽은 고객 데이터 보호(대칭), 저쪽은 위조 방지(비대칭).
  같은 "암호화"라는 말로 묶여 혼동되기 쉬워 가이드 문서에서도 절을 분리했다.

## 7. 반복된 함정

- **PowerShell `Set-Content -Encoding UTF8`이 커밋 메시지 한글을 깨뜨렸다** — 세 번째. 이제 규칙:
  **한글이 들어가는 파일은 PowerShell로 쓰지 말고 Write 도구로 쓴다.**
- **BOM 없는 `.ps1`은 MS949로 읽힌다** — 한글이 깨지면서 존재하지도 않는 `&` 파서 오류로 나타났다.
  스크립트를 ASCII로만 쓰고 한글 경로는 `[char]0xD14C` 식으로 조립해 회피.
- `Invoke-WebRequest`는 `-UseBasicParsing` 없으면 NonInteractive에서 죽고,
  `WebRequestSession`은 프로세스 간 Clixml 왕복이 안 된다(→ E2E는 **한 스크립트에 통째로**).
- dev DB 접속은 `postgres / dmove / 5433`. `admin`은 없는 롤이다.
- `/hosts`는 **존재하지 않는 경로**다(실제는 `/hosts/hostgroups`·`/hosts/server`). catch-all 핸들러가
  `NoResourceFoundException`을 삼켜 **404가 아니라 500**으로 나온다 — 별건으로 남김.
