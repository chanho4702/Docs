# 승인 중·승인 후 페이지 편집 정책 설계

> 상태: **축 B는 2026-08-12에 구현됨** — `ALLOW_MARK_STALE`이 설정 없이 유일한 동작이 됐다
> ("버전 기록 모델", `_workspace/design-reapproval.md` · 커밋 b522c17/e06aa16).
> `APPROVED`는 편집·마감에도 영구 유지되고, 화면은 "최신 승인 버전 vs 현재 버전" 파생 비교(stale)로
> 재승인 필요를 표시하며, 상세 모달의 원클릭 CTA(`fromRequestId`)로 같은 결재선 재승인을 만든다.
> 축 A(진행 중 편집 만료)는 현행 유지. 축 A/C의 `LOCK` 계열은 여전히 미구현 설계다.
> 관련 코드: `ApprovalPageUpdateListener`, `ApprovalRequest.expireForContentVersion`, `ApprovalSettings`

## 1. 다루는 문제

승인은 "이 시점의 이 내용"에 대한 동의다. 그런데 페이지는 승인 도중에도, 승인이 끝난 뒤에도 편집할 수 있다.
편집을 어떻게 다룰지 정하지 않으면 **승인 기록이 실제 문서와 어긋난다.**

두 시점을 나눠서 봐야 한다.

- **승인 진행 중(`PENDING`)** — 1단계는 승인했고 2단계가 남았는데 본문이 바뀌는 경우
- **승인 완료 후(`APPROVED`)** — 결재가 끝난 문서를 나중에 고치는 경우

## 2. 지금 동작 (코드로 확인한 사실)

`ApprovalPageUpdateListener.onPageUpdate`가 `PageUpdateEvent`를 받아
`expireForPageVersion(pageId, version)`을 호출한다.

```java
// ApprovalRequest.expireForContentVersion
if (currentContentVersion <= target.contentVersion() || !canExpire()) return false;
status = ApprovalStatus.EXPIRED;

// canExpire()
return status == ApprovalStatus.PENDING || status == ApprovalStatus.APPROVED;
```

정리하면 이렇다.

| 상황 | 현재 결과 (2026-08-12 버전 기록 모델 이후) |
|---|---|
| 진행 중 편집 | 전체 `EXPIRED`. **이미 받은 단계 승인도 전부 무효**, 처음부터 재요청 |
| 완료 후 편집 | **`APPROVED` 유지.** pill이 `v{a} 승인 · v{c} 미승인`(stale)으로 바뀌고, 상세 모달에 diff 링크·버전별 승인 이력·재승인 CTA가 표시된다 |
| 완료 후 마감 경과 | **`APPROVED` 유지** (승인 기록은 마감으로 소멸하지 않는다) |
| 감사 기록 | 진행 중 편집 만료 시 `EXPIRED` 이벤트 사유 `CONTENT_VERSION`. `CONTENT_VERSION_AFTER_APPROVAL`은 과거 데이터 표시 전용으로만 남고 새로 생성되지 않는다 |
| 알림 | 진행 중 편집 만료: 요청자 + 아직 결정하지 않은 승인자 |
| 편집 차단 | **없음** |

`PageUpdateEvent`는 저장이 끝난 뒤 발행되는 사후 이벤트다. **여기서 저장을 취소할 수 없다.**
따라서 "편집을 막는다"는 이벤트 리스너가 아니라 사전 권한 제어로만 가능하다.

## 3. 설계 축

정책을 세 축으로 나눈다. 축을 섞으면 조합이 폭발하므로 각각 독립 설정으로 둔다.

### 축 A — 진행 중 편집

| 값 | 동작 | 적합한 상황 |
|---|---|---|
| `ALLOW_EXPIRE` (현행) | 편집 허용, 편집되면 요청 만료 | 초안을 돌려가며 다듬는 문서 |
| `LOCK` | 편집 제한을 걸어 애초에 못 고치게 함 | 결재 대상이 고정돼야 하는 문서 |

### 축 B — 완료 후 편집

| 값 | 동작 | 적합한 상황 |
|---|---|---|
| `ALLOW_EXPIRE` (현행) | 편집 허용, `APPROVED` → `EXPIRED` | 승인은 "그때 그 버전"에 대한 기록으로만 씀 |
| `ALLOW_MARK_STALE` | 편집 허용, 상태는 유지하되 "승인 후 변경됨"을 표시 | 승인 이력은 남기고 변경 사실만 드러내고 싶을 때 |
| `LOCK` | 승인 후에도 편집 제한 유지 | 규정 문서. 바꾸려면 관리자가 명시적으로 해제 |

`ALLOW_MARK_STALE`은 새 상태를 만들지 않고 **파생 값**으로 계산한다.
`APR_REQ.CONTENT_VERSION < 현재 페이지 version` 이면 `staleSince`가 참이다.
`dueSoon`을 저장하지 않고 응답 시점에 계산한 것과 같은 이유다 — 저장하면 값이 썩는다.

### 축 C — 잠금 시 요청자 예외

`LOCK`을 선택했을 때만 의미가 있다.

| 값 | 동작 |
|---|---|
| `REQUESTER_MAY_EDIT` | 요청자는 편집 가능. 고치면 축 A의 만료 규칙이 그대로 적용돼 사실상 "회수 후 수정" |
| `LOCKED_FOR_ALL` | 요청자도 편집 불가. **요청 취소 기능이 없으면 막다른 길이 되므로 함께 만들어야 한다** |

## 4. 잠금 구현 방식과 Confluence의 제약

`com.atlassian.confluence.core.ContentPermissionManager` +
`com.atlassian.confluence.security.ContentPermission.EDIT_PERMISSION`으로 페이지 편집 제한을 건다.

**중요한 제약 세 가지.**

1. **Confluence의 편집 제한은 허용 목록이다.** "아무도 편집 못 함"을 표현할 수 없고,
   최소 한 주체는 편집 가능해야 한다. 제한 집합을 비우면 "제한 없음"이 된다.
   → `LOCKED_FOR_ALL`은 실제로는 "관리자 그룹만 편집 가능"으로 구현된다. 문구를 그렇게 써야 오해가 없다.
2. **Confluence 관리자는 제한을 우회한다.** 잠금은 완전한 차단이 아니다.
   → 그래서 **잠금과 만료는 배타가 아니라 계층이다.** 잠금은 1차 방어, 만료 리스너는 최후 방어로 남긴다.
   `LOCK` 모드에서도 `ApprovalPageUpdateListener`를 끄지 않는다.
3. **기존 제한을 덮어쓰면 원래 설정이 사라진다.** 페이지에 이미 편집 제한이 걸려 있을 수 있다.
   → 잠그기 전에 기존 제한을 **스냅샷으로 저장**하고, 해제할 때 그대로 복원한다.

### 잠금 원장 (신규 AO 엔티티)

```text
APR_LOCK
  REQUEST_ID      잠금을 유발한 승인 요청
  PAGE_ID         대상 페이지
  ORIGINAL_EDIT   잠그기 전 EDIT 제한 스냅샷 (JSON, UNLIMITED)
  APPLIED_AT      적용 시각
  RELEASED_AT     해제 시각. null이면 아직 잠겨 있음
  LAST_ERROR      마지막 해제 실패 사유
```

이 원장이 있어야 "해제가 안 끝난 잠금"을 찾아 재시도할 수 있다.
`APR_NOTIF`를 outbox로 쓴 것과 같은 구조다 — 상태 변경과 부수 효과를 한 트랜잭션에 묶을 수 없으니
**원장에 적고 나중에 수렴시킨다.**

## 5. 실패 처리 — 여기가 이 기능의 진짜 위험

### 잠금 적용 실패

승인 요청은 만들어졌는데 편집 제한을 못 걸면, 통제가 없는 채로 승인이 도는 것이다.
알림 적재 실패와 성격이 다르다(알림은 없어도 승인은 유효하지만, 잠금은 그 자체가 목적).

→ **요청 생성을 실패시키고 보상 롤백한다.** 요청을 지우고 `400`을 돌려준다.
"승인 요청은 됐는데 잠기지 않은" 상태를 남기지 않는다.

### 잠금 해제 실패 — 더 위험

문서가 잠긴 채 남는다. 사용자는 왜 못 고치는지 알 수 없다.

1. 해제는 승인 완료·반려·만료 **모든** 종료 경로에서 시도한다.
2. 실패하면 `APR_LOCK.LAST_ERROR`에 남기고 `RELEASED_AT`은 비워 둔다.
3. 기존 만료 sweep과 같은 `RUN_ONCE_PER_CLUSTER` job이 미해제 잠금을 주기적으로 재시도한다.
4. 관리자 화면에 **"해제 대기 중인 잠금"** 목록과 수동 해제 버튼을 둔다.
   자동 복구가 실패해도 사람이 풀 수 있는 문이 있어야 한다.
5. 잠금이 걸린 페이지의 승인 패널에 "승인 절차로 편집이 제한된 문서입니다"를 표시한다.
   이유를 모르는 잠금이 가장 나쁘다.

### 요청이 삭제되거나 플러그인이 비활성화되면

플러그인이 꺼지면 해제할 주체가 사라진다. 그래서 잠금은 **플러그인 밖에서도 풀 수 있어야** 한다 —
Confluence 기본 제한 화면에서 관리자가 직접 풀 수 있으므로 이 조건은 충족된다.
다만 원장과 실제 상태가 어긋나므로, 해제 시 원장에 없는 제한을 건드리지 않도록
**복원은 스냅샷과 현재 상태를 비교해 우리가 건 것만 되돌린다.**

## 6. 영역(`CONTENT_REGION`) 승인에서의 문제

편집 제한은 **페이지 단위**로만 걸 수 있다. 영역 단위 잠금은 Confluence에 없다.

같은 페이지에 영역이 여러 개일 때 하나만 승인 중이어도 페이지 전체가 잠긴다.
다른 영역 작업자까지 막히므로 부작용이 크다.

→ **기본값은 "영역 승인에는 잠금을 적용하지 않는다".**
   영역 승인의 편집 정책은 축 A/B의 `ALLOW_EXPIRE`만 쓴다.
   페이지 전체 잠금을 원하면 페이지 승인을 쓰라고 안내한다.
   이걸 옵션으로 열지는 4단계(아래)에서 다시 판단한다.

## 7. 설정 스키마

`ApprovalSettings`는 이미 `PluginSettingsFactory` 기반이고
"값이 없거나 범위를 벗어나면 읽는 시점에 기본값으로 대체"하는 규칙이 있다. 그대로 따른다.

| 키 | 타입 | 기본값 | 의미 |
|---|---|---|---|
| `editPolicyWhilePending` | enum | `ALLOW_EXPIRE` | 축 A |
| `editPolicyAfterApproved` | enum | `ALLOW_EXPIRE` | 축 B |
| `pendingLockScope` | enum | `REQUESTER_MAY_EDIT` | 축 C |
| `lockRetryIntervalMinutes` | int | 10 | 미해제 잠금 재시도 주기 |

**기본값을 모두 현행 동작으로 둔다.** 설정을 건드리지 않은 설치는 오늘과 똑같이 동작한다.
`emailNotificationsEnabled`를 `false`로 둔 것과 같은 판단이다 — 부수 효과가 큰 기능은 명시적으로 켜야 한다.

Flow별 오버라이드(`APR_FLOW.EDIT_POLICY`)도 가능하지만 **1차 구현에서는 넣지 않는다.**
전역 정책이 실제로 어떻게 쓰이는지 본 다음 결정한다.

## 8. 조합별 최종 동작

| 축 A | 축 B | 진행 중 편집 | 완료 후 편집 |
|---|---|---|---|
| `ALLOW_EXPIRE` | `ALLOW_EXPIRE` | 만료 후 재요청 (현행) | 만료 (현행) |
| `ALLOW_EXPIRE` | `ALLOW_MARK_STALE` | 만료 후 재요청 | 승인 유지 + "승인 후 변경됨" 배지 |
| `LOCK` | `ALLOW_EXPIRE` | 편집 불가 | 승인 끝나면 잠금 해제, 이후 편집 시 만료 |
| `LOCK` | `LOCK` | 편집 불가 | 계속 편집 불가. 관리자가 수동 해제 |

## 9. 구현 순서

각 단계가 그 자체로 배포 가능해야 한다.

1. **`ALLOW_MARK_STALE` 먼저.** 권한을 건드리지 않고 파생 값 계산과 화면 표시만 추가한다.
   위험이 거의 없고, 축 B 요구의 상당 부분을 여기서 충족한다.
2. **설정 3종 추가 + 관리자 화면.** 아직 `LOCK`은 선택해도 동작하지 않게 두거나 목록에서 감춘다.
3. **`APR_LOCK` 원장 + 잠금 적용/해제 + 보상 롤백.** 여기가 본체다.
4. **미해제 잠금 재시도 job + 관리자 해제 화면.**
5. 영역 승인 잠금 여부, Flow별 오버라이드는 이후 판단.

**1·2단계까지만 해도 "옵션으로 처리 가능한가"라는 요구는 충족된다.**
3단계부터는 권한을 조작하므로 되돌리기 비용이 크다.

## 10. 아직 정하지 못한 것

- `LOCKED_FOR_ALL`을 쓸 경우 **요청 취소(회수) API**가 반드시 필요하다. 지금은 없다.
  누가 취소할 수 있는지(요청자만? 관리자도?), 취소된 요청의 상태를 무엇으로 둘지
  (`EXPIRED` 재사용 vs `CANCELLED` 신설 — 후자는 domain 상태 머신 변경) 결정이 필요하다.
- 잠금 중에 승인자가 "내용을 조금 고쳐야 승인하겠다"고 할 때의 경로.
  반려 후 재요청이 유일한 길인데, 단계가 많으면 비용이 크다.
- 페이지 이동·복사·템플릿화 시 잠금이 따라가는지. Confluence 제한 상속 규칙을 실측해야 한다.
- 승인 완료 후 `LOCK`을 유지하면 페이지가 사실상 동결된다.
  이 상태의 문서가 쌓였을 때 운영이 감당 가능한지 — 조직 규모에 달린 문제라 실제 사용 후 판단.
