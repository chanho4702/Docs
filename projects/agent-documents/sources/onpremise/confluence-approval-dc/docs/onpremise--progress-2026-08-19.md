# 진행 기록 — 2026-08-19

## 배치 9 — 결재 위임 + 독촉 알림

관리자 설정 두 개(`delegationEnabled`, `reminderEnabled`)로 켜고 끄며, **둘 다 기본은 꺼짐**이다.
설정을 건드리지 않은 설치는 어제와 똑같이 동작한다.

### 1. 위임이 실제로 쓰이려면 필요한 것

위임은 "등록 화면"만으로는 기능이 되지 않는다. 대리인이 **대상 건을 찾고**, **버튼을 보고**,
**결과가 사실대로 기록되어야** 비로소 쓸 수 있다. 그래서 다섯 지점을 함께 건드렸다.

| 지점 | 무엇을 했나 |
|------|------------|
| 저장 | `APR_DELEG` — 결재자·대리인·기간·메모·사용 여부. `ApprovalDelegationStore.isActive`가 기간 판정을 한 곳에서 한다 |
| 결재 경로 | `decide()`가 본인이 아니면 `denyDelegation()`으로 위임을 확인하고, 통과하면 결정은 **결재선 주인의 키로** 넣고 누른 사람은 `delegateKey`로 이벤트에 남긴다 |
| 업무함 | `approverScopedRequests()` — 내 결재 + 지금 대리 중인 사람들의 결재 |
| 내 차례 판정 | `String currentKey` 하나로 보던 것을 키 묶음(`own` = 본인 userKey·username, `acting` = own + 대리 중인 키들)으로 넓혔다. 배지·집계·필터·`myTurn`이 모두 같은 묶음을 본다 |
| 페이지 배너 | `resolveDelegatedActorKey()`가 결재선에서 내가 대리하는 사람을 찾아 그 자리에 세우고, `대리 결재 — OOO` 표시를 붙인다 |

이력 표시는 업무함 상세와 페이지 모달 양쪽에 `(대신 결재: OOO)`으로 붙였다.
**결재선의 자리는 위임으로 바뀌지 않는다** — 위임은 "누가 눌렀나"만 바꾼다.

### 2. 위임을 끄면 즉시 멈춘다

`denyDelegation()`은 등록된 위임을 보기 전에 `settings.delegationEnabled()`부터 확인한다.
관리자가 끄는 순간 등록된 위임이 남아 있어도 대리 결재는 403이다. 업무함 노출(`approverScopedRequests`)과
배너(`resolveDelegatedActorKey`)도 같은 조건을 본다 — 한쪽만 막으면 "보이는데 눌리지 않는" 화면이 된다.

### 3. 사람 찾기 엔드포인트를 새로 뗀 이유

기존 `/users/page`는 **관리자 전용**이고 검색어가 없으면 디렉터리 전체를 넘긴다. 위임 대상 선택은
일반 결재자가 하는 일이라 그대로 열 수 없어, `/users/lookup`을 따로 뒀다 — 로그인 사용자에게 열리되
**2자 이상 검색해야만 응답하고 최대 20건**이다. Confluence 자체 사용자 선택기와 같은 수준이다.

### 4. 독촉 — 새 스케줄러를 만들지 않았다

만료 sweep job이 이미 주기적으로 돌고 마감 임박 알림을 쌓는다. 독촉을 여기에 얹었다.

문제는 sweep이 몇 분마다 도는데 독촉은 며칠 주기라는 점이다. **회차 번호를 알림 키에 넣어** 풀었다:

```
eventId = "reminder:" + requestId + ":" + round
round   = (기다린 날수 - 첫 독촉일) / 반복 주기 + 1
```

회차는 날수에서만 나오므로 같은 날 sweep이 몇 번 돌든 같은 값이고, outbox의 중복 방지
(eventId + recipient + channel)가 나머지를 막는다. `ReminderRoundTest` 4건으로 고정했다.

받는 사람은 `canDecideNow`인 결재자뿐이다. **상급자 상신은 넣지 않았다** — Confluence에는 조직 계층이
없어서 "상급자"를 정할 근거가 없다(2026-08-19 결정, 백로그 기록).

"차례가 온 시각"은 처음에 `updatedAt`으로 잡았다가 QA에서 되돌렸다(6절 참조) — 같은 단계에
결재자가 여럿이면 남의 승인으로도 갱신되기 때문이다. 지금은 도메인의 `currentStepOpenedAt()`을 쓴다.

`bulkApprovalEnabled`(기본 꺼짐). 업무함 **내 차례** 탭에서만 고를 수 있다 — 다른 탭에는 지금

**검증을 갈라 두지 않았다.** 일괄이 따로 권한·위임·상태를 확인하면 언젠가 한쪽만 고쳐진다.
`decide()`의 알맹이를 `decideOne()`으로 떼어 내고 일괄도 그 길을 지나게 했다. 일괄에만 있는 것은
`pinVerified` 하나뿐이다 — PIN은 묶음 전체에 한 번만 묻는다.

`actorKey`는 클라이언트가 보내지 않는다. 건마다 `effectiveApproverKey`로 서버가 정한다 —
대리 중이면 위임한 사람의 자리, 아니면 내 자리다.

**반려는 넣지 않았다.** 반려 사유는 건마다 다르고, 같은 문장을 여러 건에 붙이는 것은 기록으로서
의미가 없다.

일부 실패는 정상 상황이다(그 사이 남이 처리했거나 영역 본문이 바뀐 경우). 첫 실패에서 멈추지 않고

## 대리 결재의 도장 — 누구 것을 찍는가 (사용자 결정)

배치 9는 도장을 **결재선 주인**의 것으로 찍었다. 결정이 그 사람 이름으로 기록되니 자연스러워
보였지만, 감사 관점에서는 틀렸다. **서명은 "누가 동의했는가"가 아니라 "누가 그 자리에서
확인했는가"의 산출물**이다. 위임자의 서명이 찍히면 실제로 하지 않은 확인을 한 것처럼 남는다.

사용자 결정(2026-08-19): **대리인의 도장을 찍되 대리라는 사실을 표시한다.**

- 도메인에 `delegateKeyFor(approverKey)` — 그 결재자의 결정을 대신 눌러 준 사람. 본인이면 null.
- 도장의 주인·이니셜·서명 이미지가 모두 이 값을 따른다. 테두리를 점선으로 구분하고
  옆에 `대리` 꼬리표를 붙이며, 툴팁은 `대리인 (대리 결재 — 원 결재자)`.
- 서명 이미지 REST의 권한 검사가 `decisions`만 봤다 — 대리인은 거기 없어 403이었다.
  "자기 이름으로 결정했거나, 남을 대신해 눌렀거나"로 넓혔다.
- **결정 기록은 그대로 원 결재자 이름이다.** 바뀐 것은 도장의 주인뿐이다.

### 함께 드러난 기존 결함

업무함 상세의 결재란이 `x.type === "APPROVE"`로 비교하고 있었다. 서버가 넣는 값은 `"APPROVED"`라
**도장이 한 번도 뜬 적이 없다**(배치 8부터). 문자열 비교 오타라 테스트로 고정했다.

| 읽지 않은 알림이 지워진다 | drain이 채널을 가리지 않고 `markSent` 하므로 in-app도 `SENT`가 된다. 정리 조건이 `STATUS`만 봐서 **읽지 않은 알림까지 삭제 대상**이었다 | 삭제 조건에 채널을 넣었다. in-app은 `READ_AT`이 있을 때만 지운다 |
| 위임 해제가 다른 노드에 늦게 전파 | 설정 캐시의 무효화 카운터가 JVM-local이라, 클러스터의 다른 노드는 최대 5초간 옛 값을 들고 대리 결재를 허용한다 | `delegationEnabledNow()` — 권한을 여닫는 이 한 키만 캐시 밖에서 매번 읽는다 |
| 잘못된 대리 자리를 고른다 | `effectiveApproverKey`가 "결재선에 있는 첫 키"를 골랐다. A→B 결재선에서 B가 A에게 위임하면, A가 1단계를 끝낸 뒤에도 **이미 닫힌 A 자리**가 잡혀 열린 2단계를 놓쳤다. 패널·매크로는 내 자리가 있으면 대리를 아예 찾지 않았다 | **지금 결재할 수 있는 자리를 먼저** 찾고, 없을 때만 결재선 순서를 따른다 |
| 반려 대리인의 서명 노출 | `stamped()`가 이벤트 종류를 안 봐서, 도장이 찍히지도 않는 **반려**를 대신한 사람의 개인 서명이 페이지 열람자에게 열렸다 | `APPROVED` 이벤트만 허용 |

### 보통·낮음·확인필요

- **이미 승인한 사람에게 독촉** — `canDecideNow()`는 결정 여부를 보지 않는다. 다인원 단계에서
  먼저 누른 사람도 계속 재촉받았다. 수신자에서 뺐다.
- **독촉 키에 단계가 없다** — 단계가 넘어가면 회차가 1로 돌아간다. 같은 사람이 두 단계에 관여하면
  (위임으로 두 자리를 대리하는 경우) 2단계 독촉이 1단계 것과 같은 키가 되어 걸러졌다.
  키에 `currentStepOrder()`를 넣었다.
- **1,000건 상한의 굶주림** — "나머지는 다음 주기로 넘긴다"고 로그에 적었지만 사실이 아니었다.
  매 주기 같은 앞쪽 1,000건만 읽는다. 로그를 사실대로 고치고 관리자가 할 일을 안내한다.
- **legacy username 위임** — REST만 두 형태를 보고 패널·매크로·스케줄러는 exact 비교였다.
  세 경로 모두 userKey로 정규화해 견주게 했다.
- **선택 열 추가 후 열 번호** — 상세 행 `colSpan`이 7로 남았고 반응형 `nth-child`가 한 칸씩 밀려
  좁은 화면에서 엉뚱한 열이 숨었다.
- **위임 동시 등록** — REST의 사전 조회는 동시 요청 두 건을 막지 못한다. `APR_DELEG`에는
  "살아 있는 위임"을 표현할 unique 컬럼을 둘 수 없어(enabled·기간의 조합) 저장 직전 재확인으로 막았다.
- **감사 화면의 위임 라벨 누락** — `DELEGATION`이 원문으로 보였다.

### 실기동 재검증

코덱스가 짚은 시나리오를 그대로 재현했다.

```
1단계 admin 본인 승인   → actor=admin,  delegate=-
2단계 tester 자리 대리  → actor=tester, delegate=admin
admin 업무함: myTurn=true, delegatedFor=결재 테스터
반려 대리인 서명 열람   → 403
감사 이력              → DELEGATION 기록됨
```

테스트 도메인 61, C9 186.
