# 배포 운영 문서 — 고객 스테이징

> 대상: 이 앱을 고객 환경에 올리는 사람(개발/운영).
> 고객에게 그대로 나가는 문서는 `guide-admin.md`·`guide-user.md`다. 이 문서는 **내부용**이다.
> 기준 버전: 1.0.0 · Confluence 9.2.x · 작성 2026-08-20

## 1. 무엇을 배포하는가

| 항목 | 값 |
|------|-----|
| 산출물 | `approval-confluence9/target/approval-confluence9-1.0.0.jar` |
| 지원 | Confluence **9.2.x** (Data Center), Java 17 또는 21 |
| Confluence 10 | **제공하지 않는다.** 어댑터가 미완성이다(소스 7개 대 57개) |

C10 어댑터는 순차 승인 이전 시점에서 멈춰 있고 업무함·설정·알림·서명·위임·i18n·XSRF가 없다.
고객이 Confluence를 10.x로 올릴 계획이 있으면 **업그레이드 전에 반드시 알아야 한다.**

## 2. 산출물 만들기

```bash
# 1) 도메인 먼저
mvn -pl approval-domain clean test package

# 2) 어댑터 (전체 테스트 포함)
mvn -pl approval-confluence9 -am test

# 3) 패키징
mvn -pl approval-confluence9 package -DskipTests
```

### 반드시 통과해야 하는 게이트

```powershell
powershell.exe -File scripts/release-check.ps1
```

**exit 0이어야 배포한다.** 스크립트가 확인하는 것:

| 검사 | 왜 |
|------|-----|
| 도메인 클래스 16개 임베드 | 0개면 설치 후 앱이 통째로 죽는다 (아래 참조) |
| 핵심 도메인 타입 존재 | 낡은 클래스로 패키징된 경우를 잡는다 |
| plugin descriptor 존재 | — |
| **번역 키가 두 파일에서 일치** | 한쪽에만 있는 키는 다른 로케일 화면에 키 문자열이 그대로 드러난다 |
| C10 산출물이 섞이지 않음 | 같은 plugin key를 쓴다. 함께 올리면 앱 전체가 비활성화된다 |

스크립트는 게이트가 실제로 막는지 역검증했다 — 도메인을 뺀 jar를 주면 exit 1로 배포를 거부한다.

수동으로 확인하려면:

```bash
unzip -l approval-confluence9/target/approval-confluence9-1.0.0.jar \
  | grep -c "approval/domain/.*class"
```

**16이 나와야 한다. 0이면 배포 금지.**

`approval-domain`은 `<Embed-Dependency>`로 jar 안에 들어간다. 재료는
`approval-confluence9/target/classes/kr/dmove/confluence/approval/domain/`인데, 여기가 비었거나
낡으면 도메인이 빠진 jar가 만들어지고 **설치하면 REST·패널·매크로가 전부
`NoClassDefFoundError`로 죽는다.** 겉으로는 설치가 성공한 것처럼 보이므로 게이트를 반드시 본다.

도메인을 고쳤다면 패키징 전에 최신 클래스를 넣어 준다.

```bash
cp -f approval-domain/target/classes/kr/dmove/confluence/approval/domain/*.class \
      approval-confluence9/target/classes/kr/dmove/confluence/approval/domain/
```

## 3. 설치

1. Confluence 관리자로 로그인
2. **일반 설정 → 앱 관리(UPM)** 에서 jar 업로드
3. 앱 활성화 확인
4. 아무 페이지나 열어 상단 헤더에 **승인** 아이콘이 뜨는지 확인
5. 편집 권한이 있는 페이지에서 **승인 요청** 버튼이 보이는지 확인

### 처음 뜰 때 만들어지는 것

**AO 테이블 12개**가 자동 생성된다. 수동으로 만들 것은 없다.

```
APR_REQ · APR_APV · APR_EVT · APR_NOTIF
APR_FLOW · APR_FLOW_P · APR_GROUP
APR_SIGN · APR_PIN · APR_CC · APR_AUDIT · APR_DELEG
```

실제 DB에서는 Confluence가 AO 접두사를 붙이므로 `AO_XXXXXX_APR_REQ` 형태로 보인다.

**스케줄러 작업 2개**가 등록된다.

| Job | 하는 일 | 주기 |
|-----|--------|------|
| `kr.dmove.confluence.approval.expiry-sweep` | 마감 만료 처리, 마감 임박 알림, 독촉 | 기본 10분 |
| `kr.dmove.confluence.approval.notification-drain` | 알림 발송, 오래된 알림 정리 | 기본 1분 |

둘 다 `RUN_ONCE_PER_CLUSTER`다 — 다중 노드에서 한 노드만 실행한다.

## 4. 설정 초기값 권장안

**설치 직후 기본값은 "기존과 같은 동작"이다.** 부수 효과가 큰 기능은 전부 꺼져 있다.
스테이징에서는 **켜서 확인**하고, 실서비스 전환 시 고객과 합의한 값으로 되돌린다.

| 설정 | 기본값 | 스테이징 권장 | 실서비스 권장 | 왜 |
|------|-------|-------------|-------------|-----|
| 기본 마감일 | `0`(없음) | `7` | 고객 결정 | **0이면 진행 중 요청이 영영 안 줄어든다.** 독촉 후보 상한(1,000건)과 맞물려 문제가 된다 |
| 만료 sweep 주기 | 10분 | 10분 | 10분 | — |
| 마감 임박 기준 | 24시간 | 24시간 | 고객 결정 | — |
| 반려 사유 필수 | 꺼짐 | **켬** | 고객 결정 | 사유 없는 반려는 이력으로 쓸모가 없다 |
| 알림 | 켜짐 | 켜짐 | 켜짐 | — |
| **이메일 알림** | 꺼짐 | **켬** | 고객 결정 | 로컬에서 한 번도 실발송해 본 적이 없다. 스테이징에서 반드시 확인 |
| 알림 발송 주기 | 1분 | 1분 | 1분 | — |
| **알림 보존 기간** | `0`(정리 안 함) | **`90`** | `90` 이상 | 0이면 알림이 단조 증가한다. **삭제는 되돌릴 수 없으니** 값을 정할 때 고객 합의 필요 |
| 전자서명 | 꺼짐 | 켬 | 고객 결정 | — |
| 서명 PIN 필수 | 꺼짐 | 켬 | 고객 결정 | 켜면 결재 때마다 PIN을 묻는다. 사용자 부담이 크다 |
| **결재 위임** | 꺼짐 | **켬** | 고객 결정 | 남이 내 이름으로 결재하게 된다. 고객이 감사 정책을 확인해야 한다 |
| 독촉 알림 | 꺼짐 | 켬 | 고객 결정 | 첫 독촉 3일 / 반복 3일이 기본 |
| **일괄 승인** | 꺼짐 | 켬 | 고객 결정 | 여러 건을 한 번에 확정한다. 실수의 파급이 크다 |
| 적용 스페이스 | 미설정(전체 허용) | 특정 스페이스만 | 고객 결정 | 미설정이면 **모든 스페이스**에서 승인 UI가 뜬다 |

### 반드시 고객에게 확인받을 것

1. **결재 위임을 켤 것인가** — 대리 결재는 결정이 원 결재자 이름으로 남고 도장은 대리인 것이
   찍힌다(`대리` 표시 붙음). 조직의 감사 규정이 이를 허용하는지 확인해야 한다.
2. **알림 보존 기간** — 지운 알림은 복구할 수 없다.
3. **적용 스페이스** — 정하지 않으면 전사 모든 스페이스에서 승인 버튼이 보인다.

## 5. 스테이징 검증 체크리스트

로컬(H2·단일 노드·사용자 2명·메일 서버 없음)에서 **확인할 수 없었던 것**들이다.
코드와 테스트로만 확인한 항목이 섞여 있으므로 여기서 반드시 실측한다.

### 5.1 기반 — 로컬에서 확인 불가했던 것

- [ ] **실 DB에서 AO 테이블 12개가 생성되는가** (PostgreSQL/Oracle/MSSQL 등)
      → 특히 `APR_REQ`의 `DEDUPE_KEY` unique 제약이 실제로 걸리는지
- [ ] **같은 페이지에 동시에 승인 요청 2건**을 보내면 하나만 성공하는가(409)
      → "열린 요청은 대상당 하나" 불변식의 실 DB 검증
- [ ] **다중 노드**에서 스케줄러가 한 번만 도는가 (양쪽 노드 로그 비교)
- [ ] **다중 노드에서 설정 전파** — 노드 A에서 결재 위임을 끈 직후 노드 B로 대리 결재를 시도하면
      즉시 403인가 *(코덱스 지적 높음2. 캐시를 우회하도록 고쳤으나 실측 못 함)*
- [ ] **실제 메일 발송** — 요청/승인/반려/마감임박/독촉 메일이 실제로 도착하는가, 본문 인코딩은 정상인가
- [ ] 메일 서버가 없을 때 outbox가 무한 재시도하지 않는가(최대 재시도 5회)

### 5.2 알림 정리 — 삭제는 되돌릴 수 없다

- [ ] 보존 기간을 짧게(1일) 두고, **읽지 않은 in-app 알림이 남는지** 확인
      *(코덱스 지적 높음1. 채널 조건을 넣어 고쳤으나 실측 못 함 — 여기서 반드시 확인)*
- [ ] 읽은 알림과 발송이 끝난 메일 행만 사라지는가
- [ ] 정리 중 `notification-drain` job이 오래 잡히지 않는가(한 번에 500건 상한)

### 5.3 규모

- [ ] 사용자 수백 명 규모에서 **결재선 검색**이 쓸 만한가 (`/users/page` 상한 3,000)
- [ ] 진행 중 요청 수백~수천 건에서 **업무함 첫 화면** 응답 시간
- [ ] **적용 스페이스 해제** 시 영향 집계가 느리지 않은가 *(P4 미해결 — 진행 중 요청마다 페이지 조회)*
- [ ] 진행 중 요청이 1,000건을 넘을 때 **독촉이 앞쪽 1,000건에만 가는 것**을 고객이 수용하는가
      → 기본 마감일을 설정하면 자연히 해소된다

### 5.4 기능 동선 (조직 실데이터로)

- [ ] 페이지 승인: 요청 → 승인 → 이력
- [ ] 영역 매크로 승인: 한 페이지에 독립 결재 2개 이상
- [ ] 순차 다단계 결재선 (3단계 이상)
- [ ] 그룹 결재선 (Confluence 그룹 / 직접 선택 그룹, 전원 승인)
- [ ] 반려 → 재승인 요청 → 이력 계보
- [ ] 회수(CANCELLED)
- [ ] 편집 후 재승인(stale 표시 → 원클릭 재승인)
- [ ] 위임 등록 → 대리인 업무함 노출 → 대리 결재 → **도장이 대리인 것 + `대리` 표시**
- [ ] 일괄 승인 (전체 선택 포함, 일부 실패 시 건별 사유)
- [ ] CSV 내보내기 (Excel에서 한글이 깨지지 않는가)
- [ ] 다크 모드 / 영어 로케일

### 5.5 권한·보안

- [ ] 일반 사용자가 `/plugins/servlet/approval-settings`에 직접 접근 → 403
- [ ] 남의 결재를 `actorKey`만 바꿔 승인 시도 → 403
- [ ] `X-Atlassian-Token` 없는 POST → 403
- [ ] 페이지 VIEW 권한이 없는 사용자에게 그 요청이 업무함에 보이지 않는가
- [ ] 설정 관리자(위임)로 지정된 일반 사용자가 설정 화면 전체를 다룰 수 있는가

## 6. 롤백

**되돌리기 쉬운 것**과 **되돌릴 수 없는 것**을 구분한다.

| 상황 | 방법 |
|------|------|
| 앱을 이전 버전으로 | UPM에서 이전 jar 재업로드. **승인 데이터와 매크로는 유지된다** |
| 기능만 끄고 싶다 | 설정에서 해당 스위치를 끈다(위임·독촉·일괄 승인·전자서명). 즉시 반영 |
| 특정 스페이스에서만 빼고 싶다 | 적용 스페이스에서 제외. 진행 중 건이 있으면 건수를 경고한다 |
| 앱 비활성화 | UPM에서 비활성화. **AO 테이블과 데이터는 남는다** |

### 되돌릴 수 없는 것

- **알림 정리로 지운 알림** — 보존 기간을 켜기 전에 값을 신중히 정한다
- **결재 이력** — 물리 삭제를 제공하지 않는다(감사 추적 보존이 설계 의도)
- **AO 스키마 다운그레이드** — 새 컬럼이 생긴 뒤 옛 jar로 내리면 그 컬럼은 남는다.
  동작에는 지장이 없으나 완전한 원복은 아니다

## 7. 알려진 한계 (고객에게 미리 알릴 것)

| 항목 | 내용 |
|------|------|
| Confluence 10 | 지원하지 않는다. 업그레이드 계획이 있으면 사전 협의 필요 |
| 독촉 상한 | 진행 중 요청이 1,000건을 넘으면 오래된 순 1,000건에만 독촉이 간다. 기본 마감일 설정으로 해소 |
| 헤더 배지 | 다른 사람이 만든 요청은 최대 2분 늦게 배지에 반영된다(세션 캐시) |
| 설정 전파 | 클러스터에서 설정 변경이 다른 노드에 최대 5초 늦게 보인다. 단, **결재 위임 스위치는 예외로 즉시 반영**된다 |
| 매크로 도입 | 기존 페이지에 영역 결재를 쓰려면 각 영역을 매크로로 감싸는 편집이 1회 필요하다 |
| 대리 결재와 서명 | 도장은 대리인 것이 찍힌다(`대리` 표시). 조직 감사 규정 확인 필요 |

## 8. 문제가 생기면 볼 곳

- **앱이 통째로 안 보인다** → jar에 도메인이 빠졌을 가능성. 2절의 게이트를 확인
- **REST가 전부 404** → 앱 비활성화 또는 plugin key 충돌(C9/C10 산출물을 함께 올린 경우)
- **알림이 안 온다** → 설정에서 알림·이메일이 켜져 있는지, 메일 서버가 설정돼 있는지,
  `notification-drain` job이 도는지
- **결재 버튼이 안 보인다** → 적용 스페이스에 포함됐는지, 그 사람이 결재선에 있는지,
  지금 그 사람 차례인지
- 서버 로그에서 `kr.dmove.confluence.approval` 네임스페이스를 본다
## 9. 다중 node 상태 전이 검증

- [ ] 서로 다른 두 node에서 같은 승인 요청에 대해 승인과 반려를 동시에 시도한다.
- [ ] 하나의 상태 전이만 저장되고, 다른 요청은 409 Conflict 또는 최신 상태 안내로 종료되는지 확인한다.
- [ ] cluster lock 서비스를 일시적으로 사용할 수 없을 때 승인·반려·회수·만료가 저장되지 않는지 확인한다.
- [ ] 위 상황에서 Confluence 재기동 없이 앱 상태를 확인하고, 필요하면 앱을 다시 활성화한 뒤 요청을 다시 시도할 수 있는지 확인한다.

cluster lock을 사용할 수 없는 동안 애드온은 상태 변경을 fail-closed로 차단한다. lock 없이 처리를 계속하지 않으므로
다중 node에서 승인 상태가 덮어써지는 것을 방지한다.
