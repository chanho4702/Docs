# 스트라드비전 개발·기능 제공 제안서

Moves Workforce + Moves Approval | 2026-10-16 | 고객 제안용 v3.3

## 1. 제안 내용

두 앱을 연결하여 **작업 입력 → 팀장 승인 → 승인 기록 보호 → 이력 확인 → 승인 기준 보고**를 하나의 업무 흐름으로 제공하겠습니다. Workforce는 조직·프로젝트·작업 입력·집계를, Approval은 승인·기간 마감·변경 통제·감사 이력을 담당합니다.

두 앱은 각각 외부 API를 제공하고 상대 앱의 API를 호출하는 형태로 개발합니다. 조직 정보는 Workforce에서, 승인과 잠금 정보는 Approval에서 확인하며, 실제 작업 기록은 Jira에 보관합니다. 앱 간 정보를 프로퍼티로 교환하는 방식은 이번 제안의 연동 방식에 포함하지 않습니다.

이 문서는 개발 방향과 제공할 기능을 설명하는 제안서입니다. API 경로·인증 세부 절차·데이터 구조·내부 모듈 설계는 별도 기술 구현 문서에서 다룹니다. 현재 확보한 검증 결과와 납품 전 추가 확인 항목은 [기능 검증 결과서](cloudjira--02_%EA%B8%B0%EB%8A%A5_%EA%B2%80%EC%A6%9D_%EA%B2%B0%EA%B3%BC%EC%84%9C.md)에 정리했습니다.

### 2.1 Atlassian 인프라와 Forge 앱

두 제품은 **Atlassian Forge 앱**으로 제공합니다. Jira 안에 표시되는 Custom UI에서 사용자가 입력·승인·조회하고, Forge bridge를 통해 호출되는 backend resolver와 Forge Functions에서 권한 확인 및 업무 처리를 수행합니다. 업무 서버와 앱 저장소는 Atlassian이 관리하는 Forge 환경을 사용하도록 구성하며, 핵심 승인 기능을 위해 별도 고객 운영 서버를 두는 구조는 제안하지 않습니다.

구성도의 Atlassian Cloud 영역은 논리적인 서비스 경계입니다. 브라우저의 UI 실행 위치, 물리 서버·네트워크·데이터센터 위치를 나타내는 배치도는 아닙니다. 입력·승인 요청은 앱 backend에서 처리하고, 전달 대기·후속 처리는 Forge의 이벤트·큐·배치 기능으로 이어갑니다.

### 2.2 앱별 Forge 저장소

| 저장 영역 | 제안에서의 용도 | 연결 원칙 |
| --- | --- | --- |
| Workforce Forge SQL | 업무 데이터와 보고·집계에 필요한 관계형 데이터 | Workforce backend에서 접근 |
| Workforce KVS / Custom Entity | 설정과 조직 등 기존 저장 모델 활용 | 상세 데이터 배치는 기술 설계에서 확정 |
| Approval Forge SQL | 승인 요청·결정·잠금·변경 이력 | 승인 판정의 기준 원장 |
| Approval KVS | 설정 및 처리 표식 등 보조 상태 | 승인 원장과 역할 구분 |
| Jira 데이터 | 실제 이슈와 작업 기록 원본 | 두 앱이 Jira REST API로 접근 |

Forge Hosted Storage를 사용하며, 각 앱의 저장소는 분리합니다. 상대 앱의 SQL을 직접 읽는 대신 소유 앱의 REST API에서 허용한 업무 결과를 조회합니다. Forge SQL은 설치별 데이터베이스를 제공하므로 고객 설치별 데이터 격리를 기반으로 구성합니다. [Forge Storage](https://developer.atlassian.com/platform/forge/storage-reference/), [Forge SQL](https://developer.atlassian.com/platform/forge/storage-reference/sql/)

### 2.3 외부 연결 가능한 REST API

각 앱에 **Forge app REST API (`apiRoute`)**를 마련하여 HTTPS 요청을 받도록 개발하겠습니다. Workforce는 조직·입력 조건 조회와 승인 결과 알림 수신을, Approval은 승인·잠금 조회와 변경 작업 조정을 제공합니다. 실제 상호 호출은 각 앱 backend에서 수행합니다. 구성도에서 API 상자 사이의 연결선은 이 업무 인터페이스의 상호 연결을 나타냅니다.

외부 고객 시스템도 허용된 API를 호출할 수 있는 형태로 확장합니다. SAP 등 외부 시스템은 Forge 저장소에 직접 접근하지 않고, 인증된 API를 통해 필요한 결과만 수신합니다. 외부 연계는 고객 측 호출 프로그램과 연결 설정이 필요하며, 이번 제안에서는 우선 파일 전달을 활용하고 자동 API 연계를 별도 개발 범위로 둡니다.

Forge app REST API는 현재 **Preview**이며, 공식 모델은 OAuth 2.0 3LO와 앱 정의 scope를 사용합니다. 사이트 관리자의 API 활성화 및 호출 권한 설정 후 Atlassian이 인증·scope를 확인하여 Forge 함수로 연결합니다. 앱 두 개를 설치하는 것만으로 상호 호출 권한이 자동 부여되지는 않습니다. 이 방식을 목표로 개발하고 양방향 호출·사용자 권한·무인 실행·인증 갱신은 통합 시험에서 확인합니다. [Forge app REST APIs](https://developer.atlassian.com/platform/forge/app-rest-apis/)

### 2.4 Jira API와 앱 API의 역할 구분

| 연결 | 목적 | 제공 형태 |
| --- | --- | --- |
| Custom UI → 자기 앱 backend | 입력·승인·조회 요청 | Forge bridge / resolver |
| Workforce backend ↔ Approval API | 승인·잠금 확인 및 변경 작업 조정 | 인증된 HTTPS REST API |
| Approval backend ↔ Workforce API | 조직·입력 조건 확인 및 승인 결과 전달 | 인증된 HTTPS REST API |
| 각 앱 backend → Jira REST API | 실제 작업 기록 조회·저장·통제 | 사용자 권한 기본, 승인된 시스템 처리만 앱 권한 |
| 각 앱 backend → 자기 Forge 저장소 | 업무 원장·설정 저장 | Forge SQL / KVS / Custom Entity |
| 외부 시스템 → 앱 REST API | 허용된 업무 결과 조회·연계 | 별도 연결·scope 설정 후 제공 |

앱 REST API는 우리가 제공하는 승인·조직 업무 기능의 진입점이고, Jira REST API는 Jira 원본을 다루는 연결입니다. API 접근 권한과 실제 사용자의 승인·편집 자격은 별도로 확인합니다. 현재 상태 확인이 실패하면 변경을 보류하는 업무 원칙도 그대로 적용합니다.

| 계획 초과 알림 | 계획 대비 실적 확인에 더해 수신자와 중복 처리를 갖춘 알림을 개발합니다. | 대상 관리자에게 필요한 알림 전달 |

### 3.1 DB에 보관하는 정보와 관리 주체

![DB 소유권과 앱별 처리 책임](images/07.png)

Workforce는 **조직·프로젝트·참여 정보**를 관리하고, Approval은 **승인·잠금·이력**을 관리합니다. 실제 작업 기록은 Jira에 보관합니다. 두 앱은 상대 DB에 직접 접근하지 않고 필요한 정보를 REST API로 주고받습니다.

| 저장소 | 보관 정보 | 관리 역할 |
| --- | --- | --- |
| Workforce DB — Forge SQL | 사용자·프로젝트·참여자·배정 정보 | 누가 어떤 프로젝트에서 일하는지 관리 |
| Workforce Forge 저장소 | 팀·팀장·조직 구조·업무 설정 | 승인자 선정과 입력 조건에 필요한 기준 제공 |
| Approval DB — Forge SQL | 승인 요청·결정·승인 당시 시간·잠금·변경 이력 | 승인 결과의 기준과 변경 통제 근거 보존 |
| Approval Forge 저장소 | 앱 설정·처리 보조 상태 | 승인 기능 및 연동 상태 관리 |
| Jira | 실제 작업 기록·이슈·작성자·작업일·기록 시간 | 양쪽 앱에서 사용하는 원본 보관 |

### 3.2 Workforce → Approval: 무엇을 제공하는가

Workforce는 대상 사용자·프로젝트·이슈를 기준으로 필요한 정보를 조회할 수 있는 REST API를 제공합니다.

| 제공 정보 | 제공할 때 | Approval에서의 활용 |
| --- | --- | --- |
| 사용자 소속 팀·담당 팀장 | 승인 요청 접수 및 승인자 확인 | 담당 승인자와 팀 범위 확인 |
| 프로젝트·사용자 참여 여부 | 대상 작업 기록 확인 | 해당 프로젝트의 승인 대상인지 확인 |
| 이슈에 적용되는 입력 조건 | 작성·변경 조건 확인 | 승인·마감 상태와 함께 처리 가능 여부 판단 |
| 저장된 작업 기록 참조 | 입력 후 승인 요청 연계 | Jira 원본을 확인하고 승인 대기로 접수 |
| 정보 갱신 시각 | 위 정보 조회 시 함께 제공 | 최신 조직·업무 기준인지 확인 |

급여·단가·개인 일정 상세처럼 승인에 필요 없는 정보는 제공 범위에서 제외합니다. 조직 정보를 받았다는 이유만으로 승인 권한을 부여하지 않고, Approval에서 실제 승인 자격과 Jira 접근 범위를 확인합니다.

### 3.3 Approval → Workforce: 무엇을 돌려주는가

Approval은 승인 결과가 바뀌면 Workforce에 알리고, 상세 결과는 REST API로 조회할 수 있도록 제공합니다.

| 제공 정보 | Workforce에서 제공하는 기능 |
| --- | --- |
| 건별 대기·승인·반려 상태 | 작업 기록에 상태 표시 |
| 승인 인정 시간·결정 시각 | 실제 기록 시간과 승인 인정 시간을 구분하여 집계 |
| 수정·삭제 가능 여부와 사유 | 변경 전 확인하고 불가한 작업은 중단·안내 |
| 기간 마감 및 통제 적용 상태 | 마감 안내와 적용 대기·오류 상태 표시 |
| 월·프로젝트별 승인 결과와 합계 | 보고서 및 SAP 전달 자료 생성 |

### 3.4 두 앱이 담당하는 역할

| Workforce | Approval |
| --- | --- |
| 조직·팀장·프로젝트·참여자 관리 | 조직 정보를 활용한 승인자 및 대상 확인 |
| 사용자 작업 입력과 현황 제공 | 건별 요청 접수·팀장 승인·반려·일괄 처리 |
| Approval에 변경 가능 여부 확인 후 입력 처리 | 승인·마감에 따른 변경 허용 여부 판정 |
| 승인 상태와 인정 시간 표시·집계 | 승인 당시 값·결정자·시각 및 변경 이력 보존 |
| 월별 보고·고객 전달 자료 생성 | 최신 승인·잠금·결과 정보를 API로 제공 |

Workforce는 조직과 보고의 기준을, Approval은 승인과 잠금의 기준을 담당합니다. 연결이 끊겨 최신 상태를 확인할 수 없으면 변경을 보류하고 반영 대기를 표시합니다.

### 3.5 정보의 제공 범위

| 대상 | 제공 범위 |
| --- | --- |
| 작성자 | 본인 기록·승인 상태·변경 가능 여부·허용된 이력 |
| 팀장 | 담당 팀의 승인 대상과 결정에 필요한 정보 |
| 관리자 | 연결 상태·전달 오류·통제 적용 및 재처리 상태 |
| 연동 앱 | 승인·입력·집계에 필요한 대상 정보 |
| 외부 시스템 / SAP | 합의한 월·프로젝트별 승인 자료와 전달 항목 |

외부 연결은 인증된 REST API로 제공하며, DB 전체를 공개하지 않습니다. 조회 대상과 사용자 역할에 맞춰 제공 범위를 제한합니다.

### 3.6 정보 흐름 예시

이는 제안하는 제공 흐름입니다. 실제 수행한 검증과 추가 확인 항목은 별도 검증 결과서에서 구분합니다.

## 4. 입력부터 승인 요청까지

작성자는 소속·프로젝트·입력 기간에 맞춰 시간을 기록합니다. 서버에서 현재 입력 가능 여부를 확인한 뒤 저장하고, 저장된 기록을 승인 요청과 연결합니다. 자동 요청을 사용하는 경우 저장 후 승인 대기로 접수하며, 팀장의 실제 결정을 거쳐 승인 완료로 전환합니다. 팀장을 확인할 수 없거나 저장 결과가 불명확하면 확인 대기로 표시합니다.

## 5. 승인 처리와 승인을 막는 조건

![팀장 승인과 승인 거부](images/04.png)

[이 도식 편집하기 — draw.io](editable/04.drawio)

승인 버튼을 누를 수 있는지뿐 아니라 실제 결정을 저장하는 시점에 승인 자격과 대상 상태를 확인하겠습니다. 지정 승인자가 아니거나 팀 범위를 벗어나면 거부하고, 대상이 변경 중이거나 최신 상태를 확인할 수 없으면 결정을 보류합니다. 이미 확정된 결정을 중복 요청으로 덮어쓰지 않습니다.

일괄 승인은 각 기록을 개별 확인하여 성공·거부·미처리 결과를 구분합니다. 승인 당시 시간·작업일·결정자·시각은 보존하며, 이후 원본이 달라지면 승인 당시 값을 조용히 바꾸는 대신 불일치 상태를 보여 줍니다.

## 6. 승인 후 변경 차단과 마감

![수정 삭제 및 마감 통제](images/05.png)

[이 도식 편집하기 — draw.io](editable/05.drawio)

승인된 기록과 마감 기간의 기록은 두 앱의 수정·삭제 처리에서 차단합니다. 날짜를 옮기는 수정은 변경 전후 기간을 함께 확인합니다. 다른 변경이 진행 중이거나 연결 장애로 현재 상태를 확인하지 못하면 변경을 보류합니다. 소명·재승인 요청만으로 기존 잠금을 해제하지 않습니다.

Jira 직접 REST·Automation 등은 앱 화면과 별도 경로입니다. 기존 기록에 대한 수정·삭제 제한 효과는 실제 고객 사용 경로와 계정으로 검증하여 적용 범위를 확정합니다. 외부 신규 생성은 모든 경로에서 사전 차단된다고 제시하지 않으며, 생성 후 감지·위반 표시·확정 집계 제외 등 후속 처리로 구분합니다.

## 7. 결과 전달과 연결 장애 처리

![승인 결과 반영과 장애 복구](images/06.png)

[이 도식 편집하기 — draw.io](editable/06.drawio)

승인 결정 후 Workforce에 변경을 전달하고 최신 결과를 반영합니다. 모든 대상의 수신과 합계 대조가 끝난 뒤 승인 기준 집계로 전환합니다. 중복 전달은 중복 집계를 만들지 않으며, 일부 누락이나 연결 장애가 있으면 반영 대기를 표시하고 복구 후 다시 대조합니다.

사용자는 승인 완료 여부, Jira 변경 제한 적용 여부, Workforce 반영 여부를 구분해 확인할 수 있습니다. 전달 실패가 이미 저장한 승인 결정을 취소하지 않도록 제공합니다.

### 7.1 Forge Storage에 승인·변경 이력 보관

Approval의 **Forge Storage에 승인 이력과 워크로그 변경 이력을 저장**하겠습니다. 승인·반려 결과뿐 아니라 기록의 생성·수정·삭제를 확인하여, 누가 어떤 기록을 언제 처리했는지 조회할 수 있도록 제공합니다. 이력 원장은 Forge SQL을 활용합니다.

| 보관 대상 | 저장할 정보 | 제공하는 기능 |
| --- | --- | --- |
| 승인 요청과 결정 | 대상 작업 기록, 요청·승인·반려, 승인자, 결정 시각 | 요청부터 결정까지의 처리 이력 조회 |
| 승인 당시 값 | 승인 당시 작업일·기록 시간과 대상 식별 정보 | 이후 원본 변경 시 승인 근거 대조 |
| 워크로그 업데이트 | 생성·수정·삭제 구분, 확인 가능한 행위자·시각, 변경 전후 작업일·시간 | 변경 내역 추적 및 감사 자료 제공 |
| 통제 처리 | 잠금·제한 적용, 해제 등 확인 가능한 처리 내역 | 승인 결과와 실제 통제 상태 확인 |
| 워크로그 설명 | 설명의 일부와 변경 여부 확인에 필요한 정보 | 변경 맥락의 부분 확인 |

작성자와 승인자는 허용된 대상의 이력을 확인하며, 화면 조회와 파일 내보내기에 같은 접근 범위를 적용합니다. 승인 후 기록이 달라져도 승인 당시 값을 덮어쓰지 않고 변경 사실을 구분하여 표시합니다. 행위자나 이전 값을 확인할 수 없는 경우에는 확인 불가로 남깁니다.

### 7.2 워크로그 설명은 부분 지원

워크로그 **Description은 이력에서 부분 보존·조회하는 범위로 제공**합니다. 저장량을 고려하여 설명의 일부를 보존하고 변경 여부를 확인할 수 있게 하되, 모든 변경 시점의 전체 설명 원문을 보관하거나 복원하는 기능으로 제시하지 않습니다.

현재 Jira에서 열람 가능한 설명과 Approval이 과거 이력으로 보관한 설명은 구분합니다. Jira에서 원본이 바뀌거나 삭제된 경우, 부분 보존한 이력만으로 전체 문장을 복원할 수는 없습니다. 설명 보존 범위와 표시 길이는 고객의 감사 요구와 예상 데이터량을 확인하여 정합니다.

### 7.3 주기적인 이력 파일 제공

Forge Storage의 저장공간 한도를 고려해 **누적 이력을 주기적으로 파일로 내보내는 기능**을 개발하겠습니다. 사용자는 최근 이력을 앱에서 확인하고, 장기 보관 자료는 제공된 파일로 관리할 수 있습니다.

| 항목 | 제공 방안 |
| --- | --- |
| 파일 대상 | 기간별 승인·반려 이력, 워크로그 변경 이력, 필요한 통제 내역 |
| 파일 구성 | 대상 기간, 생성 시각, 기록 식별 정보, 처리자·처리 시각, 변경 전후 값, 건수 등 |
| 설명 포함 범위 | 앱에서 보존한 부분 설명과 변경 정보만 포함 |
| 제공 방식 | 정기 파일 생성 후 관리자 다운로드 제공. 지정 외부 저장소로의 자동 전달은 연결 범위를 확정해 구현 |
| 대사 | 앱 이력과 파일의 대상 기간·건수·승인 시간 및 대상 식별 정보 대조 |
| 미완료 처리 | 파일 생성·전달 실패 또는 누락 시 대기·오류를 표시하고 원본을 보존한 채 재처리 |

내보내기 주기, 앱 내 온라인 보관 기간, 파일 형식과 보관 위치는 적용 규모에 맞춰 확정합니다. 이번 제안에서는 정기 파일 제공 방향을 제시하며, 자동 내보내기가 이미 구현·검증 완료되었다고 표시하지 않습니다.

### 7.4 저장공간 관리와 이력 정리

파일 생성만으로 앱의 저장공간이 줄어들지는 않습니다. **파일 생성·내용 대조·보관 확인이 끝난 뒤**, 합의한 보관 기준에 따라 정리 가능한 이력을 관리하도록 개발합니다. 현재 승인·잠금 판단과 진행 중인 요청에 필요한 핵심 근거는 유지합니다.

사용자는 앱에서 조회할 수 있는 기간과 파일로 보관한 기간을 구분할 수 있어야 합니다. 파일 생성 실패·전달 미확인·건수 불일치 상태에서는 원본을 먼저 삭제하지 않습니다. 정리 대상과 보관 기간은 실제 누적량을 확인해 정하며, 모든 이력을 내보낸 뒤 즉시 삭제하는 방식으로 제시하지 않습니다.

### 7.5 이력 관리의 제공 전 검증

| 검증 항목 | 확인할 내용 |
| --- | --- |
| 승인·반려 이력 | 대상 기록·결정자·시각·승인 당시 시간이 화면과 저장 이력에서 일치 |
| 워크로그 업데이트 | 생성·수정·삭제 후 변경 전후 값과 확인 가능한 행위자를 조회 |
| 설명 부분 지원 | 보존 범위까지만 표시되고 전체 원문 복원으로 오인되지 않음 |
| 정기 파일 생성 | 지정 기간의 이력이 빠짐없이 포함되고 앱 조회와 건수·내용 일치 |
| 저장공간 정리 | 보관 확인 전 원본 유지, 정리 후 현재 승인·잠금 기능 유지 |

위 검증의 실제 결과와 증거는 수행 후 작성합니다. 기존 자동 테스트 결과를 정기 내보내기·고객 환경 검증의 성공 결과로 대신하지 않습니다.
