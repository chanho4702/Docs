# Approval 워크로그 승인 UI·UX 흐름

2026-10-13. `frontend-design`과 사용자 추가 UX 요구 적용. Jira/Atlaskit 업무형 미니멀을 유지한다. 외부 폰트·새 UI 라이브러리·장식·KPI 카드를 추가하지 않는다. 화면마다 주 동작 하나를 먼저 보이게 하며 실제 backend 보고서의 DTO가 이 문서보다 우선한다.

## 1. 이슈 패널: 입력 → 상태 목록 → 상세·이력

`entries/issue.jsx`의 일반/상태/필드 승인 개요를 기본 흐름에서 제외하고 워크로그 진입점 하나로 모은다. 전체 폭 패널은 입력 폼 다음 기록 목록이다. 좁은 우측 context는 요약과 패널 열기만 제공한다. Workforce Jira 이슈 탭에는 두 번째 입력기를 두지 않는다.

- 입력은 일자·시간·설명이다. 기본 승인자와 `변경`을 같은 요청 흐름에 둔다. 주 버튼은 `저장`, 안내는 “저장하면 승인 요청이 자동으로 접수됩니다.” 한 줄이다. 저장 API가 승인자 입력을 지원하지 않으면 추측해 보내지 않고 저장된 행에서 변경한다.
- 목록은 일자·시간·작성자·승인 상태·`상세`가 기본이다. 잠금은 상태 옆 짧은 문구로 표시하고 배지를 쌓지 않는다. 사전 승인/인증/내 승인 요청 표를 아래에 또 붙이지 않는다. 요청이 필요한 행만 `승인 요청`을 보조 동작으로 제공한다.
- 상세는 작업 요약 → 현재 승인 상태와 다음 행동 → 승인·변경 이력 순서다. 누가 언제 승인했는지와 반려 사유는 본문에서 읽게 한다. 확인되지 않은 사람·시각은 추정하지 않는다. 기술 진단·전체 정책 설정은 넣지 않는다.
- 기존 `WorklogTab`, `WorklogDetailModal`, `WorklogHistoryPanel`, `PersonAvatar`, `ModalLayout`, `SectionMessage`, `CursorPagingTable`을 재사용한다. snapshot은 표시용이고 동작 가능 여부는 최신 서버 응답을 따른다.

## 2. 상태와 다음 행동

| 상태 | 문구·정보 | 다음 행동 |
|---|---|---|
| 저장 전 | 저장하면 승인 요청이 자동 접수됩니다. | `저장`; 처리 중 중복 클릭 방지 |
| 저장·자동 요청 성공 | 저장됨 · 승인 대기 / 승인자 | 새 행 반영, 입력 폼 초기화 |
| 저장 성공·접수 지연 | 기록은 저장되었습니다. 승인 요청을 확인 중입니다. | `새로고침`; 다시 저장하도록 유도하지 않음 |
| 승인자 부재 | 승인자를 선택해야 요청할 수 있습니다. | `승인자 선택` → `승인 요청` |
| 승인 대기 | 승인 대기 / 승인자 | 상세에서 `승인자 변경`; 서버가 허용할 때만 취소·재접수 |
| 반려 | 반려 / 결정자·시각·사유 | `다시 승인 요청`; 수정은 서버 허용 시만 |
| 승인 | 승인됨 / 결정자·시각 / 수정 불가 | 보조 동작 `소명·재승인 요청` |
| 기간 마감 | 승인 기간 마감 / 수정 불가 | 승인 여부와 별도 표시; 허용 시 소명 |
| 소명 중 | 소명 검토 중 / 기존 승인·잠금 유지 | 중복 접수 방지, 요청 이력 열기 |
| 조회 실패 | 상태를 확인할 수 없습니다. | `다시 확인`; 확인 전 쓰기 활성화 금지 |

요청 폼은 승인자와 사유만 둔다. `requestWorklogApproval({issueId,worklogId,approverId?,reason?})`, `appealWorklogApproval`은 같은 입력에 reason 필수다. 후보는 `listWorklogApprovalCandidates({issueId,query?})`로 조회한다. 기본값과 동작 노출은 `getWorklogCertification`의 `approval/canRequest/canAppeal/approvers/defaultApproverIds/locked/lockReason`을 따른다. 클라이언트가 팀장이나 수정 권한을 추론하지 않는다. 소명 제출에 “검토 중에도 기존 승인과 잠금은 유지됩니다.”를 한 번 안내한다.

## 3. 승인자 업무함과 설정

업무함 기본은 승인 대기 워크로그다. 작성자·작업일·이슈·시간·요청 종류를 비교하고 행 선택 시 `선택 N건 승인`이 주 동작이 된다. 전체 선택은 현재 불러온 승인 가능 행에 적용하며 범위를 명시한다. 기존 InboxTable과 일괄 결정 흐름을 재사용한다.

처리 후 “12건 승인, 2건 처리 실패”처럼 실제 결과를 표시한다. 성공 행은 선택 해제, 실패 행과 이유는 유지하여 실패분만 재시도한다. 서버 remaining은 “계속 처리”로 이어가며 전체 성공으로 표시하지 않는다. 소명 요청은 텍스트 표식으로 구분한다.

설정 기본 노출은 자동 승인 요청·승인 마감일·승인 후 수정 금지 세 항목이다. 연동 정책의 관리 위치는 “Workforce 프로젝트 설정”으로 표시한다. 사전 승인·인증 세부·진단은 고급 또는 과거 기록에 두고 상태 변경 승인 토글은 기본 기능에서 제외한다. 기존 `SettingsSection/SettingsRows/SettingsPageIntro`를 재사용한다.

## 4. 좁은 iframe·키보드·피드백 완료 기준

- 320px·480px·전체 폭에서 입력은 필요 시 한 열, 버튼은 줄바꿈한다. 표는 보조 열보다 날짜·시간·상태·상세를 우선한다. 긴 사유는 줄바꿈한다.
- 기존 body margin 0 유지, 여백은 container padding. 모달에 `100vh`나 고정 높이를 넣지 않는다. 하단 버튼까지 스크롤로 도달해야 한다.
- label을 placeholder로 대체하지 않는다. 키보드로 입력·후보 검색·행 선택·상세·제출을 조작할 수 있어야 한다. 모달 종료 시 시작 버튼에 초점 복구, 오류 시 첫 오류 필드로 이동한다. 검색 Enter가 전체 제출을 유발하지 않게 한다.
- 상태는 색상과 텍스트를 함께 사용한다. 성공/처리 중은 접근 가능한 status 알림, 실패는 오류 문구로 제공한다. 로딩은 해당 영역만 대체하고 실패 시 입력값을 보존한다.
- 빈 목록은 “아직 작성한 워크로그가 없습니다.”와 기존 입력 동작 하나로 충분하다. 저장·결정·소명·모달 종료 후 queryKey factory의 목록·상세·이력·업무함을 무효화한다. 별도 iframe에서 돌아와도 최신 상태를 보여 준다.

이 문서는 흐름 설계만 보완한다. 코드·빌드·테스트는 수행하지 않았다.
