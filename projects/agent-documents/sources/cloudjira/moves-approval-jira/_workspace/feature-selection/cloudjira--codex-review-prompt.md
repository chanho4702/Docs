## 리더(Claude)의 진단과 제안
진단: 제품에는 독립된 선택 축이 셋 있는데 설정 어디에도 "선택"으로 보이지 않는다.
1. 어떤 기능을 쓰나 — 이슈 승인(상태 변경·필드 변경) / 타임시트(워크로그) 승인 / 둘 다. **현재 명시적 스위치가 없다.** 타임시트는 팀 명부에 팀이 있으면 돌고, 이슈 승인은 프로젝트에 규칙이 있으면 돈다. 안 쓰는 기능의 메뉴도 전부 보인다.
2. 어느 프로젝트에 적용하나 — "적용 프로젝트" 메뉴. `src/resolver/transition/projectEnablement.js` 기준 **이슈 승인(+워크로그 이력 범위)에만** 걸리고, 타임시트 승인은 사람×월 단위라 프로젝트 범위가 아니다.
3. 타임시트 결재자 원천 — 우리 팀 명부 / 워크포스 지정 팀장(`src/resolver/timesheet/TimesheetRouting.js`, `TeamScope.js`: 워크포스가 정한 사람이 1단계, 없으면 명부 팀장).

제안:
- 설정 > 일반 맨 위에 **"기능 선택"** 페이지. 세 질문을 평문으로: "이슈 상태 변경 승인을 사용합니다", "타임시트 승인을 사용합니다", "타임시트 결재자는 워크포스에서 지정한 팀장이 합니다".
- 끈 기능의 메뉴 묶음(이슈 승인 / 워크로그·타임시트)은 통째로 접는다(운영 모드와 같은 방식, 저장값 유지). 업무함의 해당 탭·제출 버튼도 숨긴다.
- 라벨 전부 평문화. 예: "전환 승인 강제(끄면 모든 validator 가 통과)" → 비상 해제 섹션으로 분리 + 확인 모달.
- 백엔드: "타임시트 승인 사용" 정책 키 신설(`timesheetApprovalEnabled`?). 이슈 승인 쪽은 기존 `transitionApprovalEnabled`(비상 스위치, 끄면 validator 전부 통과)를 기능 스위치로 **겸용**하는 안.

## 검토해 달라
1. **모델 검증**: 위 세 축 진단이 코드와 맞나? 빠진 축이나 잘못 묶은 것이 있나(예: 필드 변경 승인·이슈 일반 승인(`issue-approval`)·워크로그 인증(certification)·워크로그 통제가 "이슈 승인/타임시트" 둘로 깨끗히 갈리나?). 적용 프로젝트가 실제로 어디까지 영향을 주는지 코드로 확인(`isProjectEnabled` 소비처 전수).
2. **`transitionApprovalEnabled` 겸용의 위험**: 비상 해제 스위치와 기능 사용 스위치를 하나로 두면 생기는 문제(감사 기록·의미 혼동·validator 가 이미 걸린 워크플로에서 "기능 끔"의 사용자 경험). 분리해야 한다면 어떤 키·어떤 동작.
3. **"타임시트 승인 끔"의 정의**: 꺼졌을 때 서버가 막아야 하는 경로(제출·결재·기간 마감·자동 마감 스윕·워크포스 게시·시간 추적 제공자 화면·워크로그 통제)를 코드에서 전수 조사해 목록으로. 각각 "막는다 / 그대로 둔다 / 숨긴다"를 권고. 유휴 SQL 예산(`idleSqlBudget.test.js`)에 영향이 있나.
4. **UX 대안**: "기능 선택" 페이지 vs 첫 설치 온보딩(위저드) vs 각 묶음 머리의 토글. 관리자가 Jira 설정 > 앱 에서 처음 들어왔을 때 가장 덜 헷갈리는 형태는? 메뉴 묶음을 통째로 접는 것이 맞는지, 아니면 비활성 표시로 남기는 것이 나은지(운영 모드와의 일관성 포함).
5. **라벨 평문화**: `locales/kr/policy.json`, `timesheet.json`, `worklogControl.json`, `workforce.json` 에서 비개발자가 이해하기 어려운 라벨 상위 15개를 뽑고 대체 문구를 제안(한 줄씩).
6. **구현 비용·순서**: 백엔드 변경 최소안과 전체안, 각각 영향 파일 수 추정, 권장 순서.
