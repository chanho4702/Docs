**판정표**

UTF-8로 이전 보고서·보완 설계·두 저장소 코드를 대조했다. 아래 ‘해결’은 **설계 보완의 적정성**이며 구현 완료를 뜻하지 않는다. `D`는 설계, `A`는 승인 앱, `WF`는 워크포스다.

| N1 — 사전 승인 표식 위조 | **해결** | D §5.7은 프로퍼티를 배제하고 DB의 worklog·이슈·작성자·APPLIED·승인 상태·작업 날짜를 대조한다. 기존 entry 스키마로 구현 가능하다. 같은 날짜의 시간 변경을 허용하는 것은 명시된 보장 범위다. |

**새 지적**

1. **N8 — P1: 최종 보장인 제출 대조에 설정의 최초·최신 수신 계약이 없다**
   - **근거:** D §5.1의 강제 재조회 대상에 타임시트 제출이 없고, §5.7·§15는 설정 캐시 SELECT와 승인 entry 대조만 명시한다. 현재 [WorklogPolicyResolver.js:15](/C:/CloudJira/moves-approval-jira/src/resolver/worklogPolicy/WorklogPolicyResolver.js:15)와 [WorklogPolicyRepository.js:22](/C:/CloudJira/moves-approval-jira/src/resolver/worklogPolicy/WorklogPolicyRepository.js:22)는 DB 캐시만 읽는다.
   - **재현:** 워크포스에서 설정 게시 → 승인 앱 미접속·이벤트 관찰 없음 → Jira에서 직접 작성 → 타임시트 제출. 설정이 미수신이면 새 제한을 모르고, 기존 캐시가 있으면 변경 전 허용값으로 대조할 수 있다.
   - **필요 보완:** 제출·미리보기의 이슈별 설정 수신, 최신성 기준, 미해결 시 제출 거부를 명시한다. 이벤트 0건·최초 제출·허용→제한 변경 사례를 추가해야 한다. 캐시만으로는 “이벤트 관찰 없이도 최종 보장”을 주장할 수 없다.

2. **N9 — P1: ctl 게시 대상 1,000건 제한으로 일부 이슈의 넘김이 영구 누락될 수 있다**
   - **근거:** D §15는 이슈 5,000건을 가정하지만 재사용하는 [WorklogControlCtl.js:35](/C:/CloudJira/moves-approval-jira/src/resolver/worklogControl/WorklogControlCtl.js:35)의 조회는 `LIMIT 1000`이고 정렬·커서가 없다. `targets()`와 `bodyFor()`가 모두 이를 사용한다.
   - **영향:** 프로젝트 공통 ctl이 없는 구성에서는 초과 이슈에 `ch`·`rx`가 게시되지 않아 직접 작성하거나 승인 설정 편집이 열리지 않는다. WF의 프로젝트 신호는 모든 구성에서 존재하지 않는다([ApprovalLinkAdminService.js:144](/C:/CloudJira/moves-workforce/src/resolver/approvalLink/ApprovalLinkAdminService.js:144)).
   - **필요 보완:** 대상 전체를 예산 내 커서로 순회하고 다음 배치가 이어받도록 한다. 1,001건 이상·프로젝트 ctl 없음·APP 토글 후 전체 수렴을 검증해야 한다.

3. **N10 — P2: 직속 편집 범위와 조직 모드 활성화 기준이 아직 이중 명세다**
   - D §4.2·§8.3은 Q15 직속 기준을 권고하지만 W1은 후손 팀 포함을 기대한다.
   - D §8.3은 `workforceLinkEnabled + 신뢰 키`를 조직 모드 기준으로 쓰고, §9·§17.1은 별도 `workforceTeamSource` 토글을 둔다.
   - 최종 기준을 하나로 확정하고 권한·Routing·TeamScope·테스트를 맞춰야 한다.

**결론**

**착수 불가: 확정된 직접 작성 복귀 금지와 충돌하고, 게시 충돌 시 제한 미적용·조직 권한의 무기한 유지·제출 설정 미수신·ctl 대상 누락이 남아 있다.**

기억 키·cap·알림·감사 대기 장치 제거 자체는 합리적이다. 그러나 사후 표시가 사전 차단을 대신하거나, 오래된 두 문서의 인가를 무기한 인정하는 것을 ‘보장 범위 밖’으로 돌리는 것은 수용하기 어렵다. 해당 경계를 보완한 뒤 구현에 착수해야 한다.

코드·파일 수정, 테스트·빌드·배포는 하지 않았다. 계약 7파일은 현재 두 저장소에서 raw byte 기준 모두 동일하다.
