# issue-approval — 이슈 일반 승인(검토·결재) 화면 공개

> 로드맵 7번(2026-10-04 사용자 지시). QUESTIONS Q1 답: **연다**.
> core-port 에서 `TargetKind.ISSUE` + `IssueTargetAdapter`(참조 어댑터)와 resolver 는 이미 있다. 이번 일은 **제품 기능으로 노출**하는 것이다.

## 목표

"이 이슈를 검토·결재해 주세요" — 상태 변경과 무관한 일반 승인. Confluence 판의 페이지 승인과 같은 수준(결재선·마감·참조·메시지·서명/PIN·위임·증명서).

## 해야 할 것

1. **진입점**: 이슈 ••• 메뉴(`jira:issueAction`)·이슈 패널에서 "승인 요청" — transition-approval 이 쓰는 modal/issue 엔트리를 재사용하고, 요청 종류(일반 승인 / 상태 변경 승인)를 고르게 한다. 상태 변경 규칙이 없는 이슈에서도 일반 승인은 가능.
2. **결재선**: 요청자가 직접 구성(`ApprovalLineEditor`) 또는 Flow 선택 — 상태 변경 승인(규칙 Flow 고정, Q56)과 다르다는 점을 화면에서 구분.
3. **열린 요청 하나**: `ISSUE:{issueId}` (이미 예약). 상태 변경 승인(`TRANSITION:…`)과는 별개 대상이라 동시에 열릴 수 있다.
4. **요청 이후 수정**: Confluence 판 원칙("편집은 요청을 죽이지 않는다") 그대로 — 요청 이후 이슈가 수정되면 상세·이슈 요약에 "요청 이후 수정됨" 안내, 요청자는 **다시 상신**(이전 요청 SUPERSEDED, `prev_request_id`). 수정 판단 기준(이슈 `updated` 시각 또는 changelog)과 비용은 설계에서 정한다.
5. **표시**: 이슈 우측 요약(issueContext)에 일반 승인 상태도 함께. 업무함·알림·증명서는 대상 종류만 추가.
6. **권한**: 요청 `{issue:'edit'}`, 조회·결정은 이슈 열람 권한 + 결재자 본인(형제 resolver 전부 같은 범위).

## 완료 기준

테스트·빌드 통과, 상태 변경 승인과 일반 승인이 같은 이슈에 동시에 있어도 서로의 scopeKey·요약 표시가 섞이지 않음을 테스트로 증명.
