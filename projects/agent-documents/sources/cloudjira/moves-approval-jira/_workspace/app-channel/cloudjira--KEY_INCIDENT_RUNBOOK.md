| 항목 | 내용 |
|---|---|
| 대상 | 승인 앱 ↔ 워크포스 Web Trigger 채널의 키·주소·연결 사고 |
| 작성일 | 2026-10-19 |
| 함께 보는 문서 | `KEY_MANAGEMENT_PRINCIPLES.md`(관리 원칙·키 대장), 설계서 `_workspace/workforce-channel-rest/01_architect_design.md` §2.2·§2.6 |
| 원칙 | **의심되면 먼저 막는다.** 막으면 연동은 안전한 쪽으로 멈추고(기존 잠금 유지, 연동 이슈 쓰기는 승인 앱 화면으로 넘김) 데이터는 바뀌지 않는다 |

## 0. 이 문서를 여는 경우

- 서명 키(seed)가 파일·커밋·채팅·스크린샷 등에 남은 것을 발견
- 폐기한 kid 로 서명된 요청이 들어옴
- 서명은 맞는데 요청자 권한 거부(`ACTOR_NO_ACCESS`·`ACTOR_INACTIVE`)·속도 제한(`RATE_LIMITED`)이 급증
- 송신·수신 대조에서 받은 수 > 상대가 보낸 수 (T1 구현 후)
- Forge 앱 기여자 계정 탈취·분실 의심, 퇴사자가 기여자로 남아 있음
- Web Trigger 주소·연결 코드가 외부에 노출
- 특정 사이트 호출이 폭주하거나 그 사이트에서 429(호출 한도) 발생

## 3. 시나리오별 절차

### A. 서명 키 유출 (S1)

예: `wf-prd-1` seed 노출. 아래 `<old>`=유출 kid, `<new>`=새 kid(예: `wf-prd-2`), 서명 앱=유출 키를 쓰는 앱, 받는 앱=상대 앱.

**1) 차단 — 받는 앱이 유출 키를 믿지 않게 한다**

| 방법 | 절차 | 특징 |
|---|---|---|
| ① 신뢰 목록으로 즉시 차단 (먼저 실행) | 받는 앱에 `forge variables set -e production MOVES_LINK_TRUSTED_KIDS <new>` → `forge deploy -e production` | `<new>` 는 아직 키링에 없으므로 신뢰 집합이 비어 **그 방향 연동 전체가 멈춘다**(fail-close). 코드 수정 없이 가장 빠르다 |
| ② 키링으로 폐기 | `keyring.js` 의 `<old>` 에 `notAfter: <지금 epoch ms>` → 승인 앱 원본 수정·워크포스로 복사(`SHARED_READY.md` 해시 갱신) → 두 앱 배포 | 영구 조치. 이후 `<old>` 서명은 시각 검사로 거부 |

- 환경 변수 변경이 재배포 없이 반영되는지는 **미검증**이다. 재배포까지 하는 것을 기본으로 한다.
- 키는 모든 고객 사이트가 함께 쓰므로 차단도 **모든 사이트에 동시에** 적용된다. 고객별로 나눠 막을 수 없다.

**2) 복구 — 새 키로 바꾼다 (끊김 순서 주의)**

| 순서 | 할 일 | 하는 사람 |
|---|---|---|
| 1 | `node scripts/workforce-link/gen-key.mjs <new>` (관리 원칙 P1~P3 준수) | 키 관리자 |
| 2 | 서명 앱: `forge variables set --encrypt -e production MOVES_LINK_SIGNING_KEY <seed>`, `forge variables set -e production MOVES_LINK_SIGNING_KID <new>` → 터미널 지움 | 키 관리자 |
| 3 | `keyring.js` 에 `<new>: { x, env: 'prd', notAfter: null }` 추가(②를 안 했으면 `<old>` 의 `notAfter` 도 함께), 두 리포 동일 복사 | 키 관리자 |
| 4 | **받는 앱 먼저 배포**, 그다음 서명 앱 배포 | 배포 담당 |
| 5 | 받는 앱의 `MOVES_LINK_TRUSTED_KIDS` 삭제(미설정 = prd 키만) → 재배포 | 배포 담당 |
| 6 | 개발 사이트와 고객 사이트 1곳 이상에서 연결 확인(설정 화면 "연결 확인" = `pingWorkforce`/`pingApproval`) + 공개키 지문 대조 | 배포 담당 + 키 관리자 |
| 7 | 키 대장 갱신: `<old>` 폐기·사유·시각, `<new>` 생성 | 키 관리자 |

**3) 조사**

| 항목 | 방법 |
|---|---|
| 유출 기간 | 유출 가능 시점(커밋 시각, 채팅 전송 시각 등) ~ 차단 시각 |
| 처리된 작업 | 감사 이벤트 중 `detail.via = 'WORKFORCE_CHANNEL'` 이고 `detail.kid = <old>` 인 것을 기간으로 추출 → 사이트·op·actor 별 집계 (**추출 경로 준비 필요** — 관리 원칙 7장) |
| 이상 요청 판별 | 같은 기간 서명 앱의 정상 송신과 비교(T1 구현 후 자동). 평소 없던 시간대·op·actor 조합, 같은 actor 의 권한 거부 연속 |
| 노출 데이터 범위 | 받는 작업에 승인·반려·삭제 실행이 없으므로 **조회 응답의 범위**를 확인한다. 각 요청은 actor 권한으로 좁혀졌으므로 "그 사용자가 볼 수 있던 범위"가 상한 |
| 유출 경로 | 커밋 → 리포 공개 여부·포크·CI 로그 / 채팅 → 수신자·외부 연동 여부 / 기여자 계정 → G 시나리오 병행 |

커밋으로 유출됐다면 **이력을 지워도 키는 교체한다.** 이력 정리는 교체 뒤에 한다.

**4) 고지** — 6장.

### B. 폐기한 키로 서명된 요청 감지 (S1)

- 폐기 전에 키가 이미 새어 나갔다는 뜻이다. 이미 거부되고 있으므로 차단은 되어 있다.
- 현재 서명 키도 같은 경로로 유출됐을 수 있다. 유출 경로가 확인될 때까지 **현재 키도 A 절차로 교체**한다.
- A 의 조사를 폐기 시점 이전 기간까지 넓힌다.

### C. Web Trigger 주소 노출 (S3, 폭주가 있으면 S2)

| 순서 | 할 일 | 하는 사람 |
|---|---|---|
| 1 | 해당 고객사 관리자에게 주소 바꾸기 안내: 승인 앱 설정 > 워크포스 연동 > 주소 바꾸기(`rotateWorkforceChannelUrl`), 워크포스는 승인 앱 연동 > 주소 바꾸기(`rotateApprovalChannelUrl`) | 고객 관리자(우리가 안내) |
| 2 | 앱이 새 주소를 만들고 상대 앱에 서명된 `sys.rekey` 로 알린 뒤 옛 주소를 지운다. 연결 확인으로 마무리 | 자동 |
| 3 | 노출 경로 기록(관리 원칙 P19~P20 위반 여부) | 우리 |

주소는 고객 사이트 단위라 공급자가 대신 바꿀 수 없다. 고객 관리자 권한이 필요하다.

### D. 연결 코드 노출 (S3)

| 상황 | 조치 |
|---|---|
| 아직 사용 전 | 30분이 지나면 무효. 급하면 새 코드를 만들고 새 코드로 연결한다(옛 대기 코드 처리 방식은 확인 필요) |
| 이미 연결됨 | 코드는 같은 사이트의 상대 앱에서만 쓸 수 있으므로 실제 피해 가능성은 낮다. 그래도 연결 상대가 의도한 앱인지 의심되면 E 절차(해제 후 재연결) |

### E. 특정 사이트 연결 오용 의심 (S2)

| 순서 | 할 일 | 하는 사람 |
|---|---|---|
| 1 | 즉시 멈춤이 필요하면 고객 관리자가 연동 스위치를 끈다(받는 앱이 관리 작업 외 모든 요청을 `LINK_DISABLED` 로 거부) | 고객 관리자 |
| 2 | 연결 해제(`unpairWorkforce` / `unpairApproval`) 후 새 연결 코드로 재연결 → 새 `linkId`, 옛 연결 요청 즉시 거부 | 고객 관리자 |
| 3 | 해당 사이트만 A 의 조사 방법으로 기간 추출. 같은 시기 다른 사이트에도 같은 패턴이 있으면 **키 유출(A)로 격상** | 우리 |

### F. 호출 폭주·가용성 (S2)

| 순서 | 할 일 |
|---|---|
| 1 | 거부 사유 확인: 서명 실패·미등록 키가 대부분이면 주소 노출(C), 서명 통과 후 권한 거부·속도 제한이면 키 유출 의심(A 로 격상) |
| 2 | 해당 사이트에서 429(설치당 분당 7,000회·초당 300회 한도) 여부를 Forge 개발자 콘솔·사용자 신고로 확인 |
| 3 | C 절차로 주소 바꾸기. 옛 주소 호출은 더 이상 앱 함수에 닿지 않는다 |

### G. Forge 앱 기여자 계정 탈취·퇴사자 잔존 (S1)

배포 권한이 있으면 코드를 바꿔 seed 를 읽을 수 있으므로 **키 유출로 간주**한다.

| 순서 | 할 일 |
|---|---|
| 1 | Developer console 에서 해당 계정을 두 앱 기여자에서 제거, Atlassian 계정 비밀번호·2단계 인증 재설정 |
| 2 | 두 앱의 배포 이력에서 그 계정이 한 배포·환경 변수 변경이 있는지 확인. 의심 배포가 있으면 알려진 정상 커밋으로 재배포 |
| 3 | 그 계정이 접근할 수 있던 **모든 환경의 seed** 를 A 절차로 교체. 외부 API OAuth 클라이언트 비밀도 재발급 |
| 4 | 리포·CI 접근 권한도 함께 회수 |

### H. 개발·검증 키 유출 (S3)

- production 은 dev·stg 키를 신뢰하지 않으므로(미설정 = prd 만) 운영 영향은 없다.
- 해당 환경에서 A 절차를 그대로 연습 삼아 실행하고 키 대장을 갱신한다.
- production 에 `MOVES_LINK_TRUSTED_KIDS` 가 설정돼 있지 않은지 함께 확인한다.

## 4. 명령 모음

```text
# 키 생성 (사람만, 출력은 화면에서만 쓰고 지운다)
node scripts/workforce-link/gen-key.mjs <kid>

# 서명 앱: 새 seed·kid
forge variables set --encrypt -e production MOVES_LINK_SIGNING_KEY <seed>
forge variables set -e production MOVES_LINK_SIGNING_KID <kid>

# 받는 앱: 신뢰 목록 일시 지정(차단) / 해제
forge variables set -e production MOVES_LINK_TRUSTED_KIDS <kid>
forge variables unset -e production MOVES_LINK_TRUSTED_KIDS

# 현재 값 확인 (암호화 값은 표시되지 않는다)
forge variables list -e production

# 배포 (keyring 변경은 코드 변경이라 manifest 변경 없이 배포)
forge deploy -e production
```

- 두 리포 각각에서 실행한다. 승인 앱 `C:\CloudJira\moves-approval-jira`, 워크포스 `C:\CloudJira\moves-workforce`.
- `keyring.js` 는 공유 파일이다. 승인 앱에서 고치고 워크포스로 바이트 그대로 복사한 뒤 `SHARED_READY.md` 해시를 갱신한다.

## 5. 차단·복구 후 확인 목록

- [ ] 두 앱 `forge variables list -e production` 에서 `MOVES_LINK_SIGNING_KID` 가 새 kid, `MOVES_LINK_TRUSTED_KIDS` 없음
- [ ] 두 앱 `keyring.js` 가 같은 해시, 옛 kid 에 `notAfter` 설정
- [ ] 설정 화면 공개키 지문 = `gen-key` 출력 지문
- [ ] 연결 확인 성공(개발 사이트 + 고객 사이트 1곳 이상)
- [ ] 연동 실패 기록에서 `UNTRUSTED_KID`·`BAD_SIGNATURE` 가 줄어드는지 1시간 관찰
- [ ] 키 대장 갱신, 사고 기록 작성
- [ ] seed 가 남은 곳이 없는지(터미널 기록, 클립보드, 임시 파일) 확인

## 8. 미검증·준비 필요

| 항목 | 영향 |
|---|---|
