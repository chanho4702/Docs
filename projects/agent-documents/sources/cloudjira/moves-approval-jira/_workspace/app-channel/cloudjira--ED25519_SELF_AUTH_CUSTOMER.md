# Moves 앱 간 통신 보안 설계: Web Trigger + Ed25519 서명 인증

| 항목 | 내용 |
|---|---|
| 대상 | Moves Approval(승인 앱) ↔ Moves Workforce(워크포스) 사이의 앱 간 통신 |
| 기준 | 2026-10-19 설계 기준 |
| 함께 보는 그림 | `ED25519_SELF_AUTH_CUSTOMER.drawio` 5페이지. 본문의 **[그림 NN 삽입]** 표시 위치에 넣습니다(Confluence 는 draw.io 매크로 또는 PNG 내보내기) |
| 범위 밖 | 외부 시스템에 제공하는 API(API Route + Atlassian OAuth 2.0). 10.5절에 간단히 정리 |

---

## 1. 요약

- 두 앱은 Atlassian Forge 의 **Web Trigger** 로 서로 통신합니다.
- Web Trigger 는 Atlassian 이 호출자를 인증하지 않으므로, **두 앱이 Ed25519 전자서명으로 서로를 직접 인증**합니다.
- 보내는 앱은 요청서 전체에 자기 **서명 키(비밀)** 로 서명하고, 받는 앱은 배포본에 들어 있는 **상대 앱의 공개키** 로 서명을 확인합니다.
- 요청서에는 대상 고객 사이트, 연결 식별자, 작업 종류, 서명 시각, 일회용 번호, 요청한 사용자가 들어 있습니다. 그래서 다음 공격을 모두 막습니다.
  - 위조: 서명 키 없이 요청을 만들 수 없습니다.
  - 변조: 요청서가 한 글자라도 바뀌면 서명 검증에 실패합니다.
  - 재전송: 정상 요청을 다시 보내도 시각과 일회용 번호 검사에서 거부됩니다.
  - 다른 사이트 사칭: 다른 고객 사이트용 요청은 사이트 대조에서 거부됩니다.
- 응답에도 서명합니다. 보내는 앱은 서명과 내용을 확인한 응답만 사용합니다.
- 받는 앱은 서명이 맞더라도 **요청한 사용자의 Jira 권한을 다시 확인**하고, 그 사용자가 볼 수 있는 범위만 처리합니다.
- 받는 앱이 처리하는 작업 목록에는 **승인·반려·정책 변경·삭제 실행이 없습니다.** 앱 간 통신만으로는 승인 결과를 바꿀 수 없습니다.

## 2. 배경: 왜 앱이 직접 인증하는가

### 2.1 Web Trigger 의 특성

| 특성 | 의미 | 근거 문서 | 해당 부분 (섹션 · 요지) |
|---|---|---|---|
| 호출자 인증이 없다 | Web Trigger 주소로 오는 요청은 Atlassian 이 신원을 확인하지 않고 앱 함수에 전달합니다 | Atlassian Forge Web trigger 모듈 https://developer.atlassian.com/platform/forge/manifest-reference/modules/web-trigger/ | **Properties** — Web Trigger 주소는 공개되어 있고 Forge 플랫폼이 인증하지 않는다. 들어오는 요청을 확인하는 인증 로직을 핸들러 안에 직접 구현해야 한다 |
| 〃 | 〃 | Atlassian Forge Web trigger 이벤트 https://developer.atlassian.com/platform/forge/events-reference/web-trigger/ | **Request** — 함수에는 요청의 본문·헤더·메서드·경로·쿼리만 JSON 으로 전달된다. 호출자 신원 정보는 없다 |
| 사용자 정보가 없다 | 함수 안에서 "누가 요청했는지"를 플랫폼이 알려 주지 않으며, 사용자 권한으로 Jira 를 호출할 수도 없습니다 | Atlassian Forge Web trigger 모듈 https://developer.atlassian.com/platform/forge/manifest-reference/modules/web-trigger/ | **Properties** — Web Trigger 함수에서는 asUser(사용자 권한) API 호출이 동작하지 않는다 |
| 〃 | 〃 | Atlassian Forge Function arguments https://developer.atlassian.com/platform/forge/function-reference/arguments | **Context** — principal(요청한 사용자)은 없을 수 있는(undefined) 값이다 |
| 사이트 정보는 있다 | 어느 고객 사이트에 설치된 앱이 호출됐는지는 플랫폼이 알려 줍니다 | Atlassian Forge Function arguments https://developer.atlassian.com/platform/forge/function-reference/arguments | **Context** — 컨텍스트는 모든 모듈에서 같은 형태이고, installContext 는 설치된 사이트(클라우드)를 가리키는 식별자다 |

원문은 영어이며 확인일은 2026-10-19 입니다. 다른 장의 근거는 16장에 모았습니다.

따라서 다음 세 가지를 앱이 스스로 확인해야 합니다.

1. 정말 연동 상대 앱이 보냈는가
2. 보내는 도중 내용이 바뀌지 않았는가
3. 예전 요청을 다시 보낸 것은 아닌가

### 2.2 왜 Web Trigger 를 쓰는가

| 선택지 | 판단 |
|---|---|
| Web Trigger + 앱 자체 서명 인증 | **채택.** 사람이 개입하지 않는 자동 처리(이벤트, 예약 작업)에서도 동작하고, 고객 관리자가 별도 토큰을 발급하거나 관리할 필요가 없습니다 |
| API Route + Atlassian OAuth 2.0 | 앱 간 통신에는 채택하지 않음. OAuth 토큰이 특정 사용자 한 명에 묶여 있어서, 그 사람이 퇴사하거나 권한이 바뀌면 자동 처리가 멈춥니다. 대신 **외부 시스템용 API 에 채택**했습니다(10.5, [근거 8]) |
| 공급자 자체 서버 경유 | 채택하지 않음. 고객 데이터가 Atlassian 플랫폼 밖 서버를 거치게 됩니다 |

## 3. 적용 범위와 주고받는 데이터

### 3.1 방향별 작업

| 방향 | 주요 작업 | 성격 |
|---|---|---|
| 워크포스 → 승인 앱 | 이슈별 승인·잠금 상태 조회, 워크로그 작성·수정 가능 여부 판정, 변경 확정 알림 | 조회와 판정. 승인 결정은 하지 않음 |
| 승인 앱 → 워크포스 | 사용자의 소속 팀·팀장 조회, 연결된 이슈·작성 기간 조회, 변경 알림 | 조회와 알림 |
| 양방향 | 처음 연결, 연결 해제, 주소 변경 알림 | 관리 작업 |

각 방향마다 **받을 수 있는 작업 목록이 정해져 있고**, 목록에 없는 작업은 서명이 맞아도 거부합니다.

### 3.2 데이터 최소화 원칙

| 원칙 | 내용 |
|---|---|
| 필요한 항목만 | 응답에는 판정에 필요한 식별자, 상태, 시간, 숫자만 담습니다 |
| 개인 정보 제외 | 이메일 같은 개인 정보는 주고받지 않습니다. 사용자는 Atlassian 계정 식별자로만 가리킵니다 |
| 본문 제한 | 워크로그 설명 원문은 작성자 본인이 요청할 때만 전달합니다. 팀장 조회에는 시간, 일자, 이슈만 전달합니다 |
| 건수 제한 | 작업마다 한 번에 처리하는 건수에 상한이 있습니다 |

### 3.3 데이터가 지나가는 길

- 두 앱 모두 Atlassian Forge 위에서 실행됩니다.
- 통신 대상은 **상대 앱의 Forge Web Trigger 주소 하나뿐**이고, HTTPS 로 암호화됩니다.
- 공급자 자체 서버나 제3자 서비스를 거치지 않습니다.

## 4. 사용 기술과 선택 이유

| 항목 | 내용 |
|---|---|
| 서명 방식 | Ed25519 (RFC 8032). 약 128비트 보안 강도의 타원곡선 전자서명입니다 [근거 10] |
| 실행 환경 | Forge 런타임(Node.js)의 표준 암호 모듈. 외부 암호 라이브러리를 쓰지 않습니다 [근거 11] |
| 전송 구간 | HTTPS(TLS). Web Trigger 주소는 https 로 발급됩니다 [근거 1]. 서명은 전송 구간 암호화와 별개로 **내용의 출처와 무결성**을 보장합니다 |
| 실측 확인 | Forge 런타임에서 서명·검증이 동작하고, 내용을 바꾸면 검증이 실패하는 것을 공급자 개발 환경에서 확인했습니다 |

Ed25519 를 고른 이유

- 공유 비밀번호(HMAC 등) 방식과 달리 **받는 쪽은 공개키만 가집니다.** 받는 앱이 유출돼도 보내는 앱을 사칭할 수 없습니다.
- 서명이 짧고(64바이트) 검증이 빨라서, 위조 요청이 많이 와도 앱 부하가 작습니다 [근거 10].
- 서명할 때마다 새 난수가 필요하지 않고 부채널 공격에 강한 방식이라, 구현 실수로 약해질 여지가 적습니다 [근거 10].

## 5. 구성 요소 (그림 01)

| 구성 요소 | 보관 위치 | 비밀 여부 | 역할 |
|---|---|---|---|
| 서명 키 | 각 앱의 Forge 암호화 환경 변수 [근거 4] | **비밀** | 자기 요청과 응답에 서명합니다. 소스 코드와 저장소에는 넣지 않고, 화면(프론트엔드)으로 내보내지 않습니다 |
| 키 이름 | 각 앱의 환경 설정 | 공개 | 어떤 키로 서명했는지 표시합니다. 키 교체를 가능하게 합니다 |
| 상대 앱 공개키 목록 | 각 앱 배포본에 내장 | 공개 | 상대 앱의 서명을 확인합니다 |
| 신뢰 키 목록 | 각 앱의 환경 설정 | 공개 | 운영 사이트에서는 운영용 키만 신뢰합니다. 개발·검증용 키로 만든 서명은 거부합니다 |
| 연결 정보 | 각 앱의 Forge 저장소 | 내부 | 연결 상태, 연결 식별자, 상대 앱 주소를 둡니다. 다시 연결하면 연결 식별자가 바뀝니다 |
| 일회용 번호 | 요청마다 새로 생성 | 공개 | 재전송을 감지하고, 응답을 해당 요청에 묶습니다 |

**비밀은 각 앱의 서명 키 하나뿐입니다.** 고객 관리자가 관리해야 하는 비밀번호나 토큰은 없습니다.

### 5.1 그림 01 전체 구성

> **[그림 01 삽입]** `ED25519_SELF_AUTH_CUSTOMER.drawio` → "01 전체 구성" 페이지

**무엇을 보여 주나:** 한 고객 Jira 사이트 안에서 두 앱이 무엇을 가지고 있고, 어떻게 서로 요청을 주고받는지 한 장으로 보여 줍니다.

**색과 선 읽는 법** (그림 01~05 공통)

| 표시 | 뜻 |
|---|---|
| 초록 상자 | 승인 앱(Moves Approval)의 구성 요소 |
| 파란 상자 | 워크포스(Moves Workforce)의 구성 요소 |
| 보라 상자·보라 선 | Web Trigger, 앱 사이의 요청과 응답 |
| 빨간 상자 | 비밀(서명 키). 그림에서 유일한 비밀 |
| 주황 상자 | 공개키(상대 앱 서명 확인용) |
| 회색 상자 | 연결 정보, 원칙·참고 |
| 진한 파랑 상자 | Jira(Atlassian) |
| 실선 화살표 | 요청 또는 처리 흐름 |
| 점선 화살표 | 응답, 또는 키를 쓰는 관계(서명·검증) |

**영역별 설명**

| 영역 | 설명 |
|---|---|
| 바깥 큰 상자 "Atlassian Cloud · 고객 Jira 사이트" | 그림의 모든 것이 Atlassian Forge 실행 환경 안에 있습니다. 공급자 서버나 제3자 서비스는 없습니다(3.3절) |
| 맨 위 관리자 두 명 | 고객사의 두 앱 관리자입니다. 처음 한 번만 연결 코드를 주고받습니다(8장, 그림 04). 이후 통신에는 사람이 끼지 않습니다 |
| 왼쪽 초록 영역 / 오른쪽 파란 영역 | 두 앱은 **같은 구조**입니다. 각 앱에 보내기, 받기, 업무 데이터, 서명 키, 상대 공개키, 연결 정보가 하나씩 있습니다 |
| "화면 요청 처리 · 권한 확인" | 사용자가 화면에서 작업하면 앱이 Atlassian 이 확인한 로그인 사용자 기준으로 먼저 권한을 확인합니다. 통과한 요청만 "보내기"로 넘어갑니다 |
| "보내기" | 요청서를 만들고 서명 키로 서명해 상대 앱에 보냅니다. 돌아온 응답의 서명도 여기서 확인합니다 |
| "받기 · Web Trigger" | 상대 앱의 요청을 받는 입구입니다. 12단계 검증(그림 03)과 요청자 권한 재확인을 통과해야 업무 데이터로 넘어갑니다 |
| "업무 데이터 (Forge SQL)" | 각 앱이 원래 가진 데이터입니다. 승인 판정·잠금은 승인 앱, 팀·팀장·작성 기간은 워크포스가 직접 답합니다. 상대 앱의 데이터를 복사해 두지 않습니다 |
| 빨간 "서명 키 (비밀)" → 점선 "서명" | 서명 키는 보내기 모듈만 씁니다. Forge 암호화 환경 변수에 있고 소스 코드에는 없습니다 |
| 주황 "상대 앱 공개키" → 점선 "검증" | 받기 모듈이 상대 앱 서명을 확인할 때 씁니다. 공개 정보라 앱 배포본에 들어 있습니다 |
| 회색 "연결 정보" | 연결 상태, 연결 식별자, 상대 앱 주소입니다. 받을 때 요청서의 연결 식별자와 대조합니다(9단계) |
| 가운데 "Jira (Atlassian)" | 받기 모듈이 요청자 계정과 이슈별 권한을 다시 확인하는 곳입니다(7장). 두 앱의 받기 모듈 모두 사용합니다 |

**화살표 ①~④**

| 번호 | 뜻 |
|---|---|
| ① | 승인 앱 → 워크포스 요청. HTTPS 로 요청서와 Ed25519 서명을 보냅니다. 요청서에는 사이트, 연결 식별자, 시각, 일회용 번호, 요청자가 들어 있습니다 |
| ② | 워크포스의 서명된 응답. 요청의 일회용 번호가 들어 있어 이 요청에 대한 응답임이 보장됩니다 |
| ③ | 반대 방향(워크포스 → 승인 앱) 요청. 규칙은 ①과 같습니다 |
| ④ | 승인 앱의 서명된 응답. 규칙은 ②와 같습니다 |

**아래 상자**

- "보안 원칙": 이 구조로 막는 것 다섯 가지를 요약했습니다. 자세한 내용은 9장 위협별 대응을 봅니다.
- "참고 · 외부 시스템용 API": 고객 연계 도구용 API 는 이 구조가 아니라 Atlassian OAuth 2.0 이 인증합니다(10.5절).

**이 그림에서 확인할 점**

1. 비밀은 빨간 상자 두 개(앱마다 하나)뿐입니다.
2. 앱 사이의 모든 화살표는 서명된 요청 또는 서명된 응답입니다.
3. 받은 요청은 반드시 검증과 권한 재확인을 거친 뒤에만 업무 데이터에 닿습니다.

## 6. 요청 한 번의 흐름 (그림 02, 03)

### 6.1 보내는 앱

1. 사용자가 화면에서 작업합니다.
2. 앱이 Atlassian 이 확인한 로그인 사용자 기준으로 **먼저 권한을 확인**합니다. 통과한 요청만 상대 앱에 보냅니다.
3. 요청서를 만듭니다.
   - 대상 사이트, 연결 식별자, 작업 종류, 보내는 앱, 받는 앱
   - 키 이름, 서명 시각, 일회용 번호
   - 요청자: Atlassian 이 확인한 로그인 사용자의 계정 식별자. 화면에서 넘어온 값은 쓰지 않습니다
4. 요청서 전체에 서명 키로 서명합니다. 서명 앞에는 용도 표시를 붙여, 다른 용도(예: 연결 코드)의 서명을 가져다 쓸 수 없게 합니다.
5. HTTPS 로 상대 앱의 Web Trigger 주소에 보냅니다.


**그림 02 요청 한 번의 흐름**

> **[그림 02 삽입]** `ED25519_SELF_AUTH_CUSTOMER.drawio` → "02 요청 한 번의 흐름" 페이지

**무엇을 보여 주나:** 사용자의 화면 작업 하나가 상대 앱을 거쳐 결과로 돌아오기까지의 순서입니다. 예시는 워크포스 화면에서 워크로그를 저장할 때 승인 앱에 작성 가능 여부를 묻는 경우이며, 반대 방향도 같습니다.

**읽는 법:** 세로 점선 네 개는 참여자(사용자, 보내는 앱, 받는 앱, Jira)이고, 위에서 아래로 시간이 흐릅니다. 가로 화살표는 참여자 사이의 메시지, 상자는 그 참여자 안에서 하는 일입니다.

| 번호 | 위치 | 하는 일 | 보안 의미 |
|---|---|---|---|
| 1 | 사용자 → 보내는 앱 | 화면에서 워크로그 저장 | |
| 2 | 보내는 앱 | Atlassian 이 확인한 로그인 사용자 기준으로 권한 확인 | 권한 없는 요청은 상대 앱까지 가지 않음 |
| 3 | 보내는 앱 | 요청서 작성: 사이트, 연결 식별자, 작업, 시각, 일회용 번호, 요청자 | 요청자는 화면 값이 아니라 Atlassian 이 확인한 계정 |
| 4 | 보내는 앱 | 서명 키로 요청서 전체에 서명 | 한 글자라도 바뀌면 검증 실패 |
| 5 | 보내는 앱 → 받는 앱 | HTTPS 요청 | 전송 구간 암호화 |
| 6 | 받는 앱 | 12단계 검증(그림 03) | 위조·변조·재전송·다른 사이트 요청 거부 |
| 7·8 | 받는 앱 ↔ Jira | 요청자 권한 확인과 결과 | 서명이 맞아도 요청자가 볼 수 없는 데이터는 처리 안 함 |
| 9 | 받는 앱 | 요청자가 볼 수 있는 범위만 업무 처리 | 데이터 최소화 |
| 10·11 | 받는 앱 | 응답에 요청의 일회용 번호를 넣고 서명 | 응답을 이 요청에 묶음 |
| 12 | 받는 앱 → 보내는 앱 | 서명된 응답 | |
| 13 | 보내는 앱 | 응답 검증: 서명, 일회용 번호, 사이트, 연결, 작업, 시각 | 예전 응답을 끼워 넣어도 사용 안 됨 |
| 14 | 보내는 앱 → 사용자 | 결과 표시: 저장, 또는 승인 앱 화면에서 입력하도록 안내 | |

빨간 상자 "실패 시"는 어느 단계에서든 실패하면 받는 앱은 업무 데이터를 쓰지 않고, 보내는 앱은 허용하지 않는 쪽(fail-close)으로 처리한다는 뜻입니다(12장).
### 6.2 받는 앱: 12단계 검증

비용이 적은 검사부터 합니다. **1~8단계는 데이터베이스를 쓰지 않습니다.** 위조 요청이 대량으로 와도 업무 데이터에 접근하지 않고 바로 거부합니다.

| 단계 | 검사 | 실패 시 |
|---|---|---|
| 1 | 허용된 요청 방식인지, 최대 크기 이하인지 | 거부 |
| 2 | 요청서 구조가 올바른지, 받는 앱이 자신이고 보낸 앱이 연동 상대인지 | 거부 |
| 3 | 이 방향에서 허용된 작업인지 | 거부 |
| 4 | 서명 시각이 지금 기준 2분 이내인지 | 거부(만료) |
| 5 | 서명한 키가 신뢰 키 목록에 있는지 | 거부(인증 실패) |
| 6 | Ed25519 서명이 요청서 전체와 맞는지 | 거부(인증 실패) |
| 7 | 요청서의 대상 사이트가 이 고객 사이트인지 | 거부(다른 사이트) |
| 8 | 최근 5분 안에 같은 일회용 번호를 받은 적이 있는지 | 거부(재전송) |
| 9 | 연결 상태가 정상이고 연결 식별자가 같은지 | 거부(연결 안 됨 또는 옛 연결) |
| 10 | 라이선스가 활성인지 | 거부 |
| 11 | 요청자 정책: 사람이 필요한 작업에 시스템 요청이 왔는지, 시스템 요청 사유가 허용 목록에 있는지 | 거부 |
| 12 | 요청자 권한 재확인(7장) 후 업무 처리 | 거부 또는 범위 축소 |

1~8단계에서 거부할 때는 최소한의 응답만 돌려주고, 어떤 단계에서 실패했는지 외부에 자세히 알리지 않습니다.


**그림 03 받는 앱 12단계 검증**

> **[그림 03 삽입]** `ED25519_SELF_AUTH_CUSTOMER.drawio` → "03 받는 앱 12단계 검증" 페이지

**무엇을 보여 주나:** 위 표의 12단계를 위에서 아래로 그린 것입니다. 요청은 한 단계라도 실패하면 오른쪽 빨간 상자로 빠지고, 12단계를 모두 통과해야 아래의 서명된 응답에 도달합니다.

| 그림 요소 | 설명 |
|---|---|
| 맨 위 보라 상자 "요청 도착" | Web Trigger 로 들어온 요청. 이 시점에는 아무것도 믿지 않습니다 |
| 가운데 흰 상자 1~12 | 검사 단계. 6단계(주황, 굵게)가 Ed25519 서명 검증입니다 |
| 오른쪽 빨간 상자 | 그 단계에서 실패했을 때의 거부 사유. 거부된 요청은 다음 단계로 가지 않습니다 |
| 왼쪽 띠 "DB 미사용 · 즉시 거부" (1~8) | 이 구간은 데이터베이스와 저장소를 전혀 쓰지 않습니다. 위조 요청이 아무리 많아도 업무 데이터에 닿지 않고, 비용도 거의 들지 않습니다 |
| 왼쪽 띠 "연결 정보 1회 확인" (9) | 처음으로 저장소를 읽는 단계. 이 사이트의 현재 연결과 맞는지 봅니다 |
| 왼쪽 띠 "정책 확인" (10~11) | 라이선스와 요청자 정책. 저장소를 더 쓰지 않습니다 |
| 왼쪽 띠 "업무 데이터 · Jira 권한" (12) | 여기서 처음 업무 데이터와 Jira 권한 조회를 씁니다 |
| 아래 초록 상자 "서명된 응답" → 파란 상자 | 응답에도 서명하고, 보내는 앱은 응답을 다시 검증한 뒤에만 결과를 씁니다(6.3절) |
| 맨 아래 메모 | 1~8단계 거부는 최소 응답만 보내 실패 단계를 노출하지 않고, 9단계 이후 실패는 기록하고 관리자 화면에 표시합니다(11장) |

**핵심:** 싼 검사(시각, 키, 서명, 사이트, 재전송)를 앞에 두어, 정상 요청만 비용이 드는 단계에 도달하게 했습니다.
### 6.3 응답도 검증한다

받는 앱은 응답에 서명하고, 응답에 **요청의 일회용 번호를 넣습니다.** 보내는 앱은 아래를 모두 확인한 응답만 씁니다.

- 응답 서명이 맞는가
- 응답에 든 일회용 번호가 내가 보낸 번호와 같은가
- 보낸 앱, 받는 앱, 연결 식별자, 사이트, 작업 종류가 요청과 같은가
- 응답 시각이 2분 이내인가

예전에 받은 정상 응답을 중간에서 끼워 넣어도 사용되지 않습니다.

## 7. 요청한 사용자를 어떻게 확인하는가

서명은 "연동 상대 앱이 보냈다"는 것을 보장합니다. 받는 앱은 여기서 멈추지 않고 **요청자 기준으로 한 번 더 확인**합니다.

| 수준 | 방법 | 적용 작업 |
|---|---|---|
| 기본 | 보내는 앱의 1차 권한 확인을 믿습니다. 민감하지 않은 정보만 해당합니다 | 연결 여부, 작성 기간, 화면 갱신 알림 |
| 계정 확인 | 요청자가 이 사이트의 실제 활성 사용자인지 Jira 에 확인하고, 앱의 업무 규칙(본인, 담당 팀장, 관리자)을 적용합니다 | 기간 상태, 결재선, 원가 숫자 |
| 이슈별 권한 | 요청자가 해당 이슈를 보거나 워크로그를 쓸 권한이 있는지 이슈마다 Jira 에 확인합니다. 그 사용자에게 권한이 확인된 경우에만 허용합니다 | 워크로그 작성·수정 판정, 이슈 상태 표시, 숨긴 워크로그 목록 |

- 권한 확인 결과는 허용·거부 판정에만 쓰고, 응답이나 로그로 내보내지 않습니다.
- 권한 확인이 실패하거나 시간이 초과되면 **거부**합니다.
- 사람이 없는 자동 처리(이벤트, 예약 작업)는 요청자를 "시스템"으로 표시합니다. 시스템 요청은 허용된 사유에서만 쓸 수 있고, 대상도 앱이 Jira 데이터로 정한 1건으로 제한됩니다. 그래서 시스템 요청으로 조회 범위가 넓어지지 않습니다.

## 8. 처음 연결: 연결 코드 (그림 04)

두 앱이 서로의 주소를 안전하게 알아내는 단계입니다. 고객 관리자가 한 번만 하면 양방향 연결이 끝납니다.

1. A 앱 관리자가 "연결 코드 만들기"를 누릅니다.
2. A 앱은 자기 Web Trigger 주소, 새 연결 식별자, 일회용 확인값, 30분 만료가 담긴 연결 코드를 만들고 **A 앱 서명 키로 서명**합니다. 확인값은 원문이 아니라 해시만 저장합니다.
3. A 관리자가 코드를 복사해 B 앱 관리자에게 전달합니다.
4. B 관리자가 B 앱에 코드를 붙여 넣습니다.
5. B 앱은 코드의 서명, 상대 앱 종류, 운영·개발 환경 구분, 대상 사이트, 만료, 주소 형식을 확인합니다.
6. B 앱이 A 앱에 "연결 완료" 요청을 서명해 보냅니다. 요청에는 확인값과 B 앱 주소가 들어 있습니다.
7. A 앱은 12단계 검증을 거친 뒤 연결 식별자, 만료, 확인값을 대조하고 연결을 저장합니다. 연결 코드는 한 번 쓰면 폐기합니다.
8. A 앱의 서명된 응답을 확인한 B 앱도 연결을 저장합니다.

보호 장치

- 코드에는 일회용 확인값이 있으므로 화면에는 복사 버튼만 두고, 로그와 감사 기록에는 코드 원문을 남기지 않습니다.
- 다른 사이트에서 만든 코드는 B 앱에서 한 번, A 앱의 검증에서 또 한 번 거부됩니다.
- 30분이 지난 코드나 이미 쓴 코드는 거부됩니다.
- 다시 연결하면 연결 식별자가 바뀌고, 옛 연결로 온 요청은 즉시 거부됩니다.

### 8.1 그림 04 처음 연결

> **[그림 04 삽입]** `ED25519_SELF_AUTH_CUSTOMER.drawio` → "04 처음 연결 (연결 코드)" 페이지

**무엇을 보여 주나:** 고객 관리자 두 명이 연결 코드를 한 번 주고받아 두 앱이 서로의 주소를 안전하게 알게 되는 과정입니다. A 는 코드를 만든 앱, B 는 붙여 넣은 앱이며 어느 쪽이 A 가 되어도 됩니다.

**읽는 법:** 세로 점선 네 개는 A 앱 관리자, A 앱, B 앱, B 앱 관리자입니다. 위에서 아래로 진행합니다.

| 번호 | 위치 | 하는 일 | 보안 의미 |
|---|---|---|---|
| 1 | A 관리자 → A 앱 | "연결 코드 만들기" | 앱 관리자 권한이 있어야 함 |
| 2 | A 앱 | 자기 주소, 새 연결 식별자, 일회용 확인값 생성. 확인값은 해시만 저장 | 저장소가 유출돼도 확인값 원문은 없음 |
| 3 | A 앱 → A 관리자 | A 서명 키로 서명한 연결 코드 표시(30분 유효) | 코드 위조·변조 불가, 30분 뒤 무효 |
| 4 | A 관리자 → B 관리자 | 코드 전달(사람 사이) | 1:1 경로로 전달 권장 |
| 5 | B 관리자 → B 앱 | 코드 붙여넣기 | |
| 6 | B 앱 | 코드 확인: A 공개키 서명, 앱 종류, 운영·개발 환경, 대상 사이트, 만료, 주소 형식 | 다른 사이트·다른 환경의 코드 거부 |
| 7 | B 앱 → A 앱 | "연결 완료" 요청(B 서명 키로 서명). 확인값과 B 주소 포함 | 일반 요청과 같은 12단계 검증을 받음 |
| 8 | A 앱 | 검증 후 연결 식별자·만료·확인값 대조, 연결 저장, 코드 폐기 | 코드는 한 번만 쓸 수 있음 |
| 9 | A 앱 → B 앱 | 서명된 응답(7번 요청의 일회용 번호 포함) | |
| 10 | B 앱 | 응답 검증 후 연결 저장 | |
| 11 | B 앱 → B 관리자 | "연결됨" 표시 | |

**이 그림에서 확인할 점**

1. 사람이 주고받는 것은 서명된 연결 코드 하나뿐이고, 비밀번호나 키를 주고받지 않습니다.
2. A 는 B 의 주소를 7번 요청에서, B 는 A 의 주소를 코드에서 얻습니다. 두 주소 모두 서명으로 보호됩니다.
3. 다른 사이트에서 만든 코드는 6번(B)과 8번(A)에서 두 번 거부됩니다.

## 10. 키 관리와 사고 대응 (그림 05)

### 10.1 키 생명주기

| 단계 | 절차 |
|---|---|
| 생성 | 공급자가 운영·개발·검증 환경별로 따로 만듭니다. 서명 키는 파일이나 소스 저장소에 남기지 않습니다 |
| 보관 | 서명 키는 해당 앱의 Forge 암호화 환경 변수에만 저장합니다. 공개키는 상대 앱 배포본에 넣습니다 |
| 교체 | ① 새 공개키를 양쪽 앱에 추가 배포 → ② 서명 키를 새 것으로 전환 → ③ 옛 공개키 제거 배포. 교체 중에도 두 키를 함께 신뢰하므로 통신이 끊기지 않습니다 |
| 폐기 | 공개키 목록에서 해당 키를 빼고 배포하면 그 키로 만든 모든 서명이 즉시 무효가 됩니다 |

Web Trigger 주소는 같은 사이트·환경에서 새 버전을 배포해도 바뀌지 않고, 삭제한 주소로는 더 이상 앱을 호출할 수 없습니다 [근거 2].

### 10.2 사고 대응

| 상황 | 대응 | 효과 |
|---|---|---|
| 서명 키 유출 의심 | 새 키로 교체하고 옛 키 폐기 | 옛 키로 만든 요청 즉시 거부 |
| 특정 사이트의 연결 오용 의심 | 고객 관리자가 연결 해제 후 다시 연결 | 새 연결 식별자, 옛 요청 즉시 거부 |
| Web Trigger 주소 노출 | 새 주소를 발급하고 상대 앱에 서명된 변경 알림을 보낸 뒤 옛 주소 삭제 | 옛 주소 호출 불가. 단, 주소가 노출돼도 서명 없이는 요청이 처리되지 않음 |

### 10.3 탐지와 모니터링

서명 키가 유출되면 공격자의 요청은 서명 검증을 통과합니다. 그래서 "서명 실패"만 보지 않고, 아래 신호를 함께 봅니다.

| 신호 | 의미 | 판단 |
|---|---|---|
| 서명 실패·신뢰하지 않는 키 요청이 늘어남 | 누군가 주소를 알고 요청을 시도하는 중. 키는 안전 | 관찰 |
| 다른 사이트용 요청, 재전송 요청이 늘어남 | 가로챈 요청을 옮기거나 다시 보내려는 시도 | 관찰 |
| **폐기한 키로 서명된 요청** | 옛 키가 유출되어 실제로 쓰이고 있음 | **유출로 간주** |
| **서명은 맞는데 요청자 권한 거부가 늘어남** | 권한 없는 사용자 이름으로 데이터를 조회하려는 시도 | **유출로 간주** |
| 사용자별 요청 속도 제한 초과 | 대량 조회 시도 | 조사 |
| **받은 요청 수가 상대 앱이 실제로 보낸 요청 수보다 많음** | 상대 앱이 아닌 누군가 서명된 요청을 만들고 있음 | **유출로 간주** |

| 장치 | 내용 | 상태 |
|---|---|---|
| 연동 실패 기록 | 연결 상태 확인(9단계) 이후 실패를 사유·횟수와 함께 기록하고, 관리자 화면에 "연결 확인 필요" 표시 | 설계 반영 |
| 감사 이력의 서명 키 이름 | 앱 간 통신으로 처리한 변경마다 요청자·연결·서명 키 이름·작업을 기록. 사고 때 특정 키·기간으로 처리 내역을 뽑아낼 수 있음 | 설계 반영 |
| 거부 사유 집계 | 1~8단계 거부를 사유별로 집계해 급증할 때만 기록. 폐기한 키 이름은 한 건만 들어와도 경보 | 적용 예정 |
| 송신·수신 대조 | 두 앱이 사이트별로 "보낸 요청 수"와 "받아서 처리한 요청 수"를 세어 하루 한 번 서명된 요약으로 맞춰 봄. 차이가 나면 경보 | 적용 예정 |
| 공급자 정기 점검 | 사이트별 거부 사유 분포, 요청자 권한 거부 비율, 평소 대비 호출량 변화 점검 | 적용 예정 |

### 10.4 키 유출 대응 절차

| 단계 | 할 일 |
|---|---|
| 1. 판정 | 10.3의 신호로 등급을 나눕니다. 요청 시도는 관찰하고, "유출로 간주" 신호가 나오면 바로 2단계로 갑니다 |
| 2. 차단 | 해당 키를 신뢰 목록에서 빼고 두 앱을 다시 배포합니다. 그 키로 만든 서명은 모든 사이트에서 즉시 무효가 됩니다. 새 키가 배포될 때까지 연동은 안전한 쪽으로 멈추고(12장) 기존 잠금은 유지됩니다 |
| 3. 복구 | 새 키를 만들어 등록하고 두 앱을 배포합니다. 고객 관리자가 할 일은 없습니다 |
| 4. 조사 | 감사 이력에서 해당 키 이름과 기간으로 처리된 작업·요청자·사이트를 뽑습니다. 받는 작업에 승인·반려·삭제가 없으므로, 조사는 조회된 데이터의 범위를 확인하는 데 집중합니다 |
| 5. 고지 | 영향받은 고객 사이트를 확정하고 계약과 관련 법령에 따라 안내합니다 |

### 10.5 참고: 외부 시스템용 API

외부 시스템(예: 고객의 연계 도구)에 제공하는 API 는 이 문서의 방식이 아니라 **Atlassian API Route + OAuth 2.0(3LO)** 를 씁니다 [근거 9]. API Route 는 현재 Atlassian 의 Preview 기능입니다.

- Atlassian 게이트웨이가 토큰과 허용 범위(scope)를 검증한 뒤에만 앱 함수로 요청을 넘깁니다 [근거 8].
- 앱 REST API 는 사이트마다 기본으로 꺼져 있어 고객 사이트 관리자가 켜야 하고, 연동 담당자가 동의해야 토큰이 발급됩니다 [근거 8].
- 앱은 토큰 주인 기준으로 업무 권한을 다시 확인합니다.

## 11. 감사와 기록

- 앱 간 통신으로 일어난 모든 변경과 설정 변경 알림은 앱 감사 이력에 남깁니다. 기록 항목은 요청자, 경유 채널, 연결 식별자, 서명 키 이름, 작업 종류입니다.
- 연결, 연결 해제는 감사 이력에 남깁니다.
- 연결 상태 확인(9단계) 이후에 실패한 요청은 앱의 연동 실패 기록에 남기고, 관리자 화면에 "연결 확인 필요"로 표시합니다. 탐지에 쓰는 신호는 10.3절에 정리했습니다.
- 1~8단계에서 거부한 요청은 데이터베이스를 쓰지 않으므로 Forge 실행 로그에 요청 내용 없이 한 줄만 남깁니다.
- 서명 키, 연결 코드 원문, 일회용 확인값 원문은 어떤 기록에도 남기지 않습니다.

## 12. 장애 시 동작

상대 앱이 응답하지 않거나 응답 검증에 실패하면 **안전한 쪽으로 멈춥니다(fail-close).**

| 상황 | 동작 |
|---|---|
| 승인·잠금 상태를 확인할 수 없음 | 기존 잠금을 그대로 유지합니다. 잠긴 기록이 풀리지 않습니다. 화면에는 마지막 확인값과 "확인 불가" 경고를 함께 표시합니다 |
| 워크로그 작성 가능 여부를 판정할 수 없음 | 저장하지 않고 승인 앱 화면에서 입력하도록 안내합니다. 판정할 수 없으면 허용하지 않습니다 |
| 조회 응답이 늦거나 오류 | 조회는 한 번만 다시 시도하고, 실패하면 최근 확인값을 쓰거나 "확인 불가"로 표시합니다. 쓰기 판정은 다시 시도하지 않고 바로 막습니다 |
| 서명·연결 검증 실패 | 다시 시도하지 않고, 관리자 화면에 "연결 확인 필요"를 표시합니다 |
| 상대 앱이 사라짐 | 단독 모드로 자동 전환하지 않습니다. 고객 관리자가 연결을 해제할 때만 단독 모드가 됩니다 |
