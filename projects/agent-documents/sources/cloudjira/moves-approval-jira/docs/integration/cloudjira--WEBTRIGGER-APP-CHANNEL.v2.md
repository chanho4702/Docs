# 승인 앱 ↔ 워크포스 연동 — 서명된 앱 간 채널(webtrigger)

> **문서 성격** 내부 공유 + 고객 설명용 · **기준일** 2026-10-20 · **검증 환경** 개발 사이트(development)
> **관련 문서** 외부 시스템 → 워크포스 조회 API(apiRoute + OAuth 2.0 3LO) · 스트라드비전 요구사항 아키텍처 정리
> ℹ️ 정보 패널로: "§1~§4 는 고객과 공유할 수 있습니다. §5~§7 은 기술 검토자용 상세입니다."

---

## 1. 한 장 요약

| 질문 | 답 |
|---|---|
| **무엇을 하나** | Moves Approval(승인)과 Moves Workforce(인력·작업) 두 Forge 앱이 서로 필요한 정보를 **직접, 실시간으로** 주고받습니다. 조직·팀장 정보는 Workforce가, 승인·잠금 정보는 Approval이 답합니다. |
| **어떻게 연결하나** | 관리자가 한쪽 앱에서 만든 **연결 코드를 다른 쪽 앱에 한 번 붙여 넣으면** 끝입니다. OAuth 앱 생성·토큰 보관 같은 별도 설정은 없습니다. |
| **왜 안전한가** | 모든 요청과 응답에 **Ed25519 전자 서명**을 붙이고, 받는 앱이 **데이터에 접근하기 전에** 서명·사이트·시각·재전송 여부를 검사합니다. URL이 유출되어도 서명 키 없이는 아무것도 할 수 없습니다. |
| **누구 권한으로 처리하나** | 요청을 일으킨 **실제 사용자(행위자)의 권한**으로 처리합니다. 앱끼리 연결되었다고 해서 사용자가 볼 수 없는 데이터가 보이지 않습니다. |
| **장애 시에는** | 상대 앱이 응답하지 않으면 **변경을 보류**합니다(fail-close). 승인된 기록의 잠금은 그대로 유지되고, 화면에 "확인 불가·대기"가 표시됩니다. |
| **검증 결과** | 개발 사이트에 두 앱을 실제로 배포·연결해 **기능 8종 화면 검증 통과**, **위조 요청 26종과 동시 80건을 전부 거부**(데이터베이스 접근 0건)했습니다. |
| **감수한 것** | 이 방식을 쓰면 두 앱 모두 Marketplace의 **"Runs on Atlassian" 배지 자격을 잃습니다**. 데이터는 여전히 Atlassian Forge 안에만 저장되며, 앱 간 통신만 Atlassian 인프라 안의 HTTPS 호출로 이루어집니다(§4.3). |

## 2. 왜 이 방식인가

### 2.1 풀어야 했던 문제

두 앱은 같은 Jira 사이트에 설치되지만 **서로의 저장소(Forge SQL·KVS)를 직접 읽을 수 없습니다**. Forge는 앱마다 저장소를 격리합니다. 따라서 "이 사람의 팀장은 누구인가", "이 작업 기록은 승인되어 수정할 수 없는가"를 상대 앱에 물을 통로가 필요합니다.

### 2.2 검토한 세 가지 방법

| 비교 항목 | **서명된 webtrigger 채널 (채택)** | apiRoute + OAuth 3LO | Jira 엔티티 프로퍼티 (이전 방식) |
|---|---|---|---|
| 고객 설치 작업 | 연결 코드 1회 붙여 넣기 | 사이트마다 REST API 켜기 → OAuth 앱 생성 → 권한 연결 → 동의 → Secret 보관 (4단계) | 없음 |
| 사람 없이 도는 작업(자동 처리·야간 정리) | 가능 | 토큰을 발급한 사람에 묶임. **그 사람이 퇴사하면 멈춤** | 가능 |
| 응답 속도 | 약 0.2초 | 약 1.8초 | 게시 주기만큼 지연(최대 하루) |
| 위조 방어 | 서명·사이트·재전송·작업 허용 목록 | 플랫폼 토큰 | **이슈 편집 권한자 누구나 덮어쓰기·삭제 가능** |
| 최신성 | 질문 시점의 원장 값 | 질문 시점의 원장 값 | 마지막 게시 시점 값 |
| Runs on Atlassian | 실격 | 호출하는 쪽 실격 | 유지 |

**결론**: 엔티티 프로퍼티는 Jira 이슈를 편집할 수 있는 사람이면 누구나 값을 바꿀 수 있어 **승인·잠금 판단의 근거로 쓸 수 없습니다**. apiRoute는 고객 설정 부담이 크고 사람 계정에 묶여 무인 작업이 불안정합니다. 그래서 앱 간 통신은 webtrigger 채널로, **외부 시스템(SAP·BI 등) 연동은 apiRoute로** 역할을 나눴습니다.

### 2.3 원칙 — "원장 주인이 답한다, 바뀌면 알린다"

| 정보 | 원장(주인) | 상대 앱의 역할 |
|---|---|---|
| 조직·팀·팀장, 프로젝트 연결, 팀장이 정한 작성 기간, 근무 기준 | Workforce | Approval이 필요할 때 묻고, 바뀌면 Workforce가 알림 |
| 승인 결과·인정 시간, 수정 가능 여부, 기간 마감, 결재선 | Approval | Workforce가 필요할 때 묻고, 바뀌면 Approval이 알림 |
| 실제 작업 기록(워크로그) | Jira | 두 앱 모두 Jira 원본을 기준으로 확인 |

받은 값은 **임시 캐시일 뿐 원장이 아닙니다**. 의심스러우면 언제든 원장 주인에게 다시 물어볼 수 있습니다.

## 3. 고객 관점 — 무엇을 하면 되고, 무엇이 보장되나

### 3.1 고객 관리자가 할 일

| 단계 | 누가 | 어디서 | 소요 |
|---|---|---|---|
| ① 두 앱 설치(또는 업그레이드 동의) | Jira 사이트 관리자 | Atlassian Marketplace / 앱 관리 | 수 분 |
| ② "연결 코드 만들기" | 한쪽 앱 관리자 | Approval: 설정 › 워크포스 연동 / Workforce: 설정 › 승인 앱 연결 | 1분 |
| ③ 다른 쪽 앱에 코드 붙여 넣기 | 다른 쪽 앱 관리자 | 위와 반대편 화면 | 1분 |
| ④ 양쪽 화면 "연결됨"·상대 버전 확인 | 관리자 | 같은 화면 | — |

- 연결 코드는 **30분 뒤 만료**되고 **한 번만 쓸 수 있습니다**.
- 어느 쪽에서 코드를 만들어도 됩니다. 붙여 넣는 순간 양방향 연결이 완성됩니다.
- Jira 권한 스킴·OAuth 앱·API 토큰 등 **추가 설정은 필요 없습니다**.

### 3.2 보장하는 것

| 보장 | 근거 |
|---|---|
| 사용자는 원래 볼 수 있는 것만 봅니다 | 요청마다 행위자의 Jira 권한과 앱 권한(작성자 본인·담당 팀장·관리자)을 받는 쪽이 다시 확인합니다(§6.3). |
| 승인된 기록은 어느 앱에서 입력해도 같은 규칙으로 막힙니다 | Workforce에서 저장하기 전에 Approval이 판정합니다(`write.judge` → `write.commit`). |
| 연결 장애가 잠금을 풀지 않습니다 | 상대가 응답하지 않으면 변경을 보류하고, 기존 잠금은 유지합니다. |
| URL이 새어도 데이터는 새지 않습니다 | 서명 키 없이는 모든 요청이 데이터 접근 전에 거부됩니다(§7.2 실측). |
| 연결은 언제든 끊을 수 있습니다 | 관리자가 "연결 해제"하면 상대 URL이 즉시 무효가 됩니다(404). |

### 3.3 보장하지 않는 것(정직한 한계)

- **Atlassian 플랫폼 자체 장애**나 호출 한도 초과(429) 시에는 연동 기능이 일시적으로 보류됩니다. 이때도 잠금은 풀리지 않습니다.
- 첫 호출(콜드 스타트)은 **4~7초**가 걸릴 수 있습니다. 이후에는 대부분 1초 안에 응답합니다.
- **운영(production) 환경 실측 전**입니다. 개발 환경에서 모두 확인했고, 운영 배포 전 확인할 항목은 §7.4에 공개합니다.

### 3.4 자주 받는 질문

**Q. 우리 데이터가 Atlassian 밖으로 나가나요?**
A. 아닙니다. 두 앱의 데이터는 각 앱의 Forge 저장소에 있고, 앱 간 호출은 Atlassian이 운영하는 Forge webtrigger 주소(HTTPS)로만 갑니다. 제3의 서버나 저희(개발사) 서버를 거치지 않습니다. "Runs on Atlassian" 배지가 없는 이유는 **앱이 다른 앱의 주소로 HTTPS 호출(egress)을 하기 때문**이지, 외부 서버를 쓰기 때문이 아닙니다.

**Q. 누군가 연결 주소(URL)를 알아내면요?**
A. 주소만으로는 아무것도 할 수 없습니다. 모든 요청에 개발사가 관리하는 비밀 키로 만든 서명이 필요하고, 서명이 없거나 틀리면 데이터베이스에 접근하기 전에 거부합니다. 의심되면 관리자가 주소를 교체할 수 있고, 옛 주소는 즉시 무효가 됩니다.

**Q. 앱끼리 연결하면 팀원이 다른 팀 기록을 볼 수 있게 되나요?**
A. 아닙니다. 앱 간 요청은 "누가 이 요청을 일으켰는가"를 서명된 봉투에 담아 보내고, 받는 앱이 그 사람의 Jira 권한과 앱 권한을 다시 확인합니다. 화면에서 볼 수 없는 데이터는 연동으로도 볼 수 없습니다.

**Q. Workforce만 쓰다가 나중에 Approval을 붙일 수 있나요? 반대로 끊으면요?**
A. 언제든 연결·해제할 수 있습니다. 연결하지 않으면 각 앱은 단독으로 동작합니다. 해제해도 이미 저장된 승인 이력과 작업 기록은 지워지지 않습니다.

**Q. Atlassian이 webtrigger를 바꾸면요?**
A. webtrigger는 Forge 정식(GA) 기능입니다. 인증은 Atlassian 플랫폼이 아닌 저희 서명으로 하므로, 플랫폼이 인증 방식을 바꿔도 영향이 작습니다. Atlassian이 HMAC 인증 webtrigger(제안 단계 RFC-141)를 정식 출시하면 기존 서명에 추가로 적용하는 방안을 검토합니다.

## 4. 전체 구조

### 4.1 구성도

> 🖼️ (기존 구성도 이미지 유지)

```
 ┌────────────── Jira Cloud 사이트 (고객) ──────────────┐
 │                                                      │
 │  Moves Approval                    Moves Workforce   │
 │  ┌──────────────┐  서명된 요청 ▶   ┌──────────────┐   │
 │  │ ChannelClient│ ───────────────▶│ ChannelServer│   │
 │  │ ChannelServer│ ◀─────────────── │ ChannelClient│   │
 │  └──────┬───────┘  ◀ 서명된 응답    └──────┬───────┘   │
 │         │ Forge SQL·KVS                  │ Forge SQL·KVS│
 │         ▼ (승인·잠금·이력)               ▼ (조직·프로젝트)│
 │                 Jira REST (워크로그 원본)              │
 └──────────────────────────────────────────────────────┘
```

- 두 앱은 **대칭 구조**입니다. 각 앱에 받는 창구(webtrigger 1개)와 보내는 클라이언트 1개가 있습니다.
- 봉투·서명·작업 목록·공개 키 목록·연결 코드를 담은 **공유 계약 파일은 두 앱에서 바이트 단위로 같고**, 자동 테스트로 일치를 강제합니다.

### 4.2 채널로 주고받는 작업(14종)

| 방향 | 작업 | 화면에서 보이는 결과 |
|---|---|---|
| 양쪽 | `pair.complete` · `sys.ping` · `sys.rekey` · `sys.unpair` | 연결·연결 확인(상대 버전 표시)·주소 교체·연결 해제 |
| Approval → Workforce | `org.get` · `org.teams` | 결재자(소속 팀장) 자동 결정, 설정 › 팀의 "워크포스에서 받은 팀" |
| Approval → Workforce | `link.resolve` · `kb.get` | 연동 이슈 여부, 팀장이 정한 작성 기간·사전 승인, 근무 기준(하루 시간·공휴일) |
| Approval → Workforce | `change.notify` | 승인·기간 마감·통제·결재선 변경 알림 → Workforce 캐시 즉시 갱신 |
| Workforce → Approval | `cert.query` · `issue.control` · `period.status` | 승인 배지·인정 시간 집계, 수정 가능 여부, 기간 마감 상태 |
| Workforce → Approval | `write.judge` → `write.commit` | Workforce에서 입력한 워크로그를 Approval이 판정한 뒤 저장, 승인 요청 자동 생성 |
| Workforce → Approval | `flows.list` · `change.notify` | 팀장 승인 설정의 결재선 목록, 조직·연결·작성 기간 변경 알림 |

허용 목록에 없는 작업이나 **방향이 뒤바뀐 작업은 서명이 맞아도 거부**합니다.

### 4.3 Runs on Atlassian 실격의 의미

| 오해 | 사실 |
|---|---|
| "외부 서버를 쓴다" | 쓰지 않습니다. 모든 코드는 Forge 함수, 모든 데이터는 Forge SQL·KVS에 있습니다. |
| "데이터가 해외·제3자에게 간다" | 앱 간 호출 대상은 같은 사이트에 설치된 상대 앱의 Forge webtrigger 주소뿐입니다. |
| 실격 사유 | ① dynamic webtrigger 사용(서명 응답을 돌려주려면 필수) ② 상대 앱 주소로의 egress 선언. Atlassian 규정상 이 둘은 자동 실격입니다. |

## 5. 운영 절차 (관리자·지원 담당)

| 상황 | 조치 | 결과 |
|---|---|---|
| 처음 연결 | §3.1 순서 | 양쪽 "연결됨" |
| 연결 상태 확인 | 설정 화면의 "연결 확인"(`sys.ping`) | 상대 앱 버전·응답 시간 표시 |
| 주소 유출 의심 | "주소 교체"(`sys.rekey`) | 새 주소 발급 → 상대가 새 주소 확인 → 옛 주소 삭제(404). 2단계라 중단 없음 |
| 연결 끊기 | "연결 해제"(`sys.unpair`) | 양쪽 연결 정보 삭제, 이후 요청은 `NOT_PAIRED` |
| 서명 키 교체(개발사) | 새 키 ID를 양쪽 키 목록에 추가·배포 → 서명 전환 → 옛 키 제거 | 무중단 교체 |
| 상대 앱 응답 없음 | 자동 fail-close. 화면에 "확인 불가" 표시, 연동 이슈 쓰기 보류 | 복구 후 자동 재개 |
| 연동 스위치 끔 / 라이선스 만료 | 받는 쪽이 `LINK_DISABLED` / `LICENSE_INACTIVE` 로 거부 | 각 앱 단독 동작 |

## 6. 기술 상세 (검토자용)

> Confluence에서는 이 장을 **확장(expand) 매크로**로 접어 두기를 권합니다.

### 6.1 Forge 플랫폼 사실 확인

| 질문 | 답 | 근거 |
|---|---|---|
| 앱 백엔드가 다른 앱을 직접 부를 수 있나 | 가능. 상대 webtrigger URL을 `fetch`. 사용자 컨텍스트 없이 200 | 사전 실측 |
| 받는 쪽이 호출자를 알 수 있나 | 없음. `principal: null`, 사이트 ARI만 | 사전 실측 · 공식 "Web trigger URLs are not authenticated by the Forge platform" [1] |
| 호출자 인증 수단 | 요청·응답 원문 Ed25519 서명. Forge 런타임(Node 22) `crypto`로 동작, 1바이트 변조 감지 | 사전 실측 |
| 큰 데이터 | 200KB 본문 0.26초 | 사전 실측 |
| 상대 URL 얻기 | `webTrigger.getUrl(key)` = CLI URL. 재배포·major 업그레이드 후에도 유지 | 사전 실측 · 공식 [2] |
| URL 교체 | `getUrl(key, true)` 새 URL, `deleteUrl` 직후 옛 URL 404 | 사전 실측 |
| 응답 서명 헤더 | dynamic 응답의 사용자 헤더가 호출자에 그대로 전달 | 사전 실측 · 공식 [1] |
| 받는 쪽에서 행위자 권한 확인 | `asUser()` 불가(세션 없음). asApp `user/permission/search?accountId=` 200(0.4~0.6초). asApp `permissions/check`+accountId는 403 | 사전 실측 |
| Marketplace 영향 | dynamic webtrigger·egress로 Runs on Atlassian 실격 | 공식 [3] · 배포 도구 출력 |

"사전 실측"은 본 개발 전에 시험용 앱 두 개를 같은 사이트에 설치해 측정한 결과입니다.

### 6.2 요청 한 건이 거치는 12단계

요청은 `POST {상대 URL}`, 헤더 `x-moves-link-sig: <Ed25519 서명 86자>`, 본문은 JSON 원문입니다.
서명 대상은 `"moves-link-rpc/1\n" + 본문 원문 바이트`입니다. 재직렬화하지 않으므로 정규화 차이가 없고, 접두 문자열이 다른 용도의 서명과 섞이는 것을 막습니다.

```json
{ "env": { "v":1, "linkId":"<연결 id>", "op":"org.teams", "from":"approval", "to":"workforce",
           "cloudId":"<사이트>", "kid":"ap-dev-1", "iat":1792476027960, "nonce":"<22자>",
           "actor":{"type":"USER","accountId":"<보낸 사람>"} },
  "data": { … } }
```

> 🖼️ (기존 검증 단계 그림 유지)

| 단계 | 검사 | 실패 시 | 데이터 접근 |
|---|---|---|---|
| 1 | POST, 본문 ≤ 256KB | 405 / 413 | 없음 |
| 2 | JSON 형태, `to`=수신 앱, `from`=상대 앱 | 400 `MALFORMED` | 없음 |
| 3 | 발급 시각 ±120초 | 401 `STALE_REQUEST` | 없음 |
| 4 | 서명 키 ID가 신뢰 목록에 있음 | 401 `UNTRUSTED_KID` | 없음 |
| 5 | Ed25519 서명 | 401 `BAD_SIGNATURE` | 없음 |
| 6 | `cloudId` = 현재 설치 사이트 | 403 `SITE_MISMATCH` | 없음 |
| 7 | 작업이 그 방향의 허용 목록에 있음 | 400 `OP_UNKNOWN` | 없음 |
| 8 | nonce 재사용 아님 | 409 `REPLAYED` | 없음 |
| 9 | 연결 상태 `PAIRED`, 같은 `linkId` | `NOT_PAIRED` / 409 `STALE_LINK` | KVS |
| 10 | 라이선스·연동 스위치 | `LICENSE_INACTIVE` / `LINK_DISABLED` | KVS |
| 11 | 행위자 정책(사람 필수 여부, 시스템 작업 사유 허용 목록)·요청 스키마 | `ACTOR_NOT_ALLOWED` / `MALFORMED` | 없음 |
| 12 | 행위자 실재·활성 확인 후 그 행위자 기준으로 처리 | 작업별 코드 | DB |

**1~8단계는 DB·KVS에 접근하지 않습니다.** 위조 요청은 여기서 끝나므로 데이터 노출도, 저장소 비용도 없습니다.
호출하는 쪽도 응답의 서명·시각을 검증하고, 응답이 **자기가 보낸 nonce에 대한 답인지**(`re`)와 `from`·`to`·`linkId`·`cloudId`·`op`를 대조합니다. 이전 응답을 끼워 넣는 공격을 막습니다.

### 6.3 행위자 기준 처리

**보내는 쪽** — `ChannelClient`에는 accountId 인자가 **아예 없습니다**. resolver가 연 실행 범위에서 플랫폼이 준 사용자 ID만 읽어 봉투에 넣습니다. 화면이나 요청 값으로 다른 사람을 사칭할 수 없습니다. 보내기 전에 보내는 앱의 권한 가드와 asUser 확인을 이미 통과한 상태입니다.

**받는 쪽** — webtrigger에는 사용자 세션이 없으므로:

- **Approval**: asApp `/user?accountId`로 실재·활성을 확인합니다. 이슈가 걸린 작업은 asApp `user/permission/search?accountId=actor` 결과가 **정확히 `[actor]` 한 명일 때만** 허용합니다(빈 목록·여러 명·오류·시간 초과는 거부). 그다음 기존 DB 규칙(작성자 본인·담당 팀장·관리자)으로 범위를 좁힙니다. 조회 결과는 허용/거부 판정에만 쓰고 응답·로그로 내보내지 않습니다.
- **Workforce**: 자체 권한 세트(DB)로 판정합니다. Jira 관리자 판정·이름 조회처럼 asUser가 필요한 단계는 채널 경로에서 건너뜁니다. 이 생략은 **범위를 좁히는 방향으로만** 작동합니다.

**사람 없는 요청**(트리거·큐)은 `actor:SYSTEM`과 미리 정한 사유 목록만 쓸 수 있고, 대상은 서버가 Jira 데이터로 정한 1건(또는 캐시 무효화)으로 제한됩니다.

**작업 기록 설명 원문**은 작성자 본인 경로에서만 실어 보냅니다. 팀장에게는 시간·일자·이슈만 갑니다.

### 6.4 연결 코드와 키 관리

> 🖼️ (기존 연결 순서 그림 유지)

- 형식 `MLNK1.<payload>.<서명>`. payload = 앱·환경·사이트·자기 URL·linkId·일회용 pin·만료(30분).
- 코드에 비밀 값(pin)이 들어 있으므로 화면은 **복사만** 제공하고, 로그에는 해시만 남깁니다.
- 순서: A가 코드 생성 → B가 붙여 넣고 서명·사이트·만료 확인 → B가 A에 `pair.complete{pin, B의 URL}` → A가 pin 확인·저장 후 서명 응답 → B 저장.
- 서명 키: 앱마다 Ed25519 한 쌍. **비밀 키는 Forge 암호화 환경 변수**, 공개 키는 두 앱에 내장된 키 목록, 신뢰 범위는 환경 변수로 지정합니다.
- 상대 URL은 KVS에만 저장하며 화면·로그에 남기지 않습니다.

### 6.5 Forge 공식 제약과 대응

| 제약(공식) | 대응 |
|---|---|
| 플랫폼 인증 없음 — URL을 알면 누구나 호출 [1] | Ed25519 서명·사이트·연결 ID·시각·재전송 검사로 직접 인증(§6.2) |
| webtrigger 안에서 asUser 불가 | asApp으로 행위자 권한 조회(§6.3). 기존 서비스 재사용 시 asUser 단계 생략 |
| dynamic은 Runs on Atlassian 실격 [3] | 서명 응답에 dynamic이 필수 → 실격 수용 |
| 첫 dynamic webtrigger 추가 = major 버전 | 이미 major 배포(고객 재동의 1회). 이후 같은 모듈 유지 |
| `urlFormat` 기본 v1, 새 트리거는 v2 권장 | 현재 기본값. URL은 설치마다 다르다는 전제로 연결 시 교환. 형식 변경 시 재연결 계획 필요 |
| 실행 시간 최대 55초, webtrigger는 `timeoutSeconds` 지정 불가 | 핸들러 자체 6초, 호출자 대기 8초로 제한 |
| 요청 본문 최대 5MB | 수신 1단계에서 256KB 제한, 작업별 상한·커서 |
| 호출 한도: 설치당 분당 7,000·초당 300, 사용자당 분당 1,200. webtrigger 자동 재시도 없음 | 플랫폼 429는 즉시 재시도하지 않고 5xx만 재시도. 위조 폭주는 한도를 소모할 수 있으나 DB 비용 0 → URL 교체로 대응 |
| 외부 요청 한도: 호출당 분당 100, 앱당 분당 50,000 | 화면 1회당 채널 호출 1~수 건 |
| 함수 결과 형식이 틀리면 500 | 서명 실패 시에도 최소 JSON 응답 |
| CLI URL 생성은 설치 관리자만 | 런타임 `getUrl`로 자동 생성 — 고객 CLI 불필요 |
| (제안) HMAC 인증 webtrigger RFC-141 | 미사용. 정식 출시 시 추가 적용 검토 |

## 7. 검증 — 방법과 결과

### 7.1 자동 테스트

- **공유 계약**: 고정 서명 예제(테스트 벡터), 봉투 검증 단계별 거부, 두 앱 공유 파일 바이트 일치.
- **서버**: 단계별 거부와 서명 응답, 행위자 정책, 동시 연결 경쟁 상황(원자적 상태 전이).
- **채널 경로 고정**(2026-10-20 추가): 중첩 실행 범위에서 채널 표시 유지, 채널에서 asUser 단계 생략, KVS의 없는 키 처리.

### 7.2 보안 실측 — 공격자 관점

두 앱을 개발 사이트에 실제 배포·연결한 뒤, 외부 스크립트로 상대 URL에 직접 요청을 보냈습니다.

| 공격자가 가진 것 | 시도 | 결과 |
|---|---|---|
| **URL만**(키 없음) | GET, JSON 아닌 본문, 300KB, 방향 뒤집기, 시각 ±10분, 모르는 키, 서명 없음·위조, 사람 사칭, 다른 사이트, 위조 40건 동시 — 두 앱 모두 | **전부 거부**(405/400/413/401/403). 거부 응답은 코드만, **DB 흔적 없음** |
| **서명 키까지**(시험 키를 잠시 신뢰) | 재전송, 서명 후 변조, 다른 사이트, 다른 연결 ID, 오래된 시각, 모르는 작업, 허용 안 된 시스템 사유, 없는 사람 사칭, 스키마 밖 필드 | **전부 거부**. 시험 키 제거 후 `UNTRUSTED_KID` 확인 |
| 공격 직후 | 정상 연결 확인 | Approval→Workforce 0.8초, Workforce→Approval 2초 — 정상 |

> 의미: 서명 키가 새는 최악의 경우에도 **다른 사이트, 다른 연결, 존재하지 않는 사람, 허용 목록 밖 작업으로는 넘어갈 수 없습니다**. 키 유출 시에는 §5 키 교체 절차로 무력화합니다.

### 7.3 기능 실측 — 화면 검증

실제 화면을 조작하면서 브라우저가 받은 서버 응답도 확인했습니다. 판정 기준은 "그 데이터가 상대 앱에서만 나올 수 있는가"입니다.

| 작업 | 확인 내용 | 결과 |
|---|---|---|
| 연결 | 양쪽 설정 화면 "연결됨"·상대 버전 | 통과 |
| `org.teams` | Approval 설정 › 팀의 "워크포스에서 받은 팀" | 통과(수정 후) |
| `org.get` | "내 Workforce 결재자 구성"의 팀·팀장 | 통과 |
| `link.resolve`·`kb.get` | 연동 이슈 Work log 탭: 연동 판정, 하루 480분·근무일 22일 | 통과 |
| `flows.list` | Workforce 작업 관리 › 승인 설정 | 통과(수정 후) |
| `cert.query` | Workforce My Work 달력의 승인 잠금·확인 중 시간 | 통과 |
| `issue.control` | 승인된 기록 모달 "승인됨·수정 불가" | 통과 |
| `write.judge`→`write.commit` | Workforce에서 1시간 입력 → `signed:true` → Approval에 "승인 대기" + 승인 요청 자동 생성 | 통과 |

> 🖼️ (기존 화면 캡처 6장 표 유지: 승인 앱 연결됨 / 워크포스 연결됨 / 워크포스에서 받은 팀 / 연동 이슈 판정 / 워크포스 입력 / 승인 앱 "승인 대기")

**실측에서 발견해 고친 결함 2건** — 단위 테스트로는 드러나지 않았던 문제라 기록합니다.

1. Workforce 관리자도 팀 목록 조회를 거부당함 → 채널이 재사용한 기존 서비스 안의 asUser 호출(Jira 관리자 판정·이름 조회)이 webtrigger에서 실패. 채널 경로에서 해당 단계를 건너뛰도록 고치고 테스트로 고정.
2. 팀장 이슈 설정이 하나도 없으면 목록 조회·연동 판정 실패 → KVS `batchGet`이 없는 키를 실패 목록(`KEY_NOT_FOUND`)으로 반환. 이 코드만 "없음"으로 처리.

### 7.4 운영 배포 전 확인할 항목

| 항목 | 왜 필요한가 | 확인하지 못했을 때의 대응 |
|---|---|---|
| 운영 환경 webtrigger 도메인 | egress 선언·URL 검사 정규식 확정 | 도메인에 맞춰 선언만 수정(설계 변경 없음) |
| egress 와일드카드 허용 여부 | 설치 환경마다 다른 호스트 | 호스트를 정확히 명시 |
| webtrigger의 라이선스 정보 | 유료 설치 판정(10단계) | 마지막 화면 호출의 라이선스 판정을 저장해 사용 |
| 권한 없는 활성 계정의 권한 조회 응답 | 거부 코드 세분화 | 현재도 "정확히 본인일 때만 허용"이라 안전 쪽(거부) |
| 권한 여러 개 동시 조회의 의미 | 호출 수 1회 vs 3회 | 권한마다 1회 조회 유지 |

## 8. 용어

| 용어 | 뜻 |
|---|---|
| webtrigger | Forge 앱이 외부 HTTP 요청을 받는 창구. dynamic은 응답 본문·헤더를 앱이 정할 수 있는 종류 |
| Ed25519 | 공개 키 전자 서명 방식. 비밀 키로 서명, 공개 키로 검증 |
| 행위자(actor) | 요청을 일으킨 실제 사용자. 사람이 없는 자동 작업은 `SYSTEM` |
| nonce | 요청마다 새로 만드는 일회용 값. 같은 요청을 다시 보내는 공격(재전송)을 막음 |
| fail-close | 확인할 수 없으면 허용하지 않고 보류하는 원칙 |
| egress | 앱이 외부 주소로 나가는 호출. manifest에 미리 선언해야 함 |
| Runs on Atlassian | Atlassian 밖으로 데이터를 보내지 않는 앱에 주는 Marketplace 배지 |
