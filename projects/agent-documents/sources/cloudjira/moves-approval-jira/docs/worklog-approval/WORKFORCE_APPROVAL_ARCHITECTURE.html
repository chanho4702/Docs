워크로그 승인·잠금 연동 아키텍처

무엇을 어디에 저장하고, 어떻게 인증하며, 승인 후 어떤 로직으로 잠그는지 설명합니다.

Jira 프로퍼티는 두 앱 사이의 서명된 교환 문서입니다. 실제 작업시간은 Jira worklog에, 승인·잠금 판단과 감사의 원본은 Approval SQL에 저장합니다.

Workforce → Approval

movesRms.org: 팀·팀장

movesRms.policy: 연동 범위 신호

movesRms.issue: 이슈별 작성 기간·자동 요청·결재선

Approval → Workforce

movesApproval.ctl: 병합된 쓰기 규칙

movesApproval.cert.YYYY-MM: 건별 승인·확정 시간

movesApproval.YYYY: 기간 승인·마감 상태

원본과 사본

프로퍼티는 서명 검증 후 사용하는 projection입니다.

승인 요청·결정·인증·변경 이력은 Approval SQL의 append-only 원장에 남습니다.

범위 원칙: Jira project(스페이스)와 Workforce project는 같은 식별자가 아닙니다. 한 스페이스의 이슈가 여러 Workforce project에 나뉘어 연결되면 최종 정책과 연결 정보는 issue 단위로 게시합니다. project property는 전체 스페이스가 하나의 Workforce project에 무필터로 연결되어 모든 이슈에 같은 규칙을 적용할 때만 공통 문서로 사용합니다.

작성 → 승인

승인 결과 게시 → 수정 제한

ALLOW

Workforce가 wr와 승인 상태로 허용한 입력을 Jira에 저장합니다.

DENY

금지 조건이면 저장하지 않습니다. Approval 수정·삭제도 현재 SQL 승인·기간 상태를 다시 검사합니다.

DEFER

사전 승인·이슈 예외·불량/만료 문서 등 Workforce가 확정할 수 없으면 저장하지 않고 Approval로 연결합니다.

건별 승인은 해당 기록의 수정·삭제를 잠급니다. 기간 승인·마감은 해당 기간의 추가·수정·삭제를 잠그는 별도 조건입니다. 외부 신규 POST의 사전 차단은 따로 검증합니다.

인증은 두 층입니다

Jira 호출 인증

Forge asUser() / 제한된 asApp()

사용자 화면과 조회는 기본 asUser()입니다. 로그인 사용자가 없는 이벤트·큐 게시 등 문서화된 경로만 asApp()을 씁니다.

Forge가 Jira REST 호출 자격증명을 관리합니다. 고객 API token을 두 앱 사이에 전달하지 않습니다. Jira scope·권한·이슈 열람 검사는 별도입니다.

문서 발행자 인증

서명 대상에 cloudId, 문서 종류 typ, 실제 대상 ent가 들어갑니다. 같은 property를 다른 사이트·사용자·이슈·기간으로 복사하면 검증용 바이트가 바뀌어 BAD_SIGNATURE가 됩니다. UNKNOWN_KID, UNTRUSTED_KID, 미래 발행시각, 잘못된 schema도 거부합니다.

서명은 위변조·발행자 확인입니다. 암호화가 아니므로 property에 비밀키·토큰·민감한 설명 원문을 넣지 않습니다. 서명 통과 후에도 팀장 범위, 이슈 열람, 현재 Approval DB 상태를 다시 검사합니다.

API를 열었는데도 내부 연동에 쓰지 못했던 이유

apiRoute를 정의한 것과 상대 Forge 앱이 자동으로 인증되어 호출하는 것은 다른 문제였습니다. 당시 공식 접근 경로는 사용자 동의 기반 3LO였습니다.

apiRoute 개설URL·custom scope 정의
→
관리자 활성화사이트에서 App REST APIs 허용
→
OAuth 3LO사용자 동의·token 교환
→

Approval 승인/변경 이력 GET, Workforce 조직 GET apiRoute상대 앱의 기본 asApp() 자격으로 무설정 호출되는 구조가 아님
관리자가 base URL과 access token을 넣는 조회 UIOAuth callback, refresh token, 자동 갱신, 철회·재동의 운영 미구현

정확한 결론은 “API 통신이 기술적으로 불가능했다”가 아니라, 그 구현만으로 무인·지속적인 앱 간 동기화를 충족하지 못했다입니다. 그래서 별도 App REST API용 3LO 연결 없이 Jira entity property를 읽고 쓰며 Ed25519로 발행자를 검증하는 방식으로 단일화했습니다. Approval의 apiRoute는 현재 manifest에서 제거됐습니다.

Atlassian 공식 App REST API 접근 절차

고객 적용 전에 우려되는 점

높음

Jira 직접 입력 우회

REST·자동화로 마감 기간에 신규 worklog를 만들 수 있다면 “추가 사전 차단” 요구가 남습니다.

확인: 일반 사용자로 POST·PUT·DELETE·visibility 해제 시험. 사후 감지·숨김·삭제와 생성 전 차단을 구분합니다.

높음

승인·통제·게시 사이의 시간차

SQL 승인 완료, Jira visibility 제한, Workforce 결과 반영은 동시에 끝나지 않습니다.

확인: 각 완료 시각과 실패 상태를 기록하고 게시 장애 중 앱 잠금·재시도 수렴을 확인합니다.

높음

혼합 연결 스페이스의 범위 오판

한 Jira 스페이스의 이슈가 서로 다른 Workforce project에 연결된 상태에서 project ctl을 최종 정책으로 쓰면 다른 프로젝트 규칙이 적용될 수 있습니다.

확인: 두 이슈를 서로 다른 Workforce project에 연결하고 issue ctl의 ent.issueId·규칙이 각각 다른지, 한쪽 문서가 없거나 만료됐을 때 project ctl로 허용하지 않고 DEFER하는지 시험합니다.

보완 필요

팀장 전용 일괄 승인

일반 bulkApprove는 현재 지정 결재자 기준입니다. 고객의 “팀장에 한해”와 같지 않습니다.

확인: 팀장 역할과 자기 팀원 범위를 서버에서 강제하도록 보완하고 비팀장·다른 팀 혼합 요청을 거부해야 합니다.

조건부

이력의 완전성

수집 전 변경, 이벤트 누락 사이의 중간 변경, 삭제된 설명 원문과 알 수 없는 actor를 모두 복원할 수는 없습니다.

확인: 생성→2회 수정→삭제의 실제 이력과 UPDATED 건수, changedAt/observedAt을 대조합니다.

높음

서명 키 운영

키는 고객별이 아닌 앱 환경별이므로 유출 영향이 여러 설치에 걸칠 수 있습니다.

대응: 개인키 암호화 저장, 환경 분리, 접근 최소화, 공개키/kid 교체·재게시 절차를 운영합니다.

조건부

서명된 옛 문서와 revision

서명이 맞아도 최신 문서라는 뜻은 아닙니다. 문서별 만료와 revision 후퇴 검사가 필요합니다.

확인: 만료된 wr, 옛 조직 문서, 다른 계정·기간으로 복사한 문서가 허용으로 처리되지 않아야 합니다.

운영 설계

월별 문서 잘림과 SQL 용량

월 인증 목록은 1,000건 및 30,000바이트 예산으로 잘릴 수 있고 보호 원장은 계속 누적됩니다.

삭제된 이슈의 감사 열람

SQL에 근거가 남아도 이슈 삭제·권한 회수 뒤 화면과 내보내기에서 원문 열람을 보장할 수 없습니다.

대응: 삭제 전 내보내기 정책과 삭제 이슈용 감사 보관함 요구를 별도로 확정합니다.

팀장 보고 문안: 서명된 Jira 프로퍼티로 두 앱을 연동하고 승인·감사 원장을 Approval에 보관하도록 구현했습니다. Jira 스페이스와 Workforce project의 범위가 다르므로 혼합 연결은 issue 단위 정책으로 처리하고, project property는 전체 스페이스 공통 규칙에만 사용합니다. 고객 적용 전에는 범위 누락 시 fail-closed, Jira 직접 경로, 팀장 전용 일괄 승인, 비동기 반영 구간, 키 교체와 장기 보존 용량을 수용 시험으로 확인해야 합니다.
