## 2. 승인 대상과 "기록 vs 강제"

| 대상 | 트리거 | Jira 장치 | 강제 수준 |
|---|---|---|---|
| ① 이슈 전환 | 사용자가 전환 버튼 | `jira:workflowValidator`(함수형) — 승인된 요청이 없으면 전환 거부 + 사유 문구 | **강제** (워크플로에 validator 를 붙인 프로젝트 한정) |
| ② 워크로그 | 기간 제출(사용자) 또는 기간 마감 자동 제출 | 이벤트 `avi:jira:{created,updated,deleted}:worklog` + 보정 스윕 | **기록 + 감지.** 승인된 기간이 바뀌면 `CHANGED_AFTER_APPROVAL` → 재승인 요구·알림. 되돌리기는 opt-in(asApp 쓰기, 작성자 표시가 바뀜) |
| ③ 기타 변경 | 패널의 "변경 요청" | 승인 후 앱이 적용 | **요청형** — 최종 결재자 asUser 로 적용(이력 수정자 = 결재자), 직접 편집은 감지·기록만(field-change-approval). 지원 필드 날짜·사용자·우선순위·숫자·단일 선택 |
| ④ 이슈 일반 승인 | 이슈 화면·••• "Request approval" 의 일반 승인 | 없음(앱 내 결재). 요청 이후 수정은 조회 때 changelog 로 판정 | **기록형(강제 없음).** scopeKey `ISSUE:{issueId}` — 전환 승인과 별개 대상이라 동시에 열릴 수 있다. 수정돼도 요청은 산다(표시 + 요청자 재상신) — issue-approval 2026-10-04 |

②의 본질적 제한(어떤 구조로도 사전 차단 불가, 차단하려면 고객이 Jira 권한 스킴에서 워크로그 편집 회수)은 **수용 기준에 문장으로 올린다**(워크포스 v2.1 교훈: 괄호 안에 숨기면 계약 때 터진다).

### 2.0 입력 통제 3층 (2026-10-03 공식 문서 확인)

| 층 | 장치 | 막는 것 | 한계 |
|---|---|---|---|
| 1. 누가 쓰나 | Jira 권한 스킴 "Work on work items"를 **프로젝트 역할**에만 부여 + 워크포스가 참여 인원을 그 역할에 동기화 | 미소속자의 모든 경로(UI·REST) — Jira 자체 권한이라 우회 없음 | 고객 Jira 관리자의 스킴 변경 필요. 시간 조건 없음(참여 기간은 동기화 주기로 근사). team-managed 프로젝트는 권한 스킴을 안 씀(확인 필요) |
| 2. 언제 쓰나 | **`jira:timeTrackingProvider`**(Forge, Preview) — 관리자가 우리 앱을 시간 추적 제공자로 고르면 Jira 기본 "Log work" 버튼·작업 로그 탭이 숨겨지고 우리 화면으로 바뀜 → 마감·승인 기간 입력을 우리 화면이 거부 | 일반 사용자의 Jira 화면 입력 | REST·자동화·모바일·가져오기 경로가 막히는지 문서에 없음(스파이크). 제공자는 사이트당 하나 → **Tempo 와 공존 불가**, 전환 시점 합의 필요 |
| 3. 남은 구멍 | 워크로그 이벤트 + 일일 점검으로 감지 | 2층을 우회한 변경 | 사후 감지·재승인 |

시간 기반 잠금은 권한으로 표현할 수 없다(권한에 기간 조건이 없음). 그래서 2층이 기간 잠금의 본체다.
"Edit/Delete own worklogs" 회수는 우리 화면도 asUser 라 같이 막히므로 기본안에서 쓰지 않는다.

**2026-10-11 개정(worklog-control, 설계 2판·codex 검토 반영):**
- 4층 **수정·삭제의 통제권 이관** — 우리 화면의 수정·삭제는 앱이 현재 DB 상태(본인 작성분 → 통제 작업 중 → 기간 창 → 인증 잠금 → 기간 잠금 → 정책)로 판정한 뒤 asApp 으로 실행한다. 작성은 작성자 보존을 위해 asUser + 서버 op 출처 증명.
- Jira 경로 차단 수단은 **워크로그 visibility 를 앱 역할(`atlassian-addons-project-access`)로 제한**하는 방식을 1순위로 한다(고객 권한 스킴 무변경). 단계: A 기본(진단·쓰기 재설계·기간 창·다른 경로 FLAG) → B 확정분(승인·인증)만 숨김 → C 연동 이슈 전체 숨김 → D 출처 증명 없는 다른 경로 입력 자동 삭제. B~D 는 사이트별 실측 관문 기록 없이는 서버가 저장 거부, D 는 통제 알림(Q130) 준비 전 무조건 거부.
- "Edit/Delete own 회수 + 앱 대행"(PERMISSION_SCHEME)은 선택지로만 남긴다.
- 다른 경로로 **새로 쓰는 것**은 여전히 원천 차단 불가 — 감지·FLAG·인증 시 경고.
- 숨긴 워크로그는 작성자 본인(우리 화면·워크포스 탭)과 팀장 인증 경로에만 asApp 으로 보인다(CLAUDE.md 불변식 8 예외).
- 기간 창(이슈 Start date~Due date): Start date 필드 id 는 사이트마다 달라 관리자가 매핑·표본 검증, 못 읽거나 연동 판정 실패 시 쓰기 거부(fail-close).

### 2.1 ① 이슈 전환 승인 흐름

```
사용자 [완료] 클릭 → validator: 승인 규칙(프로젝트×이슈유형×전환) 일치? 
   ├ 규칙 없음 → 통과
   ├ APPROVED 요청 있고 이슈 상태·대상 전환이 요청과 같음 → 통과 + 요청 CONSUMED
   └ 그 외 → 거부 "승인이 필요합니다 — 이슈 패널에서 요청하세요"
이슈 패널 [승인 요청] → 결재선(규칙 기본값/직접) → 결재 → 승인되면 요청자에게 알림 → 요청자가 다시 전환
```

- **validator 는 함수형만.** 표현식(Jira expression)형은 이슈 프로퍼티를 읽을 수 있어 빠르지만, 이슈 프로퍼티는 이슈 편집 권한자 누구나 쓸 수 있어 **위조된 "승인됨"을 통과시킨다.**
- 자동 전환(승인 즉시 앱이 전환)은 asApp 이 되어 이력 작성자가 앱이 된다 → 기본 꺼짐, 정책으로만.
- 열린 요청 하나 규칙: `scopeKey = TRANSITION:{issueId}:{toStatusId}` — 전환 id 가 아니라 목적 상태 id(전환 id 는 워크플로 교체 시 바뀌어 규칙이 조용히 풀린다. `_workspace/transition-approval/01_architect_design.md` §3.2).

### 2.2 ② 타임시트 승인 흐름

```
대상 = (사용자, 기간)  periodKey = '2026-W40' | '2026-10'   ← 정책 approvalUnit
scopeKey = TIMESHEET:{accountId}:{periodKey}
제출 → 스냅샷 확정(워크로그 id·초·시작일·이슈 → contentHash) → 결재선(팀장[→PM]) → 결정
팀장 화면: 팀 × 기간 매트릭스, 행 = 팀원, [전원 승인](일괄, PIN 1회)
승인 후 워크로그 이벤트 → 해당 기간 스냅샷 hash 불일치 → CHANGED_AFTER_APPROVAL, 재제출 요구
```

- 워크포스 v2.1 이 지적한 대로 **팀×기간 한 행이 아니라 사용자×기간(`approval_subject`)** 이 단위다. 팀 일괄은 그 묶음 결정일 뿐.
- 기간 마감(`period_close`): 마감일 이후 해당 기간 워크로그 변경은 감지 즉시 플래그 + 알림. 우리 화면(워크포스 내 워크로그 입력 포함)은 입력을 막는다.

## 3. 두 가지 동작 모드

| | 단독(워크포스 없음) | 연동(워크포스 같이 설치) |
|---|---|---|
| 팀·팀장 | Jira 그룹 매핑 또는 앱 명부(Confluence 판 명부 이식) | 워크포스 팀·팀장(RFC-204 "팀장=이끄는 팀 구성원") |
| 2단계 승인자(PM) | 프로젝트 역할 매핑 | 워크포스 프로젝트 PM |
| 제한선 | 일·주 최대 시간, 미래 일자, 소급 N일, 마감 후 변경 | + 계획 대비 초과, 참여 기간 밖, 미소속 프로젝트 |
| 승인 결과 사용처 | 이 앱 화면·내보내기 | + 워크포스 원가 "승인분만" 옵션, 내 워크로그·이슈 맵 상태 배지, SAP export 의 승인 상태 열 |

**워크포스 표시 원칙(권장안)**: 워크로그는 승인 여부와 무관하게 **전부 보이고 상태 배지로 구분**한다(미제출·제출·승인·반려·승인 후 변경). 운영 지표(진척·가동률·내 워크로그)는 전체 기준, 원가·정산·SAP 내보내기만 "승인분만" 옵션. 승인 전 데이터를 숨기면 이번 달 화면이 비어 실시간 관리 도구로서의 가치가 사라진다.

모드 판정은 설치 감지가 아니라 **"서명이 맞는 워크포스 게시물이 있는가"** 로 한다(§4). 게시물이 없으면 그 기능만 단독 경로로 떨어진다(부분 장애에 강하다).

## 4. 워크포스 연동 계약 — Jira 엔티티 프로퍼티 + 서명

Forge 앱끼리는 저장소(SQL·KVS)를 공유하지 못하고, 서로의 resolver 를 부를 수도 없다(외부 호출로 우회하면 Runs on Atlassian 배지를 잃는다). **Jira 엔티티 프로퍼티가 유일한 공용 채널**이다. 워크포스는 이미 `movesRms`·`movesRmsLink`·`movesDocs` 이슈 프로퍼티를 쓰고 있다(실측: `src/api/jira/issue/IssuePropertyApi.js`).

### 4.1 위조 문제와 서명

엔티티 프로퍼티는 해당 엔티티 편집 권한자 누구나 쓸 수 있다. 자기 워크로그에 `status: APPROVED` 를 써 넣으면 끝이다. 그래서 **프로퍼티는 운반 수단일 뿐, 신뢰는 서명으로 만든다.**

- 각 앱이 Ed25519 개인키를 `forge variables set --encrypt` 로 보관, 상대 앱은 **공개키를 빌드에 내장**(둘 다 우리 앱이라 가능).
- 서명 대상에 `cloudId` + 엔티티 id 를 넣어 **다른 사이트·다른 워크로그로 복사 재사용**을 막는다.
- 검증 실패 = 없는 것으로 취급(조용히 단독 경로). 감사 로그엔 남긴다.

### 4.2 방향별 게시물

| 방향 | 엔티티 · 키 | 내용 | 쓰는 시점 |
|---|---|---|---|
| 승인 → 워크포스 | **워크로그** `movesApproval` | `{v, status, periodKey, requestId, contentHash, decidedAt, approverKeys, sig}` | 결정·변경 감지 시 |
| 승인 → 워크포스 | 이슈 `movesApproval` | 열린/최근 전환 승인 요약(배지용, 판정엔 쓰지 않음) | 요청·결정 시 |
| 워크포스 → 승인 | 사용자 `movesRms.org` | `{teamKey, leaderKeys, rev, sig}` | 팀·팀장 변경 시(RFC-204 쓰기 4경로) |
| 워크포스 → 승인 | 워크로그 `movesRms.check` | 제한선 위반 목록 `{codes:['OVER_PLAN','OUT_OF_PERIOD',…], sig}` | 워크포스가 워크로그 이벤트를 받을 때 |
| 워크포스 → 승인 | 프로젝트 `movesRms.pm` | PM accountId 들 + sig | PM 지정 시 |

- 워크포스는 `GET /issue/{id}/worklog?expand=properties` 로 워크로그와 승인 상태를 **한 번에** 읽는다(추가 N+1 없음, 미검증).
- 승인 후 워크로그가 바뀌면 워크포스는 현재 값으로 contentHash 를 재계산해 **불일치 = "승인 후 변경"** 으로 스스로 판정한다. 승인 앱의 갱신을 기다리지 않는다.
- **제한선 판정은 데이터 주인이 한다.** 계획·참여 기간·소속은 워크포스가 판정해 게시하고, 승인 앱은 위반 코드를 받아 "예외 승인 단계"를 결재선에 끼운다. 승인 앱이 워크포스 데이터를 흉내 내 재계산하지 않는다.

### 4.3 워크포스 DB 무증가 원칙 (2026-10-02 사용자 목표)

- 승인 데이터의 원본은 **승인 앱의 Forge SQL**(앱마다 설치당 별도 1 GiB)이고, 교환물은 **Jira 엔티티 프로퍼티**(Jira 저장소)에 둔다. 워크포스는 새 테이블·KVS 키를 만들지 않는다.
- 워크포스는 검증만 한다(공개키 내장, 상태 없음). 이미 읽는 워크로그 응답에 `expand=properties` 를 얹는 식이라 추가 호출도 최소다.
- **게시 단위는 워크로그가 아니라 사용자×기간을 기본으로 한다.** 팀장 일괄 승인 1회(50명 × 기간당 워크로그 수십 건)에 워크로그 프로퍼티를 건별로 쓰면 수천 번 PUT → 25초 한도·rate limit. 사용자 프로퍼티 `movesApproval.{yyyy}` 에 `{periodKey: {status, worklogSetHash, decidedAt, sig}}` 를 두면 사용자당 1회. 워크포스는 그 기간 워크로그로 hash 를 다시 계산해 일치 여부만 본다. 사용자 프로퍼티 쓰기가 안 되면(§10) 워크로그 단위 + 큐로 후퇴.

### 4.4 연동의 한계 — "자유롭지는 않다"

| 하고 싶은 것 | 가능 여부 |
|---|---|
| 워크포스가 승인 앱에 실시간 질의("이 팀 10월 승인됐나?") | **불가.** 앱 간 호출 경로가 없다. 게시된 것만 읽는다 |
| 승인 상태로 검색·필터(JQL) | 이슈 프로퍼티만 인덱싱 가능(`jira:entityProperty`). 워크로그·사용자 프로퍼티는 검색 안 됨 → 읽어 와서 걸러야 함 |
| 상대 앱 화면을 내 화면 안에 삽입 | 불가. 상대 앱 전역 페이지로 **링크 이동**만 |
| 즉시 일관성 | 아니다. 게시 실패·지연 가능 → 승인 앱 스윕이 재게시(멱등), 워크포스는 "확인 중" 상태 허용 |
| 큰 데이터 교환 | 프로퍼티 하나당 32KB → 연 단위로 키를 나눔 |
| 한쪽만 설치 | 각자 단독으로 동작. 서명 검증 실패·부재는 "연동 없음"으로 처리 |

## 5. 제한선(가드레일)

| 규칙 | 판정 주체 | 위반 시 (정책 선택) |
|---|---|---|
| 일 최대 시간(예 12h) / 주 최대 | 승인 앱 | 경고 · **예외 승인 단계 추가** · 제출 거부 |

## 8. 데이터 모델 추가 (Confluence 스키마 위에)

```
approval_request      + target_kind, issue_id, transition_id, subject_account, period_key
                        (전환 소비 consumed_at 은 부속 테이블 transition_request 로 옮겼다 — transition-approval 설계 §5.2)

approval_violation    (request_id, code, source 'SELF'|'WORKFORCE', detail_json)       -- 제한선
```

용량 추정 (200명, 주 단위 타임시트, 승인 대상 전환 하루 50건 가정 · 인덱스 포함 ×2 · 실측 전):

| 항목 | 연 건수 | 연 용량 |
|---|---|---|
| 타임시트 요청 + 결재자·이벤트·업무함 행 (요청당 약 2.4KB) | 1.04만 | 약 50MB |
| 전환 승인 요청 (동일) | 1.2만 | 약 60MB |
| 워크로그 스냅샷 — 행 단위(`approval_snapshot`) | 24만 | 약 50MB |
| 〃 — **요청 행 안 압축 JSON(id:초 목록)으로 대체 시** | — | 약 10MB |
| 알림(180일 자동 정리, 상시) | — | 약 25MB |
| **합계** | | **연 약 150MB → 스냅샷 압축 시 약 110MB** |

- 기본 보관 3년이면 330~450MB. 1 GiB 의 절반 이하. 보관 기간 정리·사용량 게이지는 Confluence 판 데이터 관리 그대로.
- **권장: 스냅샷은 별도 테이블 대신 요청 행의 압축 JSON.** 변경 감지에 필요한 건 워크로그 id·초·시작일뿐이라 행으로 펼칠 이유가 없다. 위 표의 `approval_snapshot` 테이블은 이 안이 채택되면 없앤다.
- 가장 큰 변수는 전환 승인 빈도(규칙을 넓게 걸면 선형 증가)와 인원수. 1,000명이면 타임시트 부분이 5배.

## 9. 단계와 기간 (1인 + AI)

| 단계 | 내용 | 기간 |
|---|---|---|
| P0 | 스파이크(§10) | 1주 |
| P1 | 리포·코어 이식, **이슈 전환 승인**(validator·패널·규칙·업무함) | 2~3주 |
| P2 | **타임시트 승인 단독 모드**(기간·제출·팀장 일괄·스냅샷·변경 감지·마감·자체 제한선) | 3~4주 |
| P3 | **워크포스 연동**(서명 계약, 양 앱 게시·검증, 워크포스 원가 "승인분만"·상태 배지) — 워크포스 쪽 작업 포함 | 2~3주 |
| P4 | 요청형 필드 변경, 증명서·내보내기 Jira 판, 안정화·E2E | 2주 |
| | **합계** | **10~13주** |

워크포스 분석의 12~16주(미러형 + REST)보다 짧은 이유: 승인 엔진·업무함·서명이 이미 있고, 워크로그 미러·REST·SAP 는 이 앱 범위가 아니다.
