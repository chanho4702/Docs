# Moves Workforce 연동

Moves Approval은 단독으로 사용할 수 있습니다. 연동은 Workforce가 서명한 팀·팀장·PM·점검 자료를 타임시트 결재에 활용하고, Approval이 서명한 기간 승인 상태를 Workforce에 게시합니다. 두 앱 설치만으로 자동 연결되지는 않습니다.

**2026-10-06 코드 확인 기준:** Approval에는 설정·수신 검증·게시 기능이 있지만 공개키 목록은 비어 있습니다. 확인한 Workforce 소스에서는 이 계약의 송수신 구현과 관리자 연동 메뉴를 찾지 못했습니다. 호환 출시 버전·키 배포·양쪽 실환경 검증이 준비되어야 아래 시험을 완료할 수 있습니다. 이 문서는 준비 절차이며 연동 성공을 인증하는 기록이 아닙니다.

이 연동은 **이미 Jira에 기록한 워크로그의 월/주 타임시트 승인**을 대상으로 합니다. [건별 사전 승인](cloudjira--06-worklog-period-lock.md)의 미등록 입력안은 Workforce에 워크로그로 게시하지 않습니다. 승인된 입력안을 실제 Jira에 등록한 뒤 기존 타임시트·연동 절차를 적용합니다. 점검 정보나 계약의 승인 유형이 미등록 입력안 승인 상태를 전달한다는 뜻은 아닙니다.

## 1. 설치 전제와 담당 역할

같은 Jira Cloud 사이트에 호환되는 두 앱을 설치합니다. 다른 사이트의 게시물을 복사해 연결할 수 없습니다. 공급자에게 양쪽 출시 버전·지원 프로젝트 유형·서명 계약 지원 여부를 확인하세요. 지원 버전 번호는 아직 확정되지 않았습니다.

| 담당 | 준비할 일 |
| --- | --- |
| 사이트 관리자 | 설치·필요한 권한 업그레이드, 시험 프로젝트·계정의 Jira 열람/워크로그 권한, Workforce 팀·프로젝트 자료 |
| Jira 관리자·Approval 설정 관리자 | 적용 프로젝트·자체 팀/팀장·제한선·예외 그룹, 연동 사용 설정, 진단·재게시·시험 기록 |
| 공급자·배포 담당자 | Workforce 송수신 기능, 양쪽 공개키 배포, 환경별 개인키·키 ID·상대 키 신뢰 목록, 플랫폼 권한·스케줄 검증 |

설정 화면에는 개인키 입력·생성·공개키 목록 편집 기능이 없습니다. 공급자가 암호화된 Forge 변수 `MOVES_LINK_SIGNING_KEY`, 키 ID `MOVES_LINK_SIGNING_KID`, 필요 시 `MOVES_LINK_TRUSTED_KIDS`를 준비합니다. 개인키를 문서·티켓에 넣지 마세요. 관리자가 프로퍼티를 임의 작성해도 유효한 서명 없이 연동 자료가 되지 않습니다.

Approval 자체 팀·팀장·예외 그룹을 유지하세요. Workforce의 기존 일반 설정·팀 관리가 이 연동 활성화 메뉴라는 뜻은 아닙니다. 상대 앱 전용 설정 경로는 기능 출시 후 공급자가 안내해야 합니다.

## 2. 데이터 방향과 사용 조건

| 방향 | 자료 | 사용 조건 |
| --- | --- | --- |
| Workforce → Approval | 팀·팀장 (`rms.org`) | 검증 자료에 본인 이외 결재자가 있으면 첫 결재 단계에 사용. 팀장은 검증된 자기 팀원 범위를 조회 |
| Workforce → Approval | 프로젝트 PM (`rms.pm`) | Workforce 위반과 예외 단계 추가 정책이 있을 때 PM 추가. PM이 없으면 예외 그룹 사용. 자체 위반에는 예외 그룹이 필요하며 두 단계가 함께 붙을 수 있음 |
| Workforce → Approval | 워크로그 점검 (`rms.check`) | 계획·소속 등 점검 코드를 자체 제한선과 합침. 점검 지원을 선언한 사용자에게 자료가 없거나 검증 실패하면 점검 누락 위반이 생길 수 있음. Jira가 점검 프로퍼티 자체를 제공하지 않으면 지원 여부 확인 필요 |
| Approval → Workforce | 타임시트 상태 (`approval.timesheet`) | 사용자·기간의 제출/승인/반려/승인 후 변경, 마감·잠금·제출 지문 등을 사용자 연도별 프로퍼티에 게시. 예: `movesApproval.2026` |

일반 이슈·전환·필드 승인 게시와 사전 승인 워크로그는 이 절차의 대상이 아닙니다. Workforce의 수신 검증·표시·원가/정산 반영 기능은 상대 출시·검증이 필요합니다. Approval의 **게시됨**은 상대 반영 완료를 뜻하지 않습니다.

## 3. 설정 화면과 서명 상태

Jira 앱 관리의 **Moves Approval 설정 → 워크포스 연동**, 또는 **Moves Approval 업무함 → 설정 → 워크포스 연동**을 엽니다. 설정 관리자는 업무함 경로를 사용합니다. 일반 요청자·팀장은 관리자 진단 권한이 없을 수 있습니다.

1. **워크포스 연동 사용**을 확인합니다. 스위치 변경은 즉시 저장됩니다. 기본 켜짐이어도 상대 기능·키가 없으면 연동되지 않습니다.
2. **연동 상태**에서 다음 항목을 확인합니다.
3. 준비되지 않은 항목을 공급자가 해결한 뒤 승인 1건 시험을 진행합니다.

| 화면 항목 / 진단 필드 | 의미·대응 |
| --- | --- |
| 서명 기능 / `crypto.available` | **서명 기능 정상**이어야 함. 런타임 자가 시험이며 상대 기능 검증은 아님 |
| 서명 키 / `signing.configured` | 형식이 유효한 개인키·키 ID가 설정됨. 키 ID·공개키 지문 기록. 상대 검증 가능성까지 보장하지 않음 |
| 키 안내 / `signing.inKeyring` | 내장 Approval 공개키와 개인키에서 유도한 공개키가 일치함. **워크포스가 검증할 수 있는 키입니다** 안내가 있어도 같은 키가 상대 출시 버전에 배포되고 신뢰되는지 별도 확인 |
| 신뢰하는 워크포스 키 / `trustedPeerKids` | 수신 검증을 허용한 상대 키 ID 목록. 상대 서명 키 ID가 포함되어야 하며 **없음**이면 정상 수신을 기대할 수 없음 |
| 사이트 정보 / `cloudIdKnown` | 서명을 이 사이트에 묶을 식별정보를 학습함. **확인됨**이 아니면 연동 화면을 다시 열고 재확인. 설치 감지·연결 성공 표시는 아님 |
| 저장소 준비 안내 / `storageReady` | 잠시 후 확인. 오래 지속되면 공급자에게 마이그레이션 확인 요청. 이때 0건을 정상 무자료 상태로 단정하지 않음 |

키 ID·공개키 지문은 문의에 포함할 수 있지만 개인키·PIN·토큰은 보내지 않습니다.

## 4. 게시·수신 진단 읽기

**승인 상태 게시 → 게시 상태 → 정상**은 로컬 게시 전제에 막힌 항목이 없다는 뜻이며 상대 수신 성공·대기열 완료를 뜻하지 않습니다. 꺼짐·서명 키 없음·서명 기능 없음·사이트 정보 없음·저장소 준비 중이면 전제를 먼저 해결합니다.

| 표시 | 의미 |
| --- | --- |
| 대기 N건 | 게시 처리가 필요한 사용자×연도 문서 |
| 실패 N건 | 대기 중이며 실패 시도가 1회 이상인 문서 |
| 반복 실패 N건 | 대기 중이며 실패 시도가 8회 이상인 문서 |
| 게시됨 N건 | 한 번 이상 게시한 문서. 이후 다시 대기/실패 중인 문서도 포함될 수 있음 |
| 마지막 게시·마지막 오류 | 마지막 처리 시각과 오류 단서. 다른 게시 성공 뒤에도 오류가 남을 수 있어 최근 실패·대기 수와 함께 판단 |

카운트는 승인 요청 수가 아니며 서로 겹치므로 합산하지 않습니다. 기존 문서 갱신은 게시 수가 늘지 않을 수 있습니다.

**워크포스 정보 검증**에서 **팀·팀장**, **프로젝트 PM**의 검증 수·검증 실패 수·마지막 검증을 봅니다. 검증 수는 보관 중인 유효 자료 수, 실패 수는 마지막 판정이 오류인 자료 수입니다. 동일 자료가 양쪽에 포함될 수 있습니다. 이미 검증된 조직·PM 자료가 삭제되거나 깨지면 마지막 검증값을 유지할 수 있습니다. 실패가 늘어도 즉시 자체 명부로 바뀐다고 가정하지 마세요. 처음부터 유효 자료가 없거나 결재자를 정하지 못하면 자체 명부를 사용합니다.

**워크로그 점검**은 마지막 확인 시각만 표시합니다. 이 시각이나 검증 0건으로 모든 워크로그의 정상 여부를 판단할 수 없습니다. **내 타임시트**에서 실제 위반·결재 경로를 확인합니다. 수신 조회는 사용자 동작으로 발생하므로 관리자 화면만 열어 상대 자료가 모두 수집되지는 않습니다.

**최근 실패**는 방향(받기/게시)·종류·대상·사유·횟수·마지막 시각을 최대 20개 표시합니다. 대상·시각을 시험 계정과 대조합니다. 전체 장애 이력이나 현재 실패의 전수 목록은 아닙니다.

## 5. 승인 1건으로 단계별 확인

상대 기능·키 준비 후 요청자 A, 팀장 B, 둘 다 볼 수 있는 시험 이슈와 짧은 워크로그, 이미 시작한 시험 기간을 준비합니다. 원가·정산에 영향을 주지 않는 자료를 사용하세요.

1. 관리자 C가 키 ID·지문·신뢰 목록·사이트 상태와 게시/수신 수·시각을 기록합니다.
2. 공급자가 Workforce의 A 팀·B 팀장 자료 게시를 확인합니다. A와 B가 Approval을 각각 열어 본인 자료를 읽게 하고 C가 진단을 다시 확인합니다.
3. A가 **내 타임시트**의 Workforce 팀/팀장 결재 경로를 확인하고 제출합니다. 자체 명부 경로면 유효 팀 자료·본인 이외 승인자·키 신뢰부터 확인합니다. **제출본 보기**에서 내용을 기록합니다.
4. B가 **팀 타임시트**에서 A 제출본을 검토·승인합니다. Approval의 승인 완료·결정 이력을 먼저 확인합니다.
5. C가 연동 화면을 다시 열어 시험 이후 마지막 게시 시각·관련 실패를 확인합니다. 필요하면 공급자가 A 연도 게시물에 **해당 기간 승인 상태**가 있는지 확인합니다. 기존 문서 갱신은 게시 수가 그대로일 수 있습니다.
6. 공급자와 Workforce의 같은 A·기간 수신 검증·표시를 확인합니다. 상대 기능 미준비면 **Approval 게시만 확인 / Workforce 수신 미검증**으로 기록합니다.
7. PM 예외 단계·점검 위반은 별도 시험합니다. 예외 단계 추가 정책과 위반·PM·예외 그룹을 준비해 예상 결재 경로를 확인합니다. 정상 승인 1건이 이 시험을 대신하지 않습니다.

게시 스윕은 5분 주기이며 일부 변경은 약 3분 안정화 대기 후 탐지합니다. 대기열·재시도로 더 늦어질 수 있고 수신 캐시도 통상 5분입니다. 즉시 반영을 보장하지 않습니다. 버전·역할·기간·요청 ID·시각·화면 결과를 기록하고 [심사 안내](cloudjira--13-marketplace-review-guide.md)의 실환경 결과와 구분하세요.

## 6. 재게시 버튼과 범위

원인 해결 후 사용합니다. 성공은 **예약**이며 즉시 Jira 쓰기나 상대 수신 완료가 아닙니다. 연동 꺼짐·서명/저장소 미준비 상태에서는 예약할 수 없습니다.

| 버튼 | 범위 |
| --- | --- |
| 실패분 재게시 | 대기 중 실패 시도가 있는 문서의 횟수·대기 시간을 초기화. 반복 실패 포함. 실패 0건이면 비활성화 |
| 전체 재게시 | 설정 시간대·승인 단위를 기준으로 현재 연도와 직전 연도 문서 재구성 예약. 해당 연도 타임시트 이력 사용자·자체 팀 구성원·검증 조직 자료의 사용자/팀원이 대상. Jira 전체 사용자·모든 과거 연도는 아님 |

사용자·기간 선택 기능은 없습니다. 내용·키가 같으면 쓰기를 생략하며 최초 게시할 내용이 없는 사용자에게 빈 문서를 만들지 않을 수 있습니다. **대상 사용자 수 상한 초과**면 공급자에게 전달하세요. 반복 클릭보다 예약 결과·다음 스윕·대기/실패 상태를 확인합니다.

## 7. 장애 대응과 문의 자료

| 증상·사유 | 대응 |
| --- | --- |
| 키 없음·내장 공개키 경고·신뢰하는 키 없음 | 공급자가 환경별 개인키·ID·양쪽 공개키·신뢰 목록을 맞춰 배포. 스위치·재게시만으로 해결되지 않음 |
| 모르는 키·신뢰하지 않는 키·서명 불일치 | 상대 키 ID·지문·버전·환경·사이트 대조. 임의 프로퍼티 편집 대신 공급자의 유효 자료 재게시 요청 |
| 형식 오류·지원하지 않는 버전·미래 시각 서명·이전 버전 | 공급자가 계약 호환·시각·revision 확인. 과거 자료 복사로 복구하지 않음 |
| 쓰기 거부 / HTTP 401·403 | 공급자가 앱의 사용자 프로퍼티 권한·설치 버전 확인. 연속 거부 시 **Jira 가 사용자 프로퍼티 쓰기를 거부합니다** 표시 가능. 개인 편집 권한만 늘려 해결된다고 가정하지 않음 |
| 게시 실패 / HTTP 429·5xx·네트워크 | 제한·일시 장애 확인 후 자동 재시도 대기. 첫 실패 5분부터 대기가 늘며 8회 이상이면 24시간 간격. 원인 해결 뒤 실패분 재게시로 대기 초기화 가능 |
| 승인했지만 게시 없음 | 사용 설정·키·사이트·저장소·스케줄·대기열 확인. 같은 사용자 연도 문서는 게시 수가 늘지 않으므로 기간 상태·마지막 시각 확인 |
| 게시 정상인데 Workforce 표시 없음 | 상대 수신 기능·버전·Approval 키 신뢰·계정/기간 확인. 상대 구현 준비 전에는 정상 표시를 기대할 수 없음 |
| 사라지거나 바뀜(이전 값 유지)·워크로그 내용과 다름 | 이전 조직값 유지 또는 점검 불일치 가능. 현재 자료·워크로그와 공급자 재게시 확인. 오래된 검증 수만으로 정상 판단 금지 |
| 게시물이 바뀌어 재게시·게시물이 없어져 재게시 | 일일 대조에서 변경·삭제 감지. 원인·후속 게시 결과 확인 |
| 크기 초과·대상 사용자 상한·저장소 준비 지속 | 공급자에게 문서 규모·범위·마이그레이션 점검 요청. 고객이 임의 데이터 삭제하지 않음 |

문의에는 양쪽 버전·환경·사이트, 시각/시간대, 사용자·기간·요청 ID, 게시/수신 화면, 최근 실패 방향/종류/사유/횟수, 키 ID·공개키 지문, 재게시 범위·실행 시각을 포함합니다. 설명·개인정보는 마스킹하고 개인키·PIN·토큰은 제외합니다. HTTP 상태는 공급자 진단으로 확인하며 화면에 모두 직접 표시되지는 않습니다.

## 8. 연동 해제·복구와 데이터 제한

**워크포스 연동 사용**을 끄면 새 게시·수신 검증을 멈추고 자체 명부·제한선을 사용합니다. 기존 Jira 프로퍼티는 삭제되지 않고 진행 중 요청의 결재선을 소급 재작성하지 않습니다. 상대 앱이 남은 게시물을 사용하는지 확인하세요. 자료 삭제만으로는 이전 검증값 유지 때문에 연동 해제를 대신할 수 없습니다.

해제·복구 체크리스트:

- [ ] 자체 팀·팀장·예외 그룹을 준비하고 일반 계정의 새 제출 경로를 시험했는가
- [ ] 진행 중 요청·기존 승인·상대 정산 처리 기준과 변경 전 화면을 기록했는가
- [ ] 스위치를 끄고 새 제출의 자체 명부 경로를 확인했는가
- [ ] 기존 게시물 정리 여부를 공급자와 정했는가(스위치는 삭제 기능이 아님)
- [ ] 복구 전에 호환 버전·키·사이트·권한을 확인했는가
- [ ] 다시 켠 뒤 승인 1건·필요 범위 재게시·상대 수신까지 확인했는가

수신은 사용자 Jira 권한, 배경 게시·대조는 제한된 앱 권한으로 처리합니다. 연동이 이슈 열람이나 다른 팀 접근 권한을 주지 않습니다. 서명은 출처·내용·사이트/대상 결속 검증이며 암호화·비공개 보장이 아닙니다. 프로퍼티의 식별정보·승인 상태·지문은 Jira 공개 범위에 영향을 받습니다. 제한 공개 워크로그의 가시성 차이로 양쪽 지문이 다를 수 있어 승인분 산정도 실환경 확인이 필요합니다.

## 워크로그 정책 계층 안내

워크로그 정책 수신은 typ **rms.policy**, Jira property **movesRms.policy**를 사용합니다. 프로젝트 엔티티와 선택적인 이슈 제약에 별도로 게시합니다. envelope는 `{v:1,typ:'rms.policy',iss:'moves-workforce',cloud,ent:{projectId,issueId?},iat,exp,kid,body:{rev,values,locks},sig}`입니다. values는 sparse override, locks는 해당 values 키별 boolean입니다. 사이트 전용 historyRetentionMonths/approvalUnit/timeZone은 송신하지 않습니다.

서명 메시지는 UTF-8 `moves-link/policy/1\n` + sig를 제외한 envelope의 canonical JSON이며 Ed25519로 검증합니다. WORKFORCE keyring의 신뢰 공개 키와 trustedKids를 구성하고 발행자·cloud·project/issue·5분 미래 skew·최대 30일 TTL·만료·key.notAfter·서명을 함께 맞춰야 합니다. 기본 keyring은 비어 있어 앱을 둘 다 설치하거나 연동을 켜는 것만으로 수신되지 않습니다. 송신 구현과 fixture·키 provisioning·실제 Forge property 지원은 live 검증 전입니다. 개인키를 안내서·이슈·스크린샷에 노출하지 마세요.

프로젝트 관리자가 **Workforce 정책 새로 수신**을 실행합니다. asUser property GET만 사용하고 runtime은 SQL의 마지막 검증본만 읽습니다. 낮은 rev는 STALE_REV, 같은 rev의 다른 body/expiry는 EQUIVOCATION으로 거부합니다. 동일 문서는 UNCHANGED이며 UPDATE하지 않습니다. 잘못된 후보는 마지막 검증본을 덮지 않고 실패 결과만 남깁니다. 실패 후에도 유효한 기존 정책이 계속 적용될 수 있습니다.

FRESH → 만료 뒤 24시간 STALE → EXPIRED 순서입니다. 유예 뒤 unlocked 값은 사이트/로컬 fallback, locked 값은 해당 키와 관련된 쓰기를 막습니다. 잠금 floor보다 강한 로컬 값은 비교 가능한 키에만 허용하며 설명 보관 등 비교 불가 키는 재정의할 수 없습니다.

비용 특성: resolve는 이슈 100개 chunk당 범위 SELECT 최대 3개이고 runtime property N+1은 없습니다. refresh는 최대 이슈 100개, 5개 병렬·20초 예산이며 미처리는 BUDGET_DEFERRED로 다음 수신이 필요합니다. 새 schedule을 추가하지 않았습니다. history가 완전히 꺼지고 인증 추적이 없으면 기존 sweep를 조기 종료하지만 보수적인 활성 힌트와 추적 인증이 있으면 scan이 남을 수 있습니다. 시간 상한 판정의 Jira 조회 비용과 실제 지연은 사이트에서 측정해야 합니다. diagnostics 카운터는 응답 범위이고 Jira 호출은 물리 실측이 아니라 경로 예산입니다.
