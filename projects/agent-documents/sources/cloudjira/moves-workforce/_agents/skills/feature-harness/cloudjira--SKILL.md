# Feature Harness — 기능 설계·구현·검증

요청 범위에 필요한 역할을 선택하고, 계약과 실제 코드가 일치하는 상태로 작업을 완료한다.
작은 수정은 리더가 담당 스킬로 직접 처리한다. 복수 계층 변경은 전문 에이전트에 위임한다.
설계만 요청했다면 설계와 설계 검토까지 수행한다.

## 시작 시 확인

1. `AGENTS.md`(작업 규칙), `CLAUDE.md`(아키텍처), 관련 경험 INDEX와 노트, 실제 영향 파일을 읽는다. runtime은 `manifest.yml`, 명령은 각 `package.json`을 확인한다.
2. `git status --short`와 관련 diff로 기존 변경을 기록한다. 다른 작업자의 변경을 되돌리지 않는다. ignored 하네스는 `rg --files --hidden --no-ignore .agents .codex`로 찾는다.
3. 사용자 목적·완료 조건·영향 범위·이미 받은 권한을 정리한다. 필요한 정보만 질문하고 독립 작업은 계속한다. 허가된 수정에 중간 승인 단계를 추가하지 않는다.
4. 현재 세션에 노출된 도구와 에이전트 타입을 확인한다. 아래 호출 규약은 실제 도구 스키마와 함께 사용한다.

## 에이전트와 실행 규약

에이전트 정의는 `.codex/agents/*.toml`, 스킬은 `.agents/skills/*/SKILL.md`에 있다.

| agent_type | 담당 스킬 | 기본 소유 범위 | 산출물 |
|---|---|---|---|
| `feature-architect` | [feature-design](../feature-design/cloudjira--SKILL.md) | 요구사항·설계서 | `01_architect_design.md` |
| `backend-engineer` | [forge-backend-dev](../forge-backend-dev/cloudjira--SKILL.md) | `src/`, 백엔드 테스트, 필요한 manifest 변경 | `02_backend_report.md` |
| `frontend-engineer` | [forge-frontend-dev](../forge-frontend-dev/cloudjira--SKILL.md) | `static/ui/src/`, `locales/kr/`, `locales/en/` | `02_frontend_report.md` |
| `integration-verifier` | [integration-verify](../integration-verify/cloudjira--SKILL.md) | 검증·보고서, 위임받은 경우만 수정 | `03_verify_report.md` |

- `collaboration.spawn_agent`가 제공되면 `agent_type`, `task_name`, `message`로 호출한다. 메시지에 **목적, 저장소 절대 경로, 읽을 스킬, 작업 디렉토리, 입력, 소유 파일, 완료 조건**을 전달한다. 공유 작업 공간이며 타인의 변경을 보존해야 함을 명시한다.
- `collaboration.send_message`는 실행 중 에이전트에 정보를 전달한다. **유휴 에이전트의 작업 재개는 `collaboration.followup_task`**를 사용한다. 같은 문제의 수정은 기존 에이전트를 재사용한다.
- 모델은 현재 세션 설정을 상속한다. 사용자나 적용 지침이 모델을 지정했을 때만 지원 여부를 확인해 설정한다. 사용할 수 없는 모델 이름을 호출에 넣지 않는다.
- 커스텀 타입이 노출되지 않으면 지원되는 기본 타입에 해당 TOML의 `developer_instructions`와 스킬을 읽도록 전달한다. 위임 도구가 없거나 상위 지침이 금지하면 리더가 같은 계약으로 수행한다.
- 문서에 적힌 다른 도구 이름을 제공되는 도구로 가정하지 않는다. 협업 도구를 `functions.exec` 내부에서 호출하지 않는다.

## 작업 디렉토리와 재개

리더가 영문 kebab-case 슬러그를 정해 `_workspace/<slug>/`를 전달한다.

```text
_workspace/<slug>/
  00_input/requirement.md
  00_status.md
  01_architect_design.md
  02_backend_report.md
  02_frontend_report.md
  03_verify_report.md
```

- `requirement.md`: 목적, 범위, 완료 조건, 가정. 작은 수정은 요청과 변경 파일을 간결히 적는다.
- `00_status.md`: 기준 HEAD와 기존 diff, 작업 디렉토리, 에이전트 ID·상태·소유 파일, 완료/남은 일, 변경된 계약, 검증 명령·결과·당시 변경 범위. 리더가 단계 전환 때 갱신한다.
- 후속 요청은 상태·관련 보고서와 **현재 코드**를 대조한다. 파일 존재만으로 완료를 판단하지 않는다. 오래된 보고서나 에이전트 ID는 그대로 신뢰하지 않는다.
- 같은 기능의 수정은 기존 디렉토리에서 이어간다. 별도 실행이 필요하면 `_workspace/<slug>/runs/<timestamp>/`에 새 산출물을 만든다. 기존 디렉토리를 자동 이동하거나 덮어쓰지 않는다.
- 프론트만 수정하면 현재 백엔드 계약을 읽고 프론트 구현과 영향 경계 검토만 수행한다. 구현 단계 축소가 AGENTS.md의 필수 검증 명령 생략을 뜻하지는 않는다. 백엔드만 수정하더라도 반환 계약이 바뀌면 프론트·내부 서비스 소비자 검토를 생략하지 않는다. 사용자 범위를 넘는 변경이 필요하면 근거를 알린다.

## 실행 흐름

### 1. 설계와 계약

신규 기능·권한·스키마·공용 응답 변경에는 architect가 설계한다. 작은 수정은 리더가 기존 계약을 확인해 기록한다.
계약에는 함수명, 입력/검증, 성공·실패 응답, 권한·데이터 범위, 소비자, 쿼리키·무효화 범위를 포함한다.
리더는 요구사항과 계약을 비교하고 모호한 부분을 해소한 뒤 구현을 시작한다.

### 2. 구현과 인계

기본 순서는 **설계 → 백엔드 → 프론트 → 통합 검증**이다. 해당 변경이 없는 단계는 생략 사유를 기록한다.

- 백엔드 보고서는 실제 함수명·응답 예시·등록/권한 위치·소스 위치·테스트 증거를 포함한다.
- 프론트는 설계와 백엔드 소스를 확인해 실제 응답을 소비한다. 보고서에 소비 훅·필드 경로·쿼리키·i18n merge 결과를 기록한다.
- **계약과 실제 구현이 다르면 어느 쪽이 요구사항을 만족하는지 먼저 판단한다.** 의도한 변경이면 설계·소비자·검증 기준을 함께 갱신하고, 구현 결함이면 구현을 수정한다. 실제 구현이라는 이유로 계약을 덮어쓰지 않는다.
- 독립 모듈은 계약이 확정되고 수정 파일이 겹치지 않을 때 병렬로 위임할 수 있다. 미확정 API에 의존하는 UI는 선행 결과를 기다린다. 리더도 수행할 독립 작업이 있을 때만 추가 에이전트를 생성한다.
- 동시 작업 수는 현재 슬롯 한도에 맞춘다. 번역 merge, lockfile, manifest, 공용 스토어 등 공유 파일과 빌드 출력은 담당자 한 명이 순서대로 갱신한다.

### 3. 검증과 수정

verifier는 설계·보고서를 참고하되 실제 생산자와 소비자 코드로 판정한다. 관련 모듈 완료 시 영향 경계를 먼저 검증하고 최종 변경 상태에서 필수 검증을 마친다.
명령과 증거 규칙은 [검증 절차](references/cloudjira--verification.md)를 따른다.

- 실패는 재현 조건·파일 위치·영향을 담당자에게 전달한다. 수정 후 영향 항목을 재검증한다.
- 필수 선행 단계가 실패하면 그 결과에 의존하는 작업을 진행하지 않는다. 리더가 원인을 해결하거나 범위가 분명한 작업을 직접 인수한다. 독립 작업은 계속할 수 있다.
- 같은 시도가 반복 실패하면 새 근거로 접근을 바꾼다. 횟수 제한만으로 해결 가능한 작업을 미완성 종료하지 않는다.
- 도구/환경 때문에 실행하지 못한 항목은 `미검증`, 확인된 결함은 `실패`다. 둘 다 `통과`로 보고하지 않는다.

### 4. 완료

리더가 최종 diff와 완료 조건을 확인하고 상태·보고서를 갱신한다. 사용자에게 변경 효과, 검증 결과, 남은 제약과 파일 경로를 한국어로 전달한다.
재사용할 교훈이 생기면 경험 Vault에 기록하고 INDEX에 연결한다. 사용자가 제공한 피드백은 다음 수정에 반영한다.
커밋·푸시는 요청받았을 때만 수행한다. 배포·설치는 요청 범위와 기존 권한을 확인해 진행한다.

## 하네스 유지보수 검증

하네스 자체를 수정할 때는 구현 파이프라인 대신 [검증 절차](references/cloudjira--verification.md)의 구조 검사와 [시나리오](references/cloudjira--scenarios.md)를 사용한다. 모델 판단이 필요한 시나리오는 독립 평가가 가능하고 허용될 때 제한된 드라이런으로 확인한다. 구조 검사 통과를 실제 기능 구현 성공으로 보고하지 않는다.
