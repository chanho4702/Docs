# Moves Workforce (Moves RMS) 제품 소개

- 개발사/형태: Dmove Inc. — Atlassian Jira Cloud용 Forge 앱 (Custom UI)
- 런타임: Forge `nodejs22.x` (arm64, 256MB)
- 프론트엔드: React 18 + Atlaskit, 백엔드: Forge resolver + Forge SQL + Forge KVS + Jira REST API
- 설치: Forge CLI(`forge deploy` / `forge install`)로 대상 Jira Cloud 사이트에 배포
- 브랜치 전략: 기능 개발 `RFC-NNN` → 통합 `develop` → 배포 `master`
- 출처: `README.md`, `CLAUDE.md` (본 저장소)
- 정리일: 2026-08-25

## 1. 제품 개요

Moves Workforce(Moves RMS)는 Jira Cloud 프로젝트의 **인력·팀·워크로그·MD/MM·가동률·진척도·비용·간트**를 관리하고 분석하는 Atlassian Forge 앱이다. Jira 자체가 제공하지 않는 "프로젝트 인력이 어떻게 배정돼 있고, 얼마나 일했고, 얼마가 들었고, 언제 끝나는가"를 하나의 화면 체계로 통합해서 보여주는 것이 목적이다.

핵심 목적은 세 가지다.

1. 프로젝트 인력·팀 배정과 워크로그를 한 곳에서 추적
2. MD/MM(공수)·가동률·진척도·비용을 수치화해 분석
3. 간트/WBS 기반으로 일정과 작업 구조를 시각화

이슈/워크로그 원본은 항상 Jira를 진실 소스로 사용하고, 앱은 필요한 결과만 단기 캐시한다 — Jira 데이터와 앱 화면이 어긋나지 않게 하기 위한 설계 원칙이다.

**저장소 구조**
- Forge SQL 13개 테이블 + KVS Custom Entity 12개
- 보안: 중앙 `PermissionMap` + `guardedDefine` 가드, 프로젝트 스코프(`ALL`/`MEMBER_ONLY`/`TEAM_ONLY`), 비용 데이터(`PROJECT_COST`) 별도 분리

## 2. 주요 기능

### 2.1 프로젝트 관리

| 하위 기능 | 설명 |
|---|---|
| 프로젝트 목록 / 칸반 | `/project` — 프로젝트 리스트와 칸반 보드 탭 |
| 프로젝트 대시보드 | 프로젝트 상세 내 `react-grid-layout` 기반 위젯 대시보드, 작업/인력 분석 조망 차트 |
| 인력 | 프로젝트 소속 인력, 급여(투입급여), 작업 배정 하위 탭 |
| 작업관리 | 목록/트리/간트 3종 뷰 전환, 작업 이력은 분석 리포트로 이동 |
| 진척도 · 비용 | 진척도 산식 기반 분석, 프로젝트 비용(인건비) 분석 |
| 캘린더 | FullCalendar 기반 프로젝트 일정 |
| 이슈 관리 | 프로젝트 이슈 뷰 |
| 프로젝트 구독 | 스페이스 단위 구독 시 신규 이슈가 자동으로 프로젝트에 편입 |

### 2.2 인력 / 자원관리 (`/resource`)

- **인력현황**: 전사 인력 카드, 스킬·역할·팀 정보, 인력 360도 프로필 드로어(할당 이슈, 참여 프로젝트, 완수율)
- **프로젝트배정**: 프로젝트↔담당자 N:M 관계도(중복 배정 강조), 프로젝트 내/전사 이중 스코프 후보 테이블 + 배정 실행
- **팀 분석**: 팀별 가동률·인력 분석, 3레이어 관계도

### 2.3 분석 · 대시보드

- **포트폴리오 대시보드** (`/dashboard`): 전사 통합 현황, Time/Scope/Resource 축 재구성, 위젯·토폴로지·필터 시스템
- **프로젝트 상세 분석 리포트**: 이슈 분석 / 인력 분석 / 팀 분석 (상단 조망 차트 포함)
- **가동률·MD/MM 분석**: 이슈별·인력별 MM 분석, 경과기간 기반 가동률

### 2.4 간트 · 일정관리

- `@svar-ui/react-gantt` 기반 이슈 연결 간트 — 폴더 계층, WBS 해제, 이슈 유형 아이콘, 전체화면
- 작업 일괄 적용/제외(부분 업데이트 계약), 상위 지정, 관계 편집
- 트리 뷰는 간트 데이터·계층을 재사용하는 읽기 전용 화면

### 2.5 개인 워크스페이스

| 하위 기능 | 설명 |
|---|---|
| 내 워크로그 | `/myWork` — 앱 기본 진입 화면, 워크로그 입력/조회 |
| 내 일정 | `mySchedule` — 개인 일정 |
| 마이페이지 | `/my-page` — 프로젝트 선택형 개인 대시보드, 참여 프로젝트/작업 요약, 권한 매트릭스 |

### 2.6 백오피스 · 거버넌스

- 사용자 / 팀 / 스킬 / 역할 / 등급 / 프로젝트 상태 / 공휴일 / 설정 관리 (`/backoffice/*`)
- 권한 설정 (`/backoffice/permission`) — 정책 모듈(`ProjectScope`, `ResourceCatalog`, `CostAccess`, `SalaryVisibility`, `TeamAnalyticsScope`, `TeamLeadFieldPolicy`)
- DB 사용량 모니터링 (`/backoffice/storage`) — Forge SQL/KVS 용량 경고, 앱 정지 예방
- 엑셀 업로드(대용량 사용자 업로드는 큐 기반 처리 + 진행률 폴링)

## 3. 누가 필요한가 (타겟 사용자)

| 대상 | 필요한 이유 |
|---|---|
| PM / 프로젝트 관리자 | 진척도·비용·인력 배정을 프로젝트 단위로 한 화면에서 파악해야 함 |
| 팀장 / 리소스 매니저 | 소속 인력의 프로젝트 배정 현황, 가동률, 팀 단위 분석이 필요함 |
| 재무 / 원가 담당자 | 프로젝트 인건비·투입급여를 산정해야 하지만 급여는 일반 인력 데이터와 분리해 접근을 제한해야 함 |
| 실무자(개발자 등) | 본인 워크로그를 기록하고 담당 작업·일정을 확인해야 함 |
| 경영진 / 의사결정자 | 전사 프로젝트 현황을 포트폴리오 대시보드로 요약해서 봐야 함 |
| IT 관리자 / 시스템 운영자 | 권한(역할/스코프) 설정, DB 사용량 모니터링, 백오피스 마스터 데이터 관리가 필요함 |

## 4. 왜 필요한가 (근본 문제)

**Jira 기본 기능만으로는 인력·공수 관리가 안 됨**
Jira는 이슈 트래킹 도구이지, 프로젝트 인력 배정·MD/MM 공수·가동률·인건비를 계산해주지 않는다. 이런 수치는 보통 별도 스프레드시트로 수기 관리되며 Jira의 실데이터(워크로그, 이슈 상태)와 쉽게 어긋난다.

**흩어진 데이터의 통합**
워크로그, 이슈, 인력 배정이 각각 따로 존재하면 "이 프로젝트에 누가 얼마나 투입됐는가"를 답하기 위해 매번 수작업 취합이 필요하다. 이 앱은 Jira 데이터를 원본으로 삼아 인력·공수·비용·진척도를 한 데이터 모델로 묶는다.

**재무 데이터는 보호돼야 함**
급여·원가는 아무나 봐서는 안 되는 데이터다. 권한 가드를 통과했다고 데이터 범위까지 열리는 것은 아니므로, `CostAccess`/`SalaryVisibility` 같은 별도 정책으로 응답 내용 자체를 좁힌다.

**일정은 시각화돼야 함**
이슈 리스트만으로는 프로젝트 전체 일정과 작업 간 관계(WBS)를 파악하기 어렵다. 간트/트리 뷰가 있어야 상위-하위 작업 구조와 진행 상황을 한눈에 볼 수 있다.

## 5. 언제 사용하는가 (실제 사용 시나리오)

- **매일**: 실무자가 `myWork`에서 워크로그를 입력하고, `myPage`에서 본인 작업·일정을 확인한다
- **주간/월간 리뷰**: PM/팀장이 진척도·비용 분석과 팀 가동률을 점검한다
- **프로젝트 착수 시점**: 인력을 배정하고 간트에서 WBS(작업 구조)를 수립한다
- **프로젝트 진행 중**: 작업 배정을 조정하거나 일정을 간트에서 편집한다 (일괄 적용/제외 포함)
- **경영 보고 시점**: 포트폴리오 대시보드로 전사 프로젝트 현황을 스냅샷으로 확인한다
- **조직 개편 / 인사 변동 시점**: 백오피스에서 팀/역할/스킬/권한 마스터 데이터를 정비한다
- **신규 스페이스 편입 시**: 프로젝트 구독 기능으로 스페이스의 신규 이슈가 프로젝트에 자동 반영되는지 확인한다
- **비용/예산 산정 시점**: 급여 정책(등급 밴드/인원별)에 따라 프로젝트 투입 인건비를 산정한다
- **운영 점검 시점**: 백오피스 DB 사용량 모니터링으로 Forge SQL/KVS 용량 경고를 확인한다
