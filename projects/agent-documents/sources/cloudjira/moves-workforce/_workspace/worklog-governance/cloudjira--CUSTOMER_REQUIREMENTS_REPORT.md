## 1. 요약

고객이 명시한 우선순위는 **SAP 연동 → 워크로그 잠금·승인 → 팀 멤버 자동화** 순이다. 세 가지 모두 현재 제품에 없는 기능이며, 이 중 SAP 연동은 월 1회 배치 전달이라 범위가 작고, 잠금·승인은 제품 성격을 바꾸는 큰 기능이다.

| 우선순위 | 요구 | 현재 제품 | 1차 판단 |
|---|---|---|---|
| 1 | SAP 연동 (시간·프로젝트 데이터, 월 1회) | 없음. CSV 수동 추출만 있음 | 월 1회 파일 전달이면 소규모. SAP 측 필드 명세가 선결 |
| 2 | 워크로그 잠금·승인 (팀장 일괄, 팀별, 리뷰어 기록) | 없음 | 큰 기능. 승인 "기록"과 "편집 차단"을 분리해 범위 확정 필요 |
| 3 | 팀 멤버 자동화 (입사·퇴사, Atlassian 조직 반영) | 팀 관리·엑셀 사용자 업로드는 있음. 자동 동기화 없음 | Jira 사용자·그룹 기반 동기화는 가능. Atlassian 조직 단위는 검증 필요 |

## 2. 요구사항 상세

### 2.1 인원 관리

| # | 요구 | 고객 발언 | 현재 제품 | 대응 방향 |
|---|---|---|---|---|
| 1-1 | 입사자·퇴사자 자동 반영 | "팀 멤버 자동화, 이거 핵심" | 사용자 등록·팀 배정은 수동. 엑셀 일괄 업로드는 있음 | Jira 사용자 상태(활성·비활성)와 그룹을 주기 동기화해 팀 구성원을 갱신 |
| 1-2 | Atlassian 조직 반영 | "1순위" | 없음 | Jira 그룹 기준 동기화를 1단계로, Atlassian 조직·팀 단위는 기술 검증 후 결정 |
| 1-3 | 엑셀 조직도 → 팀 import | — | 사용자 엑셀 업로드 있음. 팀 단위 import 없음 | 기존 업로드 기능에 팀 컬럼을 추가하는 방향 |
| 1-4 | 프로젝트와 팀을 따로 관리 | — | **이미 지원.** 백오피스 팀 관리와 프로젝트 인력 배정이 분리돼 있음 | 현행 유지 |
| 1-5 | SAP 인력 데이터 관리 | — | 없음 | 범위 미정. SAP가 인력 마스터인지, 우리 쪽이 마스터인지부터 확인 |

### 2.2 워크로그 거버넌스

| # | 요구 | 고객 발언 | 현재 제품 | 대응 방향 |
|---|---|---|---|---|
| 2-1 | 워크로그 잠금·승인 | "핵심 기능, 무조건 필요" | 없음 | 승인 상태 모델과 팀장 검토 화면 신설. 편집 차단은 별도 판단 (아래 3장) |
| 2-2 | 단순 단계 승인, 팀장 일괄 승인 | — | 없음 | 1단계 승인(팀장)만. 기간(주 또는 월) 단위로 팀원 전체를 한 번에 승인 |
| 2-3 | 팀별 승인 체계 | "팀별 승인 체계가 필요하다" | 팀·팀장 개념은 있음 | 팀장이 자기 팀 구성원의 워크로그만 승인. 기존 팀장 권한 범위 재사용 |
| 2-4 | 승인자(리뷰어) 기록 | "감사할 때 누가 승인했는지" | 없음 | 승인·반려마다 승인자·시각·대상 기간을 기록 |
| 2-5 | 변경 이력 감사 로그 | — | 없음. Jira 기본 이력은 시간값 변화만 남김 | 워크로그 생성·수정·삭제를 이벤트로 받아 이전 값과 함께 보관 |
| 2-6 | 프로젝트 미소속자는 워크로그 작성 금지 | — | 우리 화면은 소속 프로젝트 이슈만 보여줌. Jira 화면 직접 작성은 막지 못함 | 우리 화면은 현행으로 충족. Jira 전체 차단은 고객의 Jira 권한 설정 영역 |
| 2-7 | 월별 계획 초과 알림 (PM 메일) | "메일로 PM한테" | 없음. 계획 대비 실적 비교는 진척도·비용 화면에 있음 | 월 배치로 초과를 판정하고 Jira 알림(메일)으로 PM에게 전달. 앱 자체 메일 발송은 불가하므로 Jira 알림 경로 사용 |
| 2-8 | 퇴사자 데이터 보존 | "Tempo는 퇴사자 데이터가 안 보인다" | 사용자 비활성화 시 이력 조회 동작은 확인 필요 | 비활성 사용자의 워크로그·집계가 계속 보이도록 보장. 현재 동작 점검 후 결정 |

## 3. 핵심 쟁점: 승인은 "기록"인가 "차단"인가

워크로그는 Jira 이슈에 저장된다. 사용자는 우리 앱을 거치지 않고 Jira 화면에서 직접 워크로그를 고칠 수 있다. 이 때문에 승인·잠금 요구는 두 수준으로 나뉜다.

| 수준 | 내용 | 가능 여부 | 비용 |
|---|---|---|---|
| 승인 기록 | 팀장이 기간별로 승인하고, 승인자·시각이 남는다. 승인 뒤 변경되면 감지해 표시·알림한다 | 가능 | 중 |
| 편집 차단 | 승인·마감된 기간의 워크로그를 아무도 못 고친다 | 앱만으로는 불가. Jira에 워크로그 쓰기를 사전에 막는 장치가 없다 | 상. 고객이 Jira 권한 설정에서 워크로그 편집 권한을 회수해야 성립 |

**권장:** 1차 범위는 "승인 기록 + 승인 후 변경 감지·알림"으로 확정하고, 편집 차단은 고객의 Jira 권한 설정 변경을 전제 조건으로 별도 합의한다. 이 구분을 계약 전에 명확히 해야 한다.

## 4. 확인이 필요한 사항 (고객 회신 요청)

1. **SAP 연동:** SAP가 가져가는 데이터 필드 목록과 형식. 파일 전달인지 API 호출인지. 전달 방향.
2. **승인 단위:** 주 단위인지 월 단위인지. 반려 흐름이 필요한지.
3. **편집 차단 요구 수준:** 승인 기록만으로 충분한지, 승인 뒤 수정 자체를 막아야 하는지. 후자면 Jira 권한 설정 변경 수용 여부.
4. **워크로그 작성 제한 범위:** 우리 앱 화면에서만 막으면 되는지, Jira 화면 전체에서 막아야 하는지.
5. **Atlassian 조직 반영:** 조직 단위가 Jira 그룹인지, Atlassian 관리자 콘솔의 조직·팀인지.
6. **퇴사자 데이터:** 조회만 보존인지, 집계·리포트에도 계속 포함인지.
7. **OKR·Outlook:** 실제로 기대하는 기능.
