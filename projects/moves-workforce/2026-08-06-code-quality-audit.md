## 1. 1단계 — 사용자에게 거짓말하던 것들

### 1-1. 실패했는데 "모두 취소되었습니다" ★

기간 워크로그를 여러 건 등록하다 실패하면 이미 등록된 것을 롤백한다.
그런데 **삭제 결과를 확인하지 않고** 안내 문구를 고정으로 띄우고 있었다.

```
등록 실패 → 롤백 삭제 시도 → (결과 안 봄) → "등록된 항목은 모두 취소되었습니다"
```

악질인 지점: **등록을 막은 원인이 대개 삭제도 막는 원인**이다(권한·필드 상태·Jira 측 거부).
즉 롤백이 성공하는 정상적인 경우엔 문구가 맞고, **정작 문제가 생긴 상황에서만 거짓말을 한다.**
사용자는 "취소됐다"는 말을 믿고 화면을 닫고, 잔여 워크로그는 남는다.

→ 삭제 결과를 개별 확인해 안내를 분기하고, **워크로그 캐시를 무효화해 남은 항목이 목록에 드러나게** 했다.

> 롤백·정리·취소 경로는 실패 시나리오에서만 실행되므로 **테스트도 사용자도 거의 밟지 않는다.**
> "실패 처리 코드의 실패"는 구조적으로 발견이 늦다.

### 1-2. 나머지 3건

| 결함 | 증상 |
|---|---|
| `findUserByAccountId` 빈 결과 null 참조 | 없는 사용자 조회 시 `TypeError` 로 끝남 → `USER_NOT_FOUND` 추가 |
| 급여 히스토그램 이상치 제거 후 값 1개 | 구간 폭이 0 이 되어 터짐 → 단일 bucket 반환 |
| query key 인라인 배열 2곳 | `queryKeyContract` 테스트 실패 → `subscriptionKeys.issueTypes/ownership` 팩토리로 교정 |

+ 브라우저 콘솔에 입력·응답을 남기던 디버그 로그 5건 제거.

## 2. 2단계 — 중복 통합, 그리고 합치지 않은 것

### 2-1. 합친 것

- **quick-add bulk 3벌**(Level/Role/Skill) → `addCatalogItemsBulk`
  도메인마다 다른 건 **저장 record 형태뿐**이라 `buildRecord` 로만 주입한다.
  중복 판정과 `added/skipped` 집계는 공유 — 이게 갈리면 화면마다 "몇 건이 추가됐는지"의 **의미가 달라진다.**
- **프로젝트 전체 이슈 수집 루프 3벌** → `fetchAllProjectIssues`
  조회 경로(`getProjectIssuesByFilter`)는 건드리지 않고 **그 위만 감쌌다.**

### 2-2. 파일을 일부러 나눈 이유 ★ (테스트가 구조를 결정한 사례)

`fetchAllProjectIssues` 를 `IssueApi` 안에 두지 않고 별도 파일로 뺐다.

```
소비 서비스 테스트가 IssueApi 모듈 **전체**를 mock 해서 `as` 전달을 검증한다
  └ 같은 모듈에 새 함수를 두면 그 함수도 함께 mock 된다
      └ 검증이 자기 자신을 mock 한 채 통과한다 (무력화)
```

**모듈 단위 mock 은 그 모듈에 새로 들어오는 코드까지 조용히 삼킨다.**
"어디에 두는 게 자연스러운가"보다 "여기 두면 무엇이 검증되지 않게 되는가"가 먼저였다.

### 2-3. 합치지 않은 것

- **근무일 산식(frontend/backend)** — 빌드 경계 때문에 파일을 합칠 수 없다.
  대신 **같은 fixture 로 양쪽 결과를 대조하는 동기화 테스트**를 뒀다.
  → 코드를 하나로 만들 수 없으면 **불일치를 감지하는 장치**로 대신한다.
- **frontend quick-add 3벌** — 주입 인자가 6개라 통합 이득이 크지 않다. 남겨 뒀다.

## 3. 같은 날 별건 — Forge 런타임 두 곳

### 3-1. 큐·스케줄 트리거에는 invocation context 가 없다 ★

queue consumer 와 scheduled trigger 는 resolver 와 달리 **context 를 받지 못한다.**
이 경로에서 환경을 못 읽으면 `production` 으로 폴백하는데, 그러면 dev/staging 설치가
License API self-query 로 넘어가고 유효한 `active` boolean 이 없어 `UNAVAILABLE`(= **차단**)로 끝난다.

즉 **fail-closed 정책이 환경 오판과 만나면 개발 환경을 통째로 잠근다.**

→ 런타임이 직접 알려주는 `getAppContext().environmentType` 을 **마지막 폴백**으로 추가.
context/환경변수 경로가 있으면 그대로 우선하므로 기존 판별은 그대로다.

> 배경 실행 경로(큐·스케줄·웹트리거)는 **resolver 가 당연히 갖는 것을 안 가진다.**
> 공통 유틸을 배경 경로에 재사용할 때는 "이 값이 여기에도 있나"를 먼저 확인해야 한다.

### 3-2. "큐에 넣었다" ≠ "끝났다"

전사 재집계는 큐 컨슈머가 전 프로젝트를 훑어 수십 초~수 분 걸리는데, 트리거 응답은
큐 push 까지만 말한다. 기존 코드는 **8초 뒤 딱 한 번 무효화**해서 아직 도는 중의 옛 시각을 다시 보여줬다
(사용자에겐 "눌러도 안 바뀐다"로 보인다).

→ 트리거 시점의 `lastAggregatedAt` 을 **기준선**으로 잡고 값이 바뀔 때까지 15초 간격 폴링.
버튼 로딩은 집계가 끝날 때까지 유지하고, 진행 중에는 옛 시각 대신 진행 문구를 보여준다.

폴링을 붙이며 나온 함정 3개:

- **대기 상한(10분)은 타이머로 건다.** 응답 안에서 검사하면 폴링이 계속 실패할 때
  검사가 **한 번도 실행되지 않아** 버튼이 영영 로딩으로 남는다.
- **완료 판정은 성공 응답에서만.** 실패 응답에는 `lastAggregatedAt` 이 없어 그대로 비교하면
  "값이 바뀌었다"로 오판하고 집계 도중에 폴링을 끊는다.
- **권한·라이선스 거부에는 폴링을 걸지 않는다** — 집계가 시작된 게 아니다.

## 5. 한 줄 정리

**실패 처리 경로의 실패는 아무도 밟지 않는다.** 롤백·취소·폴백은 성공 시나리오에서 조용하고,
정작 필요한 순간에만 거짓말을 한다. 그리고 **모듈 단위 mock 은 그 모듈에 새로 들어오는 코드까지 삼키므로,
"어디에 두는 게 자연스러운가"보다 "여기 두면 무엇이 검증에서 사라지는가"를 먼저 봐야 한다.**
