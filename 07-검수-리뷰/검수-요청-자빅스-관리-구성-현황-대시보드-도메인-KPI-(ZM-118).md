## 2. 🔴 불안한 지점 (여기부터 봐 주십시오)

### 2.1 `MonitoringCoverageService` 리팩터링 — 기존 화면 회귀 위험 ✅ 확인함
조회를 `HostSnapshotReader`(신규 공용 컴포넌트)로 빼고, 판정만 `judge(hosts, includeDisabled)`로 분리했다.
- 판정 로직은 한 줄도 바꾸지 않았고 기존 테스트의 어서션도 그대로다(협력자 목만 교체).
- **실화면 확인 완료**: `/monitoring-coverage`가 정상 렌더되고, 사각지대 건수가 대시보드 작업 큐와 **정확히 일치**한다(템플릿 미연결 2 · 수집 Item 없음 1 · Trigger 없음 4 · Agent 불가 44 · 진단 74 / 제외 2 / 전체 76). 같은 스냅샷을 나눠 쓴다는 설계 의도가 실증됐다.
- 다만 그룹 필터·중지 호스트 포함 토글을 건 상태의 회귀는 확인하지 못했다.

### 2.2 아이템/트리거의 "모집단 이원"이 사용자에게 전달되는가
정의(7,891)와 수집(11,834)은 다른 수인데 한 화면에 같이 있다. 섹션 부제로 구분했지만(`정의 기준 — 관리 대상으로 만들어 둔 것` / `수집 기준 — 호스트에서 실제로 값이 오가는 것`), **이 문구로 충분한지 자신이 없다.** 실사용자가 "왜 두 숫자가 다르냐"고 물을 여지가 남아 있다고 본다.

### 2.3 캐시 무효화를 일부러 하지 않았다
호스트 60초 / 구성물 300초 TTL이고, CRUD 후 무효화를 심지 않았다. 근거는 "모든 쓰기에 무효화를 걸면 결합만 늘고 새로고침 버튼이면 충분하다"인데, **템플릿을 방금 연결하고 대시보드에 왔을 때 최대 5분간 옛 수가 보인다.** 이 판단이 맞는지 봐 주십시오. (`collectedAt`은 항상 화면에 띄운다.)

### 2.4 렌즈 화면 2곳에 탭 컨테이너를 새로 씌웠다
아이템·트리거 렌즈는 원래 탭이 없는 단일 목록이었다. `?tab=` 없으면 목록이 열리도록 해 기존 URL을 보존했지만, **URL에 필터를 많이 싣는 화면이라** 탭 전환 시 필터 리셋 규칙(keyword·offset·status만 비움)이 부족할 수 있다.

### 2.5 규모 상한의 실효성
아이템 정의 전건 스캔에 `app.overview.item-scan-cap`(기본 10만)을 걸었다. dev는 7,891이라 **상한에 걸리는 경로를 실데이터로 밟아 보지 못했다**(단위 테스트로만 검증). 고객사 규모에서 이 상한이 적절한 값인지도 근거가 약하다.

### 2.6 액션 count 10콜 · 아이템 count 10콜의 Zabbix 서버 부하
동시 6으로 묶었고 dev에서는 전부 1초 내지만, **호스트 수천 대 환경에서 이 콜들이 실 모니터링에 영향을 주는지 모른다.**
