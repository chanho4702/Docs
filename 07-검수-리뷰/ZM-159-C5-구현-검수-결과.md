## 중점 확인 요청 1~7 판정

1. **분할 전후 동작 동등성: 불충족.** 완전 종료의 창 경계와 itemid 집합은 타당하고 `getRange` 값 폴백도 유지된다. 그러나 불완전 종료 subset, DESC 최신값, 기존 `List` 소비자의 절단 판정이 달라진다(R1, R2, R6).
2. **정렬 비용: 개선 권장.** 정확한 시간 단조성은 맞지만 비교마다 `Instant.parse`를 반복한다. 동일 clock 행의 legacy 순서는 보장되지 않는다(R6).
3. **예산 선택: 불충족.** 10만은 분할 완주와 양립하지 않고 전역 50만/1만 설정 중 어느 의미도 일관되게 따르지 않는다. type별 누적으로 실제 보유량도 10만을 넘는다(R1, R5).
4. **완전성 전파: 결과형 내부 판정은 타당, 전체 전파는 불충족.** 여러 history type 중 하나라도 불완전하면 전체 불완전인 판단은 맞다. 다만 기존 `querySeries`/`getHistoryByItemids`/`getRange`가 상태를 버린다. `deliveredPoints`는 계산은 일관되지만 현재 사용처가 없다(R2, R5).
5. **상태 기계: 구현은 설계와 일치.** 부분 RAW 폐기와 재시도 순환 방지는 적절하다. 빈 차트·WORST_STATE 의미 변경을 사용자에게 알리지 않는 점은 후속 계약이 필요하다(R8).
6. **호출 수/창 확대: 현 규칙 그대로 승인하기 어렵다.** 하루 상한의 안전성은 단일 itemid에만 성립하고, 서비스 예산과 결합하면 overflow 분할이 막힌다. `scanByIds`·`scanByCursor`·trend 경로의 직접 회귀는 찾지 못했지만, 인터페이스의 20회 제한은 내부 RPC를 세지 않는다(R1, R3, R4).
7. **테스트: 불충족.** 변경 테스트는 통과하지만 production 예산 결합과 주요 회귀 경로를 고정하지 않는다(R7).
