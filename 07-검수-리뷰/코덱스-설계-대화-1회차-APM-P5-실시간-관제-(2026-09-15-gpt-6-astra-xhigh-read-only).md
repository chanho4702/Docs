**핵심 방향에 조건부 동의합니다.** 다만 “전량”은 계측·전송에 성공한 완료 SERVER 스팬의 수신 목표이며, 유실 없는 수집이나 15분 전량 표시를 뜻할 수 없습니다.

### (a) Collector 큐·재시도·메모리 영향

다음 네 가지를 v0에 반영해야 합니다.

1. **분기 앞 비용은 SERVER 스팬 수가 아니라 전체 스팬 수에 비례합니다.**  
   R1의 SERVER 비율 약 13%를 적용하면 SERVER 1,000개/초는 전체 약 7,700개/초에 해당합니다. 필터가 버리기 전에 복제·순회하는 비용을 포함해야 합니다. “1,000스팬/초에 코어 5~15% 추가”는 아직 근거가 없습니다.

2. **`queue_size: 50`은 기본적으로 50배치이지 50스팬이나 50초가 아닙니다.**  
   최대 4,000스팬/배치이면 대기분만 200,000스팬입니다. 500B/스팬 가정 시 **직렬화 크기 환산 약 100MB**이며, 실제 Collector 힙은 별도입니다. 여기에 소비 중 배치·복제본·gzip 버퍼가 붙습니다. 초안의 “수 MB”에는 큐가 빠져 있습니다. [exporterhelper 0.159.0](https://github.com/open-telemetry/opentelemetry-collector/blob/v0.159.0/exporter/exporterhelper/README.md)

3. **재시도 OFF는 유지하되 큐의 바이트·관측 수·체류 시간 예산을 정해야 합니다.**  
   `wait_for_result: false`, `block_on_overflow: false`를 명시하고, 큐 단위를 고정합니다. `timeout: 3s`는 큐 대기까지 포함한 freshness 상한이 아닙니다. 시작값은 **수 초분의 작은 큐**로 두고 R1·R2에서 정하는 것을 권합니다. 큐를 늘려 유실률만 낮추면 오래된 데이터를 “실시간”으로 보냅니다.

4. **저장 경로 보호는 장애 주입으로 증명해야 합니다.**  
   라이브 BE 무응답·429·연결 거부·메모리 압박 중에도 저장 경로의 처리량·지연·중복이 유지되는지 봐야 합니다. 실패하면 우선 큐·동시성·부하를 줄이고, 그래도 분리가 필요하면 **별도 live Collector 프로세스**를 검토합니다. 이 경우에도 최초 분기 지점의 공유 비용은 남습니다.

또한 “같은 processor 이름을 쓰면 상태가 공유된다”는 설명은 수정해야 합니다. 공식 구조상 **processor는 pipeline마다 인스턴스가 생기고 설정을 공유**합니다. 라이브 전용 이름은 설정 변경의 영향을 분리하는 데 유용합니다. [Collector processor 구조](https://opentelemetry.io/docs/collector/architecture/)

### (b) 이중 전송 비용 재산정

**R3 수치로 트레이스 전송량을 환산할 수 없습니다.** R3는 `apm_metric_1m` 14.04M행/일·약 9.6GB/일의 DB 증가량이며, 트레이스 저장은 실측 범위 밖입니다. 라이브를 휘발성으로 구현하면 **이 메트릭 DB에 추가되는 라이브 행은 0**입니다. [R3 §1·§8](../08-%EA%B2%80%EC%A6%9D-QA/R3-APM-Postgres-%EB%B3%BC%EB%A5%A8-%EB%A1%A4%EC%97%85-%EC%A7%88%EC%9D%98-%EC%8B%A4%EC%B8%A1-%28WBS-1.7%29.md)

기존 R1 JSON 캡처를 읽어 SERVER 스팬 64개를 허용 속성 중심으로 재구성한 정적 계산에서는 **평균 약 410B/개**였습니다. events·links·이름·메시지 등을 제거한 결과이며, Collector 실행이나 성능 실측 결과는 아닙니다. 따라서 계획값은 우선 **500B/개, 민감도 범위 400~800B/개로 추정**하는 편이 낫습니다.

| SERVER 스팬/초 | 라이브 관측/일 | 추가 JSON 전송량, 500B 가정 | gzip 5~9배 가정 |
|---:|---:|---:|---:|
| 100 | 8.64M | 4.32GB/일 | 0.48~0.86GB/일 |
| 1,000 | 86.4M | 43.2GB/일 | 4.8~8.6GB/일 |
| 5,000 | 432M | 216GB/일 | 24~43GB/일 |

**모두 추정입니다.** gzip 비율은 R1의 기존 배치에서 가져온 가정이고, 실제 1초 슬림 배치에는 다시 측정해야 합니다.

현재 **샘플 저장 전송량 대비** 증가율은 다음처럼 계산해야 합니다.

`추가율 = SERVER 비율 × 슬림 스팬 크기 ÷ (실효 스팬 보존율 × 저장 스팬 크기)`

예를 들어 SERVER 비율 13%, 슬림 500B, 저장 스팬 1,000B라고 **가정**하면:

- 실효 보존율 2%: **추가 +325%, 합계 4.25배**.
- 실효 보존율 10%: **추가 +65%, 합계 1.65배**.

여기서 실효 보존율은 정상 샘플 설정값이 아니라 **실제로 export된 전체 스팬의 비율**입니다. 오류·느린 트레이스는 스팬 수와 크기도 다릅니다. 초안의 “약 10% 추가”는 **샘플링 전 전체 데이터**를 분모로 삼았을 때 가능한 이야기입니다.

### (c) 별도 EP를 선택할 이유

별도 `POST /apm/otlp-live/v1/traces`와 명시적인 `traces_endpoint`를 권합니다. 해당 설정은 trace용 목적지 URL을 직접 지정합니다. [OTLP HTTP exporter](https://github.com/open-telemetry/opentelemetry-collector/tree/v0.159.0/exporter/otlphttpexporter)

기존 EP의 플래그 방식은 헤더 누락 시 **슬림 전량을 저장 경로로 보내는 사고**, 반대로 잘못 붙이면 **보존할 데이터를 휘발 처리하는 사고**가 가능합니다.

별도 경로에는 ArchUnit 등록 외에 **SecurityConfig·프록시 라우팅·JWT 처리 경계**도 필요합니다. 현재 machine 수신 허용은 `/apm/otlp/**`여서 `/apm/otlp-live/**`에 자동 적용되지 않습니다. [SecurityConfig.java:79](/C:/solutions/moveseye-be-spring/src/main/java/com/dmove/moveseye/config/SecurityConfig.java:79)

## 3. 초안이 놓친 것

### ① “전량”을 보장하는 상류 조건

Collector 이전에 버린 스팬은 복구할 수 없습니다. SDK sampling, 상류 parent의 sampled flag, SDK 큐 초과, 프로세스 종료, 계측 제외 경로가 영향을 줍니다. Java 기본 sampler도 `parentbased_always_on`입니다. 따라서 **“Collector 도달 SERVER 스팬 전체 대상”**과 **“전체 실제 요청”**을 구분해야 합니다. [Java sampler 설정](https://opentelemetry.io/docs/languages/java/configuration/)

또한 SERVER에는 HTTP 이외 RPC도 포함될 수 있습니다. HTTP RED 메트릭과 비교할 때는 HTTP만 대상으로 할지, protocol별로 분리할지 정해야 합니다.

### ② 집계 시간축·늦은 도착·중복

- **도착한 1초의 건수는 완료 TPS가 아닙니다.** 배치가 몰려 도착하면 가짜 급증이 생깁니다. `endTs`로 집계하고, 뒤쪽 몇 초의 집계를 revision과 함께 다시 보내 덮어쓰게 해야 합니다.
- 최신 bucket은 **잠정값**입니다. 지연 허용 구간과 집계 확정 시각을 계약에 넣어야 합니다.
- `retry_on_failure: false`가 중복 없음의 증거는 아닙니다. 상류 재전송·중복 Collector 설정 등을 고려해 **`(traceId, spanId)` 기반 유계 dedup**이 필요합니다.
- 현재 점에는 `spanId`가 없고, 병합 규칙에는 `seq`가 있는데 payload에는 없습니다. `streamEpoch`, `seq`, `dictVersion`, snapshot 기준 sequence를 정의해야 합니다.
- snapshot 생성과 구독 등록 사이의 유실·중복을 막고, **snapshot 다음부터 증분이 이어지는 절차**를 정해야 합니다.

### ③ DB 0회와 기존 컴포넌트 재사용의 충돌

[ApmReceiveTokenService.authenticate:342](/C:/solutions/moveseye-be-spring/src/main/java/com/dmove/moveseye/premium/apm/collector/token/ApmReceiveTokenService.java:342)는 매번 토큰을 조회하며 일부 호출에서 last-seen을 갱신합니다. [ApmRegistrar.resolve:145](/C:/solutions/moveseye-be-spring/src/main/java/com/dmove/moveseye/premium/apm/service/registry/auto/ApmRegistrar.java:145)는 서비스·인스턴스 등록과 갱신까지 수행합니다.

권장 구조는 다음과 같습니다.

- 라이브 hot path: **검증된 토큰·승인된 서비스의 유계 메모리 snapshot 조회**.
- DB 조회·등록·갱신: 기존 관리·수집 경로 및 별도 갱신 작업.
- 캐시 miss·만료·DB 장애: `metadataUnavailable` 등으로 구분하여 거절.
- 토큰 회수·서비스 승인/삭제의 캐시 무효화와 최대 반영 지연 명시.

회수 즉시 반영과 DB 무의존을 함께 원한다면 이벤트 전파까지 포함해야 합니다. “같은 서비스 호출”만으로는 해결되지 않습니다.

### ④ PII 제거는 속성 `keep_keys`로 끝나지 않음

`keep_keys(attributes, …)`는 span 전체를 정리하는 명령이 아닙니다. **span name·status message·events·links·trace state·scope attributes**를 별도로 검사해야 합니다. [OTTL span 필드](https://raw.githubusercontent.com/open-telemetry/opentelemetry-collector-contrib/v0.159.0/pkg/ottl/contexts/ottlspan/README.md)

- 허용한 route·service name·instance id·error.type도 길이와 값 제한이 필요합니다.
- PII 제거 실패 시 `error_mode: ignore`로 원문을 통과시키는 상황을 막아야 합니다.
- BE에서 버리는 것은 **이미 발생한 전송 노출**을 되돌리지 못합니다.
- 현재 `OtlpTracesReader`는 events·links·status message를 읽습니다. 앞에서 `readTree`했다면 나중에 무시해도 JSON 객체 할당은 이미 발생합니다. **라이브 전용 선택적 파싱**의 비용을 따로 산정해야 합니다.
- 본문 바이트 외에 문자열 길이·JSON 깊이·스팬 수·동시 해제 수·읽기 시간도 제한합니다.

### ⑤ 힙은 살아 있는 점 수가 아니라 할당량·최대 동시 점유로 검증

초안 배열의 원시 필드 합은 점당 **33B**입니다. `spanId`와 sequence에 각각 8B를 더하면 49B이므로, 50B 계획값은 가능하지만 사전·인덱스·집계는 별도입니다.

특히 아래 세 항목이 빠져 있습니다.

- **서비스별 사전 할당:** 200서비스에 200k 배열을 각각 확보하면 40M 슬롯입니다. 50B 가정 시 **약 2GB**로, “현재 점 1.2M 이하”와 무관합니다. 전체 allocation을 제한하는 chunk pool 등의 설계가 필요합니다.
- **집계 분포:** 15칸 `long` histogram만 해도 120B입니다. p50·p95를 계속 갱신할 분포를 보유하면서 집계 슬롯 전체를 64B로 잡을 수는 없습니다.
- **snapshot 동시 생성:** 300k점 × 50B는 약 15MB/연결입니다. 50개의 다른 필터가 동시에 재접속하면 직렬화 데이터만 **약 750MB 추정**입니다. 공유·분할·입장 제한이 필요합니다.

검증식은 최소한 다음이어야 합니다.

`기존 Live + 새 점 저장 + 사전·dedup + 집계 + 수신/직렬화 임시 객체 + SSE 큐·snapshot ≤ 전체 Live 예산`

기능별 예산뿐 아니라 JVM의 다른 상주 데이터와 GC 여유도 고려합니다. R3 실패 대안의 **`float → short ms`는 제외**해야 합니다. 표현 범위를 넘어선 장기 요청이 잘려 가장 중요한 장애 데이터가 틀어집니다.

### ⑥ 다운샘플 배지로는 시각적 왜곡을 해소할 수 없음

실제 오류 1%·정상 99%에서 오류는 모두, 정상은 10%만 남기면 화면의 오류 점 비율은:

`1 ÷ (1 + 9.9) ≈ 9.17%`

즉 **실제보다 약 9배 붉은 화면**입니다. 전체 `keepRatio` 하나로는 이 왜곡을 복원할 수 없습니다.

권장 사항:

- 기본 분포는 균등 표본, 오류·느림은 별도 강조 계층.
- 초·서비스·계층별 `observedCount`, `displayedCount`, sampling 정책 제공.
- TPS·오류율·백분위·패턴 계산은 표시 표본과 분리.
- reservoir 교체가 발생하면 단순 append만으로 FE를 동기화할 수 없으므로 **시간 bucket 교체 또는 점 삭제 계약** 필요.
- 브러시 표는 “선택 영역의 표시 표본”임을 명시. 전체 요청 목록으로 표현 금지.
- 정상·느림·오류가 모두 100%인 각 극단에서 메모리 상한 유지.

### ⑦ 브라우저·SSE에서 큰 비용은 초기 진입과 재접속

500k점 상한은 검증 전 허용값으로 보기 어렵습니다. 초기 snapshot의 JSON 파싱·typed array 변환·ECharts 내부 복사·브러시 필터링·표 정렬까지 합쳐 측정해야 합니다.

- `appendData`는 기존 그래픽을 지우지 않으며 `dataset`과 함께 쓸 수 없습니다. [ECharts 공식 API](https://raw.githubusercontent.com/apache/echarts-doc/master/en/api/echarts-instance.md)
- `notMerge` 재생성 때 zoom·brush·선택 상태를 보존할 계약이 필요합니다.
- 느린 writer들이 공용 pool을 모두 점유하면 연결별 큐가 있어도 다른 연결이 굶습니다. 연결별 순서 보장과 쓰기 deadline이 필요합니다.
- 큐 초과 → 연결 종료 → 대형 snapshot 재요청의 반복을 막도록 재접속 backoff·jitter·snapshot admission을 둡니다.
- 숨겨진 탭·일시정지·전체화면 복귀 정책도 정합니다. 시각적으로 멈춘 화면에 “연결됨”만 표시하면 오독합니다.
- **직렬화만 공유될 뿐**, 전송·TLS·복사 비용까지 사용자 수와 무관해지는 것은 아닙니다.

### ⑧ 액티브·리소스 값은 현재 그대로 재사용하면 거짓이 될 수 있음

현재 [LiveBuffer.recordActive:484](/C:/solutions/moveseye-be-spring/src/main/java/com/dmove/moveseye/premium/apm/overview/live/LiveBuffer.java:484)는 서비스의 마지막 관측 하나를 사용합니다.

- 미지원 인스턴스·오래된 관측·재시작을 구분하고 `observedInstances/expectedInstances`, `asOf`를 제공합니다.

- 수평 띠는 정상 polling·고정 지연일 수 있습니다.
- 수직선은 event-time으로 계산해야 배치 전송 효과를 배제할 수 있습니다.
- 1초 p95 몇 개의 회귀에 높은 의미를 부여하지 말고 최소 건수·지속·신뢰도를 요구합니다.
- baseline 계산은 SSE tick과 분리하고 캐시합니다.

화면 표현은 “GC 발생”이 아니라 **“완료 시각 집중 관측 — 원인 확인 필요”**가 적절합니다. 또한 초안의 네 패턴은 JENNIFER 공식 페이지의 네 패턴과 같지 않으므로 우리 휴리스틱임을 명시해야 합니다. [JENNIFER 패턴 소개](https://jennifersoft.com/ko/product/apm/features/)

### ⑫ 운영에서 조용히 틀리는 조건

- **다중 BE:** 브라우저 sticky session만으로는 Collector 배치와 같은 노드를 보장하지 못합니다. 단일 live 노드 라우팅을 배포 조건으로 강제하고 `nodeId`, `startedAt`, `coverageFrom`을 제공합니다.
- **사전:** instance id 앞 8자는 표시용으로만 사용합니다. 내부 식별은 전체 값으로 하고, 인스턴스 사전 상한·ID 재사용 세대를 정합니다.
- **설정 변경:** Collector별 `SLOW_MS`·정상 샘플 비율이 다르거나 옛 yaml이 남을 수 있습니다. “항상 정상 2%”를 하드코딩하지 않습니다.
- **자기계측:** QA에서 MovesEye 수신 요청 자체가 Live에 나타났습니다. 새 live ingest·SSE·자기 메트릭 경로가 관제 트래픽을 증폭하거나 업무 TPS를 오염시키지 않도록 제외 기준이 필요합니다.
- **프록시:** Apache의 `flushpackets`는 공식 문서상 **AJP·FCGI에만 적용**됩니다. HTTP SSE 해결책으로 확정하면 안 됩니다. 실제 프록시 경로에서 측정해야 합니다. [Apache mod_proxy](https://httpd.apache.org/docs/2.4/mod/mod_proxy.html#proxypass)

## 4. 단계·공수 재추정

P3 1일·P4 2일 실적은 반영하되, 이번 작업은 지속 스트리밍·부하·유실·재접속 검증이 추가됩니다. **기존 주 단위 산정에 일정 배수를 일괄 적용하는 방식은 권하지 않습니다.**

아래는 기존 QA 환경을 사용할 수 있고 설계 왕복이 당일 이어진다는 전제의 **달력 기준 추정**입니다.

| 단계 | 착수 순서·완료 기준 | 달력 추정 |
|---|---|---:|
| **R-P5 선행** | R1·R2와 최소 링·브라우저 시제품으로 분기·PII·메모리·snapshot 가능성 확인 | **0.5~1일** |
| **5.1** | 수신 관문·메타데이터 경로·집계/표본 분리·링·snapshot/증분·SSE 유계화·계약 | **1.5~2일** |
| **5.2** | X-View·표본 표시·브러시·점 상세·재접속·필터·진입 부하 검증 | **1~1.5일** |
| **5.3** | 게이지·대시보드·인스턴스별 active·리소스 집계·freshness 표시 | **0.5~1일** |
| **5.4** | 검증 가능한 패턴 휴리스틱·동일 시간 창 기준선·warm-up·오탐 검증 | **1.5~2.5일** |
| **검수·종단 QA** | 두 차례 검수, 장애·부하·권한·재접속 확인 및 수정 | **0.5~1일** |
| **합계** | 5.3b 제외, 반올림 | **약 6~9일** |
| **5.3b 별도** | R5 이후 시작·종료·재조정·호환성 검증까지 | **추가 3~5일 추정**, 제품 지원 결정 별도 |

착수 순서는 **선행 실측 → 5.1 최소 종단 → 5.2 → 5.3 → 5.4**를 권합니다. 5.1에서 확정한 계약으로 5.2·5.3의 화면 작업 일부는 겹칠 수 있습니다. 계절 기준선의 실제 학습에 필요한 시간은 구현 공수와 별개입니다.

### R-P5에서 착수 전 필수인 것

여기서 “착수 전”은 **본 구현·계약 확정 전**이며, 측정을 위한 작은 시제품은 허용하는 구분입니다.

| 실측 | 착수 전 필수 | 보강할 실측 설계 |
|---|---|---|
| **R1 분기·지연·PII** | **필수** | 고정 버전·실제 생성 yaml 사용. 모든 span kind, 구/신 semconv, events·links·name·message·scope에 식별용 민감 문자열을 심어 전송 결과 확인. 앱 완료 ID와 Collector·BE 수신 ID를 대조. 종료→링뿐 아니라 **종료→브라우저 p50/p95/p99** 측정. |
| **R2 Collector 영향** | **필수** | live OFF/ON A/B. SERVER 1,000/초에 실제와 비슷한 CLIENT·INTERNAL 비율을 함께 투입. 라이브 무응답·429·연결 거부 중 **저장 경로 처리량·지연·중복·큐·RSS** 측정. “+20%”의 분모를 코어 사용량·RSS 각각 명시. |
| **R3 링 힙** | **최소 시제품 필수** | 균등 10서비스뿐 아니라 단일 hot service·200서비스·route/instance churn·오류 100%·상한 도달·회전까지. 점당 바이트 외에 **전체 retained heap·할당률·GC·snapshot peak** 확인. 완성 코드로 재확인. |
| **R4 브라우저** | **렌더 방식·상한 확정 전 필수** | 300k/500k 초기 snapshot, 5분/15분, append와 재생성, 브러시·표 정렬, 다중 탭·숨김 복귀·재접속. p95 갱신 비용·최장 정지·브라우저 전체 메모리·입력 반응을 측정. **100ms만으로 합격 선언 금지**. |
| **R5 Java 확장** | **5.1~5.4에는 불필요. 5.3b 착수 전 필수** | 시작→표시 외에 route 미확정·종료 유실·역전·crash·장기 요청·다중 SERVER/trace·지원 버전 호환 확인. 앱 p99 지연과 할당·CPU 측정. |
| **추가: 수신·보안 장애** | **계약 확정 전 설계 필수, 출시 전 실측 필수** | 토큰 저장소 장애·회수·라이선스 만료·미지원 encoding·압축 폭탄·과대 배치·느린 본문·연결 51개·snapshot 폭주·프록시 경유. 500 누출과 저장 경로 영향 확인. |

R1의 `<0.1% 유실`은 정상 상태의 합격선으로 유지할 수 있습니다. 장애 상태에서는 **손실을 숨기지 않고 저장 경로를 보호하는지**가 별도 합격 기준입니다.
